# 句子、命名、術語與知識卡

## 句子與命名

### 句子的槽位

每一句由槽位組成，每個槽位填的是這個領域裡實際存在的東西。這條標準適用於 `content/`、`.claude/skills/`、AGENTS.md 與 `docs/rules/` 的分冊、CLAUDE.md 的所有書面產出。

槽位的完整清單是動作者、動詞、受詞、結果、量詞的範圍、時機與觸發原因。描述操作的句子要填前四格；用到量詞時填量詞的範圍；描述做法、條件句與段落首句另外要寫出時機與觸發原因。規則檔對執行者下的祈使句（「提交前跑……」），動作者就是讀這份規則的執行者，合規；下面「動作者被藏起來」那一種指的是描述句。

- **操作句**的四格：動作者（人、腳本、工具、系統元件）、動詞（執行、轉換、比對、寫入）、受詞（動詞在這個領域裡能作用的對象）、結果（輸出或狀態變成什麼）。判斷標準是受詞是不是動詞在這個領域裡能作用的對象：「遠端一個字都沒有執行」語法完整，而「執行」作用於指令，沒有任何系統逐字執行東西。讀者要先認出這是慣用語、把「字」對回指令、把「一個都沒有」對回零個，再重組，才拿到「遠端沒有執行任何指令」。
- **結果寫成可以觀察到的狀態**：安裝、執行、成功、失敗、沒有回應、回傳哪個錯誤碼。「裝得起來」「跑不動」「被擋住」只說了結果的方向，沒有說出結果是什麼。
- **論斷句、段標、總結句與過渡句**的缺口在名詞裡：本身要求「誰的、什麼的」的名詞（來源、輸出、代價、差別、位置）要把所屬寫在這一句或前一句；形容詞與動詞不直接當名詞用。「錯的來源不只一種，而輸出都不帶訊號」改成「答案錯掉的成因不只一種，而引擎一種都不會報錯」。

同一個標準管以下幾種寫法，寫的當下逐句檢查：

- **動作者填了指令片段**：「`tr -d '\r'` 處理的是行尾」→「腳本裡每一行 `getprop` 的結尾都接了 `tr -d '\r'`，作用是去掉輸出裡的歸位字元」。
- **位置槽位填了指示詞**：「字串比對在這裡會失敗」→「補進來的 `0x0D` 會讓 shell 的字串比對失敗」。
- **量詞的範圍沒有具名**：「徵兆與行尾被改寫完全一樣」沒寫在哪些面向上一樣，而下一節給了分辨方法。範圍在句內具名的（「任何指令」「兩個 md5 完全相同」）合規。
- **動作者被藏起來、時機與觸發原因缺席**：以對象起手的條件句接沒有主詞的祈使（「一個檔案同時對上兩列時，依……來分」）、被動句或「由……」只交代次要動作的動作者、指標當主詞（「這個數字決定」）。寫的順序是誰 → 在讀者工作流程的哪一步 → 做什麼 → 為什麼（「工程師做 code review、查看檔案的修改紀錄時，從版本歷史發現它被幾個不同的需求修改過」）。把審查意見改進稿件時最容易寫出這一種：先把審查意見交代的情形寫進句子，再寫處置。

判定的人不代替句子填槽位：單位要寫在句子裡，從上下文推得出來不算。判斷是是非題「有沒有寫在句子裡」；寫成「推不推得出來」的話，判定的人會替句子補上單位然後放行。

寫的人跟審的人是同一個模型時，審查者會替句子補上作者的意圖，所以這一條在寫的當下判，不等審查。偵測與完整的判讀在 `compositional-writing` 的〈每一句先填槽位再成句〉。依據：[技術文章的每一句寫清楚誰對什麼做了什麼事](/report/command-fragment-as-subject-hides-the-actor/)、[口語的語氣強調寫進文章後變成讀者的解碼成本](/report/spoken-emphasis-is-silent-in-text/)、[名詞要求的「誰的、什麼的」也是槽位，論斷句與段標的省略藏在名詞裡](/report/noun-without-its-owner-passes-the-slot-check/)、[以對象起手的句子：缺少的動作者、時機與觸發原因，審查修正寫出這類句子的成因與偵測方式](/report/topic-first-sentence-drops-actor-and-timing/)。

### 程式碼區塊的引數

句子的槽位檢查走到程式碼區塊就停下來，因為指令沒有主詞也沒有謂語。示範指令有四個位置：工具、子命令、選項、引數。工具與子命令讀者查得到，選項多半有 `--help`，而引數的語意常常只有文章講得出來（路徑為什麼選在這裡、兩個引數哪個是來源、給不給這個引數會讓指令做不同的事），而且它是讀者最常要動手改的位置。

判斷標準：讀者要把這條指令用在自己的機器上，他得改哪幾個位置；每一個要改的位置，文章有沒有說過它填的是什麼。掃描從區塊裡的字面值開始，不從佔位符開始：`<serial>` 自帶「這裡要換」的訊號，`/sdcard/screen.png` 看起來像一個完整可用的答案，讀者與作者都不會停下來。依據：[示範指令的引數要說明，寫成字面值的那些最不像需要說明](/report/literal-operand-hides-the-change-point/)。

### 正文裡的對象用它是什麼來命名

文章裡反覆提到的對象，名字的職責跟程式變數相同：讀者只看到名字就知道它指什麼。「三支」「七步」「第三步」「第五節」「第一級」「前提一」「A 那一列」「A1 與 C」是作者規劃結構時的索引，讀者要回頭翻才知道指什麼。

- **寫的當下就用內容名**：分組用它涵蓋的主題命名（「語意模型」），步驟用動作（「選寫法」），分級用它的判斷標準（「當場報錯」），並排的做法用描述（「日期差自連接」）。段標不帶序號，引用用節名或內容；標題與 slug 裡的計數一起改，舊網址用 `aliases` 保留。
- **成員數不變也要改**：名字是索引時，讀者從中段落進來就讀不懂，跟集合會不會再變無關。
- **作者的編排思路不進正文**：見`content-folders.md`〈目錄頁 `_index.md` 與文章檔的分工〉。
- **介紹另一篇時寫出成員**：在文章結尾、`description`、目錄頁交付欄寫「四個追問、三種寫法」，讀者讀完仍不知道那些是什麼。寫出成員（「用自連接、視窗函數與相關子查詢各寫一次」），數字通常可以拿掉；在這些位置逐句問沒讀過那一篇的人知不知道成員是什麼。
- **連結文字寫完整標題**：`[SQL.13](/backend/01-database/sql/...)` 要讀者點進去才知道講什麼。連結文字會被搬進另一篇文章的句子裡，所以標題要是主旨（見`writing.md`〈標題與段標寫主旨〉）。

作者與同源的審查者（與作者同一個模型、讀過全文的審查者）手上都有那份清單，讀到「第一支」當場解得開，所以這一類要在寫的當下擋；審查時列為必修（「必修」的定義見`review.md`〈理解探針〉末段）。掃描指令在 `compositional-writing` bank 的〈序數、計數與字母代號當名字〉，判讀用變數名稱測試與落點測試。依據：[正文裡的對象要用它是什麼來命名，序數、計數與字母代號是作者腦中的索引](/report/ordinal-labels-are-the-authors-index/)、[摘要另一份內容時寫出成員，計數只告訴讀者清單有多長](/report/counted-summary-delivers-only-the-length/)。

### 先界定一個概念並命名，之後用名字引用

一個概念（一個理論、一種情形、一個案例）要被反覆談論之前，先在一個位置界定它、給它名字，之後每次都用名字指它，跟程式裡把重複出現的運算式抽成變數是同一件事。沒有這樣做的文章有兩種樣子：

- **匿名暫存**：用「一部分」「另一半」「那一側」「這部分」「這件事」承擔一個還沒被命名的概念，讀者要從例子自己歸納那一塊是什麼。
- **重複的運算式**：同一個概念每次出現都換一個描述重講一次，讀者分不出這幾次講的是不是同一件事。

寫法：

- **界定先於命名**：切開一個集合時，第一個位置寫出切分的依據（「判斷時要讀的資訊，機器在那一刻讀不讀得到」），不寫結果（「有一部分交得出去」）。
- **名字依序從三處找**：業界已有的術語（靜態分析、約束、counterexample、test oracle）、文章裡現成的案例名、最後才是描述內容的短語。業界術語同時把讀者接到那個概念在外面的全部文獻。
- **之後只用名字**：段落首句用名字開頭；被切開的整體也要有名字；同一組對象只用一組名字。
- **命名由句子結構完成**：「盲區有兩種，各取一個名字，下文都用這兩個名字」的後半句刪掉之後讀者什麼都沒少，寫成「一個觀察者的盲區分成檢查範圍盲區與位置盲區」，下一句起逐一定義。判讀用刪除測試：刪掉這個子句，讀者少了什麼；「下文把這一串稱為**監控鏈**」帶著所指與名字，保留。

寫的當下與審的時候各問一次：這個概念說不說得出它的名字、界定它的那一句在哪裡；說不出來就先界定並命名，再往下寫。模糊的指代不必決定它指什麼，所以錯的論斷能藏在底下，替它命名時才對不上；命名時決定錯所指，也會把新錯誤寫進文章，所以替換文字裡新出現的關係要回原文核對。這一類讓讀者理解不了那一段，審查時列為必修。掃描在 `compositional-writing` bank 的〈部分與一側當名字〉與〈命名的旁白〉，重複運算式那一種沒有字詞可掃。依據：[切開一個集合之前先寫切分的依據，再替每一塊命名；「一部分」「另一半」是還沒抽出來的變數](/report/unnamed-halves-are-unextracted-variables/)。

### 同義反覆的排比

排比的資訊全部在變動格裡；變動格填的是從話題定義推得出來的描述時，那個子句的資訊量是零。例：一篇講監控的文章把監控分成好幾層（程序存活檢查、資源量測、請求紀錄），並定義「一層的問題盲區是那一層沒有在檢查的那一類故障」。接著寫出「一層的問題盲區，由問另一個問題的層接手」：只讀過那個定義的人就寫得出這一句，句子沒有說出是哪一層接手哪一類故障，讀者不必知道監控有哪幾層也能寫出它，所以它沒有交付任何新資訊。改寫是填上具名的層與故障：「程序還活著而回應變慢這一類，存活檢查看不到，由請求紀錄的延遲欄位看到」。

寫排比之前，先把每個子句的變動格填上具名的對象（元件、人、步驟），填不出名字的子句不進排比。總覽句寫在它所總覽的對象被介紹之前時最容易寫出這一種，那個位置改寫成這組分類帶來、讀者從定義推不出的判斷。自查兩步：定義代換（變動格是否只從話題的定義就推得出來）與語序翻轉（改成動作者在前，句子是否變得明顯空洞）。依據：[排比句的變動格填了話題自己的定義：同義反覆的形態、兩個檢查與改寫方向](/report/parallel-clause-filled-with-the-topics-definition/)。

### 「問題」「回答」與物理動詞

中文的「問題」對應英文的 question、problem、issue、topic，寫成「要解決的問題」時又常常指 requirement。文章的組織軸一旦是「每一層回答一個問題」，之後的自創術語、內容句與總覽句都沿用它，所以這一條在決定大綱時就要做；讀者分不出那個「問題」指故障還是需求時會學錯，審查時列為必修：

- **決定組織軸時**，不拿「X 回答什麼問題」當軸，寫出每一層實際做的動作與對象（確認程序能回應、量測資源用量、記錄請求是否成功）；自創的層名也從這個動作與對象取名。
- **寫下每一個「問題」時**，問它翻成英文要從 question、problem、issue、topic、requirement 裡選哪一個，用那個意思的中文詞寫，並寫出內容（哪裡壞了、要處理什麼、屬於哪個範圍、誰需要什麼）。選不出來時，先決定那句話要講什麼再寫。
- **「回答」換成元件實際做的動作**：執行、量測、比對、送出、標記。
- **合規**：場景裡有人實際提問、業界固定術語（「N+1 問題」）、動詞片語「出問題」。

**物理動詞佔住的內容**：物理動詞寫在抽象對象上時，佔住了一個本來要寫出內容的位置。各族佔住的內容與寫到它時的寫法：

- **撐、扛不住、撐不久、會垮**：最常寫成足夠性斷言，也就是宣稱某個對象足以或不足以滿足某個需求的句子。「單台資料庫撐得住這個流量」沒說在什麼延遲門檻與請求量之下。寫出需求（支持哪個決定、承受什麼負載）、判斷標準（滿足到什麼程度算夠）與機制（靠什麼屬性滿足、在哪一點不再滿足）；換成「足以支持」只是換一個詞佔著同一個位置。系統負載不豁免，「負載」要寫出單位（每秒請求數、同時連線數這類）。
- **掛在、由誰扛**（描述關係的用法）：換成依賴、負責，並寫出依賴或負責的對象。
- **拖垮、壓垮**：寫出失效的形態（變慢、無回應、崩潰）與它從哪個元件傳到哪個元件。
- **硬扛**：寫出誰承擔了哪些工作。
- **站得住**：多半是在替一個論點宣稱可信度。寫出可信度的來源（哪一份證據、哪一次量測）；寫不出來源時刪掉整句。

預先分類用 `python3 scripts/physical-verb-scan.py <檔案或目錄>`（不給引數時掃整個 `content/`，排除 report 與 skills）。

「問題」框架的掃描先找出以「X 回答 Y 問題」組織段落的文章，再在那一篇裡逐處翻譯；單獨的「問題」詞頻太高，不全站直接掃。從命中數最多的文章開始：

```bash
rg -c "回答的問題|回答的是|問的是|問題是：" content/ | sort -t: -k2 -nr | head
```

判讀在 `compositional-writing` bank 的〈「問題」與「回答」當框架詞〉與〈物理化錯配〉。依據：[「問題」與「回答」當框架詞：一個詞蓋住問句、故障、議題與需求，以及系統被寫成應答的一方](/report/question-answer-frame-blurs-problem-issue-request/)、[正反問句嵌進句子當名詞：位置判讀、與高頻句型的撞形，以及謂語要寫出的判斷標準](/report/a-not-a-question-as-noun-clause/)、[描述抽象概念要用貼合屬性的謂語：分析角度不會「說話」、證據不會「撐得住」](/report/word-choice-fits-concept-attributes/)、[物理動詞佔住的內容：撐、扛、垮、掛在、站得住各自要寫出什麼，以及這些詞在負載情境裡的意思](/report/physical-verbs-stand-in-for-content/)。

## 術語與知識卡

### 建卡原則

- 一張卡片只承擔一個語意責任，也就是只讓讀者理解一個概念。名詞跨情境變義時拆卡（見〈拆卡標準〉）。
- **標題以英文術語為主、中文輔助**（如 `Operating Margin（營業利益率）`）：英文社群與學術資料較豐富，而中文譯名在台灣、香港、馬來西亞、中國各有出入，以英文為主才有穩定的檢索與查證錨點。在地產業特有、沒有英文對應的術語以中文為主。
- **建卡看教學需求**：目標讀者群裡最不熟悉這個術語的讀者，缺了它就難以理解教材時，這個術語就值得建卡，即使它目前只在單篇文章出現、即使它不直接驅動某個實作選擇。出現頻率與實作影響只是補充訊號。
- 優先使用情境精確的命名，術語過於寬泛時改寫成具體情境詞，不建傘狀的卡。傘狀詞（「策略」「成長」「轉型」）建不出單一的語意責任：判斷問句是能不能寫出這個詞在本文排除了什麼，寫不出來就是傘狀詞，在文章內直接補情境精確的說明。一個詞在本文指兩個以上的不同對象，是一名多義，照〈拆卡標準〉拆卡，跟傘狀詞是兩件事。

### 拆卡標準

同一個名詞落在下列任一組對比的兩側、且兩側各自承擔不同的語意責任時，拆成兩張卡。每一組各自獨立，命中一組就拆；一張卡同時跨多組時，先拆最影響讀者判斷的那一組。

- transport vs process vs workflow
- durable vs ephemeral
- ordered vs unordered
- replayable vs one-way
- single consumer vs fan-out
- human workflow vs machine protocol
- service boundary vs language boundary

### 術語的解釋方式

術語在文章裡有三種處理：行內展開（在正文第一次出現的位置寫出定義與它在本篇論證裡的作用）、連卡（正文用術語、連到知識卡）、裸用（不解釋也不連）。選哪一種看兩件事：術語在本文的角色，以及它在不在讀者的前置知識裡。

- **主線術語**是本文的核心論證繞著轉的詞；**支撐術語**是論證的某一步要用到、但論證不繞著它轉的詞；**背景術語**是出現在情境描述裡、拿掉不影響論證的詞。
- **前置知識**取的是讀者讀過哪些前置篇章、手上已經有哪些術語，不取讀者的理解能力；把「專業工程師」算進前置知識，會讓它涵蓋整個領域的名詞，缺卡判定永遠不觸發。
- 角色與前置知識的組合怎麼對到三種處理、什麼組合代表缺卡，以 `knowledge-cards` skill 的〈缺卡判定矩陣（速查）〉為準（完整版在它的 `references/gap-audit-and-backfill.md`）；卡不存在時先建卡。卡片是概念索引，章節是決策與情境推導，所以連卡的術語在正文裡只寫它在本篇論證裡的作用，定義留在卡上。
- **承重的術語在自己的主場最容易沒有定義**：承重的術語是本篇論證依賴的術語。一個詞在某一篇是全篇的軸時，作者寫得越多、陌生感消失得越早，停下來定義它的那一刻不會到。偵測工具與用法見`writing-process.md`〈教學文章的脈絡〉裡「論證用得到的材料就地寫進去」那一項。

完整推導見 [術語解釋分層方法論](/record/term-explanation-layering-methodology/)，偵測見 [串連佔掉的是本篇的篇幅，順序要先自足再往外開門](/report/cross-links-eat-the-article-they-live-in/)。

### 譯名避開介面上已有的同名元素

這一條管正文裡由外文概念翻來的術語；產品名、協定名、程式識別字與業界通用的縮寫（HTTP、JSON）不在此列。譯名讓讀者先想到另一個東西，是嚴重的寫作錯誤：讀者照那個意思學錯，而且不會停下來問，因為那個詞他認得。

- **判斷問句**：除了要譯的這個概念，軟體或介面裡還有沒有另一個讀者常碰到的東西也叫這個名字。有的話就違規：cursor 譯成「游標」，讀者想到畫面上的游標；file handle 譯成「把手」，讀者想到拖曳把手；pagination bookmark 譯成「書籤」，讀者想到瀏覽器書籤；short-circuit evaluation 譯成「捷徑」，讀者想到桌面捷徑。
- **不算違規的範圍**：軟體以外的日常意思不構成違規（「旗標」「交易」「鉤子」「管線」「記憶體」在軟體裡沒有另一個東西叫這個名字）。比對的是台灣軟體介面上實際顯示的中文字，英文同名不算（英文 header 另指文書軟體的頁首，而它在台灣介面上叫「頁首」，不能拿來判定「標頭」違規）。日常功能相似不能當合規的理由。
- **修法**：先查對應的知識卡有沒有本站定案的寫法，有就照用；沒有就讓詞面說出功能，自組描述功能的短語（分頁的寫「接續標記（cursor）」、資料庫的寫「查詢結果的讀取物件（cursor）」）；短語說不清就改寫成完整的句子再附英文原詞。英文詞有多個意思就各自譯。替代譯名同樣要過判斷問句，定案後寫回知識卡當全站寫法。
- **術語探針量過、各份給的定義仍收斂不到同一個所指的詞**（test oracle）：第一次出現寫出中文描述再附英文原詞，之後可以沿用英文。沒跑過探針的詞不適用這一條，作者自己判斷「沒有可靠中譯」不算。
- **第一次出現的格式**：寫「中文（original term）」，之後以中文為主；程式識別字與討論英文詞本身時用英文。只寫英文、沒有任何中文說明，等於把翻譯工作交給讀者。既有譯名在其他中文資料裡流通時，附上「其他中文資料常寫作 X」。
- 拿不準時交術語探針（見 `multi-round-review` 的 `references/round-2-probes.md`〈2-B⁶ 術語探針〉）。作者與同源審查者知道那個詞在稿件裡指什麼，讀起來通順，看不出問題，所以審查時逐個譯名確認。
