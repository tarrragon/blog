# `content/` 的資料夾分類、目錄頁與 Backlog

這份分冊管一篇文章放進哪一個資料夾（含概念文章與 `hands-on/` 實作文章的分工）、寫之前要做的查核、目錄頁 `_index.md` 與文章檔的分工，以及模組 Backlog 的規則。

## `content/` 底下的資料夾分類與目錄頁

### 文章放在哪一個資料夾

教學模組（`backend/`、`infra/`、`linux/`、`ddd/` 這類主題資料夾）以外，歸檔用的資料夾各自收錄不同的主題：

| 資料夾      | 收錄的主題                                          | 典型內容                                          | 結構                                             |
| ----------- | --------------------------------------------------- | ------------------------------------------------- | ------------------------------------------------ |
| `posts/`    | blog 本身的規範、設計，以及 Hugo 與 Markdown 的經驗 | mdtools 設計、Markdown 規範、Hugo 與 Mermaid 設定 | 教學或事件紀錄，結構自由                         |
| `work-log/` | 工作中用某個工具或技術遇到的具體問題                | git、Flutter、Gradle、Dart 的個案                 | 事件說明 → 開場 → 推導與驗證 → 判斷標準          |
| `record/`   | 整理過的方法論或工作模式                            | 5W1H 自察、敏捷、acceptance criteria              | 依內容決定                                       |
| `report/`   | 從個案歸納出的工程原則（記下一類缺陷與它的解法）    | 卡片系統，卡號就是 frontmatter 的 `weight`        | 結論、為什麼、反模式、修法、關係、個案、判讀徵兆 |
| `til/`      | 跟工程無關的單一知識點                              | 單字字源、概念由來                                | 一篇一個知識點                                   |
| `other/`    | 跟特定開發專案無關的工具小技巧與雜項技術筆記        | Android 無線除錯設定、工具應用筆記                | 依內容決定                                       |
| `books/`    | 書單與導讀，依讀者的職涯位置分線                    | 各書線的導讀、選書的約束條件                      | 導讀文章加各線目錄                               |

寫一篇文章之前，依序判斷：正文是讀者照著做、從前置條件走到完成的操作步驟（每一步的指令與該看到的輸出），而且連回某個教學模組裡的概念文章 → 那個模組的 `hands-on/`（〈概念文章與實作文章：`hands-on/` 子資料夾〉）；議題屬於某個教學模組的主題、要排進那個模組的章節序列 → 那個模組的資料夾；議題是 blog 內部的設定、Hugo、Markdown 或 mdtools → `posts/`；議題是用某個工具或技術時遇到的事件 → `work-log/`；議題是整理過的方法論或工作模式 → `record/`；議題是從個案抽出可以重用的工程原則 → `report/`；議題跟工程無關、是單一的知識點 → `til/`；議題是跟特定開發專案無關的工具小技巧 → `other/`；議題是推薦哪本書、怎麼選書 → `books/`。`content/skills/` 是 `bin/skill-mirror` 產生的 skill 公開鏡像，不放手寫的文章（見 `skills.md`〈Skill 與文章是兩個 surface〉）。

`work-log/` 與 `other/` 的分界：工作中用某個工具時遇到的事件（有情境、有排查過程）放 `work-log/`；不依附任何一次事件的工具用法放 `other/`。表裡 work-log 那一列的「事件說明」定義在 `writing.md`〈寫給帶著疑問來查的讀者〉。`work-log/` 與 `hands-on/` 的分界看正文的結構：正文是一次事件的成因推導（症狀、排查、根因、判斷標準）放 `work-log/`，即使那個工具在站上有教學模組；正文是讀者照著做就能重做的步驟、而且連回模組的概念文章，放 `hands-on/`。同一次工作兩種都有時，可以拆成兩篇：排查的推導寫成 work-log，走通之後可重做的步驟寫成實作文章，兩篇互相連結。

分類邊界的案例：

| 誤判                               | 正確分類                               |
| ---------------------------------- | -------------------------------------- |
| blog 的 mermaid 設定放 `work-log/` | mermaid 是 blog 內部設定，屬 `posts/`  |
| 寫作檢討放 `record/`               | 寫作檢討是從個案抽出原則，屬 `report/` |
| git 操作技巧放 `record/`           | 是工作中遇到的具體個案，屬 `work-log/` |

教學模組之間的主題邊界：

- **Go 教材**的核心是語言精神與工程實踐，不是單一專案的維運指南。後端擴充章節可以寫，從 Go 的設計思想與工程決策出發。
- **Backend** 是語言無關層，描述服務能力、風險、成本與決策，不綁 Go 或 Python。各語言章節連到 Backend 的能力，Backend 不反向依賴語言實作：同一個能力要給多種語言的讀者用，綁在一種語言上的話，其他語言的讀者要先翻譯實作才讀得到能力本身。

### 概念文章與實作文章：`hands-on/` 子資料夾

教學模組裡，解釋概念的文章與讀者照著做的文章分開放。實作文章是讀者照著做就能重做一次的操作，有兩種：一次實測的紀錄（前置條件、每一步的指令與輸出、遇到的錯誤與除錯過程、量到的值、資源的清理順序），以及不綁在某一次實測上的操作程序或演練（local lab、restore drill 這類）。兩種都放在 `hands-on/` 子資料夾；概念文章寫觀念與判斷依據，指令只留說明觀念需要的關鍵語法，完整的流程與程式碼放在實作文章，概念文章連過去。實測紀錄的開場之前寫事件說明（`writing.md`〈寫給帶著疑問來查的讀者〉），操作程序沒有某一次實測可交代時不寫。

分開的理由是兩種文章的讀者在做不同的事。讀概念文章的人在腦中建立判斷依據，一段完整的操作流程與上百行程式碼會蓋住論證；照實作文章操作的人要的是不漏步的順序與每一步該看到的輸出，觀念的推導夾在步驟之間會打斷操作。兩邊用連結接起來：讀概念的人知道實際操作寫在哪一篇，照著做的人知道每一步背後的觀念在哪一篇。資料夾名沿用站上既有的 `hands-on`（`content/llm/`、`content/backend/01-database/vendors/*/` 底下已經有），讀者在一個模組認得這個位置，到另一個模組也認得；同一種角色用兩個名字，讀者會以為是兩種不同用途的資料夾。

- **放哪一個 `hands-on/`**：這裡的「模組」指 `content/` 底下第一層的資料夾（`content/infra/`、`content/backend/`）。實作文章操作的是某一家業者或某一個工具，而模組裡有那家業者或那個工具的資料夾時，放在那個資料夾底下（`content/infra/cloud-providers/oracle-cloud/hands-on/`）；沒有的話，放在它連回的概念文章所在的資料夾底下（概念文章是 `content/infra/cloud-providers/vm-options/` 裡的一篇，就放 `vm-options/hands-on/`）；連回的概念文章分在同一個模組的幾個資料夾時，放在包含那幾個資料夾的最近一層（`vm-options/` 與 `content/infra/03-network-foundation/` 的最近一層是 `content/infra/`，放 `content/infra/hands-on/`）；連回的概念文章跨了幾個模組時，放在主要操作對象所屬的那個模組。落點在建檔時決定，之後連結增減不搬家。`rg --files content | rg '/hands-on/'` 列得出全站的實作文章。
- **上層的 `_index.md` 與 Backlog**：`hands-on/` 是 Hugo 的 section，要有自己的 `_index.md`（〈目錄頁 `_index.md` 與文章檔的分工〉），weight 照 `markdown.md`〈列表排序與 weight〉；它的 `title` 用中文寫出對象與內容（「Oracle Cloud 的實作紀錄」），讀者在列表頁讀到的是標題，資料夾名只出現在網址裡。`hands-on/` 的上一層資料夾（`oracle-cloud/hands-on/` 的上一層是 `oracle-cloud/`）的 `_index.md` 列出這個子資料夾與它收的操作。實作文章留下的未完成工作也記在這個上一層資料夾 `_index.md` 的 `## Backlog`（〈模組的 Backlog〉），`hands-on/_index.md` 不另開 Backlog。
- **概念文章的寫法**：指令只留說明觀念需要的關鍵語法（指令的形狀、哪個參數決定了什麼）；判斷流程寫成判斷依據，不寫成逐步的操作清單；需要完整流程時，連到 `hands-on/` 裡對應的實作文章，連結寫出那一篇做了什麼操作、量到了什麼（`writing-process.md`〈教學文章的脈絡〉的「交代了目的地沒有」）。既有的概念文章裡夾著從前置條件到完成的操作流程時，這次的改動就是在重寫那段流程（一整節以上）才在同一次拆出去；其餘的改動不拆，記進那篇概念文章所在資料夾的 `_index.md` 的 `## Backlog`。不在 `hands-on/` 的既有實作類文章（模組根目錄的實測紀錄、`*-lab.md`）同樣照這個條件，改寫一整節以上時才搬。
- **實作文章的寫法**：照 `writing.md`〈三種書面產出的體例〉裡讀者照著做的程序那一段，可以用編號步驟，每一步寫出它為什麼在這個位置、做錯會看到什麼。指令要實際跑過；跑不了的照 `verification-driven-cli` skill 的三層標註處理（實跑過的照寫；本機驗不了而指令有效的保留，標明沒有實跑與原因；驗不了也沒有保留價值的不寫）。觀念不在實作文章裡重寫，連回概念文章。依時間記下的除錯過程（含走不通的路）放進實作文章時，可重做的步驟寫在正文，排查的推導另寫成 work-log 連過去（上面〈文章放在哪一個資料夾〉的分界）。
- **量到的值與讀者要填的值**：實作文章記下的量測值（限流門檻、等待時間、重試的次數）是這一次的紀錄，可以寫出來，條件是同一處寫明它依什麼而變（帳號、區域、日期），而且讀者照著做時不依賴這個值：文章給了查法，或步驟本身會依回應自己調整。正確的值取決於讀者的環境、而步驟不會自己調整的值（OCID、IP、帳號名稱）照 `writing.md`〈不寫會取代讀者查證的值〉換成佔位值與查法；會依回應自己調整的腳本，它的起點、上限與下限照寫，同一處寫出腳本怎麼依回應調整它們。
- **既有文章搬進 `hands-on/`**：在它的 frontmatter 加 `aliases` 保留舊網址（`/<分類>/…/<slug>/`）。用 slug 找出連到它的位置（`rg -n '<slug>' content/ docs/ .claude/ AGENTS.md CLAUDE.md`，絕對路徑、相對路徑與不帶尾斜線的寫法都命中），逐筆改成新網址；命中裡的 `aliases:` 那一行是搬過去的那一篇自己，不改。被搬的那一篇自己用相對路徑往外連的連結，搬過去之後層數變了，改成絕對路徑。原資料夾 `_index.md` 章節表裡那一篇的列刪掉，在 `hands-on/_index.md` 的章節表登記。搬檔是刪除加新增，`bin/commit-files` 一定會印 `[ASK-USER]`（CLAUDE.md〈提交前對照編輯紀錄〉），照 `AGENTS.md`〈要先問使用者的情形〉處理；舊檔要刪掉，留著的話舊檔與新檔的 `aliases` 搶同一個網址。

### 寫之前要做的查核

- **寫 `report/` 卡之前**：確認這個議題沒有被既有的卡涵蓋。`content/report/_index.md` 的〈場景導讀〉（依讀者遇到的情境分成多條閱讀路徑）不是全部卡的清單，目錄頁也有卡沒有登記，所以另外用議題的關鍵詞掃全部卡的 `title` 與 `description`（`rg -il '^(title|description):.*<關鍵詞>' content/report/ -g '!_index.md'`；`-g` 只對目錄掃描生效，所以給目錄、不給 `*.md`）。議題跟既有的卡重疊而角度不同時，把新卡定位成那張卡的 sibling（同層、補另一個面向的卡），在關係段的第一條寫出最接近的既有卡與本卡補的面向；這一條就是查核的紀錄。新卡的卡號在建檔之前用 `bin/report-weight next` 取（目前最大的 `weight` 加一，既有的空號不回填）；先用佔位號建檔的話，佔位號會被當成最大值。另一個 session 可能同時在建卡，提交前跑 `bin/report-weight check`：exit 1 時它列出撞號的卡（還沒提交的標「（還沒提交）」）與下一個可用的號碼。撞號的卡裡有這次新建的那一張時，把新卡的 `weight` 改成那個號碼，再用 `rg -n '#<舊號>\b' content/report/` 找出這次寫過舊號的位置（`content/report/_index.md` 的條目與 `**Last Updated**` 紀錄、別張卡關係段的連結文字）一起改；撞號的兩張都不是這次建的時，寫進給使用者的最後一則總結（`AGENTS.md`〈延到工作結束之後的動作〉）。兩個子指令 exit 2 時原因印在 stderr：不在 repo 裡時切到 repo 再跑；有卡讀不出 weight 時，那張卡是這次建的就照格式修好，不是的話不改它，寫進最後一則總結。這條檢查只看得到目前的工作樹：在 worktree 或分支裡建的卡，併進 `main` 之後在 `main` 再跑一次。
- **寫 `report/` 卡時一起做的登記**：在 `content/report/_index.md` 加這張卡的條目。新卡的條目接在依卡號排列的那份清單的最後一條之後（卡號 294 以後的條目都在那份清單裡，它位在〈場景導讀〉最後一條路徑之下、`**Last Updated**` 那幾行紀錄之前）；條目寫出卡號、完整標題與連結、什麼情境讀這張卡。另外在檔尾 `**Last Updated**` 紀錄的最後加一條（紀錄依日期往下接），寫日期、新卡的卡號與它從哪一次工作抽出。〈篇目索引〉依輪次分組的那幾節是早期的登記，不再加新條目。這張卡適合某一條閱讀路徑時，另外把卡號加進那條路徑的串列。關係段與反向指標照 `writing-process.md`〈寫完之後的檢討〉的連結既有原則那一步。
- **改既有 `report/` 卡時**：跑 `scripts/principle-mirror-check.py <slug>` 找出 skill 裡的副本，判斷要不要同步照 `skills.md`〈改既有 report 卡時查它在 skill 裡的副本〉。
- **寫 `posts/` 文章之前**：確認沒有既有文章在講同一個主題；補充既有指南的某個議題時，開場引用那篇指南。
- **寫 `work-log/` 文章之前**：用這次事件的工具名與症狀關鍵詞掃 `content/work-log/`（`rg -il '<工具名>' content/work-log/`），確認沒有既有文章已經涵蓋同一個工具的同一類排查。同一個事件的延伸補進原文；工具相同而排查的對象不同，才另寫一篇，開場寫出跟那一篇的分工。
- **寫 `hands-on/` 實作文章之前**：用這次操作的工具名或業者名掃同一個模組（`content/` 底下第一層的資料夾）裡的全部 `hands-on/`（`rg -il '<工具名>' content/<模組>/ -g '**/hands-on/**'`），確認沒有既有的實作文章已經涵蓋同一個操作。同一個操作指的是既有那一篇標題寫的操作目標：補的是同一個目標（上一次沒走通的步驟）就補進原文；目標不同（同一台主機建好之後裝軟體、接監控）另寫一篇，兩篇互相連結。
- **任何資料夾**：frontmatter 的 `slug` 與檔名一致（見 `content/posts/markdown-writing-spec.md` §6.5）。
- **新增頂層 `content/<module>/` 資料夾時**：同時在 `content/_index.md` 對應的分類段加上入口。依據：[新增頂層 content 資料夾要同步首頁 _index.md 入口](/report/top-level-content-folder-needs-homepage-entry/)。

### 目錄頁 `_index.md` 與文章檔的分工

`content/` 底下的 `_index.md` 是 Hugo 的 section list page（模組的目錄頁）。`layouts/_default/list.html` 只列出子資料夾與文章、不輸出 `.Content`，所以 `_index.md` 的正文不會出現在網站上，讀者看不到。它的使用者是寫作者與維護這個分類的 agent，內容是這個分類的工作底稿：推導源頭、章節表、問題落點表、場景導讀（讀者依情境走的閱讀路徑）、Backlog。

| 檔案        | 用途       | 內容                                                                  | 內容量的參考                 |
| ----------- | ---------- | --------------------------------------------------------------------- | ---------------------------- |
| `_index.md` | 模組目錄頁 | frontmatter、簡介（1 到 3 段）、章節文章表格、跨分類引用、Backlog     | 20 到 90 行，加上 Backlog 段 |
| `<slug>.md` | 獨立文章   | 完整的教學內容，frontmatter 有 title、date、description、weight、tags | 50 到 300 行                 |

內容量的參考值來自本站早期模組的實際行數，是經驗值，沒有量過它跟讀者負擔的關係。所以行數只用來決定要不要多看一眼：`_index.md` 遠超過時，看它的正文裡有沒有寫給讀者看的推導或範例（有就是把文章內容寫進了目錄頁，讀者看不到，要搬到文章）；分類的工作底稿（`content/report/_index.md` 的場景導讀、`content/backend/_index.md` 的 Backlog 總覽）本來就長，不因行數搬家。文章超過參考量時，照 `writing.md`〈推導過重時拆篇，不壓縮成一句話的結論〉判斷要不要拆。

建新的教學模組時，先建 `_index.md` 寫模組簡介與文章表格，再建各篇獨立文章；文章內容寫進 `_index.md` 的話，Hugo 不會把它渲染成單篇頁面。既有模組的結構可以參考 `content/infra/00-infra-mindset/`。

由「讀者看不到 `_index.md` 正文」推出下面這幾條規則：

- **讀者需要的內容不只寫在 `_index.md`**：跨篇共用的範例資料、版本說明、術語約定，獨立成一篇文章（例：`content/backend/01-database/sql/sample-bookstore-database.md`），各篇連到那一篇。
- **文章不連 `/<分類>/#錨點`**：那些錨點在渲染後的頁面上不存在。掃法是 `scripts/index-leak-check.py --anchors`（絕對與相對路徑、任何層數都解析）。`mdtools cards` 對這一類放行，因為它比對的是 markdown 裡有沒有那個段標，而目錄頁的 markdown 有。「寫在[模組入口]」這類連到目錄頁本身、宣稱內容在那裡的句子，腳本抓不到；寫到模組入口時問一次那段內容讀者看不看得到。
- **文章正文不引用目錄頁的段名或框架詞**（目錄頁用來組織這個分類的自創詞，例如分類自己訂的階段名）：「模組入口的〈X〉那一節」要讀者去一個看不到的地方找內容。掃法是 `scripts/index-leak-check.py --all`（取 `_index.md` 的段標片語，比對同目錄文章的正文）。命中是候選：判定問句是這一句是不是要讀者去目錄頁找內容；同一個固定段名（「下一步路由」「適合的讀者」）同時出現在目錄頁與文章裡、而文章那一句沒有要讀者去目錄頁找內容的，放行。命中在 `content/skills/` 底下時，那是 `bin/skill-mirror` 產生的鏡像，改 `.claude/skills/` 的源檔再重跑鏡像。這條規則的依據是 [名詞要求的「誰的、什麼的」也是槽位，論斷句與段標的省略藏在名詞裡](/report/noun-without-its-owner-passes-the-slot-check/)，那張卡記錄了目錄頁的框架詞洩漏進正文的量測。
- **作者的編排思路寫進 `_index.md`，不進正文**：「本分類其餘各篇各自處理其中一步」「兩篇的分工：步驟的定義改本篇」描述的是作者怎麼組織內容，讀者讀到時手上沒有那份編排。

### 模組的 Backlog

教學模組的未完成工作記在該模組 `_index.md` 的 `## Backlog` 段，格式的單一真實來源是 [Backlog 段格式規範](/posts/backlog-format-spec/)；寫模組大綱、記錄待辦或做跨模組盤點之前先讀那一篇。

- **適用範圍**：`content/` 底下所有有模組結構的分類。`report/`、`til/`、`work-log/`、`other/` 這幾個沒有模組結構的目錄沒有模組級的 Backlog；在這些目錄留下的未完成工作，寫進 commit message，並照 `AGENTS.md`〈延到工作結束之後的動作〉寫進給使用者的最後一則總結。
- **段名固定為 `## Backlog`**，讓一條 grep 列得出所有有待辦的模組；段名自創的話，盤點時無法確定有沒有漏掉某個模組。
- 標準表的欄位定義、表下方 H3 的寫法（模組自己的規劃敘事）、哪些內容不進 Backlog（候選、絆腳索、已完成的項目，在表裡與 H3 都不放）、分類總覽的維護規則，以 [Backlog 段格式規範](/posts/backlog-format-spec/) 為準，這裡不重寫。實例見 [content/backend/\_index.md](/backend/) 的〈Backlog 總覽〉。
