# 寫作流程、紀錄與完稿檢查

這份分冊管寫一篇 `content/` 文章時走的步驟、字句層掃描的檔案集與 `bin/` 工具的計數怎麼讀、寫或改教材之前要讀的方法、寫完之後的檢討與提交前的完稿檢查清單，以及每一次 commit 要留下的紀錄（〈掃描與探針的紀錄寫進 repo〉；改 skill 與規則檔也適用）。文章本身的寫法在 `writing.md` 與 `sentences.md`，資料夾與目錄頁在 `content-folders.md`。

## 寫作流程與紀錄

### 規則的三個時機

`writing.md`、`sentences.md`、`writing-process.md`、`review.md` 每一節規則開頭的**時機**標出這一節要做動作的階段；適用條件與檢查方法寫在那一節的正文。其他分冊沒有這個標籤，照正文的條件適用。

- **動筆**：寫之前的查核、讀範本、決定體例與大綱，以及寫或改書面產出的文字的當下。補 `description` 與 `tags`、修 lint、補卡與照審查意見改稿都算。
- **審查**：檢查已經寫好的稿件時，包括跑掃描、照清單逐項確認、派 reviewer 或探針。這次要提交的稿件，在補完 `commit-push.md`〈提交〉的欄位、修完 lint 之後做。
- **收尾**：審查跑完之後、跑 `bin/commit-files` 之前，做檢討，並把各節正文要求的紀錄寫進 commit message，判成不跑或不適用的項目也寫。

一節標了兩個時機時，兩個時機都用。審查或收尾時又改了書面產出的文字，改到的部分回到動筆與審查；是否再派 reviewer 或探針，照 `review.md`〈多輪審查〉判斷。審查一份稿件時，依據是這份稿件適用的全部規則，只標動筆的節也在內；標了審查的節，正文另外寫了審查時要做的掃描或判定。

### 新文章動筆前對齊方向

**時機**：動筆、收尾。

這一節是試行中的做法。這次要在 `content/` 新增文章檔，或使用者要求換角度改寫既有文章時，執行者在動筆與更新模組大綱之前，於回覆裡寫出下面各項，結束這一輪，等使用者回覆之後才寫。「這篇想換個角度寫」算換角度（依的是文章的切入點要變），「這段補一個例子」不算（依的是切入點不變）。排程或批次執行沒有人回覆時，同樣只寫出這些項目，不寫文章。新增的檔案是目錄頁 `_index.md`、知識卡（定義在 `sentences.md`〈建卡原則〉）、`content/report/` 的卡或 `content/skills/` 的鏡像時，不走這一節。

- **讀者**：誰來讀這篇，讀完要做什麼。
- **切入角度**：這篇從主題的哪一個面向談。
- **起點**：比較或說明從哪裡開始，例如比較的基準、讀者已經知道的內容。
- **不寫什麼**：這篇刻意不談的內容。

使用者這次已經寫明的項目也要寫出來，並寫出打算怎麼落實到章節：方向的錯誤可能出在執行者對已寫明的方向的解讀，例如使用者要文章寫聽眾對演出的期待，執行者寫成進場逐項驗收。使用者這次明說不要停下來確認時，執行者照那個指示直接寫，這一次不留試行紀錄。派 agent 寫稿時，派發的一方先做這項對齊、等使用者回覆，再把結果或使用者說不用確認的原話寫進 prompt；受派的 agent 在 prompt 裡兩者都找不到時不動筆，回報派發的一方。一次要寫幾篇時，在同一則回覆逐篇列出，這幾篇算一次對齊。

理由是每篇文章的讀者與切入角度都不同，規則文字寫不成通則；方向選錯時，使用者要等文章寫完才能糾正，修法是重寫。這個做法的依據在 [改規則之前先把使用者的糾正逐則歸因：依讀起來模糊挑出來改的規則，多半不是出過事的那幾條](/report/attribute-recorded-corrections-before-rewriting-rules/)。

**紀錄**：提交這次對齊寫出的文章時，提交的一方在 commit message 最後一段加一行 `Alignment-Trial: <使用者改了哪幾項>`，都沒改時寫 `Alignment-Trial: 無`。一次對齊分成幾個 commit 時，只加在第一個。

**結束條件**：提交之後跑 `git log --grep='^Alignment-Trial:' --format='%h %(trailers:key=Alignment-Trial,valueonly)'`。列出 5 筆以上時，執行者在最後一則總結把最早的 5 筆交給使用者決定留或撤，5 筆都是「無」時建議撤掉。本節還在就代表使用者還沒決定，照本節繼續做。留用時，執行者拿掉本節的試行說明、紀錄與結束條件；撤掉時，刪掉本節與連到本節的句子（〈文章產出流程〉、`claude-code.md`〈Agent tool 的派發〉）。

### 文章產出流程

**時機**：動筆、審查、收尾。

這次要新增文章檔或換角度改寫文章時，執行者先照〈新文章動筆前對齊方向〉（適用的範圍寫在那一節）。新寫文章，或這次改寫一整節以上時，走這幾步；比這小的措辭級改動，這幾步裡只跑〈字句層掃描的檔案集〉，其他節的規則照它們的時機與適用條件用：

1. **更新模組大綱**：文章屬於有模組結構的分類時，更新文章所在資料夾的 `_index.md`，以及往上各層裡清單會因這篇文章改變的 `_index.md`（逐篇列出文章的、列出子資料夾的；`content/programming/python/basic/_index.md` 逐篇列出各章的文章，在 `06-practical/` 加一篇時兩份都改）。未完成的工作記進哪一份目錄頁的 `## Backlog`，照 `content-folders.md`〈模組的 Backlog〉判定。沒有模組結構的目錄沒有模組大綱：`report/` 卡在 `content/report/_index.md` 加條目，位置照 `content-folders.md`〈寫之前要做的查核〉的登記那一條；`work-log/` 的文章更新 `content/work-log/_index.md` 裡人工維護的分組清單，把新文章放進它所屬的那一組；`til/`、`posts/`、`record/`、`other/`、`books/` 跳過這一步。
2. **依大綱寫草稿**。
3. **術語掃描**：補缺的卡；網站會自動連結的名字不手寫連結，跑 `./bin/mdtools autolink-gaps <文章...>`（執行時機與輸出的讀法在 `markdown.md`〈自動連結的候選：`mdtools autolink-gaps`〉）列出網站不會連的名字，照判斷補手寫連結（見 `sentences.md`〈術語與知識卡〉，自動連結那一項在〈術語的解釋方式〉）。
4. **字句層掃描**：照 `compositional-writing` skill 的「字句層 keyword bank（完整清單）」逐類掃這次新增與改動的行（skill 在動筆之前就已經叫用；檔案集的取法見〈字句層掃描的檔案集〉：新文章是全文，改既有文章是新增與改動的行）。bank 的清單以 skill 為準；`markdown.md`〈工具會擋的類別與要自己跑的類別〉只列哪些類別由工具擋下。每個命中都要走一次語意判定，命中是候選，不是判決。
5. **結構掃描**：去掉重複、補交叉引用與路由；每條跨模組路由去目的地驗一次它承接這個主題、到站第一屏看得到；跑 `scripts/index-leak-check.py --anchors` 與 `--all`（`content-folders.md`〈目錄頁 `_index.md` 與文章檔的分工〉）。
6. **完稿檢查**：照〈完稿檢查清單〉逐項確認。
7. **審查**：照 `review.md`〈多輪審查〉的「什麼時候跑」判斷，要跑的在 commit 之前跑完。
8. **檢討**：〈寫完之後的檢討〉的觸發條件成立時做。

檢查發現違規時，先修文，再進下一章。

### 字句層掃描的檔案集

**時機**：審查。

不是排版級的改動（措辭級與規則級，定義在 `AGENTS.md`〈改動的級別〉），跑一次 `compositional-writing` 的 keyword bank，掃描對象是這次的新增行：

```bash
bin/changed-lines <這次的檔案...> > <暫存目錄>/added.txt   # 新增行，不帶 diff 的 + 前綴；新檔整份都算
```

它涵蓋已經 staged、還沒 staged 的改動與還沒 add 的新檔，不寫 git index；路徑以執行時的目錄起算。stderr 的 `changed-lines: N added line(s) from M file(s)` 裡，N 是 0 而這次的改動有新增文字時，代表給的檔案不對，修正之後重跑；這次只刪除文字時 N 是 0，沒有新增行可掃，逐類表寫「只刪除，沒有新增行」。N 不是 0 時照 bank 對 `added.txt` 跑。逐類表照〈掃描與探針的紀錄寫進 repo〉留下。prompt 要求審查一篇這次沒有改動的稿件時，掃描對象是整份稿件，不跑 `bin/changed-lines`。

### 掃描工具的計數

**時機**：動筆、審查、收尾。

`bin/changed-lines`、`bin/lint-delta`、`bin/session-edits-check`、`bin/skill-version-check`、`bin/term-prompt-count`、`bin/report-weight`、`bin/content-move`、`bin/empty-sections`、`bin/alias-check`、`bin/autolink-dict`、`bin/rule-route` 在結尾印計數，格式寫在各工具的檔頭。交給它檔案清單的工具，計數要對得上交給它的數量；自己找檔案的工具（`bin/term-prompt-count`、`bin/report-weight`、`bin/content-move`、`bin/empty-sections`、`bin/alias-check`、`bin/autolink-dict`），代表掃描範圍的那一個計數是 0、或 stderr 列出讀不到的來源時，檔案集不對；那一個計數是 `content-move` 的 `page(s) moved`、`empty-sections` 的 `section(s) scanned`、`alias-check` 的 `page(s)`、`autolink-dict` 的 `card(s)`，同一行的其他計數（`collision(s)`、`empty`）是 0 代表通過（`autolink-dict` 沒有這種計數，看 exit）。

### 教學模組的產出流程

**時機**：動筆、審查。

寫跨五章以上、有現成案例庫的教學模組時，用 `case-first-module-workflow` skill 的流程：完整讀案例庫抽出 findings、依 findings 寫稿、派多個專責 reviewer 平行審查。單篇短文、沒有案例庫的新主題，以及使用者這次把速度排在品質之前的模組（快速迭代的原型屬於這一種）不用這個流程。執行者依使用者這次的指示判斷速度是否排在品質之前：「先出一版看方向，之後可能整個丟掉」算（依的是使用者接受這一版的品質之後再補或整版換掉）；「內容要寫完整，只是這週要交」不算（依的是使用者要的品質沒有降，趕的只是時程）。使用者沒有下這類指示時不算，因為執行者當下省力的選項就是不跑流程；判成速度優先時，commit message 逐字引用使用者說的那一句。方法論與實作數據見 [Case-First + Agent Team Review：教學內容的生產流程](/posts/case-first-agent-team-review-workflow/)，新模組第一次套用時先讀完那一篇。

### 掃描與探針的紀錄寫進 repo

**時機**：收尾。

**判成「不需要後續動作」的結論要留下判定的痕跡。** 規則要求判定的地方（掃描、查核、驗證、歸因、適用與否），最省力的結論都是不產生任何產物的那一個：零命中、沒有缺卡、路由驗過了、不適用、模型誤讀、只改了措辭。認真做過與完全沒做，在產物上看起來一樣，所以這一類結論在 commit message 寫出三件事：判定的對象、結論、依據。依據是第三方在這個 commit 上重跑得出同樣結果的材料：指令原文與掃描的檔案集，或原文的行號。只寫「已檢查」「不適用」等於沒有判定。

紀錄寫進 commit message；寫的是一篇給讀者看的 work-log 文章、而紀錄本身就是那篇文章的內容時，寫進同一個 commit 裡的那篇文章也算。只寫在對話回覆裡不算留下紀錄。這一條的常見實例：

- **字句層掃描的逐類表**（〈文章產出流程〉步驟 4 的產出）：每一類一列，寫出執行的指令原文、掃的檔案集（`bin/changed-lines` 取出的新增行與它印的檔案數，見〈字句層掃描的檔案集〉）、命中數、每處的語意判定。零命中的類別也列，指令原文照樣寫。對讀者喊話、自評誇飾、必然性框架、敘事姿態這幾類作者看不見（作者與同源的審查者共享同一套文體直覺，讀起來全部「自然」），所以它們的那一列一定要有指令原文；用冷讀代替 grep 時，寫出讀者是誰。**同源的審查者**是手上有作者 context 的審查者：作者自己、讀過作者寫作時的對話或說明的 reviewer、與作者在同一個 session 裡的 agent；同一個模型最常落在這個處境，但判定看的是手上有沒有作者的 context，不是模型。**異源的讀者**是手上沒有作者 context 的讀者：新派、只拿到稿件而不附作者說明的 agent，或另一位人。其他規則提到同源與異源時，指的是這裡的定義。
- **術語的處置表**（步驟 3 的產出）：本篇的承重術語各一列，寫出詞、在本篇的角色、在不在前置篇章裡、處置（行內展開、連卡、裸用；連卡另外寫是自動連結還是手寫），以及 `mdtools autolink-gaps` 印的計數行與它列出的每個候選的判定（連或不連與依據，同一個名字與原因合成一列）。
- **路由的驗證**（步驟 5 的產出）：每一條跨模組路由寫出目的地的 slug 與在那裡看到承接主題的段標。
- **理解探針的歸因與處置**：跑過理解探針的稿件，每份回報的讀法歸到哪一類、怎麼處置，歸成「模型誤讀」的附排除句的行號（見 `review.md`〈理解探針〉）。沒有跑探針時（Codex 派不出探針、或判成不需要），寫「未跑」與原因。
- **術語探針的判定**：每個測試詞的判定（通用、一名多義、非通用、同域佔用或本批無結論）與依據，以及三項前提：同批的通用性控制詞有沒有收斂、測試詞在系統提示裡的詞頻、有沒有合格的同域安慰劑詞。「同批」指放在一起比對的那一組探針報告；三個名詞的定義與判讀在 `multi-round-review` 的 `references/round-2-probes.md`〈2-B⁶ 術語探針〉。
- **寫或改寫教材時各篇的可動項清單**：單軸與列不出來分開寫（見〈教學文章的脈絡〉）。
- **多輪審查**：輪數、每輪的 frame、每輪的 finding 數與處置（見 `review.md`〈多輪審查〉）。
- **完稿檢查清單裡判成不適用的項目**：寫出項目與構成不適用的段落。

### 教學文章的脈絡

**時機**：動筆、審查。

寫或改任何一篇教材之前，先讀 [教學文章的脈絡](/record/teaching-article-context-method/)。那一篇是方法的單一真實來源，本節列它的三項支柱與各自的檢查：

- **這一篇在序列裡的位置**：說得出讀者手上已經有什麼、這一篇交付什麼、刻意不碰什麼。檢查：把這三句話實際寫下來，每一句都要指得到文章裡的一個位置（哪一段、哪一句）；指不到，代表那件事沒有寫進去。深度看讀者手上已經有什麼，不看題材的表面複雜度。依據：[基本功能衍生的問題不比進階議題簡單，而進階議題要從它推導](/report/basics-anchor-the-advanced/)。
- **論證用得到的材料就地寫進去**：承重術語（定義見 `sentences.md`〈術語的解釋方式〉）當場定義、本篇論證依賴的機制寫進正文、每一句的指涉能從已讀文字解出來。這三件事作者看不見，成因是熟悉度。檢查：跑 `python3 scripts/loadbearing-terms.py <檔案路徑>`（可以一次給多個檔），把列出的高頻實詞逐個回全文查有沒有一處說過它指什麼。它每檔只回前三名，是抽樣；跨檔高頻而單篇中頻的自創詞要另外掃：把候選換成這一批文章反覆出現的詞，逐個查它在別處有沒有被定義過。
- **往外的連結綁在本篇模型的可動項上**：可動項是本篇建立的模型裡可以獨立改變的那幾件事。跨篇連結有三種寫法：**綁在讀者的處境上**（「遇到 X 的時候去讀 Y」，讀者沒遇到那件事就等於不存在）、**綁在主題的邊界上**（「這個主題不涵蓋 A、B、C，各有專篇」，讀者知道那邊有專篇而不知道它講什麼）、**綁在可動項上**（每一條連結指向「這個可動項換成另一個值時」所討論的那一篇，讀者能預測隔壁那一篇長什麼樣）。
  - 先把本篇的可動項列出來：從本篇的結論句往回問，這個結論的成立依賴哪幾件事，其中哪幾件換掉之後結論會不一樣；換掉會改變結論的是可動項，換掉不影響的是背景。
  - 列得出兩個以上 → 寫成綁在可動項上的連結。
  - 只列得出一個 → 這一篇是單軸（判斷標準篇與術語卡多屬這一類），換掉那一項得到的是同一篇裡那個二元選擇的另一個選項，綁在主題的邊界上就是完整的寫法。
  - 一個都列不出來 → 這一篇可能沒有建立帶可動項的模型。這是要回頭檢討文章的訊號，在紀錄裡跟「單軸」分開寫。
  - 三種寫法只用在同層的鄰篇；往回問來源、往前問下游、母分類頁這類連結不綁可動項。開場交代範圍時寫的邊界連結（`writing.md`〈開場列出這篇討論的內容〉）不取代正文裡的可動項連結：同層的鄰篇在開場提過，正文寫到那個可動項時仍要連一次。
  - 驗收是兩個獨立的檢查，各測一件事：**交代了目的地沒有**（遮住目的地，讀者預不預測得出那一篇給什麼；每一條往外的連結都要過）與**綁在什麼上**（這條連結綁在處境、邊界還是可動項上；只用在同層鄰篇）。綁在邊界上的連結可以完全通過前一個檢查而不滿足後一個，所以兩個都要跑。依據：[串連佔掉的是本篇的篇幅，順序要先自足再往外開門](/report/cross-links-eat-the-article-they-live-in/)。

三項支柱都靠理解探針驗（見 `review.md`〈理解探針〉），作者自審與同源審查者對它們看不到。

### 寫完之後的檢討

**時機**：動筆、收尾。

一篇文章寫完後，下列任一條件成立時做一次檢討：同一類 finding 在兩輪以上的審查裡出現；`git log -L` 顯示同一段在這次工作裡改過兩次以上；發生了這次的計畫沒有預期到的事件（工具回報了沒想到的錯誤、使用者否決了已經提交的做法、審查推翻了某個前提）。

1. **辨識議題的層次**：視覺、語意、邏輯哪一層（見 `compositional-writing` 的 `references/writing-articles.md`〈層次意識〉）。
2. **抽出抽象原則**：問下一個類似情境會不會出同樣的事。會、而且既有的卡沒有涵蓋時，寫成 `report/` 卡；會、而既有的卡已經涵蓋時，在 commit message 寫出那張卡的 slug；不會時，在 commit message 寫出判斷的理由（這次的成因只屬於這個情境的哪一點）。
3. **連結既有原則**：新卡在關係段（段名用 `## 跟其他抽象層原則的關係`，這是卡號（`weight`）360 以後的卡一律使用的寫法；舊卡另有 `## 跟其他原則的關係`、`## 跟其他卡的關係` 等寫法，不回頭改）列至少三張既有 `report/` 卡的關係。新卡限定了既有卡的適用邊界、或補了它留下的空白時，在舊卡的關係段補一條反向指標，否則舊卡的讀者不會知道自己拿到的規則不完整。
4. **更新規範**：這次的議題在現行的規則類文件（`AGENTS.md`〈改動的級別〉）裡查不到對應的條目、或照對應的條目做會出錯時，補規範；判成不需要補時，在 commit message 寫出理由。
5. **更新 `content/report/_index.md` 的〈場景導讀〉**：這次新建的卡適合某一條閱讀路徑時，照 `content-folders.md`〈寫之前要做的查核〉的登記那一條，把卡號加進那條路徑。

commit message 寫出這次檢討判定的層次，以及新卡的 slug 或已涵蓋它的既有卡 slug。

議題同時要記在 `content/` 與 skill 兩處時，各寫一份、各自用那個 surface 的語境寫。skill 那一份不連 `content/`，因為 skill 要能複製到別的專案運作（見 `skills.md`〈Skill 的依賴邊界〉）；`content/` 那一份不連 `.claude/skills/` 的源檔，因為讀者讀的是網站，要連就連 `content/skills/` 的公開鏡像。

## 完稿檢查清單

**時機**：審查、收尾。

新寫的文章，或這次改寫一整節以上時，提交前逐項確認，每一項連到它的規則。清單涵蓋 `content/` 文章最常漏掉的檢查，不是全部規則的索引；寫 skill 時另照 `skills.md`〈Skill 的撰寫規則〉的完稿檢查。判成不適用的項目，照〈掃描與探針的紀錄寫進 repo〉在 commit message 寫出項目與構成不適用的段落。

- [ ] 文章的體例是教學而不是手冊：逐節問讀者讀完之後那個動作落在哪裡，`writing.md`〈文章被寫成手冊的裝置〉列的裝置都掃過。`_index.md` 與 `report/` 不適用；`hands-on/` 實作文章的程序段落照 `writing.md`〈三種書面產出的體例〉的程序寫法，只掃程序以外的段落。
- [ ] 指令的輸出有多種讀法時，指令旁寫出了該看的欄位與讀法（`writing.md`〈教學的產出形式〉）。

- [ ] 第一段以外的每段首句是這一段的主題句，不是例子，也不是推導出的結論（`writing.md`〈段落的第一句寫這一段的主題〉）。
