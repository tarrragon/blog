# 寫作流程、留痕與完稿檢查

## 寫作流程與留痕

### 文章產出流程

每次寫文章都走這幾步：

1. **更新模組大綱**：文章屬於有模組結構的分類時，更新該模組的 `_index.md`，未完成的工作記進 `## Backlog`（見`content-folders.md`〈模組的 Backlog〉）。寫 `report/`、`work-log/`、`til/` 這類卡片型目錄時沒有模組大綱，這一步跳過；`report/` 卡另外更新 `content/report/_index.md` 的篇目索引。
2. **依大綱寫草稿**。
3. **術語掃描**：補連結、補缺的卡（見`sentences.md`〈術語與知識卡〉）。
4. **字句層掃描**：照 `compositional-writing` skill 的「字句層 keyword bank（完整清單）」逐類掃過稿件（skill 在動筆之前就已經叫用，見`AGENTS.md`〈規則的優先序與住址〉）。bank 的清單以 skill 為準；`markdown.md`〈Markdown 與 mdtools〉只列哪些類別由工具擋下。每個命中都要走一次語意判定，命中是候選，不是判決。
5. **結構掃描**：去掉重複、補交叉引用與路由；每條跨模組路由去目的地驗一次它承接這個主題、到站第一屏看得到。
6. **完稿檢查**：照〈完稿檢查清單〉逐項確認。

檢查發現違規時，先修文，再進下一章。

### 教學模組的產出流程

寫跨五章以上、有現成案例庫、品質優先於速度的教學模組時，用 `case-first-module-workflow` skill 的流程：完整讀案例庫抽出 findings、依 findings 寫稿、派多個專責 reviewer 平行審查。單篇短文、沒有案例庫的新主題、快速迭代的原型不用這個流程。方法論與實作數據見 [Case-First + Agent Team Review：教學內容的三階段生產流程](/posts/case-first-agent-team-review-workflow/)，新模組第一次套用時先讀完那一篇。

### 掃描與探針的紀錄寫進 repo

紀錄寫進 commit message 或 work-log（`content/work-log/` 的文章；改的是 skill 或規則檔時通常寫在 commit message），只寫在對話回覆裡不算留下紀錄。要留的紀錄有四種：

- **字句層掃描的逐類表**（〈文章產出流程〉步驟 4 的產出）：掃了哪幾類、各命中幾處、每處的語意判定結果，零命中的類別也列。完全沒叫用 skill 與叫用了但零命中，在產物裡看起來一樣，所以沒有這張表的「已檢查」不成立。
- **理解探針的歸因與處置**：跑過多輪審查的稿件與規則類文件，每份探針回報的讀法歸到哪一類、怎麼處置（見`review.md`〈理解探針〉）。
- **術語探針的三項前提**：同批的通用性控制詞有沒有收斂、測試詞在規範檔裡的詞頻、有沒有合格的同域安慰劑詞。三個名詞的定義與判讀在 `multi-round-review` 的 `references/round-2-probes.md`〈2-B⁶ 術語探針〉。
- **改寫教材時各篇的可動項清單**：單軸與列不出來分開寫（見〈教學文章的脈絡〉）。

字句層有幾類作者看不見（對讀者喊話、自評誇飾、必然性框架、敘事姿態），因為作者與同源的審查者共享同一套文體直覺，讀起來全部「自然」。這幾類要實際跑 grep，或請異源的讀者冷讀（不是同一個模型、沒有讀過作者 context 的讀者，例如另一個 agent 或另一位人），回憶「我應該有遵守」不算掃描。

### 教學文章的脈絡

寫或改任何一篇教材之前，先讀 [教學文章的脈絡](/record/teaching-article-context-method/)。那一篇是方法的單一真實來源，本節列它的三項支柱與各自的檢查：

- **這一篇在序列裡的位置**：說得出讀者手上已經有什麼、這一篇交付什麼、刻意不碰什麼。檢查：把這三句話實際寫下來，每一句都要指得到文章裡的一個位置（哪一段、哪一句）；指不到，代表那件事沒有寫進去。深度看讀者手上已經有什麼，不看題材的表面複雜度。依據：[基本功能衍生的問題不比進階議題簡單，而進階議題要從它推導](/report/basics-anchor-the-advanced/)。
- **論證用得到的材料就地寫進去**：承重術語（本篇論證依賴的術語）當場定義、承重機制寫進正文、每一句的指涉能從已讀文字解出來。這三項作者看不見，成因是熟悉度。檢查：跑 `python3 scripts/loadbearing-terms.py <檔案路徑>`（可以一次給多個檔），把列出的高頻實詞逐個回全文查有沒有一處說過它指什麼。它每檔只回前三名，是抽樣；跨檔高頻而單篇中頻的自創詞要另外掃：把候選換成這一批文章反覆出現的詞，逐個查它在別處有沒有被定義過。
- **往外的連結綁在本篇模型的可動項上**：可動項是本篇建立的模型裡可以獨立改變的那幾件事。跨篇連結有三種寫法：**綁在讀者的處境上**（「遇到 X 的時候去讀 Y」，讀者沒遇到那件事就等於不存在）、**綁在主題的邊界上**（「這個主題不涵蓋 A、B、C，各有專篇」，讀者知道那邊有專篇而不知道它講什麼）、**綁在可動項上**（每一條連結指向「這個可動項換成另一個值時」所討論的那一篇，讀者能預測隔壁那一篇長什麼樣）。
  - 先把本篇的可動項列出來：從本篇的結論句往回問，這個結論的成立依賴哪幾件事，其中哪幾件換掉之後結論會不一樣；換掉會改變結論的是可動項，換掉不影響的是背景。
  - 列得出兩個以上 → 寫成綁在可動項上的連結。
  - 只列得出一個 → 這一篇是單軸（判斷標準篇與術語卡多屬這一類），換掉那一項得到的是同一篇裡那個二元選擇的另一個選項，綁在主題的邊界上就是完整的寫法。
  - 一個都列不出來 → 這一篇可能沒有建立帶可動項的模型。這是要回頭檢討文章的訊號，在紀錄裡跟「單軸」分開寫。
  - 三種寫法只用在同層的鄰篇；往回問來源、往前問下游、母分類頁這類連結不綁可動項。
  - 驗收是兩個獨立的檢查，各測一件事：**交代了目的地沒有**（遮住目的地，讀者預不預測得出那一篇給什麼；每一條往外的連結都要過）與**綁在什麼上**（這條連結綁在處境、邊界還是可動項上；只用在同層鄰篇）。綁在邊界上的連結可以完全通過前一個檢查而不滿足後一個，所以兩個都要跑。依據：[串連佔掉的是本篇的篇幅，順序要先自足再往外開門](/report/cross-links-eat-the-article-they-live-in/)。

這三項都靠理解探針驗（見`review.md`〈理解探針〉），作者自審與同源審查者對它們看不到。

### 寫完之後的檢討

一篇文章寫完後，發生了來回修改（同一處內容改了又改）、多次審查，或非預期的事故時，做一次檢討：

1. **辨識議題的層次**：視覺、語意、邏輯哪一層（見 `compositional-writing` 的 `references/writing-articles.md`〈層次意識〉）。
2. **抽出抽象原則**：問下一個類似情境會怎麼出同樣的事故；會的話寫成 `report/` 卡。
3. **連結既有原則**：新卡在關係段（新卡的段名用 `## 跟其他卡的關係`；舊卡另有 `## 關係` 與 `## 跟其他抽象層原則的關係` 兩種寫法）列至少三張既有 `report/` 卡的關係。新卡限定了既有卡的適用邊界、或補了它留下的空白時，在舊卡的關係段補一條反向指標，否則舊卡的讀者不會知道自己拿到的規則不完整。
4. **更新規範**：議題揭露既有規範缺失時，補規範。
5. **更新 `content/report/_index.md` 的〈場景導讀〉**：給之後遇到同類情境的讀者一條閱讀路徑。

議題同時要記在 `content/` 與 skill 兩處時，各寫一份、各自用那個 surface 的語境寫。skill 那一份不連 `content/`，因為 skill 要能複製到別的專案運作（見`skills.md`〈Skill 的依賴邊界〉）；`content/` 那一份不連 `.claude/skills/` 的源檔，因為讀者讀的是網站，要連就連 `content/skills/` 的公開鏡像。

## 完稿檢查清單

提交前逐項確認，每一項連到它的規則。清單涵蓋 `content/` 文章最常漏掉的檢查，不是全部規則的索引；寫 skill 時另照`skills.md`〈Skill 的撰寫規則〉的完稿檢查。

- [ ] 文章的體例是教學而不是手冊：逐節問讀者讀完之後那個動作落在哪裡，七種裝置掃過（`writing.md`〈文章被寫成手冊的裝置〉）。`_index.md` 與 `report/` 不適用。
- [ ] 指令的輸出有多種讀法時，指令旁寫出了該看的欄位與讀法（`writing.md`〈教學的產出形式〉）。
- [ ] 開場逐一列出這篇討論的內容，不熟這個主題的讀者讀完能判斷與他要找的內容有沒有關係（`writing.md`〈開場列出這篇討論的內容〉）。
- [ ] 第一段以外的每段首句是這一段的主題句，不是例子，也不是推導出的結論（`writing.md`〈段落的第一句寫這一段的核心〉）。
- [ ] 沒有只交付結論、省掉推導的句子；推導過重的部分已經拆篇（`writing.md`〈不用一句話交代或總結；推導過重時拆篇〉）。
- [ ] 標題與段標寫主旨；每個標題當成別篇裡的連結文字讀過一次（`writing.md`〈標題與段標寫主旨〉）。
- [ ] 結論與判斷標準由推導交付，沒有懸念也沒有開頭灌輸；檢討內容用客觀條件（`writing.md`〈寫給帶著疑問來查的讀者〉）。
- [ ] 讀者能從本篇判斷自己落在哪一個條件，以及各條件的後果與理由（`writing.md`〈每篇文章要寫出可操作的判斷標準〉）。
- [ ] 系統層的概念寫在案例之前（`writing.md`〈系統層的概念寫在案例之前〉）。
- [ ] 每一句的槽位填得出領域裡的名詞，結果寫成可觀察的狀態（`sentences.md`〈句子的槽位〉）。
- [ ] 示範指令的每一個要改的引數，文章都說過它填什麼（`sentences.md`〈程式碼區塊的引數〉）。
- [ ] 沒有寫進會取代讀者查證的值（`writing.md`〈不寫會取代讀者查證的值〉）。
- [ ] 正文的對象用內容命名，反覆談論的概念先界定再命名；每個自創的抽象名詞都有情境化的說明（`sentences.md`〈正文裡的對象用它是什麼來命名〉`sentences.md`〈先界定一個概念並命名，之後用名字引用〉）。
- [ ] 排比的每個子句都填了具名的對象（`sentences.md`〈同義反覆的排比〉）。
- [ ] 「問題」「回答」當框架詞、物理動詞佔住內容的位置都翻譯過（`sentences.md`〈「問題」「回答」與物理動詞〉）。
- [ ] 負向陳述降到必要的最小（`writing.md`〈主要敘述用正向陳述〉）。
- [ ] 承載推導的表格項目都選了出口；查表型與 checklist 型段落除外（`writing.md`〈表格裡的判斷要有出口〉）。
- [ ] 沒有用共通模板抹平不同情境的差異（`writing.md`〈每個情境用它自己的敘事，不套共通模板〉）。
- [ ] 沒有依賴特定專案的背景知識（`writing.md`〈不預設讀者熟悉特定專案〉）。
- [ ] 術語依角色與前置知識選了行內展開、連卡或裸用，缺的卡已建；譯名過了判斷問句（`sentences.md`〈術語的解釋方式〉`sentences.md`〈譯名避開介面上已有的同名元素〉）。
- [ ] 每條路由都去目的地確認過它承接這個主題、到站第一屏看得到，並交代了目的地會給什麼（〈文章產出流程〉的結構掃描、〈教學文章的脈絡〉的可動項）。依據：[跨模組路由要驗證目的地承接該主題、不只驗證目的地存在](/report/routing-destination-must-own-the-topic/)。
- [ ] `description` 的體例對得上內容定位，遮住它只看標題猜不出全部內容（`writing.md`〈`description` 的體例〉）。
- [ ] 新增頂層 `content/<module>/` 時，已同步更新 `content/_index.md`（`content-folders.md`〈寫之前要做的查核〉）。
- [ ] 這次留下的未完成工作已記進模組的 `## Backlog`，完成的項目已刪除（`content-folders.md`〈模組的 Backlog〉）。
- [ ] 這次要留的紀錄都寫進了 commit message 或 work-log：字句層掃描的逐類表、理解探針的歸因與處置、術語探針的控制詞、詞頻與安慰劑詞、可動項清單（〈掃描與探針的紀錄寫進 repo〉）。
