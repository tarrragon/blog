# 審查與理解探針

這份分冊管：什麼時候跑多輪審查、跑的時候守哪些底線與嚴重度、審查規則類文件時的限制，以及理解探針讀回報時的歸因與術語探針「本批無結論」的去處。frame（審查視角：一輪審查裡每位 reviewer 負責檢查的那一個面向，例如冷讀、事實核對、自審）的選擇、reviewer 的產出契約、探針的派發條件住在 `multi-round-review` skill；Claude Code 的派發參數在 CLAUDE.md。

## 審查與理解探針

### 多輪審查

**什麼時候跑**：下列情形跑 `multi-round-review` skill 的完整流程：新寫的 work-log 與 `hands-on/` 實作文章，以及既有 `hands-on/` 文章新增或改寫一整節以上（含搬進 `hands-on/` 時的改寫）；教學模組的新章節，以及既有章節裡一整節以上的措辭級改寫；規則類文件的規則級改動（不論改了幾句）。級別的定義在 `AGENTS.md`〈改動的級別〉。其餘的改動不跑；判成不跑時，commit message 寫出這次改動的級別，以及它是哪一種文件的改動。skill 自己寫的「單篇短文不適用」對本 repo 的 work-log 不成立：work-log 與實作文章是單篇，而它們的讀者一樣從搜尋直達、一樣會照著做。

**至少三輪**，Round 3 跑完之前不問「要不要繼續」：Round 1 與 Round 2 的預設 frame 以已經寫好的內容為對象，Round 3 的 frame 以還沒寫的內容為對象（漏掉的選項、反向引用、搜尋落點、知識卡缺口）。前兩輪偶爾也會撞到後一類，但它不是那兩輪的 frame 要找的對象，沒有任何一輪保證涵蓋它。Round 3 跑完之後，由主 session 判斷要不要再跑。依據：[多輪審查至少三輪是硬底線](/report/multi-round-review-minimum-three-rounds/)。

**紀錄**：commit message 寫出跑了幾輪、每輪的 frame、每輪的 finding 數與處置（見 `writing-process.md`〈掃描與探針的紀錄寫進 repo〉）。

**嚴重度**：依讀者學不學得會分兩級。**必修**是照做會學錯或做錯、在這一段理解不了、要回頭翻才讀得懂，以及作者的編排脈絡寫進了正文；**可改**是讀者拿得到資訊也不會錯，但要多花力氣。連到知識卡的術語不因為「要離開這一頁才讀得到定義」就列為必修：連卡是 `sentences.md`〈術語的解釋方式〉准許的處理，判定看離開那張卡之後本段的論證還走不走得下去。規則分冊寫「審查時列為必修」的類別，就是落在必修那一級的。量尺的完整版以 `multi-round-review` 的 SKILL.md〈每個 reviewer 的 prompt 都要指定的事〉為準。

### 審查規則類文件時

審查對象是 AGENTS.md、`docs/rules/` 的分冊或 CLAUDE.md 時，在本 repo 裡派出的 reviewer 與探針，系統提示裡都已經有受審文本的全文，而且可能是 session 開始時的舊版。系統提示裡已經有受審全文的情形，對任何會自動載入這些檔案的 agent 都成立：

- **prompt 裡寫死受審版本的 commit hash**，要求以 `git show <hash>:<檔名>` 讀到的版本為準。不用 `HEAD`：審查期間別的 session 提交時 HEAD 會移動，各份讀到的版本就不同。受審內容還沒提交時，把檔案複製到暫存目錄，prompt 給那個路徑；不為了取得 hash 先提交草稿。
- **探針回報讀錯的位置可以採信；回報讀懂的位置不能當成通過**，因為它可能是用系統提示補完的。reviewer 判定「讀得懂」時同樣適用。
- **翻譯探針不跑**：它的設計條件是譯者只拿得到文字，這裡結構上做不到。
- **修完拿任務重走一次，再派下一輪**：照 finding 修完之後、派下一輪探針或 reviewer 之前，主 session 把探針用的任務與這一輪 finding 的案例逐一走過修改後的規則，寫出每一步經過哪幾條規則、各自給什麼處置；同一步出現兩種處置，或某一步沒有任何規則管，派發之前先修。修法以句子為單位驗收，看不到兩條規則套在同一個案例上的結果，而探針拿任務走，正好看得到。做法在 `multi-round-review` 的 `references/integrating-findings.md`〈修完拿任務重走一次，再派下一輪〉。走過的案例與結果寫進 commit message。依據：[規則的修法逐句驗證會通過、套到案例上才互撞：改完才查得到的事實管不了動手之前的步驟，修完要拿任務重走](/report/rule-fixes-pass-per-sentence-and-collide-per-case/)。

### 理解探針

驗一段文字會不會被誤解時，判斷依據放在多份獨立理解實際讀到什麼，不放在任何一個 reviewer 的判斷上。做法是把同一個低階模型獨立跑多份，每一份用逐字相同的指令讀同一份稿件，回報讀到什麼。要的是低成本：份數夠多，才分得出分歧來自文字還是偶然。另外有一個觀察到的傾向：低階模型讀到殘缺的句子時，比高階模型少替句子補完，缺漏因此較常出現在回報裡；這個傾向來自少數幾次量測，沒有在同一份指令下拿高階模型對照過，當成假設用，不當成保證。

派發的條件（指令與範圍逐字相同、不給審查框架、要求標記不確定、問理解不問評價）與回報格式，以 `multi-round-review` 的 `references/round-2-probes.md`〈探針的派發契約〉為準。這些條件缺一個，份與份之間的分歧就無法歸因到文字。

**歸因先於處置**：判定「讀者讀錯了」之前，先在原文裡搜那個讀法對應的字串。回報分三類：

- **原文寫錯**：找得到逐字對應的句子，是文章自己這樣寫的。修那一句，並找出它跟哪裡衝突（同一節的正文與結尾摘要互相矛盾是常見的形態）。
- **表述有歧義**：找不到對應的句子，而現有材料足以推出那個讀法。改寫成只有一種讀法。
- **模型誤讀**：三個條件同時成立才歸這一類：指得出排除那個讀法的句子（寫出行號）、那一句在閱讀順序上位於讀錯的位置之前、同一批（放在一起比對的那幾份探針報告）有別份讀對了同一處。缺任何一個，歸「表述有歧義」。判定者自認材料已經足夠，不改變本款結果：判定者是作者或讀過全文的人時，他正是探針要繞過的那個會替文字補完的讀者。歸這一類時，紀錄附那一句的行號，在這裡結案。

前兩類都要處置，一份讀錯就修：引導讀者是寫作者的職責，任何一份讀錯都代表文字容許那個讀法。多份落在同一處提高的是證據強度，不決定要不要修。

規則類文件是理解探針的高價值對象：一條規則被讀錯，往後每個 session 都會照錯的版本執行。低階模型在事實正確性、跨檔一致性、承重論點的反證三個面向上不可信，那些仍要高階 reviewer；大量已知形態的掃描用 grep。

**術語探針判成「本批無結論」的詞**（測試詞寫在探針讀得到的系統提示裡，而探針複述了那份定義）：在本 repo 裡重派探針也讀得到同一份系統提示，重測量到的仍是詞頻。在 commit message 登記這個詞「待驗」與原因，寫進給使用者的最後一則總結；要結論時，交給讀不到本 repo 規範檔的讀者判讀（使用者本人，或另一個目錄裡、不載入這些規則檔的 session）。

探針的其他用途（重點涵蓋度、閱讀負擔、翻譯探針、術語探針、類型探針、集合探針）、各自的設計條件、處置門檻與判讀方式，以 `multi-round-review` 的 `references/round-2-probes.md` 為準。Codex 沒有派發子 agent 的工具時，探針那一項的紀錄寫「未跑」與原因，不拿自己的閱讀代替探針。
