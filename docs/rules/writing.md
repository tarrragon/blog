# 文章的定位、讀者、結構與 description

這份分冊管 `content/` 文章怎麼寫：文章的定位與它對應的體例、讀者設定、文章的結構（開場、標題、段落、拆篇、表格、判斷標準），以及 `description` 的體例。句子層的規則（槽位、命名、術語）在 `sentences.md`，寫作的步驟與紀錄在 `writing-process.md`。

## 文章的定位與體例

### `content/` 文章的定位：教學；目錄頁與 report 卡另有體例

`content/` 底下的文章是教學定位：讀者是來理解一件事的人。講 mdtools 與 Markdown 規範的那幾篇也一樣，它們向人解釋規則與理由，機器要執行的部分住在 `scripts/mdtools`。`record/` 的方法論文章是寫給來理解一種工作方式的讀者，同樣是教學定位；它多半不排在任何教學模組的序列裡，讀者帶著一種工作方式的疑問搜尋過來，所以 `description` 多半照觸發條件寫，判定照〈`description` 的體例〉的判斷問句。`work-log/`、`til/`、`other/`、`books/` 的文章也是教學定位，套這份分冊的規則；`work-log/` 與 `report/` 另外是檢討內容，加套〈寫給帶著疑問來查的讀者〉的客觀條件那一條。`record/` 裡 frontmatter 帶 `archived: true` 的是封存的舊文，不為了新規則回頭改；要改它的內容時，先拿掉 `archived`，再照現行規則改寫。

兩個位置不套教學體例：

- **`_index.md` 是分類的操作手冊**：成員表、場景導讀、Backlog、路由。使用者是要找落點的人與維護這個分類的 agent，所以它該有編號、清單、查表用的對照欄。
- **`report/` 是歸納層**：一張卡記下發現的一類缺陷、它的解法與成因，結構以結論開頭（見`content-folders.md`〈文章放在哪一個資料夾〉的表）。可以照著執行的處理方式與判斷方法寫在 skill。report 卡以結論開頭，所以四條結構規則不適用於 report 卡：〈標題與段標寫主旨〉、〈開場列出這篇討論的內容〉、〈段落的第一句寫這一段的主題〉，以及〈寫給帶著疑問來查的讀者〉裡的結論位置。同一節的「檢討內容以客觀條件組織」、〈推導過重時拆篇，不壓縮成一句話的結論〉與 `sentences.md` 的句子層規則照樣適用。

掃教學體例時，把 `_index.md` 與 `content/report/` 排除在外。

### 教學的產出形式

教學的產出是有序的說明，特徵如下：

- **有脈絡**：每一節帶著自己的上下文，讀者從任一節進來都跟得上；反覆使用的名字第一次在那一節出現時，連回或指出它被界定的位置（`sentences.md`〈先界定一個概念並命名，之後用名字引用〉）。
- **有原理**：每個指令旁邊寫它為什麼這樣用、背後的機制是什麼。
- **主詞與受詞完整**：每一句寫清楚是什麼工具對什麼對象做了什麼事（見`sentences.md`〈句子的槽位〉）。
- **輸出的讀法寫在指令旁邊**：一個指令的輸出有多種讀法時，在指令旁寫出該看的欄位與它代表什麼，不寫成提醒句讓讀者自己想出正確做法。改前：「不能預設第一行就是有焦點的那一組」。改後：「`dumpsys window` 在多螢幕的機器上替每個顯示器各印一組 `mCurrentFocus` 與 `mFocusedApp`，沒有焦點的顯示器這兩個欄位的值都是 `null`。所以值不是 `null` 的那一組屬於有焦點的顯示器。」改後那一句寫的是欄位的值代表什麼（讀法），不是要讀者做的動作。

### 三種書面產出的體例

同一套寫作規範還服務另外兩種書面產出，而它們的讀者不同：

| Surface           | 讀者               | 體例                                                                           |
| ----------------- | ------------------ | ------------------------------------------------------------------------------ |
| `content/`        | 來理解一件事的人   | 引導與脈絡：寫出為什麼是這個順序，讀者要的是判讀的依據                         |
| `.claude/skills/` | 照著執行的 agent   | 操作手冊：步驟編號是執行的位置，要寫判錯的代價，因為執行者需要知道哪一步不能錯 |
| 程式碼註解        | 正在讀那段程式的人 | 只解釋商業邏輯，原理讀程式碼就有                                               |

`content/` 裡也有讀者會在自己的環境照著做的程序（安裝步驟、遷移步驟、導入順序）。這類程序可以寫成編號步驟，因為讀者要的正是一個不會漏步的順序；每一步旁邊寫出它為什麼在這個位置、做錯會看到什麼，讓讀者在環境跟文章不一樣時判斷得了。程序以外的段落照教學的體例寫，〈文章被寫成手冊的裝置〉的掃描也只用在程序以外的段落。

為 skill 或註解設計的規則，啟動條件常常只比對文章的形狀，套到教學文章上時每一步都合規而文章被寫成手冊。所以套用一條規則之前，先確認這篇文章的定位符合那條規則的前提：讀那條規則的依據卡，找出它當初處理的是哪一種 surface 的讀者。依據：[定位決定體例，而共用的寫作規範會把一個 surface 的體例搬到另一個上](/report/positioning-decides-form-before-any-rule-applies/)。

### 文章被寫成手冊的裝置

判斷一篇文章是教學還是手冊，看讀者讀完之後那個動作落在哪裡：在世界上動手，是手冊；在腦中重新歸類，是教學。教學也會給辨識訊號與可以改的東西，所以「內容裡有沒有可執行的東西」分不開兩者。

會讓文章被讀成手冊的裝置有七種。逐節掃這些裝置，命中時改框架、資訊保留，各自的改法：

- **表徵對映的處置清單**（「看到症狀 X → 做 Y」）：右邊換成成因與它的後果（「症狀 X 代表 Z 處在什麼狀態，原因是……」）。「症狀 → 成因」本身是歸類，是教學；變成手冊的是箭頭右邊的祈使動作。
- **檢查順序的指示**（「先查 A 再查 B」）：寫出這個順序的理由（A 的結果決定 B 要不要查、A 比較便宜）。
- **配比與參數數字**：寫出數字從哪裡來、改大改小各換到什麼；特定實例的值照〈不寫會取代讀者查證的值〉處理。
- **順序關鍵加上顛倒的後果**：改寫成「順序在這裡有什麼物理意義」（哪一步的輸出是下一步的輸入）。
- **可執行的操作判斷標準**（「超過 N 就做 X」）：改成〈判斷標準寫成條件、後果與理由〉的寫法。
- **具體器具與工具作法**：保留工具名與作法，補上它在這個機制裡負責哪一段，讀者換工具時知道要找的是什麼功能。
- **序列連接詞**（先、之後、最後）：這一種最容易漏，把步驟編號換掉之後，「先…之後…最後」仍然讓讀者預期自己要照著做。改成寫出前後兩件事之間的依賴。依據：[定位決定體例，而共用的寫作規範會把一個 surface 的體例搬到另一個上](/report/positioning-decides-form-before-any-rule-applies/)（七種裝置與序列連接詞的量測）。

## 讀者設定

### 讀者是缺經驗的專業工程師

本站的讀者是專業工程師：了解研究方法、理解開發原則、知道如何邏輯推導、有開發經驗。這個設定描述的是讀者理解得了多深，不是讀者已經知道哪些名詞、原理與縮寫。讀者在乎每個流程的原因、成本與代價，以及用詞的精準：`2*4` 與 `1*8` 算出同一個值，而在程式裡一個是兩組各四個、一個是一組八個，排程與資源配置都不同；操作說明裡「查看」是打開來讀內容，「看」可能只是瞄一眼畫面，兩個動詞交代的動作不同。所以動詞與名詞不任意縮寫，這條設定也推向展開：每一句寫出是什麼元件跟什麼元件產生反應、是誰做了什麼動作、對誰產生影響。

判斷問句：這一處省略，省下的是讀者不需要的字，還是讀者要自己補回來的脈絡。後一種就展開。省略在產物上沒有痕跡（沒補的卡不存在、沒展開的原理不佔行數），所以靠 `knowledge-cards` 的缺卡判定矩陣（見`sentences.md`〈術語的解釋方式〉）與理解探針偵測。

- 文中不使用「新手」「新人」字樣；讀者是缺經驗的專業人士，不是外行人。
- 用現實服務的案例補足經驗差距，技術深度不降低。
- 講究細節會產生大量各自需要定義的名詞：照`sentences.md`〈建卡原則〉替它們建知識卡，各篇連到卡，不在每一篇從頭解釋。

依據：[讀者是缺經驗的專業人士、不是外行人](/report/audience-is-professional-not-layperson/)、[讀者定位擋住科普化的同一句話，供應了省略解釋的理由](/report/audience-level-licenses-omission/)。

### 不預設讀者熟悉特定專案

教材不預設讀者熟悉某個內部專案（例如 ccsession），不把專案私有的運作細節當成理解前提；用獨立範例、通用情境與虛擬程式碼說明。

### 不寫會取代讀者查證的值

特定機型、特定環境、特定安裝的值與處理方式不寫進文章：文章寫了那個值，該去自己機器上查的人會改讀文章，而特定實例的值正好是他那一台會不一樣的那些。

判斷問句：讀者拿這一句去用，他是去查自己的系統，還是直接照抄。照抄的那一種要改寫：寫出該去哪裡查（「接上機器跑一次就知道手上這台實際填了什麼」）；機制需要具體例子才講得清時（跨層的表示法差異、欄位的形狀），換成明顯的佔位值並寫明它是佔位的。機制、規範定義與公開 API 的行為在每一台機器上相同，不受這一條約束。

標註「未驗證」不夠：標註要讀者讀到那個標記才生效，而照抄的人多半從搜尋直達那一行、複製、離開。沒有硬體時，可以寫的是問題的形狀與該去哪裡查。

### 寫給帶著疑問來查的讀者

教學與檢討內容的讀者由搜尋或站內路由帶來，自己帶著要查的事。演講技巧（問句標題、懸念段標、三幕劇遞進）服務的是注意力會流失的聽眾，不用在這裡。

- **結論位置**：案例是推導的材料，結論與判斷標準寫在推導走完的位置；讀者讀完推導自己得出判斷標準。其他規則寫「結論位置」時指的就是這一條。把判斷標準壓到文末扣住是懸念，把結論抽成開頭一段要讀者先記住是灌輸，兩者都讓結論與推導脫節。
- 判斷標準的執行步驟可以寫成問句（「唸出型別名稱後還剩什麼」）。標題、段標與結論位置不用問句。
- 檢討內容（work-log、report）以客觀條件組織：「reviewer 問了 X、後來才想清楚」寫成「若對這個做法問 X 而答不出來，就該重新檢討」。
- **事件說明**：內容來自實際事件時，在開場之前寫一段事件說明，只寫事件的日期、環境（哪一種機器、什麼版本、什麼設定）與當時在做的操作。症狀與結果不寫進事件說明：它們是正文要推導的對象，寫在開場之前就成了〈開場列出這篇討論的內容〉不用的情境故事。事件說明交代來源，不摘要結論；「觸發場景／疑問來源／整理目的／本文邊界」這類把各段結論先摘出來放在推導之前的欄位組不建。正文用條件語言承載脈絡。work-log 的寫作模板在 `content/work-log/_index.md` 的〈寫作模板與語域〉。

依據：[教學與檢討內容寫給帶問題來的讀者，不是要被吸引的聽眾](/report/write-for-readers-not-audiences/)。

## 文章的結構

### 開場列出這篇討論的內容

讀這篇的人不一定知道這個主題由哪些部分組成，所以開場要讓沒有這個主題知識的讀者，讀完就能判斷這篇跟他要找的內容有沒有關係。做法是逐一列出各段落的主題，寫到讀者能逐項對照自己需要的程度。適用的版本與環境、這篇沒有處理的面向、另有專篇的主題，接在內容說明之後。另有專篇的主題寫成本篇的內容說明，並寫出那一篇給什麼（「Wi-Fi 配對與連線的步驟在〔…〕」），在開場裡不寫成「遇到 X 時去讀 Y」（正文的跨篇連結另有三種寫法，見 `writing-process.md`〈教學文章的脈絡〉）。開場是交代本篇範圍的位置，所以在這裡寫主題的邊界是完整的寫法；它不取代正文裡的跨篇連結，正文寫到某個可動項時照 `writing-process.md`〈教學文章的脈絡〉再連一次。文章前面有事件說明時（〈寫給帶著疑問來查的讀者〉），開場是事件說明之後的第一段。

只寫範圍不夠。「範圍從 A 開始，到 B 為止」要讀者先知道整個主題由哪些部分組成，才看得懂 A 與 B 之間有什麼。開場也不用情境故事：讀完一段故事，讀者仍然不知道這篇有哪些內容。

- 改前（情境故事）：「本篇的情境來自一次實際排查：用 `adb install` 安裝同一個 APK 執行成功，改由 App 自己下載 APK 再呼叫系統的安裝程式時，安裝程式顯示一個對話框，安裝沒有繼續進行⋯⋯」
- 改前（只交代起點）：「這篇整理電腦經由 Wi-Fi 用 adb 連線到 Android 手機之後，遠端排查用到的指令與注意事項。範圍從 `adb devices` 列出那台手機開始。」
- 改後：「這篇整理電腦經由 Wi-Fi 用 adb 連線到 Android 手機之後，遠端排查用到的指令：在多台裝置中指定要操作的那一台、擷取螢幕畫面與錄影並確認傳回的檔案完整、查出畫面最上層是哪個 App 的哪個 Activity、用 logcat 篩出某個元件啟動前後的紀錄、查詢 App 權限與使用者限制這類狀態，以及放寬安裝管控的修改型指令。Wi-Fi 配對與連線的步驟在〔Android 無線調試連接指南〕。」

依據：[教學定位被讀成教室講課，產出的是經營注意力的障礙而非有序的說明](/report/teaching-is-not-lecturing/)、[把 description 寫成觸發條件，文章就變成那個問題的答案](/report/description-frames-the-article/)。

### 標題與段標寫主旨

標題寫這一篇講的對象與交付的內容種類（機制、取捨、流程、判讀），冒號之後寫涵蓋的成員；段標寫這一節講的對象。「X 決定 Y」「X 不是 Y，是 Z」「X 才是 Y」這類斷言留在結論位置（〈寫給帶著疑問來查的讀者〉）：讀者在乎那句結論的理由是正文建立的，而標題是他讀正文之前看到的那一行，被別篇當成連結文字時，他連本篇的主題都還不知道。讀得懂的結論句也要改，因為寫標題的人手上有全部前提，分不出哪些是讀者進來之前就有的。

檢查方法：把標題當成別篇裡的一個連結文字讀一次，逐項問有沒有謂語在下斷言、每個名詞沒讀過本篇的人認不認得、只憑這一行說不說得出這一篇的對象與內容種類。描述這一篇做什麼事的「對象＋動詞」寫法是主旨（「從入口程式看應用啟動流程」）。

- **段標單獨拿出來要讀得出這一節講的對象**：「往下讀」「判讀方式」「為什麼只收這幾本」沒有下斷言，而不讀內文的人不知道判讀的是什麼、「這幾本」是哪幾本。把指示詞與泛用標籤換成它指的對象；同一個標籤在多篇重複出現時，每一篇各自寫出自己的對象。
- **固定收尾段名也要寫出對象**：「下一步路由」「判讀訊號」「往下走」寫成「內容種類：那一節實際連到或判讀的對象」（「延伸閱讀：對手方、槓桿的強制平倉與機會成本」）。
- **寫不出有意義主旨的段標就移除**，那一節併進相鄰的節。
- 標題為了寫出成員而變長是可以接受的。

這一條適用於 `content/` 的教學文章，不適用於 report 卡。依據：[教學文章的標題與段標寫主旨，結論留在正文裡推導走完的位置](/report/title-states-the-subject-not-a-premised-conclusion/)。

### 段落的第一句寫這一段的主題

開場以外的每一段，第一句寫這一段談的對象與它的屬性（主題句）：這個概念是什麼、承擔什麼責任；例子與補充接在後面，提醒與邊界放最後。先丟案例、最後才補定義的段落，讀者讀完案例還不知道它在示範什麼。主題句寫的是對象，不寫「這一段在做什麼」這種文章的自指，也不寫這一段推導出的結論：一段要推導出判斷標準時，第一句寫要判斷的對象與它的屬性，判斷標準本身寫在結論位置（〈寫給帶著疑問來查的讀者〉）。

- 改前：「cursor 要拆成兩張知識卡。它在分頁裡指接續標記……」（第一句是推導出的結論）
- 改後：「cursor 在分頁裡指接續標記、在資料庫裡指查詢結果的讀取物件，兩個所指的擁有者與生命週期都不同。……所以拆成兩張卡。」（第一句寫對象與屬性，結論在推導之後）

描述一個工具或指令的操作要寫成好幾段時，段與段之間的預設順序跟著讀者的疑問：讀者會看到什麼 → 這個工具做什麼 → 為什麼需要它（機制，指名系統元件）→ 不做的具體後果 → 副作用。這個順序管的是操作說明；解釋一個概念的段落照〈系統層的概念寫在案例之前〉，先寫概念再寫案例。情境要求別的順序時照情境寫，這個順序不是每篇都要套的模板（〈每個情境用它自己的敘事，不套共通模板〉）。每一段的第一句仍然是那一段的主題句。

文章的開場（第一段，或事件說明之後的第一段）由〈開場列出這篇討論的內容〉管：它的職責是讓讀者判斷這篇與他要找的內容有沒有關係。依據：[規範指定了某個位置要交付什麼，全批長成同一個模板時沒有任何一道檢查管得到](/report/mandated-section-hides-its-own-sameness/)。

### 推導過重時拆篇，不壓縮成一句話的結論

文章要讓讀者確實跟上討論與推導的過程，所以推導寫完整，不用「一句話」交代、解釋或總結。這裡的「一句話」指只交付結論、把推導省掉的寫法，不論它實際佔一句還是幾句：開場的內容說明、規則的理由、判斷標準、概念的引入，都寫出讀者跟得上的推導；結論寫在結論位置（〈寫給帶著疑問來查的讀者〉）。用一句話帶過預設了讀者只想看結論，而讀者要的是推導。

推導可以住在別處，只要讀者拿得到：同一份文件裡、或一個連結就到得了的位置（report 卡、record、skill 的 principle 卡：skill 裡複製 report 卡而成的副本，見 `skills.md`〈Skill 的依賴邊界〉）有完整推導時，這一處寫出結論、讓讀者判得出適用邊界的理由，再連過去，就不算壓縮。skill 與規則檔照這個方式寫，推導住在 report 卡。這一條適用於全部書面產出（範圍定義在 `AGENTS.md`〈改動的級別〉），`content/` 的 report 卡也包括在內。

檢查方法：逐個理由句與判斷標準問，讀者只讀到這裡，說不說得出這個結論是怎麼來的；說不出來，就把推導補進來，或依下面的方式拆篇。

推導寫得太重時，處置是拆分。推導過重的訊號是讀者要同時記住好幾個還沒具名的指涉、一節裡有兩條以上互相獨立的推導線，或文章超過 `content-folders.md`〈目錄頁 `_index.md` 與文章檔的分工〉表裡的內容量參考；有這幾個訊號之一時，用理解探針的閱讀負擔用途量（見 `multi-round-review` 的 `references/round-2-probes.md`），作者自認讀得通不改變這一步。訊號只決定要不要量；拆不拆看量的結果，探針回報同一處要同時記住的指涉超過它跟得上的量時，照下面的方式拆：

- **文章太長**：拆分篇幅，每一篇承擔推導的一段。
- **內容太複雜**：依專業度與難度深淺拆成幾篇，基礎的那一篇先建立後面要用到的概念。
- **內容跨領域**：各領域各寫一篇分析文章，複合領域的那一篇用連結導到單一領域文章，讓讀者延伸討論或補充知識。

### 表格裡的判斷要有出口

表格裡承載推導的每一個「情境 / 判斷」都要有出口，出口有三種：

- **就地展開**：表格下方加延伸段落，寫出這個情境在真實服務長什麼樣、為什麼成立、常見陷阱是什麼。
- **拆卡外部化**：概念與範例住進知識卡，文章保留「什麼情境用哪張卡」的判讀敘事。
- **換成連結**：那個概念已經有卡或有專章承載時，格內不寫自撰的簡述，直接連過去。

壓縮判斷標準去遷就格寬不在出口之列。選出口看概念在本篇的角色：主線概念（本篇論證繞著它轉）就地展開，因為外部化會讓讀者跳出去讀卡而中斷論證；支撐與背景概念可以拆卡或換連結（角色的定義見`sentences.md`〈術語的解釋方式〉）。

- **選出口之前**，先查這個概念在別篇有沒有不相容的版本：兩篇各給一套階段表或欄位組時，三種出口都會把矛盾保留下來。
- **「換成連結」的前提是本篇的主線不靠它**：驗收方法是把所有往外的連結當成不存在重讀一次，剩下的內容該長什麼樣依這一篇的定位而定（教材要剩得下論證，術語卡剩下定義是正常的）。
- **右欄寫判定的查表型表格不需要延伸段**：判讀徵兆表、「訊號 → 判定」對照表、關係表的讀者是逐列查詢，每一列自足即可。判定看讀者怎麼使用，不看表格密度。右欄寫的是判定、歸類或後果時屬於這一種；右欄寫的是祈使動作（「訊號 → 該做的事」）時，那是〈文章被寫成手冊的裝置〉的表徵對映處置清單，右欄改寫成判定或後果。

依據：[內容超出容器時擴充結構、不壓縮內容](/report/content-pressure-resolves-by-expansion-not-compression/)、[同一個對象被兩篇各自分解一次時，不相容會長得像互補](/report/incompatible-decompositions-look-complementary/)、[串連佔掉的是本篇的篇幅，順序要先自足再往外開門](/report/cross-links-eat-the-article-they-live-in/)、[語句要在它的消費單位內資訊自足](/report/sentence-self-sufficiency-by-consumption-unit/)。

### 每個情境用它自己的敘事，不套共通模板

情境的屬性包括業務壓力、資料形狀、流量型態、組織能力、合規壓力、失敗條件與失敗代價、回退路徑。這些屬性不同的情境，各自用該情境的敘事與判讀條件寫，不為了整齊而把案例、反例、規模對照或絆腳索（tripwire：預先設定、到達時就重新評估決策的條件，見 `AGENTS.md`〈決策分析：WRAP〉）抽成共通模板；案例、反例、絆腳索、規模對照都用該情境的屬性寫成它自己的語言。表格只用來整理資訊；欄位化之後內容變得僵硬、抽象或遺失細節時，改回段落式說明。

寫作檢查時問：這一段是不是把不同情境塞進同一組欄位。是的話，先改寫成該情境自己的判讀問題與操作條件。

### 判斷標準寫成條件、後果與理由

教學文章要寫出判讀訊號、風險、邊界與下一步路由，只寫名詞定義不夠。知識卡與 `til/` 的單一知識點不受這一條約束：它們交付的就是定義與它的由來。判斷方式：拿一個本篇沒有寫到的情境照本篇走一次，讀者能不能判斷出自己落在哪一個條件，以及各條件的後果與理由。判斷標準停在「判斷看 A、B、C」時，讀者知道要看哪些面向，卻不知道每個面向落在哪裡代表什麼，要補成條件、後果與理由。

寫法的界線在箭頭右邊：「A 成立時，系統處在 Z 狀態，代價是……，原因是……」是教學，讀者讀完在腦中重新歸類自己的情境；「看到 A → 做 X」是〈文章被寫成手冊的裝置〉裡的表徵對映處置清單，讀者讀完會在世界上照做。後一種不寫進教學文章，要讓 agent 照著執行的行動對應寫在 skill。讀者真的要照做的程序，照〈三種書面產出的體例〉的程序寫法。依據：[判斷標準要寫到條件層：維度清單是判斷標準的空殼](/report/criteria-need-condition-action-mapping/)、[定位決定體例，而共用的寫作規範會把一個 surface 的體例搬到另一個上](/report/positioning-decides-form-before-any-rule-applies/)。

### 系統層的概念寫在案例之前

先寫系統層的概念（為什麼存在、處理什麼需求），再寫具體案例；只給設定值或語法片段時，讀者拿到的是無法遷移的答案。

### 主要敘述用正向陳述

主要敘述用正向句建立概念。反例段落可以存在，用途是對照；否定句不主導段落。完稿後照 `compositional-writing` 字句層 keyword bank 的〈正向陳述優先〉一類掃一次（否定起手的定義句是那一類裡的子 pattern）（規則檔不複製詞表，詞表以 skill 為準），命中之後判斷核心概念第一次正面出現的位置在句首、還是被擠到「而是」之後；被擠到後面時，把核心概念改寫成正向句放在句首。依據：[重點優先陳述是跨語言的資訊結構原則、不是中文句型問題](/report/lead-with-the-point-cross-language/)。

## `description` 的體例

`description` 是文章的輔助說明，體例分兩種。判別時問：讀者讀到這句 `description` 的時候，他在決定什麼。

- 讀者在**掃列表決定要不要進去** → 寫成**觸發條件**（什麼情境下需要回來讀）。他還沒決定要讀，這句話要幫他判斷這一篇關不關他的事。
- 讀者**已經決定要讀、想先知道範圍** → 寫成**涵蓋交代**（這一篇涵蓋什麼、交付哪一段觀念）。

這個問句是判斷標準本身；下面的分類是把它套到常見情形的結果，兩者衝突時聽問句的。

- **涵蓋交代**：`content/` 下規劃在序列裡的文章與章節（教材），讀者是照路線走到這裡的；`books/` 的導讀，讀者是從書單的路線走進來的。
- **觸發條件**：`work-log/` 的排錯記錄、`posts/` 的文章（本站規範、Hugo 與 Markdown 的經驗、事件紀錄）、工具筆記、知識卡、`report/` 的卡、`record/` 的文章、`til/` 的知識點、`other/` 的雜項筆記（讀者帶著一件要查的事搜尋或掃列表過來），以及各分類的 `_index.md`（掃列表的位置本身）。
- **一篇有兩條到達路徑時**（`posts/` 的規範文章被規則檔指定為必讀、又出現在站上的列表），照列表那一條寫觸發條件：被指過來的讀者已經決定要讀，`description` 對他沒有作用；掃列表的讀者還沒決定，這句話對他才有作用。
- **`content/skills/` 的鏡像**：`bin/skill-mirror` 保留鏡像自己的 frontmatter，`description` 照觸發條件寫。
- **知識卡不論放在哪個分類、有沒有被排進教學模組，一律寫觸發條件**：讀者到達它的方式是帶著一個術語來查，這跟檔案位置無關。

`description` 寫成「遇到 X 時」，文章就得是 X 的答案，而教材照讀者遇到的處境組織時，沒遇到那件事的讀者永遠不會知道它。所以文章從標題發想，`description` 從文章發想。教材的四種觸發句型（以「⋯⋯時」收尾、「想知道／想確認／想判斷」起手、症狀寫在前面、問句）是候選，命中之後問這一句有沒有把讀者的處境當成本篇的目的。只避開這四種句型不等於合規：沒有命中任何一種的句子仍然可能把本篇寫成某個處境的答案，而以「時」收尾的句子也可能沒有這個毛病，所以判定看那個問句，不看句型。

兩種體例共用的規則：

- **驗收**：遮住 `description`，只看標題就猜得出全部內容 → 沒有增量 → 重寫。
- **內容**：只寫標題說不完的範圍與交付內容，操作細節留在內文。內文調整之後 `description` 就過時，代表它寫了不該寫的內容。
- **四不要**：不塞操作細節、不加假設前提（「想不起來」「卻發現」）、不用情緒修辭（「別被騙」「打架」）、不內嵌數字（「三項」「6 段」）。

依據：[把 description 寫成觸發條件，文章就變成那個問題的答案](/report/description-frames-the-article/)、[查閱型內容的 description 是未來自己的 recall trigger](/report/description-as-recall-trigger/)。
