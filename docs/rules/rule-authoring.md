# 規則的住址與寫法

這份分冊管每一種內容的住址、入口檔與分冊的分工、新增或修改規則時要寫出什麼，以及各 agent 讀到哪些檔案。`bin/rule-route` 對規則檔、`bin/` 與 `.claude/hooks/` 的路徑都會列出它。

## 入口檔與分冊的分工

`AGENTS.md` 是每個 session 都載入的入口，要讀哪幾份分冊照 `AGENTS.md`〈怎麼讀分冊〉。入口越長，agent 越容易漏掉其中的規則，而且 Codex 自動讀專案指令檔時有位元組上限（`project_doc_max_bytes`，預設 32 KiB），它載入的全部 AGENTS.md 合起來算進同一個上限，超過的部分不會進它的 context。入口的上限訂為 14 KiB，每份分冊的上限是 60 KiB（超過時 Read 回傳截斷的內容）。pre-commit 跑 `bin/rule-route --check-staged` 檢查這兩個上限、路徑表，以及路由表指到的分冊都存在，有一項不成立就擋下提交。超過上限的處置是把內容移到分冊或拆成兩份：訂這個上限之後，寫規則的人新增內容時要先寫進分冊；這個數值跟遵守率的關係沒有量過。`CLAUDE.md` 只放任何 session 都可能碰到、由一個動作觸發的 Claude Code 操作。

入口放這些內容：做哪一件事之前讀哪一份分冊的動作清單與路徑表；每一類工作都用得到、或違反時造成難以回復後果的規則，完整寫在入口，分冊只補適用範圍與細則，不重述（`AGENTS.md`〈回覆語言〉〈破壞性指令的目標寫在指令文字裡，檢查與刪除分成兩次執行〉）；被兩份以上的分冊引用的定義（`AGENTS.md`〈改動的級別〉）；連到分冊的一句話，寫出這個動作用哪個工具（`AGENTS.md`〈提交〉）。其餘的規則寫在分冊。那一句話跟分冊不一致時，以分冊為準，並在同一次改動把入口改成一致。

新增規則時，先判斷它的觸發條件：由這次要改的路徑決定的，寫進路由對到的分冊；由一個動作決定的（提交、派 agent），寫進那個動作的分冊；符合上一段「完整寫在入口」條件的（刪除），寫進入口，細則寫進那個動作的分冊。新的路徑或動作沒有對應的分冊時，先選定一份分冊或新開一份，再把路徑同時加進 `bin/rule-route` 的路由表與 `AGENTS.md`〈怎麼讀分冊〉的路徑表，把動作加進同一節的動作清單；要由 hook 檢查的動作，另外加進 `.claude/hooks/rule_read_guard.py` 的 `BASH_ACTIONS`。

## 規則的住址

**住址**：每一條規則、每一個被兩條以上規則用到的概念，都只寫在一個位置，其他位置用連結指過去。同一件事寫在兩個位置時，沒有任何工具會偵測兩份分歧：修改的人只改其中一份，照著舊的那一份工作的 agent 會做錯。超過一句話的摘要與轉述也是副本：路由表轉述分冊的觸發條件、入口重述分冊的掃描範圍，都會在原文改動之後過期。分工如下：

| 內容                                                                   | 住址                                                              |
| ---------------------------------------------------------------------- | ----------------------------------------------------------------- |
| Claude Code 與 Codex 共用的寫作規則與工程規則                          | `AGENTS.md` 與 `docs/rules/` 的分冊，分工見〈入口檔與分冊的分工〉 |
| Claude Code 專屬的操作                                                 | `CLAUDE.md`（任何 session 都可能碰到的）與 `claude-code.md`       |
| 可以照著執行的偵測細節（字句層 pattern、探針的派發與判讀、審查 frame） | 對應的 skill；規則檔寫規則與判斷標準，並連到 skill                |
| 超過一條指令、或帶分支的操作程序                                       | `bin/` 的工具與 `bin/tests/` 的測試                               |
| 規則的推導、實測紀錄、事件經過與量測數字                               | `content/report/` 的卡；規則檔寫規則與理由，連到那張卡            |
| 工具自己的行為（參數、內部邏輯、維護方式）                             | 工具的檔頭註解、README 或它的 skill                               |

例外是刻意建立、而且有工具比對的副本：skill 的 principle 卡是 report 卡的副本（`scripts/principle-mirror-check.py` 比對），`content/skills/` 是 skill 的鏡像（`bin/skill-mirror` 產生），`AGENTS.md`〈怎麼讀分冊〉的路徑表是 `bin/rule-route` 路由表的副本（`bin/rule-route --check-staged` 比對）。一處完整、別處一句話加連結不算副本。

## 新增或修改規則時

**新增或修改規則時**，在 `AGENTS.md` 或分冊寫出四件事：規則本身、執行者用來判斷的標準、判斷之後的處置、讓執行者判得出適用邊界的理由；推導過程與「先前怎麼寫、後來為什麼改」寫進 report 卡或 commit message。寫的時候守下面這幾條：

- **程序寫成工具**：要執行者照順序跑兩條以上指令、或依輸出走不同分支的程序，寫成 `bin/` 的工具並在 `bin/tests/` 附測試，規則檔只寫什麼時候跑、輸出怎麼讀、非零的 exit 怎麼處置，這三項跟著工具同一次改（`rg -n '<工具名>' AGENTS.md CLAUDE.md docs/rules .claude/skills` 列得出位置）。規則檔裡的指令沒有測試，寫的人自己也常常沒跑過，而照做的 agent 會逐字照抄。`python3 -m unittest discover -s bin/tests` 的輸出要是 `OK` 而且沒有 skipped：跳過的測試照樣印 `OK`，等於沒有在測。單一條、沒有分支的指令（一條 `rg`、一條 `git log`）可以留在規則檔，寫之前照 `AGENTS.md`〈掃描工具的零輸出〉跑一次正對照。
- **共用的概念先定義再引用**：兩條以上的規則要用到同一個概念（改動的大小、要停下來問使用者的時機）時，在一個位置定義並命名，其他規則寫名字、連過去，不各寫一份例外。定義時寫出這個概念在工作流程的哪一步之後才查得到：用它當觸發條件的規則，動作不能排在那一步之前。「只有 N 種」這類封閉的列舉只寫在那個唯一的住址，因為別處的規則一新增情形，它就默默失效。
- **觸發條件寫成查得到的事實**（指令的輸出與 exit、檔案、diff、frontmatter 欄位、這次要改的路徑），不寫成執行者的身分或主觀狀態（「拿不準時」「懷疑時」）。非用主觀狀態不可時，加一句「執行者自認不成立，不改變本款結果」，因為會誤判的人正是不認為自己在誤判的人。
- **寫作規則的每一節標出時機**：在 `writing.md`、`sentences.md`、`writing-process.md`、`review.md` 新增一節規則時（只定義用語的節不寫），標題下第一段照 `writing-process.md`〈規則的三個時機〉寫 `**時機**`，只寫動筆、審查、收尾這三個詞。適用條件與檢查方法留在正文：寫成一行摘要時，這一行會比正文窄，執行者照它做完仍可能違反正文。
- **放對檔案**：加一節之前問兩件事：這一節的修改理由在不在這份檔案既有的主題裡（不在就放進對應的分冊或新開一份）；Codex 需不需要它（需要就寫進 `AGENTS.md` 或分冊，只有 Claude Code 才有的操作才寫進 `CLAUDE.md` 或 `claude-code.md`）。

依據：[規則檔的修法逐輪製造新歧義：程序寫成有測試的工具，共用的概念只定義一次](/report/rule-patches-breed-new-ambiguity/)、[規則的修法逐句驗證會通過、套到案例上才互撞：改完才查得到的事實管不了動手之前的步驟，修完要拿任務重走](/report/rule-fixes-pass-per-sentence-and-collide-per-case/)。

## 各 agent 讀到的檔案

本 repo 同時支援 Claude Code 與 Codex（以及其他遵循 AGENTS.md 標準的 agent），目前以 Claude Code 為主。

| 檔案              | 角色                                                           | 誰讀                                                                   |
| ----------------- | -------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `AGENTS.md`       | 規則的入口：任何 session 都可能碰到的規則與讀分冊的清單        | Codex（自動讀）、Claude Code（經由 CLAUDE.md 的 `@` 匯入）、其他 agent |
| `docs/rules/*.md` | 各類工作的規則分冊                                             | 所有 agent 照 `AGENTS.md`〈怎麼讀分冊〉讀                              |
| `CLAUDE.md`       | Claude Code 任何 session 都可能碰到的操作，開頭用 `@` 匯入入口 | Claude Code                                                            |
| `.codex/`         | Codex 的工作簡報（`briefs/`）與讀取順序說明（`README.md`）     | Codex；規則以 `AGENTS.md` 與分冊為準，簡報與規則衝突時照規則           |

`@<file>` 是 Claude Code 專屬語法，Codex 不解析。`@` 匯入的檔案在 session 啟動時全文載入，這些全文佔用每個 session 的 context，所以 `CLAUDE.md` 只匯入 `AGENTS.md`，分冊不用 `@` 匯入。新增規則時依〈規則的住址〉決定寫在哪一份；Codex 專屬的規則（如果有）寫在 `AGENTS.md`，標明 `[Codex only]`。兩個 agent 共用同一份 skill 目錄的方式與拆開的訊號，在 `docs/rules/skills.md`〈Claude Code 與 Codex 共用的 skill 目錄〉。
