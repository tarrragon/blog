這個資料夾收錄**工程之外學到的小知識**（TIL、Today I Learned）— 單字字源、概念由來、歷史冷知識、科學概念都算。一篇只說一個知識點、寫下「當初是怎麼理解的」、之後忘了可以回來查。

子分類：

- [單字](vocab/)：學到的英文單字 — 字源拆解、由來故事、同字根家族、語感差異與搭配
- [跨領域術語](terms/)：同一個概念在不同領域的稱呼 — 一個領域 framing 一篇、互連成「概念↔領域語」地圖
- [數學概念](math/)：數學概念與定理 — 前置概念與定理各自成篇、匯聚到主題文章；目前圍繞緊緻性這條概念線展開
- [組織概念](organization/)：別的學科用來解釋群體怎麼運作的概念 — 體制怎麼編成、指揮怎麼分線、群體怎麼累積偏差、裡面的人敢不敢說話
- [人的行為概念](behavior/)：別的學科用來解釋個人怎麼判斷與反應的概念 — 認知的系統性偏差、壓力下的反應姿態
- [料理](cooking/)：辨別兩道菜哪裡相同、哪裡不同 — 各地相近的是手法，而目的、調味、材料與名字各自不同；從名字、形態、手法三個方向查同一批菜

開子分類的判斷標準是寫不寫得出一句「這裡收什麼」，而那句話要寫明收錄範圍、不是複述裡面某一篇的標題。寫得出來就開，一篇也可以開；寫不出來就留在根層，累積再多也還是一堆各自獨立的知識點。

數量不是判斷標準。子分類是給讀者的一個承諾——點進去會拿到某一類東西——而那個承諾在第一篇就該成立。用篇數當門檻的話，第一篇到第三篇之間落地的讀者看到的是一份沒有說明的清單，而那正是子分類要解決的問題。反向的失敗是子分類長得比文章快、首頁變成一排名詞而不是一排知識點；出現這個徵兆時的處置是合併範圍相鄰的子分類，不是回頭設數量門檻。

## 跟其他資料夾的邊界

寫作前先依序評估：

1. **是 blog 本身設定 / Hugo / Markdown 議題？** → `posts/`
2. **是工作中用某工具遇到的事件？** → `work-log/`
3. **是中性 frame 的工作方法論？** → `record/`
4. **是從 case 抽出的工程原則？** → `report/`
5. **是 OS / 工具小技巧？** → `other/`
6. **跟工程無關、純粹是學到的知識點** → **本資料夾**

判斷軸是「跟工程工作的距離」：前五個資料夾都服務工程脈絡、本資料夾收工程之外的學習。一個知識點若同時有工程應用（例如某演算法的歷史），以工程價值為主就放對應教材區、以故事本身為主就放這。
