一個檔案被幾個不同的需求修改過，可以從版本歷史數出來，這個數字決定哪些檔案值得回頭讀修改紀錄、判斷這個檔案是否要拆。本篇是軟體設計原則模組的章節，範圍從這個量測開始，到熱點的分類、從修改紀錄決定切法、拆分時與語言無關的做法、拆分合併的時機，以及拆完之後怎麼驗證切法；量測與歸類只讀 git 歷史，與專案用什麼語言寫無關，單一職責等原則的定義在本模組的[知識卡片](/design-principles/knowledge-cards/)。範例是一支以 Python 寫成的 commit 守衛 `guard.py`：多個 AI 代理人各自在自己的工作目錄同時開發時（下文稱並行期間），代理人工具在執行每一條 shell 指令之前把整條指令字串交給它判斷，它擋下把 commit 寫進其他代理人工作目錄的寫法。命令解析、狀態判斷與訊息產生三種職責寫在同一個檔案裡。

保留原本的匯入路徑、改寫分派、避免循環匯入這幾件事的寫法依語言而定，Python 的做法在[拆分 Python 模組](/python/07-refactoring/python-module-split/)，Go 拆成多檔案或多個 package 的基礎在 [1.5 從單檔到多檔案](/go/01-basics/growing-files-packages/)；規則文件、操作手冊這類文字文件的拆分寫在[依職責拆分文字文件](/record/document-split-by-responsibility/)。

## 修改競爭與單一職責原則

修改競爭指的是處理不相干需求的人或代理人要改同一個檔案。兩個需求**不相干**，指它們要求的改動屬於不同種類（例如一個改命令的解析方式、一個改提示訊息的措辭）；這要讀過修改紀錄、逐個 commit 歸類之後才判得出來，下文〈從修改紀錄找出職責邊界〉說明做法。git 只在兩邊改動的行重疊或相鄰時產生合併衝突，所以同一個檔案的修改不一定互相阻擋；會讓它們互相等待的是三種情形：

- **改動落在同一處**：例如兩個需求都在同一份清單或檔尾追加一筆。處理第一個需求的人先改、先合併，處理第二個需求的人拉最新版、解衝突、重跑測試。
- **合併沒有文字衝突，而行為互相影響**：兩邊各改一個函式，合併成功，而 rebase 之後仍要重跑測試，確認兩邊沒有改壞對方。
- **並行的代理人共用同一個工作目錄**：兩方的改動還沒提交就混在同一份檔案裡，而 commit 記錄的是整份檔案的內容，任一方提交都會帶走另一方的改動，所以一方要等另一方提交或清空改動才能動手。

排好順序與加強溝通能縮短每次等待的時間，而一個檔案承載的職責越多，落在它身上的不相干修改越多，等待的次數跟著增加。只有一個人依序開發時沒有等待成本，不相干的修改落在同一個檔案仍然有代價：一個需求的改動有機會改壞另一個需求在乎的行為。讓一個需求的改動碰不到另一個需求在乎的行為，這種隔離正是單一職責原則要保護的對象。

[單一職責原則（SRP）](/design-principles/knowledge-cards/single-responsibility-principle/)把職責定義成改變的理由：一個模組應該只有一個改變的理由，而理由的計數單位是改動的種類，提出變更的那群人用來辨認種類，兩者對不上時以改動種類為準（定義、Martin 的原文與「只做一件事」為什麼是另一條原則，在那張卡片）。這個定義把抽象的「職責」換成了可以觀察的對象——**改變的理由**。版本歷史記下了每一次改變，也記下了它是為了哪一個需求（票、issue、PR）而做，需求數因此可以當成改變理由的間接量測（proxy measure）。

本篇說的模組是有對外介面的程式單位（[Coupling（耦合）](/design-principles/knowledge-cards/coupling/)卡片有同樣的界定），量測的單位則是檔案。Python 與 Dart 一個檔案就是一個模組，兩者等價；Go 的一個 package 由好幾個檔案組成，熱點檔依職責拆成同一個 package 裡的幾個檔案，修改競爭就解掉了，那幾類是否需要各自的對外介面、是否再拆成不同的 package，是另一個判斷。

| 現象                                 | 代表什麼                                                                                             |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| 同一個需求的多次 commit 都改同一個檔 | 正常。同一主題的演進集中在一處，這是[內聚（cohesion）](/design-principles/knowledge-cards/cohesion/) |
| 三、四個**不同的需求**都要改同一個檔 | 這個檔可能有好幾種改變的理由；實際幾種，由逐個 commit 歸類決定                                       |

需求數是篩選訊號：腳本數的是不同的需求，不判斷相不相干，它決定要不要回頭讀這個檔案的修改紀錄，這個檔案實際有幾種改變的理由，在逐個 commit 歸類時才判定。本篇範例 commit 守衛的需求都服務同一件事（擋下跨工作目錄的 commit），而它們要求的改動分成三種：命令語法跟著 git 的寫法變、並行政策跟著團隊的工作流程變、提示措辭跟著使用者的回饋變，三種改動的起因不同、發生的時間也不同，即使所有票都由同一位 PM 開，看開票的人分不出來，看要求的改動種類才分得出來。這正是 [Divergent Change（發散式變更）](/design-principles/knowledge-cards/divergent-change/)：一個模組因為不同的理由、以不同的方式被修改。

### 行數與不同需求數的量測對象

常見的拆檔門檻是行數，例如超過 300 行就考慮拆。行數是檔案過大的症狀，而它在兩種檔案上給出的結果與不同需求數相反：

| 情況                                       | 行數判斷         | 不同需求數判斷             |
| ------------------------------------------ | ---------------- | -------------------------- |
| 200 行的骨架產生器，被 6 個不同需求改過    | 不到門檻         | 排在前段，回頭讀修改紀錄   |
| 900 行的解析器，只屬於同一個需求的連續演進 | 超過門檻（誤判） | 只有一個需求，不會排在前段 |

行數量的是檔案的大小，不同需求數量的是一個檔案可能混了幾種改變的理由，SRP 在意的是改變的理由有幾種。照行數把 900 行的解析器切成三份、不看修改落在哪裡時，同一主題之後的修改常常要同時改好幾個檔；一個需求改多個檔案是 [Shotgun Surgery（散彈式修改）](/design-principles/knowledge-cards/shotgun-surgery/)。與它成對的發散式變更，正是本篇用修改紀錄量的那種壞味道（從程式碼結構偵測的規則在 [Code Smell 檢查清單](/record/code_smell/)的〈B1. Divergent Change〉一節），它在並行開發時造成的等待就是修改競爭的成本。

## 用 git 歷史量出熱點

量測的前提是需求與檔案的對應查得到。本篇從 commit 標題裡的需求編號取（commit 訊息帶票號的慣例見 [Commit message vs source code doc](/record/commit-message-vs-source-doc/) 的〈Bug 號、ticket 連結、incident 紀錄〉一節；那裡的例子把票號寫在內文，下面的腳本只讀標題，處理方式見〈只讀 commit 標題〉那一條）。也可以從 issue tracker 取：匯出每個 PR 連到的 issue 與 PR 改的檔案，整理成「檔案 → 需求編號集合」的對應，就是腳本裡 `collect_changes` 回傳的那個形狀，之後的排行與判讀照用，而且沒有只讀標題帶來的限制。

commit 標題帶有需求編號（票號、issue 號）時，下面的腳本算出每個檔案被幾個不同需求改過。下文把排行前段、與同一次統計裡的其他檔案相比被明顯更多不同需求修改的檔案稱為修改熱點（簡稱熱點），它不設絕對的門檻，也沒有固定的名次。它與效能分析裡「最常執行的程式路徑」那種熱點是兩件事；git 歷史分析的文獻裡也有 hotspot（Adam Tornhill 在《Your Code as a Crime Scene》裡結合修改頻率與程式碼的複雜度），本篇數的是不同需求數，不數 commit 次數，也不乘複雜度。腳本以 Python 寫成，只呼叫 `git log`、不讀程式碼，放進 Go 或 Dart 的 repo 照樣能跑。

```python
"""依 commit 標題中的需求編號，統計每個檔案被幾個不同需求修改。"""
import collections
import os
import re
import subprocess

ISSUE_ID = re.compile(r"#(\d+)")  # 依專案的 commit 慣例調整
PR_SUFFIX = re.compile(r"\s*\(#\d+\)\s*$")  # squash merge 在標題結尾附加的 (#PR號)
STRIP_PR_SUFFIX = True  # 只在用 squash merge、標題結尾的 (#N) 是 PR 號時設 True
# 工具產生的檔案，不列入統計；依專案的套件管理工具調整
EXCLUDE = {"uv.lock", "poetry.lock", "package-lock.json", "go.sum", "pubspec.lock"}
EXCLUDE_ISSUES: set[str] = set()  # 橫切的需求編號（相依套件升級、全域改名），不列入統計

def collect_changes(since: str, path: str = ".") -> tuple[dict[str, set[str]], int]:
    log = subprocess.run(
        # core.quotePath=false：非 ASCII 檔名照原樣輸出，不轉成跳脫碼
        ["git", "-c", "core.quotePath=false", "log", f"--since={since}", "--no-merges",
         "--name-only", "--format=@@%s", "--", path],
        capture_output=True, text=True, check=True,
    ).stdout

    issues_per_file: dict[str, set[str]] = collections.defaultdict(set)
    current: set[str] = set()
    skipped = 0
    for line in log.splitlines():
        if line.startswith("@@"):
            subject = line[2:]
            if subject.startswith('Revert "'):
                current = set()  # revert 的標題帶著被還原那個 commit 的 PR 號
                continue
            if STRIP_PR_SUFFIX:
                subject = PR_SUFFIX.sub("", subject)
            current = set(ISSUE_ID.findall(subject)) - EXCLUDE_ISSUES
            skipped += not current
            continue
        if line and current and os.path.basename(line) not in EXCLUDE:
            for issue in current:
                issues_per_file[line].add(issue)
    return issues_per_file, skipped

def report(since: str, top: int = 20) -> None:
    changes, skipped = collect_changes(since)
    ranked = sorted(changes.items(), key=lambda kv: -len(kv[1]))
    for path, issues in ranked[:top]:
        print(f"{len(issues):3d} 個需求  {path}  {' '.join(sorted(issues))}")
    print(f"略過 {skipped} 個標題沒有需求編號的 commit")

if __name__ == "__main__":
    report("2 weeks ago")
```

```bash
python3 hotspots.py
```

腳本裡影響計數的設計：

- **統計的時間範圍**：`report()` 的引數是 `git log --since` 接受的時間字串（`"2 weeks ago"`、`"2026-01-01"`）。範圍要涵蓋幾輪需求，才看得出同一個檔案被不同需求反覆修改；範例的兩週適合需求密集的專案，修改頻率低的專案要拉長。被幾個需求修改算多的那個數字跟著時間範圍變，所以看排行裡的相對位置比看絕對數字穩定。
- **統計的目錄**：`collect_changes` 的 `path` 預設是 `"."`，指的是執行腳本時所在的目錄；從子目錄執行，只會統計那個子目錄底下的檔案。
- **只讀 commit 標題**：腳本傳給 `git log` 的 `--format=@@%s` 讓 git 對每個 commit 只輸出標題。把需求編號寫在內文或 trailer（訊息結尾 `Refs: #160` 這種 `鍵: 值` 形式的欄位）的專案，這些 commit 會被靜默略過；改用 `%B` 取完整訊息時，內文的行會和檔名混在一起，分隔方式與解析都要跟著改。
- **PR 號**：GitHub 的 issue 與 PR 共用同一組 `#N` 編號，squash merge（把整個 PR 壓成一個 commit 合併）又會在標題結尾附上 `(#PR號)`，只改 `ISSUE_ID` 分不開兩者；`STRIP_PR_SUFFIX` 為 `True` 時，腳本先去掉標題結尾的 `(#N)` 再比對。`STRIP_PR_SUFFIX` 這個設定只適用用 squash merge 的 repo，而且需求編號要寫在 PR 標題裡；習慣在標題結尾寫 `(#45)` 引用 issue 的專案，要把 `STRIP_PR_SUFFIX` 設成 `False`，否則那個 issue 號會被刪掉。需求編號與 PR 編號格式不同的專案（例如需求用 `PROJ-123`），改 `ISSUE_ID` 就分得開。revert 的標題會把被還原那個 commit 的 PR 號帶進引號裡，腳本略過 `Revert "` 開頭的標題。
- **工具產生的檔案**：lock 檔、每個 PR 都跟著升號的版號檔、產生的程式碼，每個需求都會改到，排行會被它們佔滿，而它們沒有任何人帶著意圖去編輯；把檔名加進 `EXCLUDE`。
- **改名與橫切的需求**：`git log` 加了 `--name-only` 不追蹤改名，大量重新命名之後，舊路徑與新路徑各自計數。相依套件升級、全域改名、格式化這類橫切的需求會讓大量檔案各加一，排行前段一整批同時出現的檔案，多半來自同一個橫切需求；`EXCLUDE_ISSUES` 用來排除這類需求的編號。
- **沒有編號的 commit**：腳本最後印出略過的 commit 數。這個數字接近全部 commit 時，統計沒有意義；commit 完全不帶編號時排行是空的、只印出這一行。這時改用〈從修改紀錄找出職責邊界〉的做法，讀 commit 標題與 `git show` 人工歸類。
- **`--no-merges`**：`git log` 預設不列出 merge commit 改了哪些檔案，所以 merge 不影響排行；標題沒有編號的 merge（`Merge branch 'x'`）會被算進略過的 commit 數，腳本加的 `--no-merges` 讓 git 不輸出它們。改用 `-m` 時，merge 對每個 parent 各列一次檔案，加上分支上原本的 commit，同一份改動會算兩次以上。改用 `--first-parent` 時只走主線，分支上的 commit 不列出，改動改由 merge commit 列出、記在 merge 標題的編號下；它與 `--no-merges` 一起用，以 merge commit 合併的 repo 會失去全部分支上的改動。
- **一則 commit 帶多個編號**：腳本用 `ISSUE_ID.findall` 取出標題裡的全部編號。一個 commit 同時處理多個需求時，它改過的每個檔都會記到每個需求名下。
- **把子需求歸到同一個主題**：點號格式的子需求（例如 `#120.3`），正規式 `#(\d+)` 只比對到第一段數字，本來就會算進根需求 120。子需求若有獨立編號（例如父需求 `#120`、子需求 `#135`），要另備一份父子對照表，把子需求歸到根需求再計數；不歸併的話，同一主題的連續修改會被誤算成多個改變理由。〈熱點的分類與處理方式〉表格裡「同一主題的連續演進」那一列，指的是子票已經歸到根需求之後的計數。

## 熱點的分類與處理方式

排行前段的檔案有些該拆、有些不該拆，依熱點類型分開處理：

| 熱點類型                                         | 例子                                                                                      | 處理                                 |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------- | ------------------------------------ |
| 一般程式碼，排在前段、被多個不同的需求修改       | commit 守衛 `guard.py`：命令解析、狀態判斷、訊息產生寫在同一個檔                          | 依〈從修改紀錄找出職責邊界〉評估拆分 |
| 同一主題的連續演進                               | 一個佇列模組，被同一個「排隊機制」需求的 5 張子票陸續修改（子票歸到根需求後只算一個需求） | 不拆，這是內聚                       |
| 集中登記檔：每加一個功能就要在這裡登記一筆的檔案 | URL 路由表、外掛註冊表、`settings.json`、依類型分支的長 if/elif 或 switch                 | 不以職責拆分，改成每個項目一個片段檔 |
| 只有測試檔是熱點                                 | 一個大測試檔被多個需求加測項                                                              | 見表下說明                           |
| 工具產生或衍生的檔案                             | lock 檔、每個 PR 都升號的版號檔、產生的程式碼                                             | 不拆，從統計排除；衝突靠重新產生解   |

工具產生的檔案由工具改寫，沒有人帶著意圖編輯，不屬於任何一種職責，處置是從統計排除、衝突靠重新產生；版號檔改由發版時的 tag 衍生，就不必每個 PR 都改它。

集中登記檔的處置跟一般程式碼相反。註冊表的職責是集中列出所有項目，每加一個功能就要登記一次，所以修改它的需求數會隨功能數一起增加。把它依職責拆成三份註冊表，每次登記仍然要改其中一份，衝突只是換到另一個檔案；兩個需求都在同一份清單的尾端追加，照樣是相鄰的改動。這類檔案的解法是讓每次登記不碰同一個檔案：每個項目一個片段檔，由載入端掃描目錄合併。這要載入端由自己控制；設定檔由外部工具讀取、而工具只認單一檔案時，片段檔進版控，由一個產生步驟（例如建置前執行的一支合併腳本）合併成那一個檔，合併出來的檔案當成工具產生的檔案從統計排除。登記的對象是程式碼時，由誰掃描依語言而定：Python 在執行期匯入目錄底下的每個模組（寫法見[拆分 Python 模組](/python/07-refactoring/python-module-split/)的〈把巨型分支改成自動登記的分派表〉），沒有執行期掃描的語言走上面那個產生步驟。片段檔的代價是登記關係不再寫在一個看得到的地方，放進目錄的半成品檔也會被登記。

測試檔的修改跟著它測的產品檔走，所以只有測試檔是熱點時，回到它測的產品檔判讀。產品檔也是熱點，測試隨產品檔一起拆。產品檔不是熱點，多半代表這個測試檔一次測了好幾個產品模組；產品檔已經拆成幾個模組、測試卻還集中在一個檔，也是同一種情形，兩者都依它測的模組拆成對應的測試檔。另一種情形是這個測試檔是共用的 fixture 或測試案例清單，每個需求都在裡面登記一筆，那是集中登記檔，依上一段處理。

## 從修改紀錄找出職責邊界

職責的邊界記在修改紀錄裡：每個需求改的是哪一種職責，讀它的 commit 就知道。熱點統計腳本的 `report()` 在每個檔案後面印出了改過它的需求編號，要看每個需求做了什麼，列出這個檔案的 commit 標題：

```bash
# 時間範圍用與熱點統計相同的範圍，路徑換成要拆的那個檔案
git log --no-merges --since="2 weeks ago" --format='%h %s' -- guard.py
```

把每個需求歸到它改的職責（並行期間指多個代理人同時在各自的工作目錄開發的期間）：

```text
需求 A：修正命令解析遇到引號時的錯誤        → 命令解析
需求 B：新增「並行期間」的判斷條件           → 狀態判斷
需求 C：提示訊息改成指引使用者改寫命令       → 訊息產生
需求 D：解析器支援 -C 參數                   → 命令解析
需求 E：並行期間改依工作位置過濾             → 狀態判斷
```

歸類的單位是每個 commit 改到的程式：`git show <hash>` 看得到那個 commit 改了哪些函式。類別依需求要求的改動種類建立，與歸類的先後順序無關。長期計畫（橫跨多張票、為同一個目標分批進行的工作，例如分好幾輪做完的一次重構）有根需求編號時照根需求歸併；沒有的話，它的 commit 改到好幾處，也只歸進其他需求已經要求過的那些種類，計畫本身不構成一個模組。只有一個需求、改到同一個檔案的好幾處，是同一主題的連續演進，不產生新的類別；那個需求若要同時改好幾個檔案，是散彈式修改的訊號，處理見 [Shotgun Surgery](/design-principles/knowledge-cards/shotgun-surgery/) 卡片。bug 修正與重構不另算一個理由，依它修的那段程式碼原本屬於哪一類歸進那一類。這個例子裡每個需求只改到一類，所以逐個需求列出來就是逐個 commit 的結果。多數需求（超過一半）都同時改到某兩類時，這兩類對需求而言是同一個改變的理由，把它們歸成同一類——依它們切開，每個需求都要同時改兩個新檔，就是散彈式修改。

歸類之後，每一類職責是一個候選模組，這個例子分出命令解析、狀態判斷與訊息產生。歸類後只剩一類時，這些需求要求的是同一類改動，這個檔案只有一個改變的理由（內聚），或者它是集中登記檔，回到〈熱點的分類與處理方式〉的表重新判斷。

## 拆分時與語言無關的做法：特徵測試、搬移與修改分開提交、單向依賴

決定切法之後，把 `guard.py` 依這三類拆成 `command_parse.py`、`state.py`、`messages.py` 而對外行為不變，有三件事與語言無關，各語言的寫法放在各語言模組。

**拆分前用特徵測試鎖住行為。** 拆分前後跑同一組測試、結果相同，才證明拆分沒有改到對外行為。這種測試叫特徵測試（[characterization test](/testing/knowledge-cards/characterization-test/)）：預期值取自拆分前程式當下的實際輸出，不是規格上應該如何。它抓得到拆分在測到的輸入與斷言的輸出上造成的任何差異，包括原本就存在的錯誤被「順手修好」；沒有斷言的輸出抓不到。測試表要涵蓋應該被擋下或應該回報錯誤的反例：只驗證正常情況會放行的測試表，在拆分改壞了擋下的判斷時依然全綠。

**搬移與修改分開提交。** 搬移和修改混在同一個 commit 裡，測試一紅，就分不出是搬錯了還是改錯了，所以純搬移的 commit 不同時修改行為，行為的修改放在之後的 commit。`git diff --color-moved` 會把搬移過的行與新寫的行用不同顏色標出，用來確認一個 commit 裡只有搬移。檔案改名也單獨提交一個只改名的 commit：git 依內容相似度判定改名，改名與大量搬移混在同一個 commit 時，留下來的那份檔案只剩原檔的一小部分，git 認不出它是改名而來，`git log --follow` 就追不到改名之前的歷史。

**拆出來的模組依賴只朝一個方向。** 判斷上下層的依據是誰需要知道誰：被較多拆出模組使用、而且自己不需要知道其他拆出模組的那一個在下層，兩個條件都要成立。這個例子裡 `command_parse.py` 只把指令字串解析成結構，在最下層；`state.py` 與 `messages.py` 使用解析結果；組合三者的那一層在最上面。兩個新模組互相呼叫時，看它們過去的修改：幾乎每次都一起發生，代表它們是同一類職責、歸類時切錯了，併回同一個模組（判斷見 [Coupling](/design-principles/knowledge-cards/coupling/) 卡片的〈設計責任〉）；修改各自發生，先確認兩個方向的呼叫是否都必要，有時拿掉其中一邊就夠了；兩邊都必要，多半代表中間有一塊共用的定義沒有抽出來，例如兩邊都用到的資料型別，把它往下抽一層，讓兩者都依賴它。

## 拆分的時機與等待中的需求

拆分合併的時間點，決定等待中的需求以哪一版為基準。拆分先合併，等待中的需求以新版本為基準，各自只改自己職責所在的新檔：

```text
拆分前：命令解析、狀態判斷、訊息產生各有一個需求在等，三個都要改 guard.py → 一個接一個
拆分後：處理命令解析需求的人改 command_parse.py，狀態判斷的改 state.py，訊息產生的改 messages.py → 可以同時進行
```

原本要一個接一個做的三個需求，拆分之後可以平行處理。拆分若在某個需求開工之後才合併，那個需求的分支改的是舊的 `guard.py`，rebase 到拆分之後的版本時，git 的改名偵測（內容相似度預設 50% 以上就判定為改名）決定衝突的形態：

- **沒有一份新檔保留原檔過半的內容**：git 判定 `guard.py` 被刪除，出現 modify/delete 衝突。
- **有一份新檔保留了原檔過半的內容**：git 把它當成 `guard.py` 改名而來，衝突以一般的內容衝突出現在那份新檔，衝突區塊裡是已經搬到其他模組的舊函式。解衝突的人照一般衝突處理接受這一段，會把搬走的函式重新塞回那份新檔，分支的改動落在那份新檔裡的舊函式副本上。在 Python 這類每個檔案各自是一個命名空間的語言裡，兩份同名函式可以並存，實際被呼叫的是搬到別處的那一份，測試仍然全綠；Go 把幾類拆成同一個 package 裡的檔案時，重新塞回的舊函式與搬走的那一份重複宣告，編譯時就被擋下。

兩種形態的處置相同：把這個分支的改動移到那一職責所在的新檔，不接受衝突區塊裡整段的舊程式碼。rebase 沒有衝突也要檢查一次：分支在被當成改名目標的那份新檔裡新增的函式會乾淨合併，即使它屬於另一類職責。用 `git diff main --stat` 與 `git diff main` 看分支新增的每個函式落在哪個檔（`main` 換成拆分合併進去的那條分支）。在檔案各自是命名空間的語言裡，拆分前就有的測試在上面這些情形下仍然全綠，這個分支為自己的改動新增或修改的測試才會紅。這也是拆分要排在等待中的需求開工之前合併的原因。

## 拆分之後重跑熱點統計：驗證切法與新檔再成熱點的判讀

拆分是否切對，用拆分之後的修改紀錄驗證。驗證的對象是拆分之後的修改，所以過了幾輪需求之後重跑熱點統計，`report()` 的引數設成拆分合併的那一天；拆分本身的需求編號加進 `EXCLUDE_ISSUES`，否則拆分那個 commit 會讓每個新檔各多算一個需求。比較拆出來的各個新檔被幾個需求修改，並看每個需求是否只改了一個新檔：多數需求同時改到兩個新檔，代表當初把同一個改變的理由切成了兩類。

某個新檔很快又成為熱點時，把它的修改再歸類一次：

- **修改落在拆分時已有的幾類而混在一起**：當初的職責分類切錯了位置。
- **出現拆分時沒有的一類**：多了一種新的職責。
- **每次修改都是登記一筆**：那個新檔本身是集中登記檔。
- **修改全部落在它自己那一類**：在這一類裡照〈從修改紀錄找出職責邊界〉再歸類一次。這些需求要求的改動分得出兩種以上的種類，代表這一類粒度太粗，可以再拆；分不出來，代表這一類就是程式最常變動的那一處，拆分已經把變動集中在那裡，不必再拆。

拆分時若另抽了一個讓幾個新檔共用的定義模組（例如幾個模組都用到的資料型別），它被每個需求都改到時，常見的原因是共用定義抽得太大，裡面混了只有某一個模組用的型別，把那些型別搬回使用它的模組。

這次驗證之後，熱點統計照原本的時間範圍定期重跑：新出現在排行前段的檔案，從〈熱點的分類與處理方式〉重新判讀。

## 思考題：熱點排行與直覺、註冊表的衝突、新檔再成熱點

1. 專案裡最常讓兩個人同時想修改的是哪個檔案？用本篇的腳本跑一次，結果和原本的直覺一致嗎？
2. 一個註冊表檔案被 10 個需求修改過。拆成兩個註冊表之後，為什麼衝突仍然在？要怎麼降低它的衝突？
3. 拆分後，拆出來的其中一個新檔很快又變成熱點，這代表什麼？

## 實作練習：父子需求對照、職責歸類

1. 子需求使用獨立編號時，為腳本加入父子對照表（例如從 issue tracker 匯出），把子需求歸到根需求後再計數。
2. 挑一個在熱點排行前段、被多個不同需求修改過的模組，依〈從修改紀錄找出職責邊界〉一節列出每次修改的職責，寫出會拆成哪幾個模組（不必實際動手拆）。
