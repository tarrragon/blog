這篇整理「多個工作負載共用同一份硬體資源」這個條件，在系統設計與 infra 規劃上各要考慮什麼。共用有三種常見的形態：一台主機上用 Docker Compose 跑整個系統（應用程式、資料庫、快取與監控都在一起）、雲端的虛擬機與其他租戶共用同一台實體機，以及開發用的筆電上 Docker 的虛擬機與其他程式共用 CPU 與磁碟。三者的共同點是：某一個工作負載用掉的資源，會從其他工作負載能用的那一份裡扣掉，而被扣掉的那一方沒有做錯任何事。這個現象叫 [Noisy Neighbor](/backend/knowledge-cards/noisy-neighbor/)。

單一容器的 CPU 與記憶體限制怎麼設，見 [容器化資源設計](/operations/05-capacity-planning/container-resource-design/)；這篇談的是限制之外、整台主機層級的取捨。

## 一次共用主機過載的樣子

一個短網址服務的開發環境：macOS 上的 OrbStack 跑 Docker Compose，入口 Nginx、兩個後端、PostgreSQL、Valkey 與監控都在同一台虛擬機裡。Mac 有 8 顆核心，與這個服務無關的其他程式讓 Mac 的 load average 在 55 到 78 之間持續了數小時。這段時間：

- **所有工作都變慢**：PostgreSQL 產生 200 萬個數字的查詢要 4 秒（正常約一百多毫秒），1.2 萬列的批次寫入要十幾秒。
- **各服務受影響的程度不同**：外部探測要求回應時間低於 500 ms，Go 後端的成功率是 92.5%、最慢 2.1 秒；Laravel 後端只有 49%、最慢 6.0 秒。
- **監控自己也受影響**：Prometheus 讀取各 exporter 的耗時最高到 14.9 秒，超過預設的 10 秒逾時，部分讀取失敗。
- **虛擬機裡看不到原因**：虛擬機的 load 除以核心數只有 0.43，容器的 CPU 用量也都很低。

所以共用主機帶來的不只是「變慢」，而是三個彼此相關的後果：容量變成不確定、多個服務一起出事、監控與被監控的對象一起退化。

## 容量估算：算的是分得到的資源，不是機器的規格

容量估算把「每秒多少請求」換成「需要多少 CPU、記憶體與連線」，前提是這些資源在需要的時候拿得到。共用主機時，拿得到的量由其他工作負載決定：

- **同一台主機上的其他服務**：資料庫的重查詢、批次工作、監控本身的讀取，和線上的請求搶 CPU 與磁碟。估算時要把它們的尖峰時段疊在一起看，而不是各自算平均。
- **同一台實體機上的其他租戶**：雲端的虛擬機分到的 CPU 時間會被 hypervisor 分給別人，Linux 虛擬機裡的 steal 時間（`/proc/stat` 的 steal，node_exporter 的 `node_cpu_seconds_total{mode="steal"}`）記錄這段被拿走的時間。可突發型的機型（例如 AWS 的 T 系列）另有 CPU 額度，用完之後只剩基準效能。
- **開發環境**：筆電上的其他程式。這一層無法控制，所以在筆電上量到的數字只代表那一刻的那台機器。

壓測量到的上限，要附上當時主機的負載；同一個服務在主機安靜時與過載時量到的數字不能互相比較。拿數字做判斷的工作開始之前，先確認主機的負載與磁碟空間，超過門檻就延後。

## 故障範圍：放在一起的服務會一起出事

共用同一台主機的服務，失效是相關的：主機的 CPU、記憶體、磁碟或網路任一樣耗盡，上面全部的服務一起受影響；主機重開或磁碟寫滿，全部一起停。[Blast Radius](/backend/knowledge-cards/blast-radius/) 的估算因此要把「放在同一台主機」當成一條依賴。實例是同一個開發環境稍早的一次：Mac 的磁碟剩不到 1 GB 時，OrbStack 的虛擬機連同裡面全部的容器被停掉了三次。

這帶出部署時要決定的幾件事：

- **哪些服務適合放在一起**：延遲敏感的線上請求與吃滿 CPU 的批次工作（重算報表、匯出）放在一起時，批次工作的尖峰就是線上請求的延遲尖峰。分開放，或至少用限制與權重讓線上請求優先。
- **資料庫與應用程式要不要同機**：同機省下網路延遲與一台機器的成本，代價是應用程式的記憶體暴增可以讓資料庫被作業系統的 OOM killer 結束。
- **監控放在哪裡**：監控與被監控的服務放在同一台主機時，主機出事的那一刻監控也跟著退化或停止，見〈監控的位置〉。

## 隔離的層級與代價

隔離可以分成幾個層級，越往下隔離得越徹底，成本與管理負擔也越高：

| 層級                         | 做法                                                                                                   | 隔離得了                             | 隔離不了                                 |
| ---------------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------ | ---------------------------------------- |
| 同一台主機，不設限制         | Compose 的預設                                                                                         | —                                    | 任何一個服務吃滿資源，其他全部受影響     |
| 同一台主機，設上限與權重     | 容器的 CPU 上限（`--cpus`，cgroup 的 `cpu.max`）、相對權重（`--cpu-shares`，`cpu.weight`）、記憶體上限 | 單一服務吃掉全部 CPU 或記憶體        | 磁碟讀寫與網路的爭用、主機本身的故障     |
| 同一台主機，保留資源與優先權 | Kubernetes 的 requests 與 `PriorityClass`、systemd 的 slice                                            | 主機吃緊時重要的服務與監控先分到資源 | 主機本身的故障                           |
| 不同主機或虛擬機             | 依角色分開部署（資料庫、應用程式、監控各自一台），Kubernetes 的 anti-affinity                          | 一台主機的資源耗盡與故障             | 同一台實體機上其他租戶的競爭（虛擬機時） |
| 專用的實體機                 | 雲端的 dedicated host、自己的機房                                                                      | 其他租戶                             | 同一個機櫃、同一個機房的共同故障         |

CPU 與記憶體的限制是成熟的做法；磁碟讀寫與網路頻寬的隔離（cgroup v2 的 `io.max`、`io.weight`）實際效果依磁碟與排程器而定，本篇沒有實測。所以高頻寫入的服務（資料庫、事件的寫入）在同一台主機上最容易互相拖累，也最常是第一個被分出去的。

選哪一個層級，看兩件事：一起出事的代價（故障範圍內的服務對使用者有多重要），以及拆開的成本（多一台機器、多一份部署與監控）。練習或早期的服務放在一台主機上是合理的起點，前提是知道哪些事會一起發生，並在它們開始發生時看得到。

## 監控的位置

共用主機對監控有兩個影響，細節見 [主機過載時的監控告警](/backend/04-observability/host-overload-alerting/)：

- **監控看不到它所在層以外的原因**：裝在虛擬機裡的監控看不到虛擬機以外的競爭（Mac 上的其他程式、實體機上的其他租戶），只能看到全部服務同時變慢。各層的監控能看到什麼，見 [單機容器服務的流量與資源監控](/backend/04-observability/host-traffic-resource-monitoring/)。
- **監控和服務一起退化**：探測與 Prometheus 自己也在等 CPU，量到的延遲包含它們自己的等待，讀取逾時會在資料裡留下空洞。正式環境至少要有一個訊號來自那台主機之外（另一台機器上的探測、外部的 uptime 服務），見 [觀測共命運失效](/backend/04-observability/observability-shared-fate/)。
