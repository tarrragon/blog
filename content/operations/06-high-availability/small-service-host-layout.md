這一篇整理一個小型服務（一組應用程式、一個資料庫、一個快取，由一個小團隊維運）從一台主機擴充到兩到三台時，每一台主機放什麼，以及每一種分法換到什麼。內容是設計與規劃：監控主機跨業者讀取服務主機、兩台主機互相監看的配置，還沒有在兩台實體主機上部署驗證，這兩部分寫的是要決定的事與它們的前提，沒有附操作指令。單一主機上監控看不到的故障見 [4.28 單台主機的監控盲區與外部視角](/backend/04-observability/single-host-monitoring-outside-view/)，冗餘的一般模式見 [冗餘設計模式](/operations/06-high-availability/redundancy-patterns/)。

## 一台主機承擔的風險

一台主機上跑著入口、應用程式、資料庫、快取與整組監控時，所有元件共用同一個[失效域](/backend/knowledge-cards/failure-domain/)。主機停掉時服務中斷，而負責通知的監控同時停掉，所以中斷不會被通知，要等使用者回報才知道。主機過載時，應用程式、資料庫與監控搶同一組 CPU 與記憶體，監控量到的延遲混進它自己的等待（見 [4.27 主機過載時的監控告警](/backend/04-observability/host-overload-alerting/)）。資料與它的備份放在同一台主機的磁碟上時，磁碟損壞或帳號被停權會讓兩者一起消失。

第二台主機可以解決其中一部分，解決哪一部分取決於它放什麼。

## 第二台主機的三種用法

**給監控。** Prometheus、Alertmanager 與 Grafana 搬到第二台，服務主機只留 exporter。服務主機停掉時，監控主機讀不到它的指標而發出告警，中斷從使用者回報變成告警通知；監控主機停掉時，服務照常運作，由下文的互相監看發現。服務本身的可用性沒有提高，主機停掉時服務照樣中斷；換到的是故障變得看得見，以及監控不再與服務搶資源。應用程式不必改任何東西，監控主機的資源需求也小（指標的量估算見 [Prometheus 容量規劃與故障模式](/backend/04-observability/vendors/prometheus/capacity-failure-modes/)），所以是成本最低的一步。

**給應用程式的副本。** 兩台主機各跑一份應用程式，前面以負載平衡器分流，一台停掉時另一台接手。換到的是服務的可用性，前提有三個：應用程式是無狀態的（session 不存在單台主機的記憶體或磁碟裡，見 [水平擴展](/operations/02-horizontal-scaling/)）；資料庫不在任何一台應用主機上，否則放著資料庫的那一台停掉時，另一台的應用程式也沒有資料可讀；負載平衡器本身不是單點（雲端業者的負載平衡器通常由業者做冗餘）。資料庫因此要搬到託管服務或第三台主機，兩台實際上變成三個元件。

**給資料庫。** 資料庫搬到第二台，應用程式與資料庫各自有一台主機的資源。換到的是效能的隔離：資料庫的大查詢不再拖慢轉址這類熱路徑，兩者的容量也能分開調整。可用性沒有提高，反而多了一個會讓服務中斷的主機：兩台任一台停掉，服務都中斷。

小型服務的第二台主機先給監控。前兩種故障（停掉沒人知道、監控與服務搶資源）在一台主機的階段就存在，給監控的那一台以最低的成本解決它們，也不需要改應用程式；應用程式的副本要先處理無狀態化與資料庫的位置，資料庫的分離解決的是效能而不是可用性。停機代價高、主機故障又頻繁的服務，例外地先做應用程式的副本，判斷方式見 [高可用的成本](/operations/06-high-availability/ha-cost/)。

## 監控主機放在另一個業者或地端

監控主機要與服務主機分屬不同的失效域。兩台虛擬機租在同一個業者、同一個區域，業者那個區域的網路故障或帳號被停權時，兩台一起受影響；所以監控主機放在另一個雲端業者，或放在地端（公司或家裡長時間開著的一台主機）。

監控是內部服務，地端是合理的位置：Grafana 只給團隊看，連線經由 SSH 或 VPN（存取方式見 [Grafana 的對外存取](/backend/04-observability/vendors/prometheus/grafana-external-access/)），不必對網際網路開放任何連接埠。地端的代價是它自己的可靠度：停電、網路斷線、機器重開時監控就停了，停掉的那段時間沒有指標。這段時間由下文的互相監看發現；監控資料的連續性要求高時，改租另一個業者的小型 VPS。

## 監控主機與服務主機之間的連線

Prometheus 主動讀取各主機的 exporter，所以監控主機要連得到服務主機上的 exporter 連接埠。這些連接埠不能對網際網路開放：exporter 沒有認證，輸出的指標透露主機的資源、服務的名稱與版本。同一個雲端業者內，exporter 綁在私有網路的位址上（[多台主機的指標收集](/backend/04-observability/vendors/prometheus/multi-host-scraping/) 以 `EXPORTER_BIND_ADDR` 設定）；跨業者或跨地端時沒有共用的私有網路，要在兩台之間建一條 VPN，例如 WireGuard 或 Tailscale（運作方式見 [Tailscale 深入](/linux/tools/remote/tailscale-tailnet-and-relay/)），exporter 改綁在 VPN 介面的位址上。

連線的方向對地端有利：Prometheus 從監控主機往外連，地端在 NAT 後面、對外 IP 會變動都不影響，地端也不必開任何對外的連接埠。反過來的架構（服務主機以 remote write 把指標推到監控主機）要監控主機接受連入，跨業者時同樣走 VPN，架構的比較見 [多台主機的指標收集](/backend/04-observability/vendors/prometheus/multi-host-scraping/) 的〈指標回到中央的架構：中央直接讀取與各主機推送〉。

跨網路讀取多了一種誤判：兩地之間的網路或 VPN 斷掉時，監控主機讀不到服務主機，在監控看來與服務主機停了相同，`up` 變成 0、主機停機的告警成立。分辨兩者要靠第三個位置的觀察者：從另一個網路對服務的公開網址發請求的外部探測。外部探測成功而監控讀不到，是兩地之間的連線斷了；兩者都失敗，是服務主機停了。告警的說明也寫上「也可能是監控主機連不過去」，值班的人先查連線再查服務。

## 兩台主機互相監看

監控主機發現服務主機停掉；監控主機自己停掉時，要由服務主機發現。服務主機上跑一個心跳監看程式（自架的 healthchecks，或一個記下最後一次心跳、超過期限就通知的小程式），接收監控主機上 Alertmanager 送出的 Watchdog 心跳（送法見 [Alertmanager 的通知管道](/backend/04-observability/vendors/prometheus/alertmanager-notification-channels/) 的〈Watchdog：告警鏈本身的心跳〉）。任一台停掉，另一台都會發現，不必用第三方的心跳監看服務。

成立的條件有三個：

- **心跳的路徑也走 VPN。** 監看程式的接收端點不對網際網路開放；心跳網址可以送出假的心跳，也可以送出假的失敗。
- **監看程式的通知不經過監控主機。** 它直接寄 email（經由業者的郵件服務或一個交易郵件服務），或送到另一個推播服務，不送給監控主機上的 Alertmanager 或 ntfy。監控主機停掉時，經過它的通知一起停。
- **監看程式自己有人盯著。** 它停掉時不會有任何訊號。它跑在服務主機上，監控主機照讀取 exporter 的方式探測它的健康端點，它停掉時由監控主機的告警通知。

剩下的風險是兩台同時停掉，這時沒有任何一方送得出通知。兩台在不同的業者時，同時停掉的機會小；它們共用的依賴（同一個 DNS 業者、同一個郵件服務、同一組 VPN 協調伺服器）會讓這種情形比預期常見，配置完成後逐項列出兩台的依賴比對一次。要涵蓋這種情形，再加一個第三方的外部探測服務當第三個觀察者，挑選條件見 [第三方心跳監看與外部探測服務](/backend/04-observability/vendors/prometheus/external-heartbeat-and-probe-services/)。

## 第三台主機的兩種配置

**應用主機、資料庫主機與監控主機。** 第三台給資料庫，應用程式與資料庫各一台，兩台在同一個業者、同一個區域，以私有網路連線；監控主機維持在另一個業者或地端。這個配置解決資源競爭，可用性與兩台時相同：應用主機或資料庫主機任一台停掉，服務中斷。適合的情形是監控已經分出去、而效能問題來自應用程式與資料庫搶資源。

**兩台應用主機加監控主機。** 兩台各跑一份應用程式，前面放業者的負載平衡器，監控主機在另一個失效域。資料庫不能放在任何一台應用主機上，所以要用業者的託管資料庫（自架與託管的取捨見 [自架還是託管：以資料庫為例](/going-live/self-host-vs-managed-db/)）。這個配置提高可用性：一台應用主機停掉時服務照常，監控主機發出告警通知有一台少了。代價是託管資料庫的費用，以及應用程式要先做到無狀態。兩台應用主機放在同一個業者的不同可用區，才不會因為同一個機房的故障一起停。

兩種配置之外，備份要放在應用與資料庫的失效域以外：另一個業者的物件儲存，或另一個帳號。備份與資料放在同一個帳號時，帳號被停權或憑證外洩後被刪除，兩者一起消失。備份的驗證見 [備份與還原的地基](/going-live/backup-restore-basics/)。

## 雲端業者負責的範圍與自己負責的範圍

服務放在雲端時，雲端業者與使用者之間以[責任分擔模型](/backend/knowledge-cards/shared-responsibility-model/)分工。業者處理所有客戶共用的部分，依應用而不同的部分留給使用者：

| 項目                                    | 業者處理的部分                           | 使用者處理的部分                                                            |
| --------------------------------------- | ---------------------------------------- | --------------------------------------------------------------------------- |
| 實體機房、硬體、電力                    | 硬體故障時把虛擬機搬到其他實體機         | 主機被搬移或重開時，服務能自己啟動回來（容器的重啟策略、開機自動啟動）      |
| 網路層的大流量攻擊（L3/L4 的 DDoS）     | 多數業者在網路邊緣有基本的防護           | 超過防護容量時，部分業者會把被攻擊的 IP 暫時移出網路；條款依業者而定        |
| 應用層的攻擊（HTTP 洪水、掃描、撞密碼） | 預設不處理                               | 入口的限流、CDN 與 [WAF](/backend/knowledge-cards/waf/)、應用程式本身的偵測 |
| 流量突增                                | 用了自動擴充群組或託管服務時，由業者擴充 | 單台虛擬機不會自己變大，要自己設定擴充或預留容量                            |
| 作業系統、應用程式、設定、資料、金鑰    | 不處理                                   | 全部                                                                        |

以短網址服務為例，最可能遇到的攻擊是以正常的 HTTPS 請求大量掃描短碼、對轉址路徑灌請求。這些請求在網路層與一般使用者相同，業者的網路層防護不會攔下，要由入口的限流與掃描偵測處理；前面加一層 CDN 或 WAF，是把應用層的第一道過濾交給 CDN 業者，仍然要自己設定規則。各業者的防護範圍與處置方式寫在它的服務條款與文件裡，選用前查自己那一家。
