## 論述基礎與限制

本卡從一次手機資料庫的升級驗證抽出。量測前，agent 從 Android 手機把 APP 的資料庫三個檔（`book_overview.db`、`-shm`、`-wal`，資料庫用 WAL 模式）複製到電腦當備份，記下三個檔的 SHA1。接著直接對備份的主檔跑 `sqlite3 <備份>/book_overview.db "PRAGMA user_version; SELECT COUNT(*) FROM books;"`，想確認版本與筆數。

之後要從備份還原時，備份目錄裡主檔的 SHA1 從 `ea3753…` 變成 `a3b3c6…`，`-wal` 變成空檔。`sqlite3` 開啟資料庫時讀了 WAL，關檔時做了 checkpoint，把 WAL 的內容寫進主檔並清空 WAL。內容沒有變（還原之後跟升級前的清單逐行比對相同），但備份的檔案已經不是當初複製下來的那一份。之後的查詢都改用 `sqlite3 -readonly` 開還原後拉回來的副本，不再開備份本身。SQLite 的〈Write-Ahead Logging〉寫明 checkpoint 由可寫入的連線發起，由此推論唯讀連線不會把 WAL 併回主檔；唯讀連線會不會寫入 `-shm`，那份文件沒有說明。所以唯讀模式保不保得住三個檔的雜湊，從文件判斷不出來，這一次也沒有拿唯讀模式在備份上比對前後的雜湊。證據來自一份 WAL 模式的資料庫。

## 核心原則

**對檔案的「讀取」由打開它的工具決定會不會寫入。** SQLite 在 WAL 模式下，資料可能還在 WAL 裡、還沒寫進主檔；一般模式開啟的連線在最後關閉時會做 checkpoint，把 WAL 併回主檔。執行的人下的是查詢，工具做的是查詢加上一次寫入。

**備份的價值在於它是某一刻的原樣，被改過之後就失去了比對的依據。** 這次內容沒有變，所以還原沒有出事；但雜湊對不上之後，「這份備份是不是當初那一份」只能靠逐行比對內容來確認。換成一個會在開啟時遷移 schema 的工具（例如 APP 本身），查看一次就會把備份升級成另一個版本。

## 反模式

- **用一般模式的工具直接開備份查內容**：工具可能在關檔時寫入（checkpoint、遷移、重建索引）。
- **只複製主檔當備份**：WAL 模式下最近的寫入可能還在 `-wal` 裡，只有主檔的備份缺了那一段。
- **雜湊對不上之後直接當成備份壞了或沒壞**：要先查是誰在什麼時候動過它，再用內容比對確認。

## 修法

1. **備份時複製全部相關檔**（WAL 模式是主檔、`-wal`、`-shm`），記下每一個檔的雜湊。
2. **查看備份時複製一份再開**：唯讀模式（`sqlite3 -readonly`）會不會寫入 `-shm`，SQLite 的文件沒有說明，要保住三個檔的雜湊就開副本；備份本身只在還原時讀取。
3. **還原之後用內容比對確認**：拿還原後的資料庫跑一份固定的查詢清單（這次是每本書的 id 與書名、標籤關聯、自訂標籤），跟備份當下跑出的清單逐行比對；這份清單在備份後立刻用副本產生。
4. **雜湊對不上時**，先找出在備份之後開過它的工具與時間，再用內容比對判斷內容有沒有變。

## 判讀徵兆

| 徵兆                                | 判讀                                                                                              |
| ----------------------------------- | ------------------------------------------------------------------------------------------------- |
| 備份的主檔雜湊變了，`-wal` 變成空檔 | 有工具以一般模式開過它並做了 checkpoint；checkpoint 只把 WAL 併回主檔，內容是否相同由內容比對判定 |
| 備份只有主檔，還原後少了最近的幾筆  | 最近的寫入還在 WAL 裡，備份時沒有一起複製                                                         |
| 備份的 `user_version` 變成新版本    | 有會遷移 schema 的工具（APP 本身）開過它                                                          |
