## 論述基礎與限制

這張卡處理的情形：寫給 agent 的規則檔變長、讀起來模糊，維護的人準備逐節改寫，手上沒有 agent 實際在哪裡出錯的資料。

來源是 2026-11-22 的一次規則檔重組。入口檔接近 Codex 32,768 bytes 的讀取上限，使用者指出過大的 context 與模糊規則會降低 LLM 執行的成功率。入口瘦身之後，執行重組的 agent 用模糊度普查挑出最模糊的節逐節改寫。**模糊度普查**指每一節派三份低階模型獨立閱讀，回報這一節的觸發條件與通過標準查不查得到。兩批改寫動了 7 節，審查的 subagent 用掉至少 500 萬 tokens。使用者要求重新檢視做法之後，agent 才回頭分析實際的糾正紀錄。

量法分成三段：

- **取單位**：本機留存的 17 個 session（2026-11-03 到 11-22）裡，主 session 中接在 agent 回覆之後、由使用者親自輸入的訊息共 225 則。原始的 1,846 則使用者文字訊息，其餘 1,621 則是系統注入的內容、斜線指令的外殼、context 壓縮摘要與每個 session 的第一則訊息，逐類計數之後加總對得上。
- **篩出糾正**：兩位評分者（低成本模型）各自讀完 225 則，標出使用者表示 agent 做錯或不是要的回覆。兩人的 Cohen's κ（扣掉隨機一致之後的一致度，1 是完全一致）是 0.93，聯集 38 則。拿先前抽樣看過的 18 則糾正核對，聯集涵蓋 17 則，漏掉的那一則補進歸因，共 39 則。
- **歸因**：每一則附上當時的規則版本、agent 在上次 context 壓縮之後載入過的規則與 skill、前後兩輪做的事。兩位評分者各自照同一份判定順序查當時的規則，κ 是 0.71。不一致的 9 則交給沒看過前兩份答案的另一位評分者，8 則取多數，1 則三位各判一類、列為未定。

39 則裡有 12 則判定為 agent 沒有失敗（使用者改變想法或追加新想法），分母是其餘 27 則：

| 成因           | 判定                                       | 則數 | 比例 | 合併同一事件之後       |
| -------------- | ------------------------------------------ | ---- | ---- | ---------------------- |
| 需求沒對齊     | 沒有規則管，而這是這個任務特有的方向或取材 | 9    | 33%  | 5                      |
| 規則缺漏       | 沒有規則管，而同樣的缺陷在別的任務也會發生 | 6    | 22%  | 5                      |
| 規則模糊       | 規則在 context 裡，文字讀得出允許這個產出  | 5    | 19%  | 4                      |
| 讀了沒做       | 規則在 context 裡也寫得清楚，產出仍然違反  | 4    | 15%  | 2                      |
| 沒讀到         | 有規則管，而那段規則不在 context 裡        | 2    | 7%   | 1                      |
| 未定           | 三位評分者各判一類                         | 1    | 4%   | 併入規則模糊的同一事件 |
| 事實或推理錯誤 | 寫錯事實、診斷錯、程式 bug                 | 0    | 0%   | 0                      |

限制：

- 紀錄只有 20 天，27 則失敗有 9 則來自同一個 session，主題集中在音響與音樂文章。
- 這份資料只算得到使用者說出口的糾正，使用者沒發現或沒提的失敗不在內。
- 評分者是模型，而判定當時的規則是否寫得清楚本身要靠判斷。
- 規則模糊的 95% 信賴區間是 8% 到 41%，上緣超過事先訂的三分之一。從這份資料判斷得出規則模糊不是最大的一類，判斷不出它的比例一定低於三分之一。
- 這個分布只描述這段期間，不能當成長期的基本率；下面各種修法的效果都還沒有量過。

## 核心原則

**維護規則的人依失敗的成因決定修法要動哪裡，改寫規則文字只對其中兩類有用。** 同樣是 agent 被糾正，各類成因的修法互不相通：

| 成因       | 修法動的位置                                           | 改寫規則文字的效果             |
| ---------- | ------------------------------------------------------ | ------------------------------ |
| 需求沒對齊 | 動筆前跟使用者對齊讀者、切入角度、比較的起點與不寫什麼 | 每個任務的方向不同，寫不成通則 |
| 規則缺漏   | 只補會重複發生的類別                                   | 有效                           |
| 規則模糊   | 只改出過事的那幾條                                     | 有效                           |
| 讀了沒做   | 把查得到的項目移到動作當下的檢查                       | 文字已經清楚，再改也一樣       |
| 沒讀到     | 修載入與觸發的時機                                     | 新文字同樣進不了 context       |

這次的 27 則裡，需求沒對齊、讀了沒做與沒讀到合計 15 則，改寫規則文字對這 15 則沒有作用。

**讀起來模糊與造成失敗是兩個量。** 普查量的是一節文字單獨拿出來讀得出多少條件。11 則規則相關失敗（規則模糊、讀了沒做、沒讀到）裡，只有 1 則出在這次普查挑出的 7 節。普查的讀數也不穩定：文字完全沒動的 33 節，四次普查量到的「觸發條件查不到」從 19 到 36。分數最好的那一版，正是審查判定改錯範圍最多的版本：agent 把判斷的答案寫成條件之後，探針讀得出條件，而條件本身是錯的。

**只抓退步的回歸量不到改善。** 這次的 114 題封閉案例在改動前後都全對。這組題目抓得到改壞，維護的人從它看不出規則有沒有變好。

**指標、停止線與各結果對應的下一步，要在看歸因之前寫下。** 執行歸因的 agent 已經投入兩批改寫，看完分布再判斷「規則模糊算不算主因」時，訂門檻的人會遷就手上的工作。這次在歸因之前登記：規則模糊低於三分之一就不再逐節改寫，每一類成因最大時對應的下一步也先寫好。

**粗略分類可能得出相反的結論。** Agent 先用關鍵詞抽出 32 則訊息、自己分類，得到「規則與流程維護是最大的一類」。逐則查過當時的規則之後，27 則失敗有 22 則在文章內容，規則與流程只有 3 則。粗分時，agent 把使用者交辦的待辦也算成了糾正。

## 反模式

- **拿讀起來模糊的程度排改寫順序**：排在前面的節讀起來最費力，跟 agent 在哪裡出錯沒有對應。
- **糾正一出現就補規則文字**：需求沒對齊與讀了沒做都不會因此減少，規則的總量卻增加。
- **拿只抓退步的回歸當改善的證據**：改動前已經全對時，改動後全對不帶任何資訊。
- **看完分布才訂門檻**：訂門檻的人會遷就手上正在做的工作。
- **用關鍵詞抽樣加一次人工分類下結論**：待辦與糾正分不開時，分母是錯的。
- **把同一個判斷的連續糾正算成多次獨立失敗**：這次一篇音樂會文章的方向連續被糾正 4 則，它們來自同一個判斷，所以合併前後的數字都要列。

## 修法

1. **取單位並對帳**：定義什麼算一則使用者回覆，把排除的每一類計數，保留數加排除數要等於原始數。
2. **歸因之前先登記**：寫下主要指標、分母、停止線，以及每一類成因最大時對應的下一步。
3. **篩出糾正**：兩位評分者獨立標註，取聯集，再拿幾則已知的糾正核對有沒有漏掉。
4. **每一則附當時的脈絡**：當時的規則版本（取訊息時間點的 commit）、agent 當時載入過的規則與 skill、前後兩輪做的事。拿現在的規則判斷，會把事後補上的規則算成當時就有。
5. **照順序判成因**，停在第一個成立的成因：agent 的失敗；事實或推理錯誤；當時沒有規則管這個缺陷（再分會重複發生的規則缺漏與任務特有的需求沒對齊）；那段規則當時不在 context 裡；文字寫得不夠清楚。
6. **不一致的交給另一位評分者**，這一位看不到前兩份答案；三位各判一類的列為未定，算比例時分別代入。
7. **列出則數與合併同一事件之後的數量**，再照事先登記的對應走下一步。

這次的處置：規則模糊低於停止線，逐節改寫停止。規則缺漏的 6 則有 5 則已在事發之後補進規則。最大的一類是需求沒對齊，所以接下來新增文章或換角度改寫文章時，agent 動筆前先寫出讀者、切入角度、起點與不寫什麼，由使用者確認。同期新增的文章有 53 篇，逐則歸因過的糾正裡這類事件粗估 2 到 3 個；照這個比率，做法完全無效時，5 篇都沒有糾正的機率仍約 75% 到 83%。所以試行看的是使用者在對齊時改了什麼，5 次對齊之後由使用者決定留或撤。試行的結果還沒有。

## 判讀徵兆

| 徵兆                                   | 判讀                                               |
| -------------------------------------- | -------------------------------------------------- |
| 準備逐節改寫規則，手上只有可讀性的分數 | 分數量的是文字，先查實際的糾正                     |
| 規則改了幾輪，封閉題回歸一直全對       | 這組題目量不到改善，要另外找證據                   |
| 糾正多半是「方向不對」「換個角度」     | 需求沒對齊，修法在動筆之前                         |
| 被糾正的內容，規則已經寫得清楚         | 讀了沒做，再改文字也一樣，查得到的項目移到動作當下 |
| 規則存在，而 agent 當時沒有載入那一份  | 沒讀到，修載入與觸發的時機                         |
| 同一篇文章連續幾則糾正                 | 先合併成一個事件再看比例                           |
| 審查每一輪都打在新寫條件的邊界         | 這次可能把判斷的答案寫成了條件，先查留意項那張卡   |

## 跟其他抽象層原則的關係

- [修法要落在缺陷所在的那一層，而看起來做得最多的那個修法通常不在](/report/fix-must-land-on-the-layer-of-the-defect/)：最接近的既有卡。那張卡判斷一處文字的修法動到的是句子成分還是段落；這張卡往上一層，判斷一類失敗該不該動規則文字。
- [工具自動檢查的品質約束買到被量測的那個數字，代價落在沒被量測的維度](/report/mechanical-constraints-buy-the-measured-number/)：模糊度普查是同一個機制。普查量的是探針讀得出多少條件，維護者把判斷寫成條件是提高分數最便宜的做法，而條件本身的對錯，普查量不到。
- [要靠判斷的原則寫成留意項：什麼時候判斷、判斷留下什麼寫成查得到的事實，判斷的答案不寫成條件](/report/judgment-rule-fixes-the-trigger-and-trace-not-the-answer/)：那張卡管一條規則確定要改時怎麼寫；這張卡管改之前先查它有沒有出過事。
- [量測的前置步驟決定了分母，而所有檢查都落在分母之後](/report/measurement-preprocessing-decides-the-denominator/)：這張卡的取單位與對帳照那張卡做。粗分把待辦算成糾正，是分母錯掉而後面的比例都算得正確的實例。
- [門檻要在派發之前寫死，否則「不處置」會被事後合理化](/report/thresholds-registered-before-dispatch/)：這張卡的事先登記用同一個理由，對象從探針的處置線換成整批工作是否繼續。
- [規則的審查走到設計稽核的停點時，先反省寫法、再反省對規則的理解、最後才簡化：理解要對照使用者的原話與既有規則的住址，必修集中在分類的邊界可能是理解偏掉的訊號](/report/rule-nonconvergence-reflect-form-then-understanding/)：那張卡在一批改寫卡住時反省；這張卡排在這一批開始之前，先確認這批改寫對準的是實際發生過的失敗。
- [給操作建議之前先查專案記錄過的結論：建議清 Gradle 快取騰出磁碟空間，前一天的規格已經寫明清它只會讓下一次建置整個建回來](/report/advice-must-check-recorded-findings/)：這張卡管改規則之前先讀記錄過的糾正；那張卡把同一件事延伸到向使用者提操作建議之前：專案記錄過的量測結論，同樣要在推論之前先讀。
