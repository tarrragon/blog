「`tr -d '\r'` 處理的是行尾」——這一句的主詞是一個指令片段。做事的人（寫腳本的工程師）與被操作的系統（adb 回來的輸出）都不在句子裡。讀者要自己還原：誰在跑 `tr`、`tr` 對什麼東西做事、為什麼要做。

這個寫法在指令手冊裡是合理的——手冊的讀者正在看某個工具的文件，主詞就是那個工具，不需要再說一次。搬到教學文章或操作指引裡，讀者帶著一個問題進來，他讀到的那一段可能跟好幾個工具有關，指令片段當主詞會讓他搞不清楚是哪一層在做事。

## 為什麼審查抓不到

跟 #357 一樣的原因：句子讀得懂、語法正確、技術事實正確。審查的判定是「讀得懂嗎？懂。」但讀者要做的還原工作是隱形的——他還原得出來不代表文章不該替他做。

它跟省略主詞（[#355](/report/teaching-is-not-lecturing/) 形態二）的差別：形態二是主詞完全省略（「回答的卻是沒問的那個問題」），這一條是主詞被換成了一個指令片段。省略的句子在語法上不完整，偶爾會被抓到；指令片段當主詞的句子在語法上完整，永遠抓不到。

## 改法

主詞換成做事的人或系統，指令片段降格成工具。

| 改前（指令片段當主詞）              | 改後（操作者或系統當主詞）                                                   |
| ----------------------------------- | ---------------------------------------------------------------------------- |
| `tr -d '\r'` 處理的是行尾           | 腳本裡每一行 `getprop` 的結尾都接了 `tr -d '\r'`，作用是去掉輸出裡的歸位字元 |
| 核心會對經過的位元組做終端機處理    | 作業系統核心的 pty 行規則會把每個 `0x0A` 補成 `0x0D 0x0A`                    |
| `-G 16M` 放大緩衝區                 | `-G` 參數設定 logcat 緩衝區的大小                                            |
| `exec-out` 把結果從版本組合裡拿出來 | 用 `exec-out` 取二進位輸出可以避開 pty 配置的版本差異                        |

判讀方式是問：**這一句的主詞是一個人或系統，還是一個指令片段。** 指令片段包括參數（`-G`）、管線的一段（`tr -d '\r'`）、子命令（`exec-out`）。讀者需要知道的是誰在用這個工具做什麼事——工具本身當主詞的時候這兩件都不在句子裡。

## 跟段落順序的關係

指令片段當主詞的段落通常順序也有問題。「`tr -d '\r'` 處理的是行尾」→ 為什麼行尾有問題 → 後果是什麼——這是工具視角的順序：工具做什麼、為什麼要做、不做會怎樣。讀者的問題序是反過來的：腳本裡這一行在幹嘛（他看到腳本裡有這一行）→ 不加會怎樣（他想知道可不可以省掉它）→ 為什麼會這樣（他想理解機制）→ 加了有沒有副作用。

主詞換對了之後，段落順序通常會自動修正——因為操作者視角的自然順序就是讀者的問題序。

## 候選 grep

這一類沒有穩定的關鍵詞。指令片段的形態太多（反引號包的任何東西都可以當主詞），grep 的假陽性率會大到沒有用。偵測靠冷讀（2-B′）裡的「主詞完整度」那一項，或理解探針裡的「這個動作是誰做的」那一欄——#355 的形態二與本卡用同一條偵測管道，差別在形態二缺主詞、本卡有主詞但主詞是錯的。
