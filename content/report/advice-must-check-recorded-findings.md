## 論述基礎與限制

本卡從一個 Flutter APP 專案連續兩天的磁碟空間不足抽出。Mac 的磁碟只剩 1 到 2 GB，Android 建置或測試因為寫不出檔案而失敗或卡住。

- 第一天，agent 量了各目錄的大小，建議清掉 Gradle 的轉換快取（`~/.gradle/caches/<版本>/transforms`，3.7 GB），使用者同意；清完之後的建置把它整個建回來。agent 在規格的〈建置與磁碟〉一節記下結論：「清掉之後同一次建置就整個重建回來，清它只會讓下一次建置變慢」，並把開發建置改成只建一種 CPU 架構。
- 第二天，磁碟又剩 2.3 GB，量測工作要 6 GB；agent 再次把「清 Gradle 轉換快取」列為建議選項，使用者再次同意。清完騰出 4.2 GB，下一次 `make build-dev` 用掉約 4 GB，可用空間回到 2.5 GB。
- 使用者問：「理論上我們不是重新 build 而已嗎？那應該跟 gradle 無關才對吧？為什麼每次都需要那麼多空間？」agent 這時才去讀規格，發現前一天的紀錄已經否定了這個建議。

實際的狀況是：這個專案平常固定佔約 6.4 GB（Gradle 快取 4.7 GB、`build/` 1.7 GB），兩者都在時增量建置約再用 1 GB；整顆磁碟 228 GB 用掉 200 GB，周轉空間不足的成因在專案以外。證據來自一個專案、同一個 agent session 在 context 壓縮前後的兩次建議。

## 核心原則

**一個操作建議是對「做了之後會怎樣」的預測，而專案自己記錄過的量測結果是這個預測最直接的證據。** 第一天量到的「清了會整個建回來」就是第二天那個建議的結果；只要在提出建議之前查一次規格，那個選項就不會出現。

**提出建議的人最容易略過自己記錄過的結論。** 寫下結論的是同一個 agent，中間經過一次 context 壓縮；壓縮之後，結論只在檔案裡，不在 agent 手上。agent 面對「磁碟不夠」時重新從目錄大小推論，推出的是跟第一天一樣的選項；選項看起來合理（它確實騰出了空間），所以不會被懷疑。

**同一個錯的建議重複出現，代價比第一次大。** 第一次是量測，結果記下來了；第二次是在已經有答案的情況下花掉使用者的一次決定、一次 4 GB 的重新下載與轉換，還讓使用者以為磁碟不夠的成因在建置本身。

## 反模式

- **從當下的觀察重新推論建議，不查專案的紀錄**：觀察（某個目錄很大）跟第一次一樣，推論也會跟第一次一樣，包括第一次已經被證明錯的部分。
- **把「騰得出空間」當成建議成立的依據**：清快取確實騰出空間，但那些空間在下一次建置就被收回；建議要看操作之後的穩定狀態，不看操作當下。
- **把專案固定佔用的工作區當成可以清的暫存**：建置每次都要用的快取與輸出目錄，清掉只會讓下一次重建；能騰出穩定空間的是專案以外的東西。

## 修法

1. **提出操作建議之前，用建議的關鍵詞查專案的規格、工作日誌與 commit 紀錄**（這次的關鍵詞是 Gradle、快取、磁碟），讀到相關的結論就照它判斷。
2. **建議寫出操作之後的穩定狀態**：這次應該寫「清完騰出 4.2 GB，下一次建置會建回來，穩定之後的可用空間不變」，使用者據此就不會同意。
3. **把會被重複遇到的結論寫在建議會出現的位置**：這次把「不要清 Gradle 快取或 `build/` 騰空間，它們是每次建置都要用的工作區；空間不夠要清專案以外的東西」寫進量測步驟與建置的注意事項，量測前的空間需求也改成增量建置的實際用量。
4. **使用者質疑一個建議時，先查這個建議以前有沒有被否定過**，承認重複的那一次，再給正確的判斷。

## 判讀徵兆

| 徵兆                                                     | 判讀                                               |
| -------------------------------------------------------- | -------------------------------------------------- |
| 同一類狀況（磁碟不足、建置失敗）在同一個專案裡第二次出現 | 專案裡很可能已經有第一次的量測與結論，先查再建議   |
| 一個建議執行之後，問題在下一次同樣的操作後回來           | 建議處理的是暫時狀態；查它的穩定狀態有沒有被記錄過 |
| 使用者問「為什麼每次都要這樣」                           | 同一個建議被提了不只一次，而它沒有解決成因         |
| context 壓縮之後立刻要做一個操作決定                     | 壓縮前的結論只在檔案裡，決定之前先讀               |

## 跟其他抽象層原則的關係

- [改規則之前先把使用者的糾正逐則歸因：依讀起來模糊挑出來改的規則，多半不是出過事的那幾條](/report/attribute-recorded-corrections-before-rewriting-rules/)：最接近的既有卡。那張卡讓改規則的人先讀記錄過的糾正；本卡讓提建議的人先讀記錄過的量測結論，兩者都是在做決定之前先查已經存在的證據。
- [審查的射程只涵蓋被審查的對象，工具與共用產物在射程外](/report/review-scope-never-includes-the-instrument/)：建議的推論只看了當下的目錄大小，專案的規格不在那一次推論的射程裡。
- [要求執行者做判定的規則，要一併規定判定留下什麼痕跡](/report/judgment-rules-must-specify-their-trace/)：第一天的結論留下了痕跡（規格裡的一句話），第二天沒有任何步驟要求去讀它；痕跡要有讀的時機才有作用。
- [信號不是承認 — 技術寫作中的歸因語氣](/report/signal-not-admission/)：寫回結論時用客觀條件描述（清快取在什麼情形下會被建回來），不寫成對誰的檢討。
