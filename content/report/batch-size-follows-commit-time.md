## 論述基礎與限制

本卡從一個 Flutter 書庫 APP 的匯入工作抽出。匯入工作把檔案裡的書分批處理：每一批先在記憶體裡規劃（解析、比對重複），再在一個 [Transaction（交易）](/backend/knowledge-cards/transaction/) 裡提交，提交後回報進度。驗收的條件是進度每秒至少更新一次（下文稱 1 秒的更新門檻）；兩次進度更新之間量到的時間，下文稱回報間隔。

在 Android 實機（Samsung SM-S9010，profile 版）往空書庫匯入 5 萬本；量測在第 1 萬本時刻意讓 APP 進背景 3 秒，驗證匯入會暫停，這段暫停期間不算進回報間隔：

- 一批固定 500 本，規劃期間每 1 秒回報一次：最大的回報間隔 1008 ms，超過門檻。
- 規劃期間的回報頻率改成每 0.8 秒一次：量了兩次，最大的回報間隔是 1205 ms 與 1014 ms，沒有變短。
- 讓量測回報最大的三個間隔在哪裡（1014 ms 那一次）：1014 ms 在 42500→43000、871 ms 在 42000→42500、719 ms 在 41500→42000，都在匯入到 4 萬多本時的兩次提交之間，每批提交要 0.7 到 1.0 秒。
- 改成依提交時間調整批次大小（提交超過 0.4 秒就照比例縮小下一批、不低於 50；比 0.2 秒快就加倍、不超過 500）：最大的回報間隔 613 ms，落在 25500→26000，也就是還是 500 本、提交超過 0.4 秒而觸發縮小的那一批；其次的 606 ms 與 579 ms 落在縮小之後的批次。全部時間 31 秒，固定 500 本時也是約 31 秒。

規劃期間每 0.8 秒回報一次的設定留在最後的版本裡：它處理的是規劃那一段的排程誤差（剛好 1 秒時加上排程的誤差會超過門檻）；落在提交裡的那一部分，靠批次大小解決。證據來自一個 APP、一支旗艦手機。

## 核心原則

**進度在一批的提交期間不會更新，所以兩次更新的間隔至少是一批提交的時間。** 規劃期間的回報只發生在規劃那一段；一批的提交在一個 transaction 裡完成，進度只在提交前後回報。提高規劃期間的回報頻率不會改變提交的長度，所以把它改成每 0.8 秒一次的那次修改沒有縮短最大的回報間隔，兩次量到的值還因為執行之間的起伏比 1 秒時更長。

**一批提交的時間隨資料量變長，固定的批次大小只在訂它的那個資料量下成立。** 500 本在書庫剛開始時提交得很快，到 4 萬多本時一批要 0.7 到 1.0 秒。成因推論是書庫越大，每寫入一本要更新的索引（全文索引、衍生欄位、畫面監聽的本數查詢）越貴；各項索引各佔多少沒有拆開量。比較慢的手機上，同一個資料量下的提交推論會更久，沒有量過。

**批次大小要依量到的提交時間調整，目標是讓每一批的提交落在更新門檻之內。** 提交時間大致跟批次大小成正比，所以超過目標時照比例縮小，下一批就回到目標附近；比目標快很多時放大，減少批次之間的固定成本。調整之後，總耗時跟固定大小時差不多，因為總工作量不變，只是切得比較細。

## 反模式

- **以規劃期間的回報頻率保證進度的更新頻率**：回報間隔的上限由最長的那一段不可中斷的工作決定，規劃期間回報得再密也縮不短它。
- **在一台手機、一個資料量下量出批次大小，寫成常數**：資料量長大、換一支比較慢的手機，一批的提交就超過更新門檻。
- **只看最大間隔超過門檻，不看它發生在哪裡**：知道間隔落在提交之間，修法才會對準批次大小；這次把規劃期間的回報頻率改成每 0.8 秒一次，就是在不知道位置時改的。

## 修法

1. **量測回報最大的幾個間隔各自發生在哪兩次回報之間**，判斷它落在規劃、提交還是兩批之間的其他工作。
2. **量每一批提交的時間**，在提交前後各取一次時間。
3. **依提交時間決定下一批的大小**：超過目標（更新門檻的一部分，其餘留給規劃與排程的餘裕；這次是 1 秒的更新門檻、0.4 秒的提交目標）時，下一批的大小乘上「目標 ÷ 這一批的提交時間」，不低於下限；遠低於目標時放大，不超過上限。
4. **拆開一批提交的時間**：SQL 本身、全文索引的更新、提交後畫面監聽的重查各佔多少，拆開之後才知道有沒有比縮小批次更便宜的做法（下面兩種這次都沒有實測）：匯入期間暫停或合併監聽的重查；匯入完成之後才建全文索引。
5. **測試用一個刻意放慢的提交**（每本多花固定的時間），確認批次大小會縮小、每一本都有寫入；最後一批是剩下的本數，下限只套用在它之前的批次。

## 判讀徵兆

| 徵兆                                         | 判讀                                               |
| -------------------------------------------- | -------------------------------------------------- |
| 進度更新的最大間隔越到工作後段越長           | 一批的提交時間隨資料量變長，批次大小沒有跟著調整   |
| 提高規劃期間的回報頻率之後，最大間隔沒有變短 | 最大間隔落在不可中斷的提交裡                       |
| 最大的幾個間隔都落在相鄰批次的提交之間       | 批次太大，提交超過更新門檻                         |
| 調整批次大小之後總耗時明顯變長               | 下限太小、批次之間的固定成本變多，或放大的條件太嚴 |
