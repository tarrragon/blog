## 論述基礎與限制

一天之內同一支共用 skill 在發佈庫上被覆蓋三次，牽涉兩個專案的三個 session。三次的結構相同而角色互換：本專案在其中兩次是被覆蓋的一方，一次是覆蓋別人的一方。

三次都可在發佈庫的 git 歷史裡逐個 commit 查證，本卡的敘述以那份歷史為準，而不是以任何一方的回報為準——其中一次的當事人回報與實際歷史不符，成因寫在下面。

**單一資產、單一工具、單日。** 成立的是機制與修法，不是頻率。

---

## 核心原則

**版號由作者指派，而不是由內容推導，所以它證明不了誰比誰新。** 兩個作者從同一個基底出發，各自取「下一個號」會取到同一個號；版號比對在這種分岔上恆真通過，推送成功那一行照樣印出來，先推的那一份被整檔蓋掉而沒有任何訊號。

能偵測分岔的是**基底**：我這一份從哪裡長出來、對方那一份從哪裡長出來、兩者的共同祖先是什麼。三方比對回答得了這個問題，版號大小回答不了——版號只有一個維度，而分岔是兩個。

推論是：**版號適合用來告訴讀者「這一份跟上一份差在哪」，不適合用來當並行寫入的閘門。** 把它當閘門，等於用一個由被檢查者自己填寫的欄位去檢查被檢查者。

---

## 三次覆蓋

| 次序 | 誰蓋掉誰                    | 版號關係             | 怎麼被發現                                     |
| ---- | --------------------------- | -------------------- | ---------------------------------------------- |
| 一   | B 的 1.8.0 蓋掉 A 的 1.8.0  | 相同                 | A 在下一輪推送前比對版號時發現                 |
| 二   | B 的 1.8.1 蓋掉 A 的 1.9.0  | 倒退                 | B 自行發現，取回歷史版本為基底重推、讓號 1.9.1 |
| 三   | A 的 1.10.0 蓋掉 B 的 1.9.1 | 遞增（而基底是舊的） | A 推完以 git clone 回讀時發現                  |

第一次是版號相同，比對恆真通過。第二次是版號倒退，工具本來會警告而推送端帶了旁路旗標。第三次的版號遞增且看起來完全正常——**A 手上的基底是舊的，於是它算出來的「下一個號」比對方已發佈的號還大，比對照樣放行**。三種形態在版號這一個維度上分別是相等、變小、變大，而三次的實質都是同一件事：推送方沒有對方那一份。

## 為什麼旁路會變成常態

推送工具本來有兩道閘門——portability 檢查與三方方向警告——而一個旗標同時關掉兩者，違規清單只印在標準錯誤。

真正讓它變成常態的是**旁路的理由每一次都成立**。那支 skill 帶著幾處教學用的票號示例，字面命中閘門的樣式而語意上正當，於是每一次推送都要靠旗標才過得去；旗標因此寫進了操作流程。**真違規混在正當豁免裡，就永遠不會被單獨看見。**（這個觀察由對方的 session 提出，本方的紀錄裡原本只有「旗標有未文件化的副作用」這一半。）

處置分兩步而順序不能顛倒：先把正當豁免消掉——那幾處票號示例改用不屬於任何專案的命名空間之後，閘門零違規通過，旗標當場不再需要——再把旗標從流程裡拿掉。只做第二步會讓每次推送都停在同一批已知無害的告警上，而人對重複出現的告警會停止閱讀。

**有一種豁免消不掉，而它正好由修法產生。** 那批票號改名之後，記錄這次改名的 changelog 為了說明改了什麼，必須把舊字面寫出來——於是裝有引用穩定性守衛的消費端拉到新版就提交不了，由該消費端回報才浮現。**汰除某個字面時，記錄那次汰除的文字是它最後一個合法住址**，而任何以字面為判準的檢查對這個住址與對真違規一視同仁。這一類要用行內豁免標記處理，並在標記裡寫出理由；判別是問這個字面在這一句裡是被使用的還是被談論的。

## 第三次的成因：拿快取端點當權威狀態

A 判定自己的內容「第二次被覆蓋」時，讀的是發佈庫的原始檔案端點。那個端點有內容分發快取，回讀到的是數分鐘前的內容，而**它與真實狀態的落差沒有任何訊號**——讀得到、格式正確、看起來就是答案。而 B 當時已經自行復原，也已經修好 A 打算修的那個問題。

於是第三次覆蓋的成因與它想修的錯誤同型：A 據一份過期的觀測做了一次多餘的重寫，而那次重寫蓋掉了 B 已經寫好的修正與紀錄。

查共用資產的實際狀態要用會取得完整歷史的方式（`git clone`），或用推送工具自己印的版號比對行——那一行比對的對象是它自己的複本，不是快取端點。這一項是[代理比本體便宜](../proxy-is-cheaper-than-the-thing-it-stands-for/)的位置重合型實例：快取端點與來源在「讀得到內容」這個位置上重合，取用它與成本差無關，而重合正是它不現形的原因。

---

## 修法

**推送前讀兩行再決定。** 不帶旁路旗標推送時，工具會印出本地與遠端的版號比對、以及「兩側自上次同步後都改動過」的方向警告。版號比對的判準是**本地版號不高於遠端就先拉取合併**；方向警告出現就去逐段比對，不要直接確認。

**讓號規則：先發佈的一方保號，後發現的一方讓號。** 理由是其他消費端可能已經拉走先發佈的那一版，改動已發佈的號會讓他們手上的內容與號對不起來。

**推完立刻以權威來源回讀。** 三次覆蓋裡有兩次是隔了一輪才發現的，而回讀的成本是一次 clone。回讀要驗的是雙方的內容各自還在，不只驗自己的。

**合併時把對方的紀錄原文放回。** 覆蓋事件最容易第二次遺失的是對方寫下的根因分析——它在 changelog 裡，而不在程式碼裡，所以任何以檔案為單位的比對都不會特別提醒它。

## 判讀徵兆

| 訊號                                  | 該做的事                                                 |
| ------------------------------------- | -------------------------------------------------------- |
| 推送流程裡寫死了旁路旗標              | 先查它每次旁路掉什麼；理由每次都成立時，先消掉那個理由   |
| 本地版號與遠端相同或較低              | 先拉取合併，不要靠「我這份比較新」的印象                 |
| 推送成功，而沒有人回讀過發佈端        | 覆蓋在推送端沒有訊號，回讀的成本是一次 clone             |
| 兩個 session 在同一天動同一份共用資產 | 推送前互相要一個可比對的指紋，不要互相問「是不是同一份」 |
| 合併時只比對程式碼與正文              | 對方的根因紀錄住在 changelog，逐檔比對不會特別提醒它     |

**核心**：版號回答「這一份與上一份差在哪」，回答不了「我這一份有沒有蓋掉別人的」。後一個問題只有基底答得出來。
