## 論述基礎與限制

本卡從一個 Flutter 書庫 APP 把藏書上限訂成 5 萬本之後的盤點與實機量測抽出。書庫只有十幾本時，兩段程式的成本看不出來；5 萬本時，完整性檢查在實機冷啟動量到了，重讀全部資料是讀程式碼找到的，單筆寫入的耗時沒有單獨量過：

- **寫入後重讀全部資料**：repository 的每一個寫入方法（新增、修改、刪除一本書）結束時呼叫一個「送出最新書單」的方法，它用 `getAllBooks()` 讀出全部的書，推進一個 broadcast 串流給 `watchBooks` 的監聽者。畫面改成直接查資料庫之後，這個串流在正式執行時已經沒有監聽者；broadcast 串流沒有監聽者時送出的資料會被丟掉，所以每一次寫入都讀出 5 萬本、組成物件，然後丟掉。這段的耗時沒有量過；推估每次寫入多花的時間跟載入全書庫同一個量級，因為兩者都讀出全部的書並組成物件，而第一次實機量測裡載入 5 萬本到首頁花了 7.3 秒（這 7.3 秒還含完整性檢查與其他啟動工作，只是量級的上限）。修法是沒有監聽者時跳過重讀（`hasListener` 為 false 就返回），行為不變。
- **每次啟動檢查整個資料庫**：開檔時有一組「只在開發模式執行」的完整性檢查（`PRAGMA integrity_check`、`foreign_key_check`）。判斷開發模式的寫法是「環境變數裡沒有 `FLUTTER_TEST`」，所以手機上的 debug、profile 與正式版都算開發模式。5 萬本的資料庫（96 MB）在 Mac 上跑這兩項約 0.7 秒，手機更久，而首頁的 provider 要等它做完才拿得到資料庫。改成只在 debug 版執行之後，實機冷啟動從 3.1 秒降到 1.33 秒。

證據來自一個 APP 的兩段程式；單筆寫入在 5 萬本時的耗時沒有量過，其他種類的附帶工作（事件匯流排、log）是同一個機制的推論。

## 核心原則

**一個操作的成本由它附帶的工作決定，不由它名義上動到的資料決定。** 修改一本書名義上動一列；附帶的「送出最新書單」動的是全部的列。附帶工作的成本隨資料量線性放大，名義上的工作不變，所以操作的耗時隨書庫長大，而讀程式的人只看到「改一本書」。

**附帶工作在小資料下量不到，所以它的存在要從程式結構上找，不能等量測。** 十幾本書時，重讀全部資料與完整性檢查都在毫秒內；跑效能測試或在實機上操作的人都感覺不到。資料量到了 5 萬本，完整性檢查在 Mac 上就要約 0.7 秒，而那時候這兩段程式已經寫好很久。

**附帶工作服務的消費者被移除或改寫之後，它的必要性就消失，而程式仍然每次做這份工作。** 「寫入後送出最新書單」當初服務的是一組畫面，那組畫面改成直接查資料庫之後，送出的資料沒有任何人接收；「開發模式才檢查」當初的意圖是只在開發時檢查，判斷式的寫法讓它在每一個非測試的執行裡都成立。兩段程式各自都沒有錯，錯的是它們的前提在系統改變之後不再成立。

## 反模式

- **每次寫入後重讀全部資料當作通知**：通知的內容是全量資料，成本跟資料量成正比，即使只改了一筆。
- **送出沒有人接收的資料**：往 broadcast 串流、事件匯流排、log 送資料的程式，在沒有消費者時照樣做完產生資料的工作。
- **以「不是測試環境」判斷開發模式**：手機上的正式版也不是測試環境；判斷式要寫成「是開發版」（`kDebugMode` 這類編譯期常數），不寫成排除某一種環境。
- **啟動路徑上的全量檢查**：完整性檢查、遷移的全表掃描、重建索引，放在使用者等待的路徑上時，耗時直接加到冷啟動。

## 修法

1. **找出每個操作附帶的工作**：讀寫入方法、開檔、啟動的程式，列出它們呼叫的每一個「順便」做的事（通知、重算、檢查、記錄），寫出每一件的工作量跟什麼成正比。
2. **跟資料量成正比的附帶工作，確認它還有消費者**：通知類的工作在沒有監聽者時跳過（broadcast 串流用 `hasListener`）；有消費者時，改成只送變動的部分，或讓消費者自己查它要的那一小部分。
3. **環境判斷寫成正向的條件**：要「只在開發時做」就判斷是不是開發版，不判斷是不是某一種非開發環境；改完在 profile 或 release 版確認那段程式不執行。
4. **用目標規模的資料在實機跑一次冷啟動與單筆寫入**：量測放在資料量已經長大的狀態，附帶工作才會現形。這次完整性檢查是在 5 萬本的實機冷啟動量到的；寫入後重讀全部資料是讀寫入方法的程式碼找到的，沒有量過單筆寫入的耗時，兩種找法都要做。

## 判讀徵兆

| 徵兆                                                   | 判讀                                     |
| ------------------------------------------------------ | ---------------------------------------- |
| 只動一筆資料的操作，耗時隨資料總量增加                 | 操作附帶了一份全量工作                   |
| 冷啟動時間隨資料量增加，而首頁只顯示幾個本數           | 啟動路徑上有全量的檢查或讀取             |
| 一個串流或事件仍然在產生資料，找不到任何訂閱它的程式碼 | 這份資料沒有消費者，產生它的成本全部浪費 |
| 「只在某種模式下執行」的判斷式寫成排除另一種模式       | 判斷式在預期以外的環境（正式版）裡也成立 |
