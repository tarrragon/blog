## 論述基礎與限制

證據來自一次完整的三輪審查：一篇 work-log 的寫作動機是記錄一個平台機制與對應寫法，三輪九個 reviewer 產出五十餘項 finding，修完之後由作者指出整篇已經變成查證報告，最重的一節（一個異常現象的假說排查）與讀者的問題無關、整節刪除。限制是單一實例，「刪除比例」與「哪一輪排這個 frame 最有效」都沒有跨批資料；本卡主張的是這個 frame 必須存在，不是它的最佳位置。

## 核心原則

多輪審查的每個 frame 都在回答「這篇寫得好不好」，沒有一個在回答「這篇該不該有這一節」。事實查核要求補證據、冷讀要求補脈絡、steelman 要求補排除的假說、個案實跑要求補涵蓋不到的情形——每一項單獨看都是正確的改進，而它們的方向一致：往裡面加。

累積的結果是文章離開它原本要解決的問題。審查因此需要一輪的問題換成：**這篇要讓讀者知道的是什麼，現在它還是在講那件事嗎。**

這一輪的操作是把寫作動機寫成一句話，逐節問「刪掉這一節，那個動機還達得成嗎」。達得成的節就是候選。判定不看那一節寫得好不好——被刪掉的往往是全篇最紮實的部分，因為它是審查投入最多的地方。

## 為什麼審查抓不到

**Reviewer 不知道目的。** 派工的 prompt 通常寫審查維度與輸出格式，不寫這篇的讀者是誰、帶著什麼問題來。上述實例的九個 reviewer 沒有一個問過這件事，於是九個都在優化一篇查證報告的嚴謹度。

**加東西有 finding、刪東西沒有。** Reviewer 的產出單位是 finding，而「這一節不該存在」需要先知道目的才提得出來。缺少目的的情況下，最省力也最安全的產出是指出可以再補什麼。

**膨脹是分次發生的。** 每一輪加的量都不足以構成問題，只有把初稿與定稿並排才看得出偏移。逐輪檢查的視角看不到累積量。

## 修法

派工時把「這篇要讓讀者知道什麼」寫進每個 reviewer 的 prompt，讓維度以外的判斷有依據。事實層與正確性修完之後，排一輪專門的 frame，問三件事：

- 概念與要素會不會太多——讀者要同時記住幾件事才讀得完
- 主題有沒有發散——目前的段落有幾個不同的主題，它們是不是同一個問題的不同面
- 想讓讀者知道的是什麼——用一句話寫下來，再逐節對照

順序不能顛倒。先確保寫的是對的，再確保寫的是需要的；反過來會刪掉還沒被驗證的內容。

## 沒這樣做的麻煩

發散的文章對帶著問題來的讀者最不友善：他要在正確但不相關的內容裡找到自己那一段。而審查投入越多，這個問題越嚴重——每一輪都讓文章更嚴謹、也更遠離讀者的問題。

代價還有一層在流程上。刪掉的那一節通常是審查投入最多的部分（排查、反證、逐條驗證），發現得越晚、丟掉的工作越多。

## 判讀徵兆

| 徵兆                                                             | 判定                                  |
| ---------------------------------------------------------------- | ------------------------------------- |
| 文章長度每輪增加，而讀者要解決的問題從第一版就沒變               | 加的內容多半服務的是審查而非讀者      |
| 某一節的存在理由說得出「這是查證的一部分」而說不出讀者用它做什麼 | 該節是過程的副產品                    |
| 段標列出來之後，有兩組以上互不從屬的主題                         | 主題發散，先問哪一組屬於原本的動機    |
| Reviewer 的 finding 全部是「可以再補什麼」                       | 沒有任何 frame 在問該不該有，補這一輪 |
| 作者要用超過一句話才說得出這篇在解決什麼問題                     | 動機本身已經漂移，先收斂動機再談內容  |

## 這條原則什麼時候不成立

單一目的明確的短文不需要專門一輪：段落數少到可以一眼看完時，發散在寫的當下就會被發現。

參考型內容（規格表、API 文件、術語表）也不適用——它們的完整度本身就是目的，「涵蓋更多」不構成發散。這一輪針對的是有明確讀者問題的文體：教學、檢討、工作紀錄。
