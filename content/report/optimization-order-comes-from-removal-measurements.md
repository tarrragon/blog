## 論述基礎與限制

本卡從三次動畫程式的效能調整抽出，三次都在 2026-11、同一台 macOS 機器上量測，CPU 用 `ps` 或 `top` 取樣；Flutter 與瀏覽器那兩次的畫面開在 144 Hz 的螢幕上，終端機那次的輸出丟到 `/dev/null`，跟螢幕無關。

- **Flutter 的裝飾性動畫**：一棵像素樹每 100 ms 換一次姿勢。照「姿勢一秒只換 10 次」推論，繪製次數降到十四分之一就該省下大部分成本。量出來繪製確實降到每秒 9.7 次，CPU 取樣跟每一幀都重畫的版本一樣落在 58% 到 68% 之間；換成計時器驅動、整條渲染管線一秒只跑 10 次，才降到 11% 到 16%（〔[Flutter 裝飾性動畫的驅動方式比較](/programming/flutter/hands-on/ambient-motion-frame-cost/)〕）。
- **瀏覽器 canvas 上的像素夜空**：讀程式碼時排出的順序是：天空的漸層每一幀重畫整個畫面、上千顆星星每顆各設一次樣式各畫一次（星星數照畫面面積算，3840 × 2160 時約四千三百顆）、整個場景跟著螢幕每秒畫 144 次。實際量的結果（3840 × 2160，Chrome 全部程序的 CPU 加總）：先把重畫上限設成每秒 30 次，從 62% 到 65% 降到 31% 到 32%；在每秒 30 次的基準上暫時把天空漸層整個拿掉，CPU 是 30.6% 到 32.5%，沒有變化；暫時拿掉星星，降到 24% 左右。排在第一的天空在這個基準下省不到 CPU，排在最後的重畫上限省下一半（〔[瀏覽器 canvas 像素動畫的 CPU 量測與重畫上限](/ux-design/06-interaction-feedback/hands-on/canvas-ambient-frame-cap/)〕）。同一個場景，用 JavaScript 計時包住每一幀的回呼，量到每幀 0.7 到 1.0 ms，離 6.9 ms 的幀預算很遠；照這個數字會判定沒什麼好改，而成本落在瀏覽器的 GPU 程序，JS 計時看不到。
- **終端機的 ASCII 鯊魚動畫**：讀程式碼時判斷主要成本可能在模擬（每條鯊魚、每條魚每一幀的運動計算）。用 Node 的 `--cpu-prof` 錄下來，主執行緒忙碌的時間裡約七成在鯊魚的柵格化（程式自己在 CPU 上把形狀逐格取樣），模擬約 4%，組輸出字串約 1.4%（〔[量終端機動畫程式的 CPU](/work-log/terminal-animation-cpu-measurement/)〕）。

限制有三項。**同一位作者、同一台機器**：三次的判讀都來自同一個人讀程式碼的習慣，換一個熟悉 GPU 管線的人，排出的順序可能本來就對。**CPU 取樣的雜訊**：同一個設定的兩次量測差到 7 到 8 個百分點，差距小於這個量的兩個條件只算落在雜訊範圍內（拿掉星星少的約 7 到 8 個百分點就在這個邊緣）；負載降低時，同樣的工作換算出的百分比可能因為處理器降頻而偏高（推論，沒有用 `powermetrics` 驗證），所以百分比降的幅度只能比大小，不能當成工作量降的比例。**拿掉的上限不等於改法的效果**：暫時拿掉一段只量得出它最多省多少，實際改法（快取、合併繪製）省下的比上限少；差額也依量的當下的基準而變，每一段的成本是頻率乘上每一次的工作，先改了頻率，其他段的差額跟著變。**只量了 CPU**：系統的合成器程序（macOS 的 WindowServer）與 GPU 本身的時間、能耗都沒有量，「天空省不到」是 CPU 上的結論。**範圍**：三個個案都是動畫與繪製；資料庫查詢這類候選之間互相牽動（拿掉一個 join 會改變整個查詢計畫）、快取冷熱隨量測順序改變的場合，差額更難逐項解讀，本卡沒有涵蓋。

## 核心原則

**讀程式碼估的是每一次呼叫做了多少事，成本卻由呼叫的頻率乘上每一次的工作決定，而且落在程式碼看不到的地方。** 一個全畫面的漸層在程式碼裡是一行，在 GPU 上可能便宜；上千次小方塊在程式碼裡是一個迴圈，看起來比較貴；「每秒畫 144 次」在程式碼裡根本沒有一行，它是動畫迴圈的預設行為。同樣地，「繪製次數降了」只描述渲染管線的其中一段，合成與柵格化有沒有跟著降，讀繪製的程式碼看不出來。

所以先後順序要等量完再排。量法有兩種，分界在成本落在哪裡。成本在同一個程序的 CPU 上時，錄一次 profile 就拿到全部函式的分布，不必改程式（終端機那一次就是這樣）。成本落在 profile 看不到的地方（瀏覽器的 GPU 程序、合成器）時，用**暫時拿掉**：把候選的那一段關掉或刪掉（畫面錯了也沒關係），量一次整體的 CPU，差額就是在這個基準下改它最多能省的量（這種量法在英文文獻裡叫 ablation）。拿掉比實作改法便宜得多，幾個候選各拿掉一次，就有一張依上限排好的清單；改完一項，基準變了，其餘候選要在新的基準上重新拿掉量。

量法本身要看得到成本落在哪裡。動畫的成本散在好幾個程序與執行緒：瀏覽器的 renderer 與 GPU 程序、Flutter 的 UI 與 raster 執行緒、終端機程式與終端機軟體本身。只量其中一段（JS 回呼的耗時、單一程序的 CPU），讀到的數字可能很小，而機器整體的用量很高。量之前先決定量哪幾個程序，量到的總和要對得上機器上看到的負載。

## 為什麼讀程式碼排出的順序每一項都像有理由

讀程式碼的人手上有一套「什麼操作貴」的直覺，這套直覺多半在 CPU 上的程式裡養成：迴圈次數、配置記憶體、字串處理。繪製的成本有些發生在 GPU 與合成器上，有些由螢幕的刷新節奏決定次數，這些在程式碼裡沒有對應的那一行，直覺也沒有給它們權重。排出來的清單每一項都有理由（全畫面重畫聽起來就貴），清單本身不會顯示它漏掉了什麼。

而且第一個實作出來的改法通常有效，只是效果小。實作者看到數字降了幾個百分點，就把它當成方向對了的證據，繼續照清單往下做；排在清單外、或排在最後的那一項（重畫的頻率）一直沒被量過。

## 修法

1. **先決定量哪幾個程序**：列出程式到畫面之間經過的每一層，各自量。瀏覽器量全部 Chrome 程序的加總，至少分成 GPU 與 renderer，用一個只開這一頁的獨立瀏覽器 profile 量，因為 GPU 程序由同一個瀏覽器的所有分頁共用；Flutter 量 `FrameTiming` 的 build 與 raster 兩段，加上整個行程的 CPU；終端機程式量程式本身，另外記下輸出量（每秒幾 MB），因為終端機軟體解析輸出的成本隨輸出量增減，中間經過 tmux 這類多工器時它也算一層。系統的合成器（macOS 的 WindowServer）與 GPU 的時間或能耗，要用 Instruments 或 `powermetrics` 才看得到。
2. **量基準**，並用一個空白的對照（空白頁、靜止的畫面）確認量法本身的底數；空白對照與基準在同一組其他程式、同一種快取狀態下量。
3. **成本在同一個程序裡時錄 profile；落在 profile 看不到的程序時，候選逐一暫時拿掉**，各量一次，差額寫成「最多省多少」的清單。重畫頻率也是候選之一：把動畫迴圈限制成每秒 30 次量一次。
4. **照清單的順序改**，每改一項量一次，並在新的基準上把其餘候選重新拿掉量一次、重排清單；改法省下的量跟在新基準上量的上限差很多時，回頭看改法，而不是換下一項。
5. **兩種量法互相對照**：profile 的比例跟拿掉的差額對不上時，先查量法（量錯程序、取樣抓到外層的包裝程序、兩次量測的基準不同）。

## 判讀徵兆

- 改法的清單寫完了，裡面沒有任何一項附數字。
- 清單裡沒有「重畫或更新的頻率」這一項，而程式是跟著螢幕刷新跑的動畫。
- 量到的單一數字（JS 回呼耗時、單一執行緒）很小，結論是沒什麼好改，而工作管理員或 `top` 顯示整個應用程式的 CPU 很高。
- 第一個改法讓數字降了幾個百分點，接下來的計畫是照原清單往下做，沒有回頭量清單外的項目。
