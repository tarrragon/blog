## 論述基礎與限制

本卡從一個 Flutter 書庫 APP 在 Android 實機上的一次升級驗證抽出。APP 的資料庫管理器是單例，取用資料庫的 getter 寫成 `_database ??= await _openDatabase(); return _database!;`。書庫的首頁原本只讀一份全書庫的串流；一次重構把首頁改成直接向資料庫查本數、借閱中的書與標籤名單，三個 provider 在首頁第一次建立時同時取用資料庫。實機上 drift 印出「created the database class multiple times」的警告，`PRAGMA journal_mode = WAL` 回 `database is locked`：同一個資料庫檔被開了好幾份連線，彼此搶鎖。

當下停掉 APP、把資料庫拉回來檢查，`integrity_check` 是 ok，資料跟升級前逐行相同；修法之後在測試裡同時取用 5 次，開檔次數從 5 降到 1（[Positive Control（正對照）](/testing/knowledge-cards/positive-control/)：換回舊寫法時是 5）。證據來自一個 APP，只在 Dart 的單一事件迴圈與 drift 的開檔上觀察到；其他語言的執行緒模型與其他資源的初始化沒有在這一次驗證。

## 核心原則

**`x ??= await init()` 要等初始化完成才寫入 `x`，這段時間裡 `x` 一直是 null。** 第一個呼叫者執行到 `await` 時讓出事件迴圈，這時 `x` 還是 null；第二個呼叫者進來，看到 null，也開始一次初始化。「還沒有」的判斷與「已經有」的寫入之間隔著整個初始化的時間，所有在這段時間裡進來的呼叫者都各自初始化一次。

**這個寫法在只有一個呼叫者時永遠正確，所以它在重構之前不會出錯。** 首頁原本只有一個串流在第一次取用資料庫；重構讓三個 provider 在同一個 frame 裡第一次取用，寫法本身沒有變，同時取用的呼叫者數量變了。單例的正確性依賴「第一次取用是循序的」這個沒有寫出來的前提，呼叫端的任何改動都可能打破它。

**要共用的是進行中的那一次初始化，不只是初始化的結果。** 把「正在開檔」的 Future 存起來，之後的呼叫者等同一個 Future；結果出來之後再存結果。初始化失敗時清掉存著的 Future，下一次取用才會重試，否則失敗的那一次會永遠留著。

## 反模式

- **`??= await` 寫在可能同時被取用的 getter 裡**：await 期間進來的呼叫者各開一份。
- **以「目前只有一個地方會先取用」為由不處理**：那是呼叫端的現況，不是單例的保證；呼叫端改成同時取用時，getter 裡沒有任何機制擋得住第二次開檔。
- **存住 Future 但失敗時不清掉**：初始化失敗一次之後，每一次取用都拿到同一個失敗的 Future，直到行程重啟。
- **只看到警告就繼續跑**：重複開啟同一個資料庫檔的警告意味著可能損壞資料，APP 繼續寫入時損壞的範圍會擴大。

## 修法

1. **存住進行中的初始化**：`_opening ??= _open();` 存的是 Future，不 await；取用時 `return _database = await _opening;`。
2. **失敗時清掉**：catch 之後，若存著的仍是這一次的 Future，就清成 null，再丟出例外。
3. **測試同時取用**：讓初始化可以在測試裡換成一個會等待的假實作，同時發出好幾次取用，斷言初始化只執行一次、拿到的是同一個實例；另外測失敗之後的下一次取用會重新初始化。
4. **測試要做正對照**：換回舊寫法跑一次，確認測試會失敗（這次舊寫法開了 5 次）。
5. **重複開啟的警告出現時，先保住資料再修**：停掉 APP，把資料庫拉回來跑完整性檢查，確認資料沒有損壞之後才改程式。

## 判讀徵兆

| 徵兆                                                         | 判讀                                                                                 |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| 「建立了好幾次」「multiple instances」這類警告只在啟動時出現 | 第一次初始化期間有多個呼叫者同時進來                                                 |
| 某次重構讓好幾個元件在同一個畫面同時第一次用到某個資源       | 單例的初始化從循序變成並行，`??= await` 寫法的 getter 會開出好幾份                   |
| 鎖定錯誤只在冷啟動出現，之後就消失                           | 啟動時有兩份連線搶同一個檔；推論是多開的連線沒有被關掉，只有最後寫入的那一份被拿來用 |
| 初始化失敗一次之後，重試永遠得到同一個錯誤                   | 存住的 Future 沒有在失敗時清掉                                                       |
