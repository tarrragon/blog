## 論述基礎與限制

這張卡處理的情形：一支程式反覆從同一個來源取得同一批紀錄（爬取、匯入、同步），每一筆的識別碼由幾種來源依序嘗試產生，取第一個拿得到的；之後的每一次執行，再拿識別碼去對 storage 裡已有的紀錄，決定是更新還是新增。

來源是 2026-11-26 一個 Chrome 擴充功能的排查。提取程式替每一本書產生 `id` 的順序是閱讀連結裡的書號（`reader-…`）、封面網址裡的檔名（`cover-…`）、書名（`title-…`）。2026-03 那一次提取時，書櫃頁剛渲染時的閱讀連結都是同一個佔位網址，96 筆裡有 72 筆改用書名產生識別碼；2026-11 重新提取時三種來源都拿得到，同一本書的 `id` 變成 `reader-…`。合併程式拿 `id`、書城書號、書名加封面三個鍵去對，三個都對不上的舊紀錄被留下，新提取的那一本被新增，同一本書有了兩筆。書名識別碼產生時只留下漢字與半形英數，「十月堂舊書事１」與「十月堂舊書事２」的識別碼因此相同，其中一本被當成新書新增。完整的排查過程見 [Chrome 擴充功能提取書目之後書庫頁停在舊資料的排查：逐段計數、頁首總數的解析、轉送層覆蓋欄位寫錯 storage key、舊識別碼對不上而新增重複、修好之後的殘留資料](/work-log/chrome-extension-library-stale-after-extraction/)。

限制：只有這一次事件；其他系統（資料庫的 upsert、ETL 的去重、行動 App 的離線同步）裡的對應情形，是依同一個機制推得的，沒有在別的專案量過。

## 核心原則

**後備鏈產生的識別碼是當下狀態的函數，不是紀錄本身的屬性。** 「有書號用書號、沒有就用網址、再沒有就用名稱」這條規則，對同一筆紀錄產生哪一個識別碼，取決於執行那一刻哪些來源拿得到。來源的可得性會變：網頁改版、渲染時序、權限、網路失敗、資料補齊，都讓同一筆紀錄在兩次執行之間走到後備鏈的不同位置。識別碼一換，拿識別碼比對的合併程式就認不出它，結果是新增一筆重複，而舊的那一筆繼續留著。

這個失敗很安靜：

- **每一次執行單獨看都對**：每一次產生的識別碼都照規則產生，合併程式照規則比對，沒有一步拋錯。錯誤只在把兩次執行並排時才看得到。
- **後備鏈越長，換位置的機會越多**：鏈上每多一種來源，「這次拿到、上次沒拿到」的組合就多一種。
- **重複的那一筆缺新欄位**：舊紀錄是舊版程式寫的，沒有之後新增的欄位；畫面上看到的是「有些紀錄缺資料」，不像重複。

**後備來源經過正規化時，兩筆不同的紀錄可能得到同一個識別碼。** 名稱、網址這類來源先經過正規化（去掉空白、標點、大小寫、全形字元）再拿來當識別碼時，正規化把原本不同的值壓成同一個。以識別碼建索引、一個識別碼只記一筆時，撞號的兩筆裡後處理的那一筆找不到可以對的紀錄，被當成新的新增，它自己的舊紀錄留下來；或者兩筆被併成一筆，其中一筆的資料被另一筆蓋掉。

**改正規化規則等於替所有紀錄換識別碼。** 發現撞號之後最直接的修法是讓正規化保留更多字元，而它會讓所有以那個來源產生識別碼的舊紀錄在下一次執行時全部對不上，影響比撞號本身大。

## 反模式

- **只存選中的那一個識別碼**：產生識別碼時丟掉其他來源的值，之後換了來源就沒有任何線索可以把新舊兩筆連起來。
- **每次執行都重新推導識別碼，覆寫紀錄原有的識別碼**：紀錄的身分跟著每一次的來源可得性漂移。
- **合併只比對識別碼一個鍵**：取了不同來源的新舊紀錄對不上。
- **索引一個鍵只記一筆**：正規化撞號時，後處理的那一筆無處可對，或兩筆被併成一筆。
- **把沒對上的舊紀錄一律當成殘留刪掉**：其中可能有來源上已經不存在、而屬於使用者的紀錄（已經下架、封存、歸還的項目）。

## 修法

1. **第一次寫入時把識別碼固定下來**：更新既有紀錄時沿用它原本的識別碼，不用這一次推導出的值覆寫；識別碼從這一刻起是一個 fact，不再是每次執行的推導結果。
2. **每一次執行把每一種來源的識別碼都產生並帶著走**（閱讀連結書號、封面檔名、名稱各一個欄位），合併程式拿每一種去對舊紀錄可能用過的那一種；舊紀錄的識別碼前綴（`title-`、`cover-`）讀得出它當初取自哪一種來源。
3. **撞號用一對多的索引與認領處理**：索引一個鍵記下全部同鍵的紀錄，比對時跳過這一次已經被認領的，優先選原始值（完整名稱）完全相同的那一筆；原始值也相同時，用其他欄位（作者、出版者）分開，分不開時標記成待人工判斷，不默默併成一筆。
4. **正規化規則要改時當成遷移處理**：寫一次性的對照（舊識別碼 → 新識別碼），把舊紀錄一起換掉，不讓下一次執行自然對不上。
5. **沒對上的舊紀錄先分類再處理**：在新取得的資料裡找它的對應（同名、同書號）。找得到的是識別碼對不上而新增的重複，把使用者加過的資料併到新的那一筆再清；找不到的是來源上已經不存在的紀錄，保留。

## 判讀徵兆

| 徵兆                                                               | 判定                                                                                   |
| ------------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| 重新匯入或提取之後總數比來源多，多出的那幾筆缺新欄位               | 舊紀錄的識別碼取自後備鏈的另一個位置，跟這次的識別碼對不上，被新增成重複               |
| 同一批紀錄的識別碼前綴不一致（有的 `reader-`、有的 `title-`）      | 識別碼由後備鏈推導，取了哪一種來源隨執行當下的可得性而變                               |
| 兩筆名稱只差一個符號或全形數字的紀錄，其中一筆每次重新提取都被新增 | 正規化把兩個名稱壓成同一個識別碼，索引一個鍵只記一筆                                   |
| 合併摘要裡「沒對上而留著」的筆數每次執行都一樣，而來源沒有減少     | 那幾筆舊紀錄的識別碼與這次的任何一種來源都對不上，可能是重複，也可能是來源上已經不存在 |
| 修好正規化規則之後，重新提取新增的筆數暴增                         | 改規則替所有舊紀錄換了識別碼，沒有做舊識別碼到新識別碼的遷移                           |
