## 論述基礎與限制

這張卡處理的情形：資料從產生端經過一層以上的轉送才到使用端，轉送層替資料加上自己的附註（從哪裡送來、何時轉送），而使用端拿資料裡的某個欄位決定資料寫到哪裡。

來源是 2026-11-26 一個 Chrome 擴充功能（Manifest V3）的排查。content script（見 [Content Script（內容腳本）](/ux-design/knowledge-cards/content-script/) 卡）從書城網頁提取書目，經過 service worker（見 [Extension Service Worker（擴充功能的背景程式）](/ux-design/knowledge-cards/extension-service-worker/) 卡）裡的訊息轉送層送到事件處理器，事件處理器再寫進 `chrome.storage`。提取解析出 1068 本、寫入前也是 1068 本，書庫頁讀到的卻是幾個月前的 96 本。寫入的 key 是 `[object Object]_books`：轉送層在事件資料的 `source` 欄位放進轉送資訊物件（`{ type: 'content-script', tabId, url }`），事件處理器原本拿 `source` 當書城 ID，用 `` `${source}_books` `` 組 key。content script 送出的事件本來沒有帶 `source`，事件處理器一直靠預設值得到書城 ID。同一次排查另外發現同一個書城的 ID 在兩層有兩種寫法：content script 寫 `books-com-tw`，事件處理器寫 `books_com_tw`，就算傳到的是字串，博客來的書目也會寫進沒有人讀的 key。完整的排查過程見 [Chrome 擴充功能提取書目之後書庫頁停在舊資料的排查：逐段計數、頁首總數的解析、轉送層覆蓋欄位寫錯 storage key、舊識別碼對不上而新增重複、修好之後的殘留資料](/work-log/chrome-extension-library-stale-after-extraction/)。

限制：只有這一次事件，兩個形態都出在同一個專案的同一條資料流上；其他語言與框架裡的對應寫法（物件展開、`Object.assign`、dict 的 `update`、訊息佇列的 middleware）是依同一個機制推得的，沒有在別的專案量過。

## 核心原則

**一個欄位名在資料經過的每一層代表同一件事。** 轉送層往資料加附註時，附註放在轉送層自己的欄位名底下，不寫進下游已經賦予業務意義的欄位。這條規則被打破時的失敗形態很安靜：

- **下游照常執行**：被佔用的欄位仍然有值，只是型別或意思換了。下游把它當成原本的意思使用，下游的處理沒有拋錯。
- **型別錯的值被安靜轉成字串**：JavaScript 的樣板字串（template literal）與字串串接遇到物件時轉成 `[object Object]`；其他語言的格式化函式轉成型別名或物件的字串表示（Java 的 `ClassName@hash`、Python 的 dict 內容）。接收端接受任意字串時（`chrome.storage` 的 key、[S3](/devops/infra/knowledge-cards/s3/) 的 object key），組出來的 key 或路徑照樣合法，寫入成功；字串裡帶 `/` 時，路徑還會被切成多層。名稱規則嚴格的接收端（Kafka 的 [Topic](/backend/knowledge-cards/topic/)、資料庫的識別字）會在寫入時報錯，那時失敗不安靜。
- **資料完整寫進錯的位置**：寫入端的 log 印出的筆數是對的；只有讀取端看到的資料停在舊的那一份。排查的人從「資料抓不到」的方向查，會一路查到寫入都是對的。
- **預設值在欄位被佔用時不生效，在產生端沒提供時遮住缺值**：使用端寫成「有值就用、沒有就用預設」（`source || 'readmoo'`）時，被佔用成物件的值是真值（truthy），預設值不會生效；而原本該由產生端提供、實際上沒提供的時候，預設值讓這個欄位看起來一直有正確的值。資料有多個來源時，後果更重：來源不明的資料被寫進預設來源的位置，跟那個來源自己的資料混在一起。

**同一個值在兩層用兩種寫法，是同一類缺陷的另一個形態。** 欄位名相同、值的寫法不同（`books-com-tw` 與 `books_com_tw`）時，值能通過每一層自己的檢查，組出的位置同樣沒有人讀。兩個形態的共同點是：決定資料寫到哪裡的那個值，它的意思由使用端認定，而產生端與轉送層的程式裡沒有這份認定。

**寫測試的人手寫理想的輸入時，測試沒有經過佔用發生的那一層。** 使用端的單元測試自己組事件時，組出來的是使用端預期的形狀，明確帶上正確的 `source: 'readmoo'`，每一項都通過；實際送到使用端的事件經過轉送層，欄位的值不一樣。這次事件處理器的三個測試檔裡有 20 處送出的事件直接帶著書城 ID 的字串，沒有一處經過轉送層。

## 反模式

- **轉送層用常見的欄位名放附註**：`source`、`type`、`id`、`timestamp`、`meta` 這類名字，下游很可能已經用在業務意義上。
- **轉送層把附註展開進資料的同一層**（`{ ...data, source: {...} }`）：展開的順序決定誰覆蓋誰，寫的人看不出覆蓋了什麼。
- **使用端把欄位值直接拼進位置**：沒有檢查值是不是預期值域裡的一個，物件、`undefined`、大小寫或分隔符不同的寫法都組得出合法的字串。
- **同一個識別值在不同層各自定義一份清單**：content script 一份書城 ID、事件處理器一份書城 ID，差在分隔符，各自通過自己的檢查。
- **使用端的測試用手寫的理想輸入**：測不到中間層對資料做的事。

## 修法

1. **附註跟資料分開放**：最穩的做法是封套，資料包在一個欄位、附註放在另一個欄位（`{ data, meta }`），訊息佇列則把附註放進 message header；資料與附註不在同一層，就不共用欄位名。沿用同一層的寫法時，附註放在 `forwardedFrom`、`_transport` 這類只屬於轉送層的欄位名底下，寫轉送層的人在新增欄位之前列出資料已經有的欄位名、避開它們；這只對當下的欄位有效，之後新的產生端可能用到同一個名字。
2. **決定位置的值在使用處驗證值域**（驗證的通用做法見 [Input Validation](/backend/knowledge-cards/input-validation/) 卡）：拿欄位值組 key、路徑、分區名稱之前，先把值正規化到使用端的寫法（分隔符、大小寫），再對照已知值的清單；不在清單裡時改取下一個來源（資料本身帶的欄位）。都沒有時，有多個來源的系統拒收、或把資料放進隔離區（dead-letter）並記錯誤，不寫進預設來源的位置；只有單一來源的系統才用預設，用到時記一筆警告。
3. **寫入時把組出來的位置印進 log**：只印筆數時，「數量對、位置錯」看不出來。印出實際寫入用的那個 key（同一個變數，不在 log 裡另組一次），`[object Object]` 這類字串一眼就看得到。
4. **測試輸入取使用端實際收到的形狀**：在轉送層的出口錄一份實際的資料當測試輸入，或讓測試經過轉送層。這是 mock 跳過一層的同一類盲區，見 [Mock Masking（Mock 遮蔽）](/testing/knowledge-cards/mock-masking/) 卡。
5. **修好之後處理已經寫錯位置的資料**：錯位置的資料在修正上線之後仍然留著，佔空間，有時還讓修正看起來沒有生效（例如舊程式新增的重複紀錄，修好比對規則之後仍然留在畫面上）。先確認它能不能從來源重建：不能重建時（訊息已經確認收下、來源不能重放），它是唯一的一份，先搬回正確位置；已經重建進正確位置時，它是多餘的副本，列出來交給資料的擁有者決定清除。重複的紀錄上使用者加過的資料，先併到保留的那一筆。

## 判讀徵兆

| 徵兆                                                                                                                  | 判定                                                                                                       |
| --------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| storage key、檔名、路徑或分區名稱裡出現 `[object Object]`，或其他語言的物件字串表示（`ClassName@hash`、`{'k': ...}`） | 組位置的欄位值是物件，上游可能有一層佔用了這個欄位名                                                       |
| 寫入端 log 的筆數正確，直接讀 storage 也找不到這批資料在讀取端的 key 底下，而 log 印出的 key 跟讀取端的不同           | 資料寫進了讀取端不讀的位置；key 相同時，成因在寫入之後（寫入失敗、被舊副本蓋回、讀的是另一個儲存區或實例） |
| 某一個來源的資料寫入成功、畫面上永遠是空的，其他來源正常                                                              | 其中一種成因是同一個識別值在兩層用不同寫法；讀取端沒有這個來源、過濾掉它、解析不了它的形狀也會這樣         |
| 使用端的測試全部通過，實機失敗                                                                                        | 其中一種成因是測試輸入沒有經過中間層；在使用端入口印出實際收到的資料，逐欄比對欄位、型別與值分得出來       |
| 轉送層的程式碼把附註展開進資料（`...data` 之後接自己的欄位）                                                          | 附註的欄位名可能跟下游的業務欄位同名，後展開的一方覆蓋另一方                                               |

- [#157 語意錨用單一字串、同義雙名讓引用修復退回人腦對應](/report/semantic-anchor-single-string/)：那張卡是一個對象有兩個名字；本卡裡轉送層佔用欄位名的形態反過來，一個名字指兩個對象（書城 ID 與轉送資訊），同一個值兩種寫法的形態則跟那張卡同形（一個書城兩種寫法），差在受影響的是程式組出的位置，不是人寫的引用。

- [#386 破壞性指令的目標用變數的字串截取組出來時，審核的人看不到要刪什麼；空值、尾斜線與截取對不上會改變刪除範圍，而這類清理夾在檢查指令裡時，核准一次檢查就核准了一次刪除](/report/destructive-target-built-by-string-expansion/)：同一個機制用在刪除上：位置由變數組出來，變數的值不是預期的那一種時，組出的位置照樣合法，動作照樣執行。
