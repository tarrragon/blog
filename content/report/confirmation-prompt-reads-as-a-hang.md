## 論述基礎與限制

本卡從一次把共用 skill 庫推壞的事故抽出。那次操作要刪掉兩個已廢除的檔案並同步到九個專案共用的遠端庫，工具在執行前擋了兩次，兩次都被繞過，結果是多刪一個檔案並把另一個專案做過的一整批修正推回舊版。

證據是單一事故，而機制可以逐步指認：關卡怎麼表現、繞過它的動作為什麼看起來合理、警告為什麼被讀在事後。可推廣的是這個形態與處置；不可推廣的是它多常發生，一次事故量不出頻率。

## 核心原則

互動式確認在沒有 stdin 的環境裡不會說「我需要確認」，它就停在那裡。而停住讀起來是故障——指令跑不完、輸出停在半路、逾時。這個時候手邊正好有一個旗標，名字叫 `--force` 或 `--yes` 或 `-y`，它的功能是跳過確認，而在故障的框架下它被重新讀成「這個環境要用的旗標」。

於是**正是那個設計來讓人看一眼的關卡，在自動化環境裡不只失效，還誘導人主動拆掉它**。失效的形式不是被忽略，是被當成障礙排除。

同一個旗標常同時承擔兩件事：跳過確認，以及在檢查不通過時強行通過。第一個語意在非互動環境裡確實需要，第二個從來不需要——而它們共用一個名字，所以取得第一個就順帶取得了第二個。

## 反模式：把「它會不會做我要的事」當成驗證

刪除類的旗標（`--prune`、`--delete`、`--clean`）驗證起來有一個不對稱：問「它會不會刪掉我要刪的」得到「會」，問「它還會刪掉什麼」也得到答案，而只有第二個問題擋得住人。

實例的 `--prune` 語意是「刪掉只存在於遠端的檔案」。本地要刪的兩個檔案確實符合，所以第一個問題通過了；而遠端另有一個檔案本地一直沒有，它同樣符合，於是一起被刪。那個檔案在事後從別的專案取回，若當時九個專案都沒有它就取不回來了。

同一個事故的第二層更難察覺：工具在輸出第一行印了「雙邊自上次同步後各自改過，這個操作可能丟棄另一側的修改」。那一行是準確的——本地那份停在未清理的舊版，遠端帶著別處做過的清理，推上去把清理整批覆蓋掉。它沒有被忽略，它是被讀在事後：指令送進背景或接了 `tail`，回來時只看結尾的成功訊息。

## 修法

**在非互動環境裡取預覽，不要取執行。** 多數這類指令在確認前會印出完整計畫，所以把「拒絕」餵進去就能拿到計畫而不執行：

```bash
echo "n" | <destructive-command>
```

這一步把關卡從「擋住我」變成「印給我看」，成本是一次額外執行，而它正是原本設計要發生的那件事。看過計畫再決定要不要送。

**逐區段讀計畫，而不是找自己預期的那一項。** 預覽通常分區（新增／修改／刪除），確認自己要的那一項在裡面之後，剩下的區段才是這一步的價值所在。

**警告要在動作之前讀。** 背景執行與 `| tail` 都會讓開頭的警告被結尾的成功訊息蓋過。改動別人也在用的東西時，輸出從頭讀。

**旗標的兩個語意分開要。** 工具若把「跳過確認」與「強行通過檢查」綁在同一個旗標上，先把檢查真的修乾淨，再用那個旗標——這樣它只剩下前一個語意。實例裡的可攜性違規只需要改一句話，而繞過它會在紀錄裡留下一筆本來不必存在的例外。

## 判讀徵兆

- 一條會動到共用資源的指令跑不完，而下一個動作是加旗標重跑。
- 手上的旗標叫 force、yes、skip、no-verify、allow，而使用理由是「這個環境不能互動」。
- 對刪除類旗標的驗證只確認過自己要刪的東西在清單裡。
- 指令送進背景或接了 `tail`，而它會改動的東西不只自己在用。
- 事後回讀輸出時，發現警告在第一行。

## 這條原則什麼時候不成立

**只影響自己的操作。** 本地建置、暫存清理、可以重跑的東西，繞過確認的代價是自己重來一次，不值得為它加一道預覽。

**真正的環境缺陷。** 有些指令在非互動環境裡確實會壞，而不是在等確認。分辨方式是看它停在哪：停在印出計畫之後是關卡，停在計畫之前是故障。

**冪等且可還原的操作。** 版本控制之內的改動可以退回，這時預覽的價值降到只剩省時間。實例的推送落在版控裡而仍然構成事故，是因為八個消費端會各自 pull，還原的時間窗不由自己決定。
