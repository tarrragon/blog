## 論述基礎與限制

本卡從一個 Flutter 書庫 APP 的匯入工作抽出。APP 用 drift 管 SQLite：正式執行時資料庫跑在背景 isolate（`NativeDatabase.createInBackground`；isolate 是 Dart 的執行單位，各自有獨立的記憶體，彼此只能傳訊息），主 isolate 每送一條 SQL、等一次結果，就是一次跨 isolate 的訊息往返；單元測試與 widget 測試用 `NativeDatabase.memory()`，資料庫跟測試在同一個 isolate，沒有往返。寫入一本書要送出約 12 條 SQL：寫入書本身、清掉這本書舊的標籤關聯，以及每個標籤各寫 `tags` 與 `book_tags` 一條。資料庫寫入之後會發出變更通知，畫面上監聽這幾張表的查詢據此重查。

量到的數字：

- 換成 drift 之前，資料庫還是 `sqflite_common_ffi` 時，Mac 上的記憶體資料庫測試匯入 1,000 本約 1 秒，效能測試通過。換成 drift、加上背景的匯入工作之後，測試仍然用同一個 isolate 的記憶體資料庫，量不到往返。
- 換成 drift 之後，Android 實機（Samsung SM-S9010，profile 版）匯入第一個 1 萬本花了約 9.5 分鐘，一批 500 本約 28 秒。
- 在 Mac 上改用跟手機一樣的背景 isolate 執行器重量，一批 500 本要 270 到 350 ms；把同一批 SQL 記下來、用 drift 的 batch 一次送到背景 isolate 之後，降到 50 到 72 ms。實機上同樣 1 萬本從約 9.5 分鐘降到約 4 秒。Mac 上一批 0.3 秒、手機上 28 秒：兩邊同樣用背景 isolate，每條 SQL 的平均成本仍然差了將近百倍。這個平均是總時間除以條數，手機上的 28 秒裡除了往返本身，還可能有匯入期間主 isolate 忙著規劃與畫 frame、回覆要等它空出來，以及監聽查詢在資料庫 isolate 裡排隊，這些成分沒有拆開。

證據來自一個 APP、一種資料庫函式庫與一支手機；其他跨邊界的執行器（網路資料庫、另一個行程的服務）沒有在這一次量過。

## 核心原則

**一段程式的耗時等於它做的工作乘上每一份工作的單位成本，而測試只量到測試環境的單位成本。** 逐條 `await` 的寫入，工作量是 SQL 的條數；每一條的單位成本取決於執行器跟呼叫端隔著什麼。同一個 isolate 的記憶體資料庫，一條 SQL 的成本幾乎只有 SQLite 本身的執行時間；背景 isolate 的執行器，每一條要多付一次訊息的傳遞與等待。所以兩個環境的耗時差隨條數放大：每一條的單位成本差一次往返，條數越多差值越大，而測試環境量到的只有不含往返的那一份成本。

**效能測試能代表正式環境的前提，是兩邊的成本模型一致，不是兩邊跑同一段程式。** 這個 APP 的測試跑的是正式的 repository 程式碼，只換了資料庫的執行器；換掉的正好是決定單位成本的那一件。測試結果在「這段邏輯對不對」上可以代表正式環境，在「這段邏輯要多久」上不能。

**往返的成本在介面的設計上消掉：批次送出的責任集中在一個元件，各個寫入方法照原本的方式寫。** 這個 APP 的寫入邏輯（一本書寫哪些表、標籤怎麼寫）分散在好幾個方法裡，每個方法都對著一個執行器介面逐條寫。修法做了一個同樣介面的語句記錄器，寫入的方法照原本的方式寫：寫入邏輯對著它跑一遍，它只記下 SQL 與參數，最後一次送出。寫入邏輯維持一份，批次送出的責任集中在一個地方。

## 反模式

- **用記憶體資料庫的效能測試當作效能已驗證的依據**：測試通過的那一段，在正式環境的耗時可能差兩個數量級，而兩邊的程式碼一字不差。
- **批次 API 內部仍然逐條 `await`**：這個 APP 原本的批次物件把操作收進清單，提交時在一個 [Transaction（交易）](/backend/knowledge-cards/transaction/) 裡逐條 `await`；介面看起來是批次，往返次數跟逐條寫一樣。
- **以「Mac 上很快」推論手機上也夠快**：兩者的差距不只是 CPU 的快慢，還有執行器的結構；手機上換成背景 isolate 的那一層，Mac 的測試裡根本不存在。
- **為了批次送而另寫一份寫入邏輯**：兩份邏輯（逐條版與批次版）對同一本書寫出的資料要保持一致，之後任何一邊改了，兩份寫出的資料就可能不同，而沒有測試會發現。

## 修法

1. **找出成本模型不同的那一層**：列出測試環境換掉了正式環境的哪些元件（執行器、網路、磁碟、序列化），每一個換掉的元件寫出它在正式環境裡每一次呼叫的成本來源。
2. **效能驗收的數字在正式環境上量**：在 Mac 上用跟手機一樣的 `createInBackground` 開一個檔案資料庫，重現的是往返的次數，用來確認修法減少了往返；每一次往返的成本要在實機上量（這次 Mac 上一批 0.3 秒，手機上 28 秒）。替身環境的數字不當驗收。
3. **把逐條往返改成一次送出**：寫入邏輯對著記錄器跑、記錄器一次送出；送出時在同一個 transaction 裡，一批的寫入一起成功或一起回滾。需要每一條結果的寫入（例如更新之後檢查影響的列數），改成送出之前先用一次查詢確認前提，因為批次送出拿不到逐條的結果。
4. **合併通知**：一次送出寫到好幾張表時，把這些表合成一次變更通知；分開通知的話，監聽資料庫的查詢會被觸發好幾次（這次既有的測試「一批寫入只讓監聽重查一次」在逐表通知時失敗）。

## 判讀徵兆

| 徵兆                                                            | 判讀                                                                                                   |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 測試裡很快、實機上慢了幾十倍以上，而兩邊 CPU 的差距估計只有幾倍 | 兩邊的單位成本不同：測試換掉的執行器決定有沒有往返，實機上每次往返的單價（含排隊與等待）只量得到總平均 |
| 耗時跟寫入的條數（而不是資料量）成正比                          | 成本在每一條的往返，不在 SQLite 本身                                                                   |
| 批次寫入的介面在 transaction 裡逐條 `await`                     | 介面是批次的，往返仍是逐條的                                                                           |
| 換成跟正式環境相同的執行器之後，Mac 上改成一次送出也明顯變快    | 成本跟往返次數有關，加速 CPU 消不掉它                                                                  |
