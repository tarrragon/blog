三個時刻會用到這一篇：為一段還沒有測試的邏輯決定第一條測試該測什麼；改功能、加功能或重構之前，評估現有的測試會替這次變更擋什麼；review 裡爭論某個約束該寫成註解還是測試。三個問題表面不同，共用同一個視角——測試的價值在時間軸上怎麼分布。

## 建立測試時：綠燈當下沒有價值，價值在未來的紅燈

寫測試的當下，程式是對的——不對的話會先修程式再讓測試過。所以測試寫完的那顆綠燈，驗證的是「此刻的行為與此刻的預期一致」，而這件事作者本來就知道。測試的價值全部發生在未來：某一次變更讓行為偏離預期、測試變紅、變更的人在合併之前就知道。

這個時間差改變了建立測試時該問的問題：不是「現在的行為對不對」，是「**未來哪一種改壞，要被這條測試擋下**」。

兩個問題會選出不同的測試。一個批次操作有兩個入口按鈕，差別在合併完成後的收尾——一種回到編輯流程、一種直接進入下一階段；程式的順序是先重設選取狀態、之後才讀取用途值。問「現在對不對」，寫出來的是主流程斷言：合併後清單變成一筆。問「哪種改壞要被擋」，看到的是另一件事：任何人把用途值加進重設的清除清單，第二種用途就靜默走成第一種——不報錯、不彈窗，使用者按 B 得到 A。於是有了這條測試：「直接進入下一階段：不做編輯流程的收尾」。兩條測試在今天都綠，防護範圍完全不同。

防護存不存在可以當場觀察、不必推測：在違反約束的位置故意加一行改動，跑測試——

```text
+2 -1: 直接進入下一階段：不做編輯流程的收尾 [E]
  Expected: Step:<Step.finished>
    Actual: Step:<Step.editing>
```

紅了，防護存在；還原改動。建立一條防護型測試之後做一次這個動作，比讀十遍測試碼可靠——「有測試」與「那條測試會對這個違反發聲」是兩件事。

接手零測試的專案時，「未來哪種改壞要被擋」的第一批答案在風險集中處，起步順序見[無測試 legacy 專案的起步順序](/testing/01-test-strategy-layers/legacy-test-bootstrap/)；變更前先把現狀鎖住的測試形態是 [characterization test](/testing/knowledge-cards/characterization-test/)——它的斷言對象是「現在的行為」而不是「正確的行為」，正是防護視角在缺規格時的退位形式。

## 變更時：測試是唯一在改壞當下發聲的機制

改功能、加功能、重構，三種變更都會經過別人寫下的程式。變更的人手上有哪些防護，差別在訊號出現的時機、以及能不能被忽略：

| 手段 | 訊號出現的時機           | 對變更的人的作用                       |
| ---- | ------------------------ | -------------------------------------- |
| 型別 | 編譯當下，無法忽略       | 寫不出違反約束的程式碼                 |
| 測試 | 跑測試時（pre-commit / CI） | 改壞的當下變紅，合併前就知道           |
| 命名 | 讀到呼叫點時             | 動手前多看一眼，但不會自動發聲         |
| 註解 | 剛好讀到宣告處時         | 批次整理與重構的人常常根本不經過那一行 |

型別的訊號最早，但裝得下的約束窄——「不該是負數」用非負型別就寫不出來；「必須活過某次重設」這種跨函式的讀寫順序寫得出來、而且編譯得過。跨時間必須恆真的條件（[不變式](/ddd/knowledge-cards/invariant/)）落在型別外面時，測試是唯一在改壞當下發聲的位置。

重構時測試有雙重角色，分界在斷言的對象。斷言行為的測試是重構的安全網——行為不變就綠，結構怎麼改都放心；斷言實作的測試是重構的阻力——內部調整就紅，而那顆紅燈不代表壞掉。這條分界就是[斷言品質三問](/testing/05-test-design-judgment/assertion-quality/)的第一問（斷言的是行為嗎），防護視角補上它的理由：重構需要的是「行為被改壞才發聲」的訊號，對實作發聲的測試把訊號稀釋成噪音。

加功能時，既有測試定義舊行為的邊界。新功能動到共用狀態、舊測試紅，代表新功能改壞了舊契約——這顆紅燈正是建立時那個「未來哪種改壞」的兌現，它比使用者回報早了一個部署週期。

## 測試與註解的分工

review 裡「這個約束該寫註解還是測試」的爭論，判準是**這段資訊有沒有對應的斷言**——存不存在一條會紅的斷言，不是造不造得出句子：

- 寫得出會紅的斷言（讀寫順序、時序耦合、狀態邊界）→ 資訊的家是**測試名稱**。
- 要寫出來必須引用 repo 之外的事實（法規、稽核要求、後端契約、當初的取捨）→ 這才是 doc comment 該留的。
- 兩者可以同時成立：`test('留存不得少於七年')` 既有斷言、來源又在 repo 外——測試守行為、註解留出處，各寫各的那一半。

動機是防護的註解是一份沒有保護力的副本：註解不參與執行，改壞的當下不產生任何訊號，它的作用只發生在有人剛好讀到的時候。更糟的是宣稱約束的註解會讓 reviewer 以為有人在守——半年後有人在重設函式補上一行清除，那次 diff 不包含註解所在的行，reviewer 讀到的是一段合理的清理程式碼。

分工有邊界：測試涵蓋不到的 surface（設定檔、build script、schema 定義）註解是唯一載體；給下游用的公開 API，下游 clone 不到專案內部的測試檔，doc 在那裡是契約介面。完整的動機辨識、消除 gate 與失效邊界見 [#253 寫註解的動機是怕被改壞時，要處理的是那個約束](/report/protective-comment-signals-missing-enforcement/)。

## 測試自身的文字：名稱承載意圖，reason 承載處置

上面那條失敗輸出只給了症狀：預期進入下一階段、實際停在編輯階段。拿到紅燈的人下一個問題是「為什麼這個行為是刻意的」——承擔這個「為什麼」的是**測試名稱**。「直接進入下一階段：不做編輯流程的收尾」把意圖寫在名稱裡，紅燈的人讀名稱就知道自己撞到的是一條刻意的規則、不是漏網的 bug。名稱說不出這件事為什麼成立，先改名稱；改完仍說不出來，才考慮在測試旁留註解。

名稱、reason、skip 訊息、檔頭與 setup 註解的逐項紀律——包含 reason 寫失敗的後果與處置、分析詞彙不入程式碼——見[測試註解與命名紀律](/testing/05-test-design-judgment/test-comment-and-naming-discipline/)，該篇文末的彙總判斷表把每類文字的落點列齊了。
