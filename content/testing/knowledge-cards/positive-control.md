Positive Control（正對照）是餵給一道檢查一個已知會被它抓到的輸入，確認它在這個寫法、這個環境下確實會報出來。一道檢查回報「零」有兩種成因：目標確實不存在，或檢查沒有在看（pattern 打錯、掃描範圍不含目標、工具沒找到、輸入的形式它讀不懂）；兩種成因印出的結果相同，讀結果的人要靠正對照才分得開。名稱借自實驗科學（生物與醫學實驗常寫作陽性對照）：同一批實驗放一個已知會產生反應的樣本，它沒有反應時，這一批的陰性結果不能採信。它跟 [Test Oracle](/testing/knowledge-cards/test-oracle/) 分屬判定的兩端：oracle 是判定結果算不算對的依據，正對照確認檢查產生得出「不對」這個結果。

## 跟其他概念的關係

正對照驗的是檢查本身，不是被檢查的對象。[Mutation Testing（突變測試）](/testing/knowledge-cards/mutation-testing/) 是同一個想法用在測試套件上：故意把程式改壞（每一個突變體都是一個已知該被抓到的輸入），看測試套件有沒有失敗；沒有失敗的突變體代表測試在那個位置沒有在看。負對照（negative control）是另一個方向：餵一個已知不該被報出的輸入，確認檢查不會誤報。

一道檢查會印出「讀到幾筆」這類計數時，計數能抓出一筆都沒讀到的情形，抓不出漏讀一部分：計數與違規來自同一次解析，被跳過的那一部分不會被計入。漏讀一部分要靠正對照涵蓋輸入的每一種寫法。

## 可觀察訊號與例子

需要正對照的訊號是一道檢查回報零，而接下來要依這個零做決定：當成「通過」提交、當成「沒有改變」結案、當成「不存在」刪掉防護。2026 年本站 SQL 練習頁的兩個例子：

- 擋寫死值的 CSS 檢查腳本，對重構後的檔案回報 0 處違規。拿重構前、已知寫滿色碼與 px 字級的舊檔跑一次，它報出 123 處，這個 0 才能讀成「沒有違規」。
- 量 id 加權是否還必要的腳本，用 CSSOM 改寫七條規則的選擇器之後，比對結果是「沒有改變」。腳本印出它實際改寫的規則只有一條：過濾條件把六條元件規則誤當成 token 定義跳過了。這次的正對照是拿改寫條數對照預期的七條。

兩例的完整經過在 [CSS 改用 token 取值的重構與驗證：逐元素比對計算後的樣式、字級分成尺寸階與功能字級（primitive 與 semantic token）、!important 與提高特定性的 id 選擇器的替代寫法](/work-log/css-token-refactor-verified-by-computed-style-diff/)。

## 判斷條件與後果

正對照命中、而受檢對象回報零時，這個零可以讀成目標不存在，前提是正對照的輸入跟受檢的輸入是同一種形式：用未壓縮的手寫 CSS 當正對照，證明不了檢查讀得懂壓縮過的 CSS；在本機命中，證明不了 CI 的環境裡也裝了同一個工具。

正對照也沒有命中時，問題在檢查，不在被檢查的對象：先修指令（pattern、範圍、工具路徑、輸入的形式），修到正對照命中，再重跑受檢對象；修好之前的那次零不採用。

正對照只涵蓋它示範的那幾種寫法。受檢的輸入有好幾種語法形式（一行一條規則與一行多條規則、色碼與色名）時，每一種形式各放一個正對照，才知道檢查擋得住哪幾種；沒有放正對照的那幾種，檢查的零只代表沒有量過。
