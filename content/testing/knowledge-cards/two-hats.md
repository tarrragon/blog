Two Hats（兩頂帽子）是 Kent Beck 提出、Martin Fowler 在《Refactoring》裡沿用的重構紀律：寫程式的人同一段時間只戴一頂帽子，戴重構的帽子時只改結構、不改行為，戴加功能的帽子時改行為、不重整結構（這一頂泛指所有改行為的改動：加功能、修 bug、刻意改外觀），要換帽子時先停下來、讓手上的那一批完成。兩頂帽子的驗收不同：重構那一批的驗收是「行為跟改之前一樣」，既有的測試與特徵測試（[Characterization Test](/testing/knowledge-cards/characterization-test/)）照樣通過、比對結果沒有行為上的差異（量測造成的差異與規範上等價的寫法不算）；加功能那一批的驗收是「新的行為符合預期」，要有寫出預期的新測試。一般中文裡「戴兩頂帽子」指一個人身兼兩個角色，跟這裡不是同一件事。

## 跟其他概念的關係

帽子分開的價值在歸因：一批改動只做一種事時，驗收的結果只有一種讀法。重構那一批出現任何行為差異，就是重構改壞的，不必再判斷「這是想要的改變嗎」；混著做時，同一份差異裡有想要的改變也有改壞的地方，讀結果的人要逐處判斷，判錯的那幾處會留下來。重構那一批的「沒有差異」也要確認比對確實在讀，檢查方法見 [Positive Control（正對照）](/testing/knowledge-cards/positive-control/)。

## 可觀察訊號與例子

帽子沒分開的訊號是驗收的人在同一份差異前停下來問「這一處是故意的嗎」：測試失敗了，不知道是改壞了還是預期要改；畫面比對有差異，要回頭問寫的人每一處的意圖。

2026 年本站把 SQL 練習頁的整份 CSS 改成引用 [Design Token（具名設計值）](/ux-design/knowledge-cards/design-token/) 時，把改動分成兩種批次，兩種都逐元素比對改動前後的 [Computed Style（計算後的樣式）](/ux-design/knowledge-cards/computed-style/)。顏色與線寬那一批是重構的帽子：色碼換成引用同值的 token，計算後的值應該不變，比對出現的每一筆差異都先歸成預期以外，再逐筆查是來自量測、規範上等價的寫法，還是畫面改了，只有畫面改了的那幾筆退回。字級收斂那一批是加功能的帽子：十幾種字級併成由小到大固定幾級的尺寸階，計算後的字級刻意要變，開始前先寫下每一個舊值要變成哪一個新值，比對時只放行對得上這張對應表的差異。兩種批次的比對做法與差異歸類在 [CSS 改用 token 取值的重構與驗證：逐元素比對計算後的樣式、字級分成尺寸階與功能字級（primitive 與 semantic token）、!important 與提高特定性的 id 選擇器的替代寫法](/work-log/css-token-refactor-verified-by-computed-style-diff/)，給 agent 照著執行的版本在 [Refactor Without Visual Change — 重構 CSS 而不改外觀的比對與差異歸類](/skills/frontend-with-playwright/refactor-without-visual-change/)。

## 判斷條件與後果

一次改動裡兩種事都有時（重構時發現一個 bug、整理 CSS 時順便收斂字級），分成兩批、各自提交，順序看哪一批的驗收依賴另一批。重構那一批驗的是「行為跟改動前一樣」，基準是改動前的行為，含已知的 bug 也可以，特徵測試記錄的就是含 bug 的現狀；所以已知有 bug 而比對讀得出結果時，可以先重構、把 bug 列成清單，在之後改行為的那一批修，bug 卡在糾結的結構裡時，重構之後常常比較好修。比對讀不出結果時要先處理：既有測試本來就紅，重構那一批的驗收分不出紅燈是舊的還是新的，先修好那幾個測試，或把它們隔離（[Quarantine（隔離）](/testing/knowledge-cards/quarantine/)）；修 bug 的改動小、而且不碰要重構的範圍時，先修也划算。兩批改的是互不依賴的屬性時（顏色與字級），哪一批先做都不影響驗收，本站的例子就是字級那一批先提交。分開的代價是多一次提交與多跑一次驗收；不分開的代價是驗收的人分不出那一批的每一處差異來自哪一種改動，只能逐處猜。

加功能那一批的改動本身是「刻意改值」時，在開始前寫下預期改變的屬性與對應表，驗收的人看每一處差異是否都對得上這張表，跟著改變的值（字級變了，元素的寬高跟著變）要出現在表上那幾個屬性也有差異的元素上才算預期內，不整類放行；沒有這張表，加功能那一批的比對結果跟沒有比對一樣，因為每一處差異都可以說成是想要的。

批次的大小也要讓差異追得到來源：重構那一批一次只動一個元件或一組相關的規則，出現差異時找得出是哪一條改動造成的；一批改了幾百處而出現一處差異，退回整批的成本跟不分批差不多。
