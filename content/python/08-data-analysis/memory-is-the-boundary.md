pandas 把整批資料放進記憶體才開始算，所以記憶體容量是它的硬邊界。這個邊界可以事先估算，而越過之後有三個方向可以走，各自付不同的代價。

## 資料本身佔多少，可以乘出來

數值欄位每一格佔固定的位元組數，所以列數乘欄數乘每格的位元組數就是估算值。`int64` 與 `float64` 各佔 8 個位元組。

五百萬列、兩個數值欄的表格實測佔 76 MB，與 5,000,000 × 2 × 8 = 80 MB 相符。這個量級對現在的機器不構成問題，往上推一個量級（五千萬列）到 760 MB 仍然可行，再往上就要看機器。

字串欄位不適用這個乘法，它的佔用取決於實際的字元內容與 pandas 的字串儲存方式，要用 `df.memory_usage(deep=True)` 實際量。

## 運算過程要的空間比資料本身多

估算容易漏掉的是中間結果。合併與分組會產生暫時的陣列，而它們與原始資料同時存在於記憶體裡。

實測一次 `merge`：兩張表本身合計 38 MB，合併結果 46 MB，而合併期間的額外配置峰值是 136 MB——大約是資料本身的三倍半。

所以判斷標準是「資料量的數倍要放得下」，而不是「資料量放得下」。倍數隨操作而變，合併與排序這類要重排全部資料的操作最高。

## 越過邊界之後的三個方向

**把運算推回資料庫。** 資料如果本來就在資料庫裡，先用 SQL 把量壓下來再載入。這條路不需要換工具，代價是那段運算必須用 SQL 表達得出來。

**換成不需要全部載入的引擎。** DuckDB 接受 SQL，而查詢的對象可以直接是磁碟上的檔案。實測查一個 129 MB 的 CSV 算出列數與平均值，Python 端的配置峰值是 0.0 MB；同一件事用 pandas 先載入再算，峰值 114.5 MB、載入後的 DataFrame 佔 76 MB。

這裡的 0.0 MB 要照字面讀：量的是 Python 自己配置的記憶體，DuckDB 的運算發生在它自己的引擎裡、記憶體不經過 Python 的配置器。它逐段讀檔案，任何時刻只持有其中一段。

Polars 走的是另一條類似的路：介面接近 DataFrame，而它的延遲執行模式讓整段運算先被規劃過再執行，可以只讀用得到的欄位。

**換成分散式。** 資料量大到單機放不下時才進這一格。Spark 把同一份運算拆到多台機器上，代價是叢集本身的維運成本與除錯難度，兩者都比單機高一個量級。

## 換工具之前先確認瓶頸真的是記憶體

程式跑不動有幾種原因，記憶體不足只是其中一種，而它有明確的訊號：程序被作業系統終止、或者機器開始把記憶體換出到磁碟而整體速度崩落。

如果訊號是「慢」而不是「爆」，成因通常在別處——逐列套用函式而沒有用向量化的操作，或者反覆複製整張表。那些換工具解決不了，換了之後在新工具上一樣慢。
