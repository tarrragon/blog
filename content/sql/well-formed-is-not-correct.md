一段查詢送進[引擎](/sql/knowledge-cards/database-engine/)，它檢查的是這段文字合不合法：名字解析得到、型別配得上、子句的組合合乎[關聯代數](/sql/knowledge-cards/relational-algebra/)的規則。通過之後它照著算，回一批列。**「這批列是不是那個問題的答案」不在它檢查的範圍裡**，因為問題不在查詢裡——查詢是問題的一種表達，而表達得對不對，只有提問的人知道。

本篇要用到這兩層的名字。**合法**指上一段那三項檢查都通過——判它不必讀任何一列資料，但要知道是哪一家引擎在判：各家的線不同，標準禁止的寫法有的引擎照收，而那條線怎麼動由「文字之外還有誰在決定」那一支承接；**問對了**指算出來的那份[關係](/sql/knowledge-cards/relation/)（欄位固定、由若干列構成的集合，查詢的結果就是一份關係）正好是那個問題的答案，這個詞是本篇為了指認上面那一層而取的，SQL 的標準術語裡沒有它。

本分類把這個語言拆成三支，本篇屬於問「結果集由什麼決定」的那一支（[章節](/sql/#章節)）。同一支的其餘各篇各講[語意模型](/sql/knowledge-cards/semantic-model/)的一項規則——語意模型指這個語言規定的、由查詢的文字算出結果的那套規則——以及那項規則與直覺相反的那一處；這一篇講直覺錯掉之後會發生什麼——引擎照樣算完、照樣回一批結果，而那批結果不帶任何出錯的訊號。

## 同一個問題，錯的寫法照樣回結果

書店要找出沒有五星評價的訂單。[共用資料](/sql/#各篇共用的範例資料庫)裡訂單 101 有一則五星、訂單 102 沒有評價，所以答案是 102。

正確的寫法把星等的條件放進 `ON`，再挑配不到的那些（[1.5 ON 描述關係、WHERE 篩選結果](/sql/on-describes-where-filters/) 的「找沒配到的那些」一節）：

```sql
SELECT 訂單.訂單編號 FROM 訂單
LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號 AND 評價.星等 = 5
WHERE 評價.評價編號 IS NULL;
-- 102
```

**第一種錯法把「沒有五星」寫成「星等不等於五」。** 其餘不動，只把星等條件挪進 `WHERE` 並改成不等於：

```sql
... LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號
WHERE 評價.星等 <> 5;
-- 0 列
```

這一段問的是「至少有一則非五星評價的訂單」，與「沒有五星評價的訂單」是兩個不同的問題。在這批資料上它回零列：101 唯一那則是五星，條件判成假；102 那一列的星等是[外連接](/sql/knowledge-cards/outer-join/)補上的 [`NULL`](/sql/knowledge-cards/null/)，`NULL <> 5` 的真值是未知，而 `WHERE` 只留下判成真的列（[1.6 連接產出的是新的關係](/sql/join-changes-rows-and-nulls/) 的「NULL 不等於任何值」一節）。**問錯了問題與 `NULL` 擋掉一部分，這兩件疊在一起，所以看到什麼由資料決定。** 訂單 101 多一則三星之後，同一段回的是 101——正解仍然是 102，而它交出了恰好相反的那一列。

補 `OR 評價.星等 IS NULL` 也修不掉。在同一批加了三星的資料上，那樣回的是 101 與 102；而在原本那批資料上，同一個修法回的正好是 102，看起來完全正確。

**第二種錯法漏掉星等條件，而它在現有資料上回了正確答案。** 這一種的星等條件哪裡都沒出現：

```sql
SELECT 訂單.訂單編號 FROM 訂單
LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號
WHERE 評價.評價編號 IS NULL;
-- 102
```

這一段問的是「沒有任何評價的訂單」。它與正解在這批資料上是同一批列，因為有評價的那張訂單剛好只有五星那一則。訂單 102 多一則三星評價之後，正解仍然是 102，而這一段回零列。

**第三種錯法用 `NOT IN` 表達否定的成員判斷。** 星等條件回到[子查詢](/sql/knowledge-cards/subquery/)裡，連接整個省掉：

```sql
SELECT 訂單編號 FROM 訂單
WHERE 訂單編號 NOT IN (SELECT 訂單編號 FROM 評價 WHERE 星等 = 5);
-- 102
```

評價表裡出現一則訂單編號還沒填的五星評價之後，這一段回零列。子查詢這時交出的是 101 與一個 `NULL`，而 `NOT IN` 展開之後是「不等於 101，而且不等於 `NULL`」——後面那一項的真值是未知，整串連乘因此永遠不會是真（完整推導在 [1.6](/sql/join-changes-rows-and-nulls/) 的「NOT IN 碰到一個 NULL 就整個失效」一節）。同一句換成 `NOT EXISTS` 回的仍然是 102。

## 錯的來源不只一種，而輸出都不帶訊號

前兩種問了另一個問題。第一種問「至少有一則非五星評價」，第二種問「有沒有任何評價」——兩段查詢都精確地回答了它們自己問的那一題，而那一題不是要問的那一題。這一類與模型的規則無關：換引擎、加約束、跑靜態分析都碰不到它，因為那段文字沒有任何一處是錯的。

第三種是對模型的一條規則預期錯了。`NOT IN` 的展開方式由模型定死，而寫的人預期它表現得像「不在這個集合裡」。這一類修得掉，改對之後永遠對。

第一種同時踩到兩邊——問錯了問題，而它問的那個問題又被 `NULL` 擋掉一部分——所以它的輸出隨資料變動，這是它比另外兩種難診斷的原因。

這兩種不是全部。 至少還有兩種來源不在上面。一種是引擎接受了標準禁止的寫法並自己補一個值：分組之後把非分組欄放進 `SELECT`，實例住在 [1.2](/sql/clause-evaluation-order/) 與 [1.9 分組鍵決定每一組代表什麼](/sql/grouping-key-decides-the-unit/)，換一家引擎就浮現。另一種是問題本身還沒被決定——「所有訂單都被評價過的顧客」在一張訂單都沒下過的人身上為真，而提問的人多半還沒想過那算不算。這一種連換誰來寫都不會浮現，因為要問的那一題還沒成形。

共通的地方在輸出。**引擎保證的是兩件事：這段文字合法，而算出來的關係符合語意模型。兩項都不決定答案對不對，而答案對不對也不影響這兩項，所以錯誤沒有任何一條經由引擎回報的管道。** 三段查詢一則錯誤訊息都沒有，沒有型別衝突，沒有一列長得奇怪。

輸出本身給不出訊號，而給不出的方式不只一種。第二種的第一版回了正確答案，看不出問題；另外兩種回零列，而零列既可能是「確實沒有」也可能是條件整段失效——分不出這兩者，正是 [1.8 IN、EXISTS 與 JOIN](/sql/in-exists-join/) 把否定式一律交給 `NOT EXISTS` 的理由。結果的形狀正確也不構成保證：兩張訂單的金額是 300 與 500，總額 800；替 101 再加一則評價之後把訂單接上評價再加總，101 那一列被複製成兩列、金額算了兩次，總額變成 1100，而列數與欄位沒有一處看起來不對（[1.6](/sql/join-changes-rows-and-nulls/)）。

第二種另有一個性質：它在寫下的當時通得過任何檢驗。拿現有資料驗它，答案是對的；逐句讀它，每一個子句都符合語法與模型。

## 判準只能來自查詢之外

「問對了沒有」需要一個答案來比對，而那個答案不在查詢裡，也不在資料裡——它在提問的人手上。這是這一層沒有機械**判定**的原因。

**沒有機械判定，不等於什麼都機械不了。** 有些錯法在查詢的文字與表的結構之間就已經自相矛盾，而矛盾成立與否與意圖無關。第一種的 `WHERE 評價.星等 <> 5` 對補 `NULL` 的那些列判成未知，於是外連接保護下來的列一列都留不住——那個 `LEFT` 是死的，換成內連接結果一模一樣，而這個等價由三值邏輯決定，與資料裡有什麼無關。第三種是 `NOT IN` 疊在一個可為空的欄上：建表的時候就宣告了那一欄會有 `NULL`，而 `NOT IN` 碰到 `NULL` 的行為由模型定死，兩件事湊在一起的結果是固定的。這一類的矛盾住在文字自己裡面，所以它成不成立不必提問的人在場。留在提問的人那一側的是**這個形狀是不是他要的**：第二種的文字與正解是同一種寫法，只差 `ON` 少一個條件，而表的結構裡沒有一處說那個條件該在。判準交不出去，而文字自身的矛盾交得出去。

有一部分判準交得出去。[約束](/sql/knowledge-cards/constraint/)是寫進資料庫、由它在每次寫入時檢查的規則：`NOT NULL` 寫下「這一欄不會缺」，外鍵寫下「這個編號一定指得到人」。上面第三種錯法的前提是評價表出現了訂單編號未填的列，而那一欄若帶著 `NOT NULL`，那筆資料一開始就進不來——這是「否定式一律用 `NOT EXISTS`」那條規則的豁免條件，不是那個誤解的修法。**交得出去的界線落在判斷需要什麼**：一句對資料的判斷（一個斷言），若在寫入的那一刻用該筆資料本身、或它指向的那一列就判得完，寫得成約束；判斷需要知道「現在要問的是什麼」的，寫不進去。前兩種錯法問錯了問題，而問題不是資料的性質，所以那一側沒有約束接得住。

交不出去的那一半仍然有一個出口，就在上面三個例子的共同結構裡：每一種都由**一筆讓正解與那個錯的寫法分岔的資料**現形——第一種要一則屬於同一張訂單的非五星評價，第二種要一則 102 的非五星評價，第三種要一則訂單編號未填的五星評價。

**那筆資料從表的結構推得出來，不必先知道哪一種寫法是錯的。** 這一類錯法長在同一批位置上：某一欄是空的、某一欄填了一個指不到任何一列的編號、同一個鍵配到不只一列、被連過去的那張表一列都沒有。那幾種狀態模型全部允許，而寫查詢的人容易當成它們不會發生。兩種寫法的分岔就落在那裡，因為它們對那幾處的假設不同。

一份把那幾處各佔滿一次的資料（五張訂單加七則評價）足以讓上面三種寫法各自交出不同的答案，而提問的人出的仍然只有一件事：這五張訂單裡哪幾張是答案。造得出那筆資料，等於把「要問的是什麼」說到夠精確；造不出來，代表兩個問題在手上這批資料的範圍內確實同義。造得出分岔的資料，與判準交不出去並不牴觸：那筆資料與它對應的正確答案仍然由提問的人給出，機械化的只有比對這一步。

這個出口與約束不在同一層上做事。約束改變的是資料能長成什麼樣，不是查詢的合法性——加上 `NOT NULL` 之後第三種不再回零列，是因為觸發它的那一列進不來，而那段查詢照樣合法、照樣是同一個誤解，同一個人在下一個可為空的欄位上會再寫一次 `NOT IN`。分岔的資料連資料能長成什麼樣都沒動，判準仍然在原地，只是被寫成一個往後還讀得到的形式——那個形式就是一則測試案例，而讀者手上多半已經有跑它的工具。**分岔的資料也只證偽、不證成**——上面第二種在原本那批資料上通過了一切檢驗，而通過從來不是對的證明。射程另有一道邊界：那筆資料由同一個人依他當時對問題的理解寫下，所以這個做法分得出「想的對而寫錯了」，分不出「想的就不對」。

這件事在測試那一側有名字，而那一側分得比這裡細：預期值從哪裡取得叫 [test oracle](/testing/knowledge-cards/test-oracle/)，那張卡列了四種來源與各自抓不到的那些；「寫斷言的人與寫實作的人共用同一份誤解」叫 [test provenance](/testing/knowledge-cards/test-provenance/)；而「造不出分岔的資料」在 [Mutation Testing](/testing/knowledge-cards/mutation-testing/) 裡叫 equivalent mutant。本篇只把這件事放回 SQL 的兩層裡講，那三張卡有本篇沒有的射程。

## 換掉其中一項就走到另一篇

本篇建立的模型裡有三件事可以各自換掉——錯在哪一層、錯給誰看、以及判準由誰持有——每換掉一件就走到另一篇。

**把「答案錯而查詢跑得動」換成「跑不動」**：模型也擋掉一些寫法，而擋得掉的與擋不掉的那條線不由求值順序決定。[1.2 子句的求值順序](/sql/clause-evaluation-order/) 除了求值順序，另一半就寫這條線落在哪裡——同一個放錯邊的條件在一家報錯、在另一家回一份錯的清單。

**把「答案給錯了問題」換成「文字給錯了下一個人」**：那時查詢的答案是對的，錯的是它對讀的人說的話。[1.18 關鍵字宣告意圖，引擎只執行行為](/sql/declared-intent-vs-behaviour/) 把宣告落空的幾種形態收在一起。兩篇處理的是同一道裂縫的兩邊——這一篇的裂縫在問題與文字之間，那一篇在文字與行為之間。

**把判準從提問的人手上移進資料庫**：那是約束做得到的範圍，以及它為什麼只涵蓋一部分。[1.17 外鍵寫下保證，各家引擎決定它生不生效](/sql/foreign-key-and-referential-integrity/) 拿參照完整性走完一輪——它擋下哪些寫入、宣告與生效在哪三個位置分開，以及生效之後上面兩種錯誤各自消失在哪裡。五種約束各保證什麼在 [Constraint（約束）](/sql/knowledge-cards/constraint/)。

本篇之外還有一個與正確性互不覆蓋的軸：同一段查詢要花多久。一段查詢問對了沒有，與它要花多久，各自的判準管不到對方，而代價那一層有一個機械的出口——向引擎要[執行計畫](/sql/knowledge-cards/query-plan/)。[1.16 代價由資料與索引決定](/sql/cost-lives-in-the-plan/) 拿一道題的三種寫法示範排名怎麼隨索引重排。

第一支到這裡結束。它問的是結果集由什麼決定，而答案是那個語意模型加上它與直覺相反的那幾處，以及模型學對了仍然會錯的這一層。**判一段查詢合不合法的是某一家引擎，而各家的線不同**——那條線，連同識別字、權限、最佳化器與約束，是第二支點名的幾方。從 [1.13 識別字送進引擎之後會被改寫](/sql/identifier-rules/) 進去。
