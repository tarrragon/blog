一段查詢送進引擎，它檢查的是這段文字合不合法：名字解析得到、型別配得上、子句的組合合乎[關聯代數](/sql/knowledge-cards/relational-algebra/)的規則。通過之後它照著算，回一批列。**「這批列是不是那個問題的答案」不在它檢查的範圍裡**，因為問題不在查詢裡——查詢是問題的一種表達，而表達得對不對，只有提問的人知道。

本篇要用到這兩層的名字。**合法**指上一段那三項檢查都通過，站內其餘各篇也用這個意思——它只看查詢的文字，一列資料都不必讀就判得出來；**問對了**指算出來的那份[關係](/sql/knowledge-cards/relation/)（欄位固定、由若干列構成的集合，查詢的結果就是一份關係）正好是那個問題的答案，這個詞是本篇為了指認上面那一層而取的，SQL 的標準術語裡沒有它。

本分類把這個語言拆成三支，本篇屬於問「結果集由什麼決定」的那一支（[章節](/sql/#章節)）。同一支的其餘各篇各講**語意模型**的一項規則——語意模型指這個語言規定的、由查詢的文字算出結果的那套規則——以及那項規則與直覺相反的那一處；這一篇講直覺錯掉之後會發生什麼——引擎照樣算完、照樣回一批結果，而那批結果不帶任何出錯的訊號。

## 同一個問題，錯的寫法照樣回結果

書店要找出沒有五星評價的訂單。[共用資料](/sql/#各篇共用的範例資料庫)裡訂單 101 有一則五星、訂單 102 沒有評價，所以答案是 102。

正確的寫法把星等的條件放進 `ON`，再挑配不到的那些（[1.5 ON 描述關係、WHERE 篩選結果](/sql/on-describes-where-filters/) 的「找沒配到的那些」一節）：

```sql
SELECT 訂單.訂單編號 FROM 訂單
LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號 AND 評價.星等 = 5
WHERE 評價.評價編號 IS NULL;
-- 102
```

**第一種錯法把「沒有五星」寫成「星等不等於五」。** 其餘不動，只把星等條件挪進 `WHERE` 並改成不等於：

```sql
... LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號
WHERE 評價.星等 <> 5;
-- 0 列
```

這一段問的是「至少有一則非五星評價的訂單」，與「沒有五星評價的訂單」是兩個不同的問題。在這批資料上它回零列：101 唯一那則是五星，條件判成假；102 那一列的星等是連接補上的 `NULL`，`NULL <> 5` 的真值是未知，而 `WHERE` 只留下判成真的列（[1.6 連接產出的是新的關係](/sql/join-changes-rows-and-nulls/) 的「NULL 不等於任何值」一節）。**問錯了問題與 `NULL` 擋掉一部分，這兩件疊在一起，所以看到什麼由資料決定**：訂單 101 多一則三星之後，同一段回的是 101——正解仍然是 102，而它交出了恰好相反的那一列。在同一批加了三星的資料上補 `OR 評價.星等 IS NULL` 也修不掉，那樣回的是 101 與 102；而在原本那批資料上，同一個修法回的正好是 102，看起來完全正確。

**第二種錯法漏掉星等條件，而它在現有資料上回了正確答案。** 這一種的星等條件哪裡都沒出現：

```sql
SELECT 訂單.訂單編號 FROM 訂單
LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號
WHERE 評價.評價編號 IS NULL;
-- 102
```

這一段問的是「沒有任何評價的訂單」。它與正解在這批資料上是同一批列，因為有評價的那張訂單剛好只有五星那一則。訂單 102 多一則三星評價之後，正解仍然是 102，而這一段回零列。

**第三種錯法用 `NOT IN` 表達否定的成員判斷。** 星等條件回到子查詢裡，連接整個省掉：

```sql
SELECT 訂單編號 FROM 訂單
WHERE 訂單編號 NOT IN (SELECT 訂單編號 FROM 評價 WHERE 星等 = 5);
-- 102
```

評價表裡出現一則訂單編號還沒填的五星評價之後，這一段回零列。子查詢這時交出的是 101 與一個 `NULL`，而 `NOT IN` 展開之後是「不等於 101，而且不等於 `NULL`」——後面那一項的真值是未知，整串連乘因此永遠不會是真（完整推導在 [1.6](/sql/join-changes-rows-and-nulls/) 的「NOT IN 碰到一個 NULL 就整個失效」一節）。同一句換成 `NOT EXISTS` 回的仍然是 102。

## 錯的來源分兩種，而輸出都不帶訊號

前兩種問了另一個問題。第一種問「至少有一則非五星評價」，第二種問「有沒有任何評價」——兩段查詢都精確地回答了它們自己問的那一題，而那一題不是要問的那一題。這一類與模型的規則無關：換引擎、加約束、跑靜態分析都碰不到它，因為那段文字沒有任何一處是錯的。

第三種是對模型的一條規則預期錯了。`NOT IN` 的展開方式由模型定死，而寫的人預期它表現得像「不在這個集合裡」。這一類修得掉，改對之後永遠對。

第一種同時踩到兩邊——問錯了問題，而它問的那個問題又被 `NULL` 擋掉一部分——所以它的輸出隨資料變動，這是它比另外兩種難診斷的原因。

共通的地方在輸出。**引擎保證的是兩件事：這段文字合法，而算出來的關係符合語意模型。兩項都不決定答案對不對，而答案對不對也不影響這兩項，所以錯誤沒有任何一條經由引擎回報的管道。** 三段查詢一則錯誤訊息都沒有，沒有型別衝突，沒有一列長得奇怪。

輸出本身給不出訊號，而給不出的方式不只一種。第二種的第一版回了正確答案，看不出問題；另外兩種回零列，而零列既可能是「確實沒有」也可能是條件整段失效——分不出這兩者，正是 [1.8 IN、EXISTS 與 JOIN](/sql/in-exists-join/) 把否定式一律交給 `NOT EXISTS` 的理由。**結果的形狀正確也不構成保證**：兩張訂單的金額是 300 與 500，總額 800；替 101 再加一則評價之後把訂單接上評價再加總，101 那一列被複製成兩列、金額算了兩次，總額變成 1100，而列數與欄位沒有一處看起來不對（[1.6](/sql/join-changes-rows-and-nulls/)）。

第二種另有一個性質：它在寫下的當時通得過任何檢驗。拿現有資料驗它，答案是對的；逐句讀它，每一個子句都符合語法與模型。

## 判準只能來自查詢之外

「問對了沒有」需要一個答案來比對，而那個答案不在查詢裡，也不在資料裡——它在提問的人手上。這是這一層沒有機械檢查的原因。

有一部分判準交得出去。[約束](/sql/knowledge-cards/constraint/)是寫進資料庫、由它在每次寫入時檢查的規則：`NOT NULL` 寫下「這一欄不會缺」，外鍵寫下「這個編號一定指得到人」。上面第三種錯法的前提是評價表出現了訂單編號未填的列，而那一欄若帶著 `NOT NULL`，那筆資料一開始就進不來。**交得出去的界線落在判斷需要什麼**：一句對資料的判斷（一個斷言），若在寫入的那一刻用該筆資料本身、或它指向的那一列就判得完，寫得成約束；判斷需要知道「現在要問的是什麼」的，寫不進去。前兩種錯法問錯了問題，而問題不是資料的性質，所以那一側沒有約束接得住。

交不出去的那一半仍然有一個出口，而它就在上面三個例子的共同結構裡：每一種都由**一筆讓兩種寫法分岔的資料**現形——第一種要一則同訂單的非五星評價，第二種要一則 102 的非五星評價，第三種要一則訂單編號未填的五星評價。造得出那筆資料，等於把「要問的是什麼」說到夠精確；造不出來，代表兩個問題在手上這批資料的範圍內確實同義。**造得出分岔的資料，與判準交不出去並不牴觸**：那筆資料與它對應的正確答案仍然由提問的人給出，機械化的只有比對這一步。

這個出口與約束不在同一層上做事。約束寫下去之後，引擎在每一次寫入時檢查它，「合法」那一層確實變大了；分岔的資料沒有讓引擎多驗任何一件事，判準仍然在原地，只是被寫成一個往後還讀得到的形式。它也只證偽、不證成——上面第二種在它自己的那批資料上通過了一切檢驗，而通過從來不是對的證明。射程另有一道邊界：那筆資料由同一個人依他當時對問題的理解寫下，所以它分得出「想的對而寫錯了」，分不出「想的就不對」。

## 換掉其中一項會變成什麼

本篇建立的模型裡有三件事可以各自換掉——錯在哪一層、錯給誰看、以及判準由誰持有——每換掉一件就走到另一篇。

**把「答案錯而查詢跑得動」換成「跑不動」**：模型也擋掉一些寫法，而擋得掉的與擋不掉的那條線不由求值順序決定。[1.2 子句的求值順序](/sql/clause-evaluation-order/) 除了求值順序，另一半就寫這條線落在哪裡——同一個放錯邊的條件在一家報錯、在另一家回一份錯的清單。

**把「答案給錯了問題」換成「文字給錯了下一個人」**：那時查詢的答案是對的，錯的是它對讀的人說的話。[1.15 關鍵字宣告意圖，引擎只執行行為](/sql/declared-intent-vs-behaviour/) 把宣告落空的幾種形態收在一起。兩篇處理的是同一道裂縫的兩邊——這一篇的裂縫在問題與文字之間，那一篇在文字與行為之間。

**把判準從提問的人手上移進資料庫**：那是約束做得到的範圍，以及它為什麼只涵蓋一部分。[Constraint（約束）](/sql/knowledge-cards/constraint/) 寫五種約束各保證什麼，以及為什麼豁免的條件必須是一條約束而不是一次觀察——翻遍現在的資料都沒有 `NULL`，只證明此刻沒有。

本篇之外還有一個與正確性互不覆蓋的軸：同一段查詢要花多久。一段查詢問對了沒有，與它要花多久，各自的判準管不到對方，而代價那一層有一個機械的出口——向引擎要計畫。[1.14 代價由資料與索引決定](/sql/cost-lives-in-the-plan/) 拿一道題的三種寫法示範排名怎麼隨索引重排。

還有一種安靜的錯誤來源不在語意模型裡：分組之後把非分組欄放進 `SELECT`，標準禁止這個寫法而有的引擎接受，並自己從那一組列裡挑一個值補上。實例住在 [1.2](/sql/clause-evaluation-order/) 與 [1.9 分組鍵決定每一組代表什麼](/sql/grouping-key-decides-the-unit/)，而它屬於「文字之外還有誰在決定」那一支的議題。
