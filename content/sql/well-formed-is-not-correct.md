一段查詢送進引擎，它檢查的是這段文字合不合法：名字解析得到、型別配得上、子句的組合是語言允許的那些之一。通過之後它照著算，回一批列。**「這批列是不是那個問題的答案」不在它檢查的範圍裡**，因為問題不在查詢裡——查詢是問題的一種表達，而表達得對不對，只有提問的人知道。

本篇要用到這兩層的名字。**合法**指這段文字是[關聯代數](/sql/knowledge-cards/relational-algebra/)允許的一個組合；**問對了**指那個組合算出來的關係，正好是那個問題的答案。引擎驗前一件，後一件沒有機械檢查。這兩個詞是本篇為了分開這兩層而取的稱呼，SQL 的標準術語裡沒有它們。

第一支前面十篇各講模型的一項規則，以及那項規則與直覺相反的那一處。這一篇講直覺錯掉的時候會發生什麼——引擎回一批看起來完全正常的列，而錯誤訊息不會出現。

## 同一個問題，三種安靜的錯法

書店要找出沒有五星評價的訂單。[共用資料](/sql/#各篇共用的範例資料庫)裡訂單 101 有一則五星、訂單 102 沒有評價，所以答案是 102。

正確的寫法把星等的條件放進 `ON`，再挑配不到的那些（[1.5](/sql/on-describes-where-filters/)）：

```sql
SELECT 訂單.訂單編號 FROM 訂單
LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號 AND 評價.星等 = 5
WHERE 評價.評價編號 IS NULL;
-- 102
```

**第一種錯法把「沒有五星」寫成「星等不等於五」。** 其餘不動，只把星等條件挪進 `WHERE` 並改成不等於：

```sql
... LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號
WHERE 評價.星等 <> 5;
-- 0 列
```

102 那一列的星等是連接補上的 `NULL`，而 `NULL <> 5` 的答案是未知，`WHERE` 只留下判成真的列（[1.6](/sql/join-changes-rows-and-nulls/)）。要找的那一列，正好是被 `NULL` 擋掉的那一列。

**第二種錯法漏掉星等條件，而它在現有資料上回了正確答案。** 這一種的星等條件哪裡都沒出現：

```sql
SELECT 訂單.訂單編號 FROM 訂單
LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號
WHERE 評價.評價編號 IS NULL;
-- 102
```

這一段問的是「沒有任何評價的訂單」。它與「沒有五星評價的訂單」在這批資料上是同一批列，因為有評價的那張訂單剛好只有五星那一則。訂單 102 多一則三星評價之後，正解仍然是 102，而這一段回零列。

**第三種錯法用 `NOT IN` 表達否定的成員判斷。** 星等條件回到子查詢裡，連接整個省掉：

```sql
SELECT 訂單編號 FROM 訂單
WHERE 訂單編號 NOT IN (SELECT 訂單編號 FROM 評價 WHERE 星等 = 5);
```

評價表裡出現一則訂單編號還沒填的五星評價之後，這一段回零列。子查詢的結果裡有一個 `NULL`，而 `NOT IN` 展開之後的那串連乘因此永遠不會是真（[1.8](/sql/in-exists-join/)）。同一句換成 `NOT EXISTS` 回的仍然是 102。

## 三種的機制不同，共通的是那批列看起來很正常

三種各自對應模型的一項規則。第一種是三值邏輯：條件的答案有真、假與未知三種，而 `WHERE` 只留真。第二種是條件與它該描述的對象對不上——那一段描述的是「有沒有評價」，而問題問的是「有沒有五星評價」。第三種是 `NOT IN` 的展開方式。三項都是模型定死的規則，三段查詢也都合法。

共通的地方在輸出。三段回來的列數是 0、1、0，沒有錯誤訊息，沒有型別衝突，沒有一列長得奇怪。第二種甚至回了正確答案，只是理由由當時的資料決定。**結果集的形狀正確，是這一類失效安靜的原因**——形狀是引擎保證的那一項，而形狀對與內容對是兩件事。

第二種另有一個性質：它在寫下的當時通得過任何檢驗。拿現有資料驗它，答案是對的；逐句讀它，每一個子句都符合語法與模型。要它現形，需要一筆當時還不存在的資料。

這三種都住在模型裡。同一類失效還有一個來自模型之外的來源——引擎接受了標準禁止的寫法，並自己從組裡挑一個值補上，那一種在 [1.2](/sql/clause-evaluation-order/) 與 [1.9](/sql/grouping-key-decides-the-unit/)，屬第二支的範圍。

## 判準只能來自查詢之外

「問對了沒有」需要一個答案來比對，而那個答案不在查詢裡，也不在資料裡——它在提問的人手上。這是這一層沒有機械檢查的原因，與引擎做了多少無關。

有一種判準交得出去。[約束](/sql/knowledge-cards/constraint/)是寫進資料庫、由它在每次寫入時檢查的規則：`NOT NULL` 寫下「這一欄不會缺」，外鍵寫下「這個編號一定指得到人」。上面第三種錯法的前提是評價表出現了訂單編號未填的列，而那一欄若帶著 `NOT NULL`，那筆資料一開始就進不來。**約束把一部分「問對了」的前提搬進「合法」這一層，於是引擎接手檢查它。** 它涵蓋得了關於資料本身的斷言，涵蓋不了「這段查詢問的是不是那個問題」。

## 換掉其中一項會變成什麼

本篇的可動項是：錯在哪一層、錯給誰看、以及判準由誰持有。

**把「答案錯而查詢跑得動」換成「跑不動」**：模型也擋掉一些寫法，而擋得掉的與擋不掉的那條線不由求值順序決定。[1.2 子句的求值順序](/sql/clause-evaluation-order/) 寫每一步手上有什麼，並示範同一個放錯邊的條件在一家報錯、在另一家回一份錯的清單。

**把「答案給錯了問題」換成「文字給錯了下一個人」**：那時查詢的答案是對的，錯的是它對讀的人說的話。[1.15 關鍵字宣告意圖，引擎只執行行為](/sql/declared-intent-vs-behaviour/) 把宣告落空的幾種形態收在一起。兩篇處理的是同一道裂縫的兩邊——這一篇的裂縫在問題與文字之間，那一篇在文字與行為之間。

**把判準從提問的人手上移進資料庫**：那是約束做得到的範圍，以及它為什麼只涵蓋一部分。[Constraint（約束）](/sql/knowledge-cards/constraint/) 寫哪幾種斷言寫得進去，以及判斷標準的豁免條件為什麼從那裡來。

**把「錯在正確性」換成「錯在代價」**：兩者要分開驗，而代價那一層有一個機械的出口——向引擎要計畫。[1.14 代價由資料與索引決定](/sql/cost-lives-in-the-plan/) 拿一道題的三種寫法示範排名怎麼隨索引重排。
