求值順序是語意模型規定的先後：`FROM` 決定要處理哪個資料集合、`WHERE` 篩掉列、`GROUP BY` 分組、`HAVING` 篩掉組、`SELECT` 算出要輸出的欄位、`ORDER BY` 排序、`LIMIT` 取前面幾列。它與書寫順序不同，寫在最前面的 `SELECT` 在這裡排在倒數第二。

這個順序不規定引擎照什麼次序做事（見 [1.1](/sql/declarative-not-procedural/)）。它規定的是**每一步手上有什麼**——而手上沒有的東西，那一步就用不了。引擎因此會擋下某些寫法，而擋下來的理由分兩種：有的是這一步真的拿不到那個值，換哪一家引擎都一樣；有的是照模型拿不到而這一家替使用者補上了，換一家就變。這兩種在錯誤訊息上長得一樣。

## 每一步手上有什麼

`FROM` 走完之後手上是一個 [relation](/sql/knowledge-cards/relation/)，欄位是來源表的欄位。`WHERE` 因此只能引用這些欄位，一列一列判斷留不留。

`GROUP BY` 之後手上的單位從列換成組，這是整個順序裡變化最大的一步。原本每一列各自獨立，之後每一組是一個單位，而組裡那些列的個別值不再直接可用。

`HAVING` 篩掉的是組，所以它能用[聚合函數](/sql/knowledge-cards/aggregate-function/)——每一組的計數、總和、最大值到這一步都算得出來了。`SELECT` 到這裡才把要輸出的欄位算出來，別名也是在這一步才誕生。`ORDER BY` 排的是已經算好的輸出，所以它用得到別名。`LIMIT` 在最後，它切的是排序完的結果——**沒有 `ORDER BY` 的 `LIMIT` 取到哪一列沒有保證**，因為前面沒有任何一步決定過順序。

這條線走完之後，兩類限制就分得開了：有些值是這一步真的拿不到，有些是照模型拿不到而引擎替使用者補上了。真的拿不到的那些換任何引擎都一樣，引擎補上的那些換引擎會換行為。

## 真的拿不到的：把聚合放進 WHERE

書店有三位顧客，訂單表裡兩張都掛在佳穎名下。要找出下過一張以上訂單的顧客，把「訂單張數大於一」這個條件寫進 `WHERE`：

```sql
SELECT 顧客編號 FROM 訂單 WHERE COUNT(*) > 1 GROUP BY 顧客編號;
```

SQLite 回 `misuse of aggregate: COUNT()`，DuckDB 回 `WHERE clause cannot contain aggregates`。同一個問題移到 `HAVING`：

```sql
SELECT 顧客編號, COUNT(*) AS 張數 FROM 訂單 GROUP BY 顧客編號 HAVING COUNT(*) > 1;
-- 兩個引擎都回 (1, 2)：顧客編號 1 的佳穎，兩張訂單
```

差別在分組發生了沒有。`WHERE` 那一步手上還是一列一列的訂單，「這一組有幾張」這個值在那個時刻還不存在，所以這是模型層的限制而不是功能缺口。這個限制與引擎的寬鬆度無關。

## 引擎自己決定的：WHERE 用 SELECT 的別名

按求值順序，`WHERE` 早於 `SELECT`，別名那時候還沒誕生。標準照這個推論禁止，PostgreSQL 也照這個推論拒絕。

而 SQLite 與 DuckDB 都接受。書店查佳穎這一列，把姓名欄改名之後在 `WHERE` 用新名字：

```sql
SELECT 姓名 AS 客戶 FROM 顧客 WHERE 客戶 = '佳穎';
-- SQLite 與 DuckDB 都回 ('佳穎',)；PostgreSQL 報 column "客戶" does not exist
```

**這個放寬的範圍不是照求值順序推出來的。** `GROUP BY` 與 `HAVING` 同樣早於 `SELECT`，而它們接受別名——`SELECT substr(下單日,1,7) AS 月份 … GROUP BY 月份` 在 SQLite 與 DuckDB 上都跑得動。所以「這一步還沒算到別名」只推得出候選，推不出答案：各家對哪幾個位置放寬、放寬到什麼程度，要各自查。

而放寬是疊在語意模型上面的，沒有取代它。可以從一個細節看出疊的位置：來源表本來就有同名欄位的時候，`WHERE` 綁的是來源欄位而不是別名。實測用一張只有 `x` 與 `y` 兩欄的表，把 `y` 取名成 `x` 之後在 `WHERE` 寫 `x = 1`，SQLite 與 DuckDB 都拿來源欄位 `x` 去比對，回傳那一列的 `y`。**來源表沒有同名欄位的時候，引擎才會讓別名接手這個名字。**

## 列的條件放進 HAVING：有的引擎擋下，SQLite 給出錯的清單

上一種放錯邊會被擋下來。反過來把列的條件放進 `HAVING`，後果分兩家，而其中一家不報錯。

這一節要多幾則評價才看得出來，所以換掉共用資料裡那一則，並多加一張訂單 103——換完之後訂單 101 有五星與三星各一則，訂單 102 有兩則五星，訂單 103 有一則三星：

```sql
INSERT INTO 訂單 VALUES (103, 2, '2026-03-20', 400);
DELETE FROM 評價;
INSERT INTO 評價 VALUES (1,101,5),(2,101,3),(3,102,5),(4,102,5),(5,103,3);
```

要問的是「哪些訂單有兩則以上的五星評價」。正確的寫法把星等這個列的條件放 `WHERE`：

```sql
SELECT 訂單編號, count(*) FROM 評價
WHERE 星等 = 5 GROUP BY 訂單編號 HAVING count(*) >= 2;
-- 102 | 2
```

只有 102，因為 101 的兩則評價裡只有一則是五星。走一遍就看得到為什麼：`WHERE` 先砍掉三星那兩列，剩下三列拿去分組，組 101 只剩一列而組 102 有兩列，`HAVING` 再篩掉組 101。

把星等的條件搬進 `HAVING`：

```sql
SELECT 訂單編號, count(*) FROM 評價
GROUP BY 訂單編號 HAVING 星等 = 5 AND count(*) >= 2;
```

DuckDB 拒絕，訊息是 `column 星等 must appear in the GROUP BY clause`——分組之後組裡有兩個不同的星等，「這一組的星等」沒有定義。MySQL 8 也拒絕，而它的訊息點名了負責這件事的設定：

```text
ERROR 1055 (42000): ... not in GROUP BY clause and contains nonaggregated column
... incompatible with sql_mode=only_full_group_by
```

`ONLY_FULL_GROUP_BY` 從 MySQL 5.7 起是預設值。它是一個可以關掉的開關，而關掉之後 MySQL 的行為就與下一段的 SQLite 相同。

**SQLite 接受，回 101 與 102。** 兩張訂單都被報成「有兩則以上五星」，而 101 只有一則。SQLite 從組裡取了其中一列的星等拿去比對，而它取到的剛好是 101 那組裡五星的那一列，於是整組通過。

至於它會取到哪一列，多數時候規格不保證。唯一的例外是同一個 `SELECT` 裡只有一個 `min()` 或 `max()` 的時候——那時 SQLite 保證非分組欄取自那個極值所在的列，這一點有明文規定。除此之外不要依賴它挑中哪一列。

**這一種的危害高於前一種，因為輸出看起來完全合理。** 每組一列、欄位齊全、訂單編號都是實際存在的訂單——沒有任何一處會讓人停下來檢查。放錯邊的那個條件在報錯的引擎上寫的當下就會發現，在寬鬆的引擎上會一路帶著錯的清單走下去。

同一個機制還有一個比較溫和的形態：`SELECT 顧客編號, 下單日 FROM 訂單 GROUP BY 顧客編號`，DuckDB 同樣拒絕、SQLite 回一個從組裡任意挑的日期。那一種只是值不確定，這一種是整份清單錯了。

## 兩種限制的差別落在可攜性

分開這兩種限制的是那個值存不存在。分組還沒發生的時候，「這一組有幾張」這個值本身還沒有被算出來，所以那是真的拿不到；`SELECT` 那一步還沒算的時候，別名這個名字還沒誕生，而它要指的值早就在手上了——差的只是一個稱呼，有些引擎因此願意替使用者把名字對回去。

差別落在可攜性。真的拿不到的那些會在第一次執行就擋下來，引擎補上的那些會安靜跑過，等到換引擎才浮現——而其中最麻煩的一種連換引擎都不報錯，只是換一個值回來。

## 換掉其中一項會變成什麼

本篇的可動項是：看哪一步、限制屬於哪一種、以及條件擺在哪一步。

**把 `FROM` 那一步展開**：本篇把它當成一個交出關係的黑盒，而多張表的時候它自己就是一個過程——按書寫位置逐個把表併進來。[1.3 JOIN 的左邊是累積結果](/sql/join-left-operand-accumulates/) 寫這個累積怎麼決定每個 `ON` 引用得到哪些欄位。

**把問題從「這一步能不能用某個值」換成「同一個條件擺哪一步」**：條件的合法性換成條件的位置，答案就從報不報錯變成留下哪些列。[1.4 ON 描述關係、WHERE 篩選結果](/sql/on-describes-where-filters/) 用同一組書店資料把兩種擺法的結果並排，並給一個代進 NULL 就看得出來的測試。

**往回問這個順序從哪裡來**：它是宣告式這個選擇的產物。[1.1 宣告式的紅利與代價](/sql/declarative-not-procedural/) 用有無統計資訊的兩個計畫證明引擎並沒有照書寫順序做事，並把書寫、求值、執行三種順序分開。
