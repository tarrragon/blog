SQL 寫的是要什麼結果，不是怎麼算出來。這一條是這個語言其餘每個特徵的來源，包括它最容易讓人讀錯的那些。

**與逐步執行的程式對照一次，這個性質最清楚。** 用 pandas 或任何一種資料框寫「找出下過單的顧客」，寫下的是一串動作：先載入這張表、再依條件篩選、再與另一張表合併，每一行都指定了下一步做什麼，而執行就照那個順序發生。SQL 寫下的是一段描述——哪些表參與、配對的條件是什麼、要留下哪些列——至於先讀哪一張、用什麼演算法配對、要不要臨時建索引，一個字都沒說。

紅利是描述與實作脫鉤。一段查詢在一萬列與一億列的資料上都不必改寫，換一台機器、換一個索引配置也不必改寫，因為怎麼算從來就不在寫下的查詢文字裡面。代價是同一件事的另一面——怎麼算不在寫的東西裡面，所以從查詢的文字看不出它要花多少。

## 三種順序

**書寫順序**是子句在文字上的先後：`SELECT` 在最前面，`FROM` 跟在後面，`WHERE`、`GROUP BY`、`HAVING`、`ORDER BY` 依序往下。這個順序是給人讀的，它的作用是讓查詢讀起來像一句話。

**求值順序**是語意模型規定的先後。它與書寫順序不同：先由 `FROM` 決定要處理哪個資料集合，再用 `WHERE` 篩掉列，接著 `GROUP BY` 分組、`HAVING` 篩掉組，最後才輪到 `SELECT` 把要輸出的欄位算出來、`ORDER BY` 排序。寫在最前面的 `SELECT` 在語意上排在倒數第二步。

**執行順序**是引擎實際做的事，由 [query optimizer](/sql/knowledge-cards/query-optimizer/) 決定，而它只受一個約束：輸出的列集合要與語意模型算出來的一致。在這個約束之內，它可以任意重排、可以換演算法、可以臨時建資料結構。

這三者不一致是宣告式這個選擇本身帶來的。讀查詢時的多數誤判來自把其中兩種當成同一種——最常見的是拿書寫順序去猜執行順序，以為「寫在前面的表會先被讀」。

## 執行方式由引擎知道什麼決定，不由書寫順序決定

拿書店的兩張表來看這件事。顧客表五十列，訂單表二十萬列，要數的是兩者配得上的訂單有幾筆。同一個問題寫成兩種順序：

```sql
SELECT count(*) FROM 訂單 JOIN 顧客 ON 訂單.顧客編號 = 顧客.顧客編號;
SELECT count(*) FROM 顧客 JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號;
```

兩者都回 `200000`。看它們的 [query plan](/sql/knowledge-cards/query-plan/) 要用 `EXPLAIN QUERY PLAN`（SQLite 的 `EXPLAIN` 給的是逐行 bytecode，不是計畫），而計畫取決於引擎手上有沒有這兩張表的統計資訊。

這一節的兩張表可以這樣造：

```sql
CREATE TABLE 顧客 (顧客編號 INT, 姓名 TEXT);
CREATE TABLE 訂單 (訂單編號 INT, 顧客編號 INT, 金額 INT);

WITH RECURSIVE n(i) AS (SELECT 1 UNION ALL SELECT i+1 FROM n WHERE i < 50)
INSERT INTO 顧客 SELECT i, '顧客' || i FROM n;

WITH RECURSIVE n(i) AS (SELECT 1 UNION ALL SELECT i+1 FROM n WHERE i < 200000)
INSERT INTO 訂單 SELECT i, i % 50 + 1, i % 900 FROM n;
```

**剛建好、還沒統計過的資料庫**上，SQLite 給出兩個不同的計畫——第一種寫法掃訂單、第二種寫法掃顧客。沒有統計就不知道哪張表大，於是它照文字的順序走。

跑一次 `ANALYZE` 讓引擎去數過兩張表之後，同樣兩段查詢得到同一個計畫：

```text
SCAN 訂單
BLOOM FILTER ON 顧客 (顧客編號=?)
SEARCH 顧客 USING AUTOMATIC COVERING INDEX (顧客編號=?)
```

兩次都選擇掃二十萬列那張、對五十列那張做查找，寫誰在前面沒有影響。

**這一組對照比「順序無關」更完整地說明了問題**：書寫順序從來不是引擎的依據，它只是引擎在沒有別的資訊時的退路。真正的依據是統計資訊，而那份資訊不在查詢裡、也不在資料裡，它是引擎另外去數出來存著的東西。

還有第二件事：計畫裡有查詢文字完全沒提到的步驟。`AUTOMATIC COVERING INDEX` 是 SQLite 當場替顧客表建的[索引](/sql/knowledge-cards/indexing/)，`BLOOM FILTER` 是它加的過濾步驟。查詢裡沒有一個字要求這些。

「先讀的那張表」這個直覺因此對應不到任何固定的東西——同一段查詢在兩個資料庫狀態下先讀的表不同。文字上的先後只決定語意（見 [1.3](/sql/join-left-operand-accumulates/)），不決定執行。

## 求值順序擋得住寫法

語意模型摸不著，而它會在錯誤訊息上現形：把聚合函數寫進 `WHERE`，SQLite 與 DuckDB 都拒絕，而它們的訊息各自寫出了理由——那一步分組還沒發生，沒有組就沒有組的計數。同一件事移到 `HAVING` 就通過。

**這組錯誤訊息是這個語言少數把內部模型直接講出來的地方。** 它拒絕的理由是這一步拿不到那個值，與寫法好不好看無關。逐步的清單、各家引擎放寬到什麼程度、以及一種不報錯而給出錯答案的形態，在 [1.2 子句的求值順序](/sql/clause-evaluation-order/)。

## 代價的位置

宣告式把「怎麼算」交給引擎，代價也跟著搬到引擎那一側。查詢的文字裡沒有任何東西表示它會掃全表還是走索引、會不會臨時建一個索引、會不會把中間結果寫到磁碟——上面那段計畫證明了這一點，`SCAN`、`BLOOM FILTER` 與那個臨時索引，三者一個都不在查詢裡。

所以驗證分成兩件互相獨立的事。**結果對不對**看輸出，從查詢本身推得出來。**代價可不可以接受**看計畫，非得問引擎不可，而且同一段查詢在不同資料量、不同索引、不同統計資訊底下的答案不一樣。

練習平台驗的是前一件。題目的資料量小到任何寫法都夠快，所以通過與否只反映描述得對不對；後一件在那個環境裡沒有東西可以量。
