寫一個連接的第一個決定是**哪兩列該配在一起**，而 SQL 給了這個決定一個專屬的位置：`ON`。本篇把這件事叫**配對**——關係還在組的那個過程，哪一列跟哪一列湊成一列；這是為了指認它而取的稱呼，SQL 的標準術語裡沒有這個詞。條件寫進那裡，配對關係就成為查詢結構的一部分；條件留在 `WHERE`，配對關係就退化成一道篩子。

本篇的查詢跑在[共用的範例資料庫](/sql/#各篇共用的範例資料庫)上：三位顧客佳穎、宗翰、雅文，而只有佳穎下過兩張訂單（101 與 102，金額 300 與 500）。

這一篇處理的是**起手式**——寫連接時第一個下筆的地方，而它決定了條件之後能放哪裡。[1.5](/sql/on-describes-where-filters/) 處理的是條件寫下之後放哪一邊——那一篇會把配對與**成品**（關係組完之後手上的那一批列）並排；本篇兩個詞都會用到，而成品那一半的完整判定表在那裡。順序上這一篇在前：先有配對關係，才有條件該放哪裡的問題。

## 從全部配對縮小，是把代數的定義逐字抄下來

[關聯代數](/sql/knowledge-cards/relational-algebra/)把連接定義成兩個運算的組合：先取[笛卡兒積](/sql/knowledge-cards/cartesian-product/)，再用條件選取。所以下面這個寫法是把定義翻成 SQL：

```sql
SELECT 顧客.姓名, 訂單.訂單編號
FROM 顧客 CROSS JOIN 訂單
WHERE 訂單.顧客編號 = 顧客.顧客編號;
```

它讀起來自然是有來由的——每一種配對先擺出來，再挑走不要的。而它是**語意層的定義**：代數用它說明連接的結果集是什麼，沒有規定寫法要照這個順序展開。引擎也沒有照著做，這一段的計畫與 `JOIN ... ON` 寫同一個條件逐字相同（[1.19](/sql/declared-intent-vs-behaviour/)）。

這個起手式在內連接底下一直行得通，因為條件放 `ON` 與放 `WHERE` 在內連接底下回同一批列。行得通的經驗會累積，直到問題需要保留配不到的列。

## 兩條路徑在外連接處分開

書店要一份名單：每位顧客與他 300 元以上的訂單，而沒有這種訂單的顧客也要列出來。

從全部配對縮小：

```sql
FROM 顧客 CROSS JOIN 訂單
WHERE 訂單.顧客編號 = 顧客.顧客編號 AND 訂單.金額 >= 300;
-- 佳穎 101 / 佳穎 102
```

宗翰與雅文不在名單上。`CROSS JOIN` 這個關鍵字沒有外連接的形式，所以保護要留下來的話，這個起手式本身就得換掉。

把 `CROSS JOIN` 換成 `LEFT JOIN` 而條件留在原處：

```sql
FROM 顧客 LEFT JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號
WHERE 訂單.金額 >= 300;
-- 佳穎 101 / 佳穎 102
```

兩人仍然不在。`LEFT` 保護下來的那些列右邊全是 `NULL`，而 `WHERE` 那一步把它們篩掉了（[1.5](/sql/on-describes-where-filters/)）。**換掉關鍵字補不回那些列，因為要動的是條件的位置。**

把配對關係整個寫進 `ON`：

```sql
FROM 顧客 LEFT JOIN 訂單
  ON 訂單.顧客編號 = 顧客.顧客編號 AND 訂單.金額 >= 300;
-- 佳穎 101 / 佳穎 102 / 宗翰 （空）/ 雅文 （空）
```

三位顧客都在。**兩條路徑的差別在這裡從「寫法偏好」變成「答得出來與答不出來」**：從全部配對縮小的起手式，把所有條件都推到成品那一側，而外連接的保護正是在成品那一步被抵銷的。

## 配不到的那些列要不要，決定了連接的種類

配對關係說完之後，第二個決定是配不到對象的列怎麼處理。判準是一句話：**這些列在答案裡有沒有位置。**

有位置就用外連接，而哪一側有位置決定寫 `LEFT`、`RIGHT` 還是 `FULL`；沒有位置就用內連接（`JOIN`）（[外連接](/sql/knowledge-cards/outer-join/)那張卡寫三者各保護誰）。「哪些顧客一張單都沒下」這個問題的答案整個在補 `NULL` 的那幾列上，內連接會讓它無從回答。

**這個決定由問題決定，不由現有資料決定。** 「翻遍現在的訂單表，每一列都配得到顧客」只證明此刻如此，而查詢要活得比這一批資料久。反過來說，資料保證配得到的時候寫 `LEFT` 也有代價——它宣告了一個從未發生的情況，下一個讀的人會以為那些列存在（[1.19](/sql/declared-intent-vs-behaviour/)）。要判斷配對有沒有保證，去看[約束](/sql/knowledge-cards/constraint/)，而那條保證要真的生效才算數（[1.17](/sql/foreign-key-and-referential-integrity/)）。

## 從一句業務描述走到查詢

「每位顧客與他 300 元以上的訂單，沒有這種訂單的顧客也要列出來」這句話裡有三個決定，各自對應查詢的一個位置。

**哪兩列該配在一起。** 顧客的那一列與訂單的那一列，靠顧客編號對上，而且只跟 300 元以上的訂單配。這一整句進 `ON`——「只跟 300 元以上的訂單配」描述的是配對，所以它屬於那裡。

**配不到的列要不要。** 「沒有這種訂單的顧客也要列出來」說了要，而要保護的是顧客那一側，所以是 `LEFT JOIN`，左邊放顧客。**兩張表的時候這樣判就夠**；三張以上時「左邊」是前面幾個連接累積出來的結果，鏈中間放一個 `RIGHT` 會把前段保護下來的列整批丟掉。累積的判讀，以及同一組資料上四列變一列的實跑，在 [1.4](/sql/join-left-operand-accumulates/)。

**成品裡再篩什麼。** 這句話沒有再提條件，所以 `WHERE` 是空的。業務描述裡沒有針對顧客那一側的限制時，空的 `WHERE` 是一個合理的結果。

順序反過來走也能檢查已經寫好的查詢：`WHERE` 裡引用右表欄位的條件，回頭問它描述的是配對，還是**成品**（連接組完之後手上的那一批列）——多數形態上它描述的是配對，而它待在那裡正在抵銷某個保護。**有一個形態剛好相反**：`WHERE 右表.某欄 IS NULL` 挑的正是外連接補上 `NULL` 的那些列，它描述的是成品，待在 `WHERE` 是對的位置（[1.5](/sql/on-describes-where-filters/) 有完整的判定表，[1.19](/sql/declared-intent-vs-behaviour/) 用它示範查孤兒訂單）。

## 只提到被保護那一側的條件，`ON` 篩不掉它

上一節的三個決定裡，前兩個都在問條件與連接種類該怎麼配。而條件提到哪一側，會讓第一個決定的答案整個不同。換一對表看得清楚。「每張訂單與它的評價，只要三月五日以後下的單」——被保護的是訂單，而「三月五日以後」只提到訂單。條件寫進 `ON`：

```sql
SELECT 訂單.訂單編號, 訂單.下單日, 評價.星等
FROM 訂單 LEFT JOIN 評價
  ON 評價.訂單編號 = 訂單.訂單編號 AND 訂單.下單日 >= '2026-03-05';
-- 101  2026-03-02  （空）
-- 102  2026-03-09  （空）
```

三月二日那張照樣回來，篩選沒有發生——`LEFT` 的定義是左邊每一列都留著，而 `ON` 只決定右邊配不配得上，配不上就補 `NULL`。**而它在別的地方生效了**：101 本來配得上那筆五星評價，多了這個條件之後整個 `ON` 對它判假，於是連評價一起丟了。同一個條件改放 `WHERE` 才回到要的那批列，只剩 102 一列。

這一類條件描述的是成品，屬於 `WHERE`。判準因此要分兩步：先問這個條件提到哪幾側，只提被保護那一側的直接進 `WHERE`；兩側都提到或只提另一側的，才問它描述配對還是成品。**自連接是同一種形態的變體**——兩次出現裡被保護的那一次，它自己的過濾條件寫進 `ON` 同樣篩不掉列。放右表的條件另有一組判定，以及它為什麼對左表條件恆為真，在 [1.5](/sql/on-describes-where-filters/)。

所以空的 `WHERE` 不是一個要去追求的形狀。上一節那句業務描述留下空的 `WHERE`，是因為它確實沒有再提條件；把一個只提被保護側的條件塞進 `ON` 去換一個空的 `WHERE`，換來的是一個篩不掉列、還會丟掉本來成立的配對的條件。

## 換掉其中一項就走到另一篇

本篇的可動項是：配對關係寫在哪裡、配不到的列要不要、以及配對的兩側是不是同一張表。

**把配對關係從 `ON` 挪到 `WHERE`**：同一個條件放 `ON` 與放 `WHERE` 在內連接底下同值、在外連接底下分岔，而分岔的機制與判定表在 [1.5 ON 描述關係、WHERE 篩選結果](/sql/on-describes-where-filters/)。本篇說先把配對關係放進 `ON`，那一篇說一個已經寫下的條件該歸哪一邊。

**問配不到的那些列該由誰決定**：那是連接種類的選擇，而多個連接串起來的時候「左邊」不再是一張表。[1.4 JOIN 的左邊是累積結果](/sql/join-left-operand-accumulates/) 寫左運算元的累積過程，以及鏈中間的 `RIGHT` 保護的到底是誰。

**把配對的兩側換成同一張表**：配對關係變成同一批資料裡兩列之間的關係，而兩次出現需要各自的名字。[1.7 查詢裡的表是一個具名的出現](/sql/table-occurrence-and-alias/) 用三個引擎的錯誤訊息示範同一張表出現兩次為什麼非取名不可，並把自連接處理的關係分成三種形態。

**只問配不配得到、不把兩列並排**：那時不需要把兩列並排，半連接就夠。[1.8 IN、EXISTS 與 JOIN](/sql/in-exists-join/) 寫三者在列數上的差別與選哪一種的判準。
