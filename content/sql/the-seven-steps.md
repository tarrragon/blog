一段 SQL 查詢從業務的一句話走到上線，中間有七個決定。**本 SQL 分類其餘各篇各自處理其中一步的機制，而這裡只畫路線——哪一步在哪一篇，以及手上這個需求現在需要的是哪一篇。** 底下不解釋任何一個機制、也不寫任何一段查詢。

這七個決定，每一個都可以在不知道它存在的情況下被做掉——因為**不做決定本身就是一個決定**，只是那個答案由預設值給。分類其餘各篇各自處理其中一步的機制，而讀者逐篇讀過去的時候看不出它們是同一條路上的七站——每一篇都在講自己那個機制，沒有一篇說得出它站在哪一步。

## 七步，以及決錯之後看到什麼

| 步驟         | 要決定的                                 | 決錯之後的症狀                                             | 機制在                                                                                                                             |
| ------------ | ---------------------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 一、追問需求 | 這句話真正問的是哪一個資料問題           | 查詢寫對了，而它答的是另一題                               | 不在本分類——答案要去問人                                                                                                           |
| 二、定判準   | 什麼樣的輸出算對                         | 改完查詢不知道有沒有改好                                   | [1.13](/sql/well-formed-is-not-correct/)                                                                                           |
| 三、選寫法   | 要不要用到對方那一列的欄位               | 列數不是預期的，而後面的加總跟著錯                         | [1.8](/sql/in-exists-join/)、[1.7](/sql/table-occurrence-and-alias/)、[1.10](/sql/window-keeps-rows-grouping-collapses/)           |
| 四、補前提   | 這段寫法默默假設了什麼                   | 資料長成某個樣子之後答案就錯，而不報錯                     | [1.6](/sql/join-changes-rows-and-nulls/)、[1.12](/sql/pagination-needs-a-total-order/)                                             |
| 五、量代價   | 這段要跑多久、跑幾次                     | 開發時很快，正式資料上拖垮請求                             | [1.17](/sql/cost-lives-in-the-plan/) 代價由資料與索引決定、[Sargable](/sql/knowledge-cards/sargable/) 條件的形狀決定索引用不用得上 |
| 六、對邊界   | 需求沒說而資料會有的那些                 | 平常都對，特定幾筆資料上靜默算錯                           | [1.11](/sql/relations-have-no-order/)、[1.13](/sql/well-formed-is-not-correct/)                                                    |
| 七、交付     | 換引擎、換資料量、換讀的人之後還成不成立 | 第一級的差異搬家當天就報錯，第三、四級不報錯而清單沒有人留 | [1.19](/sql/engine-leniency-and-portability/) 管換引擎、[1.20](/sql/declared-intent-vs-behaviour/) 管換讀的人                      |

**逐格讀症狀那一欄，共同點是查詢照跑而答案不對。** 這是這條路最需要先知道的一件事。只有兩個位置會當場出聲：第五步的代價由人看得出來（慢），第七步換引擎時有一類差異第一次執行就報錯，那一類也看得出來（[1.19](/sql/engine-leniency-and-portability/) 按「差異在什麼位置發聲」分級，報錯的是最早發聲的那一級；其餘幾級要麼等某一筆資料、要麼不出聲）。其餘的失敗時欄位正常、列數合理，沒有任何東西提示要去檢查。

## 這七步在本分類的章節上怎麼排

分類的機制各篇按**誰決定結果**分成三支（[推導源頭](/sql/#推導源頭)），那個軸問的是「結果由誰定」。七步是另一個軸——它按**做事的先後**排，所以同一章會出現在不同步，而同一步也會用到好幾章。

兩個軸的用法不同：想理解這個語言為什麼長這樣，照三支讀；手上有一個要交出去的需求，照七步走。

三支與七步的對應是這樣（**哪一支有哪幾篇看[分類目錄頁的章節表](/sql/#章節)，本篇不重複那份清單**）：

| 支                          | 它處理什麼                             | 落在哪幾步     |
| --------------------------- | -------------------------------------- | -------------- |
| 第一支 語意的模型           | 結果集由什麼決定                       | 第三、四、六步 |
| 第二支 文字之外還有誰在決定 | 引擎、權限、約束、比較規則各自決定什麼 | 第五、七步     |
| 第三支 文字對讀的人說了什麼 | 下一個讀這段查詢的人會怎麼理解它       | 第七步         |

上面那張七步表只點出每一步最承重的那一兩篇，不是分類的完整篇目。沒被點到的那幾篇，機制散落在好幾步上，所以指不到單一一格。

## 哪幾步最常被跳過

**第一步與第二步。** 它們發生在打開編輯器之前，所以不留下任何痕跡——跳過了的查詢跟沒跳過的長得一模一樣。而跳過第一步的代價是整段查詢答錯題，跳過第二步的代價是後面每一次修改都不知道有沒有改好。

線上的 SQL 練習平台（題目附一組測資、提交之後只比對輸出）把這兩步整個拿掉了：題目已經是精確的資料問題、判準已經由測資給定。**那是把需求分析這一整段移到題目裡，不是把它簡化。** 所以練習平台上的解法，搬到真實需求上少了最前面兩步。

**第六步。** 它要求想出「需求沒說而資料會有」的情形，而那份清單沒有地方可以查——它由這個領域的經驗長出來。跳過它的症狀最溫和：平常都對。

## 走完整條路的實例

[1.22 一句需求走到一段上線的查詢](/sql/requirement-to-shipped-query/) 拿一個真實需求走完這七步：四個追問、三種寫法各自押的前提、兩種漏掉前提的寫法錯在相反的方向、四種形態的代價橫跨三個量級（其中一種加了索引反而變慢），以及需求沒說的四類邊界。

**兩篇的分工**：本篇定義步驟，1.22 在一個需求上把七步走一遍。步驟的定義改本篇，某一題的實跑改 1.22。

## 帶著一個問題進來的話

上面是「要交出一段查詢」的路線。手上如果是一個已經發生的症狀（數字對不上、查詢很慢、換引擎之後結果變了），那是另一個入口——[分類目錄頁的問題落點表](/sql/#帶著問題來的話這張表給落點)按症狀直接指到篇。

兩個入口的差別在讀者站的位置：**要交出一段查詢的人走七步，被一個症狀擋住的人查落點表。**

而還有第三種讀者，這兩個入口都不收：**手上要交的是一份 schema 設計，而不是一段查詢。** 他的問題在這條路線之前——表的形狀決定了往後每一段查詢要付多少，而七步每一步都把那個形狀當成給定的。那一側在 [backend 1.16 設計時下的每一個決定，替往後每一次查詢定價](/backend/01-database/design-decisions-price-every-query/)，六個決定各自替查詢定了什麼價在那裡有實測。
