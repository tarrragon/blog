`ON` 說的是兩邊怎麼配成一個 [relation](/sql/knowledge-cards/relation/)，`WHERE` 說的是從配好的關係裡篩掉什麼。這兩件事落在求值順序的不同步：`FROM` 那一步把關係組出來，`WHERE` 那一步才開始篩。

內連接底下兩者的結果相同，於是它們看起來可以互換。[外連接](/sql/knowledge-cards/outer-join/)底下不同，而不同的地方正好是外連接存在的理由。

## 同一個條件放 ON 與放 WHERE 得到不同的名單

書店想要一份名單：全部顧客都要列出來，而評價欄只顯示五星的那些。條件寫進 `ON`：

```sql
SELECT 顧客.姓名, 評價.星等
FROM 顧客
LEFT JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號
LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號 AND 評價.星等 = 5;
```

回來四列：

```text
佳穎  5
佳穎  NULL
宗翰  NULL
雅文  NULL
```

三個顧客都在。佳穎出現兩次，因為她有兩張訂單——第一張有五星評價，第二張沒有評價可配，補 NULL。

同一個星等條件改放 `WHERE`，其餘不動：

```text
佳穎  5
```

宗翰、雅文與佳穎的第二張訂單全部消失，結果與內連接相同。

## 為什麼外連接底下會分岔

`LEFT JOIN` 的定義是左邊每一列都留著，右邊配不上的補 NULL。條件寫在 `ON` 裡的時候，它參與的是「配不配得上」這個判斷——宗翰沒有訂單所以配不上任何評價，佳穎的第二張訂單配不上五星評價，照定義都補 NULL 留下來。

條件寫在 `WHERE` 裡的時候，關係已經組完了，補上的那些 NULL 也已經在裡面。這時候問「星等等於 5」，那些補 NULL 的列答不出 5，於是被篩掉。**外連接剛剛保護下來的列，`WHERE` 這一步又把它們拿掉了。**

內連接底下看不出差別，是因為它本來就不保留配不上的列。沒有被保護的列可以被抵銷，所以兩種寫法自然同值。

## 條件描述的是配對規則還是成品的篩選規則

問這個條件描述的是**配對規則**還是**成品的篩選規則**。

「只跟五星的評價配」是配對規則，放 `ON`；「最後的名單裡只要五星那幾列」是篩選規則，放 `WHERE`。這兩句話描述的是不同的事，只是內連接讓它們碰巧同值。

這個分法要靠意圖，而讀者手上有時只有條件本身。有一條不必判斷意圖的機械規則可以先跑：**外連接底下，`WHERE` 裡任何一個引用右表欄位的條件都會取消保護，`IS NULL` 與 `IS NOT NULL` 除外。** 要保護就搬進 `ON`。意圖那一層留給決定要不要保護的時候用。

一個常見的意外由此而來：`LEFT JOIN` 寫好之後，在 `WHERE` 加一個右表欄位的條件，外連接就退化成內連接了。寫的人想的通常是「順便篩一下右表」，而實際發生的是保護被取消——上面那組實測就是它，一份要涵蓋全部顧客的名單縮成了一列。

想在保留左表全部列的前提下限制右表配對範圍，條件要放進 `ON`。想真的只留配得上的列，直接寫 `INNER JOIN`，讓意圖顯示在連接型別上而不是藏在 `WHERE` 裡。

## 找沒配到的那些：條件仍然屬於 WHERE

有時候要的正是「沒配到的那些」。書店想知道哪些顧客一張單都沒下過：

```sql
SELECT 顧客.姓名
FROM 顧客 LEFT JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號
WHERE 訂單.訂單編號 IS NULL;
-- 宗翰、雅文
```

這個條件描述的是成品，所以它屬於 `WHERE`。它與上面那個「退化成內連接」的形態看起來很像——同樣是在 `WHERE` 裡引用右表欄位——而要的結果剛好相反：這一個挑的正是外連接補上 NULL 的那些列。

**分辨兩者的仍然是那個問題：這個條件描述的是配對，還是成品。** 「一張單都沒下過」是關於成品的敘述，所以它在 `WHERE` 是對的位置。
