`ON` 說的是兩邊怎麼配成一個 [relation](/sql/knowledge-cards/relation/)，`WHERE` 說的是從配好的關係裡篩掉什麼。這兩件事落在求值順序的不同步：`FROM` 那一步把關係組出來，`WHERE` 那一步才開始篩。

本篇要反覆用到這兩件事的名字。**配對**指關係還在組的那個過程——哪一列跟哪一列湊成一列；**成品**指關係組完之後手上的那份東西——已經湊好、包含補了 NULL 的那些列在內的整批資料。這兩個詞是本篇為了指認這兩個時刻而取的稱呼，SQL 的標準術語裡沒有它們。

內連接底下兩者的結果相同，於是它們看起來可以互換。[外連接](/sql/knowledge-cards/outer-join/)底下不同，而不同的地方正好是外連接存在的理由。

## 同一個條件放 ON 與放 WHERE 得到不同的名單

書店想要一份名單：全部顧客都要列出來，而評價欄只顯示五星的那些。條件寫進 `ON`：

```sql
SELECT 顧客.姓名, 評價.星等
FROM 顧客
LEFT JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號
LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號 AND 評價.星等 = 5;
```

回來四列：

```text
佳穎  5
佳穎  NULL
宗翰  NULL
雅文  NULL
```

三個顧客都在。佳穎出現兩次，因為她有兩張訂單——第一張有五星評價，第二張沒有評價可配，補 NULL。

同一個星等條件改放 `WHERE`，其餘不動：

```text
佳穎  5
```

宗翰、雅文與佳穎的第二張訂單全部消失，結果與內連接相同。

## 為什麼外連接底下會分岔

`LEFT JOIN` 的定義是左邊每一列都留著，右邊配不上的補 NULL。條件寫在 `ON` 裡的時候，它參與的是「配不配得上」這個判斷——宗翰沒有訂單所以配不上任何評價，佳穎的第二張訂單配不上五星評價，照定義都補 NULL 留下來。

條件寫在 `WHERE` 裡的時候，關係已經組完了，補上的那些 NULL 也已經在裡面。這時候問「星等等於 5」，那些補 NULL 的列答不出 5，於是被篩掉。**外連接剛剛保護下來的列，`WHERE` 這一步又把它們拿掉了。**

內連接底下看不出差別，是因為它本來就不保留配不上的列。沒有被保護的列可以被抵銷，所以兩種寫法自然同值。

## 把補了 NULL 的那一列代進條件裡，看它判成什麼

`WHERE` 只留下判成真的列。而條件的答案有三種——真、假、以及**未知**：拿 `NULL` 去跟任何值比較，答案既不是真也不是假（完整的推導在 [1.5](/sql/join-changes-rows-and-nulls/)）。

外連接補上的那些列，右表欄位全是 `NULL`，所以問題變成一句話：**這個條件對「什麼都沒有」這一列給出什麼答案。** 真的留下，假與未知都被丟掉。

| 條件                                 | 對補 NULL 的那一列      | 保護 |
| ------------------------------------ | ----------------------- | ---- |
| `評價.星等 = 5`                      | NULL 比不出來，判成未知 | 取消 |
| `評價.星等 IS NOT NULL`              | 判成假                  | 取消 |
| `評價.星等 IS NULL`                  | 判成真                  | 保住 |
| `評價.星等 IS NULL OR 評價.星等 = 5` | 前半判成真，整串就是真  | 保住 |
| `COALESCE(評價.星等, 0) >= 0`        | NULL 先被換成 0，判成真 | 保住 |

**能不能保住不看用了哪個運算子。** `IS NOT NULL` 看起來與 `IS NULL` 成對而落在相反的一側，正是因為它對空缺判成假；而 `OR` 與 `COALESCE` 這兩種寫法把未知轉成真，保護就留住了。

**這個測試回答的是保護存不存活，不回答條件該放哪一邊。** 歸屬要另外問一句：這個條件描述的是配對，還是成品。「只跟五星的評價配」描述的是配對，屬於 `ON`；「最後的名單裡只要五星那幾列」描述的是成品，屬於 `WHERE`。兩句話說的是不同的事，而內連接讓它們碰巧同值。

多數形態上這兩個問題同向——取消了保護的條件，通常正是因為它在描述成品。`IS NULL` 是兩者分開的那一個形態：它保住了保護，而它要的正好是那些被保護下來的列，所以它同時是「保護存活」與「屬於 `WHERE`」。下一節寫的就是這個形態。

## 找沒配到的那些：條件仍然屬於 WHERE

有時候要的正是「沒配到的那些」。書店想知道哪些顧客一張單都沒下過：

```sql
SELECT 顧客.姓名
FROM 顧客 LEFT JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號
WHERE 訂單.訂單編號 IS NULL;
-- 宗翰、雅文
```

這個條件描述的是成品，所以它屬於 `WHERE`。它與上面那個「退化成內連接」的形態看起來很像——同樣是在 `WHERE` 裡引用右表欄位——而要的結果剛好相反：這一個挑的正是外連接補上 NULL 的那些列。

**分辨兩者的仍然是那個問題：這個條件描述的是配對，還是成品。** 「一張單都沒下過」是關於成品的敘述，所以它在 `WHERE` 是對的位置。

## 往下走

外連接與分組常常在同一個查詢裡一起出錯，而錯的位置不同：`WHERE` 取消了保護是一回事，分組鍵選在右表欄位上又是另一回事——後者的完整推導在 [1.8 分組鍵決定每一組代表什麼](/sql/grouping-key-decides-the-unit/)，它從「沒消費的人不會出現在訂單表」這個業務事實走到 `NOT EXISTS`。

另外兩件事各佔一篇：連接讓一列變成多列、以及那些 `NULL` 為什麼不能用等號比，在 [1.5](/sql/join-changes-rows-and-nulls/)；三張表以上時「左邊」是什麼，在 [1.3](/sql/join-left-operand-accumulates/)。

查詢寫對而次數失控是另一個層次的問題，[backend 模組一的查詢反模式](/backend/01-database/query-anti-patterns/) 把 N+1、延遲載入與長交易列成可診斷的清單，並給出每請求的查詢次數預算。
