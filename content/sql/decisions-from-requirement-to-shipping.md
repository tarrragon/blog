這篇整理一段 SQL 查詢從業務的一句話走到上線之間要做的決定——追問需求、定判準、選寫法、補前提、量代價、對邊界、交付——每一個決定要決定什麼、決錯之後看到什麼症狀，以及它背後的機制在哪一篇展開。範圍從拿到需求的那一刻開始，到查詢交給下一個環境為止。

## 每個決定要決定什麼，決錯之後看到什麼

| -------- | ---------------------------------------- | -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 追問需求 | 這句話真正問的是哪一個資料問題           | 查詢寫對了，而它答的是另一題                                         | 答案要去問提出需求的人                                                                                                                                                                                                     |
| 定判準   | 什麼樣的輸出算對                         | 改完查詢不知道有沒有改好                                             | [1.13 合不合法由引擎驗，答案對不對由提問的人負責](/sql/well-formed-is-not-correct/)                                                                                                                                        |
| 選寫法   | 要不要用到對方那一列的欄位               | 列數不是預期的，而後面的加總跟著錯                                   | [1.8 IN、EXISTS 與 JOIN 描述的是三件不同的事](/sql/in-exists-join/)、[1.7 查詢裡的表是一個具名的出現](/sql/table-occurrence-and-alias/)、[1.10 分組把列收掉，視窗函數把列留著](/sql/window-keeps-rows-grouping-collapses/) |

**決錯之後的症狀有一個共同點：查詢照跑而答案不對。** 只有兩個決定決錯時會當場出聲：量代價決錯時查詢慢得看得出來；交付時換了引擎，有一類差異第一次執行就報錯。[1.19 引擎的寬鬆度沒有總排名，可攜性要逐個寫法決定](/sql/engine-leniency-and-portability/) 把跨引擎的差異按發聲的位置分級，第一次執行就報錯的叫當場報錯，其餘的要麼等某一筆資料才報錯、要麼始終靜默。其餘的失敗時欄位正常、列數合理，沒有任何東西提示要去檢查。

## 哪幾個決定最常被跳過

**追問需求與定判準。** 這兩個決定發生在打開編輯器之前，所以不留下任何痕跡——跳過了的查詢跟沒跳過的長得一模一樣。而跳過追問需求的代價是整段查詢答錯題，跳過定判準的代價是後面每一次修改都不知道有沒有改好。

線上的 SQL 練習平台（題目附一組測資、提交之後只比對輸出）把追問需求與定判準整個拿掉了：題目已經是精確的資料問題、判準已經由測資給定。**那是把需求分析這一整段移到題目裡，不是把它簡化。** 所以練習平台上的解法，搬到真實需求上少了追問需求與定判準。

**對邊界。** 這個決定要求想出「需求沒說而資料會有」的情形，而那份清單沒有地方可以查——它由這個領域的經驗長出來。跳過它的症狀最溫和：平常都對。

## 這些決定都把表的形狀當成給定的

從追問需求到交付，每一個決定都做在一組已經建好的表上：選寫法、補前提的時候，那一組鍵唯不唯一、那一欄允不允許為空已經定了；量代價的時候，長欄位放在哪一張表、常一起取的資料切在幾張表也已經定了。那些形狀是建表時的決定造出來的，而它們替往後每一段查詢定了價——手上要交的是一份 schema 設計而不是一段查詢時，問題落在追問需求之前。六個設計決定各自替查詢定了什麼價，實測在 [backend 1.16 設計時下的每一個決定，替往後每一次查詢定價](/backend/01-database/design-decisions-price-every-query/)。
