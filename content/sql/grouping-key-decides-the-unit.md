`GROUP BY` 把鍵的值相同的列收成一組，所以鍵決定了**一組代表什麼**，而後續的 `HAVING` 與 `SELECT` 全部是對那個對象提問。

選錯鍵的時候查詢照樣跑得動，只是每一組代表的對象與預期的不同。

## 用右表的欄位當鍵，沒配到的列會全部併成一組

書店的三位顧客裡只有佳穎下過單，兩張都是她的。要找出一張單都沒下的顧客，用 `LEFT JOIN` 接起來之後按訂單那一側的顧客編號分組：

```sql
SELECT 訂單.顧客編號 AS 分組鍵, count(*) AS 這組幾列,
       count(訂單.顧客編號) AS 有值幾列, group_concat(顧客.姓名) AS 裝了誰   -- group_concat 把一組裡的名字串起來
FROM 顧客 LEFT JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號
GROUP BY 訂單.顧客編號;
```

MySQL、SQLite 與 DuckDB 的答案一致：

```text
分組鍵  這組幾列  有值幾列  裝了誰
NULL    2         0         宗翰,雅文
1       2         2         佳穎,佳穎
```

**宗翰與雅文被併進同一組。** 他們沒有配到訂單，外連接給他們的 `訂單.顧客編號` 都是 `NULL`，而 `GROUP BY` 把值相同的列收成一組——[NULL](/sql/knowledge-cards/null/) 在這裡與其他值一樣參與分組，所有沒配到的列因此共用同一個鍵。

到這裡條件本身可以是對的。`count(訂單.顧客編號) = 0` 確實選中了那一組，因為 `count(欄位)` 只數有值的列而那一組一列都沒有。**選中的是一組，而那一組裝著兩個人。**

## 輸出非分組欄時，一家給錯答案而不報錯

輸出顧客姓名時，姓名不在分組鍵裡，於是三家引擎在這裡分岔：

```sql
SELECT 顧客.姓名 FROM 顧客
LEFT JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號
GROUP BY 訂單.顧客編號 HAVING count(訂單.顧客編號) = 0;
```

MySQL 8 預設拒絕：

```text
ERROR 1055 (42000): Expression #1 of SELECT list is not in GROUP BY clause and contains
nonaggregated column ... incompatible with sql_mode=only_full_group_by
```

DuckDB 同樣拒絕。SQLite 接受，從那一組裡任意挑一列回傳——只回宗翰，**雅文消失了，而且沒有任何錯誤訊息**。

## 選鍵的判準：一組要代表誰

一組要代表一位顧客，鍵就是顧客的識別欄位：

```sql
SELECT 顧客.姓名 FROM 顧客
LEFT JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號
GROUP BY 顧客.顧客編號, 顧客.姓名
HAVING count(訂單.顧客編號) = 0;
-- 宗翰、雅文
```

現在三家引擎都給出兩列。分組鍵換掉之後，`NULL` 不再是任何一組的鍵——宗翰與雅文各自有不同的顧客編號，所以各自成組，而每一組的訂單計數都是零。

**判斷方法：先說出「我要每一組代表什麼」，鍵就是那個對象的識別欄位。** 說不出來的時候，多半是這一題根本不需要分組。

鍵還要涵蓋一件事：**`SELECT` 裡沒有被聚合的欄位全部要進 `GROUP BY`**。上面補的 `姓名` 就是為此——少了它 MySQL 與 DuckDB 會拒絕（正是上一節那個錯誤）。

**而補進去的欄位必須與鍵一對一，否則分組的粒度會跟著變。** 姓名與顧客編號一對一，補了不影響；換成下單日就不是——把它補進 `GROUP BY`，同一位顧客的每一張訂單各自成組，計數從「這位顧客有幾張單」變成「每張單有幾列」，而引擎不會報錯。

所以非一對一的欄位不能靠補進鍵來輸出，要用聚合包起來（`max(下單日)` 這種），讓它回到「這一組的某個值」而不是「這一組的分法」。

## 先問這一題需不需要分組

上面那一組修正讓查詢回出正確答案，而更前面還有一個問題沒被問：這一題需要分組嗎。

從業務事實推一次。**沒消費過的顧客，在訂單表裡不會有任何一列。** 這句話有一個可以直接驗證的推論——「他的訂單數是零」這件事，從訂單表本身問不出來：

```sql
SELECT 顧客編號, count(*) FROM 訂單 GROUP BY 顧客編號;
-- (1, 2)
```

只有佳穎。宗翰與雅文不在結果裡，因為訂單表沒有他們的列，所以沒有一組可以代表他們，也就沒有計數可以是零。

**那個零是外連接造出來的。** `LEFT JOIN` 替他們各生一列全是 `NULL` 的假訂單，`count(欄位)` 數那一列得到零。所以「計數等於零」是查詢自己製造出來再讀回去的產物，而不是資料本身帶著的性質。

計數預設有東西可以數，而這一題的對象恰好是什麼都沒有的那些人。**這就是分組那條路從一開始就對不上的來源**，比鍵選錯更上一層。

翻成 SQL 最貼字面的形式是存在性判斷：

```sql
SELECT 姓名 FROM 顧客
WHERE NOT EXISTS (SELECT 1 FROM 訂單 WHERE 訂單.顧客編號 = 顧客.顧客編號);
-- 宗翰、雅文
```

一句話對一句話——「找不到對應訂單的顧客」。沒有分組、沒有計數。`LEFT JOIN` 加 `WHERE 訂單編號 IS NULL` 是同一件事的另一種寫法，兩者都對。差別在描述的路徑——`NOT EXISTS` 直接說「找不到」，外連接那一版先讓每位顧客都保留下來、再挑出補了 `NULL` 的那些。[1.4](/sql/on-describes-where-filters/) 從條件該放哪一邊的角度走同一題，兩篇的結論一致。

**`GROUP BY` 是換單位的工具**，用在單看一列答不出來的問題上——「這位顧客下了幾張單」「哪張訂單被評價超過兩次」那一類。判斷仍然是 [1.2](/sql/clause-evaluation-order/) 那一句：這個條件需不需要看到組裡的其他列才能回答。不需要就留在 `WHERE`，連 `GROUP BY` 都不必寫。

三種寫法各自描述什麼、以及 `NOT IN` 為什麼在這裡是危險的那一個，在 [1.7](/sql/in-exists-join/)。

## 往下走

**每一步手上有什麼**：[1.2 子句的求值順序](/sql/clause-evaluation-order/) 走過從 `FROM` 到 `ORDER BY` 每一步的單位變化，並分開語意模型擋得住的限制與各家引擎自己放寬的。

**那些 `NULL` 是誰補的**：[Outer Join（外連接）](/sql/knowledge-cards/outer-join/) 寫三種保護方向，以及連接補上的 `NULL` 與資料裡本來就有的空值來源不同。

**`NULL` 在別的地方的行為**：[1.5 連接產出的是新的關係](/sql/join-changes-rows-and-nulls/) 寫它為什麼不能用等號比、以及 `NOT IN` 碰到一個 `NULL` 就整段失效。分組是少數 `NULL` 表現得像一般值的地方——它會自成一組。
