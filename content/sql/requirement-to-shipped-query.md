這一篇走一個業務需求到一段上線查詢之間的完整路線。需求是「**想知道哪幾天氣溫比前一天高**」，範圍從這句話開始、到查詢交付為止。前面各篇各自處理路線上的一步，這裡把它們用在同一件事上。

這句需求離一段可以執行的查詢還有四個決定，而四個決定的答案都不在資料庫裡，也不在 SQL 裡。

本篇的查詢跑在自己的表上，不用[共用的範例資料庫](/sql/#各篇共用的範例資料庫)——氣溫資料需要缺測與多測站才顯示得出要講的那幾件事。輸出都是實際跑出來的，引擎是 SQLite 3.51.0。

## 一、這句話還不是一個資料問題

四個追問，答案要在寫下任何一段查詢之前拿到，因為每一個的答案都會換掉後面全部的東西：

**這個結果要餵給哪一個決定。** 是要在超過門檻時發告警、是月報上的一張圖、還是模型的一個特徵。答案決定它跑幾次——一次性的查詢、每天排程一次、還是每次有人開頁面就跑一次。而跑的次數決定代價預算，代價預算決定第五節那張表要看哪一欄。

**「前一天」是日曆上的前一天，還是資料上的前一筆。** 這兩個是不同的問題，而**資料完整的時候它們的答案相同**——所以在開發用的乾淨資料上分不出來，要等到缺測發生。

**缺一天的時候要什麼答案。** 三種都合理：跳過（沒有前一天就不算）、視為斷點（明確標示這裡量不到）、或者補值（用前後內插）。三種對應三段不同的查詢。

**一個測站還是幾百個。** 一個的時候整批資料就是一條時間序列；幾百個的時候「前一天」必須限定在同一個測站之內，而漏掉這個限定不會報錯。

這四題的答案**不在資料庫裡，也不在 SQL 裡，要去問人**。而不問的話，每一題都會有一個預設答案被偷偷選走：多數人預設會寫成「資料上的前一筆」、預設跳過缺測、預設只有一個測站。

這一題在 SQL 練習平台上的版本（[LeetCode 197 Rising Temperature](https://leetcode.com/problems/rising-temperature/)）把四題全部關掉了：一張只有一個測站的表、明寫「沒有兩列的 `recordDate` 相同」、資料連續不缺日、只驗答案不驗代價。四題各自對應上面四個追問，逐項關掉之後剩下的就是一道語法題（這件事的一般形態在 [1.0 的〈哪幾步最常被跳過〉](/sql/the-seven-steps/)）。

## 二、追問之後，寫成一句可以驗收的話

四題的答案決定了要寫的是哪一段查詢。本篇往下取這一組：要餵給每天一次的排程報表、「前一天」指日曆上的前一天、缺測的那一天不算、而且有很多個測站。

翻成一句話：

> 對每一個測站，找出所有「同測站、日期剛好早一天」的那筆觀測存在、而且氣溫比它高的那些觀測。

這句話可以驗收，因為給定一組資料就說得出正確答案是哪幾筆。造一組刻意帶缺測的資料：

```sql
-- 各節的表名重複，照順序跑要先清掉上一節的（SQLite 的 DROP 一次只收一張表）
DROP TABLE IF EXISTS 氣溫;
CREATE TABLE 氣溫 (
  紀錄編號 INTEGER PRIMARY KEY,
  測站     TEXT,
  觀測日   TEXT,
  攝氏     INT
);

-- 台北的 3/05 缺測（感測器當天離線），其餘每天一筆
INSERT INTO 氣溫 (測站, 觀測日, 攝氏) VALUES
 ('台北','2026-03-01',18),('台北','2026-03-02',22),('台北','2026-03-03',20),
 ('台北','2026-03-04',15),                          ('台北','2026-03-06',25),
 ('台北','2026-03-07',24),
 ('高雄','2026-03-01',26),('高雄','2026-03-02',25),('高雄','2026-03-03',28),
 ('高雄','2026-03-04',27),('高雄','2026-03-05',29),('高雄','2026-03-06',30),
 ('高雄','2026-03-07',28);
```

照上面那句話逐筆判，正確答案是四筆：

```text
台北  2026-03-02    22 > 18
高雄  2026-03-03    28 > 25
高雄  2026-03-05    29 > 27
高雄  2026-03-06    30 > 29
```

台北的 3/06（25 度）不算——它的前一天是 3/05，而那一天沒有觀測。**這一筆是整組資料的判準**：任何一段回它的查詢，都答錯了上面那句話。

## 三、三種寫法都做得到，而它們押的前提不同

**自連接**把同一張表當成兩次出現，一次扮演「今天」、一次扮演「昨天」（[1.7](/sql/table-occurrence-and-alias/)）：

```sql
SELECT 今.測站, 今.觀測日
FROM 氣溫 今
JOIN 氣溫 昨
  ON 昨.測站 = 今.測站                                  -- 限定在同一個測站之內
 AND 昨.觀測日 = date(今.觀測日, '-1 day')              -- 「前一天」是日曆上的前一天
WHERE 今.攝氏 > 昨.攝氏
ORDER BY 今.測站, 今.觀測日;
```

`date(今.觀測日, '-1 day')` 是 SQLite 的日期運算，把字串日期往前推一天。別名 `今` 與 `昨` 各自標示這一次出現扮演什麼角色——欄位一定要帶前綴，兩次出現共用同一個表名的時候不帶前綴會直接被擋下（`ambiguous column name: 測站`）。

**視窗函數**沿著排好的順序往前取一列（[1.10](/sql/window-keeps-rows-grouping-collapses/)）：

```sql
SELECT 測站, 觀測日 FROM (
  SELECT 測站, 觀測日, 攝氏,
         LAG(攝氏)   OVER w AS 前溫,
         julianday(觀測日) - julianday(LAG(觀測日) OVER w) AS 相隔
  FROM 氣溫
  WINDOW w AS (PARTITION BY 測站 ORDER BY 觀測日)
)
WHERE 攝氏 > 前溫 AND 相隔 = 1
ORDER BY 測站, 觀測日;
```

`WINDOW w AS (...)` 把窗的定義取個名字，讓兩個 `LAG` 共用同一個窗；`julianday()` 把日期換成可以相減的數值，兩筆相差幾天由它算出來。`相隔 = 1` 這個條件是必要的——`LAG` 交出的是**排序後的相鄰一列**，而需求要的是**日曆上的前一天**，兩者只在資料連續時相同。

**相關子查詢**對每一列去問一次「我的前一天是幾度」（[1.8](/sql/in-exists-join/)）：

```sql
SELECT 測站, 觀測日
FROM 氣溫 今
WHERE 攝氏 > (SELECT 攝氏 FROM 氣溫 昨
              WHERE 昨.測站 = 今.測站
                AND 昨.觀測日 = date(今.觀測日, '-1 day'))
ORDER BY 測站, 觀測日;
```

前一天不存在的時候括號裡那一段回零列，純量子查詢因此給出 `NULL`，而拿任何數字跟 `NULL` 比大小的答案是未知，那一列被 `WHERE` 丟掉（[1.6](/sql/join-changes-rows-and-nulls/)）。**台北 3/06 正是靠這個機制被排除的**——排除它的是空值的比較落在第三種答案上，而查詢裡沒有任何一個條件在擋它。

三段都回同一批四列：

```text
台北  2026-03-02
高雄  2026-03-03
高雄  2026-03-05
高雄  2026-03-06
```

三者押的前提不同。自連接押「同一個日期在同一個測站上只有一筆」——有兩筆的時候一列會配到多列，結果多出來（[1.6](/sql/join-changes-rows-and-nulls/)）。視窗函數押「排序鍵在每個分區裡分得出唯一的次序」——並列的時候「前一列」是哪一列沒有定義（[1.12](/sql/pagination-needs-a-total-order/)）。相關子查詢押「括號裡那一段最多回一列」——而**回多列的時候兩家引擎的反應相反**：PostgreSQL 18.6 報 `more than one row returned by a subquery used as an expression`，SQLite 3.51.0 靜默取其中一列往下算。這一條落在 [1.19](/sql/engine-leniency-and-portability/) 的引擎差異上。

**三個前提說的是同一件事**：`(測站, 觀測日)` 這一組唯不唯一。那是 schema 上的一條約束，而三段查詢沒有一段查得到它有沒有成立——[外鍵與約束要去系統目錄查](/sql/foreign-key-and-referential-integrity/)，設計側的完整推導在 [backend 1.16 設計時下的每一個決定](/backend/01-database/design-decisions-price-every-query/)。

## 四、漏掉前提的兩種寫法，錯在相反的方向

上面那個 `相隔 = 1` 與 `PARTITION BY 測站`，漏掉任何一個查詢都照跑。

**漏掉相隔天數**的版本：

```sql
SELECT 測站, 觀測日 FROM (
  SELECT 測站, 觀測日, 攝氏,
         LAG(攝氏) OVER (PARTITION BY 測站 ORDER BY 觀測日) AS 前溫
  FROM 氣溫
) WHERE 攝氏 > 前溫;
```

```text
台北  2026-03-02
台北  2026-03-06      ← 多出來的
高雄  2026-03-03
高雄  2026-03-05
高雄  2026-03-06
```

五筆。台北 3/06 拿 3/04 當「前一天」比，25 大於 15，於是被選中——**它跨過了缺測的那一天，而缺測在結果裡沒有留下任何痕跡**。

**漏掉分區**的版本（距離條件還在）：

```sql
SELECT 測站, 觀測日 FROM (
  SELECT 測站, 觀測日, 攝氏,
         LAG(攝氏)   OVER (ORDER BY 觀測日) AS 前溫,
         julianday(觀測日) - julianday(LAG(觀測日) OVER (ORDER BY 觀測日)) AS 相隔
  FROM 氣溫
) WHERE 攝氏 > 前溫 AND 相隔 = 1;
```

```text
高雄  2026-03-05
```

一筆。少了三筆。沒有分區的時候排序把兩個測站的列交錯在一起，於是多數列的「前一列」是另一個測站同一天的觀測，相隔天數是零，被 `相隔 = 1` 擋掉。

| 版本                | 回幾筆 | 方向 |
| ------------------- | ------ | ---- |
| 三種正解            | 4      | —    |
| 漏掉相隔天數        | 5      | 多報 |
| 漏掉 `PARTITION BY` | 1      | 少報 |

**兩個錯版的方向相反，而它們都不報錯、輸出的欄位也完全正常。** 少報那一個尤其危險——多報的還有機會被人發現數字怪，少報的看起來只是「那幾天沒有升溫」。

分辨它們要靠一筆刻意造的資料，也就是第二節那個「台北 3/06 不該出現」的判準。**那個判準要在寫查詢之前就決定好**，寫完再回頭挑資料的人，會挑到讓自己通過的那一組。

## 五、代價：同一組資料，四種形態差三個量級

前面四段都對，而「哪個比較快」要向引擎問（[1.17](/sql/cost-lives-in-the-plan/)）。把資料放大到二十個測站、兩年、每隔九十七天缺一天，共 14460 列：

```sql
-- 各節的表名重複，照順序跑要先清掉上一節的（SQLite 的 DROP 一次只收一張表）
DROP TABLE IF EXISTS 氣溫;
CREATE TABLE 氣溫 (紀錄編號 INTEGER PRIMARY KEY, 測站 TEXT, 觀測日 TEXT, 攝氏 INT);

-- d 產生 0 到 729 的天數位移，s 產生 1 到 20 的測站編號
-- (i+j) % 97 <> 0 這個條件讓每個測站隔一段時間缺一天
WITH RECURSIVE d(i) AS (SELECT 0 UNION ALL SELECT i+1 FROM d WHERE i < 729),
               s(j) AS (SELECT 1 UNION ALL SELECT j+1 FROM s WHERE j < 20)
INSERT INTO 氣溫 (測站, 觀測日, 攝氏)
SELECT '站'||j, date('2024-01-01', i||' day'), 10 + (i*7+j*13) % 25
FROM s, d WHERE (i+j) % 97 <> 0;
```

自連接分兩種寫法量。兩者的演算法相同，差別只在「前一天」那個條件寫成什麼形狀：

```sql
-- 以下是同一段自連接的 ON 子句，兩種寫法只差這一行，其餘逐字相同。
-- 這個區塊是片段，不能單獨執行——完整的查詢在第三節。

-- A1：等號兩邊的欄位都包進函式，算日期差
ON 昨.測站 = 今.測站 AND julianday(今.觀測日) - julianday(昨.觀測日) = 1

-- A2：等值比較，函式只作用在「今」那一側，「昨」那一側是索引上找得到的值
ON 昨.測站 = 今.測站 AND 昨.觀測日 = date(今.觀測日, '-1 day')
```

四種形態各跑三次取最小值，計時在行程內。下一段對 A1 另外做了一輪七次的重複性量測，用來確認那個反直覺的結果不是離群值：

| 寫法                | 沒有索引 | 有 `(測站, 觀測日)` 索引 | 答案  |
| ------------------- | -------- | ------------------------ | ----- |
| A1 自連接（日期差） | 739 ms   | **1045 ms**              | 10297 |
| A2 自連接（等值）   | 10 ms    | 6 ms                     | 10297 |
| B 視窗函數          | 13 ms    | 12 ms                    | 10297 |
| C 相關子查詢        | 3971 ms  | 8 ms                     | 10297 |

四段查詢的答案完全相同，而時間橫跨三個量級。三件事值得逐個看。

**A1 與 A2 的差別只在條件的形狀，而它是七十倍。** 同一個自連接、同一個演算法，把 `julianday(今) - julianday(昨) = 1` 換成 `昨.觀測日 = date(今.觀測日, '-1 day')` 就從 739 毫秒掉到 10 毫秒。原因是 A1 把兩張表的欄位都包進函式裡，引擎沒有辦法拿索引上的值去比；A2 的函式只作用在外層那一側，內層要找的是一個算好的值（[Sargable](/sql/knowledge-cards/sargable/)）。**上面那道練習題的官方參考解法用的正是 A1 那個形狀**（`DATEDIFF(w1.recordDate, w2.recordDate) = 1`），因為在幾十列的資料上兩者都是零毫秒。

**A1 加了索引之後變慢。** 739 毫秒變成 1045 毫秒。這一條反直覺，所以單獨對 A1 再跑一輪七次量測確認：兩段的範圍不重疊（735–780 對上 955–1252），不是離群值。計畫說明了原因：

```text
沒有索引    SCAN 今
            SEARCH 昨 USING AUTOMATIC COVERING INDEX (測站=?)

有索引      SCAN 今
            SEARCH 昨 USING INDEX ix_站日 (測站=?)
```

沒有索引的時候 SQLite 當場替這段查詢建了一個**覆蓋**索引，內層要的欄位全部在索引裡。有了 `ix_站日` 之後它改用那一個，而那個索引只含 `(測站, 觀測日)`、不含 `攝氏`，於是每一列內層都要多回表一次取攝氏。**手動建的那個索引比引擎當場建的差，所以加了之後變慢**——這件事沒有辦法從查詢的文字推出來，只能問計畫。

**C 的排名從最後一名跳到第一名。** 沒有索引時 3971 毫秒，有索引時 8 毫秒，差了五百倍。計畫上是 `CORRELATED SCALAR SUBQUERY` 底下的 `SCAN 昨` 變成 `SEARCH 昨 USING INDEX`——子查詢逐列執行這個結構沒有變，變的是每一次的單價。**所以「相關子查詢慢」這個說法要加一個條件**：它慢在那個逐列查找沒有索引可用的時候。

**B 對索引幾乎無感**（13 對 12 毫秒），而計畫上有變化——`USE TEMP B-TREE FOR ORDER BY` 消失了，因為索引本身就提供了 `PARTITION BY 測站 ORDER BY 觀測日` 要的順序。省下的排序成本在這個資料量上還看不出來。

回到第一節那個追問：**這個結果要餵給哪一個決定**。每天排程跑一次的報表，四種形態都可以接受，那就挑最好讀的；每次開頁面就跑一次的話，A1 那一欄的數字會直接變成使用者等待的時間。

## 六、需求沒說，而資料會有的那些

第二節那句可驗收的話管住了缺測。下面這幾件需求同樣沒說，而資料遲早會有。

**同一個測站、同一天有兩筆。** 感測器重送、補登、或者換了設備之後兩套系統各寫一筆。自連接的一列會配到多列，結果多出來；視窗函數的「前一列」在並列之間沒有定義，同一段查詢可以給出不同答案；相關子查詢在 PostgreSQL 上報錯、在 SQLite 上靜默取其中一列。**三種寫法對同一件事的反應完全不同，而在本篇用的 SQLite 上沒有一種會出聲**——會出聲的那一種要換到 PostgreSQL 才看得到。 要決定的是哪一筆算數（最後寫入的、還是某個來源優先），而這個決定屬於 schema——一條 `UNIQUE (測站, 觀測日)` 約束把它前移到寫入的那一刻。

**時區。** `觀測日` 存的是哪個時區的日期。跨時區的測站各自用當地日期的話，「前一天」在資料上是對的而在比較上不可跨站；統一存 UTC 日期的話，當地的「一天」會被切開。這件事在單一時區的開發環境裡量不出來。

**補登的資料改變歷史答案。** 台北 3/05 的觀測三個月後補進來了。同一段查詢在同一段日期上，昨天回四筆、今天回五筆——**而且是對的**。報表若把結果存下來，存的那一份與重跑的那一份會不同。要決定的是這份報表回答的是「現在資料庫怎麼說」還是「當時我們知道什麼」，兩種要的儲存方式不同。

**測站搬家。** 同一個 `測站` 值在某一天之後指的是另一個地點。`PARTITION BY 測站` 會把搬家前後接成同一條序列，而那一天的「比前一天高」比的是兩個地方。這一類問題不在查詢裡，在**識別碼的語意有沒有隨時間改變**。

四件事有一個共同點：**它們都讓查詢繼續回出形狀正確的列**。沒有一件會讓程式停下來（[1.13](/sql/well-formed-is-not-correct/)）。

## 七、這一段上線之後會壞在哪

寫完不等於交付完。三件事要在上線之前決定好：

**答案變了要不要有人知道。** 第六節的補登會讓同一段日期的答案改變。要不要偵測，取決於第一節那個「餵給哪一個決定」——告警要知道，月報的圖不必。

**資料量長大之後排名會重排。** 第五節那張表是 14460 列上的結果。列數再大一個量級，A1 與 C 的數字會變，而 A2 與 B 未必。判斷要重問一次計畫，而且**要在改動索引之後再問一次**——A1 那一格已經示範過加索引可以讓事情更糟。

**換一家引擎，這四段裡有兩段要改寫。** `julianday()` 與 `date(x, '-1 day')` 是 SQLite 的日期函式，PostgreSQL 寫成 `觀測日 - INTERVAL '1 day'`、MySQL 寫成 `DATE_SUB(觀測日, INTERVAL 1 DAY)`；`WINDOW w AS (...)` 這個具名窗各家支援程度不同。這一層的差異第一次執行就會報錯，屬於最省事的那一級——而同一段查詢還有不報錯的差異，分級在 [1.19](/sql/engine-leniency-and-portability/)。

## 這條路線的下一段在哪裡

走完七步之後，這一題就交出去了。而同一條路線上還有三個往外的接點，各自接在不同的步驟上。

第三步與第四步的接點在**設計那一側**。三種寫法押的同一個前提是 `(測站, 觀測日)` 唯不唯一，而那不是查詢能決定的事——它是建表時的一個決定。同樣的決定還有五個（可空性、表有多寬、常一起取的資料切在幾張表、字串的比較規則寫在哪一層、外鍵生不生效），每一個都在替往後每一次查詢定價，逐條實測在 [backend 1.16 設計時下的每一個決定，替往後每一次查詢定價](/backend/01-database/design-decisions-price-every-query/)。

第五步的接點在**工具那一側**。本篇讀的計畫只有三四行，真實系統的計畫有巢狀節點與估計列數，而且要分得出「估計錯了」與「真的很慢」。[PostgreSQL Query Optimization](/backend/01-database/vendors/postgresql/query-optimization/) 給 `EXPLAIN` / `EXPLAIN ANALYZE` / `auto_explain` 三層工具的分工，以及統計過時讓計畫選錯的實際案例。

第一步的接點在**預算那一側**。第一步問這份結果餵給哪一個下游用途，而那個答案決定它跑幾次；一個請求裡跑幾段查詢則有另一套預算，兩者相乘才是真正的代價。[backend 1.13 應用層查詢反模式與 Query 預算](/backend/01-database/query-anti-patterns/) 處理後面那一半。

換一個題目的話，七步照走，而第一節那四個追問與第六節那四類邊界的答案會全部不同——那正是為什麼它們是追問而不是清單。
