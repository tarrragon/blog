`FROM` 子句由上往下把表併進來，每一個 `JOIN` 的左運算元是它上面全部合起來的結果。第一個 `JOIN` 的左邊剛好是一張表，從第二個開始就不是了。

左運算元會累積這件事決定三件事：每個 `ON` 引用得到哪些欄位、每個 `LEFT` [保護](/sql/knowledge-cards/outer-join/)的是哪些列、以及在鏈中間換成 `RIGHT` 會發生什麼。

累積這件事在只有一個 `JOIN` 的查詢裡不現形，從第二個開始才有分量：某個 `LEFT` 保護了哪些列，取決於它上面累積出來的是什麼。

## 左運算元隨著往下走而變大

書店的顧客有三位——佳穎下過兩張單，宗翰與雅文一張都沒有，而兩張單裡只有一張被評價過。要一份完整名單：每位顧客連同他的訂單與那張訂單的評價，沒下單的顧客與沒被評價的訂單也要出現。三張表往下接：

```sql
SELECT 顧客.姓名, 訂單.訂單編號, 評價.星等
FROM 顧客
LEFT JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號
LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號;
```

回來四列：

```text
佳穎  101   5
佳穎  102   NULL
宗翰  NULL  NULL
雅文  NULL  NULL
```

第二個 `LEFT JOIN` 的左邊是顧客與訂單併出來的結果，包含宗翰與雅文那兩列補 NULL 的訂單欄。問它「左邊是哪一張表」得不到答案，因為左邊已經不是一張表。**判讀的作法回到查詢的文字：在要判讀的那個 `JOIN` 所在的那一行上方畫一條橫線，橫線以上寫到的表合起來是左運算元，那一行自己掛的那張表是右運算元。**

由此得到兩個可以直接用的結論。第二個 `ON` 寫得出顧客表的欄位，因為顧客在左運算元裡面。第二個 `JOIN` 若換成 `INNER`，砍掉的是線以上那四列裡配不到評價的三列，而不只是「沒有評價的訂單」——宗翰與雅文會一起消失，儘管他們與評價這張表毫無關係。

## 鏈中間的 RIGHT 保護的是那一張單表

把最後一個 `LEFT` 換成 `RIGHT`，其餘一個字不動：

```sql
FROM 顧客
LEFT  JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號
RIGHT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號
```

結果從四列變成一列，只剩 `佳穎 101 5`。

`RIGHT` 保護的是右運算元，而右運算元是評價這一張表。左運算元——顧客與訂單累積出來的那四列——整批降級成可選的，配不上評價的就丟掉。宗翰、雅文、以及佳穎那張沒被評價的訂單，全部消失。

**語意上這等於宣告「每一則評價都要留著，而顧客與訂單可有可無」。** 書店大概不會想問這個問題。它幾乎不會是任何人在寫第三個 `JOIN` 時想表達的事，而它讀起來只像是把 `LEFT` 打成了 `RIGHT`。

## 全部寫成 LEFT，鏈的方向就一致

不用 `RIGHT` 的話，鏈裡每個 `JOIN` 都是同一個方向：要保護的那張表寫在最上面，往下一行一行掛可選的表。要判斷查詢裡任何一個 `JOIN` 保護了什麼，在它那一行上方畫橫線就夠了。

真正需要保護的表放到 `FROM` 之後、寫成鏈最上面那一張就好。

**兩張表都需要保護的時候這個做法不適用**，那時要的是 `FULL JOIN`——它兩側都保護，配不上的兩邊各補一次 `NULL`。鏈裡出現它，「最上面那張表受保護」這個規律就不成立了，判讀要回到逐個連接看保護的方向。要「每一則評價都在、順便看得到它屬於誰」，就從評價開始往下掛訂單與顧客——同樣的列集合，而鏈的方向沒有中途反轉。

## 左右決定保護誰，執行順序決定誰先被掃

左右是書寫位置決定的語意，與引擎實際先處理誰無關。同一個連接寫成 `FROM 訂單 JOIN 顧客` 與 `FROM 顧客 JOIN 訂單`，在跑過 `ANALYZE` 的資料庫上，SQLite 兩次給出完全相同的 [query plan](/sql/knowledge-cards/query-plan/)——它掃二十萬列的訂單、對五十列的顧客做查找，與誰寫在前面無關（沒有統計時它會改照文字順序走，見 [1.1](/sql/declarative-not-procedural/)）。

**左右決定哪一側的列被保護，執行順序決定誰先被掃，兩者互不相干。** 混用這兩個直覺會讓人以為調換書寫順序可以調效能，或以為從查詢文字看得出引擎的動作。

## 換掉其中一項就走到另一篇

本篇繞著保護走，而保護的方向、橫線畫在哪一行、以及它建立之後誰去動它，可以各自換。

**保護建立之後，讓 `WHERE` 去動它**：本篇算出來的那四列會在下一個子句被篩掉三列，而條件改放 `ON` 就不會。[1.5 ON 描述關係、WHERE 篩選結果](/sql/on-describes-where-filters/) 寫這個抵銷怎麼發生，以及為什麼同樣兩種寫法在內連接底下看不出差別。同一組書店資料。

**把補進來的 `NULL` 當成資料看**：它們是連接的產物而不是資料裡本來的空值，而後續的計數與比較分不出這件事。[Outer Join（外連接）](/sql/knowledge-cards/outer-join/) 定義三種保護方向與這些 `NULL` 的來源；[1.6 連接產出的是新的關係](/sql/join-changes-rows-and-nulls/) 寫它們怎麼讓聚合算錯、以及為什麼不能用等號比。

**把「左右」換成「誰先被掃」**：兩者互不相干，而混在一起就會以為調換書寫順序可以調效能。[1.1 宣告式的紅利與代價](/sql/declarative-not-procedural/) 用有無統計資訊的兩個計畫證明引擎照文字順序走只是它沒有別的資訊時的退路。
