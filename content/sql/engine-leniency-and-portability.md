SQL 標準留下許多沒有規定的地方，而每一家[引擎](/sql/knowledge-cards/database-engine/)都得替那些地方做一個決定。**寬鬆度指的是引擎在一段文字不合標準、或標準沒有規定的時候，選擇收下它並自己補上那個決定**——收不收、以及補什麼，各家不同。

本篇是第二支的收尾（[章節](/sql/#章節)）。同一支的其餘各篇各處理一方：識別字規則決定名字指向誰、collation 決定字串怎麼比、權限決定誰能送出這段 SQL、約束決定資料能長成什麼樣、最佳化器決定要花多久。這一方與它們的關係不同——**它決定的是前面那幾方各自的線畫在哪裡**，所以它的實例散在整個分類裡，而本篇把它們並置起來。

本篇的量測跑在四家引擎上：SQLite 3.51、DuckDB v0.10.3、PostgreSQL 18、MySQL 8.4。兩張表，兩列資料：顧客有 `Anna` 與 `anna`，訂單有金額 700 與一列金額為空的。

## 同一組寫法，四家的分組每一條都不同

```text
                              SQLite        DuckDB      PostgreSQL   MySQL
A 非分組欄放進 SELECT           接受          拒絕        拒絕         拒絕
B SELECT 別名用在 WHERE         接受          接受        拒絕         拒絕
C 同一張表出現兩次沒取別名       引用欄位才拒絕  FROM 就拒絕  FROM 就拒絕   FROM 就拒絕
D WHERE 姓名 = 'anna'          回 1 列       回 1 列     回 1 列      回 2 列
E ORDER BY 金額（一列為空）      空的排最前     空的排最後   空的排最後    空的排最前
```

**五條行為分出五種不同的組合。** A 只有 SQLite 收；B 是 SQLite 與 DuckDB 一組；C 四家都拒絕而 SQLite 拒絕的時機不同；D 只有 MySQL 給另一個答案；E 把四家切成兩邊，而那兩邊與前面幾條的切法都不重疊。

**同一家引擎也可以坐在同一列的兩邊。** A 那一列在 MySQL 上是拒絕，而把 `sql_mode` 清空之後同一段查詢回 `1 101`——寬鬆度是「哪一家加上哪一組設定」，不是「哪一家」。SQLite 收下的時候做的是同一件事：三列一組的資料上，它回的是其中一列的 `101` 與 `300`，而哪一列由執行方式決定、文字裡沒有說。

所以「哪一家最寬鬆」這個問題沒有答案，而**帶著一個排名去做決定會錯在具體的位置**：以為 SQLite 最寬鬆而 PostgreSQL 最嚴，就會預期從 SQLite 搬到 PostgreSQL 只會遇到「本來能跑的變成報錯」；D 與 E 那兩列說的是另一回事——那裡沒有任何一家報錯，而答案不同。

各條的完整推導住在它們自己的篇裡：A 在 [1.2](/sql/clause-evaluation-order/) 與 [1.9](/sql/grouping-key-decides-the-unit/)（SQLite 收下之後自己從那一組挑一列的值），B 在 [1.11](/sql/order-by-and-pagination/)（`WHERE` 那一步發生在算出別名之前），C 在 [1.7](/sql/table-occurrence-and-alias/)，D 在 [1.14](/sql/string-comparison-and-collation/)，E 在 [1.11](/sql/order-by-and-pagination/)。

## 差異被發現的成本分四級

上面那張表的五列落在不同的級數上，而級數決定的是**要花多少工夫才會知道有這件事**。

**第一級：剖析或名稱解析就擋下來。** A 與 B 從寬鬆的那一家搬到嚴格的那一家時屬於這一級——第一次跑就報錯，訊息指名了那個欄位。這一級的差異最省事：它自己會現身，而且現身得早。

**第二級：執行到某一筆資料才擋下來。** [約束](/sql/knowledge-cards/constraint/)是這一級的主場——搬過去之後查詢照跑，直到第一筆違反它的資料寫進來。所以這一級的現身時機由資料決定，而測試資料多半不含觸發它的那一筆。

**第三級：照樣跑而答案不同。** D 與 E 在這裡。四家沒有一家報錯，回來的都是形狀正確的列，而列不一樣。要發現它得**把同一段查詢在兩家上各跑一次、比對輸出**——這個動作不會自己發生，因為沒有任何訊號要求它發生。

**第四級：照樣跑而某個保證消失了。** [1.17](/sql/foreign-key-and-referential-integrity/) 記的那幾種屬於這一級：同一段 `REFERENCES` 在一家建得出約束、在另一家被靜默丟掉，而建表語句成功、查詢也成功。第三級至少在輸出上留下差異，這一級連差異都不在輸出裡——它在系統目錄裡，要主動去查才看得到。

**級數與嚴重性沒有對應關係，它對應的是偵測成本。** 第一級的差異可能改起來很麻煩（整批查詢要重寫），而第四級的差異可能只要加一行設定。分開它們的用處在於決定要為它做什麼：第一級不必準備，它自己會現身；第四級要在搬家之前就列進待查清單，因為之後沒有任何時刻它會自己浮現。

## 可攜性是查詢加上一組宣告的性質

一段 SQL 單獨拿出來問「它可不可攜」是答不出來的。上面 D 那一列在四家上有兩種答案，而把比較規則寫進欄位宣告之後，四家的答案就統一了（[1.14](/sql/string-comparison-and-collation/) 的「把規則寫出來」一節）。E 那一列同理——`ORDER BY 金額 NULLS LAST` 或 `ORDER BY (金額 IS NULL), 金額` 把引擎自己補的決定收回到文字裡。

所以可攜性的操作對象多半是**那些原本讓引擎代為決定的位置**，而不是查詢本身。判斷標準是一句話：**這段文字裡有沒有一個決定是它沒說、而由收下它的那一方補上的。** 有，那個位置就是可攜性的斷點，不論它現在跑得多正常。

這一條也解釋了為什麼可攜性測不出來——在單一引擎上跑一萬次，那個由引擎補上的決定每一次都一樣。它是查詢與這一家引擎之間的性質，不是查詢的性質。

## 要維持在哪一級，是一個有成本的選擇

「一律照最嚴格的標準寫」聽起來是安全的預設，而它有價錢：每一個原本可以讓引擎決定的位置都要自己寫出來，查詢變長，寫的人要知道每一條預設是什麼。這筆錢值不值得花，看的是可攜性在這個系統裡承擔什麼。

**不追求可攜的時候**，寬鬆度是引擎給的便利，用它沒有問題。代價落在換引擎的那一天，而那一天的工作量由第三級與第四級的差異數量決定——第一級的那些會自己冒出來。這個選擇的風險不在「會不會換引擎」，在**換的時候有沒有辦法知道要查哪些位置**。

**只求「搬過去會報錯」的時候**，要避開的是第三級與第四級的形態，第一級可以留著。這條路的性價比通常最好：把引擎自己補的決定寫出來（collation、空值的位置、識別字的引號），而非分組欄、別名這一類就算不改，搬家時也會當場現身。

**求答案完全一致的時候**，除了寫出那些決定，還要有一份跨引擎的對照——同一批查詢在目標引擎上各跑一次，比對輸出。這一步無法由閱讀代替，理由與[稽核查詢](/sql/declared-intent-vs-behaviour/)那一層相同：宣稱的真值住在文字之外。

**用一層抽象把 SQL 包起來的時候**（查詢建構器、物件關聯對映），問題換成了另一個問題而不是消失——那一層自己要對每一家引擎做同樣的決定，而它做了哪些決定通常沒有寫在讀得到的地方。判斷這條路划不划算，看的是那一層有沒有把它的引擎差異處理攤開來讓人查。

## 重新評估的訊號

這個選擇不是一次做完的。**目標引擎清單變長的時候要重新算一次**——維持一致的成本隨引擎數量成長，而不是隨查詢數量成長。**引擎升級或設定變動的時候要重新算一次**：上面 A 那一列在 MySQL 上由 `sql_mode` 決定，而那個變數可以在連線層設定——同一個資料庫、同一段查詢，換一個連線設定就換一邊。這一類的差異不在查詢裡也不在 schema 裡，所以它不在任何一份程式碼審查的射程內。**測試環境與正式環境用不同引擎的時候**，第三級與第四級的差異會在正式環境第一次浮現，而那時它們看起來像資料問題。

## 換掉其中一項就走到另一篇

本篇建立的模型裡有幾件事可以各自換掉：差異落在哪一級、決定由誰補上，以及可攜性維持在什麼標準。

**把「這一家收不收」換成「收下之後名字指到誰」**：識別字的摺疊規則是寬鬆度的一個具體實例，而它的形態特別隱蔽——在不區分大小寫的引擎上開發，混用引號的地方一路正常。[1.13 識別字送進引擎之後會被改寫](/sql/identifier-rules/) 寫各家的摺疊規則，以及兩種一致做法之間的中間地帶。

**把「收不收」換成「收下之後怎麼比」**：D 那一列的完整推導，包含索引與條件的比較規則要對得上這件事，在 [1.14 字串的相等與大小由 collation 決定](/sql/string-comparison-and-collation/)。

**把「引擎補上的決定」換成「引擎不補的決定」**：查詢問對了沒有，是沒有任何一家引擎會代為決定的那一層，而它與寬鬆度無關——換引擎、加約束、跑靜態分析都碰不到它。[1.12 合不合法由引擎驗，答案對不對由提問的人負責](/sql/well-formed-is-not-correct/) 寫那一層的判準為什麼只能來自查詢之外。

**把「跨引擎的一致」換成「跨時間的一致」**：一段文字說了什麼給下一個讀它的人，與它在另一家引擎上做什麼，是兩個不同的可攜性。[1.19 關鍵字宣告意圖，引擎只執行行為](/sql/declared-intent-vs-behaviour/) 處理文字對下一個讀它的人說了什麼那一半。

**把引擎差異放回一次實際的遷移裡**：本篇處理的是語言這一側，而遷移還有雙寫、回填、切流與回滾。[資料庫轉換實作](/backend/01-database/database-migration-playbook/) 給那條路徑的完整順序與每一步要留下的證明。
