SQL 標準留下許多沒有規定的地方，而每一家[引擎](/sql/knowledge-cards/database-engine/)都得替那些地方做一個決定。**寬鬆度指的是引擎在一段文字不合標準、或標準沒有規定的時候，選擇收下它並自己補上那個決定**——收不收、以及補什麼，各家不同。

本篇是第二支的收尾（[章節](/sql/#章節)）。同一支的其餘各篇各處理一方：識別字規則決定名字指向誰、collation 決定字串怎麼比、權限決定誰能送出這段 SQL、約束決定資料能長成什麼樣、最佳化器決定要花多久。寬鬆度與那五方的關係不同——**它決定的是那五方各自的線畫在哪裡**，所以它的實例散在整個分類的各篇裡，而本篇把那些實例並置起來。

本篇前半是形態學——各家的分割長什麼樣、差異在什麼位置發聲；後半是決策——維持到哪一級、什麼時候要重算。**兩者的關係是前半決定後半的輸入**：不知道差異落在哪一級，就算不出維持到哪一級要付多少。

本篇的量測跑在四家引擎上：SQLite 3.51、DuckDB v0.10.3、PostgreSQL 18、MySQL 8.4。兩張表，兩列資料：顧客有 `Anna` 與 `anna`，訂單有金額 700 與一列金額為空的。

## 同一組寫法，沒有一條分割能預測下一條

五條寫法擺在四家上，每一條把四家切成兩邊，而切法彼此對不上：

```text
                              SQLite        DuckDB      PostgreSQL   MySQL
A GROUP BY 之外的欄位進 SELECT   接受          拒絕        拒絕         拒絕
B SELECT 別名用在 WHERE         接受          接受        拒絕         拒絕
C 同一張表出現兩次沒取別名       引用該欄位才拒  FROM 就拒絕  FROM 就拒絕   FROM 就拒絕
D WHERE 姓名 = 'anna'          回 1 列       回 1 列     回 1 列      回 2 列
E ORDER BY 金額（一列為空）      空的排最前     空的排最後   空的排最後    空的排最前
```

**沒有一條分割能預測下一條。** A 只有 SQLite 收；B 換成 SQLite 與 DuckDB 一組；D 只有 MySQL 給另一個答案；E 又切成 SQLite 加 MySQL 對上另外兩家。C 的分割與 A 相同（都是 SQLite 對上其餘三家），這一點不減損上面那句——**同一組引擎可以在兩條行為上一起站在同一邊，而那不預測第三條**。

**同一家引擎也可以坐在同一列的兩邊。** A 那一列在 MySQL 上是拒絕，而把 `sql_mode` 清空之後同一段查詢回 `1 101`——寬鬆度是「哪一家加上哪一組設定」，不是「哪一家」。SQLite 那一側收下的時候也在補一個決定，只是補得更隱蔽：一組裡有幾列，它就挑其中一列的值交出來，而挑哪一列由執行方式決定、查詢的文字裡沒有說。**收下與拒絕之間還有第三種可能——收下並替你選一個答案**（多列一組的實例在 [1.9](/sql/grouping-key-decides-the-unit/)）。

**排名確實存在，而它只覆蓋得了一條軸。** 就「收不收」而言 SQLite 確實比 PostgreSQL 寬鬆——A、B、C 三列都是，D 打平。問題在於 D 與 E 不在收不收那條軸上：那裡四家全部收下，而答案不同。所以帶著「SQLite 最寬鬆、PostgreSQL 最嚴」去搬家，會準確地預期到「本來能跑的變成報錯」，然後被完全沒有報錯的那兩列打中。

各條的完整推導住在它們自己的篇裡：A 在 [1.2](/sql/clause-evaluation-order/) 與 [1.9](/sql/grouping-key-decides-the-unit/)（SQLite 收下之後自己從那一組挑一列的值），B 在 [1.11](/sql/relations-have-no-order/)（`WHERE` 那一步發生在算出別名之前），C 在 [1.7](/sql/table-occurrence-and-alias/)（同一張表出現兩次為什麼非取名不可），D 在 [1.15](/sql/string-comparison-and-collation/)（「相等」由哪一條比較規則定義），E 在 [1.11](/sql/relations-have-no-order/)（空值與任何值都比不出大小，落在哪一端由引擎規定）。

## 差異在什麼位置發聲，分四級

上面那張表的五列落在不同的級數上，而分級的依據是**這個差異在正常的執行路徑上會不會發出聲音、在哪裡發**。級數量的對象沿用上一節的單位——不是「這一家與那一家」，是**這一家的這個版本配上這一組設定，與另一家的另一個版本配上另一組設定**。同一家跨一個大版本、或同一個資料庫換一條連線設定，都會產生下面四級的差異。

**第一級：剖析或名稱解析就出聲。** A 與 B 從寬鬆的那一家搬到嚴格的那一家時屬於這一級——第一次跑就報錯，訊息指名了那個欄位。這一級的差異最省事：它自己會現身，而且現身得早。

**第二級：執行到某一筆資料才出聲。** [約束](/sql/knowledge-cards/constraint/)是這一級的主場——搬過去之後查詢照跑，直到第一筆違反它的資料寫進來。所以這一級的現身時機由資料決定，而測試資料多半不含觸發它的那一筆。

**第三級：不出聲，而輸出有差。** D 與 E 在這裡。四家沒有一家報錯，回來的都是形狀正確的列，而列不一樣。要發現它得**把同一段查詢在兩家上各跑一次、比對輸出**。而這個比對不會有人自發去做，因為兩邊都沒有報錯——沒有任何東西提示這裡需要被比對。

**第四級：不出聲，輸出也沒差。** [1.18](/sql/foreign-key-and-referential-integrity/) 記的那幾種屬於這一級：同一段 `REFERENCES` 在一家建得出約束、在另一家被靜默丟掉，而建表語句成功、查詢也成功。第三級至少在輸出上留下差異，這一級連差異都不在輸出裡——它在系統目錄裡，要主動去查才看得到。

**級數量的是發聲的位置，不是嚴重性、也不是偵測要花多少工夫。** 修起來多麻煩與級數無關（第一級可能要重寫整批查詢，第四級可能只要加一行設定）；連偵測成本都不隨級數單調——第四級查一次系統目錄就有答案，而第三級要持續的跨引擎輸出比對，後者其實更貴。分級真正決定的是**什麼時候會知道有這件事**：第一級不必準備，它自己會現身；第四級在往後任何一個時刻都不會自己浮現，所以知道它存在的唯一途徑落在搬家之前那一次盤點裡。

## 可攜性是查詢加上一組宣告的性質

一段 SQL 單獨拿出來問「它可不可攜」是答不出來的。上面 D 那一列在四家上有兩種答案，而把比較規則寫進欄位宣告之後，四家的答案就統一了（[1.15](/sql/string-comparison-and-collation/) 的「把規則寫出來」一節）。E 那一列同理——`ORDER BY 金額 NULLS LAST` 或 `ORDER BY (金額 IS NULL), 金額` 把引擎自己補的決定收回到文字裡。

所以可攜性的操作對象多半是**那些原本讓引擎代為決定的位置**，而不是查詢本身。判斷標準是一句話：**這段文字裡有沒有一個決定是它沒說、而由收下它的那一方補上的。** 有，那個位置就是可攜性的斷點，不論它現在跑得多正常。

這一條也解釋了為什麼可攜性在**單一一組設定**上測不出來——同一段查詢跑一萬次，那個被補上的決定每一次都一樣。「單一引擎」還不夠：同一個 MySQL 實例上，一條連線 `SET SESSION sql_mode = ''`、另一條用預設，同一段 A 那樣的查詢一邊回結果、一邊回 `ERROR 1055`。可攜性是查詢與**那一組組態**之間的性質，不是查詢的性質。

## 維持到哪一級，先看現在跑在幾種組態上

「一律照最嚴格的標準寫」這條路有價錢：每一個原本可以讓引擎決定的位置都要自己寫出來，查詢變長，寫的人要知道每一條預設是什麼。這筆錢值不值得花，主要落在一個可以現在就數出來的量上——**這段 SQL 現在跑在幾種組態上**。「組態」是上一節那個單位：換一家算一種，同一家換一個大版本或換一組連線設定也算一種，所以升級一次 MySQL 與換去 PostgreSQL 在這條軸上是同一類事。

數出來是一的時候，還要問第二句：**這個一會不會被別人改成二**。數出來已經大於一的時候這一句不必問，答案在成本上沒有分別。第二個變數比第一個難察覺，因為它不在系統裡：資料庫由自己選的系統，與資料庫由客戶指定的系統，現在可能都只跑在一種組態上，而它們對同一段 SQL 的要求完全不同——前者可以把整筆帳推遲，後者推遲不了。

**現在只有一種，而換不換由自己決定的時候**，寬鬆度是引擎給的便利。代價全部推遲到換引擎的那一天，而那一天的工作量由第三級與第四級的差異數量決定——第一級的那些會自己冒出來。這條路的風險不在「會不會換引擎」，在**換的時候有沒有辦法知道要查哪些位置**：推遲的不只是工作，還有那份清單。

**現在只有一種，而換不換由別人決定的時候**（客戶指定的資料庫、或遲早要跟上的版本升級），那一天會來而日期不在自己手上，所以成本前置到寫的當下——但只前置第三、四級那些：把引擎自己補的決定寫出來（collation、空值的位置、識別字的引號）。第一級留著不動，因為它搬家時會當場現身。這條路把「什麼時候知道」從搬家那一天提前到編譯那一刻，而付的是幾個子句的長度。

**現在就不只一種的時候**（產品裝在客戶各自的資料庫上、或測試與正式本來就不同家——後者是自己選的，前者不是，而在這一級上兩者的成本相同），答案要完全一致，而完全一致無法只靠寫出那些決定——還要一份跨引擎的對照，同一批查詢在目標引擎上各跑一次、比對輸出。這一步的成本是持續的（每次改查詢都要重跑），換到的是第三級差異不再靠人記得去查。**而它有一個取得性的問題正好落在最需要它的那個情形上**：產品裝在客戶的資料庫上時，客戶那一組版本加設定多半拿不到也不見得授權得起，這時退而求其次的是把自己手上那幾種組態的對照跑起來，並把「我們驗過哪幾種組態」寫成一份可以交出去的清單。它無法由閱讀代替，理由與 [1.20 查證一段查詢的宣告](/sql/declared-intent-vs-behaviour/)那一層相同：宣稱的真值住在文字之外。

**還有一條路不在這條軸上**：用查詢建構器或物件關聯對映把 SQL 包起來。前面三條是決定自己維持到哪一級，這一條是把整個決定交出去——那一層自己要對每一家引擎做同樣的決定，而它做了哪些決定通常沒有寫在讀得到的地方。所以它換掉的是「誰來查這些位置」，不是「有沒有這些位置」。

## 這個選擇綁在一組前提上，前提換了它就不成立

**前提一是目標組態的清單。** 維持一致的成本隨組態數量成長，而不是隨查詢數量成長，所以清單變長那一刻的重算幅度比想像中大。讓清單變長的事件多半來自外部——客戶要求裝在自己的資料庫上、併購進來一套用別家引擎的系統，或者一次跨大版本的升級。升級這一種特別容易被漏掉，因為它在直覺上不算「換引擎」，而上面五條行為裡至少有一條（A）的答案由一個可以在連線層設定的變數決定，換一個版本的預設值就換一邊。

**前提二是那些引擎的設定。** 上面 A 那一列在 MySQL 上由 `sql_mode` 決定，而那個變數可以在連線層設定——同一個資料庫、同一段查詢，換一個連線設定就換一邊。這一類的差異不在查詢裡也不在 schema 裡，所以讀程式碼看不到它。

**前提三是測試環境與正式環境用的是同一家引擎。** 測試跑 SQLite、正式跑 PostgreSQL 是最常見的一種配對，而第三級與第四級的差異在這種配對下會延到正式環境才第一次浮現——那時它們看起來像資料問題。

## 換掉其中一項就走到另一篇

本篇底下有三樣可以各自換掉：差異落在哪一級、那個決定由誰補上、可攜性維持在什麼標準。

**把「這一家收不收」換成「收下之後名字指到誰」**：識別字的摺疊規則是寬鬆度的一個具體實例，而它的形態特別隱蔽——在不區分大小寫的引擎上開發，混用引號的地方一路正常。[1.14 識別字送進引擎之後會被改寫](/sql/identifier-rules/) 寫各家的摺疊規則，以及兩種一致做法之間的中間地帶。

**把「收不收」換成「收下之後怎麼比」**：D 那一列的完整推導，包含索引與條件的比較規則要對得上這件事，在 [1.15 字串的相等、大小與索引可用性都由 collation 決定](/sql/string-comparison-and-collation/)。

**把「引擎補上的決定」換成「引擎不補的決定」**：查詢問對了沒有，是沒有任何一家引擎會代為決定的那一層，而它與寬鬆度無關——換引擎、加約束、跑靜態分析都碰不到它。[1.13 合不合法由引擎驗，答案對不對由提問的人負責](/sql/well-formed-is-not-correct/) 寫那一層的判準為什麼只能來自查詢之外。

**把「跨引擎的一致」換成「跨時間的一致」**：一段文字說了什麼給下一個讀它的人，與它在另一家引擎上做什麼，是兩個不同的可攜性。[1.20 關鍵字宣告意圖，引擎只執行行為](/sql/declared-intent-vs-behaviour/) 處理文字對下一個讀它的人說了什麼那一半。

**把引擎差異放回一次實際的遷移裡**：本篇處理的是語言這一側，而遷移還有雙寫、回填、切流與回滾。[資料庫轉換實作](/backend/01-database/database-migration-playbook/) 的 `Type I：加約束` 一節給補約束的完整順序，而每一步要留下什麼證明在 [Schema Migration Rollout 證據](/backend/01-database/schema-migration-rollout-evidence/)。
