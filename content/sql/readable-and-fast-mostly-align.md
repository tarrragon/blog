一段 SQL 同時要給引擎執行與給人維護，而這兩個需求在 SQL 上多數時候指向同一個寫法。理由落在這個語言的性質上：**引擎執行的是計畫，不是那段文字**（[1.1](/sql/declarative-not-procedural/)），所以文字裡為了讓人看懂而多出來的結構，多數在計畫上留不下痕跡。

這一篇與 [1.14](/sql/declared-intent-vs-behaviour/) 都問文字寫給誰。那一篇問文字對讀的人說了什麼，這一篇問文字該為誰而寫。

## 多數的寫法差異是免費的

同一批列的兩種寫法送進[最佳化器](/sql/knowledge-cards/query-optimizer/)之後常常收斂成同一個計畫。`CROSS JOIN` 加等值條件與 `JOIN ... ON` 寫同一個條件，計畫逐字相同（[1.14](/sql/declared-intent-vs-behaviour/) 有並排的輸出）。[1.8](/sql/in-exists-join/) 從另一條路走到同一個處置：肯定式的 `IN` 與 `EXISTS` 語意相同，所以選哪一個按可讀性挑。它的依據是語意而非計畫——這兩種寫法在 SQLite 上各自走不同的計畫（`LIST SUBQUERY` 對 `CORRELATED SCALAR SUBQUERY`），而語意相同已經足以讓選擇落在可讀性上。

這一類的判斷很省事——兩種寫法各要一次計畫，一樣就按好讀的挑。

## 分岔發生在條件的形狀上

寫法影響代價的位置很集中：條件把索引欄位包進函式或運算裡的時候，索引就用不上了（[Sargable](/sql/knowledge-cards/sargable/)）。而那個寫法常常正是好讀的那一個。

三十萬列的訂單表，`下單日` 上有索引，問三月有幾張訂單（SQLite 3.51，`SELECT count(*)`，各跑三次取最小）：

| 寫法                                               | 時間  |
| -------------------------------------------------- | ----- |
| `strftime('%Y-%m',下單日) = '2021-03'`             | 53 ms |
| `下單日 >= '2021-03-01' AND 下單日 < '2021-04-01'` | 5 ms  |

上面那個直接說出「這一列屬於哪個年月」，下面那個要讀的人自己把兩個邊界拼回一個月份，還要留意右邊是開區間。十倍的差距量得出來，而好讀的是慢的那一個。

## 出口在 schema 那一層

同一個好讀的寫法，把索引建在運算式上：

```sql
CREATE INDEX ix_月 ON 訂單(strftime('%Y-%m',下單日));
```

再量一次是 6 ms，計畫是 `SEARCH 訂單 USING COVERING INDEX ix_月 (<expr>=?)`。原本的查詢一個字都沒有改。

所以碰到這種分岔時，第一個問題是**這個代價能不能在 schema 那一層買掉**，而不是要不要把查詢寫醜。索引的代價落在寫入端（[索引](/sql/knowledge-cards/indexing/)那張卡寫這一條），那是一個可以評估的交換；把查詢改成需要讀的人自己拼邊界，換到的速度一樣，而付出的是往後每一次維護。

## 方向常常相反：拆開讓最佳化器多知道一件事

一般語言裡「拆成小塊比較好讀但比較慢」是常見的直覺，SQL 上量到的常常相反。同一個問題——「金額高於自己所屬顧客平均的訂單有幾張」——寫成一整段的相關子查詢，與拆成 CTE：

```sql
-- 一整段
SELECT count(*) FROM 訂單 o
WHERE o.金額 > (SELECT avg(金額) FROM 訂單 i WHERE i.顧客編號 = o.顧客編號);

-- 拆開
WITH 每人平均 AS (SELECT 顧客編號, avg(金額) AS 均 FROM 訂單 GROUP BY 顧客編號)
SELECT count(*) FROM 訂單 o JOIN 每人平均 p ON p.顧客編號 = o.顧客編號
WHERE o.金額 > p.均;
```

SQLite 3.51，`顧客編號` 上有索引，**顧客數固定在 500 而列數翻倍**，四個資料量各跑四次取最小：

| 列數  | 一整段 | 拆成 CTE |
| ----- | ------ | -------- |
| 5000  | 12 ms  | 6 ms     |
| 10000 | 37 ms  | 8 ms     |
| 20000 | 129 ms | 12 ms    |
| 40000 | 553 ms | 21 ms    |

列數翻倍，一整段那一欄的三段比值是 3.1、3.5、4.3，CTE 那一欄是 1.3、1.5、1.8。**顧客數固定這個條件在這裡是承重的**：列數翻倍而顧客數不動，等於每位顧客的訂單數也翻倍，相關子查詢每一列要掃的量因此跟著漲；顧客數若隨列數一起成長，那一欄的成長會平緩得多。計畫說明了原因：相關子查詢對外層的每一列各執行一次（[子查詢](/sql/knowledge-cards/subquery/)那張卡寫這個區別），而 CTE 把每位顧客的平均算成一次，再拿去連接。

**拆開讓引擎看得見「這個平均每位顧客只有一個」這件事**，而寫成相關子查詢等於把它藏起來。人讀得懂的結構，引擎往往也算得動。

## 為速度而寫醜，押的是一個會變的狀態

真要在兩者之間排序的話，理由落在 [1.13](/sql/cost-lives-in-the-plan/) 已經證過的一件事上：同一組寫法的快慢排名會隨索引對調。**為當下的代價而扭曲的文字，在別人加了一個索引之後就失去理由，而那段文字會留著。** 可讀性沒有這個問題——它不隨資料庫的狀態改變。

這也對得上優化該動哪裡：[1.13](/sql/cost-lives-in-the-plan/) 列的那四項（資料量、分布、索引、統計資訊）全部在資料庫那一側，所以調整的位置在 schema 與計畫，而查詢的文字負責把意圖說清楚。

## 文字層無解而 schema 動不了的時候

例外收在同一句話裡：唯讀複本、改不動的 vendor schema、或索引的寫入代價付不起，那時文字層是唯一能動的地方，寫成難讀的形式就有理由。

這種時候把理由寫成註解——**難讀的寫法自己不會說明它為什麼難讀**，而下一個人看到的只是一段可以「順手整理一下」的查詢。註解要寫的是那個約束（哪一層動不了、量測差多少），不是重述這段 SQL 在做什麼。

## 換掉其中一項會變成什麼

本篇的可動項是：讀的人是誰、代價落在哪一層、以及那個代價量了沒有。

**換掉讀的人為引擎**：同一段文字的問題從「說得清不清楚」變成「跑得快不快」，而跑得快不快答不出來的時候要向引擎要計畫。[1.13 代價由資料與索引決定](/sql/cost-lives-in-the-plan/) 說明為什麼比較兩段文字答不出這個問題，以及要問兩次。

**換掉動查詢為動 schema**：條件的形狀與索引的形狀是一組互補的選擇，把運算搬進索引就讓好讀的條件重新走得了。[Sargable（可走索引的條件形狀）](/sql/knowledge-cards/sargable/) 給判斷標準與三種改寫方向。

**換掉「寫得好不好」為「說了什麼」**：可讀性之上還有一層是正確性——文字說的話與查詢的行為對不對得上。[1.14 關鍵字宣告意圖，引擎只執行行為](/sql/declared-intent-vs-behaviour/) 寫宣告落空的幾種形態與查證它的動作。
