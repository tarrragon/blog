一段查詢有兩個讀者。引擎讀的是行為——這段文字要求它算出哪一批列；人讀的是宣告——寫的人選了 `LEFT` 而不選 `INNER`，選了 `CROSS` 而不選 `JOIN ... ON`，每一個選擇都在說明他預期資料長什麼樣。**引擎執行行為，而它從不檢查宣告有沒有兌現。**

兩者分岔的時候查詢照常回正確答案，測試照常通過，[執行計畫](/sql/knowledge-cards/query-plan/)上也看不出異常。付出代價的是下一個改它的人：他讀到的是宣告，於是他手上的前提從一開始就是錯的。

本篇的查詢跑在[共用的範例資料庫](/sql/#各篇共用的範例資料庫)上：三位顧客佳穎、宗翰、雅文，而只有佳穎下過兩張訂單（101 與 102，金額 300 與 500）。本篇假設讀者已經有 [1.4](/sql/join-left-operand-accumulates/) 到 [1.6](/sql/join-changes-rows-and-nulls/) 的語意模型——哪些列會被保留、條件在哪一步生效、連接怎麼改變列數。這一篇不重寫那些機制，它問的是同一段查詢對讀的人說了什麼。

## 每一個關鍵字都在宣告一件事

`LEFT JOIN` 說的是「右邊配不到對象的左邊那些列也要留著」。寫的人選它，等於宣告他預期有配不到的列，而且那些列對答案有意義。

`CROSS JOIN` 說的是「我要每一種配對」。`DISTINCT` 說的是「這一組值本身會重複，而重複對我沒有意義」。`COALESCE` 說的是「這裡會有空值」。這些宣告是免費的，寫下去沒有人會查證。

落空的樣子不只一種。宣告可能**被同一段查詢的別的部分撤銷**（`LEFT` 加上一個問右表的 `WHERE`）、可能**描述一個引擎並沒有執行的動作**（`CROSS` 加等值條件）、可能**描述一個從一開始就不存在的情況**（配對已有保證時的 `LEFT`），也可能**指向錯的成因而答案仍然正確**（`DISTINCT` 收掉連接製造的重複）。指向錯成因那一種在下一次修改就現形；另外三種要有人動到那一行才會被發現，所以可以躺很久。

## LEFT 的保護被下一行撤銷

書店想找出下過大單的顧客。查詢寫成這樣：

```sql
SELECT 顧客.姓名
FROM 顧客 LEFT JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號
WHERE 訂單.金額 > 200;
-- 佳穎、佳穎
```

`LEFT` 在這裡宣告「沒有訂單的顧客也要留著」。而下一行的 `WHERE` 問了一個右表欄位，宗翰與雅文那兩列右邊全是 `NULL`，`NULL > 200` 答不出真，於是被篩掉。同一段換成 `JOIN`，結果一個字都沒有變。

機制在 [1.5](/sql/on-describes-where-filters/)：條件放 `ON` 參與配對，放 `WHERE` 篩成品，而外連接補上的那些列過不了成品這一關。這裡要看的是另一件事——**這段查詢的行為是內連接，而它的文字說的是外連接**。

下一個維護的人讀到 `LEFT`，會以為沒下單的顧客在結果裡。他想加一個「顯示零元」的欄位，於是寫 `COALESCE(訂單.金額, 0)`，跑出來仍然只有佳穎，而他找不出原因——因為問題在他沒有動的那一行。

## CROSS 宣告全部配對，引擎做的是內連接

要比較同一批資料的兩列時，常見的寫法是把表跟自己配對再篩：

```sql
SELECT 今天.訂單編號
FROM 訂單 昨天 CROSS JOIN 訂單 今天
WHERE 今天.顧客編號 = 昨天.顧客編號 AND 今天.金額 > 昨天.金額;
```

`CROSS JOIN` 宣告「我要每一種配對」，讀起來像是先造出所有配對再挑。而等值條件寫進去之後，[最佳化器](/sql/knowledge-cards/query-optimizer/)產出的計畫與內連接的計畫一模一樣。同一組資料上兩種寫法的計畫逐字相同：

```text
-- CROSS JOIN 加 WHERE 等值（SQLite 3.51，共用的範例資料庫，沒有另外建索引）
|--SCAN 昨天
|--BLOOM FILTER ON 今天 (顧客編號=?)
`--SEARCH 今天 USING AUTOMATIC COVERING INDEX (顧客編號=?)

-- JOIN ... ON 同一個條件
|--SCAN 昨天
|--BLOOM FILTER ON 今天 (顧客編號=?)
`--SEARCH 今天 USING AUTOMATIC COVERING INDEX (顧客編號=?)
```

`AUTOMATIC` 表示這個索引是引擎為了這一次查詢臨時建的——訂單表上沒有 `顧客編號` 的索引，而它判斷建一個比逐列掃描划算。兩段查詢連這個決定都一樣。

`CROSS JOIN` 在代數上確實對應[笛卡兒積](/sql/knowledge-cards/cartesian-product/)，而那張卡寫明展開由條件決定：條件把兩邊綁起來時全部組合一次都沒有被造出來。

這一項的誤導方向反過來。`LEFT` 那一節是宣告承諾了引擎沒做的事，這一節是宣告讓讀的人誤判了代價——看到 `CROSS` 就以為它是列數的平方，於是花力氣改寫一段本來就是內連接的查詢。代價由什麼決定在 [1.13](/sql/cost-lives-in-the-plan/)，而在這裡要先分清楚：`CROSS JOIN` 加等值條件與 `JOIN ... ON` 是同一段查詢的兩種寫法，換掉它省下的是讀的人的疑慮，不是執行時間。

## 宣告的情況，資料裡從來沒有出現過

每一張訂單都帶著一個有效的顧客編號時，這樣寫也會過：

```sql
SELECT 訂單.訂單編號, 顧客.姓名
FROM 訂單 LEFT JOIN 顧客 ON 顧客.顧客編號 = 訂單.顧客編號;
```

`LEFT` 宣告「訂單可能找不到顧客」。而兩列訂單都配到了，`count(*)` 與 `count(顧客.姓名)` 同樣是 2——這個宣告一次都沒有生效過。

它的代價要等到有人相信它才出現。下一個人想查有沒有孤兒訂單，順手接上這段查詢寫 `WHERE 顧客.姓名 IS NULL`，拿到零列，於是回報「資料乾淨」。零列在這裡有兩種來源：確實沒有孤兒訂單，或者這個宣告本來就沒有內容。這段查詢分不出兩者。

真正保證配對的是[約束](/sql/knowledge-cards/constraint/)——外鍵存在時每一張訂單都指得到顧客，那時 `LEFT` 描述的是一個資料庫已經排除掉的情況。宣告與約束衝突時，讀的人多半相信宣告，因為它就在眼前，而約束在另一個檔案裡。

## DISTINCT 收掉的重複來自連接

顧客與訂單連起來之後，佳穎出現兩次，因為她有兩張訂單。要一份「下過單的顧客」名單，加 `DISTINCT` 就對了：

```sql
SELECT DISTINCT 姓名 FROM 顧客 JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號;
-- 佳穎
```

`DISTINCT` 宣告「姓名這一欄有重複值」。而顧客表裡佳穎只有一列——重複是連接製造出來的（[1.6](/sql/join-changes-rows-and-nulls/)）。宣告指向了錯的成因，答案卻是對的。

這種宣告落空的代價由下一次修改觸發，而觸發它的動作很小——多要一個欄位就夠：

```sql
SELECT DISTINCT 姓名, 金額 FROM 顧客 JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號;
-- 佳穎 300
-- 佳穎 500
```

`DISTINCT` 作用在整列上，兩列的金額不同，於是它一列都收不掉。上一個人的修法在這裡失效，而失效的理由要回到「重複從哪裡來」這個問題——那個問題當初被 `DISTINCT` 跳過了。

## 宣告與行為的差別只有在換掉關鍵字時現形

文字本身看不出宣告有沒有兌現——`LEFT` 寫在那裡，而它保護下來的列可能一列都不剩。差別要現形，得讓那個關鍵字消失一次：**把它換成最弱的版本再跑一次，結果變不變就是它有沒有在做事。**

| 宣告                         | 換成                     | 結果不變表示               |
| ---------------------------- | ------------------------ | -------------------------- |
| `LEFT JOIN` / `RIGHT JOIN`   | `JOIN`                   | 這段查詢的行為是內連接     |
| `CROSS JOIN` 加 `WHERE` 等值 | `JOIN ... ON` 同一個條件 | 這段本來就是內連接         |
| `DISTINCT`                   | 拿掉                     | 這一組值原本就各不相同     |
| `COALESCE(欄位, 預設值)`     | 直接用該欄位             | 這一欄在現有資料上沒有空值 |

結果變了的時候，這個動作只走完一半——它證明那個關鍵字在做事，還沒證明宣告是對的。`DISTINCT` 那一格就是這種：拿掉之後結果會變，而變的理由是連接把列複製了，與「這一欄有重複值」無關。所以第二個問題是**變化的成因與宣告說的是不是同一件事**。

外連接還有一種宣告落空是這個動作測不出來的：配對由外鍵保證的時候，`LEFT` 與 `JOIN` 在現有資料上結果相同，而換掉之後仍然看不出宣告當初有沒有意義。那一種要去查[約束](/sql/knowledge-cards/constraint/)，判斷標準是資料庫有沒有替這個配對背書。

對讀別人查詢的人來說，這個差別回答的是「我可以相信這段文字說的話嗎」——而那個問題在讀的當下沒有別的入口。

## 換掉其中一項會變成什麼

本篇的模型有三樣可以各自抽換：宣告落空的是哪一個關鍵字、讀的人是誰、以及落空這件事有沒有辦法發出聲音。

**換掉關鍵字，就換到它自己的語意那一篇**。`LEFT` 保護了誰在 [1.4 JOIN 的左邊是累積結果](/sql/join-left-operand-accumulates/)，它與條件位置的互動在 [1.5 ON 描述關係、WHERE 篩選結果](/sql/on-describes-where-filters/)，連接怎麼把一列變成多列在 [1.6 連接產出的是新的關係](/sql/join-changes-rows-and-nulls/)。那三篇答的是「這個關鍵字做什麼」，本篇答的是「它說了什麼」。

**把讀的人換成引擎**，同一段文字的問題就從「說得對不對」變成「跑得快不快」。[1.13 代價由資料與索引決定](/sql/cost-lives-in-the-plan/) 說明兩段文字比不出快慢，要向引擎要計畫；而 `CROSS JOIN` 那一節是這兩個問題最容易被混起來的位置——換掉它改善的是可讀性，執行時間留在原地。

**讓落空發出聲音**，責任就從查詢移到結構。[Constraint（約束）](/sql/knowledge-cards/constraint/) 寫資料庫在每次寫入時檢查什麼；外鍵存在的時候「訂單可能沒有顧客」這個宣告當場就是可以否證的，用不著等到有人相信它。
