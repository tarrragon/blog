在連接查詢裡，`ON` 與 `WHERE` 分處不同的求值階段。本篇先以書店外連接查詢對照同一條件寫進 `ON` 與 `WHERE` 的結果差異，再從求值順序解釋為何兩者在外連接分岔而在內連接同值；後半段以「將補 `NULL` 的列代入條件」測試外連接保護是否留存，並界定左表條件與尋找未配對列的 `IS NULL` 條件歸屬。

在求值順序裡，`ON` 參與 `FROM` 步驟，定義 `JOIN` 左右兩側的列如何組成新的 [Relation（關係）](/backend/01-database/sql/knowledge-cards/relation/)；`WHERE` 排在 `FROM` 之後，從組好的關係裡篩選要保留的列。下文以**配對**指稱關係正在組合的過程（決定哪兩列湊成一列），以**成品**指稱關係組合完成後得到的那批列（包含外連接補上 `NULL` 的列）；這兩個稱呼用來區分這兩個階段，並非 SQL 標準術語。

在內連接中，條件寫在 `ON` 或 `WHERE` 會得到相同的列集合；在 [Outer Join（外連接）](/backend/01-database/sql/knowledge-cards/outer-join/)中，兩種位置會產出不同的列，差別在於外連接的保護是否留存。保護指 `LEFT JOIN` 把左表配不到對象的列留在結果中，並在右表欄位補上 `NULL`；將右表的配對條件誤放進 `WHERE`，正是 `LEFT JOIN` 靜默退化成內連接的成因。

## 同一個條件放 ON 與放 WHERE 的結果

以下查詢使用 [SQL 各篇共用的範例資料庫：一家小書店的顧客、訂單與評價表](/backend/01-database/sql/sample-bookstore-database/)（顧客為佳穎、宗翰、雅文；僅佳穎有訂單 101 與 102，其中僅訂單 101 有一則五星評價）。書店需要一份名單：列出所有顧客，評價欄只顯示五星評價。將星等條件寫進 `ON`：

```sql
SELECT 顧客.姓名, 評價.星等
FROM 顧客
LEFT JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號
LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號 AND 評價.星等 = 5;
```

查詢回傳四列：

```text
佳穎  5
佳穎  NULL
宗翰  NULL
雅文  NULL
```

三位顧客都在名單裡。佳穎出現兩次是因為她有兩張訂單：第一張配到五星評價，第二張沒有評價可配而補 `NULL`。（單一顧客因一對多連接變成多列屬於列數變化，機制見 [SQL.6 連接之後的列數與空缺：列數膨脹、外連接補的 NULL 與三值邏輯](/backend/01-database/sql/join-changes-rows-and-nulls/)。）

將同一個星等條件移到 `WHERE`，其餘不變：

```sql
SELECT 顧客.姓名, 評價.星等
FROM 顧客
LEFT JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號
LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號
WHERE 評價.星等 = 5;
-- 佳穎  5
```

宗翰、雅文與佳穎的第二張訂單全部消失，輸出與內連接一致。需求要求列出全部顧客時，這個版本回傳了錯誤答案，但引擎照常執行且不報錯（這類錯誤的成因與查證方式見 [SQL.13 查詢的合法性與答案的正確性：引擎檢查的範圍、答案錯掉的成因與查證方法](/backend/01-database/sql/well-formed-is-not-correct/)）。若需求原本只要有五星評價的訂單，輸出雖然正確，但查詢文字仍保留了未生效的 `LEFT`，容易讓後續閱讀者誤以為未配對列被保留（見 [SQL.21 關鍵字的宣告與引擎的行為：宣告落空的形態與查證](/backend/01-database/sql/declared-intent-vs-behaviour/)）。

## 條件放 ON 與放 WHERE 在外連接底下分岔的原因

`LEFT JOIN` 的定義要求左運算元的每一列都保留在結果中，右運算元配對不到時補 `NULL`。條件寫在 `ON` 裡時，它只決定右側是否存在符合配對資格的列：宗翰沒有訂單、佳穎的第二張訂單沒有五星評價，兩者配對失敗後仍照 `LEFT JOIN` 定義補 `NULL` 保留。

條件寫在 `WHERE` 裡時，連接已完成，補了 `NULL` 的列也已進入成品。引擎對成品逐列評估 `評價.星等 = 5`，補了 `NULL` 的列無法滿足該條件而遭到排除。`WHERE` 把 `LEFT JOIN` 剛保留下來的列再度移除了。

內連接沒有保留未配對列的機制，因此不存在會被 `WHERE` 抵銷的保護，兩種寫法產出的列集合相同。這段查詢連接了顧客、訂單與評價三張表，第二個 `LEFT JOIN` 的左運算元是顧客與訂單累積出來的結果，鏈式連接的保護範圍判讀見 [SQL.4 鏈式連接的左運算元：累積方式與外連接的保護範圍](/backend/01-database/sql/join-left-operand-accumulates/)。

## 外連接保護是否保留的測試：將補 NULL 的列代進條件

`WHERE` 只保留條件評估為真的列。SQL 條件的評估結果有真、假與**未知**三種，任何值與 `NULL` 做比較運算都會得到未知（三值邏輯與它讓 `NOT IN` 回傳空集合的推導見 [SQL.6 連接之後的列數與空缺：列數膨脹、外連接補的 NULL 與三值邏輯](/backend/01-database/sql/join-changes-rows-and-nulls/)）。

外連接補出來的列，右表欄位全是 `NULL`，因此判斷某個 `WHERE` 條件是否保留外連接保護，可以將右表全為 `NULL` 的列代入該條件，觀察評估結果：結果為真則保留保護，結果為假或未知則取消保護。

| 條件                                 | 代入補 `NULL` 列的評估結果 | 外連接保護的狀態 |
| ------------------------------------ | -------------------------- | ---------------- |
| `評價.星等 = 5`                      | 與 `NULL` 比較，結果為未知 | 取消             |
| `評價.星等 IS NOT NULL`              | 結果為假                   | 取消             |
| `評價.星等 IS NULL`                  | 結果為真                   | 保留             |
| `評價.星等 IS NULL OR 評價.星等 = 5` | 前半為真，整串結果為真     | 保留             |
| `COALESCE(評價.星等, 0) >= 0`        | `NULL` 先轉成 0，結果為真  | 保留             |

保護是否保留取決於條件對 [NULL（空值）](/backend/01-database/sql/knowledge-cards/null/) 的評估結果，不取決於運算子外觀。`IS NOT NULL` 與 `IS NULL` 外觀成對，但 `IS NOT NULL` 對空值判假而取消保護，`IS NULL` 判真而保留保護；`OR` 與 `COALESCE` 則把原本的未知轉為真，使保護得以留存。

上表列的條件全部針對右表欄位，左表條件不適用於這個測試。補 `NULL` 的列保留了左表原本的值，左表條件對它都能判出真假，外連接保護不會因此被取消。左表條件的錯誤形態出現在寫進 `ON` 的時候：它既無法篩除左表的列，還會讓原本能配對成功的列因條件判假而失去右表資料。以下將 `顧客.姓名 <> '佳穎'` 分別放在三個位置對照：

```sql
-- 放 WHERE：佳穎被篩掉，宗翰與雅文的保護完好
SELECT 顧客.姓名, 訂單.訂單編號, 評價.星等
FROM 顧客
LEFT JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號
LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號 AND 評價.星等 = 5
WHERE 顧客.姓名 <> '佳穎';
-- 宗翰  NULL  NULL
-- 雅文  NULL  NULL

-- 放進顧客接訂單的 ON：佳穎與她的兩張訂單判假、配不上，照 LEFT 的定義補 NULL 留下
SELECT 顧客.姓名, 訂單.訂單編號, 評價.星等
FROM 顧客
LEFT JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號 AND 顧客.姓名 <> '佳穎'
LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號 AND 評價.星等 = 5;
-- 佳穎  NULL  NULL     三位顧客全回來，佳穎的兩張訂單一起消失
-- 宗翰  NULL  NULL
-- 雅文  NULL  NULL

-- 放進接評價的 ON：顧客與訂單在上一步已經配好，佳穎的兩張訂單留著，只是配不到評價
SELECT 顧客.姓名, 訂單.訂單編號, 評價.星等
FROM 顧客
LEFT JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號
LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號 AND 評價.星等 = 5 AND 顧客.姓名 <> '佳穎';
-- 佳穎  101   NULL
-- 佳穎  102   NULL
-- 宗翰  NULL  NULL
-- 雅文  NULL  NULL
```

因此左表條件不必做補 `NULL` 測試，它直接屬於 `WHERE`。這條邊界在多租戶共用資料表（pool 模式：多個租戶共用同一張資料表，以 `tenant_id` 欄位區分）的授權查詢裡特別關鍵：當查詢寫成從子表左連接父表（例如 `FROM 子表 LEFT JOIN 父表 ON 子表.父編號 = 父表.編號 AND 父表.tenant_id = :current`），由於 `ON` 只約束右表配對、不篩除左表列，`LEFT JOIN` 會保留全部租戶的子表列，只把其他租戶的右表欄位補成 `NULL`，造成跨租戶資料外洩。這裡的修法並非單純把 `父表.tenant_id = :current` 搬進 `WHERE`（那只會靠把 `LEFT JOIN` 退化成內連接來偶然擋住，一旦需求改寫成 `OR 父表.編號 IS NULL` 保留無父列資料，其他租戶的孤兒列依然外洩），而是把租戶隔離條件直接加在左表（`WHERE 子表.tenant_id = :current`），並在建表層以子表冗餘租戶鍵與列級安全性（RLS）補強防線（實測與防線設計見 [1.21 資安、權限與合規決定的資料表設計：軟刪除與唯一約束、多租戶子表與列級安全性、RBAC 與非同步任務複查、存取憑證撤銷與優先序、個資分離與不可變稽核、角色預設權限與逾時護欄](/backend/01-database/security-and-compliance-schema-decisions/)）。

將補 `NULL` 列代入條件的測試只判斷保護是否留存，不決定條件該放哪一邊。決定歸屬的依據是條件描述的對象：描述「配對」的條件（「只跟五星評價配對」）放在 `ON`；描述「成品」的條件（「最終名單只要五星那些列」）放在 `WHERE`。內連接因不保留未配對列，使這兩種不同語意偶然得到相同輸出。

多數形態上，取消外連接保護的條件通常正是在描述成品（屬於 `WHERE`）；但 `IS NULL` 是兩個判斷指向不同方向的特例：它保留了保護，卻因為描述的是成品而屬於 `WHERE`。

## 找沒配到的那些列：IS NULL 條件的歸屬

當需求正是找出沒有對應資料的紀錄——例如書店要找出沒有下過訂單的顧客——查詢寫法如下：

```sql
SELECT 顧客.姓名
FROM 顧客 LEFT JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號
WHERE 訂單.訂單編號 IS NULL;
-- 宗翰、雅文
```

`訂單.訂單編號 IS NULL` 雖然同樣在 `WHERE` 引用右表欄位，但目標與退化成內連接的寫法相反：這段查詢利用外連接保留未配對列並補 `NULL` 的結果，再於成品階段篩出這些補 `NULL` 的列。因為「未下過訂單」描述的是連接完成後的成品狀態，該條件放進 `WHERE` 才正確。

找出沒有消費的顧客也能從業務事實切入。[SQL.9 分組鍵的選擇：鍵與一組所代表的對象](/backend/01-database/sql/grouping-key-decides-the-unit/) 從「沒消費的顧客在訂單表裡沒有任何一列」推導出 `NOT EXISTS` 寫法，並說明外連接後分組再檢查計數為零的寫法中，那個零是由 `LEFT JOIN` 先補出 `NULL` 列、再讓 `count(欄位)` 數出零所製造的產物。
