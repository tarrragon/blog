多張資料表串接成鏈式連接時，每一個 `JOIN` 的左運算元都是前方所有連接累積出的結果。本篇說明如何從查詢文字判讀每層 `JOIN` 的左運算元與可用欄位，並以三表連接示範鏈中出現 `RIGHT JOIN` 時保護對象如何反轉；同時說明統一改寫為 `LEFT JOIN` 與 `FULL JOIN` 的界線、書寫順序與引擎執行順序的分工，以及 `WHERE` 引用鏈尾資料表時會撤銷哪些列的保護。

在 `FROM` 子句裡，引擎由上往下逐一併入資料表，每一個 `JOIN` 的左運算元是它上方全部資料表合併後的結果。第一個 `JOIN` 的左運算元剛好是單一資料表，從第二個 `JOIN` 開始則變成前方累積出來的中間 [Relation（關係）](/backend/01-database/sql/knowledge-cards/relation/)。

左運算元累積的性質影響三件事：每一個 `ON` 能引用的欄位範圍、每一個 `LEFT JOIN` 所**保護**的列集合（保護指左運算元中配不到對象的列仍留在結果中，右運算元欄位補 `NULL`，定義見 [Outer Join（外連接）](/backend/01-database/sql/knowledge-cards/outer-join/)），以及在鏈中間換成 `RIGHT JOIN` 後的結果變化。這項性質在單一 `JOIN` 中不顯眼，到了兩個以上 `JOIN` 串接時會直接決定哪些列留在結果裡。

## 左運算元的累積與判讀方法

在 [SQL 各篇共用的範例資料庫：一家小書店的顧客、訂單與評價表](/backend/01-database/sql/sample-bookstore-database/) 裡，顧客共有佳穎、宗翰、雅文三人；佳穎下過兩張訂單，其中只有一張有評價，宗翰與雅文沒有訂單。查詢目標是列出每位顧客連同其訂單與評價，沒下單的顧客與沒評價的訂單都要保留，寫法如下：

```sql
SELECT 顧客.姓名, 訂單.訂單編號, 評價.星等
FROM 顧客
LEFT JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號
LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號;
```

查詢回傳四列：

```text
佳穎  101   5
佳穎  102   NULL
宗翰  NULL  NULL
雅文  NULL  NULL
```

第二個 `LEFT JOIN` 的左運算元是顧客與訂單合併後的結果，其中已經包含宗翰與雅文兩筆訂單欄位為 `NULL` 的列，而非單一的訂單表。要判讀鏈中任一 `JOIN` 的左右運算元，可將該 `JOIN` 所在那一行上方視為切線：切線以上所有資料表合併後的結果是左運算元，該行接上的單一資料表是右運算元。

由這個判讀法可直接推出兩個結論。第一，第二個 `ON` 可以引用顧客表的欄位，因為顧客表在橫線以上的左運算元裡。第二，若把第二個 `LEFT JOIN` 換成 `INNER JOIN`，被篩掉的是橫線以上那四列中配不到評價的全部三列，而不僅限於「沒有評價的訂單」——即使宗翰與雅文與評價表無關，也會一併消失：

```sql
SELECT 顧客.姓名, 訂單.訂單編號, 評價.星等
FROM 顧客
LEFT JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號   -- 橫線以上：佳穎 101、佳穎 102、宗翰、雅文四列
JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號;       -- 內連接：四列裡配不到評價的三列一起移除
-- 佳穎  101  5
```

宗翰與雅文這兩列在訂單欄位的 `NULL` 是外連接補上的結果，並非原始資料表裡的空值，但後續的計數與比較運算無法區分兩者來源。`LEFT`、`RIGHT` 與 `FULL` 各自保護哪一側及空值的來源定義見 [Outer Join（外連接）](/backend/01-database/sql/knowledge-cards/outer-join/)；這些空值如何讓聚合算錯及為何不能用等號比較，見 [SQL.6 連接之後的列數與空缺：列數膨脹、外連接補的 NULL 與三值邏輯](/backend/01-database/sql/join-changes-rows-and-nulls/)。

## 鏈中間的 RIGHT JOIN 保護的對象

將「顧客 `LEFT JOIN` 訂單 `LEFT JOIN` 評價」的第二個 `LEFT` 改成 `RIGHT`，其餘語法維持不變：

```sql
FROM 顧客
LEFT  JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號
RIGHT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號
```

結果從四列縮減成一列，只剩 `佳穎 101 5`。

`RIGHT JOIN` 保護的對象是右運算元，也就是評價這張單獨的資料表。左運算元（顧客與訂單累積出的四列）整批變成非保護側，配不上評價的列全部被捨棄，宗翰、雅文與佳穎未獲評價的訂單 102 都從結果中消失。

這段語法在語意上宣告的是「保留每一則評價，顧客與訂單配不到也無妨」。在從顧客出發串接訂單與評價的鏈尾使用 `RIGHT JOIN`，會把整條鏈原本建立的保護方向反轉，讓查詢意圖與起始表完全背離。

## 只用 LEFT JOIN 的鏈：保護方向的判讀與 FULL JOIN 的例外

在連接鏈中統一使用 `LEFT JOIN` 可以維持單一保護方向：將必須完整保留的表放在 `FROM` 最上方，往下逐行接上可選配對的資料表。需要確認鏈中任何一個 `JOIN` 保護的列集合時，只需看它上方累積的資料表即可。

需要保留每一則評價並順帶附上對應訂單與顧客時，改將評價放在 `FROM` 第一張表，往下以 `LEFT JOIN` 依序連接訂單與顧客：

```sql
SELECT 顧客.姓名, 訂單.訂單編號, 評價.星等
FROM 評價
LEFT JOIN 訂單 ON 訂單.訂單編號 = 評價.訂單編號
LEFT JOIN 顧客 ON 顧客.顧客編號 = 訂單.顧客編號;
-- 佳穎  101  5，與鏈尾換成 RIGHT 的那段查詢是同一個列集合
```

整段查詢的每一個連接都是 `LEFT JOIN`，保護方向從頭到尾一致，沒有中途反轉。

若需求要求兩側未配對列都必須保留，單向的 `LEFT JOIN` 不適用，必須使用 `FULL JOIN`——兩側配不到的列都會保留並各自在對側補 `NULL`。一旦鏈中出現 `FULL JOIN`，最上方資料表單獨受保護的規律不再成立，判讀時須逐一檢視每個連接的保護方向。

## 書寫的左右與引擎的執行順序

`JOIN` 的左右位置只定義語意上的保護方向，不決定引擎實際先讀取哪張表。把同一個內連接寫成 `FROM 訂單 JOIN 顧客` 與 `FROM 顧客 JOIN 訂單`，在執行過 `ANALYZE` 的資料庫上，SQLite 兩次都產出相同的 [Query Plan（執行計畫）](/backend/01-database/sql/knowledge-cards/query-plan/)：掃描二十萬列的訂單表並對五十列的顧客表做查找。引擎只有在缺乏統計資訊時才會退回照文字順序讀取，有無統計資訊的計畫對照見 [SQL.1 宣告式的紅利與代價：書寫、求值與執行順序各自由誰決定](/backend/01-database/sql/declarative-not-procedural/)。

書寫左右決定保護哪一側的列，執行順序由最佳化器依統計資訊決定先讀哪張表，兩者各自獨立。調換表的書寫順序會改變外連接的保護方向，無法作為調整查詢效能的手段；引擎的實際掃描順序須透過執行計畫確認。

## WHERE 引用鏈尾那張表時被撤掉保護的列

`WHERE` 的篩選對象是整條連接鏈累積完成的結果（顧客接訂單再接評價累積出的四列）。當 `WHERE` 條件引用鏈尾評價表的欄位時，佳穎的訂單 102、宗翰與雅文這三列的評價欄全是補出來的 `NULL`，會被條件一併濾除——即使宗翰與雅文的保護來自第一個 `LEFT JOIN` 且與評價表毫無關聯：

```sql
SELECT 顧客.姓名, 訂單.訂單編號, 評價.星等
FROM 顧客
LEFT JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號
LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號
WHERE 評價.星等 = 5;   -- 補出來的 NULL 判成未知，那三列被篩掉
-- 佳穎  101  5
```

在這份資料上，被 `WHERE 評價.星等 = 5` 移除的列，正好與把第二個連接改為 `INNER JOIN` 時消失的列相同。判讀某個 `WHERE` 條件會撤銷哪些列的保護時，同樣回到累積順序：找出條件引用的表位於連接鏈的哪一行，該行以上累積進來且無法與該表配對的列都在影響範圍內。[SQL.5 ON 與 WHERE：連接條件與篩選條件各自的職責](/backend/01-database/sql/on-describes-where-filters/) 進一步以「代入補 `NULL` 列」的方法整理各種 `WHERE` 條件如何保留或取消外連接保護。
