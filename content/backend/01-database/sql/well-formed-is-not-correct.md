SQL 查詢通過引擎檢查並回傳結果，只代表語法與語意模型層面的合法，不保證結果符合業務需求。本篇先以「找出沒有五星評價的訂單」對照正解與多組錯誤寫法，接著依偏差環節分類成因並說明引擎不報錯且輸出外觀仍正常的原因；後半段區分靜態分析、資料庫約束與反例資料各自能檢驗的邊界，並標明執行代價與文字之外影響因素的專篇。

查詢文字送進 [Database Engine（資料庫引擎）](/backend/01-database/sql/knowledge-cards/database-engine/) 後，引擎負責檢查三件事：識別字能解析到存在的表與欄、運算元的型別相容，以及子句組合合乎 [Relational Algebra（關聯代數）](/backend/01-database/sql/knowledge-cards/relational-algebra/) 的規則。在靜態強型別引擎（如 PostgreSQL 與 DuckDB）上，這三項檢查於編譯期完成、不需讀取任何資料列即判定**合法**；採動態型別（type affinity）的 SQLite 則會在編譯期放行部分跨型別運算，而除零、純量子查詢回多列或 `CAST` 轉換失敗等執行期錯誤，在各家引擎皆須讀到資料列才觸發（各家寬鬆界線詳見 [SQL.19 引擎寬鬆度與可攜性：各家對同一組寫法的差異、分級與處理時機](/backend/01-database/sql/engine-leniency-and-portability/)）。通過檢查後引擎便依 [Semantic Model（語意模型）](/backend/01-database/sql/knowledge-cards/semantic-model/) 計算並回傳一份 [Relation（關係）](/backend/01-database/sql/knowledge-cards/relation/)。

這份結果集是否符合提問者的業務需求（以下稱**符合需求**），不在引擎的檢查範圍內。業務需求存在於提問者的腦中或規格裡，SQL 查詢只是該需求的一種文字表達，引擎無從驗證這段表達是否忠實對應原本的需求。語意模型的規則在子句順序、連接左右、條件位置與分組鍵上都有容易違反直覺之處；當寫查詢的人直覺偏離模型時，引擎照樣算完並回傳一批不帶任何異常訊號的列。

## 正解與錯誤寫法：「不等於五」「漏掉星等」與「NOT IN」

在靜態合法卻未對應業務需求的查詢裡，同一句需求常能寫出外觀合理卻各自偏離的錯誤版本。以書店「找出沒有五星評價的訂單」為例，在[SQL 各篇共用的範例資料庫：一家小書店的顧客、訂單與評價表](/backend/01-database/sql/sample-bookstore-database/)中，訂單 101 有一則五星評價、訂單 102 沒有評價，因此正確答案是訂單 102。

正解將星等條件寫進 `ON`，再於 `WHERE` 挑出右表補 `NULL` 的列（[SQL.5 ON 與 WHERE：連接條件與篩選條件各自的職責](/backend/01-database/sql/on-describes-where-filters/) 的〈找沒配到的那些列：IS NULL 條件的歸屬〉一節說明歸屬推導）：

```sql
SELECT 訂單.訂單編號 FROM 訂單
LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號 AND 評價.星等 = 5
WHERE 評價.評價編號 IS NULL;
-- 102
```

**「不等於五」的錯誤寫法**把「沒有五星」改成「星等不等於五」，並將條件移至 `WHERE`：

```sql
... LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號
WHERE 評價.星等 <> 5;
-- 共用資料：0 列
--   101 唯一那則評價是五星，5 <> 5 判成假
--   102 沒有評價，外連接替它補一列、星等是 NULL，NULL <> 5 的真值是未知，WHERE 只留判成真的列
-- 訂單 101 多一則三星之後：101
```

這段查詢實際表達的是「至少有一則非五星評價的訂單」，與「沒有五星評價的訂單」屬於兩個不同需求。[Outer Join（外連接）](/backend/01-database/sql/knowledge-cards/outer-join/) 替未配對訂單補上評價欄位全為 [NULL（空值）](/backend/01-database/sql/knowledge-cards/null/) 的列，MySQL 手冊稱為 NULL-complemented row（以下稱**補出來的列**）。無法對補出來的列評估為真的條件稱為**拒絕 NULL 的條件**（null-rejected condition），`評價.星等 <> 5` 即為一例（[SQL.6 連接之後的列數與空缺：列數膨脹、外連接補的 NULL 與三值邏輯](/backend/01-database/sql/join-changes-rows-and-nulls/) 的〈NULL 的比較結果與 IS NULL〉一節推導了 `NULL` 比較判為未知的規則）。需求轉換錯誤疊加拒絕 NULL 的條件，使結果隨資料變動：當訂單 101 多出一則三星評價時，正確答案仍是 102，這段查詢卻回傳恰好相反的 101。

若只補上 `OR 評價.星等 IS NULL` 企圖保留補出來的列，查詢在不同資料上會時對時錯，因為原本的需求轉換錯誤並未修正：

```sql
... LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號
WHERE 評價.星等 <> 5 OR 評價.星等 IS NULL;
-- 共用資料：102，看起來完全正確
-- 訂單 101 多一則三星之後：101 與 102
```

**「漏掉星等」的錯誤寫法**未在 `ON` 加入星等條件，卻在共用資料上回傳正確答案：

```sql
SELECT 訂單.訂單編號 FROM 訂單
LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號
WHERE 評價.評價編號 IS NULL;
-- 共用資料：102
-- 訂單 102 多一則三星評價之後：0 列（正解仍然是 102）
```

這段查詢實際表達的是「沒有任何評價的訂單」。它在共用資料上與正解結果相同，是因為有評價的訂單 101 剛好只有五星評價；一旦某張訂單擁有非五星評價，兩段查詢的輸出立刻分開。

**「NOT IN」的錯誤寫法**改用 [Subquery（子查詢）](/backend/01-database/sql/knowledge-cards/subquery/) 與 `NOT IN` 表達否定成員判斷，不透過連接完成：

```sql
SELECT 訂單編號 FROM 訂單
WHERE 訂單編號 NOT IN (SELECT 訂單編號 FROM 評價 WHERE 星等 = 5);
-- 共用資料：102
-- 評價表多一則訂單編號還沒填的五星評價之後：0 列
--   子查詢交出 101 與 NULL，NOT IN 對訂單 102 展開成 102 <> 101 AND 102 <> NULL
--   前一項為真、後一項的真值是未知，AND 的結果是未知，WHERE 不留

-- 同一個需求寫成 NOT EXISTS，加了那則評價之後仍然回 102
SELECT 訂單編號 FROM 訂單
WHERE NOT EXISTS (SELECT 1 FROM 評價
                  WHERE 評價.訂單編號 = 訂單.訂單編號 AND 星等 = 5);
```

引擎把 `NOT IN` 展開成一串不等於的 `AND`，子查詢只要回傳一個 `NULL`，該項對所有列皆判為未知，整串因此無法為真（完整推導見 [SQL.6 連接之後的列數與空缺：列數膨脹、外連接補的 NULL 與三值邏輯](/backend/01-database/sql/join-changes-rows-and-nulls/) 的〈子查詢含 NULL 時的 NOT IN 與 NOT EXISTS〉一節）。`NOT EXISTS` 則逐列檢查是否存在相配的五星評價，訂單編號為 `NULL` 的評價配不上任何訂單，不影響外層結果。

## 答案錯掉的成因分類與引擎不報錯的原因

從業務需求到最終結果集經過三個環節：寫查詢的人將需求轉成查詢文字、語意模型定義這段文字的結果集、引擎依實作執行計算。依偏差發生的環節，答案錯誤的成因分為四類：**寫錯查詢需求**（需求轉成文字時偏離原意）、**誤解語意模型**（撰寫者對規則的預期與語意模型規定不符）、**引擎寬鬆**（引擎實作放寬並偏離標準），以及**需求尚未定義清楚**（業務需求本身還沒界定邊界）。

「不等於五」與「漏掉星等」屬於寫錯查詢需求：「不等於五」表達的是「至少有一則非五星評價」，「漏掉星等」表達的是「沒有任何評價」，兩段查詢都精確算出了各自條件定義的列集合，只是與目標需求不符。單純寫錯查詢需求與語意模型無關，更換引擎或加上約束都無法攔截，因為查詢文字本身沒有語法或模型瑕疵（至於「不等於五」同時誤用了外連接與 `NULL` 的語意規則，因此只看查詢文字與執行計畫就能偵測出 `LEFT` 被撤銷，見〈查詢是否符合需求的檢驗方法：靜態分析、約束與反例資料〉的靜態分析一段）。寫錯查詢需求是結構合法卻回傳錯誤結果；與之方向相反的是宣告落空：查詢結果正確，但失效的關鍵字（例如已被撤銷的 `LEFT`）向後續閱讀者傳達錯誤預期，[SQL.21 關鍵字的宣告與引擎的行為：宣告落空的形態與查證](/backend/01-database/sql/declared-intent-vs-behaviour/) 專篇分析各種宣告落空形態。

「NOT IN」的寫法屬於誤解語意模型：`NOT IN` 遇見 `NULL` 的展開規則由語意模型定死，撰寫者誤以為它表現得像集合差集。誤解語意模型在改用正確構造（`NOT EXISTS`）後即可永久修復。分頁查詢未補唯一決勝鍵、導致同分列順序變動進而重複或遺漏，同樣屬於誤解語意模型（見 [SQL.12 分頁的排序鍵與接續標記：同分的列、全序與 OFFSET 的代價](/backend/01-database/sql/pagination-needs-a-total-order/)）。

「不等於五」這段查詢同時帶有寫錯查詢需求與誤解語意模型兩項偏差——查詢條件既不對應原需求，又在 `WHERE` 以拒絕 NULL 的條件濾掉補出來的列——導致結果隨資料變動，診斷難度高於「漏掉星等」與「NOT IN」。

引擎寬鬆發生在引擎接受標準禁止的寫法並自行補值時，「不等於五」「漏掉星等」與「NOT IN」未涵蓋此類。典型實例是在 `GROUP BY` 後將非分組欄位寫進 `SELECT`（實測見 [SQL.9 分組鍵的選擇：鍵與一組所代表的對象](/backend/01-database/sql/grouping-key-decides-the-unit/)）或將列條件寫進 `HAVING`（實測見 [SQL.2 子句的求值順序：每一步可用的欄位、語意模型擋下的寫法與各家引擎放寬的寫法](/backend/01-database/sql/clause-evaluation-order/)），寬鬆引擎接受並回傳錯誤清單，換至嚴格引擎才報錯。需求尚未定義清楚的實例則是「找出所有訂單都被評價過的顧客」：對於一張訂單都沒下過的顧客，由於找不到任何一筆未評價的訂單當反例，邏輯上的空真（vacuous truth）會讓「所有訂單都被評價」自動成立，但提出需求的人往往尚未決定這類顧客是否應列入。這類成因即使更換撰寫者也無法解決，必須先釐清規格。

上述四類成因都不會觸發引擎報錯。引擎只透過錯誤訊息與結果集兩個管道回應，而它只保證兩件事：查詢文字合法，以及算出的關係符合語意模型。文字合法與符合語意模型都不保證結果符合業務需求，因此這四類錯誤完全不會產生錯誤訊息、型別衝突或格式異常。

檢視回傳的結果集外觀也難以察覺錯誤。「漏掉星等」在共用資料上回傳正確答案 102；「不等於五」與「NOT IN」回傳零列，外觀與「確實沒有符合訂單」毫無差別（這正是 [SQL.8 IN、EXISTS 與 JOIN：列數、可取用的欄位與 NULL 的處理](/backend/01-database/sql/in-exists-join/) 建議否定式一律改用 `NOT EXISTS` 的理由）。即使回傳單一數值、形狀與預期完全一致，結果仍可能錯誤——例如訂單接上評價後直接加總金額：

```sql
SELECT SUM(訂單.金額) FROM 訂單
LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號;
-- 共用資料：800（101 是 300、102 是 500）
-- 替 101 再加一則評價之後：1100
--   101 配到兩則評價，連接後那張訂單變成兩列，300 算了兩次
```

兩次查詢都回傳一列一欄的單一數字，外觀完全正常（列數膨脹機制見 [SQL.6 連接之後的列數與空缺：列數膨脹、外連接補的 NULL 與三值邏輯](/backend/01-database/sql/join-changes-rows-and-nulls/)）。「漏掉星等」甚至在撰寫當下通過所有現有資料驗證與語法檢查，直到新資料出現才暴露差異。

## 查詢是否符合需求的檢驗方法：靜態分析、約束與反例資料

驗證查詢結果是否符合業務需求，需要一份基準答案作為比對依據。這份基準答案在提問的人手上，既不在查詢文字裡，也不在資料表裡，因此寫不出一條規則，讓程式自動判定整段查詢是否符合需求。

整體驗證雖然無法完全交給機器，但拆解後的局部檢查可依「機器在檢查當下能讀取哪些資訊」劃分責任：只讀查詢文字與表結構的檢查屬於**靜態分析**；只讀寫入當下該筆資料與既有資料列的檢查可寫成資料庫**約束**；需要業務需求作為判斷基準的驗證，則由提問者構造**反例資料**並給定預期答案，機器只負責比對查詢輸出與預期答案是否一致。

**靜態分析**只讀取查詢文字與表結構，不需任何資料列或提問者介入。「不等於五」就是靜態分析可偵測的案例：查詢使用外連接，但 `WHERE` 裡的星等條件屬於拒絕 NULL 的條件，補出來的列全數會被濾除，在任意資料集上皆等價於內連接。這項等價性由三值邏輯決定、與資料內容無關，最佳化器在規劃階段就會直接改寫（MySQL 手冊稱為 outer join simplification）。引擎改寫時不發警告，須查閱 [Query Plan（執行計畫）](/backend/01-database/sql/knowledge-cards/query-plan/) 才能發現：

```sql
-- 「不等於五」的錯法
EXPLAIN
SELECT 訂單.訂單編號 FROM 訂單
LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號
WHERE 評價.星等 <> 5;
-- 星等條件拒絕 NULL：補出來的列星等是 NULL，NULL <> 5 判成未知，全數被濾掉
-- PostgreSQL 16 印出 Hash Join：最佳化器已經把 LEFT JOIN 改成內連接
-- MySQL 8 的 SHOW WARNINGS 印出改寫後的查詢，連接寫的是 join

-- 正解
EXPLAIN
SELECT 訂單.訂單編號 FROM 訂單
LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號 AND 評價.星等 = 5
WHERE 評價.評價編號 IS NULL;
-- 星等條件在 ON 裡；WHERE 的 評價編號 IS NULL 對補出來的列判成真，補出來的列留下
-- PostgreSQL 16 印出 Hash Left Join：外連接保留下來
```

外連接被最佳化器改寫為內連接，代表查詢中的 `LEFT` 已失去作用，與保留無評價訂單的意圖矛盾。

「NOT IN」則是靜態分析可標出風險（而非確定錯誤）的案例，判斷同時依據表結構與查詢文字，同樣不需讀取資料列：

```sql
-- 表結構：評價表的訂單編號沒有宣告 NOT NULL，這一欄可能是 NULL
CREATE TABLE 評價 (評價編號 INT, 訂單編號 INT, 星等 INT);

-- 查詢文字：NOT IN 的子查詢讀的正是那一欄
SELECT 訂單編號 FROM 訂單
WHERE 訂單編號 NOT IN (SELECT 訂單編號 FROM 評價 WHERE 星等 = 5);
-- 子查詢只要交出一個 NULL，NOT IN 對每一列都判不成真，整段回零列
-- 現有資料裡沒有訂單編號未填的評價，所以這段此刻回的仍是 102
```

靜態分析無法偵測「漏掉星等」：該查詢結構與正解完全一致，只少了 `ON` 裡的星等條件，查詢文字與表結構裡沒有任何線索顯示該條件應存在。

**資料庫約束**在每次寫入資料時檢查，讀取範圍由約束種類決定：[Constraint（約束）](/backend/01-database/sql/knowledge-cards/constraint/) 裡，`NOT NULL` 與 `CHECK` 只檢查正要寫入的那一筆，`UNIQUE` 比對單欄或複合欄位的既有值，外鍵確認指向的父列存在，PostgreSQL 的 [Exclusion Constraint（排除約束）](/backend/01-database/sql/knowledge-cards/exclusion-constraint/) 另涵蓋同表非等值跨列比較（如區間不重疊）。超出這些範圍的跨表規則（例如「評價時間必須晚於出貨時間」）同樣可在寫入時驗證，但須以觸發器或應用層檢查實作。「NOT IN」的失效前提是評價表存在訂單編號為 `NULL` 的五星評價，或外層 `訂單.訂單編號` 本身出現 `NULL`；唯有外層比對欄位與子查詢欄位兩側皆宣告了 `NOT NULL`，空值資料才無法寫入，該雙側非空宣告構成可安全沿用 `NOT IN`（而不必改用 `NOT EXISTS`）的豁免前提，但並未修正撰寫者對 `NOT IN` 三值展開的誤解。「不等於五」與「漏掉星等」則無法寫成約束，因為偏差出在查詢條件未對應業務需求，而非資料列違反資料規則。外鍵擋下的寫入、宣告與生效分開的位置及對查詢的保證，詳見 [SQL.18 外鍵與參照完整性：宣告、生效與查詢得到的保證](/backend/01-database/sql/foreign-key-and-referential-integrity/)。

**反例資料**將提問者的業務判斷轉成可重複驗證的輸入與預期輸出。反例資料（取自邏輯術語 counterexample）是一筆能讓正解與錯誤寫法回傳不同結果的資料：只要兩段查詢在同一筆資料上輸出不同，即可證明兩者不等價。針對「不等於五」「漏掉星等」與「NOT IN」三種錯法，各自有一筆對應反例：「不等於五」需要訂單 101 多一則非五星評價，「漏掉星等」需要訂單 102 多一則非五星評價，「NOT IN」需要一則訂單編號為 `NULL` 的五星評價。

構造反例資料不需要事先猜出所有錯誤寫法，可從表結構與查詢條件以**等價類劃分**（equivalence partitioning）推導：依查詢對輸入的行為將資料分類，每類至少放入一筆。對應本題的等價類包含訂單配到零則評價、配到多則評價、配到的全是或部分為非五星評價，以及外鍵欄為 `NULL`。未設約束的資料表允許所有這些資料形態，而正解與錯誤寫法對這些形態的處理各異，輸出便會在等價類資料上分開。

一份涵蓋上述各等價類的測試資料，足以讓正解與三種錯法各自產出不同輸出：

```sql
-- 從建好的空表開始；101、102 與 9001 同共用資料
INSERT INTO 訂單 VALUES (101,1,'2026-03-02',300), (102,1,'2026-03-09',500),
                        (103,2,'2026-03-10',200), (104,2,'2026-03-11',400),
                        (105,3,'2026-03-12',600);
INSERT INTO 評價 VALUES
  (9001,101,5), (9002,101,3),   -- 101：配到不只一則，其中一則五星
  (9003,103,3),                 -- 103：配到的全部不是五星
  (9004,104,5),                 -- 104：只配到一則五星
  (9005,105,4), (9006,105,2),   -- 105：配到不只一則，全部不是五星
  (9007,NULL,5);                -- 訂單編號是空值的五星評價
-- 102 一則評價都配不到
-- 正解：102、103、105
-- 「不等於五」：101、103、105、105（105 配到兩則非五星評價，出現兩次）
-- 「漏掉星等」：102
-- 「NOT IN」：0 列
```

提問者仍須決定這五張訂單中哪些屬於目標結果。能構造出反例資料，表示業務需求已清楚到足以區分兩種寫法；若在表結構允許的所有資料形態上都構造不出反例，則兩種寫法完全等價。反例資料並未取代提問者的判斷，而是把該判斷固化為輸入與預期答案，機器接手的僅是比對這一步。

反例資料與約束改變的對象各不相同。約束限制資料表能寫入的資料形態，不改變查詢寫法——加上 `NOT NULL` 讓 `NOT IN` 不再回零列，僅是因為空值資料無法寫入，若撰寫者對 `NOT IN` 的誤解仍在，在另一個允許空值的欄位仍會重犯。反例資料不限制資料表，而是將需求判斷保存成可重複執行的測試案例，每次修改查詢皆可重新驗證。反例資料只能證偽、不能證成：在現有資料上通過驗證（如「漏掉星等」在共用資料上通過），不證明查詢在所有資料形態上皆正確。此外，反例資料依據提問者或測試建立者當時對需求的理解建立，因此可找出「理解正確但 SQL 寫錯」，無法找出「需求理解本身就錯誤」。

反例資料與預期答案在測試領域有更細的分工：預期答案的來源稱為 [Test Oracle](/testing/knowledge-cards/test-oracle/)（涵蓋規格、參照實作、人工判斷與現狀，以及各自抓不到的缺陷）；測試斷言與查詢實作源於同一份誤解的風險稱為 [Test Provenance（測試出處）](/testing/knowledge-cards/test-provenance/)；構造不出反例資料的等價改寫在 [Mutation Testing（突變測試）](/testing/knowledge-cards/mutation-testing/) 中稱為 equivalent mutant。

## 正確性之外：查詢的代價與由引擎、資料庫決定的事

除了結果正確性，查詢還有執行時間與掃描量這個獨立面向：查詢結果是否正確與執行速度多快互不保證，而執行代價可透過向引擎索取 [Query Plan（執行計畫）](/backend/01-database/sql/knowledge-cards/query-plan/) 直接檢視。[SQL.17 查詢的代價：資料分布、索引與寫法各自的影響](/backend/01-database/sql/cost-lives-in-the-plan/) 實測同一查詢加建索引後，最慢的寫法可縮短至與最快寫法同一量級。

本篇分析的錯誤發生在業務需求與查詢文字之間：引擎依語意模型算出了精確結果，只是該結果不符需求。除此之外，查詢的最終結果還受多項不寫在查詢文字裡的引擎與資料庫設定影響：

- **引擎寬鬆度**：各家對標準禁止寫法是否接受及回傳什麼，見 [SQL.19 引擎寬鬆度與可攜性：各家對同一組寫法的差異、分級與處理時機](/backend/01-database/sql/engine-leniency-and-portability/)。
- **識別字規則**：各家對表名與欄名的大小寫摺疊、引號與保留字處理，見 [SQL.14 識別字的規則：各家的大小寫摺疊、引號與保留字](/backend/01-database/sql/identifier-rules/)。
- **權限模型**：連線帳號被授予哪些操作權限，見 [SQL.16 SQL 的權限模型：角色、GRANT 的授權單位與最小權限](/backend/01-database/sql/privilege-model/)。
- **執行計畫與最佳化器**：書寫順序、求值順序與執行順序的分工，見 [SQL.1 宣告式的紅利與代價：書寫、求值與執行順序各自由誰決定](/backend/01-database/sql/declarative-not-procedural/)。
- **表上約束**：外鍵與參照完整性的宣告、生效與查詢保證，見 [SQL.18 外鍵與參照完整性：宣告、生效與查詢得到的保證](/backend/01-database/sql/foreign-key-and-referential-integrity/)。
- **字串比較規則**：collation 對相等、排序、`LIKE` 與索引的影響，見 [SQL.15 字串比較與 collation：相等、排序、LIKE 與索引可用性](/backend/01-database/sql/string-comparison-and-collation/)。
- **部署形態**：單一寫入者與多連線伺服器在並行寫入、連線協調與身分上的差異，見 [SQL.20 引擎的部署形態與 SQL 構造：SQLite 與 PostgreSQL 在並行寫入、連線協調與身分上的差異](/backend/01-database/sql/deployment-shape-and-sql-constructs/)。
