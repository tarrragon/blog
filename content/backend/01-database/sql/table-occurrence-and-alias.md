在 `FROM` 子句裡，表名代表該資料表在這段查詢中的一次出現，這正是同一張表能以不同別名參與自連接的基礎。本篇先說明表名、多表共用欄名與同表出現兩次時各家引擎的反應，再以訂單先後配對示範自連接條件，並歸納前後配對、同組比較與層級關係等適用情境及改用 `EXISTS`／`NOT EXISTS` 的邊界；文末整理單表別名、命名原則，以及表別名與欄位別名各自可用的子句。

在 `FROM` 子句裡，寫下的表名指的是該資料表在這段查詢中的一次出現，該名稱即為這次出現的稱呼。SQL 標準將這個概念稱為 table reference，關聯演算（relational calculus）稱為 range variable，各家引擎文件也常寫成 correlation name。同一張表因此能在同一個查詢裡出現多次、各自扮演不同角色，這正是自連接（self-join）的基礎。

當資料表只出現一次時，表名與該次出現是一對一的；當同一張表出現兩次且未取別名時，兩次出現共用同一個預設稱呼，引擎無法分辨欄位歸屬於哪一次出現，因而拒絕查詢。

各家引擎拒絕同名兩次出現的時機分為兩種。PostgreSQL 與 DuckDB 在剖析 `FROM` 階段即中止，分別回報 `table name "訂單" specified more than once` 與 `Duplicate alias "訂單" in query!`；SQLite 允許 `FROM` 通過，直到查詢引用該表欄位、無法辨別歸屬時才回報 `ambiguous column name`。由於表名本身就是預設別名，同一張表出現兩次而不另取別名，等於替兩個不同對象指定同一個名稱。

## 兩張表共用欄名時的欄位歸屬

引擎依名稱判斷每個欄位屬於哪一次出現，因此兩張不同的資料表含有同名欄位時同樣會產生歧義。在 [SQL 各篇共用的範例資料庫：一家小書店的顧客、訂單與評價表](/backend/01-database/sql/sample-bookstore-database/) 中，顧客表與訂單表都有 `顧客編號`：

```sql
SELECT 顧客編號 FROM 顧客 LEFT JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號;
-- MySQL:  ERROR 1052: Column '顧客編號' in field list is ambiguous
-- SQLite: ambiguous column name: 顧客編號
-- DuckDB: Ambiguous reference to column name "顧客編號"
```

像 `id` 這類多數資料表皆具備的欄名最常發生衝突。連接完成後，每個欄位引用都必須能明確對應到某一次出現，在欄名前加上表名或別名作為前綴即可消除歧義。自連接是這個規則的極端情形：兩次出現連表名都相同，即使加上原表名前綴仍無法區分，必須各自賦予別名。

當連接的資料表增多時，需要確認每個 `ON` 可以引用哪些已出現的表：位於該 `JOIN` 上方的表已併入左運算元而可引用，位於下方的表尚未併入。左運算元的累積方式見 [SQL.4 鏈式連接的左運算元：累積方式與外連接的保護範圍](/backend/01-database/sql/join-left-operand-accumulates/)。

## 用別名分開同一張表的兩次出現

書店的訂單表裡有兩張屬於佳穎的訂單。若要找出同一位顧客的訂單先後配對（哪一張較早、哪一張較晚），需要同時比較訂單表裡的兩筆列；逐列處理的單表查詢看不到其他列，必須讓訂單表出現兩次並以別名區分：

```sql
SELECT 早.訂單編號, 早.下單日, 晚.訂單編號, 晚.下單日
FROM 訂單 AS 早
JOIN 訂單 AS 晚 ON 早.顧客編號 = 晚.顧客編號 AND 早.下單日 < 晚.下單日;
-- 101 | 2026-03-02 | 102 | 2026-03-09
```

`早` 與 `晚` 代表訂單表的兩次出現。`ON` 條件完成兩件事：`顧客編號` 相等把配對限定在同一位顧客，`下單日` 的嚴格小於關係決定哪一次出現扮演較早的訂單、哪一次扮演較晚的訂單。

嚴格小於條件不可或缺。少了它，每張訂單會與同一位顧客的所有訂單配對（包含與自己配對，且兩張不同訂單會正反各配一次）；加上嚴格小於之後，每對不同訂單只保留一個方向，自己與自己配對的組合也因日期相等而排除。同一位顧客有三張不同日期的訂單時，每兩張各配對一次：

```sql
-- 拿掉日期的比較，只留顧客編號相同
SELECT 早.訂單編號, 晚.訂單編號
FROM 訂單 AS 早
JOIN 訂單 AS 晚 ON 早.顧客編號 = 晚.顧客編號;
-- 共用資料：101|101、101|102、102|101、102|102（兩個方向各一次，加上各自跟自己配）

-- 日期的比較放回去
SELECT 早.訂單編號, 晚.訂單編號
FROM 訂單 AS 早
JOIN 訂單 AS 晚 ON 早.顧客編號 = 晚.顧客編號 AND 早.下單日 < 晚.下單日;
-- 共用資料：101|102
-- 佳穎多一張 103（下單日 2026-03-15）之後：101|102、101|103、102|103
```

## 自連接的適用情境：前後配對、同組比較與層級關係

自連接用來表達同一批資料裡兩列之間的關係，而不是同一列裡兩個欄位的關係。逐列判斷的單表查詢在處理某一列時看不到其他列的欄位值，唯有讓表出現兩次才能同時存取兩列。

自連接涵蓋三種常見形態：**前後配對**（把同一位顧客在時間上相鄰或有先後順序的兩筆訂單擺在一起）、**同組比較**（找出金額高於同一位顧客其他訂單的紀錄），以及**層級關係**（員工表的主管欄位指向同一張表的另一列，查詢員工與其主管姓名時讓員工表分別扮演員工與主管）。

這三種形態的共同前提是要比較的兩列位於同一張表。決定是否寫成自連接的依據有兩點：第一，需求是否需要把一列與同一張表的另一列相比（不需要的屬於單表查詢）；第二，輸出是否需要帶出另一列的欄位（這個條件決定使用自連接或改用存在性判斷）。

是否輸出另一列的欄位，與 [SQL.8 IN、EXISTS 與 JOIN：列數、可取用的欄位與 NULL 的處理](/backend/01-database/sql/in-exists-join/) 的選用標準一致——自連接本質上也是 `JOIN`。僅需確認是否存在另一列符合條件、而不輸出該列欄位時，使用 `EXISTS` 或 `NOT EXISTS` 可避免多對多配對造成的列數展開；需要將兩列欄位並排輸出（例如同時列出較早與較晚的訂單編號與金額）時，則使用自連接。

使用 `EXISTS` 相對於自連接所節省的展開成本，取決於連接鍵在對側是否唯一。若連接鍵在對側具唯一性，一列最多只配到一列，兩種寫法的列數相同，選用依據回歸可讀性；若一列可能配到多列，自連接會造成列數膨脹（見 [SQL.6 連接之後的列數與空缺：列數膨脹、外連接補的 NULL 與三值邏輯](/backend/01-database/sql/join-changes-rows-and-nulls/)）。判斷連接鍵是否唯一的可靠依據是資料表的 [Constraint（約束）](/backend/01-database/sql/knowledge-cards/constraint/)，僅觀察當下資料不含重複值並無法保證未來寫入後不發生膨脹。

同組比較中常見的「找出每位顧客金額最高的訂單」屬於不需輸出另一列欄位的類型：查詢只輸出該張訂單自身的欄位，同顧客的其他訂單僅用來比較金額大小，因此寫成 `NOT EXISTS` 即可；反之，「列出每筆訂單與同顧客下一筆訂單的金額差額」需要用到另一列的金額，則需使用自連接（或視窗函數）。

以 `NOT EXISTS` 搭配大於比較實作每組最大值時，會遇到**並列最大值**與**可為空的比較欄**兩個邊界。第一，金額並列最高的多張訂單都會被保留，若只要留一筆須補上決勝條件（例如取訂單編號較小者）。第二，`NULL` 與任何數值比較都得到未知，金額為 `NULL` 的訂單永遠找不到「比它大的訂單」，因而被誤選為最大值；排除該列須在外層查詢加上 `IS NOT NULL`，寫在子查詢裡無法攔截（機制見 [SQL.6 連接之後的列數與空缺：列數膨脹、外連接補的 NULL 與三值邏輯](/backend/01-database/sql/join-changes-rows-and-nulls/)）：

```sql
-- 每位顧客金額最高的訂單：同顧客裡找不到比它大的那一張
SELECT o.訂單編號, o.金額
FROM 訂單 o
WHERE NOT EXISTS (
  SELECT 1 FROM 訂單 i
  WHERE i.顧客編號 = o.顧客編號 AND i.金額 > o.金額
);
-- 共用資料：102 | 500
-- 佳穎多一張 103（金額 500）之後：102 | 500、103 | 500（並列的兩張都留下）
-- 佳穎多一張 104（金額 NULL）之後：102 | 500、104 | NULL（NULL 那一張被選成最大）

-- 決勝的條件：金額相同時，編號較小的那一張也算「比它大」
SELECT o.訂單編號, o.金額
FROM 訂單 o
WHERE NOT EXISTS (
  SELECT 1 FROM 訂單 i
  WHERE i.顧客編號 = o.顧客編號
    AND (i.金額 > o.金額 OR (i.金額 = o.金額 AND i.訂單編號 < o.訂單編號))
);
-- 佳穎多一張 103（金額 500）之後：102 | 500

-- 排除金額是 NULL 的那一張：條件寫在外層
SELECT o.訂單編號, o.金額
FROM 訂單 o
WHERE o.金額 IS NOT NULL
  AND NOT EXISTS (
    SELECT 1 FROM 訂單 i
    WHERE i.顧客編號 = o.顧客編號 AND i.金額 > o.金額
  );
-- 佳穎多一張 104（金額 NULL）之後：102 | 500
-- 同一句改寫進子查詢（AND i.金額 IS NOT NULL）：仍回 102 | 500、104 | NULL
```

## 表只出現一次時別名的作用

當一張資料表在查詢裡只出現一次時，別名主要用來縮短欄位前綴，在連接三四張長表名資料表的查詢裡可以降低閱讀負擔。

指定別名同時會取代原本的表名。一旦寫下 `FROM 訂單 AS 早`，這次出現的唯一有效稱呼就是 `早`。後續子句若繼續引用原表名 `訂單`，各家引擎都會拒絕：PostgreSQL 回報 `invalid reference to FROM-clause entry for table "訂單"` 並提示改用別名，SQLite 回報 `no such column`，DuckDB 回報 `Referenced table "訂單" not found`。

## 別名的取名：標示這次出現扮演的角色

在自連接裡，同一張表的兩次出現扮演不同角色，別名是查詢中唯一標示這兩個角色的位置。以下以顧客的訂單先後配對為例：

```sql
SELECT 早.訂單編號, 晚.訂單編號, 晚.金額 - 早.金額
FROM 訂單 早 JOIN 訂單 晚
  ON 晚.顧客編號 = 早.顧客編號 AND 晚.下單日 > 早.下單日;
```

若把別名改成 `a` 與 `b`，查詢結果完全相同，但讀到 `b.金額 - a.金額` 時必須回頭檢視 `ON` 條件才能確認哪一個代表較晚的訂單。別名命名的判斷標準是：讀到引用欄位的那一行時，能直接從名稱辨識該次出現的角色與方向，如 `晚.金額 - 早.金額`。

引擎不驗證別名文字是否與條件方向一致。若將兩個別名與條件同時對調：

```sql
FROM 訂單 晚 JOIN 訂單 早
  ON 早.顧客編號 = 晚.顧客編號 AND 早.下單日 > 晚.下單日
```

名為 `早` 的別名實際對應到較晚的訂單，查詢照常執行並回傳與前例相同的列，但別名與角色完全相反。別名因此也是一種給閱讀者的宣告，宣告是否與實際條件一致由撰寫查詢的人負責（詳見 [SQL.21 關鍵字的宣告與引擎的行為：宣告落空的形態與查證](/backend/01-database/sql/declared-intent-vs-behaviour/)）。

## 表的別名與欄位別名各自可用的時機

`FROM` 裡的 `AS` 替資料表的一次出現命名，`SELECT` 裡的 `AS` 替輸出的欄位或運算式命名；兩者寫法相同，作用範圍與建立時機卻位於求值順序的兩端。

表的別名在 `FROM` 步驟即已建立，因此後續的 `ON`、`WHERE`、`GROUP BY`、`HAVING`、`SELECT` 與 `ORDER BY` 都能使用。欄位別名在 `SELECT` 步驟才建立，依語意模型在 `WHERE` 中無法使用。部分引擎（例如 SQLite 與 DuckDB）允許在 `WHERE` 引用欄位別名，屬於引擎寬鬆而非標準規定；[SQL.2 子句的求值順序：每一步可用的欄位、語意模型擋下的寫法與各家引擎放寬的寫法](/backend/01-database/sql/clause-evaluation-order/) 完整對照了各子句可用欄位與引擎放寬行為。
