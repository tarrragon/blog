`GROUP BY` 將每組收斂為單列，視窗函數則保留原有明細列並在旁附上同組統計值。本篇先以每位顧客的消費總額對照兩者的輸出列數與明細同列計算，建立依結果單位選用兩者的依據與子查詢篩選寫法；後半段介紹 `LAG` 與 `LEAD` 取相鄰列的語法，分析漏寫分區、漏寫距離條件與排序鍵不唯一造成的錯誤，以及 `OVER` 規格作為查詢宣告的意義。

`GROUP BY` 與視窗函數都能針對一組列算出彙總值，兩者的核心區別在於計算完畢後是否保留原本的明細列：分組把一組列收成單一列，視窗函數則保留所有原始列並將彙總值附在每一列旁邊。本篇銜接 [SQL.9 分組鍵的選擇：鍵與一組所代表的對象](/backend/01-database/sql/grouping-key-decides-the-unit/)：確定分組鍵（每組代表誰）之後，接著決定彙總結果是否要與原本的明細列並列顯示。

本篇範例在[SQL 各篇共用的範例資料庫：一家小書店的顧客、訂單與評價表](/backend/01-database/sql/sample-bookstore-database/)的訂單表額外新增兩列，讓佳穎（顧客 1，訂單 101、102，下單日 3/02、3/09）與宗翰（顧客 2）各有兩張訂單：

```sql
INSERT INTO 訂單 VALUES (105,2,'2026-03-05',200), (106,2,'2026-03-20',450);
```

## 同一個總額用分組與用視窗函數寫的輸出

計算「每位顧客的總消費」時，使用 `GROUP BY` 會把四筆訂單收成兩列：

```sql
SELECT 顧客編號, sum(金額) AS 總額 FROM 訂單 GROUP BY 顧客編號;
```

```text
1  800
2  650
```

使用視窗函數計算同一個總額時，輸出仍維持四筆訂單列，每一列附上所屬顧客的總額：

```sql
SELECT 訂單編號, 顧客編號, 金額,
       sum(金額) OVER (PARTITION BY 顧客編號) AS 該顧客總額
FROM 訂單;
```

```text
101  1  300  800
102  1  500  800
105  2  200  650
106  2  450  650
```

`PARTITION BY` 承擔與 `GROUP BY` 相同的分組劃分功能，決定每組由哪些列構成。兩者差別完全在於輸出單位：`GROUP BY` 壓縮後只剩兩列，單筆訂單的金額已無法直接呈現。

## 明細與組的值同列的計算：訂單佔該顧客消費的比例

需求為「每張訂單佔該顧客總消費的比例」時，同一列需要同時具備單筆訂單金額與顧客總額，使用視窗函數可直接計算：

```sql
SELECT 訂單編號, 金額,
       round(金額 * 100.0 / sum(金額) OVER (PARTITION BY 顧客編號), 1) AS 佔該顧客百分比
FROM 訂單;
```

```text
101  300  37.5
102  500  62.5
105  200  30.8
106  450  69.2
```

若改用 `GROUP BY` 計算同一結果，必須讀取訂單表兩次再連接起來——一次先算出每位顧客的總額，一次以明細表與總額結果連接：

```sql
SELECT 訂單.訂單編號, 訂單.金額,
       round(訂單.金額 * 100.0 / 各顧客.總額, 1) AS 佔該顧客百分比
FROM 訂單
JOIN (SELECT 顧客編號, sum(金額) AS 總額      -- 讀第一次：收成每位顧客一列總額
      FROM 訂單 GROUP BY 顧客編號) AS 各顧客
  ON 各顧客.顧客編號 = 訂單.顧客編號;         -- 讀第二次：每一張訂單接上它那位顧客的總額
-- 101 300 37.5
-- 102 500 62.5
-- 105 200 30.8
-- 106 450 69.2（與視窗函數那一段的結果相同）
```

視窗函數省去了這次額外的連接，使明細與組總計在同一層查詢中完成。這項優勢在於結構精簡，不代表視窗函數必然執行得較快；實際執行耗時取決於資料量、分組數與 [Index（索引）](/backend/01-database/sql/knowledge-cards/indexing/)，且同一句若含多個不同 `ORDER BY` 規格的視窗函數，引擎須執行多趟排序，實際成本須向引擎查閱執行計畫（有無索引造成各寫法排名對調的實測見 [SQL.17 查詢的代價：資料分布、索引與寫法各自的影響](/backend/01-database/sql/cost-lives-in-the-plan/)）。

## 選用分組或視窗函數的依據：結果集單列的代表對象

選用 `GROUP BY` 或視窗函數的依據是結果集的每一列代表什麼對象：每列代表一位顧客（組）時用 `GROUP BY`，每列代表一張訂單（明細）且附帶顧客層彙總值時用視窗函數。這項判斷與 [SQL.9 分組鍵的選擇：鍵與一組所代表的對象](/backend/01-database/sql/grouping-key-decides-the-unit/) 互補：分組鍵決定一組由哪些列構成，輸出單位決定這組是否收成單一列。

後續的篩選寫法也隨這個選擇而不同。`GROUP BY` 的聚合值可直接寫進 `HAVING` 篩選組（[SQL.2 子句的求值順序：每一步可用的欄位、語意模型擋下的寫法與各家引擎放寬的寫法](/backend/01-database/sql/clause-evaluation-order/) 說明 `HAVING` 排在分組之後的求值位置）；視窗函數的值在 `SELECT` 步驟才算出，`WHERE` 與 `HAVING` 都無法引用它。若要依視窗函數的結果篩選列，須把整段查詢包成子查詢，在外層用 `WHERE` 過濾（部分引擎提供 `QUALIFY` 子句簡化此步驟，但不在標準 SQL 中）。以下篩選出「佔顧客總消費超過五成」的訂單：

```sql
-- 直接在同一層寫 WHERE 佔該顧客百分比 > 50，SQLite 3.51 拒絕：
--   misuse of aliased window function 佔該顧客百分比
SELECT 訂單編號, 佔該顧客百分比 FROM (
  SELECT 訂單編號,
         round(金額 * 100.0 / sum(金額) OVER (PARTITION BY 顧客編號), 1) AS 佔該顧客百分比
  FROM 訂單
)                                -- 內層算完視窗函數，佔該顧客百分比成為一個普通欄位
WHERE 佔該顧客百分比 > 50;       -- 外層的 WHERE 讀得到它
-- 102 62.5
-- 106 69.2
```

## LAG 與 LEAD：取同一組裡相鄰的列

由於視窗函數保留了所有明細列，查詢可以進一步存取同一分組內的相鄰列（`GROUP BY` 收掉明細後只剩組與組之間的關係）。`LAG` 往排序前方取值，`LEAD` 往排序後方取值，相鄰次序由 `OVER` 裡的 `ORDER BY` 決定：

```sql
SELECT 訂單編號, 顧客編號, 金額,
       金額 - LAG(金額) OVER (PARTITION BY 顧客編號 ORDER BY 下單日) AS 與上一張的差額
FROM 訂單;
```

```text
101  1  300  （空）
102  1  500  200
105  2  200  （空）
106  2  450  250
```

每位顧客的第一張訂單前方沒有列，因此 `LAG` 回傳 `NULL`。比較同一組相鄰列也可用自連接實作，差別在於自連接須將兩列配對，`LAG` 則沿著排序直接往前取一列（自連接的配對展開與選用條件見 [SQL.7 表的出現與別名：表名的指稱、別名的作用範圍與自連接](/backend/01-database/sql/table-occurrence-and-alias/)）。

## 排序相鄰與需求要的相鄰：分區、排序鍵與距離條件

`LAG` 取得的是**排序相鄰**（依 `ORDER BY` 排列後緊鄰的前一列），而業務需求常要求**語意相鄰**（同一位顧客的上一筆、日曆上的前一天或上個月）。當兩者不一致時，引擎仍會正常執行並回傳錯誤數值。

移除依顧客編號分區的 `PARTITION BY` 之後，`LAG` 會沿全表的 `下單日` 跨顧客取前一列。將無分區與有分區兩個欄位並排在同段查詢裡即可對照差異：

```sql
SELECT 訂單編號, 顧客編號,
       金額 - LAG(金額) OVER (ORDER BY 下單日) AS 沒分區的差額,                       -- 沿全表的下單日往前取一列
       金額 - LAG(金額) OVER (PARTITION BY 顧客編號 ORDER BY 下單日) AS 分區後的差額   -- 只在同一位顧客之內往前取
FROM 訂單
ORDER BY 下單日;                  -- 列序照全表的下單日：3/02、3/05、3/09、3/20
```

```text
訂單  顧客  沒分區的差額   分區後的差額
101   1     （空）         （空）
105   2     -100           （空）
102   1     300            200
106   2     -50            250
```

首列以外的三列數值全部錯誤：宗翰的第一張訂單減去了佳穎的金額得出 -100，佳穎的第二張減去了宗翰的金額得出 300，而引擎未發出任何錯誤。

排序相鄰與需求相鄰的落差也會發生在時間間隔上：依 `下單日` 排序後的相鄰兩列，在日曆上可能間隔數天甚至數週。若需求明確要求比較「前一天」，因為排序只保證先後、不保證間隔為一天，必須另外計算兩列日期差並在篩選條件中限制距離：

```sql
SELECT 訂單編號 FROM (
  SELECT 訂單編號, 金額,
         LAG(金額) OVER w AS 前一筆,
         julianday(下單日) - julianday(LAG(下單日) OVER w) AS 相隔天數
  FROM 訂單 WINDOW w AS (PARTITION BY 顧客編號 ORDER BY 下單日)
)
WHERE 金額 > 前一筆 AND 相隔天數 = 1;
-- 本篇的四列訂單：零列（102 與佳穎的上一張相隔 7 天，106 與宗翰的上一張相隔 15 天）
-- 拿掉 AND 相隔天數 = 1：102、106
```

缺少距離條件時，間隔 7 天的訂單 102 與間隔 15 天的訂單 106 都會被誤判為與前一天比較。在長期的逐日資料中，偶發的缺測斷點只會多出少量錯誤比較，僅看結果筆數與外觀幾乎觀察不到異狀。

若在同一段 `SELECT` 裡同時使用聚合視窗函數（如 `sum(金額) OVER ...`）與 `LAG`，不可直接共用帶有 `ORDER BY` 的具名視窗 `WINDOW w`：依 SQL 標準，聚合視窗的 `OVER` 不帶 `ORDER BY` 時預設計算整個分區總計；一旦加上 `ORDER BY`，預設視窗框架（window frame）會切換為 `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`（含同值並列列的累計值），使顧客總額靜默變成累計值。

`OVER` 括號裡的三項條件各自承擔不同職責：`PARTITION BY` 界定不跨對象的窗邊界，`ORDER BY` 指定相鄰順序，而排序鍵在分區內唯一才能讓「前一列」有唯一指涉。排序鍵有並列值時，「前一列」沒有明確定義，同一段窗規格在不同執行計畫下可能回傳不同結果；甚至在同一段 `SELECT` 裡加上另一個排序方向不同的視窗函數，就足以讓結果翻轉：

```sql
-- 本篇的四列訂單再加一張與 102 同一天下單的 107（只在這一段成立）
INSERT INTO 訂單 VALUES (107,1,'2026-03-09',100);

SELECT 訂單編號, LAG(訂單編號) OVER (PARTITION BY 顧客編號 ORDER BY 下單日) AS 上一張
FROM 訂單;
-- 102 的上一張是 101，107 的上一張是 102

SELECT 訂單編號, LAG(訂單編號) OVER (PARTITION BY 顧客編號 ORDER BY 下單日) AS 上一張,
       row_number() OVER (ORDER BY 金額) AS 金額名次   -- 多一個按金額排序的視窗；上一張那一欄的寫法沒動
FROM 訂單;
-- 107 的上一張變成 101，102 的上一張變成 107（SQLite 3.51）
```

當排序鍵可能出現多筆合法紀錄並列時，補上決勝次鍵（例如 `ORDER BY 下單日, 訂單編號`）才能使兩段查詢都固定將 102 接在 101 之後、107 接在 102 之後；若並列源自感測器重送等重複資料，補決勝鍵只固定順序而不消除重複，須先去重再取 `LAG`。此外，`OVER (ORDER BY ...)` 裡的 `NULL` 預設排序位置同樣隨引擎而異（SQLite 預設 `NULLS FIRST`、PostgreSQL 預設 `NULLS LAST`，詳見 [SQL.11 查詢結果的列序：沒有 ORDER BY 時的來源與 ORDER BY 的規定範圍](/backend/01-database/sql/relations-have-no-order/)），排序鍵允許為空時須顯式寫出 `NULLS LAST` 或 `NULLS FIRST`，以免 `LAG` 在跨引擎環境靜默偏移。即使分區、排序鍵與排序唯一性皆已成立，只要業務需求的「相鄰」（例如相隔一天）不等同於資料列相鄰，仍須另補距離條件才能排除跨多天的配對。

## OVER 括號裡的分區與排序作為宣告

`PARTITION BY 顧客編號` 向閱讀查詢的人宣告「相鄰比較限定在同一位顧客之內」。當資料中每位顧客都恰好只有一筆紀錄時，拿掉 `PARTITION BY` 輸出不變，[SQL.21 關鍵字的宣告與引擎的行為：宣告落空的形態與查證](/backend/01-database/sql/declared-intent-vs-behaviour/) 分析了這類宣告未生效的形態。反之，漏寫分區或漏寫距離條件時，查詢照常執行且結果外觀正常，卻回傳錯誤答案，[SQL.13 查詢的合法性與答案的正確性：引擎檢查的範圍、答案錯掉的成因與查證方法](/backend/01-database/sql/well-formed-is-not-correct/) 整理了這類靜默算錯的成因與查證方法。
