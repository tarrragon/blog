撰寫連接查詢有兩種常見起手方式：先列出笛卡兒積再於 `WHERE` 過濾，或直接把配對條件寫進 `ON`。本篇先比較這兩種寫法在外連接處為何分岔，接著說明未配對列在結果中的角色如何區分內連接、外連接與半連接；後半段展示業務描述如何對應到 `ON`、連接種類與 `WHERE`，並分析只提及被保護資料表的條件為何屬於 `WHERE`。

撰寫連接時第一個要決定的事項是哪兩列應配對在一起，SQL 為此提供專屬子句 `ON`。下文沿用 [SQL.5 ON 與 WHERE：連接條件與篩選條件各自的職責](/backend/01-database/sql/on-describes-where-filters/) 的區分，以**配對**指稱資料表還在組合的過程、以**成品**指稱連接完成後得到的那批列（含外連接補上 `NULL` 的列）；兩階段的完整定義、對照表與補 `NULL` 檢驗法以 SQL.5 為主。把配對條件寫進 `ON`，配對關係會固定在連接結構中；若留在 `WHERE`，它就成了對成品的篩選。

本篇範例執行於[SQL 各篇共用的範例資料庫：一家小書店的顧客、訂單與評價表](/backend/01-database/sql/sample-bookstore-database/)：三位顧客為佳穎、宗翰、雅文，其中只有佳穎有兩張訂單（101 金額 300，102 金額 500）。

## 從全部配對縮小的起手式與關聯代數的定義

[Relational Algebra（關聯代數）](/backend/01-database/sql/knowledge-cards/relational-algebra/)把連接定義為兩個運算的組合：先計算 [Cartesian Product（笛卡兒積）](/backend/01-database/sql/knowledge-cards/cartesian-product/)，再以條件選取符合的列。直接把這個定義翻譯成 SQL 會得到以下寫法：

```sql
SELECT 顧客.姓名, 訂單.訂單編號
FROM 顧客 CROSS JOIN 訂單
WHERE 訂單.顧客編號 = 顧客.顧客編號;
```

這段寫法直觀呈現出先列出所有組合再過濾的概念，但笛卡兒積加選取是語意層的數學定義，用來界定連接的結果集合，並未規定查詢必須照此寫法展開。引擎也不會先產生完整笛卡兒積；這段查詢產出的執行計畫與 `JOIN ... ON` 逐字相同，實測見 [SQL.21 關鍵字的宣告與引擎的行為：宣告落空的形態與查證](/backend/01-database/sql/declared-intent-vs-behaviour/)。

在內連接情境下，條件寫在 `ON` 與寫在 `WHERE` 會回傳同一批列，因此從全部配對縮小的寫法在內連接裡都能正常運作。直到需求要求保留未配對的列，這個寫法的限制才會浮現。

## 從全部配對縮小與寫進 ON 在外連接處的差別

當需求要求保留配對不到對象的列時，把條件寫在 `WHERE` 與寫在 `ON` 的結果會開始分岔。以書店的需求為例：查詢每位顧客連同他 300 元以上的訂單，沒有符合條件訂單的顧客也要列出來。

沿用從全部配對縮小的寫法：

```sql
FROM 顧客 CROSS JOIN 訂單
WHERE 訂單.顧客編號 = 顧客.顧客編號 AND 訂單.金額 >= 300;
-- 佳穎 101 / 佳穎 102
```

宗翰與雅文沒有出現在名單上。外連接的機制是**保護**：讓**被保護的表**中配不到對象的列留在結果裡，另一張表（**補 `NULL` 的表**）的欄位在這些列上補上 `NULL`。因為 `CROSS JOIN` 沒有外連接形式，要保留沒有訂單的顧客，整個起手寫法就必須更換。

若只把 `CROSS JOIN` 換成 `LEFT JOIN`，而將金額條件留在 `WHERE`：

```sql
FROM 顧客 LEFT JOIN 訂單 ON 訂單.顧客編號 = 顧客.顧客編號
WHERE 訂單.金額 >= 300;
-- 佳穎 101 / 佳穎 102
```

宗翰與雅文依然不在結果裡。`LEFT JOIN` 保留下來的列右側欄位全是 `NULL`，`WHERE` 步驟會把它們全部濾掉（機制詳見 [SQL.5 ON 與 WHERE：連接條件與篩選條件各自的職責](/backend/01-database/sql/on-describes-where-filters/)）。只更換連接關鍵字無法保留這些列，條件的位置也必須移動。

將配對條件完整移進 `ON`：

```sql
FROM 顧客 LEFT JOIN 訂單
  ON 訂單.顧客編號 = 顧客.顧客編號 AND 訂單.金額 >= 300;
-- 佳穎 101 / 佳穎 102 / 宗翰 （空）/ 雅文 （空）
```

三位顧客全部出現在結果裡。從全部配對縮小是把所有條件寫在 `WHERE` 裡過濾成品，而外連接的保護正是在成品階段被 `WHERE` 抵銷；在外連接需求下，這兩種起手方式的差異不再是風格選擇，而是查詢能否產出正確結果。

## 連接種類的選擇：配不到的列在結果中的定位

確定配對條件之後，接著決定配不到對象的列如何處理，判斷依據是這些列在結果中是否需要保留。

結果需要保留未配對列時使用 [Outer Join（外連接）](/backend/01-database/sql/knowledge-cards/outer-join/)，依需要保留哪一側選擇 `LEFT`、`RIGHT` 或 `FULL`；結果不保留未配對列時使用內連接（`JOIN`）。以「找出沒有下過任何訂單的顧客」為例，答案全屬於補 `NULL` 的未配對列，改用內連接會讓結果變成空集合。

另一類需求只需確認對象是否存在，不輸出右側資料表的任何欄位。這種情況對應的運算是半連接：配對後只保留左側列，右側表只作為存在性條件，詳細定義見 [Semi-join 與 Anti-join（半連接與反連接）](/backend/01-database/sql/knowledge-cards/semi-join-and-anti-join/)。若誤寫成 `JOIN`，一筆左列配到多筆右列時結果會重複；`IN`、`EXISTS` 與 `JOIN` 在列數上的差異與選用判斷標準，見 [SQL.8 IN、EXISTS 與 JOIN：列數、可取用的欄位與 NULL 的處理](/backend/01-database/sql/in-exists-join/)。

是否保留未配對列取決於業務需求，不取決於當下的資料現況。目前訂單表裡每一列都配得到顧客，只代表此刻沒有孤兒列，無法保證未來的資料維持同樣狀態。反過來說，若資料庫約束已保證配對必然存在，仍寫成 `LEFT JOIN` 會誤導後續維護者以為存在未配對列（見 [SQL.21 關鍵字的宣告與引擎的行為：宣告落空的形態與查證](/backend/01-database/sql/declared-intent-vs-behaviour/)）。判斷配對是否有保證，依據的是表上的 [Constraint（約束）](/backend/01-database/sql/knowledge-cards/constraint/)，且須確認該約束實際生效（見 [SQL.18 外鍵與參照完整性：宣告、生效與查詢得到的保證](/backend/01-database/sql/foreign-key-and-referential-integrity/)）。

## 業務描述對應到查詢的位置：ON、連接種類與 WHERE

將業務描述轉譯成外連接查詢時，描述裡的各段條件分別落在配對資格、連接種類與成品篩選三個獨立位置。以「除了雅文以外的每位顧客，連同他 300 元以上的訂單，沒有這種訂單的顧客也要列出來」為例，這句描述恰好覆蓋三個位置：

**配對條件（`ON`）承載兩表如何對應的資格。** 顧客列與訂單列以顧客編號對應，且只與金額 300 元以上的訂單配對。「只與 300 元以上的訂單配對」界定的是配對資格，因此整段條件歸入 `ON`。

**連接種類（`JOIN` 關鍵字）承載未配對列是否保留。** 「沒有這種訂單的顧客也要列出來」要求保護顧客這張表，對應的運算即是以顧客為左側的 `LEFT JOIN`。兩張表相連時左右即決定保護方向；三張表以上時，每一個連接的左運算元是前方所有連接累積的結果，在鏈中間使用 `RIGHT JOIN` 會捨棄前段保護的列（[SQL.4 鏈式連接的左運算元：累積方式與外連接的保護範圍](/backend/01-database/sql/join-left-operand-accumulates/) 以三表實測展示這項累積機制）。

**成品篩選（`WHERE`）承載連接完成後的過濾條件。** 「除了雅文以外」限制的是最終名單裡的顧客集合，屬於對成品的篩選，因此寫進 `WHERE 顧客.姓名 <> '雅文'`。反之，若業務描述未對顧客本身或最終成品設限（例如涵蓋全部三位顧客），省略 `WHERE` 才是對應的結果。

將這個對應反過來，也能用來檢查既有查詢：檢視 `WHERE` 裡引用右表欄位的條件，確認它描述的是配對或成品；描述配對的條件若寫在 `WHERE` 會抵銷外連接保護。`WHERE 右表.某欄 IS NULL` 則是相反的形態：它挑選的正是外連接補 `NULL` 的列，描述的是成品，寫在 `WHERE` 才正確（完整對照表見 [SQL.5 ON 與 WHERE：連接條件與篩選條件各自的職責](/backend/01-database/sql/on-describes-where-filters/)，孤兒訂單的查詢實例見 [SQL.21 關鍵字的宣告與引擎的行為：宣告落空的形態與查證](/backend/01-database/sql/declared-intent-vs-behaviour/)）。

## 只提到被保護的表的條件該放的位置

條件涉及哪一張表，會直接改變它屬於 `ON` 或 `WHERE`。以訂單與評價為例，需求是「每張訂單與它的評價，只保留三月五日以後下的單」，被保護的表是訂單，而日期限制只提及訂單。若將日期條件寫進 `ON`：

```sql
SELECT 訂單.訂單編號, 訂單.下單日, 評價.星等
FROM 訂單 LEFT JOIN 評價
  ON 評價.訂單編號 = 訂單.訂單編號 AND 訂單.下單日 >= '2026-03-05';
-- 101  2026-03-02  （空）
-- 102  2026-03-09  （空）
```

三月二日的訂單 101 仍然出現在結果中，因為 `LEFT JOIN` 強制保留左表所有列，`ON` 只影響右表是否配對成功。把日期條件寫進 `ON` 沒能濾掉訂單 101，反而讓原本配得上的五星評價判成假而變成 `NULL`。將日期條件改放 `WHERE` 才會得到目標結果：

```sql
SELECT 訂單.訂單編號, 訂單.下單日, 評價.星等
FROM 訂單 LEFT JOIN 評價 ON 評價.訂單編號 = 訂單.訂單編號
WHERE 訂單.下單日 >= '2026-03-05';
-- 102  2026-03-09  （空）
```

外連接的保護機制保證左表每一列都會留在成品中，因此要篩除左表列時，只提及被保護資料表的條件寫進 `ON` 無法縮減左表列數，反而會拆散原本成立的配對；這類條件須放在作用於成品的 `WHERE` 階段（唯有需求刻意要求「保留全部左表列，但只替符合條件的左表列帶出右表資料」時，該條件才屬於 `ON`）。當條件涉及兩張表或提及補 `NULL` 的右表時，判斷依據回到 [SQL.5 ON 與 WHERE：連接條件與篩選條件各自的職責](/backend/01-database/sql/on-describes-where-filters/) 的配對／成品分界與補 `NULL` 列代入檢驗法。在自連接寫成外連接時，同樣的機制一樣成立：自連接指同一張表在查詢裡出現兩次、各自扮演不同角色（例如較早的訂單與較晚的訂單），針對被保護那一次出現的過濾條件若寫進 `ON`，同樣無法濾掉該側的列，命名規則與形態見 [SQL.7 表的出現與別名：表名的指稱、別名的作用範圍與自連接](/backend/01-database/sql/table-occurrence-and-alias/)。

因此，省略 `WHERE` 並非寫連接時應刻意追求的目標。「每位顧客與他 300 元以上的訂單」這段查詢沒有 `WHERE`，是因為業務需求本身未對成品設限；把只提及被保護資料表的條件硬塞進 `ON`，只會造成該排除的列沒被濾掉，還破壞原本成立的配對。
