本篇以「哪幾天氣溫比前一天高」這句業務需求，連續走完 [SQL.0 一段查詢從需求到上線的決定：追問需求、設定判斷標準、選寫法、補前提、量代價、對邊界與交付](/backend/01-database/sql/decisions-from-requirement-to-shipping/) 列出的全部決定：

- 追問模糊需求並定案為可驗收規格，建立含缺測的驗收資料。
- 對照自連接、視窗函數與相關子查詢三種寫法各自依賴的資料前提，並以漏掉相隔天數與漏掉分區的錯誤版本驗證預設判斷標準。
- 在放大資料集上實測日期差自連接、等值自連接、視窗函數與相關子查詢於有無索引下的耗時與執行計畫（含加上索引反而變慢的案例）。
- 盤點同日重複、時區、補登與測站搬家等邊界情形，並交代上線前的異動偵測、資料量成長、跨引擎改寫及外部工程接點。

這句業務描述距離可上線的查詢還隔著多項關鍵決定，且這些決定的答案不在資料庫結構裡，也不在 SQL 語法裡。本篇所有範例建於專屬的氣溫資料表（不沿用[SQL 各篇共用的範例資料庫：一家小書店的顧客、訂單與評價表](/backend/01-database/sql/sample-bookstore-database/)），以涵蓋缺測與多測站情境；本篇實測輸出於 SQLite 3.51.0 取得，跨引擎對照處另標明引擎版本。

## 寫查詢之前的追問：結果的用途、「前一天」的定義、缺測與測站數

撰寫任何 SQL 之前未先釐清以下定義，會直接讓後續查詢結構與效能預算建立在猜測上：

**結果的下游用途。** 這份結果是要驅動即時告警、產出每日報表圖表，還是作為模型特徵。用途決定執行頻率（一次性查詢、每日排程或每次載入頁面觸發），執行頻率決定可容忍的耗時預算，進而決定後續量測表要採納哪一種寫法。

**「前一天」的定義。** 指的是日曆上的前一天，或是資料集裡依時間排序的前一筆紀錄。資料完全無缺漏時兩者答案相同，開發用的乾淨小資料分不出差別，唯有缺測出現時兩者才會分岔。

**缺測日的處理方式。** 遇到缺少前一天紀錄時，可跳過不計、標示為資料斷點，或以前後數值內插補值，三種定義各自對應完全不同的查詢。

**測站數量。** 只有單一測站時整張表是一條時間序列；有多個測站時，「前一天」必須限定在同一測站之內，漏掉這項限定時引擎不會報錯。

這些追問的答案必須向提出需求的人確認。若跳過追問直接動筆，撰寫者容易隱性套用預設假設——把查詢當成一次性執行、把「前一天」寫成資料上的前一筆、忽略缺測並假設只有單一測站。

## 可驗收的需求敘述與帶缺測的驗收資料

本篇將這四項追問定案如下：查詢用於每日執行一次的排程報表、「前一天」指日曆上的前一天、缺測前一天時跳過不算，且資料涵蓋多個測站。這組決定可收斂為一句可驗收的規格：

> 對每一個測站，找出所有「同測站、日期剛好早一天」的觀測存在，且當日氣溫高於該筆觀測的紀錄。

給定一份刻意加入缺測的測試資料，即可逐筆推算出正確答案：

```sql
-- 各節的表名重複，照順序跑要先清掉上一節的（SQLite 的 DROP 一次只收一張表）
DROP TABLE IF EXISTS 氣溫;
CREATE TABLE 氣溫 (
  紀錄編號 INTEGER PRIMARY KEY,
  測站     TEXT,
  觀測日   TEXT,
  攝氏     INT
);

-- 台北的 3/05 缺測（感測器當天離線），其餘每天一筆
INSERT INTO 氣溫 (測站, 觀測日, 攝氏) VALUES
 ('台北','2026-03-01',18),('台北','2026-03-02',22),('台北','2026-03-03',20),
 ('台北','2026-03-04',15),                          ('台北','2026-03-06',25),
 ('台北','2026-03-07',24),
 ('高雄','2026-03-01',26),('高雄','2026-03-02',25),('高雄','2026-03-03',28),
 ('高雄','2026-03-04',27),('高雄','2026-03-05',29),('高雄','2026-03-06',30),
 ('高雄','2026-03-07',28);
```

依規格逐筆核對，正確答案只有四筆：

```text
台北  2026-03-02    22 > 18
高雄  2026-03-03    28 > 25
高雄  2026-03-05    29 > 27
高雄  2026-03-06    30 > 29
```

台北的 3/06（25 度）不在答案裡，因為日曆上的前一天 3/05 沒有觀測紀錄。這筆紀錄是整份驗收資料的關鍵檢核點：任何回傳台北 3/06 的查詢皆違反上述規格。

## 自連接、視窗函數與相關子查詢各自依賴的前提

**自連接**讓氣溫表出現兩次，分別以別名 `今` 與 `昨` 標示角色（同表別名與自連接規則見 [SQL.7 表的出現與別名：表名的指稱、別名的作用範圍與自連接](/backend/01-database/sql/table-occurrence-and-alias/)）：

```sql
SELECT 今.測站, 今.觀測日
FROM 氣溫 今
JOIN 氣溫 昨
  ON 昨.測站 = 今.測站                                  -- 限定在同一個測站之內
 AND 昨.觀測日 = date(今.觀測日, '-1 day')              -- 「前一天」是日曆上的前一天
WHERE 今.攝氏 > 昨.攝氏
ORDER BY 今.測站, 今.觀測日;
```

`date(今.觀測日, '-1 day')` 是 SQLite 的日期函式，將日期字串往前推一天。同一張表出現兩次時，所有欄位引用皆須加上別名前綴，否則引擎會報 `ambiguous column name: 測站`。

**視窗函數**依分區與日期排序後以 `LAG` 往前取一列（`LAG` 分區與距離條件推導見 [SQL.10 分組與視窗函數：各自的產出、選用的依據與 LAG、LEAD 的相鄰列](/backend/01-database/sql/window-keeps-rows-grouping-collapses/)）：

```sql
SELECT 測站, 觀測日 FROM (
  SELECT 測站, 觀測日, 攝氏,
         LAG(攝氏)   OVER w AS 前溫,
         julianday(觀測日) - julianday(LAG(觀測日) OVER w) AS 相隔
  FROM 氣溫
  WINDOW w AS (PARTITION BY 測站 ORDER BY 觀測日)
)
WHERE 攝氏 > 前溫 AND 相隔 = 1
ORDER BY 測站, 觀測日;
```

`WINDOW w AS (...)` 讓兩個 `LAG` 共用同一視窗定義，`julianday()` 將日期轉成可相減的天數。`相隔 = 1` 不可或缺：`LAG` 回傳的是排序相鄰的前一列，而非日曆上的前一天，兩者只在無缺測時相等。

**相關子查詢**對外層每一列查詢同測站前一天的攝氏氣溫（純量相關子查詢的求值次數見 [Subquery（子查詢）](/backend/01-database/sql/knowledge-cards/subquery/)，存在性查詢與相關子查詢辨識見 [SQL.8 IN、EXISTS 與 JOIN：列數、可取用的欄位與 NULL 的處理](/backend/01-database/sql/in-exists-join/)）：

```sql
SELECT 測站, 觀測日
FROM 氣溫 今
WHERE 攝氏 > (SELECT 攝氏 FROM 氣溫 昨
              WHERE 昨.測站 = 今.測站
                AND 昨.觀測日 = date(今.觀測日, '-1 day'))
ORDER BY 測站, 觀測日;
```

當前一天缺測時，純量子查詢回傳零列並轉為 `NULL`；數值與 `NULL` 比較的真值為未知，`WHERE` 因此排除該列（三值邏輯見 [SQL.6 連接之後的列數與空缺：列數膨脹、外連接補的 NULL 與三值邏輯](/backend/01-database/sql/join-changes-rows-and-nulls/)）。台北 3/06 正是透過這項隱性比較規則被排除。

三段查詢在驗收資料上都回傳相同的四筆紀錄：

```text
台北  2026-03-02
高雄  2026-03-03
高雄  2026-03-05
高雄  2026-03-06
```

然而三種寫法各自依賴不同的前提，破壞時表現各異。自連接依賴同測站同日僅有一筆紀錄，出現重複時一列配多列導致結果膨脹（見 [SQL.6 連接之後的列數與空缺：列數膨脹、外連接補的 NULL 與三值邏輯](/backend/01-database/sql/join-changes-rows-and-nulls/)）。視窗函數依賴分區內排序鍵唯一，並列時「前一列」未定義（見 [SQL.12 分頁的排序鍵與接續標記：同分的列、全序與 OFFSET 的代價](/backend/01-database/sql/pagination-needs-a-total-order/)）。相關子查詢依賴純量子查詢至多回傳一列，回傳多列時 PostgreSQL 18 報錯 `more than one row returned by a subquery used as an expression`，SQLite 3.51.0 則靜默取其中一列繼續計算（屬跨引擎寬鬆度差異，見 [SQL.19 引擎寬鬆度與可攜性：各家對同一組寫法的差異、分級與處理時機](/backend/01-database/sql/engine-leniency-and-portability/)）。

這三項前提歸結為同一個資料表 [Constraint（約束）](/backend/01-database/sql/knowledge-cards/constraint/)：`(測站, 觀測日)` 是否唯一。查詢文字本身無法查證該約束是否已宣告並生效——查唯一約束可在 PostgreSQL／MySQL 查 `information_schema.table_constraints`（`constraint_type = 'UNIQUE'`）、在 SQLite 查 `PRAGMA index_list`，而約束宣告與生效分離的查證思路（以外鍵為例）見 [SQL.18 外鍵與參照完整性：宣告、生效與查詢得到的保證](/backend/01-database/sql/foreign-key-and-referential-integrity/)，建表設計取捨見 [1.16 Schema 設計決定的查詢代價：可空性、排序鍵唯一性、表寬、一對多的切法、比較規則、外鍵執法，以及從另一張表取值時的複製與引用](/backend/01-database/design-decisions-price-every-query/)。

## 漏掉相隔天數與漏掉分區的錯誤版本

視窗函數版本裡的 `相隔 = 1` 與 `PARTITION BY 測站` 漏掉任一項時，引擎都不會報錯。

**漏掉相隔天數**的版本：

```sql
SELECT 測站, 觀測日 FROM (
  SELECT 測站, 觀測日, 攝氏,
         LAG(攝氏) OVER (PARTITION BY 測站 ORDER BY 觀測日) AS 前溫
  FROM 氣溫
) WHERE 攝氏 > 前溫;
```

```text
台北  2026-03-02
台北  2026-03-06      ← 多出來的
高雄  2026-03-03
高雄  2026-03-05
高雄  2026-03-06
```

結果多出台北 3/06：查詢跨過缺測的 3/05，直接拿 3/04 的 15 度與 3/06 的 25 度比較，且輸出不留缺測痕跡。

**漏掉分區**的版本（保留距離條件）：

```sql
SELECT 測站, 觀測日 FROM (
  SELECT 測站, 觀測日, 攝氏,
         LAG(攝氏)   OVER (ORDER BY 觀測日) AS 前溫,
         julianday(觀測日) - julianday(LAG(觀測日) OVER (ORDER BY 觀測日)) AS 相隔
  FROM 氣溫
) WHERE 攝氏 > 前溫 AND 相隔 = 1;
```

```text
高雄  2026-03-05
```

結果只剩一筆、少了三筆。未分區時，`ORDER BY 觀測日` 把同日的台北與高雄排在一起，兩者次序未定義。SQLite 在這份資料將台北排在高雄之前：除高雄 3/05 之外，高雄各列的前一列是同日台北（相隔天數為 0 而被濾除）；台北 3/02 起各列的前一列是前一日高雄（相隔天數為 1，但高雄皆比台北暖而落選）；唯獨高雄 3/05 因台北缺測，前一列剛好落回高雄 3/04 而倖存。

若將同日兩測站的次序固定並正反各測一次，錯誤方向會隨之改變：

```sql
-- 漏掉分區的查詢，窗的排序鍵補上測站，把同一天兩個測站的先後寫死
SELECT 測站, 觀測日 FROM (
  SELECT 測站, 觀測日, 攝氏,
         LAG(攝氏)   OVER w AS 前溫,
         julianday(觀測日) - julianday(LAG(觀測日) OVER w) AS 相隔
  FROM 氣溫
  WINDOW w AS (ORDER BY 觀測日, 測站)          -- 同一天台北排在高雄前面
) WHERE 攝氏 > 前溫 AND 相隔 = 1
ORDER BY 測站, 觀測日;
-- ORDER BY 觀測日, 測站：      高雄 3/05，一筆（與不寫死次序時 SQLite 回的相同）
-- ORDER BY 觀測日, 測站 DESC： 高雄 3/02、3/03、3/04、3/05、3/06、3/07，六筆
--   高雄 3/02、3/04、3/07 的前一列是台北前一天，比的是台北的氣溫：多報
--   台北 3/02 的前一列是高雄同一天，相隔天數是零：少報
```

| 版本                | 回傳筆數 | 錯誤方向                                             |
| ------------------- | -------- | ---------------------------------------------------- |
| 正確版本            | 4        | —                                                    |
| 漏掉相隔天數        | 5        | 多報                                                 |
| 漏掉 `PARTITION BY` | 1 或 6   | 取決於同日兩測站排序先後：少報，或多報與少報同時發生 |

兩個錯誤版本皆不報錯且欄位格式正常；其中少報特別難察覺，因為輸出外觀只像「那幾天沒有升溫」。分辨這類錯誤仰賴寫查詢前就定好的驗收答案：漏掉相隔天數會觸犯「台北 3/06 不應出現」，漏掉分區則須逐筆比對四筆預期答案才現形。驗收資料與預期結果必須在寫 SQL 之前定案，避免寫完後無意間挑出讓錯誤版本通過的測試資料。

## 代價：日期差自連接、等值自連接、視窗函數與相關子查詢的實測

確認各寫法輸出正確後，進一步在放大資料集上對有無 [Index（索引）](/backend/01-database/sql/knowledge-cards/indexing/) 兩種狀態量測執行代價（原則見 [SQL.17 查詢的代價：資料分布、索引與寫法各自的影響](/backend/01-database/sql/cost-lives-in-the-plan/)）。建立二十個測站、兩年、每隔九十七天缺測一天的資料表（共 14460 列）：

```sql
-- 各節的表名重複，照順序跑要先清掉上一節的（SQLite 的 DROP 一次只收一張表）
DROP TABLE IF EXISTS 氣溫;
CREATE TABLE 氣溫 (紀錄編號 INTEGER PRIMARY KEY, 測站 TEXT, 觀測日 TEXT, 攝氏 INT);

-- d 產生 0 到 729 的天數位移，s 產生 1 到 20 的測站編號
-- (i+j) % 97 <> 0 這個條件讓每個測站隔一段時間缺一天
WITH RECURSIVE d(i) AS (SELECT 0 UNION ALL SELECT i+1 FROM d WHERE i < 729),
               s(j) AS (SELECT 1 UNION ALL SELECT j+1 FROM s WHERE j < 20)
INSERT INTO 氣溫 (測站, 觀測日, 攝氏)
SELECT '站'||j, date('2024-01-01', i||' day'), 10 + (i*7+j*13) % 25
FROM s, d WHERE (i+j) % 97 <> 0;
```

自連接拆成「日期差自連接」與「等值自連接」兩種條件形狀分別量測：

```sql
-- 以下是同一段自連接的 ON 子句，兩種寫法只差這一行，其餘逐字相同。
-- 這個區塊是片段，不能單獨執行——完整的自連接查詢在〈自連接、視窗函數與相關子查詢各自依賴的前提〉那一節。

-- 日期差自連接：等號兩邊的欄位都包進函式，算日期差
ON 昨.測站 = 今.測站 AND julianday(今.觀測日) - julianday(昨.觀測日) = 1

-- 等值自連接：等值比較，函式只作用在「今」那一側，「昨」那一側是索引上找得到的值
ON 昨.測站 = 今.測站 AND 昨.觀測日 = date(今.觀測日, '-1 day')
```

量測對象為日期差自連接、等值自連接、視窗函數與相關子查詢的 `count(*)` 版本（省略 `ORDER BY` 以隔離排序成本），分別在未建索引與建立 `ix_站日` 索引後實測：

```sql
CREATE INDEX ix_站日 ON 氣溫(測站, 觀測日);

-- 拿掉它再量「沒有索引」那一欄：
-- DROP INDEX ix_站日;
```

計畫透過在查詢前加上 `EXPLAIN QUERY PLAN` 取得：

```sql
EXPLAIN QUERY PLAN
SELECT count(*) FROM 氣溫 今 JOIN 氣溫 昨
  ON 昨.測站 = 今.測站 AND julianday(今.觀測日) - julianday(昨.觀測日) = 1
WHERE 今.攝氏 > 昨.攝氏;
```

每種寫法於同一 Python 行程內以 `sqlite3` 搭配 `time.perf_counter()` 各跑三次取最小值（避開 CLI 行程啟動常數稀釋倍數）；針對加索引反而變慢的日期差自連接，另執行一輪七次重複量測排除離群值：

| 寫法         | 沒有索引 | 有 `(測站, 觀測日)` 索引 | 答案  |
| ------------ | -------- | ------------------------ | ----- |
| 日期差自連接 | 739 ms   | **1045 ms**              | 10297 |
| 等值自連接   | 10 ms    | 6 ms                     | 10297 |
| 視窗函數     | 13 ms    | 12 ms                    | 10297 |
| 相關子查詢   | 3971 ms  | 8 ms                     | 10297 |

四段查詢的筆數皆為 10297，但耗時橫跨三個量級，以下逐項分析原因。

**日期差自連接與等值自連接因條件形狀相差逾七十倍。** 將 `julianday(今.觀測日) - julianday(昨.觀測日) = 1` 改為 `昨.觀測日 = date(今.觀測日, '-1 day')` 後，無索引耗時從 739 毫秒降至 10 毫秒。日期差寫法把兩側的 `觀測日` 都包進函式，引擎無法以索引查找；等值寫法只對 `今.觀測日` 套用函式，引擎可在 `昨` 的索引上直接定位算好的目標日期（見 [Sargable（可走索引的條件形狀）](/backend/01-database/sql/knowledge-cards/sargable/)）。在小量開發資料上兩者皆為 0 毫秒，唯有放大資料量才顯現差異。

**日期差自連接加上索引後反而變慢。** 耗時由 739 毫秒升至 1045 毫秒；七次重複量測範圍完全不重疊（735–780 毫秒對上 955–1252 毫秒），確認並非量測雜訊。對照執行計畫即可查出成因：

```text
沒有索引    SCAN 今
            SEARCH 昨 USING AUTOMATIC COVERING INDEX (測站=?)

有索引      SCAN 今
            SEARCH 昨 USING INDEX ix_站日 (測站=?)
```

未建索引時，SQLite 當場替這段查詢建立含所需欄位的臨時覆蓋索引，內層不須回主表讀取（回表）；手動建立 `ix_站日` 後，SQLite 改用僅含 `(測站, 觀測日)`、不含 `攝氏` 的手動索引，導致內層每筆配對都多一次回表讀取 `攝氏`。手動建立的索引反而不如引擎臨時建的覆蓋索引——這項反直覺結果只能從執行計畫查出，無法靠閱讀查詢文字推論。

**相關子查詢在建立索引後加速約五百倍。** 耗時由 3971 毫秒降至 8 毫秒，原因在內層存取路徑從全表掃描轉為複合索引查找：

```text
沒有索引    SCAN 今
            CORRELATED SCALAR SUBQUERY 1
              SCAN 昨                                            ← 「今」的每一列都把「昨」整張掃一遍

有索引      SCAN 今
            CORRELATED SCALAR SUBQUERY 1
              SEARCH 昨 USING INDEX ix_站日 (測站=? AND 觀測日=?)   ← 「今」的每一列在索引上查一次
```

逐列執行的結構未變，改變的是單次查找成本。在本題內層依唯一鍵至多查找一列的結構下，慢源自內層查詢缺少對應索引；若內層須對同鍵多列重複聚合，即使已有索引仍會隨每組列數呈平方退化（實測見 [SQL.22 可讀性與執行代價：兩者一致與分岔的情形](/backend/01-database/sql/readable-and-fast-mostly-align/)）。

**視窗函數在有無索引下耗時相近（13 毫秒對 12 毫秒），但執行計畫已消去排序步驟**：

```text
沒有索引    SCAN 氣溫
            USE TEMP B-TREE FOR ORDER BY       ← 先把整張表排成 PARTITION BY 測站 ORDER BY 觀測日 的順序

有索引      SCAN 氣溫 USING INDEX ix_站日       ← 沿索引讀出來就是這個順序，排序那一行消失
```

索引直接提供視窗需要的排序次序，在此資料量下省下的排序時間尚未拉開顯著差距。

回到本題設定的下游用途：查詢屬於每日執行一次的排程報表，四種寫法的耗時皆在可接受範圍內，應優先挑選最易維護的寫法；若用途改為每次開頁面即時查詢，日期差自連接近一秒的延遲就會直接成為使用者等待時間。

## 需求沒說而資料會有的情形：同日重複、時區、補登與測站搬家

氣溫查詢的規格涵蓋了缺測，但在長期運行的正式系統中，還有四類需求未明說的資料形態會導致查詢靜默出錯。

**同測站同日多筆紀錄。** 感測器重送、補登或設備切換期間兩套系統並寫，會打破 `(測站, 觀測日)` 唯一的前提。三種寫法在此呈現三種不同失誤：自連接產生多對多膨脹；視窗函數因同日排序未定義而使「前一列」不定；相關子查詢在 PostgreSQL 報錯、在 SQLite 靜默挑一列往下算。在 SQLite 上三種寫法皆不報錯。業務端須定義多筆衝突時以何者為準，並以 `UNIQUE (測站, 觀測日)` 將唯一性前移至寫入階段強制執行。

**時區定義。** 跨時區測站各自存入當地日期時，「前一天」在單站合理但跨站不可直接對齊；統一轉存 UTC 日期時，單一測站的當地「一天」則會被切開。這類邊界在單一時區的開發環境不會浮現。

**延遲補登改變歷史結果。** 若台北 3/05 的觀測在三個月後補寫進資料表，重跑同一段查詢時歷史結果會改變，且新結果完全符合規格：

```sql
-- 回到〈可驗收的需求敘述與帶缺測的驗收資料〉那份 13 列氣溫表，台北 3/05 補登為 12 度
INSERT INTO 氣溫 (測站, 觀測日, 攝氏) VALUES ('台北','2026-03-05',12);

-- 〈自連接、視窗函數與相關子查詢各自依賴的前提〉那一節的自連接，原樣再跑一次
SELECT 今.測站, 今.觀測日
FROM 氣溫 今
JOIN 氣溫 昨
  ON 昨.測站 = 今.測站
 AND 昨.觀測日 = date(今.觀測日, '-1 day')
WHERE 今.攝氏 > 昨.攝氏
ORDER BY 今.測站, 今.觀測日;
-- 補登之前：四筆
-- 補登 12 度之後：五筆，多出台北 2026-03-06（25 > 12），它現在有前一天了
-- 補登的是 17 度的話：六筆，台北 2026-03-05（17 > 15）也被選中
```

若系統會持久化保存歷史報表，須事先決定報表呈現的是「目前資料庫的最新回算結果」還是「報表產出當下的快照」，兩者對應不同的儲存設計。

**測站搬家。** 同一個 `測站` 代號在某日後改指另一個實體地點時，`PARTITION BY 測站` 會把搬家前後拼成同一條序列，使搬家隔日比較的是兩個不同地點的氣溫。這屬於識別碼語意隨時間漂移的資料建模議題，無法單靠查詢本身察覺。

這四類邊界情形都不會觸發資料庫報錯，查詢仍會回傳外觀完全正常的結果集（見 [SQL.13 查詢的合法性與答案的正確性：引擎檢查的範圍、答案錯掉的成因與查證方法](/backend/01-database/sql/well-formed-is-not-correct/)）。

## 上線之前的決定：答案變動的偵測、資料量成長與換引擎

完成規格、寫法、前提、代價與邊界確認後，交付上線前還須處理三項寫在查詢文字之外的維運變因：資料變動、資料量成長與引擎方言。

**歷史結果變動時是否需要偵測。** 面對如台北 3/05 延遲補登造成的結果變動，是否建立異動偵測機制取決於下游用途：驅動告警的管線須追蹤歷史重算差異，單純呈現趨勢的月報則未必需要。

**資料量成長與索引變動後須重新檢查執行計畫。** 〈代價：日期差自連接、等值自連接、視窗函數與相關子查詢的實測〉的基準是 14460 列；當資料放大一個以上量級，各寫法的耗時差距可能因排序溢出磁碟或工作集超過快取而重新排列。每次資料量大幅成長或增刪索引後，都應再次向引擎查詢計畫——日期差自連接已證明新增索引可能導致效能倒退。

**更換資料庫引擎須改寫日期函式與視窗語法。** 本篇四段查詢皆使用了 SQLite 特有的 `date(x, '-1 day')` 或 `julianday()`。遷移至 PostgreSQL 時，因 `觀測日` 宣告為 `TEXT`，須轉型寫成 `CAST(觀測日 AS DATE) - 1`（直接寫 `觀測日 - INTERVAL '1 day'` 會回報 `operator does not exist: text - interval`）；遷移至 MySQL 則改寫成 `DATE_SUB(觀測日, INTERVAL 1 DAY)`。此外，具名視窗 `WINDOW w AS (...)` 的支援度也隨引擎版本而異。這類語法差異會在首次執行即報錯，屬於最易察覺的「當場報錯」級別；其餘不報錯的跨引擎差異分級整理在 [SQL.19 引擎寬鬆度與可攜性：各家對同一組寫法的差異、分級與處理時機](/backend/01-database/sql/engine-leniency-and-portability/)。

## 查詢之外的接點：schema 設計、計畫工具與查詢預算

這套從需求到上線的流程在三個位置銜接至查詢語言之外的工程領域。

**Schema 設計**：選寫法與補前提共同依賴 `(測站, 觀測日)` 的唯一性，這屬於建表時的結構決定。可空性、表寬、分表方式、collation、外鍵執法與複製或引用等建表決定都會影響後續查詢的正確性與成本，逐項實測見 [1.16 Schema 設計決定的查詢代價：可空性、排序鍵唯一性、表寬、一對多的切法、比較規則、外鍵執法，以及從另一張表取值時的複製與引用](/backend/01-database/design-decisions-price-every-query/)。

**執行計畫工具**：本篇示範的計畫只有數行，正式系統的執行計畫包含多層巢狀節點與估計列數，需要區分「統計估算偏差」與「實際運算緩慢」。`EXPLAIN`、`EXPLAIN ANALYZE` 與 `auto_explain` 的分工及選錯計畫的實務案例，見 [PostgreSQL Query Optimization：EXPLAIN、auto_explain、pg_hint_plan 與 planner 選錯 plan 的 production case](/backend/01-database/vendors/postgresql/query-optimization/)。

**應用層查詢預算**（單一請求容許執行的查詢次數上限）：追問需求確認了單段查詢的觸發頻率，而單一請求內觸發幾段查詢則受應用層查詢預算約束，兩者相乘才是資料庫承擔的實際負載，完整盤點整理在 [1.13 應用層查詢反模式與 Query 預算](/backend/01-database/query-anti-patterns/)。

換成另一個業務需求時，從追問需求到交付的決定框架維持不變，但追問出的定義與資料邊界會隨領域而異，因此這套流程的重點是逐項追問而非套用固定清單。
