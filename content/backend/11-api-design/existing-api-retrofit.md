本模組各章的判定序預設讀者站在決定還沒下過的位置：選版本方案、選錯誤格式、選分頁機制、設計冪等條款。實際會來讀這些章節的人多半站在另一個位置——契約已經上線、當初的決定是別人下的或根本沒人下過、消費者改不改得動不是自己說了算、而回答判定序需要的觀測資料還沒有。判定序在這個位置上仍然告訴你「應該選什麼」，卻不告訴你「已經在那裡的那個怎麼辦」。本章收的是後者：已經暴露出去的性質怎麼收回來、幾件事同時要做時的順序、以及哪些東西其實不必收。

## 已暴露的性質分成三類，收法完全不同

改造的第一步是把「想改的東西」分類，因為三類的成本差一到兩個量級，而混在同一份計畫裡會讓最貴的那類拖垮全部。

| 類別       | 性質                                     | 例子                                            | 收法                                   |
| ---------- | ---------------------------------------- | ----------------------------------------------- | -------------------------------------- |
| 加法可解   | 新行為可以跟舊行為並存，消費者不動也沒事 | 新增 cursor 參數、新增冪等 header、新增錯誤欄位 | 直接加，舊的照原樣留著                 |
| 需要載具   | 新舊行為互斥，要有一個切換點             | status 從恆定 200 改回真實值、錯誤格式換 schema | 掛在版本切片上釋出，舊切片維持現狀     |
| 只能等或斷 | 消費者不改就不可能生效                   | 移除欄位、收緊驗證、cursor 從透明改不透明       | 通知加窗口，窗口結束後接受一部分會斷掉 |

第一類的比例比多數人預期的高，而它常被誤放進第二類。分頁從 offset 換 cursor 是最典型的例子：`?page=` 照原樣留著、新增一個 `?cursor=` 參數，兩套並存，新整合方用新的、舊整合方繼續用舊的直到它們自然消失。以為要「換掉分頁」的人會去規劃一次版本升級，而實際要做的只是加一個參數。判斷方法很直接：新行為需不需要舊行為讓位。不需要的話它就是加法。

第二類的關鍵是**不要為它另開載具**。已經有版本機制時，這些變更掛在新的版本切片上；沒有版本機制時，新端點是最常見的載具，而那實際上是在做一次迷你版本化——既然要做，不如順便把版本機制本身建起來，因為第二類的變更不會只有一次。

第三類要先接受一件事：完成率不會到百分之百，而上限由消費者的可協調度決定（列不列得出名單、發不發得出通知、握不握有 SDK、有沒有強制力四項，見 [Consumer Coordinability](/backend/knowledge-cards/consumer-coordinability/)）。可做的是把「會斷的那些」從未知變成已知——退場前的觀測窗口告訴你還剩誰、而通知鏈的三種工具（公告、in-band warning、brownout）各自觸達不同的人（[11.5 的 deprecation 工具箱](/backend/11-api-design/versioning-and-deprecation/) 有完整展開）。把它排到最後做，是因為前兩類做完之後，第三類的清單通常會短很多。

## 收緊不透明性這類「應該從第一版就做」的性質

各章都有一些判準寫成「從第一版就要成立」，讀起來像是錯過就永久失去。多數情況下它們的實際語意是「從**這個介面元素**的第一版」，而新增一個介面元素隨時可以做。

cursor 的不透明性是最清楚的一個。既有 API 給的是 `?page=3`，透明且已被依賴；而收緊的做法不是把 `page` 變成不透明（那是第三類、且沒有必要），是新增 `?cursor=` 這個從它自己的第一版就 opaque 的參數。舊參數照第三類處理或乾脆永久留著。同樣的邏輯適用於錯誤格式的演化條款——「未知欄位請忽略」這句話晚寫確實不保護已經發出去的欄位，但它從寫下的那天起保護所有之後新增的，而那才是它的主要價值。

真正無法補救的只有一類：**已經被消費者依賴、且你不知道被誰依賴的隱性性質**。錯誤訊息的文字內容、ID 的長度與格式、欄位在 JSON 裡的順序、恆定 200 的解析假設——這些從來沒有被宣告成契約，而消費者依賴了。它們無法用「新增一個元素」繞過，因為消費者依賴的正是既有元素的行為。這一類的處理只有兩條路：靠版本切片切開，或接受它已經是契約的一部分並明文承認它（Stripe 把「opaque ID 的長度格式可能改變」寫進相容變更清單，正是在做這件事——把一個隱性性質變成明文的不承諾）。

## 順序：先建證據、再止血、最後動最貴的

幾件事同時要做時，順序由兩件事決定：哪個是別人的輸入、哪個最貴且最不可逆。

**第一，先建 per-consumer 與 per-parameter 的用量觀測。** 它是其餘每一步的輸入——分頁要看真實流量翻多深、版本退場要列得出收件人、錯誤格式要知道誰依賴恆定 200、冪等要看衝突集中在誰身上。先做它的另一個理由是它不動契約，因此不需要跟任何消費者協調，可以立刻開工（做法見 [11.12 API 消費者用量觀測](/backend/11-api-design/consumer-usage-observability/)）。

**第二，用不需要消費者改動的手段止血。** 正在流血的問題通常是重複寫入或效能，而這兩類多半有服務端單方面可做的解：重複寫入用 natural key 加唯一約束擋在資料庫層（不必等消費者送冪等 header，見 [Idempotency key 標準化之爭](/backend/11-api-design/idempotency-key-standardization-debate/) 的前置閘門段）、深頁掃描先用覆蓋索引與 deferred join 把常數壓下來再談換機制。這一步的價值在於它把時間買回來——後面幾步都需要跨組織協調，而客訴每天都在發生。

**第三，錯誤格式與 status 語意。** 它排在分頁與版本之前的理由是後兩者的執行都會產生新的錯誤情境（分頁參數失效、版本不支援），而錯誤格式先定下來，後面兩步才不必各自發明一次。

**第四，分頁。** 多數是加法（新增 cursor 參數），因此不需要等版本機制，也不需要跨組織協調。

**第五，版本策略最後重決。** 它最貴、最不可逆、且它的判定序需要前四步的產出當輸入——消費者清單來自第一步、當前的錯誤與分頁契約來自第三與第四步。先決定版本機制再回頭改這些，等於用一個沒有輸入的判斷鎖死後面所有選項。

這個順序有一個例外要明講：正在發生的資料正確性事故排在所有事情之前，包含第一步。觀測是為了做對決定，而資料正在錯的時候，先止血再說。

## 判讀訊號

| 訊號                                   | 判讀                                                           |
| -------------------------------------- | -------------------------------------------------------------- |
| 改造計畫的第一項是「升級到 v2」        | 順序顛倒，版本是最貴且需要別人輸入的一步                       |
| 一份計畫裡混了三類性質、共用同一個時程 | 只能等或斷的那類會拖垮加法可解的那類                           |
| 為單一變更另開端點，而已有版本機制     | 載具重複，之後會有兩套並行的變更管道                           |
| 討論停在「當初就該這樣設計」           | 把可補救的（新增元素）跟不可補救的（隱性依賴）混為一談         |
| 每一步都要等消費者配合                 | 沒有先盤點哪些是服務端單方面做得到的，止血的時間被協調成本吃掉 |
| 觀測還沒建、卻已經在討論退場日期       | 退場計畫沒有收件人，日期是猜的                                 |

前兩列指向同一個修法：分類先於排程。後兩列指向的是同一個順序錯誤的兩個症狀——把需要輸入的決定排在產生輸入的動作之前。
