對外契約的每一個變更決定，最後都會停在同一種問題上：誰還在用這個東西、用多少、停掉會傷到誰。舊版能不能下線、恆定 200 能不能改回真實 status、分頁能不能換機制、冪等條款能不能收緊——判準本身在各章都給得出來，而執行這些判準需要的證據，全部來自同一層能力：對消費者的用量觀測。缺這一層時，設計判準會退化成問了也答不出來的問題，變更決定只好靠「應該沒人在用吧」推進。本章寫這層能力該有多細、身分怎麼認、以及它的成本邊界；埋點機制、cardinality 控制與保留階梯的操作面在 [4.7 Cardinality 與成本治理](/backend/04-observability/cardinality-cost-governance/)。

## 各種契約決策要答的問題不同

觀測要建到什麼粒度，由手上待決的契約問題反推，而不同決定要的證據形狀差很多。

| 待決的契約決定               | 要答的問題                                     | 需要的觀測維度                     |
| ---------------------------- | ---------------------------------------------- | ---------------------------------- |
| 舊版本或 deprecated 欄位下線 | 還有誰在呼叫、量在衰減還是持平                 | 消費者身分 × 版本 × 欄位、時間序列 |
| 錯誤格式改回真實 status      | 恆定 200 被哪些消費者的解析邏輯依賴            | 消費者身分 × 端點 × 錯誤回應       |
| 分頁換定位機制               | 真實流量翻到多深、誰在用頁碼與總數             | 端點 × 分頁參數的分布              |
| 冪等條款收緊                 | 同 key 衝突率、replay 率、重送集中在哪些消費者 | 消費者身分 × 冪等鍵事件            |

第一列的難度最高，也最常缺。版本退場需要的不是「舊版總呼叫量」這個聚合數字，而是可以逐一點名的清單——因為退場的執行動作是通知，而通知要有收件人。只有總量時能做的判斷僅止於「還很多」或「幾乎沒有了」，而「幾乎沒有了」正是最危險的一格：長尾的絕對量小、卻可能是那三個佔營收四成的客戶。

第二列與第三列的共同點是它們問的是**參數與回應的形狀**而非呼叫次數。「誰依賴恆定 200」在 server 端其實觀察不到——server 看得到自己回了什麼，看不到 client 怎麼解讀。實務上能拿到的替代證據是間接的：改版前先在文件與 changelog 預告、觀察誰來反映，或在新端點回真實 status 並比較兩邊的錯誤處理行為。這一列的教訓是有些問題天生沒有直接觀測答案，設計時要認出它們，才不會把「量不到」誤讀成「沒有人依賴」。

第四列相對容易，因為冪等事件本來就經過服務端的去重邏輯，加一個計數維度的成本很低。它值得單獨埋的理由是衝突率會直接告訴你消費者的重試行為長什麼樣——衝突集中在少數幾個消費者時，問題通常在那幾家的退避策略而非你的條款。

## 消費者身分是這層觀測的第一個設計決定

「消費者」在觀測上要對應到一個穩定的識別符，而候選欄位各有各的破口。

API key 或 OAuth client_id 是最穩的一組：它由你發放、可歸屬到一個組織、且輪替時你知道換的是同一個對象。代價是要在發放時就把它跟組織綁好，事後從一堆裸 key 反推誰是誰，通常補不回來。token 的 subject 適合終端使用者維度，但一個整合方的 token 可能有成千上萬個 subject，拿它當消費者維度會直接把 cardinality 撐爆。User-Agent 是免費的、也是最不可靠的——它由呼叫端自己填，SDK 升級會改、自己寫 client 的人多半留空。IP 只在單一部署的整合方成立，一過雲端 NAT 就失去意義。

務實的做法是分兩層：**歸屬層**用發放時就綁定組織的識別符（key 或 client_id），承擔「這是誰」；**診斷層**才用 User-Agent 與版本字串，承擔「他用什麼在打」。兩層分開之後，前者可以要求準確，後者允許髒。

轉售與嵌入通路會讓這個模型出現一個必須明講的斷點：你發的 key 給了轉售商，而真正在用的是它底下的終端客戶。這時候「誰在用」有兩個答案，而版本退場要通知的是前者、事故影響評估要算的是後者。契約上能做的是要求轉售方在請求裡帶一個下游識別符（多數平台以自訂 header 承擔），而它的準確性由對方保證——這是委託而非觀測，設計時要標明這一格的證據強度比自己發的 key 低一階。

## 欄位級用量問不問得出來，取決於介面有沒有宣告機制

「還有誰在用這個欄位」這個問題的可答性，跟 API 風格綁得很死，而這件事在選風格時多半沒有被算進去。

消費者顯式宣告要哪些欄位的介面（GraphQL 的 query、支援 sparse fieldsets 的 REST）天然帶著這一層：每次請求就是一份宣告，欄位級用量是解析請求就得到的副產品。這是 GraphQL 的 versionless 路線能夠成立的隱藏支柱——只加不改的紀律要能執行，得先答得出「這個 deprecated 欄位上週有誰呼叫」，而它的介面剛好免費給了這個答案（該路線的完整代價見 [版本策略流派之爭](/backend/11-api-design/versioning-strategy-debate/)）。

固定回應形狀的 REST 端點沒有這一層。server 回了整個物件，消費者用了哪幾格完全在對方的程式碼裡。能做的替代是三種，強度遞減：在端點層做決定（把欄位退場升級成端點版本退場，粒度變粗但可觀測）、要求消費者宣告（引入 sparse fieldsets，這本身是一次介面變更）、或接受用不可觀測的方式退場（預告加 brownout，用短暫的真實故障觸達沒讀公告的人）。第三種在 [11.5 的 deprecation 工具箱](/backend/11-api-design/versioning-and-deprecation/) 有完整展開，這裡的重點是：它之所以必要，正是因為欄位級觀測在這個風格下拿不到。

風格選型時因此多一條判準：這個 API 的欄位預期會不會退場。答案是會、且消費者無法一次改完時，宣告式介面在退場成本上有結構性優勢，而這條在 [11.2 風格選型](/backend/11-api-design/api-style-selection/) 的判準軸裡屬於演進成本那一欄的細項。

## Cardinality 的帳與抽樣退路

per-consumer × per-field 是乘積，而乘積會爆。兩百個消費者乘上三百個欄位就是六萬條時間序列，再乘上版本與端點維度之後，這層觀測的成本會超過它服務的那些決定。

分層是唯一實務的解，分界畫在「這個維度是拿來做決定還是拿來查問題」。**做決定的維度全量、粗粒度**：消費者身分 × 版本 × 端點的呼叫計數要全量且長保留，因為退場決策要看幾個月的衰減曲線，而抽樣過的長尾會消失——長尾正是退場風險所在。**查問題的維度抽樣、短保留**：欄位級用量與請求參數分布可以抽樣，因為它回答的是「大致的形狀」而非「有沒有人」。

有一個例外要明講：欄位退場的決定本身需要的是「有沒有人」，抽樣在這裡會給出錯誤的安全感。做法是把它從持續觀測改成**取樣窗口**——決定要退場某個欄位時，開一段全量觀測窗口（一到兩週，涵蓋週期性的批次呼叫），窗口結束後關掉。用時間換空間，比長期維持全量欄位級觀測便宜好幾個量級。

cardinality 的控制手段、sampling 策略與保留階梯的完整操作面在 [4.7](/backend/04-observability/cardinality-cost-governance/)；本章只負責界定「哪些維度值得付這筆錢」。

## 判讀訊號

| 訊號                                       | 判讀                                                     |
| ------------------------------------------ | -------------------------------------------------------- |
| 退場決策的討論停在「應該沒什麼人在用了吧」 | 沒有消費者身分維度，決定建立在感覺上                     |
| 有總量、但列不出呼叫方名單                 | 觀測建在聚合層，通知這個動作沒有收件人                   |
| 每次要查「誰在用 X」都要臨時撈 log         | 這層能力還是專案而非設施，下次決定又要重來一次           |
| deprecated 欄位標了很久、沒有一個真的移除  | 缺欄位級證據，標注因此只能累積                           |
| 事故當下算不出影響哪些客戶                 | 歸屬層識別符沒跟組織綁定，或只有 User-Agent 這類自填欄位 |
| 觀測成本被質疑、而說不出它服務哪些決定     | 維度是照著「能埋就埋」長出來的，沒有從待決的契約問題反推 |

前四列指向同一個修法：先列出未來一年要做的契約決定，再從那份清單反推維度，而不是先埋再想用途。最後一列是這個順序被顛倒過來的直接症狀——說得出「這個維度服務哪個決定」的觀測，成本討論會很短。
