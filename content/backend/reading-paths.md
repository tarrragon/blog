這篇整理 Backend 教材各模組之間的閱讀順序：教材分成哪幾層、依讀者手上的目的各走哪一條路線，以及一條把各模組串起來的 checkout 流程。範圍是模組之間的順序，每個模組內部的章節順序在該模組的列表頁。

## 教材分三層：分類語言、服務路徑、具體工具

Backend 教材把後端服務能力分成三層來教。**分類語言**讓讀者知道資料、快取、事件、觀測、部署、驗證、資安、事故與容量各自承擔什麼責任；**服務路徑**用一條具體業務流程，演練這些能力之間怎麼交接；**具體工具**討論 PostgreSQL、Redis、Kafka、Kubernetes、PagerDuty、k6 這些服務落到真實操作時的能力、成本與遷移。

| 層       | 回答的問題                       | 從哪裡讀起                                                                                                                                                   |
| -------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 分類語言 | 這是哪一類問題                   | [後端服務選型模組](/backend/00-service-selection/)與[前置知識卡片](/backend/knowledge-cards/)                                                                |
| 服務路徑 | 一個服務流程怎麼把多個能力接起來 | 資料庫到容量規劃各模組的主章，加上本篇下方的 checkout 流程                                                                                                   |
| 具體工具 | 要選哪個工具、怎麼遷移           | 各模組的 `vendors/` 子目錄；案例庫在[資安與資料保護模組](/backend/07-security-data-protection/)與[效能工程與容量規劃模組](/backend/09-performance-capacity/) |

三層的順序是理解的順序：分類語言先建立，服務路徑才有詞彙可以描述交接，具體工具的比較才有一個分類責任可以回扣。已經懂分類、只想比較工具的讀者可以直接從具體工具那一層進來，遇到工具頁回扣分類責任的段落時，再回到分類語言那一層補那一類的定義。

## 一條 checkout 流程把各模組串起來

各模組可以獨立閱讀，而讀者需要一個共同的場景，才看得出某一章處理的是整個服務的哪一段。Backend 教材用一條簡化的 checkout 流程當這個場景：使用者建立訂單、付款服務回應、商品或價格資料被快取、事件送到下游的通知與報表、服務上線時產出觀測與驗證證據、事故發生時留下決策紀錄並回寫改善。

這條流程在演進中會遇到下面這些問題，每一個問題需要好幾個模組一起處理：

| 問題                             | 一起處理的模組                         | 產物                                        |
| -------------------------------- | -------------------------------------- | ------------------------------------------- |
| 訂單表新增付款狀態欄位           | 資料庫、可觀測性、事故處理             | 遷移計畫、驗證查詢、出事時的決策路徑        |
| 商品價格快取失效，回源流量要保護 | 快取、可觀測性、可靠性驗證             | 快取證據、origin protection gate、預熱計畫  |
| 訂單事件的 consumer 失敗，要重播 | 訊息佇列、可靠性驗證、事故處理         | 冪等證據、死信佇列的處理方式、重播 runbook  |
| Checkout 服務發版                | 部署平台、可觀測性、事故處理           | 發版計畫、canary 證據、drain 訊號、回滾條件 |
| 付款供應商的逾時設定變更         | 可靠性驗證、可觀測性、效能與容量       | release gate、SLO 證據、容量基準            |
| Webhook 的 secret 輪替           | 資安與資料保護、可觀測性、事故處理     | 影響範圍圖、稽核證據、回滾視窗              |
| 限時搶購的高峰準備               | 效能與容量、快取、訊息佇列、可靠性驗證 | 負載模型、飽和證據、佇列與快取的容量 gate   |

讀到資料庫模組時，它處理的是訂單表欄位演進那一段；讀到訊息佇列模組時，它處理的是訂單事件在程序之間的交接；讀到事故處理模組時，它收斂的是欄位演進、事件重播、發版與 secret 輪替這幾個問題出事之後的決策與回寫。
