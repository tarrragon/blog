這篇以 [Backend 範例系統](/backend/case-systems/) 裡的售票搶購為例，沿著一張票從使用者打開座位圖到付款記帳的路徑，逐段寫三件事：負載超過容量時這一段先耗盡什麼資源、前一段的保護把負載轉到了哪裡、這一段出錯時由哪一段補救。最後寫售票的需求讓哪些做法可以簡化、哪些需求怎麼設計都要付出成本。每一段的機制在連過去的專章裡，這一篇處理它們之間的交接。票數、請求量、持鎖時間這類規模數字是範例系統的假設；軟體的預設值取自官方文件，案例的內容取自站內的案例頁。對照的系統是 [9.0.2 交易撮合的負載路徑](/backend/09-performance-capacity/matching-engine-load-path/)，兩篇在相對應的位置（入口、排隊或拒絕、一次一筆的處理、下游的輸出）做出不同的設計。

## 售票的需求與它對負載的含意

售票系統的負載設計從兩個可以利用的性質與一項無法讓步的需求出發。**成功請求數有上限**：成功的購票數不會超過票數，一個場次五千張票、十萬人搶、每人限購一張時，票賣完那一刻，其餘九萬五千個購票請求的結果已經確定是售完（直到付款期限到期、有票被放回為止），回應它們不必讀資料庫，拒絕它們也不會少賣任何一張票。**使用者接受排隊**：搶票的人預期要等，等候幾分鐘、看得到自己的位置，比按下去之後沒有反應好得多。**不超賣，而且付款與放回不能同時成立**：同一張票不能賣給兩個人，付款成功的訂單一定有票，付款期限到期放回的票不能同時被付款。

兩個性質各自帶來一種做法：成功請求數有上限，結果已確定的請求可以提早回應；使用者接受排隊，還沒輪到的請求可以排隊延後處理。無法讓步的需求則決定了負載最後集中的位置：不論前面擋掉多少請求，扣庫存與訂單狀態的改變都要在某一個地方一次只處理一筆，這個位置下文稱**核心**（範例系統那一篇對四個系統都用這個名字）。

## 全部請求直接寫資料庫時先耗盡的資源

沒有任何保護時，每一個購票請求都在資料庫執行 `UPDATE events SET remaining = remaining - 1 WHERE id = $1 AND remaining > 0`。十萬個請求更新的是同一列，資料庫對這一列加的行鎖一次只讓一個交易持有，其餘的交易排隊等鎖。持有鎖的時間是交易從更新到提交的時間，提交時要把交易日誌寫到磁碟，所以這一列每秒能完成的更新數，由單一交易持有鎖的時間決定，不會因為連線池加大或伺服器加多而提高，等鎖的交易越多反而越低（MySQL 的文件寫到，大量執行緒等同一把鎖時，InnoDB 的死鎖偵測本身就會拖慢處理）：假設一筆交易持有鎖 1 毫秒，這一列每秒最多完成一千筆更新，十萬個請求要排一百秒。這種同一列被大量更新而排隊的情形叫熱點列（hot row），排隊的機制見 [1.18 高頻計數的寫入與彙總](/backend/01-database/high-frequency-counting/) 的〈熱點列：同一列更新的排隊機制〉，分散寫入的做法在同一篇的〈把寫入分開的三種做法：拆成多列、只新增事件、先在記憶體裡合併〉；以庫存計數當熱點列的例子見 [1.1 高併發下的 SQL 讀寫邊界](/backend/01-database/high-concurrency-access/) 的〈Hot Row / Lock Contention 識別與處理〉。

等鎖的每一個交易都佔著一條資料庫連線。在穩定的系統裡，同時被佔用的連線數等於請求到達率乘上每條連線被佔用的時間（[Little's Law](/backend/knowledge-cards/little-law/)），所以佔用時間變長，需要的連線數就跟著變多；到達率高於完成率時系統已經不穩定，差額直接累積在等待中：每秒進來一萬個扣庫存的請求（示意）而每秒只完成一千個，等待中的請求每秒增加九千，任何大小的連線池都會在幾秒內用完。連線池用完之後，新的請求在應用程式端等連線，查場次、看座位圖這些與扣庫存無關的請求也用同一個連線池，跟著等。從外面看是整個網站停止回應，而連線池耗盡只是症狀，原因是每條連線被佔用的時間因為等鎖而變長。把連線池加大不會改善，只會讓更多交易排在同一把鎖後面；讓扣庫存與其他請求用不同的連線池（[Bulkhead](/backend/knowledge-cards/bulkhead/)），至少讓查場次的請求不受影響。

這些等待最後變成哪一種結果，取決於每一層等待（行鎖、連線池、呼叫方的逾時）是否設有上限、上限多長。MySQL InnoDB 的行鎖等待預設 50 秒後逾時（逾時時只回滾當下那一句，不是整個交易），PostgreSQL 的 `lock_timeout` 預設不設上限；應用程式端等連線的時間由連線池的設定決定。等待的上限短於呼叫方（入口、瀏覽器）的逾時時，到期變成請求失敗；上限長於呼叫方的逾時、或根本沒有上限時，呼叫方先放棄，使用者看到的是無回應。同一個預設值在不同的入口後面落在不同的結果：InnoDB 預設的 50 秒比 Nginx 預設的 `proxy_read_timeout`（60 秒）短，請求會先收到資料庫的錯誤；比 CloudFront 回源的回應逾時預設值（30 秒）長，CDN 會先放棄。使用者在這時重新整理，同一個人送出第二、第三個請求，進來的請求率因此高於真實的需求，這是 [Retry Storm](/backend/knowledge-cards/retry-storm/)，它可以讓服務在開賣的人潮退去之後仍然停在失效狀態。各種結果的判斷標準與成因見 [9.16 負載超過容量時服務的表現](/backend/09-performance-capacity/overload-outcomes/) 的〈變慢之後走向哪一種結果：先耗盡的資源與等待是否設有上限〉。

所以售票系統的設計方向是讓抵達核心的請求數，接近真正可能買到票的人數。下面各段從使用者那一端往資料庫走，每一段擋下或延後某一類請求（可以由快取回應的讀取、刷票腳本、還沒輪到的購票、確定買不到的購票），而被擋下的請求並沒有消失，改由那一段的元件承受。

## 邊緣：可以快取的內容與機器人過濾

座位圖頁面上的內容依變動的頻率分開處理。場館平面圖、票價、場次資訊在開賣期間不變，CDN 可以快取一整天；各區的剩餘數量每秒都在變。剩餘數量讀到幾秒前的值是可以接受的，因為最後判斷有沒有票的是扣庫存那一步：使用者看到某區還有票、按下去才知道剛賣完，結果是一次多餘的點擊，不是超賣。所以剩餘數量也能交給 CDN，只是快取時間設得短（示意：一秒）。

快取時間短的時候要確認一件事：快取過期的那一刻，同時在讀的使用者會不會全部回源。CDN 的每個節點各自快取，快取過期時，一個節點上同時要這個頁面的請求，若每一個都送回源站，源站會在同一刻收到大量請求（[Cache Stampede](/backend/knowledge-cards/cache-stampede/)）。多數 CDN 能把同一個快取鍵同時發生的回源請求合併成一個（request coalescing，CDN 的文件也稱為 request collapsing，應用程式內的同一種做法見 [Singleflight](/backend/knowledge-cards/singleflight/)），前提是剩餘數量的回應不依 cookie 或登入身分分開快取，所有人共用同一個快取鍵；符合這個前提時，源站每秒收到的剩餘數量請求約等於 CDN 節點數乘以每秒的過期次數，與在線人數無關。源站這一端回應剩餘數量時，讀的是下文扣庫存那一段放在記憶體裡的計數，不是資料庫的那一列；這樣邊緣快取失效時，回源的請求落在記憶體，不會又回到熱點列。快取期限怎麼計算見 [12.2 新鮮度期限的計算](/backend/12-http-caching/freshness-lifetime/)，過期之後的回源驗證見 [12.3 過期副本的驗證](/backend/12-http-caching/revalidation/)。

刷票腳本與已知的惡意來源在邊緣以 WAF 的規則與依來源的速率限制擋下，擋掉的請求不消耗源站的任何資源。代價是誤判：同一個公司或校園網路後面的真實使用者共用一個對外位址，依位址的限制會把他們一起擋掉。被擋掉的比例依活動而定，沒有可以通用的數字，要從過去場次的紀錄估計。邊緣出錯時的補救在源站：WAF 規則被繞過、或 CDN 本身故障而改為直連源站時，源站仍要有自己的准入控制，不能假設進來的請求都已經過濾過。

## 准入：排隊與放行的速率

排隊把「什麼時候處理」與「什麼時候進來」分開。站內的兩個案例是兩種形式：[9.C16 SeatGeek](/backend/09-performance-capacity/cases/seatgeek-virtual-waiting-room/) 的虛擬等候室在使用者進入購票頁之前就讓他排隊，依預設的速率放行，或以同時在購票頁裡的人數為上限；[9.C15 拓元](/backend/09-performance-capacity/cases/tixcraft-ticketing-flash-sale-spike/) 依架構圖推論，是把訂單先寫進可以大幅擴充的儲存，後端用自己處理得了的速度消費。兩種形式給使用者的回應不同：等候室可以在等候頁顯示使用者的位置（SeatGeek 的原文沒寫它的等候頁顯示什麼）；寫入緩衝回應的是「已收到」，使用者可能以為已經下單，而他的請求還在等處理。

放行的速率要在業務期望的售完時間與扣庫存那一段的處理量之間取一個數字：放得太慢，票在開賣後很久才賣完；放得太快，放進來的請求超過扣庫存那一段每秒處理得了的量，請求在扣庫存那一段排隊，〈全部請求直接寫資料庫時先耗盡的資源〉的情形換到 Redis 上重演。這個數字要以扣庫存那一段實測的處理量為準，見 [9.4 Saturation Discovery](/backend/09-performance-capacity/saturation-discovery/)。

排隊的元件自己也承受負載，而且承受的形式與資料庫不同。排隊中的使用者每隔幾秒查一次自己的位置，十萬人每五秒查一次，就是每秒兩萬個查詢，這些查詢從資料庫被轉到了排隊服務。設計上要讓這個查詢便宜：位置資訊放在記憶體或邊緣、由伺服器在回應裡指定下一次查詢的間隔，或者改用伺服器推送；改用推送時，等候中的每一條連線都是要規劃的容量單位。SeatGeek 的等候室為每個連上 API Gateway 的訪客記一筆連線資料，等候人數本身就是要規劃的容量（原文沒寫連線協定）。

成功請求數有上限這個性質，在這一段可以直接利用。排隊的人數遠超過剩餘票數時，排在後面的人幾乎不可能買到，系統可以提早告訴他們「排在您前面的人數已超過剩餘票數」，讓他們選擇離開或改排候補，佇列因此不必容納十萬人，只需要容納剩餘票數加上一段預留給中途放棄的人；每人限購多張時，這個容量要以票數除以每人平均購買的張數估算。付款期限到期放回的票，由候補的人依序遞補，這也是前面那些人在售完時仍可能等到票的原因。等候室的兩種放行方式（依速率放行或限制同時在購票頁的人數）見 [9.15 無預警瞬時大流量](/backend/09-performance-capacity/unplanned-traffic-surge/) 的〈准入控制：虛擬等候室（virtual waiting room）、waitlist 與事前註冊〉，那一節也寫到發出的進入資格總數可以等於可售票數；等候人數與連線的容量見 9.C16 的〈判讀〉。

用訊息佇列當緩衝時（API 收到請求就回「排隊中」，請求放進佇列由後端消費），要處理同一筆購票被處理兩次的情形。訊息佇列在消費端以確認（ack）模式使用時保證的是至少送達一次，消費端處理到一半當機、佇列重送時，同一筆購票會再執行一次。每一次購票嘗試在進入佇列之前要有一個識別碼（[Idempotency Key](/backend/knowledge-cards/idempotency-key/)），扣庫存那一段以它辨認重送，同一個識別碼只扣一次。使用者自己重新整理產生的是新的購票嘗試，佇列分不出來，所以「一個帳號同時只能有一筆購票在排隊」要寫成業務規則，在進入佇列時檢查。佇列的送達語意與消費端的去重見 [3.4 consumer 設計與去重](/backend/03-message-queue/consumer-design/)。

排隊服務停掉時，系統要停止放行，而不是把所有人直接放進來。直接放行等於拿掉了這一段的保護，全部請求回到扣庫存與資料庫，也就是〈全部請求直接寫資料庫時先耗盡的資源〉那種情形；停止放行時，使用者看到的是暫停售票，票還在，排隊服務恢復之後照順序繼續。保護元件故障時是停止放行（fail closed）還是全部放行（fail open），依這個元件保護的是什麼而定：售票的排隊保護的是一個一定處理不了全部請求的資源，所以選停止放行。

## 扣庫存：把一次一筆的處理移到記憶體

扣庫存要一次只處理一筆，而這件事可以從資料庫移到記憶體。Redis 以單一執行緒依序執行指令，一段 Lua 腳本把「讀剩餘數量、大於零就減一」兩個動作放在同一次執行裡，執行期間不會有其他指令插進來，所以兩個請求不會同時讀到「剩一張」。它仍然是一次一筆，只是每一筆不需要寫磁碟、不需要鎖的協定，每秒處理的數量比資料庫的一列高出許多。Redis 原子操作的種類與分散式鎖的限制見 [2.1 高併發下的 Redis 讀寫邊界](/backend/02-cache-redis/high-concurrency-access/)。

負載移到 Redis 之後，Redis 有自己先耗盡的資源。**連線數**：Redis 的 `maxclients` 預設是一萬，同時連到 Redis 的連線數是所有應用程式主機上同時在處理請求的程序或執行緒數，乘上每個各開幾條連線。PHP-FPM 這類每個請求佔一個 worker 的執行環境，連線數的上限是全部主機的 worker 總數（每台的 `pm.max_children` 乘以主機數），開賣前為了接住流量把主機擴到幾十台時，總數可能超過一萬。改用持久連線（phpredis 的 `pconnect`）讓每個 worker 長期保留一條連線，省下的是每次請求的握手，連線數不會變少，閒置的 worker 也佔著一條；要讓連到 Redis 的連線數少於 worker 數，要在中間放一層連線代理（例如 twemproxy 或 Envoy 的 Redis proxy），由它以少數連線轉送。沒有持久連線時，每次新開連線還要付 TCP 握手的成本，用完的連線在主動關閉的那一端（通常是應用程式這一端）停留在 TIME_WAIT 狀態，佔住本機的連接埠。**單一鍵的處理量**：所有人扣的是同一個鍵，而一個鍵只存在 Redis 叢集的一個分片上，加分片不會提高這個鍵的處理量，這是 [Hot Key](/backend/knowledge-cards/hot-key/)。**腳本執行時間**：Lua 腳本執行時 Redis 不處理任何其他指令，腳本跑超過 `busy-reply-threshold`（預設 5 秒）之後，其他用戶端的指令收到的是 `BUSY` 錯誤，腳本本身並不會被終止，而已經執行過寫入的腳本也不能以 `SCRIPT KILL` 停下；所以腳本要短，不在裡面做大範圍的查詢或迴圈。

單一鍵的處理量不夠時，可以把庫存拆成多個鍵：五千張票拆成十個各五百張的鍵，每個請求挑一個鍵扣。代價是有的鍵扣完了、別的鍵還有票，請求要換一個鍵再試，最後幾張票的分配因此比較慢。對號入座的場次每個座位各是一個鍵，競爭分散到各個座位，熱門座位仍然有人同時搶，以「座位鍵不存在才寫入、並設保留期限」的寫法（`SET seat:A12 <訂單> NX EX 600`，`EX 600` 是 600 秒的保留期限，對應範例系統十分鐘的付款期限）讓先寫入的人保留那個座位。

Redis 出錯時，可能讓已扣的票回來。Redis 的複寫是非同步的，主節點回應「扣成功」之後，這個寫入不一定已經送到副本；主節點故障、副本被提升為新的主節點時，最後幾筆扣減會遺失，新的主節點上剩餘數量比實際多，接下來的請求可能把已賣出的票再賣一次。所以 Redis 在這裡是一道擋掉大多數請求的閘門，不超賣的保證要放在資料庫：Redis 判斷有票的請求，再到資料庫認領一張實際存在的票。

資料庫在這一段只處理通過 Redis 的請求，數量約等於票數，而且被放行速率攤開在幾分鐘裡：五千筆攤在幾分鐘是每秒數十筆，遠低於前面算出的一列每秒一千筆的上限。認領的寫法是每一張票事先在資料庫裡建一列，請求挑一列還沒被認領的票寫入自己的訂單，以 PostgreSQL 寫是：`UPDATE tickets SET order_id = $1 WHERE id = (SELECT id FROM tickets WHERE event_id = $2 AND order_id IS NULL LIMIT 1 FOR UPDATE SKIP LOCKED)`。`FOR UPDATE SKIP LOCKED` 讓子查詢跳過別的交易正在認領的列，兩個交易不會等同一把鎖；`order_id IS NULL` 讓已經被認領的票不會被選中，Redis 多放進來的請求在這裡找不到票，得到售完。對號入座時用同一個寫法，只是每一列是一個座位，請求指定要認領哪一列；付款期限到期時把那一列的 `order_id` 清回 NULL，座位就回到可售。不要在訂單表的座位欄位上加一般的唯一約束：到期的訂單會永久佔住那個座位，要用只涵蓋有效訂單的部分唯一索引（`CREATE UNIQUE INDEX ... WHERE status IN ('pending', 'paid')`）。

## 記帳與付款期限

Redis 扣成功、資料庫卻寫入失敗時，這張票既沒有賣出去也沒有回到可售。Redis 與資料庫是兩個儲存，沒有一個交易能同時包住兩者，所以寫入的順序與失敗時的補償要明確：先在 Redis 扣，再在同一個資料庫交易裡認領票並寫入訂單（以購票嘗試的識別碼做唯一鍵，重送的請求寫不進第二筆），資料庫的交易失敗時把 Redis 的數量加回去。補償本身也可能沒執行，例如程序在兩步之間當機，所以還要一個定期的對帳工作：比對 Redis 的剩餘數量與資料庫裡還沒被認領的票數，以資料庫為準修正 Redis。兩邊的數字在處理中的請求（Redis 已扣、資料庫還沒提交）存在時本來就對不上，所以對帳要在一段時間沒有新的扣減之後執行，或改成逐筆比對：Redis 每次扣減時記下購票嘗試的識別碼，對帳找出記了識別碼而資料庫沒有對應訂單、且已超過處理時限的那幾筆。這種情形造成的是少賣，票在對帳之後回到可售，符合範例系統對少賣的要求：開賣後短暫沒有全部賣出可以接受，只要之後回收得回來。對帳的做法見 [Data Reconciliation](/backend/knowledge-cards/data-reconciliation/)，跨儲存的補償見 [Saga](/backend/knowledge-cards/saga/)。

付款交給第三方金流。付款的請求數也約等於票數，而集中在開賣後的前幾分鐘，金流業者對每個商家有自己的速率限制，超過時回應錯誤或變慢。付款的呼叫要用自己的連線池與逾時，不能和購票流量共用。拓元的架構圖上，付款層是獨立的一組機器、直連金流的伺服器；這樣切開的作用是讓選位與下單的流量不會塞住付款（作用是推論，案例頁沒寫拓元的理由）。金流業者停掉時，訂單停在待付款，付款期限照常計時，金流恢復時大量訂單已經過期，使用者付不了款。處理的方式有兩種，各有代價：付款期限設得比金流業者常見的中斷時間長，票被保留得更久，放回與重新賣出都跟著延後；在金流故障期間暫停計時，要先判定金流故障，判定本身會誤判（金流只是變慢時暫停了、或已經停了卻沒暫停）。依賴方停掉時的處理見 [8.15 Vendor / 第三方依賴事故處理](/backend/08-incident-response/vendor-dependency-incident/)。

付款期限到期要放回票，而放回與付款可能同時發生：使用者在十分鐘的付款期限（示意）快到時付款，金流的回呼與到期的排程工作同時處理同一筆訂單。兩者都要寫成有條件的更新，讓其中只有一個成立：到期工作執行 `UPDATE orders SET status = 'expired' WHERE id = $1 AND status = 'pending'`，更新了一列才把票放回；付款回呼執行 `UPDATE orders SET status = 'paid', payment_id = $2 WHERE id = $1 AND status = 'pending'`。排程服務與金流回呼都可能把同一個動作執行兩次（排程服務在少數情況下會重送任務，金流業者在沒收到回應時會重送回呼，Stripe 的文件寫明同一個事件可能送達不只一次），所以更新了零列時要再讀一次訂單的狀態才知道是哪一種：狀態已經是 `paid` 而且付款識別碼相同，是同一筆付款的重送，忽略即可；狀態是 `expired`，才是到期之後才到的付款，這筆款項走退款。到期工作重送時同樣更新零列，票不會被放回兩次。

## 售票需求帶來的簡化，以及無法簡化的部分

成功請求數有上限，讓排隊服務可以提早告訴後面的人買不到，讓資料庫只需要處理約等於票數的寫入，讓 Redis 被繞過或資料遺失時還有資料庫的認領擋住超賣。使用者接受排隊，讓放行速率可以設在後端實測的處理量，而不是開賣當下的請求量。座位圖的剩餘數量允許落後，讓它可以交給 CDN 與記憶體。

無法簡化的是核心本身，也就是一次一筆的處理與狀態的互斥：它從資料庫的一列移到 Redis 的一個鍵，又在資料庫留下一道以認領與條件更新寫成的保證。抵達核心的請求，從開賣第一分鐘的每秒數萬個降到約等於票數、攤在放行的幾分鐘裡的每秒數十個，而核心始終存在。跨段的交接也無法簡化：每一個可能重送的地方（佇列、排程、金流回呼、使用者重按）都要有識別碼或條件更新，任何一段漏掉，就是一張票賣兩次或一筆款扣兩次。

這套做法成立，依賴的是成功請求數有上限而且使用者接受排隊。成功請求數沒有上限時（庫存充足的電商 checkout），擋掉的每一個請求都是少一筆訂單，提早回應結果這個做法不存在；延遲改變請求的價值時（交易撮合），排隊本身就讓請求失去下單時的意義，過載時要明確拒絕。交易撮合的負載路徑見 [9.0.2 交易撮合的負載路徑](/backend/09-performance-capacity/matching-engine-load-path/)，四個範例系統在這兩個性質上的位置見 [Backend 範例系統](/backend/case-systems/) 的〈四個系統在請求性質上的差別〉。
