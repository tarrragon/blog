這篇整理沿著一個請求的路徑分析負載時用到的幾個概念：路徑上必須一次只處理一筆的那件事、在它之前能回應掉多少請求、多出來的請求怎麼處置、每一段保護把負載轉到了哪裡，以及保護元件自己出錯時會輸出什麼。概念以 [Backend 範例系統](/backend/case-systems/) 的四個系統舉例；完整走過一條路徑的案例是 [9.0.1 售票搶購的負載路徑](/backend/09-performance-capacity/ticketing-load-path/) 與 [9.0.2 交易撮合的負載路徑](/backend/09-performance-capacity/matching-engine-load-path/)。負載超過容量之後服務呈現哪一種結果（變慢、請求失敗、無回應、程序終止、停在失效），在 [9.16 負載超過容量時服務的表現](/backend/09-performance-capacity/overload-outcomes/)。

## 一次一筆的處理與它的互斥範圍

一個服務的需求裡，通常有一件事必須一次只處理一筆：同一張票不能同時賣給兩個人，同一筆訂單不能同時被付款與取消，同一個交易對的委託要依單一順序撮合，同一個短代碼不能同時分配給兩個長網址。這件事要靠鎖、單一執行緒或條件更新排成一列，所以不論前面有多少台伺服器，抵達它的請求都要逐一通過，負載最後集中在這裡。

決定這一列有多長的，是**互斥範圍**：哪些請求彼此必須排在同一列。互斥範圍由需求決定，也由資料的表示方式決定。售票的需求要互斥的只是同一張票，全場庫存若寫成一個計數欄，所有購票請求都更新同一列，整場的請求排成一列；改成每張票一列，各自認領不同的列，只有搶同一張票（同一個座位）的請求才排在一起。撮合的需求要互斥的是整本委託簿，因為一筆委託能不能成交取決於簿上所有其他委託的價格與時間，這個範圍沒有辦法靠換表示方式縮小，只能讓單一順序上的處理變快。所以分析一條路徑的第一步，是寫出這件一次一筆的處理是什麼、它的互斥範圍是需求要求的，還是表示方式造成的；後者可以改寫法縮小，前者不行。熱點列的排隊機制與分散寫入的做法在 [1.18 高頻計數的寫入與彙總](/backend/01-database/high-frequency-counting/)。

## 能在一次一筆的處理之前回應的請求

不是每一個請求都要走到那件一次一筆的處理。在它之前能回應的請求有四類：讀取可以由快取回應（短網址的轉址、商品頁、座位圖上的剩餘數量），格式或權限不符的請求在入口就能拒絕，結果已經確定的請求可以直接告訴它結果（票賣完之後的購票請求），以及重送的請求可以回傳上一次的結果。這幾類請求佔的比例越高，前面的元件擋下的越多，一次一筆的處理承受的越少。

這個比例由需求的性質決定，而性質與比例之間的關係要看清楚。售票的成功請求總數有上限（票數），票數之外的購票請求結果在售完那一刻就確定，所以比例高；交易撮合沒有這種上限，一筆委託的結果要撮合當下才知道，只有無效的委託能提早回應，比例低。有上限不等於比例高：拍賣的成功請求總數是一（只有一個得標者），而結標之前每一次出價都要處理、誰得標事先不知道。比例高的系統，負載保護的重心在一次一筆的處理之前：快取、排隊、提早回應，把請求擋在資料庫前面。比例低的系統，重心在那件處理本身：記憶體內的狀態、單一寫入者、處理路徑上沒有資料庫，以及事先配置的容量。

## 多出來的請求：排隊、拒絕或請使用者重新確認

扣掉能提早回應的請求，抵達一次一筆的處理的請求仍可能超過它的處理量，多出來的那些要決定怎麼處置，而決定的依據是**延遲是否改變請求的價值**。售票在不劃位、固定票價時，排隊幾分鐘之後買到的仍是同一種票、同一個價格，多出來的請求可以排隊，排隊的速率設在後端實測的處理量。連續撮合的交易所，一筆委託晚一秒送進委託簿，市場已經變了，市價單以偏離預期的價格成交，排隊讓請求失去下單時的意義，多出來的委託要在接受之前明確拒絕。

延遲改變價值、所以要拒絕，還有一個前提：請求在處理時照送出當下的條件直接執行，不再經使用者確認。處理之前會讓使用者重新確認的請求，延遲只會多一次確認：checkout 的價格在使用者排隊期間變了，下單時以新價格重算並請使用者確認，訂單照樣成立。市場的規則也會改變這個判斷：以固定間隔把委託集中起來撮合的市場（集合競價），等到下一次撮合本來就是規則的一部分。

拒絕之後，負載不會就此消失。被拒絕的用戶端多半會重送，用戶端是程式時會立刻重送，重送的請求疊在原本的需求上，讓進來的請求率高於真實的需求，這是 [Retry Storm](/backend/knowledge-cards/retry-storm/)。所以拒絕的回應要帶重試的時機（`Retry-After` 這類欄位或約定的退避間隔），排隊的回應要讓使用者看得到自己的位置，兩者都在讓用戶端不要用重送去確認結果。

## 每一段保護把負載轉到哪裡

每一段保護擋下或延後某一類請求（可以由快取回應的、刷票的、還沒輪到的、結果已確定的），而被擋下的請求並沒有消失，改由做這件事的元件承受。分析一條路徑時，每加一段保護，就要問被擋下的那些請求現在落在哪個元件、那個元件先耗盡的是什麼資源。常見的轉移有幾種。

**連線數**。把扣庫存或計數移到 Redis 這類記憶體儲存，資料庫的鎖等待少了，連到那個儲存的連線數卻成為新的上限：同時連過去的連線數，是所有應用程式主機上同時在處理請求的程序或執行緒數，乘上每一個各開的連線數。PHP-FPM 這類每個請求佔一個 worker 的執行環境，上限是全部主機的 worker 總數（每台的 `pm.max_children` 乘以主機數），為了尖峰把主機擴到幾十台時，總數可能超過 Redis 預設的 `maxclients`（一萬）。持久連線（phpredis 的 `pconnect`）讓每個 worker 長期保留一條連線，省下的是每次請求的握手，連線數不會變少；要讓連線數少於 worker 數，要在中間放一層連線代理（twemproxy、Envoy 的 Redis proxy 這類），由它以少數連線轉送。沒有持久連線時，每次新開連線要付 TCP 握手的成本，用完的連線在主動關閉的那一端停留在 TIME_WAIT 狀態，佔住本機的連接埠。資料庫那一側的同一件事在 [9.14 連線池放大解法](/backend/09-performance-capacity/connection-pool-amplification/)。

**輪詢**。排隊把請求從資料庫移開，排隊中的使用者卻會反覆查自己的位置：十萬人每五秒查一次，就是每秒兩萬個查詢，落在排隊服務上。讓這個查詢便宜（位置資訊放在記憶體或邊緣、由伺服器指定下一次查詢的間隔），或改成伺服器推送；改成推送時，等候中的每一條連線都是要規劃的容量。

**重送**。用訊息佇列當緩衝時，佇列在消費端以確認（ack）模式使用時保證的是至少送達一次，消費端處理到一半當機、佇列重送，同一個請求會被處理兩次。請求在進入佇列之前要有一個識別碼（[Idempotency Key](/backend/knowledge-cards/idempotency-key/)），處理那一段以它辨認重送；使用者自己重按產生的是新的請求，佇列分不出來，要以業務規則限制（例如一個帳號同時只能有一筆在排隊）。排程服務與第三方的回呼同樣可能把同一件事送兩次，條件更新（`UPDATE ... WHERE status = 'pending'`）讓第二次執行更新零列。

**下游的接收端**。一個元件若把輸出直接送給每一個接收端、等接收端收下才處理下一筆，最慢的那一個接收端決定了整個元件的處理速度，負載以 [Backpressure](/backend/knowledge-cards/backpressure/) 的形式傳回來。把輸出先寫進一份日誌，由另外的發布服務送給各個接收端，讓跟不上的接收端只影響自己。

**外部的配額**。保護把請求順利送到下游之後，第三方業者（金流、簡訊、雲端 API）對每個商家的速率限制會成為下一個上限，而且它不在自己手上，只能事先知道數字、用獨立的連線池與逾時把它和其他流量隔開。

## 保護元件自己出錯時

保護元件故障時，系統要嘛停止放行（fail closed），要嘛全部放行（fail open），選哪一邊依這個元件保護的是什麼而定。保護的資源一定處理不了全部請求時（售票的排隊保護著扣庫存），全部放行等於拿掉保護，全部請求回到那件一次一筆的處理，選停止放行，使用者看到的是暫停，狀態還在。保護的資源平常就處理得了全部合法請求、保護只用來擋濫用時（邊緣依來源位址的速率限制），停止放行等於整個服務停擺，選全部放行。要能在恢復後照原本的順序繼續，保護元件的狀態（排隊的順序、已發出的資格）要存在它的程序以外，只存在記憶體的狀態在重啟時就丟了。

選了全部放行之後，還要確認下游讀到的值代表放行：保護元件故障時多半會輸出一個預設值，而這個預設值要是下游判成放行的那個值；元件故障時若給每個請求一個「機器人分數」零分、而下游把零分判成機器人，結果反而是全部擋掉。保護元件的故障也不只停掉一種，讀到壞掉的規則或設定檔、輸出錯的判斷，是同樣要事先決定處置的情形。保護元件是購買的服務（業者提供的等候室、WAF）時，故障時放行還是不放行由業者的行為決定，要事先查清楚業者的預設並確認能不能改。

## 停掉以外的失效：變慢、輸出錯的值、部分失效與重新開始

分析負載路徑時，最容易只想到元件整個停掉這一種失效，而幾種更常見的形態要分開處理。**依賴變慢**：依賴沒有停，只是回應慢於呼叫方的逾時，結果與停掉相同，而健康檢查可能還回報正常，或反過來，健康檢查因為變慢而失敗、把所有副本一起移出服務。**輸出錯的值**：元件還在運作，輸出的判斷是錯的（上一節的預設值、讀到壞掉的設定），下游照著錯的值處理，監控上每一層都在運作。**部分失效**：只有一部分副本連不到依賴（某一個可用區的網路出口壞了），讓那幾個副本下線是對的，而剩下的副本要承接全部流量，容量不夠時接著變慢。**重新開始**：元件從故障中恢復時，累積的請求一起湧入，恢復的那一刻成了另一次尖峰；狀態會隨時間失去價值的系統（交易所的委託簿），恢復前要先讓使用者撤掉過時的請求，再以一次集中的處理決定起點。負載退去之後服務仍停在失效狀態的情形，在 [Metastable Failure](/backend/knowledge-cards/metastable-failure/)。

## 兩個案例：售票搶購與交易撮合的負載路徑

[9.0.1 售票搶購的負載路徑](/backend/09-performance-capacity/ticketing-load-path/) 從全場庫存寫成一個計數欄時熱點列與連線池的耗盡順序起算，走過 CDN 合併回源、排隊放行、資料庫逐張認領與付款期限，示範互斥範圍怎麼靠改表示方式從整場縮到一張票、成功請求的總數有上限怎麼讓排隊服務提早告訴後面的人買不到，以及什麼條件下才值得在扣庫存前面加一道 Redis 閘門。[9.0.2 交易撮合的負載路徑](/backend/09-performance-capacity/matching-engine-load-path/) 走過閘道、依序日誌、撮合引擎與行情發布，示範互斥範圍沒辦法縮小、能提早回應的請求很少時，負載保護的重心怎麼移到處理路徑本身與事先配置的容量，以及延遲改變請求的價值時，過載與停機後的處置為什麼與售票相反。
