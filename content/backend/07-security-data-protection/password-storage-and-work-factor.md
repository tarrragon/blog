本章的責任是把密碼儲存的判讀軸講清楚：它是唯一一類**保護強度會隨時間自己下降**的原語，因此選型的產出不只是演算法，還包括一個要定期重算的參數。

本章目前是簡版，交付選型判準、參數定法與升級路徑；演算法內部機制的比較、大規模帳號庫的遷移策略與合規對照留在 backlog。

## 本章寫作邊界

本章聚焦不可逆單向轉換用在使用者密碼上的選型判讀，是 [7.28 密碼學原語選型](../cryptographic-primitive-selection/) 第四類原語的展開。認證流程本身（登入節奏、多因子、會話管理）屬 [7.2 身分與授權邊界](../identity-access-boundary/)，內容校驗用的快速雜湊（checksum、檔案指紋）不在本章範圍——它與密碼儲存的判讀軸相反，那裡速度是優點。

## 這一類原語的判讀軸

其他原語防的是攻擊者拿不到資料，密碼儲存從一開始就假設資料已經被拿走。資料庫外洩之後，攻擊者手上有全部的雜湊值與 salt，唯一還在運作的保護是「逐一嘗試要花多久」。

判讀軸因此落在計算成本，而成本有兩端：攻擊者猜一次要付的代價，與正常使用者登入時要等的時間。兩者用的是同一個參數，調高一邊就調高另一邊，所以這個選型的產出是一個區間而不是一個值。

這條軸還有一個其他原語沒有的性質：**參數的有效性隨硬體變快而下降**。金鑰位置選對了就一直對，密碼的 work factor 定好之後每年都比前一年弱。這決定了本章的交付包含一個複查節奏，而不只是一次決定。

## 演算法選型

現行的預設是 Argon2id。它同時對計算時間與記憶體用量收費，而攻擊者的優勢主要來自平行化的專用硬體，記憶體成本是目前對這種優勢最有效的抵銷方式。

bcrypt 仍然是可接受的選擇，判準是既有系統已經在用、或執行環境的函式庫支援度是決定因素。它只對計算時間收費，抵抗專用硬體的能力弱於 Argon2id，但它成熟、實作陷阱少、幾乎所有語言都有經過檢驗的函式庫。既有系統用 bcrypt 而參數維持在量測得出的區間內時，換演算法的優先序低於其他資安工作。

PBKDF2 的適用情境是合規要求限定在通過特定認證的演算法清單內。它的抗硬體能力最弱，選它通常是外部約束而非技術判斷；落在這一格時，把參數調到清單允許的上限。

以下三種形態不適用於密碼儲存，判別它們的共同點是速度快：一般用途的雜湊（SHA-256、SHA-3）設計目標是快速計算，正是這一類要避免的性質；加密（把密碼加密後存起來）保留了還原能力，而還原能力本身就是這一類要消除的東西；自製的多輪雜湊組合缺少公開檢驗，它的實際強度沒有人算得出來。

## work factor 怎麼定

參數的定法是量測而非查表，因為它取決於自己的硬體與可接受的登入延遲。

1. 在**正式環境的機器規格**上量單次雜湊耗時，開發機的數字沒有意義——兩者的差距經常是好幾倍。
2. 目標落在登入延遲預算內。這個預算由產品決定：登入是低頻操作，多數服務能接受數百毫秒等級的延遲；高頻呼叫的內部服務要另外處理，通常做法是登入一次換成 session、不在每次呼叫重算。
3. 把並行登入的尖峰算進去。雜湊耗時同時是 CPU 佔用時間，尖峰登入量乘上單次耗時就是所需的運算容量；這個數字撐不住時要往下調參數或往上加機器，兩者都是選型階段就該知道的成本。
4. 記下量測的日期與當時的機器規格。這一項讓下一次複查有比較基準，缺了它複查會退回重新猜。

複查節奏跟著硬體採購週期走：換過機器、升級過雲端執行個體規格、或距離上次量測超過一到兩年，就重量一次。

## 參數老化的形態與失效

參數老化出現在上線之後沒有再動過密碼設定的系統。這一類的成因與疏忽無關——參數當初定得正確、系統一直正常運作、沒有任何錯誤訊息與它有關，因此沒有任何既定工作會帶出「該回頭看一眼」這個動作。識別特徵是問「上一次調整 work factor 是什麼時候」，答案是「不知道」或「應該是上線的時候」。

這一類的失敗長這樣：服務上線時照當時的建議值設了參數，量測過、也在延遲預算內。幾年之間機器換過兩輪、雲端執行個體規格升過級，密碼設定沒有人動過，因為它沒有壞。資料庫外洩之後才發現，當初設計成「猜一次要付的代價」在現在的硬體上已經降到原本的一小部分，而弱密碼的比例在任何一個真實帳號庫裡都足以讓這個差距變成大量帳號被還原。查不出來的原因是參數老化沒有任何訊號——登入正常、監控正常、沒有任何一項檢查會回報「這個值已經過時」，它只在被攻擊的那一刻才顯現強度。補救要走使用者下次登入的路徑（見下節），所以止血速度由使用者的回訪頻率決定，而不是由自己的部署速度決定。

## 升級路徑

密碼的明文只在使用者輸入的那一刻存在於系統裡，因此參數升級無法用批次重算完成——手上只有舊參數的雜湊值，它不可逆。

可行的路徑是在驗證成功的當下重算：使用者登入、用舊參數驗證通過、隨即用新參數重新雜湊並覆寫。這個做法讓升級跟著使用者的回訪自然推進，代價是長期不登入的帳號會一直留在舊參數上。

因此升級要配一個收尾動作：設一個期限，期限後仍未重算的帳號強制走密碼重設流程。期限長度由帳號庫的回訪分布決定，而這個分布要先查得出來——查不出來時，這個決定會退回拍板，而拍板的期限通常過長。

儲存格式要能同時容納新舊參數，否則升級無從進行。現行的做法是把演算法識別、參數與 salt 一起編碼進雜湊字串（Argon2 與 bcrypt 的標準格式都是這樣），驗證時從字串本身讀出該用哪組參數。既有系統若把參數寫死在程式碼裡而非存在紀錄旁邊，升級的第一步是先改儲存格式。

## 常見風險邊界

- 密碼設定的參數寫死在程式碼裡、而非隨每筆紀錄儲存時，代表升級路徑不存在，這是比參數值偏低更優先的問題。
- 登入延遲預算沒有人定過時，參數會落在「不會被抱怨」的位置，而那個位置由最沒耐心的那條回饋路徑決定，與安全需求無關。
- 密碼雜湊在每次 API 呼叫都重算時，代表 session 機制缺位，參數會因為效能壓力被迫調低。
- 同一套帳號庫裡存在多種雜湊格式而沒有升級期限時，代表升級啟動過但沒有收尾，最弱的那一批會無限期留著。
