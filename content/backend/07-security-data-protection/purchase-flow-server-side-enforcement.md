這一章整理購票與限量搶購入口的前端被程式繞過的成因，以及伺服器端要補的檢查；下文的機器人指代替人送出購票請求的程式，預填指在開賣之前就把購票請求的內容組好、到時直接送出，工作階段（session）指伺服器用來辨認同一個使用者連續操作的那一段狀態，排隊放行指使用者先在等候室排隊、伺服器依速率逐批放進購票頁的做法。各節依序是：只做在前端的檢查在程式直接呼叫購票 API 時剩下什麼；伺服器端的流程狀態與伺服器簽發的步驟憑證，以及步驟憑證要檢查的簽發時間、效期、綁定、只能用一次與最短停留時間；購票要帶的識別碼事先查得到時的預填，與開賣才發、每個工作階段各發一組這兩種做法對快取與源站負載的影響；伺服器提早回傳、快取、其他入口的 API、預覽環境與直連源站造成的開賣前資料外洩；驗證碼與挑戰放在哪一步，才不會被提早解好或重複使用；最後是這些檢查擋住的捷徑，與它們擋不住的開賣競爭。繞過手法寫到防守者判斷得出它繞過哪一項檢查的程度，不寫實作。機器人在開賣那一刻的速度優勢、帳號數量優勢，以及認出之後的處置，在 [7.46 搶票與限量搶購機器人的防護](/backend/07-security-data-protection/ticket-bot-defense/)；購票請求的負載路徑在 [9.0.1 售票搶購的負載路徑](/backend/09-performance-capacity/ticketing-load-path/)。

## 只做在前端的檢查與直接呼叫購票 API 的請求

購票頁面上的檢查分成兩種位置：在使用者裝置上執行的程式（網頁裡的 JavaScript、原生 App 的程式碼），與伺服器處理請求時的程式。開賣前反灰的購票按鈕、倒數計時、欄位格式的驗證、「請先選票區」的提示，都是使用者裝置上的程式依畫面狀態決定是否讓使用者按下去；它們的用途是讓真人別送出注定失敗的請求，減少錯誤與重試。程式不經過網頁或 App、直接對購票 API 送出 HTTP 請求時，裝置上的檢查一行都沒有執行，伺服器收到的請求跟按鈕亮起之後按下去的請求長得一樣。所以每一項會影響誰買到票的條件（開賣時間是否已到、這個人是否走過選票的步驟、這個票區是否可售），都要在伺服器處理購票請求的那一刻再檢查一次，裝置上的那一份只當作使用者介面。

請求裡由客戶端送來的每一個值，伺服器都當成客戶端可以任意改寫的輸入：時間戳、價格、票區、數量、「已經排過隊」的旗標都在這一類。伺服器判斷開賣與否用的是伺服器自己的時鐘，計價用的是伺服器依票區查出的價格；客戶端送來的時間只拿來記錄，客戶端把時鐘改成什麼，都不影響伺服器的判斷。

## 伺服器端的流程狀態與步驟憑證

購票流程在伺服器端的狀態，指伺服器記得這個工作階段走到了哪一步：進入購票頁、選好場次與票區、確認訂單、送出付款。購票 API 只接受上一步已經完成的請求時，程式就沒辦法跳過前面的步驟，直接送最後一步。只有一個頁面就送出的流程，伺服器端的流程狀態只剩一步：伺服器在開賣後回傳購票頁時簽發憑證，送出購票時驗證它；這時沒有跳步可擋，下面的檢查擋住的是不載入頁面就直接呼叫購票 API、開賣前送出、重送，以及送得比最短停留時間快。

伺服器記住流程狀態有兩種做法：存在伺服器端的工作階段（多台伺服器共用時，放在 Redis 這類共用的儲存），或由伺服器簽發一個步驟憑證交給客戶端，下一步時客戶端把憑證帶回來，伺服器驗證它沒有被改過。步驟憑證是伺服器在一個步驟完成時簽發、記錄誰在什麼時間完成了哪一步的資料。伺服器用只有自己持有的金鑰替它計算訊息鑑別碼（message authentication code，MAC，例如 HMAC；機制見 [Message Authentication](/backend/knowledge-cards/message-authentication/) 卡），客戶端讀得到內容，改了任何一個欄位，伺服器重新計算時就對不上。它的內容通常包括工作階段或帳號、場次、完成的步驟、伺服器簽發的時間（issued-at）與一個隨機值（nonce）。有排隊放行時，放行那一刻發出的進入資格（7.46〈提高帳號成本：事前註冊、限購的對象與法規〉寫的 access token）擔任進入購票頁那一步的步驟憑證；簽發時間記的是放行給這個工作階段的那一刻，不是 9.15 寫的開賣前依可售票數產生名額的那一刻。排隊由外部的等候室服務負責時，進入資格用的是服務的金鑰與時鐘，排隊又常在登入之前，還沒有綁帳號；售票系統第一次收到它時先驗證，再換發自己的步驟憑證、綁定工作階段與帳號，下面各項檢查都用換發的那一張。

伺服器驗證步驟憑證時檢查的每一項，各擋住一種繞過，也各有加在真人身上的代價：

- **簽發時間不早於開賣時間**：進入購票頁那一步的憑證只在開賣之後才簽發，購票 API 檢查憑證裡的簽發時間，早於開賣時間的不接受。客戶端改了自己的時鐘、或在開賣前就送出事先組好的請求，都拿不到這張憑證，因為憑證裡的時間只來自伺服器的時鐘。所以這裡不採用 JWT 的 not-before（`nbf`）：`nbf` 允許事先簽發、到了那個時間才生效，用在這裡會讓開賣前領到的憑證在開賣那一刻變成有效。這一項也讓「開賣前先打開購票頁等著」不再是優勢：沒有排隊放行時，等在頁面上的真人與程式手上都沒有可用的憑證，都要在開賣之後向伺服器要一次，而這些請求在同一刻送出，源站的尖峰跟線上人數成正比；有排隊放行時，這個請求被放行的速率攤平。
- **效期短**：憑證只在簽發後一段時間內有效，領到之後囤著的憑證過了這段時間就失效。效期短於真人在這一步要花的最長時間時，看得慢、填資料慢的真人送出時憑證已經過期，只能重新進頁；效期比真人所需的時間長出越多，程式領到之後囤著、等其他條件湊齊再送的空間越大。效期與下面的最短停留時間一起夾出真人能送出的時間窗：從簽發後 Δ 秒到效期結束。
- **綁定工作階段、帳號與場次**：憑證只對簽發時的那個工作階段、帳號與場次有效，從真人手上買來或在另一台機器領到的憑證，換到別的工作階段送出時驗不過。真人回上一步改了場次時，伺服器在新的選擇完成時重新簽發一張，綁著舊場次的那張不再接受；客戶端送來的場次與日期只是新選擇的輸入，憑證裡的值以伺服器簽發的為準。代價是真人在流程中途重新登入、或工作階段因逾時被重建時，手上的憑證同樣驗不過，要從簽發那一步重新開始；工作階段的逾時短於整個購票流程時，這一項會擋下真人。綁定不限制同一個帳號開幾個工作階段：一個帳號開十個工作階段，就領到十張憑證、送出十次；要限制時，照 9.0.1〈准入：排隊與放行的速率〉寫的「一個帳號同時只能有一筆購票在排隊」，代價是真人開了兩個分頁時，後開的那一個要等。不必登入就能結帳的流程沒有帳號可綁，這一項只剩工作階段，而開幾個工作階段由攻擊者決定。
- **只能用一次**：伺服器在同一個不可分割的操作裡檢查並記下用過的隨機值（例如 Redis 的 `SET` 加 `NX`，或資料庫的唯一索引），同時記下第一份請求的處理結果；之後帶同一個隨機值的請求不再建立訂單，拿到的都是這份結果。並行重送同一張憑證的程式因此只買到一張，擋住把同一個合法請求原封不動重送的 [Replay Attack](/backend/knowledge-cards/replay-attack/)（那張卡寫的做法是拒絕重複的請求；這裡改成回傳第一次的結果，因為購票的重送多半是真人逾時重試，而結果綁在原本的工作階段，重送的一方拿不到第二張票）；逾時之後重送的真人看到的是第一次的結果，不是錯誤。第一份請求還在處理時，後到的請求收到「處理中」，不是錯誤也不是第二筆訂單；第一份因為伺服器端暫時故障（下游逾時、5xx）而沒有結果時，伺服器不記下那次故障，而是釋放這個隨機值，或回應真人重新進頁取得新憑證，否則逾時之後重送的真人拿到的永遠是那次故障。伺服器分不出這兩種重送，所以兩者走同一條處理路徑，這也是 [Idempotency Key（冪等鍵）](/backend/knowledge-cards/idempotency-key/) 的處理方式。先查詢「用過了沒有」、再寫入的兩段式做法，在並行送出時每一份都會查到「沒用過」而全部通過。
- **最短停留時間**：伺服器拒絕在上一步的憑證簽發之後 Δ 秒內送出的下一步，Δ 是這一項的秒數門檻。真人看清楚選項、填寫資料需要幾秒，程式可以在幾毫秒內送出；Δ 把程式在這一段能壓到的最短時間從幾毫秒拉長到 Δ 秒。真人所花的時間超過 Δ 時，程式仍然比真人早「真人所花的時間減去 Δ」（示意：真人花 6 秒、Δ 為 4 秒時，程式早 2 秒）；真人所花的時間短於 Δ 時，真人與程式都要等到 Δ，兩者在這一段打平，代價是這位真人多等了一段。Δ 設得越接近真人的操作時間，程式剩下的差距越小，被迫等待的真人也越多。送得太早的請求收到的回應寫成「請稍候」時，真人等一下就能送出；收到的是錯誤時，真人會以為失敗而重試。

只能用一次那一項讓步驟憑證也要一份共用的儲存，記錄用過的隨機值與它的處理結果，只需保留到憑證失效為止；把狀態存在伺服器端的工作階段時，每一步都要讀寫完整的流程狀態。兩種做法都需要共用的儲存，差別在每一步讀寫的內容與保留的時間：流程步驟多、每一步要帶的狀態大時，伺服器端工作階段的讀寫量跟著變大；步驟憑證的內容寫在客戶端帶回來的資料裡，共用儲存只記隨機值與結果。這份共用儲存在開賣那一刻跟扣庫存一起承受尖峰：每一筆購票多一次檢查並記下隨機值、一次寫入結果，放在扣庫存用的同一個 Redis 時，這些讀寫要算進 9.0.1〈扣庫存：資料庫逐張認領與加入 Redis 閘門的條件〉的容量。

伺服器有很多台時，各台的時鐘有落差（[Clock Skew](/backend/knowledge-cards/clock-skew/)）。NTP 正常同步時，同一個資料中心內各台的落差在毫秒級；虛擬機從快照還原、容器被暫停之後，落差可以拉到秒級以上。最短停留時間對這個落差最敏感：驗證那一台拿「憑證的簽發時間加 Δ」跟自己的時鐘比較，簽發那一台的時鐘比驗證那一台慢 s 秒時，真人實際要等 Δ＋s 秒；快 s 秒時只要等 Δ−s 秒。各台之間量到的最大偏移 s 因此讓 Δ 的實際作用落在 Δ−s 到 Δ＋s 之間：s 接近 Δ 時，這一項對憑證由時鐘較快那一台簽發的請求形同沒有，對由時鐘較慢那一台簽發的請求則把真人的等待拉長將近一倍。簽發時間不早於開賣時間那一項有同樣的偏移：落到時鐘慢的那一台簽發的憑證，可能被判成早於開賣時間而拒絕。讓這兩項不受各台落差影響的做法，是讓簽發時間與驗證時比較的現在時間取自同一個來源：開賣與否由一個共用的開賣旗標決定，不由各台比對自己的時鐘；Δ 用共用儲存回報的時間（例如 Redis 的 `TIME`）比較。代價是每次簽發與驗證多一次對共用儲存的讀取。各台落差的量測與超標節點的處置，在 Clock Skew 卡的〈判斷條件與後果〉。

## 購票要帶的識別碼：事先查得到時的預填，與開賣才發、每個工作階段各一組的做法

預填（在開賣前就把購票請求的內容組好、到時直接送出）成立的前提，是購票請求要帶的每一個值在開賣之前就查得到。購票請求通常要帶場次 ID、票區 ID、票價 ID 與數量；這些 ID 在開賣前就出現在頁面原始碼、公開的場次 API 或 App 的回應裡時，程式事先把整份請求組好，開賣那一刻只差送出。〈伺服器端的流程狀態與步驟憑證〉寫的步驟憑證讓這份請求多了一個開賣後才拿得到的欄位，程式要在開賣後多一次往返去領憑證；識別碼本身仍然是事先就準備好的。

售票系統可以把送出購票要帶的識別碼也延到開賣之後才發出：開賣前頁面上顯示的票區只有名稱與價格，送出購票要帶的票區代碼在開賣時才產生。這個代碼對所有人相同，程式在開賣後取得一次，就能填進它控制的每一個工作階段的請求；它擋住的是開賣前就組好整份請求，而步驟憑證已經讓程式在開賣後至少多一次往返，所以兩者並用時，開賣才發多出的作用，取決於系統還有沒有不驗步驟憑證的入口（下文〈開賣前的資料外洩：伺服器提早回傳、快取、其他入口的 API、預覽環境與直連源站〉）。更進一步的做法是每個工作階段各發一組：伺服器替每個工作階段產生一組隨機的票區代號，對回真正票區 ID 的對照表依工作階段分開存放，伺服器只用送出請求的那個工作階段的對照表去查。事先查到的 ID、從另一個工作階段抄來的代號，在這張表裡都查不到，請求被拒絕；每個工作階段都要各自在開賣後取得一次。

兩種做法對快取與源站負載的影響不同。開賣才發的識別碼對所有人相同，開賣之後仍然可以由 CDN 快取，代價是開賣那一刻要換掉快取裡的舊內容，這一刻的回源由 [9.0.1 售票搶購的負載路徑](/backend/09-performance-capacity/ticketing-load-path/) 的〈邊緣：可以快取的內容與機器人過濾〉寫的合併回源（CDN 把同一個快取鍵同時發生的回源請求合併成一個）處理。代號由源站產生、對照表存在源站時，每個工作階段各發一組的回應無法共用同一份快取，每一個都落回源站；所有工作階段都在開賣那一刻要這個回應時，源站的尖峰跟線上人數成正比，正是 9.0.1 讓座位圖交給 CDN 快取時要避開的情形。代號也可以改成用金鑰從工作階段與票區 ID 算出來（例如 HMAC），伺服器驗證時對每個票區重算一次，不必存對照表；這樣的計算可以交給 CDN 的邊緣運算，尖峰出現在邊緣而不在源站，代價是金鑰要放到邊緣，而邊緣運算依請求數計費。有排隊放行時，每個工作階段的票區代號跟進入購票頁的步驟憑證放在同一個回應裡，由放行的那一刻發出（9.0.1 的〈准入：排隊與放行的速率〉），源站每秒收到的這類請求數就以放行的速率為上限；座位圖與剩餘數量仍然是公開、可快取的頁面。

## 開賣前的資料外洩：伺服器提早回傳、快取、其他入口的 API、預覽環境與直連源站

開賣前的資料外洩，指開賣之後才該看得到的資料在開賣之前就能取得，讓預填與預先分析有了材料。它常見的來源不在購票頁本身：

- **伺服器在開賣前就回傳開賣後的資料**：場次 API 依「場次存在」就回傳送出購票要帶的票區 ID 與票價 ID，而不依伺服器時間判斷開賣了沒有；頁面在開賣前就把開賣後要顯示的內容放進原始碼，只用 CSS 或 JavaScript 隱藏。
- **快取裡提早出現開賣後的內容**：部署流程在開賣前就把開賣後的頁面產生出來、交給 CDN 快取時，開賣前帶著同一個快取鍵的請求讀到的就是這一份。開賣後的頁面到開賣時刻才產生，或依開賣前後用不同的網址存放時，開賣前的請求讀不到開賣後的頁面。
- **其他入口的 API**：網頁版加了檢查，App 用的 API、舊版 API、給合作夥伴的 API 沒有加時，程式改呼叫檢查最少的那一個入口。同一個動作的每一個入口共用同一套伺服器端檢查時，程式改呼叫哪一個入口都受到同樣的檢查；舊版 API 沒有下架、又沒有接上這套檢查時，它就是檢查最少的入口。
- **預覽與測試環境**：預覽或測試環境用正式的場次資料，而存取限制比正式環境寬時，開賣前的資料從那裡流出。
- **直連源站**：邊緣的檢查（CDN、WAF、[Bot Management（機器人流量管理）](/backend/knowledge-cards/bot-management/)）只對經過邊緣的請求有效，源站的位址外洩、又沒有限制只接受邊緣轉來的請求時，程式直接連源站。

## 驗證碼與挑戰放在哪一步：提早解好與重複使用的通過憑證

驗證碼（CAPTCHA）與挑戰（challenge）的用途是讓送出請求的一方多付一次成本（真人花幾秒、程式要執行瀏覽器或付費請人代解），所以它放在哪一步，決定的是攻擊者在什麼時候付這份成本。驗證碼放在登入頁、或開賣前就能進入的頁面時，攻擊者在開賣前從容地解完，開賣那一刻手上已經有通過的憑證，驗證碼對開賣那一刻的競爭沒有作用。伺服器在開賣之後、送出購票那一步才要求解驗證碼時，每一次購票都要在開賣後付一次成本。

通過驗證碼之後，伺服器或驗證碼服務發出一個「已通過」的通過憑證。通過憑證效期長或可以重複使用時，攻擊者解一次就能用很多次，也能在開賣前存下一批；效期短、只能用一次時，每一次購票都要在開賣後即時解一次。即時的付費代解仍然通得過：代解服務在通過憑證的效期內把它交回給程式，程式在自己的工作階段裡送出，所以「效期短、只能用一次」把攻擊者的成本提高到每買一次付一次代解費，代解本身擋不住，跟 7.46 與 Bot Management 卡寫的付費代解相同。這一步的代價是真人在最急的時候多一個步驟，熱門場次開賣那一刻，驗證碼的載入本身也是要規劃的負載。看不到圖片或使用輔助工具的使用者，沒有替代的驗證方式（語音驗證碼，或改走客服的管道）時，這一步把他們擋在外面。不需要真人操作的挑戰（在瀏覽器裡執行一段運算的 proof-of-work、平台的裝置證明）把成本從真人的時間換成運算或裝置的數量，邊緣的挑戰與 App 完整性證明在 Bot Management 卡的〈判斷條件與後果〉。

## 伺服器端檢查擋住的捷徑與擋不住的開賣競爭

這幾項伺服器端檢查合起來擋住的是捷徑：改客戶端時鐘、開賣前送出事先組好的請求、跳過選票步驟直接送最後一步、拿事先查到的識別碼預填、重送同一個合法請求、呼叫檢查較少的入口、提早解好驗證碼。每一條捷徑被擋住之後，程式要跟真人走同一條路：開賣後進頁、領步驟憑證、等最短停留時間、在開賣後取得識別碼、在送出那一步解驗證碼。

擋不住的是開賣那一刻的競爭本身。凡是瀏覽器做得到的步驟，由程式控制的瀏覽器也做得到，只是每一步多付一點時間與運算；程式在開賣那一毫秒進頁、領憑證，仍然比真人早。步驟憑證與最短停留時間把程式的優勢從「事先準備好、開賣瞬間送出」壓縮到兩段：開賣那一刻進頁的先後（沒有排隊放行時程式仍然領先），以及每一步比真人早送出的時間，等於真人在這一步所花的時間減去這一步的最短停留時間 Δ，多步驟的流程逐步加總（真人比 Δ 快的那一步打平）。剩下的速度優勢要靠改變競爭規則消除，也就是 [7.46 搶票與限量搶購機器人的防護](/backend/07-security-data-protection/ticket-bot-defense/) 的〈開賣前到達者的隨機排序與報名期抽籤：對速度優勢的作用與代價〉。伺服器端的檢查讓程式沒有捷徑可走，隨機排序與抽籤讓走同一條路的人不再依送達的先後分出勝負，兩者處理的是不同的優勢。採報名期抽籤時，送出的先後不影響中選，簽發時間、效期與最短停留時間在報名那一步沒有捷徑可擋，只剩加在真人身上的代價；還有作用的是綁定、只能用一次、其他入口的 API 與驗證碼，以及中選之後付款那一步的綁定。

這些檢查同時留下了辨識的材料。購票請求沒有對應的步驟憑證、步驟之間的時間貼著最短停留時間的下限、同一個帳號的憑證從多個工作階段送出，都是應用程式紀錄裡可以直接比對的事件；7.46 的〈從應用程式紀錄認出帳號背後是程式：單一帳號的行為訊號、關聯訊號與它們失效的條件〉寫的「跳過畫面直接呼叫 API」，在有了步驟憑證之後從推測變成可以逐筆查證的紀錄。

這一章的檢查都在售票系統的伺服器端實作，透過售票平台開賣時，這些檢查有沒有做是平台的屬性，主辦方改不了平台的購票流程。原生 App 的購票 API 另外有一個網頁沒有的狀況：請求可能來自被修改過的 App，判斷條件與限制在 Bot Management 卡的〈判斷條件與後果〉。
