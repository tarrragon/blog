本章處理兩個網路之間的連線怎麼設計與評估：地端主機與雲端主機、或兩個雲端業者的主機，以 VPN 或憑證接起來之後，各自對另一端暴露了什麼、限制要放在哪裡。範圍從決定要把兩個網路接起來那一刻開始。文中 WireGuard 與 Tailscale 的行為依兩者的官方文件寫成，跨主機的限制效果沒有實機驗證。

## 本章的情境與範圍：地端監控與異地備份

本章用兩個情境推導。**地端監控**：監控主機放在地端（家裡或辦公室），經由 VPN 讀取雲端服務主機上的 exporter，也經由同一條 VPN 把心跳送到服務主機上的心跳監看程式，這是 [小型服務的兩到三台主機配置](/operations/06-high-availability/small-service-host-layout/) 的配置。**異地備份**：雲端服務主機把備份送到另一個業者的物件儲存，兩邊之間沒有 VPN，只有一把寫入用的存取金鑰。兩個情境分別代表兩種接法：地端監控靠網路上的可達性，異地備份靠一把憑證。

相鄰的主題各有專篇。VPN 工具的選型（Tailscale 與自建 WireGuard 的比較）在 [遠端連線與同步工具選型](/linux/tools/remote/connection-and-sync-tools/)，Tailscale 的位址模型與中繼在 [Tailscale 深入](/linux/tools/remote/tailscale-tailnet-and-relay/)。同一個雲端業者內的 VPC 對接與 security group 在 [網路地基 — VPC、subnet 分層與 security group 設計](/infra/03-network-foundation/vpc-subnet-security-group/)，從網際網路進來的對外入口在 [7.3 入口治理與伺服器防護](../entrypoint-and-server-protection/)。存取金鑰這類機器憑證要用哪一種機制在 [7.34 機器憑證的機制選型](../machine-credential-mechanism-selection/)，跨平台的工作負載身分在 [7.10 Workload Identity 與聯邦信任邊界](../workload-identity-and-federated-trust/)。

## VPN 提供的保證與邊界模型

VPN 在兩個網路之間建立一條加密的隧道，提供三件事：封包在網際網路上傳送時被加密、兩端各自確認對方持有約定的金鑰、兩端各拿到一個在隧道裡固定的位址。WireGuard 以兩端事先交換的公鑰確認對方；Tailscale 建在 WireGuard 之上，由它營運的協調伺服器分發金鑰與位址。

三件事都發生在網路層，回答的是「這個封包是不是從持有那把金鑰的機器送來的」，不涵蓋「這台機器可以使用哪些服務」。VPN 早期的用法把兩個問題合成一個：接進來就算在內網，內網裡的服務彼此信任，這種做法稱為邊界模型（perimeter security）。[7.3 入口治理與伺服器防護](../entrypoint-and-server-protection/#問題節點出現在什麼樣的系統) 描述過它與現況錯位的後果：一個只需要看一台機器日誌的人，接進來之後連得到整個內網。業界把相反的原則稱為 [Zero Trust（零信任）](/backend/knowledge-cards/zero-trust/)：每一次連線各自通過身分與授權，網路上的位置不構成信任的理由。

兩三台主機的小型服務不需要整套導入零信任的基礎設施，本章借用的是它的問法，用來評估每一條跨網路的連線：發起的是哪一台機器、以什麼身分、連到哪一個服務。三件事都是工作需要的連線留下，其餘連得到的部分都要收回。

## 隧道兩端的可達範圍

可達範圍是一台機器經由這條連線能主動連到的位址與連接埠。隧道建立之後的預設是雙向的：地端連得到雲端，雲端也連得到地端。Tailscale 新建的 tailnet 預設政策讓所有裝置互通（[Tailscale 的存取控制文件](https://tailscale.com/kb/1018/acls)）。WireGuard 兩端連得到對方在隧道裡的位址；地端主機若開啟 IP 轉送、雲端那一側又把地端的區網網段設成經由隧道送出，雲端連得到的就不只地端主機一台，而是它背後的整個區網。

雙向的預設在兩端被入侵的機率不同時特別不划算。雲端服務主機對網際網路提供服務，應用程式的漏洞、外洩的 SSH 金鑰都是它的入口；地端的監控主機不對網際網路開任何連接埠。攻擊者拿下雲端主機之後經由隧道往地端走，就是 [Lateral Movement（橫向移動）](/backend/knowledge-cards/lateral-movement/)：以一台已經拿下的機器當跳板，連到原本從外面連不到的機器。地端主機放在家用或辦公室網路裡時，跳板的下一步是同一個網路裡的筆電、NAS 與印表機，這些裝置從來沒有按面對攻擊者的標準設定過。

Tailscale 的 tailnet 另有一種擴大。同一個帳號底下常常還有個人筆電與手機，tailnet 預設互通時，任何一台個人裝置被入侵都連得到雲端主機的 exporter 與 SSH；反過來，雲端主機被入侵時也連得到那些個人裝置。

評估可達範圍的做法是寫出一張清單，每一列是「發起的機器 → 目的機器：連接埠」，再與實際需要的連線比對。清單上多出來的每一列，都是被入侵時攻擊者多拿到的可達性。

## 地端監控情境需要的連線與連線方向

地端監控情境裡，需要經過隧道的連線全部由地端發起：

| 發起端                       | 目的地                                      | 用途                                              |
| ---------------------------- | ------------------------------------------- | ------------------------------------------------- |
| 監控主機的 Prometheus        | 服務主機上各 exporter 的連接埠（例如 9100） | 讀取指標                                          |
| 監控主機的 Alertmanager      | 服務主機上心跳監看程式的 ping 網址          | 送出 Watchdog 心跳                                |
| 監控主機的 blackbox_exporter | 服務主機上的心跳監看程式                    | 確認心跳監看程式本身還在運作                      |
| 監控主機的 WireGuard         | 服務主機的 WireGuard UDP 連接埠             | 建立與維持隧道（地端在 NAT 後面時由地端主動連出） |

用 Tailscale 時，隧道的建立由 Tailscale 處理，最後一列不需要自己開連接埠。

服務主機沒有任何一條需要主動連到地端的連線，所以地端主機的隧道介面可以只接受「自己發起的連線的回應」，拒絕所有由雲端發起的新連線。雲端主機被入侵之後，攻擊者手上的隧道只能用來回應地端的請求，連不進地端。

這個性質來自兩個選擇，換掉任何一個都要重新評估。

**讀取方向**：Prometheus 由監控主機主動讀取。改成各主機以 remote write 把指標推送到監控主機（兩者的取捨見 [多台主機的指標收集](/backend/04-observability/vendors/prometheus/multi-host-scraping/) 的〈指標回到中央的架構：中央直接讀取與各主機推送〉）時，服務主機要能連到地端的接收端點，地端就得接受一種由雲端發起的連線。這時地端只放行那一個連接埠，接收端點另外要有自己的認證。

**心跳監看程式的位置**：心跳監看程式放在服務主機上、由監控主機送心跳過去。反過來把它放在地端、由服務主機送心跳，同樣要在地端接受一種由雲端發起的連線。

監控主機改放在另一個雲端業者的 VPS 時，需要的連線與上表相同，差別在兩台都面對網際網路，被入侵的機率沒有地端那樣的不對稱。兩台的隧道介面都只放行表上的連線，不能只靠其中一台。

## 限制的設置位置：被入侵端改得到與改不到的限制

雲端主機被入侵、攻擊者拿到 root 時，主機上的一切設定都在他手上：防火牆規則、WireGuard 的設定檔、Tailscale 的用戶端設定。所以收窄可達範圍的限制要依設定存放的位置分成兩種。**被入侵端改得到的限制**存放在可能被入侵的那一台上；**被入侵端改不到的限制**存放在另一端或[控制平面](/backend/knowledge-cards/control-plane/)上。要防的是「雲端主機被入侵之後往地端走」時，只有後一種在入侵發生之後仍然成立。

WireGuard 的 AllowedIPs 同時承擔兩個角色（[WireGuard 官方說明](https://www.wireguard.com/) 的 Cryptokey Routing 一節）：送出封包時它是路由表，目的位址落在哪個 peer 的 AllowedIPs 裡，封包就以那個 peer 的金鑰加密後送給它；收到封包時它是存取清單，解密之後的來源位址不在送出那個 peer 的 AllowedIPs 裡，封包就被丟棄。由這兩個角色推出三件事：

- **地端設定裡寫給雲端 peer 的 AllowedIPs 是被入侵端改不到的限制。** 只寫雲端主機在隧道裡的那一個位址（`/32`），雲端送來的封包就只能以這個位址為來源；攻擊者改雲端自己的設定繞不過，因為檢查發生在地端。
- **雲端設定裡寫給地端 peer 的 AllowedIPs 是被入侵端改得到的限制。** 攻擊者把地端的區網網段加進去，雲端就會把往那個網段的封包送進隧道。這些封包到了地端會不會被轉送進區網，由地端決定：地端主機不開啟 IP 轉送、隧道介面的防火牆拒絕由雲端發起的新連線，攻擊者改了雲端這一側也到不了區網。
- **地端隧道介面的防火牆規則存放在地端，是被入侵端改不到的限制。** 〈地端監控情境需要的連線與連線方向〉一節「地端只接受回應」的規則就屬於這一種。

Tailscale 的存取控制規則（ACL）由每一台裝置對連進來的連線執行，規則由協調伺服器分發，執行時不經過協調伺服器（[Tailscale 的存取控制文件](https://tailscale.com/kb/1018/acls)）。雲端主機被入侵時，攻擊者改不到地端裝置收到的規則，所以 ACL 屬於被入侵端改不到的限制。tailnet 預設全部互通，要先把預設政策換成只允許清單上的連線；用 tag 把伺服器與個人裝置分開，是把可達範圍清單寫成規則的方式。能改寫 ACL 的是 tailnet 的管理帳號，它被盜時這一層限制整個失效，保護方式見〈金鑰與控制平面〉一節。

## VPN 之內仍要的應用層認證

VPN 確認的是封包來自持有金鑰的機器，VPN 裡的服務本身多半沒有認證：exporter 預設沒有認證，連得到連接埠就讀得到主機的全部指標；心跳監看程式的 ping 網址只要知道就能送出心跳或失敗；Prometheus 與 Alertmanager 的 HTTP 介面沒有權限分級，連得到 Alertmanager 就能經由它的 API 建立靜默。這些服務在 VPN 裡要不要再加一層認證，看 VPN 裡還有哪些機器。

VPN 裡只有監控主機與服務主機兩台、可達範圍又已經用被入侵端改不到的限制收到單一來源時，應用層認證是第二道防線。它擋的是限制設錯的情形，代價是每個 exporter 各自的 TLS 與認證設定，做法見 [多台主機的指標收集](/backend/04-observability/vendors/prometheus/multi-host-scraping/) 的〈exporter 的部署位置與連接埠〉。

VPN 裡還有個人裝置、或可達範圍沒有收窄時，應用層認證是第一道防線：VPN 裡任何一台被入侵，網路層都會放行它，擋在服務前面的只剩應用層的認證。

## 監控主機在信任關係裡的位置

監控主機為了工作，要連得到每一台被監控的主機，也存著通知管道的祕密（推播的網址、心跳的 ping 網址、寄信的帳號）與 Grafana 的資料來源設定。它被入侵時，攻擊者同時拿到通往每一台主機的可達範圍，以及讓告警消失的能力，例如在 Alertmanager 建立靜默、改掉通知路由。

讓告警消失的手段依範圍分成兩種。停掉整個告警鏈時，Watchdog 心跳跟著中斷，由心跳監看程式通知。只靜默特定的告警時，Watchdog 照常送出，心跳監看看不出異狀；這時還能發出通知的，是不經過監控主機的觀察者，例如第三方的外部探測直接對服務的公開網址發請求（見 [4.28 單台主機的監控盲區與失效域以外的觀察者](/backend/04-observability/single-host-monitoring-outside-view/)）。所以外部探測在這個配置裡同時承擔可用性與安全兩個責任。

由此推出監控主機的暴露面要比任何一台被監控的主機都小：不對網際網路開任何連接埠，Grafana 經由 VPN 或 SSH 通道看（做法見 [Grafana 的對外存取](/backend/04-observability/vendors/prometheus/grafana-external-access/)）；管理用的 SSH 也走 VPN，並使用與服務主機不同的金鑰，服務主機上外洩的金鑰因此登入不了監控主機。

## 金鑰與控制平面

WireGuard 的金鑰沒有到期日，金鑰的分發也明確不在 WireGuard 的範圍內（官方說明寫的是 key distribution 不屬於 WireGuard 處理的問題）。撤銷一台機器的方法是在另一端把它的 peer 從設定裡刪掉；輪替是產生新的金鑰對、兩端一起換掉。沒有人做這兩件事時，一把外洩的私鑰永遠有效。所以每一把金鑰要有紀錄：放在哪台機器上、什麼時候產生，機器退役或疑似被入侵時，在另一端刪掉它的 peer。這是機器憑證生命週期的一個實例，治理見 [7.6 秘密管理與機器憑證治理](../secrets-and-machine-credential-governance/)。

Tailscale 把金鑰分發交給協調伺服器，信任錨（trust anchor，信任關係最終追溯到的那一方）因此換成 tailnet 的管理帳號與 Tailscale 營運的協調伺服器。

**管理帳號**被盜時，攻擊者可以把自己的裝置加進 tailnet、改寫 ACL，〈限制的設置位置〉一節裡由 ACL 承擔的被入侵端改不到的限制，全部由這個帳號改得到。這個帳號的登入要用攻擊者拿不走的因子，例如 passkey 或安全金鑰（取捨見 [7.39 使用者持有型憑證](../user-held-credential-carrier/)）。

**協調伺服器**負責把每台裝置的公鑰發給其他裝置，它被入侵或作惡時，可以把不屬於這個 tailnet 的節點發給其他裝置。Tailscale 的 Tailnet Lock 讓新節點的金鑰必須帶有 tailnet 內受信任裝置的簽章，其他裝置才接受它，協調伺服器因此無法單方面加入節點（[Tailnet Lock 文件](https://tailscale.com/kb/1226/tailnet-lock)）。完全不依賴第三方協調伺服器的做法是自架協調伺服器（例如開源的 Headscale）或改用自建 WireGuard，代價是金鑰分發與撤銷回到自己手上。

**節點金鑰的到期**：Tailscale 的節點金鑰預設 180 天到期，到期之後那台裝置的連線兩個方向都中斷，直到重新認證（[Tailscale 的金鑰到期文件](https://tailscale.com/kb/1028/key-expiry)）。伺服器常為了避免監控在無人值守時斷線而關掉到期，代價是那台的金鑰變成永久有效，與 WireGuard 相同；關掉時要把它記進金鑰紀錄，撤銷的方式是在管理介面移除那台裝置。

協調伺服器暫時停擺時，已建立的連線繼續運作，新的連線建立不起來（見 [選型：單人遠端 Shell — Tailscale vs Cloudflare Tunnel](../cases/remote-shell-access-tailscale-vs-cloudflare-tunnel/)）。這是一項可用性的依賴，要算進監控主機與服務主機共用的[失效域](/backend/knowledge-cards/failure-domain/)。

## 雲端對雲端與異地備份：沒有共用私網時的接法

兩個雲端業者之間沒有共用的私有網路。一台主機需要連到另一個業者主機上的服務時，做法與地端監控相同：兩台之間建 VPN，列出需要的連線與發起端、照清單收窄可達範圍、把限制放在被入侵端改不到的位置。

異地備份情境不需要可達範圍。服務主機只需要把檔案寫進另一個業者的物件儲存，連線走公開網路與業者的 API，靠的是一把存取金鑰。這時攻擊者的目標從網路移到憑證：服務主機被入侵時，攻擊者拿到的就是那把存取金鑰，它的權限決定備份還在不在。[小型服務的兩到三台主機配置](/operations/06-high-availability/small-service-host-layout/) 把備份放到另一個業者，防的是帳號停權與主機故障；要防「存取金鑰外洩之後備份被刪」，還要在下面三種做法裡至少選一種。

**存取金鑰只給寫入權限**：權限只允許上傳，不允許刪除與覆寫。業者的權限模型能做到這個粒度時直接設定；做不到時看下一種。

**物件的版本保留或鎖定**：物件儲存開啟版本保留時，覆寫與刪除只會產生新版本，舊版本仍在；業者提供物件鎖定（object lock，S3 用的名稱）時，保留期間內的物件連持有完整權限的金鑰也刪不掉。版本保留防得了誤刪，防不了持有完整權限的人連舊版本一起刪除，物件鎖定才防得了連舊版本一起刪除。

**改由備份端拉取**：備份主機定期連到服務主機取資料，服務主機上沒有任何碰得到備份的憑證。代價是方向反過來：備份主機持有讀取服務主機的權限，它的保護要比照〈監控主機在信任關係裡的位置〉一節的監控主機。用 restic 時另有一種折衷：備份伺服器 rest-server 以 `--append-only` 模式執行時只接受新增備份，拒絕刪除與修改既有的備份（[rest-server 的說明](https://github.com/restic/rest-server)），服務主機仍然主動送出備份，而它手上的權限碰不到舊的備份。

這把存取金鑰的機制選型與輪替見 [7.34 機器憑證的機制選型](../machine-credential-mechanism-selection/) 與 [7.6 秘密管理與機器憑證治理](../secrets-and-machine-credential-governance/)。兩邊都是大型雲端、能以工作負載身分聯邦取代長期存取金鑰時，見 [7.10 Workload Identity 與聯邦信任邊界](../workload-identity-and-federated-trust/)。

## 連線本身的紀錄

收窄可達範圍之後，還要知道限制有沒有被試探、設定有沒有被改。

**WireGuard 的握手紀錄**：WireGuard 本身不記錄連線，`wg show` 列出每個 peer 最後一次握手的時間與目前的來源位址（endpoint）。一個只應該從地端連進來的 peer 出現陌生的來源位址、或一個已經退役的 peer 仍有握手，都是要查的訊號。

**Tailscale 的設定變更**：Tailscale 的管理介面記錄設定的變更，例如新裝置加入、ACL 修改。管理帳號被盜時，攻擊者要進入 tailnet 就得加入裝置，所以新裝置加入的通知是這種入侵最直接的訊號；開啟裝置核准（device approval）時，新裝置要經管理者核准才能連線。

**地端隧道介面的丟棄紀錄**：地端隧道介面的防火牆會丟棄由雲端發起的新連線。這類丟棄在正常運作時是零，記下來之後，出現就代表雲端那一側有程式在試著往回連。

這幾項訊號要接到有人看的告警，訊號的取捨與誤報成本見 [7.13 偵測覆蓋率與訊號治理](../detection-coverage-and-signal-governance/)。

## 評估一條跨網路連線的順序

評估從實際需要的連線開始，因為後面每一步都拿它當基準。

1. 列出需要的連線，每一列寫發起的機器、目的機器與連接埠。這張清單決定可達範圍的下限，也決定哪一端只需要發起、不需要接受。
2. 列出目前實際的可達範圍，與清單比對。VPN 的預設通常是全部互通，多出來的每一列都要收回。
3. 每一條收回可達範圍的限制，標記它存放在哪一台。存放在可能被入侵那一台上的限制，入侵之後就不算數；較不可信那一端（面對網際網路的那一台）的限制，要在另一端或控制平面上各有一份。
4. 依 VPN 裡還有哪些機器，決定每個服務要不要加應用層認證。有個人裝置、或可達範圍沒能收窄時，認證是第一道防線。
5. 列出信任錨與撤銷方式：每一把 WireGuard 金鑰在哪台機器上、怎麼撤銷；Tailscale 的管理帳號用什麼因子登入、協調伺服器的權力有沒有用 Tailnet Lock 收回。
6. 靠憑證連接的那一類（異地備份），列出那把憑證能做的每一件事，確認刪除與覆寫不在裡面、或有物件鎖定擋住。
7. 確認連線本身的紀錄有接到告警。

## 這個設計失敗時長什麼樣

以下是依本章的機制推演的一種形態。

一個人把服務放在雲端 VPS，監控主機放在家裡，用 Tailscale 把兩台接起來；為了方便，筆電與家裡的 NAS 也裝了 Tailscale，tailnet 維持預設的全部互通。監控運作正常，exporter 的讀取、心跳與外部探測都沒有異狀。

雲端 VPS 上的應用程式有一個檔案上傳的漏洞，攻擊者以它取得了 shell。tailnet 裡每一台裝置的位址都在 Tailscale 的 `100.x.y.z` 網段裡，攻擊者在雲端主機上掃那個網段，找到 NAS 的檔案分享服務；NAS 在家裡從來沒有面對過攻擊者，管理密碼是出廠時設定的那一組。

監控在整個過程中沒有發出任何告警，因為它量的是服務可不可用，而服務一直可用。攻擊者往回連的每一條連線，在 tailnet 的預設政策下都是被允許的連線，沒有任何一層記下它們。發現的時間點是 NAS 上的檔案被加密、出現勒索訊息的那一天。

讓這條路徑成立的是三件事同時存在：tailnet 預設互通、個人裝置與伺服器在同一個 tailnet、沒有任何一份限制放在雲端以外的位置。三件事任何一件被收回，攻擊者在雲端主機上找不到 NAS：ACL 只允許監控主機連到服務主機時，雲端主機連不到 tailnet 裡的任何一台裝置；個人裝置在另一個 tailnet 時，掃描範圍裡沒有它們。

## 常見風險邊界

- 列不出「發起的機器 → 目的機器：連接埠」這張清單時，可達範圍沒有被決定過，它等於 VPN 的預設，而預設通常是全部互通。
- 收窄可達範圍的限制只存放在面對網際網路的那一台上時，那一台被入侵就等於沒有限制。
- 個人裝置與伺服器在同一個 tailnet、又沒有 ACL 時，任何一台個人裝置被入侵都連得到伺服器，反過來也一樣。
- 監控改成由各主機推送、或心跳監看程式搬到地端時，地端就要接受由雲端發起的連線，原本「地端只發起」的評估要重做。
- WireGuard 的金鑰沒有紀錄、或 Tailscale 的伺服器關掉金鑰到期而沒有記下時，退役與疑似被入侵的機器撤銷不了。
- Tailscale 的管理帳號只有密碼保護時，所有 ACL 的限制都由那一組密碼決定。
- 異地備份的存取金鑰有刪除權限、又沒有物件鎖定時，服務主機被入侵就等於備份可以被刪掉。
- 監控主機對網際網路開放 Grafana 或其他連接埠時，最需要保護的那一台成了最容易進入的那一台。
