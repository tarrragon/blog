本章處理兩個網路之間的連線怎麼設計與評估：地端主機與雲端主機、或兩個雲端業者的主機，以 VPN 或憑證接起來之後，各自對另一端暴露了什麼、限制要放在哪裡。範圍從決定要把兩個網路接起來那一刻開始。文中 WireGuard、Tailscale、Prometheus、物件儲存與 restic 的行為依各自的官方文件寫成，跨主機的限制效果沒有實機驗證。

## 本章的情境與範圍：地端監控與異地備份

本章用兩個情境推導。**地端監控**：監控主機放在地端（家裡或辦公室），經由 VPN 讀取雲端服務主機上的 [exporter](/backend/knowledge-cards/prometheus-exporter/)（把主機或服務的狀態轉成 Prometheus 指標的程式），也經由同一條 VPN 把心跳送到服務主機上的心跳監看程式（[Dead Man's Switch（心跳監看）](/backend/knowledge-cards/dead-mans-switch/)：約定時限內沒收到心跳就通知的程式），這是 [小型服務的兩到三台主機配置](/operations/06-high-availability/small-service-host-layout/) 的配置。**異地備份**：雲端服務主機把備份送到另一個業者的物件儲存，兩邊之間沒有 VPN，只有一把寫入用的存取金鑰。兩個情境分別代表兩種接法：地端監控靠網路上的可達性，異地備份靠一把憑證。

相鄰的主題各有專篇。Tailscale 與自建 WireGuard 之間的選擇（省事，或不依賴第三方的協調伺服器）在 [Tailscale 深入](/linux/tools/remote/tailscale-tailnet-and-relay/) 的〈取捨與邊界〉，Tailscale 的位址模型與中繼在同一篇的前半。同一個雲端業者內的私有網路切分（VPC、subnet）與 security group 在 [網路地基 — VPC、subnet 分層與 security group 設計](/infra/03-network-foundation/vpc-subnet-security-group/)，從網際網路進來的對外入口在 [7.3 入口治理與伺服器防護](../entrypoint-and-server-protection/)。存取金鑰這類機器憑證要用哪一種機制在 [7.34 機器憑證的機制選型](../machine-credential-mechanism-selection/)，跨平台的工作負載身分在 [7.10 Workload Identity 與聯邦信任邊界](../workload-identity-and-federated-trust/)。

## VPN 提供的保證與邊界模型

VPN 在兩個網路之間建立一條加密的隧道，提供三件事：封包在網際網路上傳送時被加密、兩端各自確認對方持有約定的金鑰、兩端各拿到一個在隧道裡固定的位址。WireGuard 以兩端事先交換的公鑰確認對方；Tailscale 建在 WireGuard 之上，由它營運的協調伺服器（coordination server）分發金鑰與位址。

三件事都發生在網路層，回答的是「這個封包是不是從持有那把金鑰的機器送來的」，不涵蓋「這台機器可以使用哪些服務」。VPN 早期的用法把兩個問題合成一個：接進來就算在內網，內網裡的服務彼此信任，這種做法稱為邊界模型（perimeter security）。服務搬上雲端、使用者在遠端工作之後，內網與外網這條線已經不對應任何實體，[7.3 入口治理與伺服器防護](../entrypoint-and-server-protection/#問題節點出現在什麼樣的系統) 描述過這種錯位的後果：一個只需要看一台機器日誌的人，接進來之後連得到整個內網。業界把相反的原則稱為 [Zero Trust（零信任）](/backend/knowledge-cards/zero-trust/)：每一次連線各自通過身分與授權，網路上的位置不構成信任的理由。

兩三台主機的小型服務不需要整套導入零信任的基礎設施，本章借用的是它的問法，用來評估每一條跨網路的連線：發起的是哪一台機器、以什麼身分、連到哪一個服務。發起的機器、身分與目的服務三件事都是工作需要的連線才留下，其餘連得到的位址與連接埠都要收回。

## 隧道兩端的可達範圍

可達範圍是一台機器經由這條連線能主動連到的位址與連接埠。隧道建立之後的預設是雙向的：地端連得到雲端，雲端也連得到地端。Tailscale 新建的 tailnet（同一個 Tailscale 帳號底下互相連通的裝置網路）預設政策讓所有裝置互通（[Tailscale 的存取控制文件](https://tailscale.com/kb/1018/acls)）。WireGuard 兩端連得到對方在隧道裡的位址；地端主機轉送封包、雲端那一側又把地端的區網網段設成經由隧道送出時（常見的設定還會在地端做位址轉換，讓區網裝置的回應回得到隧道），雲端連得到地端主機背後的整個區網。

兩端被入侵的機率不同時，雙向的預設讓較容易被入侵的一端連得到另一端。雲端服務主機對網際網路提供服務，應用程式的漏洞、外洩的 SSH 金鑰都是它的入口；地端的監控主機不對網際網路開任何連接埠。攻擊者拿下雲端主機之後經由隧道往地端走，就是 [Lateral Movement（橫向移動）](/backend/knowledge-cards/lateral-movement/)：以一台已經拿下的機器當跳板，連到原本從外面連不到的機器。地端主機放在家用或辦公室網路裡時，跳板的下一步是同一個網路裡的筆電、NAS 與印表機，這些裝置從來沒有按面對攻擊者的標準設定過。

Tailscale 的 tailnet 另有一種擴大可達範圍的方式。同一個帳號底下常常還有個人筆電與手機，tailnet 預設互通時，任何一台個人裝置被入侵都連得到雲端主機的 exporter 與 SSH；反過來，雲端主機被入侵時也連得到那些個人裝置。

評估可達範圍的做法是寫出一張清單，每一列是「發起的機器 → 目的機器：連接埠」，再與實際需要的連線比對。清單上多出來的每一列，都是被入侵時攻擊者多拿到的可達範圍。

## 地端監控情境需要的連線、發起方向與回應內容

地端監控情境裡，需要經過隧道的連線全部由地端發起：

| 發起端                       | 目的地                                       | 用途                                              |
| ---------------------------- | -------------------------------------------- | ------------------------------------------------- |
| 監控主機的 Prometheus        | 服務主機上各 exporter 的連接埠（例如 9100）  | 讀取指標                                          |
| 監控主機的 Alertmanager      | 服務主機上心跳監看程式的心跳網址（ping URL） | 送出 Watchdog 心跳                                |
| 監控主機的 blackbox_exporter | 服務主機上的心跳監看程式                     | 確認心跳監看程式本身還在運作                      |
| 監控主機的 WireGuard         | 服務主機的 WireGuard UDP 連接埠              | 建立與維持隧道（地端在 NAT 後面時由地端主動連出） |

用 Tailscale 時，隧道的建立由 Tailscale 處理，最後一列不需要自己開連接埠。

服務主機沒有任何一條需要主動連到地端的連線，本章把這個性質稱為**地端單向發起**。它讓地端主機的隧道介面可以套用**只放行回應的規則**：只接受自己發起的連線的回應，拒絕所有由雲端發起的新連線。雲端主機被入侵之後，攻擊者沒辦法經由隧道對地端開啟新的連線。

只放行回應的規則管的是誰能開啟連線，管不到回應的內容，而回應的內容由被入侵的雲端主機決定。Prometheus 讀取 exporter、blackbox_exporter 的 HTTP 探測、Alertmanager 送出 webhook 時，預設都會跟隨 HTTP 轉址（`follow_redirects` 預設為 true）。被入侵的服務主機回一個轉址，指向 `http://192.168.1.10/` 這類區網位址，地端的程式就會自己對區網裝置發出請求；這條連線由地端發起，只放行回應的規則擋不到它。Prometheus 對單次讀取的樣本數與回應大小預設也不設上限（`sample_limit`、`body_size_limit` 預設為 0），一份刻意灌大的回應可以耗盡監控主機的記憶體。所以地端讀取雲端時，把回應當成不可信的輸入：讀取設定、blackbox 的探測模組與 Alertmanager 的 webhook 設定都關掉轉址，Prometheus 的讀取設定加上樣本數與回應大小的上限。被入侵主機回報的指標本身也不可信，它回報一切正常，不代表它實際上正常。

地端單向發起來自兩個選擇，換掉任何一個都要重新評估。

**讀取方向**：Prometheus 由監控主機主動讀取。改成各主機以 remote write 把指標推送到監控主機（兩者的取捨見 [多台主機的指標收集](/backend/04-observability/vendors/prometheus/multi-host-scraping/) 的〈指標回到中央的架構：中央直接讀取與各主機推送〉）時，服務主機不必再開放 exporter 的連接埠，換來的是地端要接受一種由雲端發起的連線：地端只放行接收端點那一個連接埠，接收端點另外要有自己的認證。兩個方向哪個較安全，取決於哪一端較不可信：要保護的是地端時，讀取讓地端維持單向發起；兩端一樣暴露、而 exporter 的連接埠才是要收的那一個時，推送比較划算。

**心跳監看程式的位置**：心跳監看程式放在服務主機上、由監控主機送心跳過去。反過來把它放在地端、由服務主機送心跳，同樣要在地端接受一種由雲端發起的連線。

監控主機改放在另一個雲端業者的 VPS 時，需要的連線與上表相同，差別在兩台都面對網際網路，被入侵的機率沒有地端那樣的不對稱。兩台的隧道介面都只放行表上的連線，不能只靠其中一台。

## 限制的設置位置：被入侵端改得到與改不到的限制

雲端主機被入侵、攻擊者拿到 root 時，主機上的一切設定都在他手上：防火牆規則、WireGuard 的設定檔、Tailscale 的用戶端設定。所以收窄可達範圍的限制要依設定存放的位置分成兩種。**被入侵端改得到的限制**存放在可能被入侵的那一台上；**被入侵端改不到的限制**存放在另一端或[控制平面](/backend/knowledge-cards/control-plane/)（control plane，下發設定與政策的那一層）上。要防的是「雲端主機被入侵之後往地端走」時，只有被入侵端改不到的限制在入侵發生之後仍然成立。

WireGuard 的 AllowedIPs 同時承擔兩個角色（[WireGuard 官方說明](https://www.wireguard.com/) 的 Cryptokey Routing 一節）。每一個 peer（WireGuard 設定裡代表一個對端的區段，含對端的公鑰）各有一份 AllowedIPs：送出封包時它是路由表，目的位址落在哪個 peer 的 AllowedIPs 裡，封包就以那個 peer 的金鑰加密後送給它；收到封包時它是存取清單，解密之後，封包在隧道內的來源位址不在送出那個 peer 的 AllowedIPs 裡，封包就被丟棄。由這兩個角色推出三件事：

- **地端設定裡寫給雲端 peer 的 AllowedIPs 是被入侵端改不到的限制。** 只寫雲端主機在隧道裡的那一個位址（`/32`），雲端送來的封包在隧道內就只能以這個位址為來源；攻擊者改雲端自己的設定繞不過，因為檢查發生在地端。
- **雲端設定裡寫給地端 peer 的 AllowedIPs 是被入侵端改得到的限制。** 攻擊者把地端的區網網段加進去，雲端就會把往那個網段的封包送進隧道。這些封包到了地端會不會被轉送進區網，由地端的防火牆決定：拒絕從隧道介面進來、要轉送到區網的封包，攻擊者改了雲端這一側也到不了區網。只靠「地端主機不開 IP 轉送」不夠可靠，監控主機跑 Docker 時，Docker 啟動時就會開啟 IP 轉送，同時把轉送封包的預設政策設成丟棄（[Docker 的封包過濾文件](https://docs.docker.com/engine/network/packet-filtering-firewalls/)）；擋住區網的是轉送路徑上的規則，要確認它沒有被其他設定改成放行。
- **地端隧道介面的防火牆規則存放在地端，是被入侵端改不到的限制。** 只放行回應的規則就屬於這一種。

Tailscale 的存取控制規則（ACL）由每一台裝置對連進來的連線執行，規則由協調伺服器分發，執行時不經過協調伺服器（[Tailscale 的存取控制文件](https://tailscale.com/kb/1018/acls)）。雲端主機被入侵時，攻擊者改不到地端裝置收到的規則，所以 ACL 屬於被入侵端改不到的限制。規則是單向的：允許監控主機連到服務主機，不等於允許服務主機連回監控主機。tailnet 預設全部互通，要先把預設政策換成只允許清單上的連線；用 tag（Tailscale 替伺服器這類非個人裝置分組的標籤）把伺服器與個人裝置分開，是把可達範圍清單寫成規則的方式：規則寫成「監控主機的 tag 可以連到服務主機的 tag 的哪些連接埠」，個人裝置不在任何一條規則裡。Tailscale 常被描述成零信任網路，而預設政策全部互通的 tailnet 行為接近邊界模型，收窄到清單上的連線之後才符合零信任的問法。能改寫 ACL 的是 tailnet 的管理帳號，它被盜時這一層限制整個失效，保護方式見〈WireGuard 與 Tailscale 的金鑰與控制平面〉一節。

## VPN 之內仍要的應用層認證

VPN 確認的是封包來自持有金鑰的機器，VPN 裡的服務本身多半沒有認證：exporter 預設沒有認證，連得到連接埠就讀得到主機的全部指標；心跳監看程式的心跳網址只要知道就能送出心跳或失敗；Prometheus 與 Alertmanager 的 HTTP 介面沒有權限分級，連得到 Alertmanager 就能經由它的 API 建立靜默（silence，讓符合條件的告警在一段時間內不送出）。這些服務在 VPN 裡要不要再加一層認證，看 VPN 裡還有哪些機器。隧道本身不做認證、後面要疊一層的原則，與對外隧道入口的做法相同，見 [5.10 Outbound Tunnel 入口與生命週期](/backend/05-deployment-platform/outbound-tunnel-entry/) 的〈認證必須疊在 tunnel 之後〉。

VPN 裡只有監控主機與服務主機兩台、可達範圍又已經用被入侵端改不到的限制收到單一來源時，應用層認證是第二道防線。它擋的是限制設錯的情形，代價是每個 exporter 各自的 TLS 與認證設定，做法見 [多台主機的指標收集](/backend/04-observability/vendors/prometheus/multi-host-scraping/) 的〈exporter 的部署位置與連接埠〉。

VPN 裡還有個人裝置、或可達範圍沒有收窄時，應用層認證是第一道防線：VPN 裡任何一台被入侵，網路層都會放行它，擋在服務前面的只剩應用層的認證。

## 監控主機在信任關係裡的位置

監控主機為了工作，要連得到每一台被監控的主機，也存著通知管道的祕密（推播的網址、心跳網址、寄信的帳號）與 Grafana 的資料來源設定。它被入侵時，攻擊者同時拿到通往每一台主機的可達範圍，以及讓告警消失的能力，例如在 Alertmanager 建立靜默、改掉通知路由。

讓告警消失這件事要分故障與入侵兩種情形看。Watchdog 是一條永遠成立的告警規則，Alertmanager 每隔固定時間把它送到心跳監看程式；規則評估、Alertmanager 的路由與送出心跳的那一段任何一處停掉，心跳就中斷。監控主機故障、Prometheus 或 Alertmanager 停掉時，心跳監看程式因此會通知。監控主機被入侵時不同：攻擊者手上有監控主機存的心跳網址，可以停掉 Prometheus 與 Alertmanager 之後自己定時送心跳，也可以只靜默特定的告警、讓 Watchdog 照常送出，兩種做法下心跳監看都看不出異狀。這時還能發出通知的，是不經過監控主機的觀察者，例如第三方的外部探測直接對服務的公開網址發請求（外部探測的位置與成立條件見 [4.28 單台主機的監控盲區與失效域以外的觀察者](/backend/04-observability/single-host-monitoring-outside-view/) 的〈外部探測：使用者看到的結果〉）。外部探測因此也是監控主機被入侵時，服務中斷的告警仍然送得出去的那一條路徑；它偵測不到靜默本身，也偵測不到不影響可用性的入侵。

由此推出監控主機的暴露面要比任何一台被監控的主機都小：不對網際網路開任何連接埠，Grafana 經由 VPN 或 SSH 通道看（做法見 [Grafana 的對外存取](/backend/04-observability/vendors/prometheus/grafana-external-access/)）。管理用的 SSH 也走 VPN，並使用與服務主機不同的金鑰，登入服務主機的私鑰（包括部署流程持有的那一把）外洩時，登入不了監控主機；連到服務主機時不開 SSH agent forwarding，否則服務主機上的 root 可以借用轉送過來的 agent 登入監控主機。

## WireGuard 與 Tailscale 的金鑰與控制平面

自建 WireGuard 的信任錨（trust anchor，信任關係最終追溯到的那一方）是每台機器上的 peer 設定，以及能改寫那些設定的人與部署流程：一台機器接受誰，由它自己設定裡列的公鑰決定。WireGuard 的金鑰沒有到期日，金鑰的分發也明確不在 WireGuard 的範圍內（官方說明寫的是 key distribution 不屬於 WireGuard 處理的問題）。撤銷一台機器的方法是在另一端把它的 peer 從設定裡刪掉；輪替是產生新的金鑰對、兩端一起換掉。沒有人做這兩件事時，一把外洩的私鑰永遠有效。所以每一把金鑰要有紀錄：放在哪台機器上、什麼時候產生、在什麼條件下停用，登記的欄位見 [7.32 機器憑證的配發](../machine-credential-issuance/)。金鑰沒有到期日，回收只能靠登記時寫下的停用條件：機器退役或疑似被入侵時，在另一端刪掉它的 peer。這是機器憑證生命週期的一個實例，治理見 [7.6 秘密管理與機器憑證治理](../secrets-and-machine-credential-governance/)。

Tailscale 把金鑰分發交給協調伺服器，信任錨因此換成 tailnet 的管理帳號與 Tailscale 營運的協調伺服器。

**管理帳號**被盜時，攻擊者可以把自己的裝置加進 tailnet、把機器分享出去、改寫 ACL，〈限制的設置位置〉一節裡由 ACL 承擔的被入侵端改不到的限制，全部由這個帳號改得到。Tailscale 多半經由 Google、GitHub 這類外部帳號登入，這個帳號的登入因子設在那個身分提供者上，要用攻擊者拿不走的因子，例如 passkey 或安全金鑰（取捨見 [7.39 使用者持有型憑證](../user-held-credential-carrier/)）。

**協調伺服器**負責把每台裝置的公鑰發給其他裝置，它被入侵或作惡時，可以把不屬於這個 tailnet 的節點發給其他裝置。Tailscale 的 Tailnet Lock 讓新節點的金鑰必須帶有 tailnet 內受信任裝置的簽章，其他裝置才接受它（[Tailnet Lock 文件](https://tailscale.com/kb/1226/tailnet-lock)）。這一項同時約束協調伺服器與被盜的管理帳號：兩者都無法單方面加入節點，而 ACL 仍由管理帳號改得到。完全不依賴第三方協調伺服器的做法是自架協調伺服器（例如開源的 Headscale）或改用自建 WireGuard，代價是金鑰分發與撤銷回到自己手上。

**節點金鑰（node key）的到期**：新建 tailnet 的節點金鑰預設 180 天到期，到期之後那台裝置的連線兩個方向都中斷，直到重新認證（[Tailscale 的金鑰到期文件](https://tailscale.com/kb/1028/key-expiry)）。裝置第一次以 tag 認證時，金鑰到期預設就是關閉的；伺服器也可以為了避免無人值守時斷線而逐台關掉到期。兩種情形下那台的金鑰都是永久有效，與 WireGuard 相同，所以用 tag 管理伺服器的 tailnet，每一台 tagged 裝置都要當成永久金鑰記進金鑰紀錄，撤銷的方式是在管理介面移除那台裝置。到期造成的斷線，在監控上看起來與 VPN 斷線相同，判讀見 [小型服務的兩到三台主機配置](/operations/06-high-availability/small-service-host-layout/) 的〈監控主機與服務主機之間的連線與連線中斷的誤判〉。

協調伺服器停擺時，已經在 tailnet 裡的裝置照常互通，直到某一台的金鑰到期；新裝置加入不了，ACL 改不了，也撤銷不了任何一台的金鑰（[Tailscale 的協調伺服器停擺說明](https://tailscale.com/docs/reference/coordination-server-down)）。撤銷不了這一項是安全面的代價：停擺期間發現某一台被入侵，只能在那台機器或對端的防火牆上擋，等不到管理介面。可用性那一面要算進監控主機與服務主機共用的[失效域](/backend/knowledge-cards/failure-domain/)（failure domain）。

## 雲端對雲端與異地備份：沒有共用私網時的接法

兩個雲端業者之間預設沒有共用的私有網路。一台主機需要連到另一個業者主機上的服務時，做法與地端監控相同：兩台之間建 VPN，列出需要的連線與發起端、照清單收窄可達範圍、把限制放在被入侵端改不到的位置。

異地備份情境不需要可達範圍。服務主機只需要把檔案寫進另一個業者的物件儲存，連線走公開網路與業者的 API，靠的是一把存取金鑰。這時攻擊者的目標從網路移到憑證：服務主機被入侵時，攻擊者拿到的就是那把存取金鑰，它的權限決定備份還在不在。[小型服務的兩到三台主機配置](/operations/06-high-availability/small-service-host-layout/) 把備份放到另一個業者或帳號，防的是帳號停權、主機故障，以及資料所在帳號的憑證外洩；寫入備份的存取金鑰仍放在服務主機上，要防它外洩之後備份被刪或被覆寫，還要在下面三種做法裡至少選一種。

**存取金鑰只給寫入權限**：權限只允許上傳，不允許刪除。上傳權限在 S3 這類物件儲存裡本身就包含覆寫同名物件，攻擊者用垃圾內容覆寫既有的備份，效果等同刪除；所以只給上傳權限時，要搭配版本保留，或以 bucket 的政策強制只能寫入還不存在的物件名稱（S3 的 conditional write）。業者的權限模型做不到這個粒度時，改用物件的版本保留或鎖定。

**物件的版本保留或鎖定**：物件儲存開啟版本保留（versioning）時，覆寫與刪除只會產生新版本，舊版本仍在，可是持有完整權限的金鑰能把舊版本一起刪掉。業者提供物件鎖定（object lock，S3 用的名稱）時，要看鎖定的模式：S3 的 compliance 模式在保留期間內連 root 帳號也刪不掉；governance 模式下，持有繞過權限的金鑰仍刪得掉（[S3 Object Lock 文件](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html)）。防存取金鑰外洩要用 compliance 模式，或確認那把金鑰沒有繞過權限。

**改由備份端拉取**：備份主機定期連到服務主機取資料，服務主機上沒有任何碰得到備份的憑證。代價是方向反過來：備份主機持有連到服務主機的權限，它的保護要比照〈監控主機在信任關係裡的位置〉一節的監控主機；拉取用的 SSH 金鑰在服務主機的 `authorized_keys` 裡以強制指令（`command=` 與 `restrict`）限制成只能讀備份需要的路徑，否則備份主機拿到的是服務主機的 shell。被入侵的服務主機仍可以交出被竄改或已加密的資料，所以舊的備份要保留多份。用 restic 時另有一種折衷：備份伺服器 rest-server 以 `--append-only` 模式執行時只接受新增備份，拒絕刪除與修改既有的備份（[rest-server 的說明](https://github.com/restic/rest-server)），服務主機仍然主動送出備份，而它手上的權限碰不到舊的備份。這個折衷把目的地從業者的物件儲存換成一台自己營運的主機，那台主機的可達範圍與認證又回到前面各節的評估。

這把存取金鑰的機制選型與輪替見 [7.34 機器憑證的機制選型](../machine-credential-mechanism-selection/) 與 [7.6 秘密管理與機器憑證治理](../secrets-and-machine-credential-governance/)；備份被讀走那一面的收斂（備份加密、備份憑證的日常權限只剩寫入與驗證）在 [7.4 資料保護與遮罩治理](../data-protection-and-masking-governance/)。兩邊都是大型雲端、能以工作負載身分聯邦取代長期存取金鑰時，見 [7.10 Workload Identity 與聯邦信任邊界](../workload-identity-and-federated-trust/)。

## 連線本身的紀錄

收窄可達範圍之後，還要知道限制有沒有被試探、設定有沒有被改。

**WireGuard 的握手紀錄**：WireGuard 本身不記錄連線，`wg show` 列出每個 peer 最後一次握手的時間，以及對端目前的公開位址與連接埠（endpoint）。endpoint 是封包在網際網路上的來源，與隧道內的來源位址是兩件事，AllowedIPs 不限制它。一個已經退役的 peer 仍有握手、或一個 peer 的 endpoint 出現在預期之外的網段，都是要查的訊號；地端在家用網路時公開位址會隨網路業者變動，判讀時比對的是業者的網段，不是單一位址。

**Tailscale 的設定變更**：新裝置加入、機器分享與 ACL 修改都記在 Tailscale 的設定稽核紀錄（configuration audit log）裡，這份紀錄本身不發通知，要變成通知得另外接 webhook 或串流到集中的日誌系統。裝置核准（device approval）讓新裝置要經管理者核准才能連線，它擋得住外洩的使用者帳號或預先產生的認證金鑰，擋不了管理帳號本身被盜，因為核准的人就是管理帳號；擋那一種的是 Tailnet Lock。

**地端隧道介面的丟棄紀錄**：只放行回應的規則會丟棄由雲端發起的新連線。正常運作時這類丟棄只有零星的遲到封包（連線紀錄逾時之後才到的關閉封包）；把狀態異常的封包與新連線分開記錄，新連線出現才代表雲端那一側有程式在試著往回連。

這幾項訊號要接到有人看的告警，訊號的取捨與誤報成本見 [7.13 偵測覆蓋率與訊號治理](../detection-coverage-and-signal-governance/)。

## 評估一條跨網路連線的順序與依賴

評估從實際需要的連線開始，因為後面每一步都拿這張清單當基準。

1. 列出需要的連線，每一列寫發起的機器、目的機器與連接埠。這張清單決定可達範圍的下限，也看得出哪一端只需要發起、不需要接受。
2. 列出目前實際的可達範圍，與清單比對。VPN 的預設通常是全部互通，多出來的每一列都要收回。
3. 對收回可達範圍的每一條限制，標記它存放在哪一台。較不可信那一端（面對網際網路的那一台）上的每一條限制，都要在另一端或控制平面上有一條對應的被入侵端改不到的限制，因為存放在較不可信那一端的限制在入侵之後不再成立。
4. 由清單上的發起方向，找出哪些連線的回應來自較不可信的一端，把那些回應當成不可信的輸入：關掉轉址、限制回應的大小。這一步要用到清單裡的發起端欄位，所以排在清單之後。
5. 依 VPN 裡還有哪些機器，決定每個服務要不要加應用層認證。有個人裝置、或可達範圍沒能收窄時，認證是第一道防線；這一步要用到第 2 步收窄之後的結果。
6. 列出信任錨與撤銷方式：每一把 WireGuard 金鑰在哪台機器上、停用條件是什麼；Tailscale 的管理帳號用什麼因子登入、有沒有開 Tailnet Lock、哪些 tagged 裝置的金鑰不會到期。
7. 靠憑證連接的那一類（異地備份），列出那把憑證能做的每一件事，確認它刪不掉、也覆寫不了既有的備份，或有 compliance 模式的物件鎖定擋住。
8. 確認連線本身的紀錄有接到告警。紀錄要比對的基準是前面幾步定下的清單與設定，所以這一步放在最後。

## 失敗推演：tailnet 預設互通時從雲端主機到家中 NAS 的入侵路徑

以下是依本章的機制推演的一種形態。

一個人把服務放在雲端 VPS，監控主機放在家裡，用 Tailscale 把兩台接起來；為了方便，筆電與家裡的 NAS 也裝了 Tailscale，tailnet 維持預設的全部互通。監控運作正常，exporter 的讀取、心跳與外部探測都沒有異狀。

雲端 VPS 上的應用程式有一個檔案上傳的漏洞，攻擊者以它取得了 shell。tailnet 裡每一台裝置的位址都在 Tailscale 的 `100.x.y.z` 網段裡，預設互通時每一台裝置也看得到其他裝置的名稱，攻擊者不必掃描就找到 NAS 的檔案分享服務；NAS 在家裡從來沒有面對過攻擊者，管理密碼是出廠時設定的那一組。

監控在整個過程中沒有發出任何告警，因為它量的是服務可不可用，而服務一直可用。攻擊者往回連的每一條連線，在 tailnet 的預設政策下都是被允許的連線，tailnet 這一層沒有留下可以告警的紀錄（Tailscale 的連線流量紀錄屬於付費方案、預設關閉）；NAS 自己的登入紀錄有記下那次登入，只是沒有人在看。發現的時間點是 NAS 上的檔案被加密、出現勒索訊息的那一天。

讓這條路徑成立的是兩件事同時存在：tailnet 裡沒有任何被入侵端改不到的限制（政策維持預設互通、也沒有在 NAS 上設防火牆），以及個人裝置與伺服器在同一個 tailnet。任何一件不成立，攻擊者都到不了 NAS：ACL 只允許監控主機連到服務主機時，雲端主機連不到 tailnet 裡的任何一台裝置；只在 NAS 上設防火牆時，NAS 仍在裝置清單裡，但連不進它的檔案分享服務；個人裝置放在另一個 tailnet 時，雲端主機看不到也連不到它們。

## 常見風險邊界：可達範圍、限制位置、回應內容、金鑰紀錄與備份憑證

- 列不出「發起的機器 → 目的機器：連接埠」這張清單時，可達範圍沒有被決定過，它等於 VPN 的預設，而預設通常是全部互通。
- 收窄可達範圍的限制全是被入侵端改得到的限制時，面對網際網路的那一台被入侵就等於沒有限制。
- 個人裝置與伺服器在同一個 tailnet、又沒有 ACL 時，任何一台個人裝置被入侵都連得到伺服器，反過來也一樣。
- 地端讀取雲端時跟隨轉址、或不限制回應大小時，只放行回應的規則擋不住被入侵的雲端主機經由回應把地端的程式導向區網。
- 監控改成由各主機推送、或心跳監看程式搬到地端時，地端不再是單向發起，只放行回應的規則與它的評估要重做。
- 監控主機被入侵時，心跳監看擋不住靜默與偽造的心跳，只剩不經過監控主機的外部探測送得出服務中斷的告警。
- WireGuard 的金鑰沒有紀錄、或 Tailscale 的伺服器以 tag 認證或關掉金鑰到期而沒有記下時，退役與疑似被入侵的機器撤銷不了。
- Tailscale 的管理帳號只靠密碼登入、又沒有 Tailnet Lock 時，所有 ACL 的限制與加入裝置的權力都由那一組密碼決定。
- 異地備份的存取金鑰刪得掉或覆寫得了既有的備份、又沒有 compliance 模式的物件鎖定時，服務主機被入侵就等於備份可以被毀掉。
- 監控主機對網際網路開放 Grafana 或其他連接埠時，最需要保護的那一台成了最容易進入的那一台。
