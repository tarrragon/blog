這篇說明一組關於邊緣安全事件的文章：網站放在 CDN 或 WAF 後面之後，請求在邊緣經過哪幾層處理、每一層的決定在事件紀錄裡留下哪些欄位、邊緣紀錄與源站 access log 怎麼分工、事件頁上的背景流量怎麼分類、各種處置（Block、Challenge、Log、Skip、限流）在紀錄裡代表什麼、哪些事件要即時告警而哪些定期翻閱，以及發現新的請求模式之後怎麼回寫成規則。判讀方法不綁定業者，Cloudflare 是貫穿各篇的實例，AWS WAF 與 Fastly 的對應欄位在各篇並列。

## 這組文章設定的讀者

讀者是替一個對外網站負責的工程師：網站已經放在 CDN 或 WAF 後面（或正在決定要不要放），手上有一個事件頁或一份匯出的紀錄，身邊沒有資安團隊替他判讀。他熟悉 HTTP、DNS 與自己網站的技術堆疊，缺的是判斷事件頁上幾百筆紀錄裡哪些跟自己的網站有關的經驗。典型的情境是有會員資料與訂單的小型電商或會員制網站，網站公開運作一段時間之後，負責的工程師定期翻閱事件頁。

## 請求在邊緣依序經過的處理層

各篇的判斷都建立在同一個機制上：請求在邊緣依序經過幾層處理，每一層各自做一個決定（放行、擋下、要求驗證、只記錄、跳過後面的層），被擋下或被攔住的請求不會到達源站。由這個機制推出三件事：

- **邊緣紀錄與源站紀錄的分工**：被擋下的請求只留在邊緣的事件紀錄裡，源站的 access log 沒有它們；被放行的請求兩邊都有紀錄。兩份紀錄各自涵蓋哪些請求，由請求在哪一層被處置決定，跟用哪一套記錄工具無關。
- **事件的 Action 欄位**：這個欄位記的是哪一層做了什麼決定，所以判讀一筆事件之前，要先知道它是哪一層留下的。
- **事件頁上量最大的那一類**：背景流量多半在最前面的幾層就被處置，所以事件頁上筆數最多的那一類，多半是對這個網站威脅最小的那一類；針對這個網站的請求，要從被放行或只被記錄的事件裡找。

讓流量一定先經過邊緣的前提，也就是源站主機只接受 CDN 來源的連線，寫在 [CDN 後面的源站主機防火牆：只放行 CDN 來源的位置與套用時機、Docker 發佈連接埠的封包路徑、出站 DNS 的限制與地理封鎖](/devops/infra/03-network-foundation/origin-host-firewall/)；這組文章從流量進了邊緣之後寫起。
