這個子系列處理網站放在 CDN 或 WAF 後面之後，邊緣留下的安全事件紀錄：請求在邊緣經過哪幾層處理、每一層的決定留下什麼紀錄、紀錄裡的背景流量怎麼分類、各種處置在紀錄裡代表什麼，以及這些紀錄怎麼排進一個持續運作的監控。判斷方法不綁定業者，Cloudflare 是貫穿各篇的實例，AWS WAF 與 Fastly 的對應欄位在各篇並列。

## 讀者定位

讀者是替一個對外網站負責的工程師：網站已經放在 CDN 或 WAF 後面（或正在決定要不要放），手上有一個事件頁或一份匯出的紀錄，但沒有資安團隊替他判讀。他熟悉 HTTP、DNS 與自己網站的技術堆疊，缺的是「事件頁上那幾百筆紀錄裡，哪些跟自己有關」的判斷經驗。典型的情境是小型電商或會員制網站：有會員資料與訂單，網站公開運作一段時間之後，站長定期翻閱事件頁。

## 推導源頭

各篇的判斷都折算回同一個機制：**請求在邊緣依序經過幾層處理，每一層各自做一個決定（放行、擋下、要求驗證、只記錄、跳過後面的層），被擋下或被攔住的請求不會到達源站**。由此推出：

- 被擋下的請求只存在於邊緣的事件紀錄，源站的 access log 看不到它們；被放行的請求兩邊都有。所以邊緣紀錄與源站紀錄的分工由這個機制決定，不是由工具決定。
- 事件的「Action」欄寫的是哪一層做了什麼決定，判讀一筆事件要先知道它是哪一層留下的。
- 背景流量多半在最前面的幾層就被處置，所以事件頁上量最大的那一類，多半是對這個網站最沒有威脅的那一類；針對性的訊號要從被放行、或只被記錄的那些請求裡找。

上游的源站防火牆系列（[CDN 後面的源站主機防火牆：只放行 CDN 來源的位置與套用時機、Docker 發佈連接埠的封包路徑、出站 DNS 的限制與地理封鎖](/infra/03-network-foundation/origin-host-firewall/)）處理的是「流量一定先經過邊緣」這個前提；本系列從流量進了邊緣之後開始。
