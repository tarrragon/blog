這一篇整理服務與監控放在同一台主機（或同一個失效域）時，監控結構上判斷不了的故障，以及從失效域以外取得訊號的方式。外部服務的挑選與接法另見 [第三方心跳監看與外部探測服務](/backend/04-observability/vendors/prometheus/external-heartbeat-and-probe-services/)，多台主機怎麼分配服務與監控見 [小型服務的兩到三台主機配置](/operations/06-high-availability/small-service-host-layout/)。觀測與被觀測系統一起退化的一般機制在 [4.25 觀測共命運失效](/backend/04-observability/observability-shared-fate/)，這一篇處理的是其中最小的情形：只有一台主機。

## 同一台主機上的監控判斷得到的範圍

監控要判斷一件事，有兩個條件：監控自己的程序在運作，以及它的位置看得到那件事。同一台主機上的 Prometheus 讀得到主機與容器的資源、每個服務的指標，也能從主機內部對各服務發探測請求，這些都在它的位置看得到。它與服務共用同一個[失效域](/backend/knowledge-cards/failure-domain/)：同一台主機、同一個網路出口、同一個雲端帳號。所以失效域本身出事的那幾種故障，在它的位置上看不到，或看到了也送不出去。

**主機整台停掉。** 當機、斷電、雲端業者的維護重開、帳號因為付款失敗被停權，Prometheus 與 Alertmanager 跟著服務一起停。通知端的結果是什麼都沒收到，而「什麼都沒收到」與「一切正常」在收件匣裡看起來相同。

**使用者到主機的路徑中斷。** 網域過期、DNS 設定改錯、憑證過期、雲端業者的網路故障、防火牆規則擋掉外部連線，主機內部一切正常，而使用者連不進來。主機內部的探測走的是容器網路或 `127.0.0.1`，不經過 DNS、不經過公開的網路入口，所以照樣回報成功。以 [4.27 主機過載時的監控告警](/backend/04-observability/host-overload-alerting/) 那個短網址服務為例，它的探測程式 Gatus 跑在同一個 Compose 專案裡，連的是服務名稱，量到的是「容器之間通不通」，不是「使用者連不連得到」。

**告警鏈中斷。** 規則照常評估、告警照常成立，而 Alertmanager 停了，或通知管道的網址打錯、外部的推播服務拒收。Alertmanager 還在運作時，送失敗會留下計數，可以寫成告警（見 [Alertmanager 的通知管道](/backend/04-observability/vendors/prometheus/alertmanager-notification-channels/) 的〈通知送不出去的偵測〉）；而這條告警本身也要經過某一條通知管道，唯一的管道壞掉時它同樣送不出去。

另一種情形是主機過載：探測程式與 Prometheus 自己也在等 CPU，量到的延遲與逾時混進了監控本身的等待，判讀見 4.27 的〈探測程式與 Prometheus 在過載主機上的 CPU 等待〉。

三種故障的共同點是判斷者與被判斷者在同一個失效域裡。在同一台主機上把監控做得更可靠（多跑一份 Prometheus、加大資源）解決不了它們，因為多出來的那一份同樣在這台主機上；要的是一個位置在失效域以外的觀察者。

## 從失效域以外取得訊號的三種方式

失效域以外的觀察者送出的訊號稱為頻外訊號（[out-of-band signal](/backend/knowledge-cards/out-of-band-signal/)）。三種方式各回答一個問題，彼此不能取代。

### 心跳監看：監控與告警鏈還在不在運作

[心跳監看](/backend/knowledge-cards/dead-mans-switch/)（dead man's switch）把判斷反過來：監控持續對外送出「我還在」，外面的監看者在期限內沒收到就通知。Prometheus 上的做法是一條永遠成立的告警規則（`Watchdog`），Alertmanager 定時把它送到監看者的網址；規則評估、路由、送出三段任何一段停掉，心跳都會中斷。所以它同時涵蓋主機整台停掉與告警鏈中斷。

它不回答使用者連不連得到服務。主機照常運作、監控照常送心跳時，DNS 改錯讓使用者全部連不進來，心跳監看看不出任何異常。

成立的條件有三個。監看者在主機的失效域以外：跑在同一台主機上的監看者，主機停掉時跟著停。監看者的通知管道不經過這台主機：它也透過這台主機上的推播服務通知時，心跳中斷的通知會走那條已經停掉的路。心跳的送出間隔小於監看者的期限加寬限：間隔的算法與 Alertmanager 的時間粒度見 Alertmanager 篇的〈Watchdog：告警鏈本身的心跳〉。

### 外部探測：使用者看到的結果

外部探測（synthetic monitoring，也叫 blackbox 探測）從失效域以外，照使用者的路徑對服務發請求：解析公開的網域、經過 HTTPS 與公開的入口，檢查回應的狀態碼與內容。它回答的是使用者連不連得到、回應對不對，涵蓋主機整台停掉與使用者路徑中斷。

它不回答監控還在不在運作。服務照常回應、Alertmanager 已經停了一整天，外部探測全部成功。

成立的條件是探測的位置與路徑：探測端在另一個網路與業者上，請求打的是使用者用的公開網址，而不是主機的 IP 或內部的服務名稱。只檢查狀態碼時，入口回一個錯誤頁也可能是 200，所以要比對回應裡的一段固定內容，或打一個只有服務正常時才回得出來的端點。

### 互相監看：兩個失效域各自當對方的觀察者

手上有兩台落在不同失效域的主機時，兩者可以互為觀察者：主機 B 上跑一個心跳監看程式，接收主機 A 上監控送出的心跳；主機 A 的監控同時讀取主機 B 的指標，B 停掉時由 A 的告警通知。任一台停掉，另一台都會發現。

成立的條件是兩台真的不共用失效域（不同的雲端業者，或一台在雲端、一台在地端），以及兩邊的通知管道彼此獨立：B 上的監看程式直接寄 email 或走另一個推播服務，不經過 A 上的 Alertmanager。剩下的風險是兩台同時停掉，這時沒有任何一方送得出通知；兩台共用某個沒注意到的依賴（同一個 DNS 業者、同一組雲端帳號）會讓這種情形比預期常見，見 [Correlated Failure](/backend/knowledge-cards/correlated-failure/)。

## 外部視角的來源：第三方服務或另一個失效域的主機

三種方式都需要一個在主機失效域以外的位置，這個位置有兩種來源。

**第三方服務。** 心跳監看與外部探測都有現成的託管服務，它們本來就跑在別人的機房與網路上，服務本身的存活也由業者維運。只有一台主機時，這是唯一取得外部位置的方式：在同一台主機上自己做，主機停掉時它跟著停，買不到任何東西。代價是告警的標籤與服務的網址會送到第三方，以及多了一個要管理的帳號與私密網址。挑選條件見 [第三方心跳監看與外部探測服務](/backend/04-observability/vendors/prometheus/external-heartbeat-and-probe-services/)。

**自己在另一個失效域的主機。** 監看程式的邏輯不複雜（記下最後一次心跳的時間、超過期限就通知），開源的心跳監看服務也可以自架。它成立的前提是那台主機與服務主機不共用失效域，而它自己停掉時有人知道，也就是上一節的互相監看。沒有這樣一台主機時，自架的監看程式只是在同一個失效域裡多放一個元件。

兩者的判斷標準是同一個問題：手上有沒有一台不會與服務主機一起停掉、它停掉時也會被發現的主機。有，就自己做；沒有，就用第三方服務。

## 三個觀察者並排時的判讀

心跳監看、外部探測與主機內部的告警各自站在不同的位置。故障發生時，先看哪幾個觀察者失去了訊號，就能在登入主機之前縮小範圍：

| 心跳監看 | 外部探測 | 判讀                                                                                                                                                     |
| -------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 正常     | 正常     | 服務對外可用，監控與告警鏈在運作；內部告警照常判讀                                                                                                       |
| 正常     | 失敗     | 主機與監控在運作，使用者連不進來；查使用者的路徑：網域與 DNS、憑證、公開入口、雲端業者的網路與防火牆。內部告警沒有成立是預期的，它們的位置看不到這條路徑 |
| 中斷     | 正常     | 服務仍在對外服務，監控或告警鏈停了；查 Prometheus 與 Alertmanager 的程序與通知管道。這段時間內部沒有告警不代表沒事                                       |
| 中斷     | 失敗     | 主機整台或它的網路停了；查雲端業者的主控台與狀態頁、主機能不能登入                                                                                       |

只能在本機測試時，所有判斷都來自主機內部，排查從登入主機看程序與日誌開始。多了外部的觀察者之後，排查的第一步換成比對各觀察者看到什麼：外部探測失敗而內部一切正常，問題在使用者的路徑上，登入主機看日誌找不到它；心跳中斷而外部探測正常，服務本身沒事，要修的是監控。

這些外部訊號平時不會觸發，所以要刻意演練一次：停掉 Alertmanager，確認心跳監看在期限後送出通知；把探測的目標網址暫時改成不存在的路徑，確認外部探測的失敗通知會到。驗證備援的一般原則見 4.25 的〈驗證備援：不測的備援是薛丁格的備援〉。
