這一篇整理值班工程師在沒有告警響起的時候，定時要讀哪些訊號、讀它們的理由，以及這些定時檢查和告警規則的分工。範圍是值班的日常：開班、交班與每週一次的營運檢視。告警響起之後的處置在 [8.1 事故分級與啟動條件](/backend/08-incident-response/incident-severity-trigger/) 之後的事故流程；長事故中事故指揮的跨班次交接是另一件事，見 [8.12 IC Handoff 與長事故跨班次協調](/backend/08-incident-response/ic-handoff-long-incident/)。

例子沿用 [4.0 服務端監控的分層](/backend/04-observability/monitoring-layers/) 的短網址服務：一台主機上的入口 Nginx、後端程式、PostgreSQL 與 Valkey，以 Prometheus 與 Alertmanager 監控，失效域以外有心跳監看與外部探測。

## 例行檢查與告警規則的分工

例行檢查讀的是告警規則刻意不通知人的那些訊號。AWS 的 John O'Shea 在 Amazon Builders' Library 的〈Building dashboards for operational visibility〉寫道，任何需要人工檢視儀表板的營運流程都會因人為疏失而失敗，所以 Amazon 以自動告警持續評估最重要的監控資料。這句話定下例行檢查的範圍：一個訊號能寫成「越過某個門檻就通知」的規則，就寫成告警，不靠值班定時去看；例行檢查留給寫不成這種規則、或寫成規則之後不值得叫醒人的訊號。

這些訊號有四種：

- **慢慢變化的趨勢**：磁碟每週多用幾個百分點、佇列的積壓每天晚一點消化完。門檻告警只在越線那一刻通知，越線之前的走向要有人看。
- **需要人判斷才知道是不是故障的狀態**：點擊量比上週少了兩成，可能是轉址出錯，也可能是一個大客戶的活動結束了。規則寫不出這個判斷。
- **要在幾小時內處理、但不值得半夜叫人的故障**：Google 的《The Site Reliability Workbook》在值班章節舉的例子是備份失敗，這類問題在幾個小時內處理就夠，告警應該開單而不是通知值班。開了的單要有人讀，例行檢查就是讀它們的時間點。
- **監控與告警本身的狀態**：還在生效的告警靜音、被暫停的心跳檢查項目、通知太多而被忽略的規則。這一類的故障讓告警不會響，所以只能在告警以外的地方看到。4.0 把它們歸在訊號失真與讀取缺口，見 [4.0](/backend/04-observability/monitoring-layers/) 的〈一層監控檢查的對象與它的缺口〉。

## 開班時讀的訊號

開班檢查的目的是讓接班的人在第一則告警響起之前，就知道系統現在的狀態與還沒結束的事。Google 的值班做法是每一班開始時讀上一班的交班紀錄、結束時寫一份給下一班（見 SRE Workbook 的〈On-Call〉章）。下面每一項都寫了它涵蓋的故障，以及讀到什麼時要動手；項目要依服務增減，判斷依據是這一項讀到異常時，值班是否會因此採取動作。

- **上一班的交班紀錄與還沒結的事件**：知道哪些事正在處理、哪些在等別人。內容見〈交班紀錄的內容〉。
- **生效中的告警靜音（silence）**：[Alert Silence（告警靜音）](/backend/knowledge-cards/alert-silence/) 是人手動設定、在一段時間內不送出符合條件的告警通知。維護時設下的靜音若結束時間設得比維護長，維護結束之後同一條規則再成立，值班也收不到通知。讀的方式是列出每一個靜音的條件、設定者、結束時間與註解，逐一確認它對應的工作還在進行。
- **上一班只送通知、沒有叫人的 warning 告警**：依嚴重度分級時，warning 只送到聊天頻道或信箱，不叫醒人（分級見 [Symptom-Based Alert](/backend/knowledge-cards/symptom-based-alert/)）。沒有人讀的 warning 等於沒有送出。
- **error budget 的消耗**：快速消耗由 [Burn Rate](/backend/knowledge-cards/burn-rate/) 告警通知值班；七天與三十天視窗的緩慢消耗不叫人，要在這裡看它的走向，決定這週還能不能照常發布（見 [Error Budget](/backend/knowledge-cards/error-budget/) 與 [4.6 SLI 量測與 SLO 訊號設計](/backend/04-observability/sli-slo-signal/)）。
- **排程工作與心跳監看的狀態**：昨晚的備份與匯出是否完成。沒有按時送心跳的工作已經由心跳監看通知；這裡要看的是心跳監看服務上有沒有被暫停的檢查項目，被暫停的項目不會通知任何人（見 [Dead Man's Switch](/backend/knowledge-cards/dead-mans-switch/)）。
- **到期事件**：TLS 憑證、網域與第三方 API 金鑰在多久之後到期。有告警規則的項目在這裡只確認規則還在；沒有規則的項目（例如手動續約的網域）只能靠這一項發現。
- **容量的走向**：主機磁碟、資料庫大小、佇列積壓的一週走勢，看它照目前的速度多久之後越過告警門檻。
- **最近的部署與 feature flag 變更**：這一班發生的故障多數與最近的變更有關，開班時知道改了什麼，故障發生時第一個檢查的方向就有了。
- **客服單量與排名在前的錯誤碼**：使用者比監控先發現的故障，會先出現在客服單上。客服回報怎麼分級、哪些會直接通知值班，見 [8.24 客服回報的分級與工程回覆](/backend/08-incident-response/support-escalation-and-engineering-reply/)。

這些項目放在同一個儀表板或同一份清單，開班檢查才會在幾分鐘內做完。以 Alertmanager 為例，生效中的靜音以 `amtool` 列出：

```bash
# 列出生效中的靜音：條件（Matchers）、結束時間、設定者與註解
# --alertmanager.url 換成自己 Alertmanager 的網址
amtool --alertmanager.url=http://localhost:9093 silence query

# 輸出的範例（ID 與時間是佔位的值）：
# ID          Matchers                                          Ends At                  Created By  Comment
# 772ca670-…  alertname="DiskWillFillIn4Hours" instance="db-1"  2026-10-14 12:05:57 UTC  oncall-a    磁碟擴充維護，預計 2 小時
```

讀輸出時對照每一列的 `Ends At` 與 `Comment`：註解寫的維護已經結束而 `Ends At` 還在後面，這個靜音要以 `amtool silence expire <ID>` 提前結束；註解是空的，就找 `Created By` 那個人問它對應什麼工作。設定靜音的人寫註解，是讓下一班讀得出它為什麼存在。

## 交班紀錄的內容

交班紀錄是值班結束時寫給下一班的一份文字，讓下一班知道上一班留下了哪些還沒結束的事。它要寫下來而不只是口頭交代，理由有兩個：下一班可能隔天才開始讀，口頭的內容到時候已經沒有人記得；每週營運檢視要統計值班負擔，資料就來自這些紀錄。

交班紀錄的內容：

- **還沒結的事件**：每一件的現況、下一步、等的是誰。
- **這一班設下的靜音與它的結束時間**：下一班不必從靜音清單反推它為什麼存在。
- **這一班做過的變更**：重啟、手動擴充、改了設定，連同還沒寫回設定檔或版本控制的部分。
- **觀察中、還沒到告警門檻的走向**：例如「資料庫連線數這兩天的尖峰在升高，還沒越過門檻」。
- **客服轉來、還在查的單**：單號與目前查到的地方。
- **這一班被通知的次數與時段**：夜間被叫醒幾次、每一則告警最後是否引發動作，供每週營運檢視統計。

## 每週營運檢視

每週營運檢視是值班、工程與相關角色一起看一週累積下來的訊號，處理單一班次看不出來的走向。Google 的 SRE Workbook 寫到團隊每天早上的站會回顧事故，每月開一次服務檢視會議，也在那個會議上以結構化資料談值班負擔的走向；Amazon 的團隊每週開營運檢視會議，以輪盤（wheel of fortune）隨機挑選要講解的儀表板。隨機挑選的作用是讓每個儀表板都有機會被講解，講不清楚、或數字對不上服務現況的儀表板會在會議上被發現。

每週營運檢視讀的訊號：

- **告警的數量與雜訊**：每一則通知最後是否引發動作。沒有動作的告警要調整門檻、降成 warning 或刪除，流程見 [4.8 訊號治理閉環](/backend/04-observability/signal-governance-loop/)；長期被忽略的告警會讓值班連實際發生的故障也跟著忽略（[Alert Fatigue](/backend/knowledge-cards/alert-fatigue/)）。
- **值班負擔**：一週叫人的次數、夜間被叫醒的次數，從交班紀錄統計。
- **重複出現的客服回報**：客服單以錯誤碼與功能分類之後排名在前的類別，各自回寫成對照表、告警或查詢工具，見 [8.24](/backend/08-incident-response/support-escalation-and-engineering-reply/) 的〈同一類回報重複出現時的回寫〉。
- **SLO 與 error budget 的月走勢**：決定下一段時間發布節奏要不要放慢。
- **交班紀錄裡反覆出現的觀察項**：連續幾週都寫進交班紀錄的同一個走向，候選改寫成告警規則，判斷條件見〈檢查項目改寫成告警的條件〉。

儀表板與告警的整理（沒人看的儀表板合併或淘汰、規則的擁有者）以季為單位做，見 [4.4 dashboard 與 alert 設計](/backend/04-observability/dashboard-alert/) 的〈定期審視〉。

## 檢查項目改寫成告警的條件

例行檢查的每一個項目都要定期確認它還該不該由人看，判斷條件是三項：

- **能不能寫出一個不需要判斷的門檻**：生效超過一天的靜音、三十天內到期的憑證、昨晚沒有完成的備份，都寫得出門檻，改寫成告警之後值班就不必每天看。以 Alertmanager 自己輸出的 `alertmanager_silences{state="active"}` 可以寫出「有靜音持續生效超過一天」的 warning 規則。
- **讀了多少次都沒有動作**：一個項目連續幾週每天都看、每天讀到的都在正常範圍，要嘛改寫成規則，要嘛從清單拿掉。
- **異常時要多快處理**：要在幾小時內處理的，改寫成開單的 warning；要立即處理的，改寫成叫人的告警，這時它本來就不該是例行檢查的項目。

寫不成規則的項目留在例行檢查裡：需要人判斷的業務數字、還在觀察的走向、以及每週營運檢視裡那些要多人一起看的訊號。

單人或兩三人的小團隊不必開會，做法可以縮成每天開工時對著一份清單看五分鐘、每週五花半小時看一週的告警與客服單；要保留的是交班紀錄與靜音的註解，因為少了它們，下一個接手的人（或休假回來的自己）無從知道上一段時間發生了什麼。
