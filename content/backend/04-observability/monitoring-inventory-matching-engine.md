這一篇拿 [4.0 服務端監控的分層](/backend/04-observability/monitoring-layers/) 的監控鏈盤點一個交易撮合系統。系統的功能與需求見 [Backend 範例系統](/backend/case-systems/) 的〈交易撮合〉，它的負載路徑（閘道、依序日誌、單一寫入者的撮合引擎、行情發布）在 [9.0.2 交易撮合的負載路徑](/backend/09-performance-capacity/matching-engine-load-path/)。同一套監控鏈在 [4.0.2 以監控鏈盤點單機短網址服務](/backend/04-observability/monitoring-inventory-single-host/) 與 [4.0.3 以監控鏈盤點 Kubernetes 上的電商 checkout](/backend/04-observability/monitoring-inventory-k8s-checkout/) 用過，這個系統讓其中三件事的答案不同：觀察者能從哪裡讀數字、「沒有訊號」代表什麼、延遲要怎麼量。撮合系統的內部監控各交易所不同，這一篇寫的是從機制推出的做法，引用公開文件的地方寫明出處。

## 觀察者不能進入撮合引擎的處理路徑

撮合引擎以單一執行緒、在記憶體裡依序處理委託，每一筆委託的處理時間以微秒計，延遲目標在毫秒以下。在這條執行緒上做任何一件需要等待的事（寫一行日誌到檔案、更新一個要上鎖的計數器、對外送一個量測封包），都直接加到每一筆委託的延遲上，也讓延遲的尾端變長。所以撮合引擎的觀察者不能像一般服務那樣在程式裡記錄每一個請求：量測本身會改變被量測的對象。

觀察者讀數字的來源因此移到處理路徑以外。撮合引擎每處理一筆委託，結果寫進它自己的輸出日誌（[9.0.2 交易撮合的負載路徑](/backend/09-performance-capacity/matching-engine-load-path/) 的〈成交回報與行情：讓慢的接收端不拖慢撮合引擎〉），另一個程序讀這份日誌，把委託數、成交數、拒絕數、各段的時間戳換算成指標，交給 Prometheus 這類觀察者讀取。引擎自己只維護幾個不需要上鎖的計數（例如已處理的最後一個序號），由別的執行緒定期讀出。這樣的代價是指標比實際的處理晚一點，而好處是觀察者壞掉、變慢時，撮合不受影響。這也決定了監控鏈各層在這個系統裡的位置：自檢與元件指標照常放在主機與程序上，應用層訊號（每一筆委託成功與否、花了多久）不在引擎裡量，在輸出日誌的讀取端量。

## 沒有新委託時，分辨市場安靜與引擎停住

一般服務的監控以「請求失敗」為訊號，撮合系統最難發現的故障卻是安靜：撮合引擎卡在一筆委託上、或日誌失去多數節點而停止接受委託時，不會有任何一筆委託失敗，只是什麼都沒有發生；而市場本身也會有安靜的時候，一個冷門的交易對幾分鐘沒有委託是正常的。只看委託數與成交數，兩種情形在指標上一模一樣。

分辨的做法是讓撮合系統在沒有委託時也產生訊號。撮合引擎每隔固定時間（示意：一秒）往輸出日誌寫一筆心跳紀錄，帶著最後處理的序號；讀取端以「最後一筆輸出紀錄距今多久」寫規則，超過幾秒就是引擎停住，與有沒有委託無關。這是 [Dead Man's Switch（心跳監看）](/backend/knowledge-cards/dead-mans-switch/) 用在處理路徑內部的形式：檢查的對象是撮合引擎的主迴圈還在轉，與告警鏈的心跳是兩件事。行情那一側同樣如此，交易所的行情協定多半有固定間隔的心跳訊息（FIX 協定的 Heartbeat 訊息與 `HeartBtInt` 欄位就是這一類），訂閱端以「多久沒收到任何訊息」判斷行情是否停住，與市場有沒有成交無關。

依序日誌那一層的停住另有一個更早的訊號：健康的節點數。日誌靠多數節點寫入才回應「已接受」，五個節點的叢集停掉三個就失去多數、選不出主節點、停止接受委託（Raft 的論文寫明叢集在任意多數節點運作時才可用，見 [Consensus Protocol](/backend/knowledge-cards/consensus-protocol/)）。所以告警不等到失去多數才成立，在健康節點數降到「再停一個就失去多數」時就送出，那時日誌還在運作，值班還有時間處理。

## 委託延遲的分段量測與時鐘

撮合系統的延遲要依段量，因為使用者感受到的是整段，而能處理的是其中一段。一筆委託的生命週期裡，閘道收到、日誌寫入多數節點、撮合引擎處理完、成交回報送出各記一個時間戳，相鄰兩個時間戳相減就是那一段的延遲：閘道到日誌這一段變長，看日誌節點的磁碟與節點之間的網路；日誌到撮合這一段變長，看撮合引擎的執行緒是不是被搶走了 CPU。延遲以 histogram 記錄、看 p99 與更尾端的百分位數，因為主節點選舉、垃圾回收、一次磁碟寫入變慢都只出現在尾端，而那幾筆委託成交的價格正是使用者會抱怨的那幾筆（[Tail Latency](/backend/knowledge-cards/tail-latency/)）。

這幾個時間戳記在不同的機器上，相減之前要先確定兩台機器的時鐘對得上：兩台機器的時鐘差一毫秒，算出來的一段延遲就差一毫秒，而延遲目標本身就在毫秒以下。所以時鐘同步的狀態本身要監看：node_exporter 的 timex 收集器輸出系統時鐘與參考時間的偏差（`node_timex_offset_seconds`），偏差超過延遲目標的一個比例時，分段延遲的數字就不可信，這是監控鏈裡訊號失真的一種。只在同一台機器上相減的兩個時間戳不受這個影響，所以能放在同一台機器上量的段，優先在同一台機器上量。

## 撮合系統現有的監控與各層的判讀

範例假設這個撮合系統接了以下監控（範例系統的設定，不是實測）：閘道與撮合引擎的程序由 systemd 管理、失敗時重啟；Prometheus 讀取各主機的 node_exporter 與輸出日誌讀取端換算出的指標，讀取端算出每個交易對的委託數、成交數、拒絕數與各段延遲；Alertmanager 依嚴重度送到值班的推播服務；一個監看程序以測試帳號每分鐘對一個測試用的交易對送一筆委託再取消，量從送出到收到取消回報的時間。日誌節點、撮合引擎與監控都在同一個可用區的同一組實體相近的主機上（[9.0.2 交易撮合的負載路徑](/backend/09-performance-capacity/matching-engine-load-path/) 的 Cluster Placement Group 那一段）。

| 監控鏈的層           | 這個系統現有的監控                                   | 判讀                                                                                                                     |
| -------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 容器與程序的自檢     | systemd 管理閘道與撮合引擎，失敗時重啟               | 讀取缺口：重啟沒有規則讀；而且撮合引擎卡在主迴圈裡時程序還在，systemd 看不出來，要靠輸出日誌的心跳                       |
| 服務網路內的探測     | 測試帳號每分鐘對測試交易對送一筆委託再取消           | 檢查範圍盲區：測試交易對與真實交易對在不同的撮合引擎上時，只證明測試的那一個引擎在運作                                   |
| 元件指標             | node_exporter；日誌節點數沒有指標                    | 檢查範圍盲區：健康的日誌節點數沒有人量，失去多數之前沒有預警                                                             |
| 應用層訊號           | 輸出日誌讀取端算出的委託數、成交數、拒絕數與各段延遲 | 訊號失真：時鐘偏差沒有規則讀，跨機器的分段延遲在時鐘漂移時不可信；檢查範圍盲區：沒有心跳紀錄，引擎停住與市場安靜分不出來 |
| 告警規則與分送       | Prometheus 規則與 Alertmanager，送到值班推播         | 訊號失真：延遲的規則以平均值與五分鐘視窗寫，毫秒以下的延遲目標在五分鐘的平均裡看不出尾端                                 |
| 告警鏈的監看         | 無                                                   | 檢查範圍盲區：沒有心跳監看服務；補的觀察者要放在這個可用區以外，日誌節點與監控在同一個可用區，可用區故障時兩者一起停     |
| 使用者路徑的合成監控 | 無                                                   | 檢查範圍盲區：沒有從外部經過公開入口（API 閘道與行情的公開端點）送委託、訂閱行情的探測                                   |

補法依序寫。重啟寫成規則；撮合引擎卡住的偵測交給心跳紀錄，不交給 systemd，因為程序沒有退出。測試委託改成對每一個撮合引擎各有一個測試交易對，或把測試帳號的委託送到每一個引擎負責的其中一個真實交易對、以不會成交的價格掛單再取消（不會成交的價格要遠離市價，否則測試委託可能實際成交，這是從機制推出的做法，交易所是否允許要看規則）。日誌節點數以「健康節點數小於多數加一」寫告警。時鐘偏差以 `node_timex_offset_seconds` 寫規則。延遲的規則改以 histogram 的高百分位數寫，視窗縮短到能看出一次幾秒的停頓（示意：一分鐘），代價是告警更容易被短暫的抖動觸發，所以分成兩條：短視窗的高百分位數送聊天頻道、持續數分鐘的才呼叫值班。

告警鏈的監看與使用者路徑這兩層，觀察者都要放到這個可用區以外：為了延遲把撮合系統放進同一個可用區，同一個可用區的故障就會讓撮合、日誌與監控一起停，而那正是最需要有人被通知的時候。外部的探測從使用者那一端經過公開入口送測試委託、訂閱行情，比對行情的心跳是否持續到達。

## 監控鏈事前偵測不到的異常：逐類查撮合系統

[4.0.1 監控鏈事前偵測不到的異常](/backend/04-observability/monitoring-outside-the-chain/) 那幾類裡，這個系統最重的是資料正確性，因為一筆錯的成交就是一個錯的帳戶部位，而撮合的每一層監控都會照常顯示正常。

**資料正確性**：三種一致要分開檢查。輸出日誌的序號要連續，讀取端（行情發布、成交回報、帳戶更新）以「收到的序號與上一個相差不是一」偵測斷號，斷號代表有一段輸出沒有送到這個讀取端；帳戶的部位要等於它所有成交加總的結果，每天以成交紀錄重算部位，與帳戶系統裡的部位比對；行情公布的最新成交價要等於成交紀錄裡最後一筆的價格，取樣比對。三者都是 [Data Reconciliation](/backend/knowledge-cards/data-reconciliation/)，比對的兩份資料都來自同一份輸出日誌的不同讀取端，所以它們抓的是讀取端各自漏掉或重複處理的紀錄。

**業務結果**：成交量的正常範圍隨市場劇烈變化，與上週同一時段比較沒有意義，可比的是同一時段其他交易對的變化，或同一個交易對在其他交易場所的成交量：其他地方都在成交而這裡沒有，才是異常。交易所處在只收取消、集合競價這類特殊狀態時（[9.0.2 交易撮合的負載路徑](/backend/09-performance-capacity/matching-engine-load-path/) 的停機後重開流程），狀態本身寫成一個指標，告警規則依狀態調整，否則重開期間每一條成交量的規則都會成立。

**到期事件**：用戶端以程式連線，閘道與行情公開端點的憑證到期時，所有程式化的用戶端同時斷線，一起重連，形成一次集中的連線湧入（[9.0.2 交易撮合的負載路徑](/backend/09-performance-capacity/matching-engine-load-path/) 的〈入口閘道：在進入撮合之前能擋下的委託〉寫的重連退避）；憑證到期要在剩下一段天數時告警，與 4.0.1 的做法相同。

**備份**：撮合系統的備份是委託簿的快照加上快照之後的日誌，還原的方式是重放；還原得回來要實際演練一次：在另一個環境載入快照、重放日誌，比對重放後的委託簿與正式環境同一個序號時的委託簿是否相同。重放結果不同，代表撮合引擎的處理有不確定的地方（讀了時鐘或亂數這類不在日誌裡的輸入），這個缺口平常不會出現在任何指標上，只有演練會發現。

**安全**：管理操作（調整交易對的參數、暫停交易、修改帳戶的速率限制）寫進稽核紀錄，與 [4.12 Audit Log 邊界與 PII 治理](/backend/04-observability/audit-log-governance/) 的做法相同；受監管的交易所另有保存委託與成交紀錄的法規要求，不在本篇範圍。

## 三個盤點結果的對照

三個系統用同一套監控鏈盤點，缺口落在不同的地方，而落在哪裡由系統的組成決定。單機短網址服務的缺口多半是少了觀察者或規則；Kubernetes 上的 checkout，工具已經把規則帶進來，缺口藏在路由、探測的對象與不在請求路徑上的消費端與回呼。撮合系統的缺口出在監控的做法本身要改：觀察者不能放進處理路徑、要靠主動產生的心跳才分得出安靜與停住、延遲要分段量而且要先確定時鐘可信，而它為了延遲把撮合、日誌與監控都放進同一個可用區，讓失效域以外的觀察者比另外兩個系統更重要。
