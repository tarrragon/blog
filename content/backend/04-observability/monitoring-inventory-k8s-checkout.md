這一篇拿 [4.0 服務端監控的分層](/backend/04-observability/monitoring-layers/) 的監控鏈盤點一個跑在託管 Kubernetes 上的電商 checkout：把它現有的每一種監控放到所屬的層，逐層判讀還開著的缺口是哪一種、補它要加什麼。四種缺口（檢查範圍盲區、位置盲區、讀取缺口、訊號失真）的定義在 4.0 的〈一層監控檢查的對象與它的缺口〉，盤點時的判讀依據在同一篇的〈以監控鏈盤點一個服務的判讀依據〉。服務的功能與需求見 [Backend 範例系統](/backend/case-systems/) 的〈電商 checkout〉；對照的案例是 [4.0.2 以監控鏈盤點單機短網址服務](/backend/04-observability/monitoring-inventory-single-host/)，那個服務的觀察者全在一台主機上，沒有佇列也沒有第三方。

## checkout 的元件與各自的失效域

這個 checkout 跑在一個雲端帳號、一個區域裡的託管 Kubernetes 叢集上。叢集裡有商品、訂單與付款三個服務，Redis 快取商品與價格，RabbitMQ 連接訂單服務與三個消費端（寄確認信、建立出貨單、更新報表）；訂單存放在同一個區域的託管 PostgreSQL。付款服務呼叫第三方金流建立付款，金流業者在付款完成時對付款服務的回呼端點送出通知；寄確認信的消費端呼叫第三方寄信業者。

這些元件分屬不同的失效域。叢集裡的服務、Redis、RabbitMQ 與跑在叢集裡的監控，共用叢集的控制平面、節點與叢集網路，叢集出事時一起停。託管 PostgreSQL 與雲端業者的監控不在叢集裡，叢集停掉時它們還在，而它們與叢集共用同一個雲端帳號與區域：帳號被停權或區域故障時，它們一起受影響。金流業者與寄信業者在服務的失效域以外，它們停掉時服務照常運作，只是付款或寄信失敗。所以這個服務的位置盲區要對三種失效分開判：叢集停掉、區域或帳號出事、第三方業者停掉。

## checkout 現有的監控與各層的判讀

假設它接了以下監控：每個服務的 liveness 與 readiness 探針（付款服務的 readiness 會呼叫金流業者的 API 確認連得到）；跑在叢集裡的 kube-prometheus-stack（把 Prometheus、Alertmanager、kube-state-metrics、node_exporter 與一組預設告警規則一起安裝的 Helm chart），另加 Redis 與 RabbitMQ 的 exporter；blackbox_exporter 對每個服務的 `/healthz` 探測；服務程式輸出每個端點的請求指標，例外送到 Sentry；Alertmanager 依嚴重度送到值班的推播服務與聊天頻道；託管 PostgreSQL 由雲端業者的監控量測，業者的告警寄到團隊的共用信箱；一個第三方的合成監控服務每分鐘請求首頁、檢查狀態碼。下表每一列是監控鏈的一層，判讀欄只記這一層還開著、沒有被別層接手的缺口：

| 監控鏈的層           | 這個服務現有的監控                                                                         | 判讀                                                                                                                |
| -------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| 容器與程序的自檢     | 每個服務的 liveness 與 readiness；chart 內建的 `KubePodCrashLooping` 規則                  | 讀取缺口（部分）：持續 15 分鐘的 CrashLoopBackOff 會送出，間隔較長的偶發重啟不會；付款服務的 readiness 設計另見下文 |
| 服務網路內的探測     | blackbox_exporter 對各服務的 `/healthz`                                                    | 檢查範圍盲區：只確認各服務回應健康端點，「放進購物車、建立訂單、取得付款頁」這條下單路徑沒有任何探測                |
| 元件指標             | 節點、容器、Redis、RabbitMQ 的 exporter；託管 PostgreSQL 由業者監控                        | 訊號失真：佇列的告警以訊息筆數的固定門檻寫；讀取缺口：資料庫的業者告警寄到沒有人值班看的共用信箱                    |
| 應用層訊號           | 每個端點的請求指標、Sentry                                                                 | 檢查範圍盲區：對金流與寄信業者的呼叫沒有逐依賴記錄成功率與耗時，付款失敗時分不出是金流還是自己                      |
| 告警規則與分送       | Prometheus 規則與 Alertmanager，送到值班推播與聊天頻道                                     | 已涵蓋                                                                                                              |
| 告警鏈的監看         | 無心跳監看服務；chart 內建的 `Watchdog` 規則一直成立，預設路由把它送到不通知任何人的接收端 | 檢查範圍盲區：沒有心跳監看服務；補的觀察者要放在叢集與雲端帳號以外，放在叢集裡的話，叢集停掉時它跟告警鏈一起停      |
| 使用者路徑的合成監控 | 第三方合成監控服務，每分鐘請求首頁、只檢查狀態碼                                           | 檢查範圍盲區：首頁不經過下單與付款，回應內容也不比對；位置已在失效域以外                                            |

叢集內的那幾列，缺口補的是規則、指標與探測的對象；告警鏈的監看那一列，補的是一個位置在叢集與帳號以外的觀察者。偶發的重啟另以 `increase(kube_pod_container_status_restarts_total[1h])` 這類以重啟次數寫的規則讀取。服務網路內的探測要加一條走下單路徑的合成交易：以一個測試帳號與一個測試商品建立訂單、取得付款頁為止，不實際付款，付款那一段改由金流業者的沙箱環境另外探測；測試訂單要能從報表與出貨裡排除，否則它會變成每分鐘一筆出貨單。佇列的告警改以等待時間寫，因為訊息筆數的正常範圍隨流量變化，促銷時的正常筆數會讓固定門檻一直成立，平常的離峰時段卻可能積了一小時的訊息還在門檻以下；佇列沒有直接提供最舊一筆的等待時間時，以筆數除以消費端每秒處理的筆數換算，lag 的意義見 [Consumer Lag](/backend/knowledge-cards/consumer-lag/)。資料庫的業者告警改送到值班會收到的管道：雲端業者的告警多半能送到推播服務或 webhook。叢集內的 Alertmanager 與叢集共用失效域，而雲端業者對資料庫的監控是叢集以外少數還在運作的觀察者，它的告警改送到叢集內的 Alertmanager 會把這個位置的優勢拿掉，所以直接送值班的推播服務。對外依賴的呼叫在付款服務與寄信的消費端各自記成請求指標，以依賴名稱當標籤，金流的失敗率升高時就知道是哪一家。

告警鏈的監看這一層，觀察者要放到叢集以外，而且不在同一個雲端帳號裡。`Watchdog` 規則已經在，通知送失敗的規則 chart 也附了（`AlertmanagerFailedToSendAlerts` 與 critical 的 `AlertmanagerClusterFailedToSendAlerts`，都以 `alertmanager_notifications_failed_total` 寫成），缺的是路由：一條子路由把 `Watchdog` 定期送到失效域以外的心跳監看服務，另一條子路由以同時接走兩條送失敗規則的 matchers 把它們送到同一個服務的另一個檢查項目，只接走前一條時，critical 那一條會走送不出去的原管道。心跳監看服務若跑在同一個雲端帳號的另一個區域，區域故障時它還在，帳號被停權時它一起停；用第三方的心跳監看服務則兩種都不受影響。心跳與送失敗的路由寫法見 [第三方心跳監看與外部探測服務](/backend/04-observability/vendors/prometheus/external-heartbeat-and-probe-services/)，chart 預設的路由與兩條送失敗規則的 matchers 見 [在 Kubernetes 上接上監控](/backend/04-observability/vendors/prometheus/kubernetes-monitoring-entry/) 的〈chart 預設的 Alertmanager 路由：不送任何通知〉。

使用者路徑那一層的觀察者位置已經對了，補的是它檢查的對象：把首頁換成下單路徑的合成交易，並比對回應內容，例如付款頁回應裡有沒有金流業者的付款表單。同一個腳本從叢集內再跑一次，以 Service 名稱直接打訂單與付款服務、不經過入口控制器；兩個位置的同一條探測並排，就能分辨失效落在公開入口還是服務本身，判讀方式見 4.0 的〈使用者路徑的合成監控〉。

## 付款服務的 readiness 納入金流業者時的後果

付款服務的 readiness 呼叫金流業者的 API，這個設計讓一次第三方故障擴大成兩個故障。金流業者的 API 從叢集連不到、或回應慢於探針的逾時時，每一個付款服務的 Pod 都判定自己沒準備好，Kubernetes 把它們全部從 Service 的端點名單拿掉，付款服務不再收到任何請求。使用者送出付款時，入口回的是沒有可用後端的錯誤，而不是付款服務自己寫的「付款暫時無法處理，訂單已保留」；更嚴重的是，付款服務同時也是接收金流回呼的端點，在這段期間金流業者若仍在送回呼（金流的 API 慢、而它的回呼系統正常時就是這樣），付款完成通知全部送不進來，訂單停在待付款，要等金流業者重送回呼，或由對帳找回。金流的 API 時好時壞時，探針反覆通過又失敗，付款服務也跟著反覆上線、下線。

Kubernetes 的文件把「確認必要的後端服務可用」列為 readiness 的用途，這個建議適用的是單一 Pod 個別失去依賴的情形：那個 Pod 下線，其他 Pod 繼續接流量。所有副本共用的外部依賴納入 readiness 時，依賴一停，全部副本同時下線，readiness 原本要隔離的是一個壞掉的副本，結果隔離掉整個服務。金流業者是付款這個功能的依賴，不是付款服務處理請求的前提：它停掉時，付款服務仍然能回應使用者、接收回呼、把訂單標成待付款，在 [Liveness 與 Readiness](/operations/04-service-health/liveness-vs-readiness/) 的依賴分類裡屬於可降級依賴。所以 readiness 只檢查付款服務自己處理請求所需的條件（程序本身與資料庫連線），金流業者的狀態由逐依賴的請求指標與金流業者的狀態頁監看。這一項不屬於四種缺口的任何一種，它是自檢那一層的觀察者本身把一個外部的故障轉成服務自己的故障，盤點時要逐個看 readiness 與 liveness 檢查了什麼。

## 監控鏈事前偵測不到的異常：逐類查 checkout

[4.0.1 監控鏈事前偵測不到的異常](/backend/04-observability/monitoring-outside-the-chain/) 那幾類，這個服務幾乎每一類都有對象，而且大部分沒有人監看。

**業務結果**：每 10 分鐘的訂單數與付款完成數，和上週同一時段比較，低於預期一定比例時告警。付款頁的前端腳本壞掉時，訂單建立的請求照常成功，付款完成數卻歸零，只有這一條規則會成立。

**資料正確性**：每天以金流業者的對帳檔比對資料庫裡付款完成的訂單，兩邊的筆數與金額對不上時告警（[Data Reconciliation](/backend/knowledge-cards/data-reconciliation/)）。金流回呼遺失、重複的回呼讓同一筆訂單入帳兩次，都要靠這一步發現。

**到期事件**：入口的 TLS 憑證由 cert-manager 自動續期，續期失敗時只在 cert-manager 的狀態與日誌裡留下紀錄。cert-manager 輸出兩個可以寫規則的指標（指標名稱出自 cert-manager 的原始碼，官方文件的指標頁沒有列出）：`certmanager_certificate_ready_status{condition="False"}` 為 1 時，代表憑證沒有就緒、續期多半已經失敗；`certmanager_certificate_expiration_timestamp_seconds` 是到期時間，以它減去現在時間寫剩下天數的規則。失效域以外的合成監控也能取得公開網址的憑證到期時間，那一份在叢集停掉時仍送得出預警。另外兩種到期在服務自己手上：對金流業者呼叫用的 API 金鑰、驗證回呼簽章用的密鑰，業者可能設有效期限或要求輪替，到期那一刻付款全部失敗，要記下期限、在剩下一段天數時告警。

**排程工作與背景工作**：三個消費端都沒有端點，blackbox_exporter 探測不到。寄確認信的消費端停掉時，訂單照常成立，使用者收不到信；監看的對象是各佇列最舊一筆的等待時間與死信佇列的筆數，等待時間的門檻依各消費端的需求分開定（確認信幾分鐘，報表幾小時）。每晚的報表工作在完成時送一次心跳。

**備份**：託管 PostgreSQL 由業者自動備份，沒有可以送心跳的工作，預期改寫成「最近一次備份的時間在一天以內」，監看業者記錄的最近備份時間；還原得回來要定期實際還原一次。

**安全**：後台的管理操作與權限變更寫進稽核紀錄，大量匯出訂單或異常的登入來源時告警，見 [4.12 Audit Log 邊界與 PII 治理](/backend/04-observability/audit-log-governance/)。

**第三方依賴**：金流是同步呼叫的依賴，它停掉時付款請求失敗，錯誤率會上升，〈checkout 現有的監控與各層的判讀〉補上的逐依賴請求指標讓它分得出是哪一家；金流的回呼是反方向的依賴，它停掉時服務的每個數字都正常，只有回呼的到達數下降，所以要比對「送出的付款數」與「收到的回呼數」，兩者的差距持續擴大時告警。寄信業者是非同步的依賴，它停掉時只有消費端呼叫失敗與佇列堆積，消費端的逐依賴指標與佇列的等待時間會一起反映。同時訂閱兩家業者的狀態頁，依賴方停掉時的處理見 [8.15 Vendor / 第三方依賴事故處理](/backend/08-incident-response/vendor-dependency-incident/)。

**成本**：叢集的自動擴充設了上限，促銷結束後擴出來的節點是否縮回、日誌量是否因為一個重試迴圈暴增，以雲端業者的預算告警與每個服務的資源用量監看，見 [9.8 效能可觀測性](/backend/09-performance-capacity/performance-observability/) 的〈Cost dashboard〉。

## 與單機短網址服務的盤點對照

兩個服務用同一套監控鏈盤點，缺口卻落在不同的位置。單機短網址服務的缺口集中在失效域以外沒有觀察者、幾個沒有人讀的結果，以及應用層沒有逐端點的請求指標；[4.0.1 監控鏈事前偵測不到的異常](/backend/04-observability/monitoring-outside-the-chain/) 的幾類裡，它沒有佇列也沒有第三方，要查的是業務結果、資料正確性、安全、成本、到期與備份六類。這個 checkout 的監控鏈各層大致齊全，kube-prometheus-stack 把重啟規則、`Watchdog` 與送失敗的規則都預先帶進來，缺口出在三處：探測與合成監控檢查的是健康端點與首頁，而不是下單與付款這條路徑；失效域從一台主機換成叢集、帳號與區域，觀察者要放到哪裡需要對三種失效分開判斷；以及佇列的消費端、第三方的回呼與對帳這些不在請求路徑上的對象，每一類都要另外定義預期。

服務的組成越接近這個 checkout（有非同步的消費端、有外部業者、有金錢上的正確性要求），盤點的工作量越往 4.0.1 那幾類移動。那幾類用得到的指標多半拿得到（佇列的 exporter、憑證的到期時間、業者的備份紀錄），而預期要由了解業務的人決定：多少筆訂單算正常、哪兩份資料該一致、確認信晚多久算太晚，沒有工具能代為決定。監控鏈各層的補法多半可以照工具文件完成，那幾類的補法要從服務自己的需求出發。
