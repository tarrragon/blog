Bot Management（機器人流量管理）是部署在邊緣（edge：CDN、反向代理或負載平衡器這些位在源站前面的元件）的一種判斷機制：替每一個進來的請求估計它是由真人操作的瀏覽器送出，還是由程式送出，再依估計的結果放行、要求挑戰（驗證碼或一段在瀏覽器裡執行的 JavaScript）、限速或擋下。它判斷的對象是發出請求的客戶端，跟比對請求內容形態的 [WAF](/backend/knowledge-cards/waf/) 分工；兩者常由同一個邊緣服務提供。

## 跟其他概念的關係

Bot Management 判斷請求的發送者是什麼；WAF 判斷請求的內容像不像攻擊；[Rate Limit](/backend/knowledge-cards/rate-limit/) 限制單一來源或單一身分在一段時間內送出的請求量。三者處理的對象不同：一個格式完全正常、速率也不高的請求，WAF 與限流都會放行，Bot Management 仍可能依客戶端的特徵判成程式。它判斷的範圍是一個請求與它的客戶端，看不到帳號跨次操作的歷史；帳號層的辨識寫在應用程式自己的紀錄裡，做法在 [7.46 搶票與限量搶購機器人的防護](/backend/07-security-data-protection/ticket-bot-defense/)。大量登入別人帳號的 [Credential Stuffing（憑證填充）](/backend/knowledge-cards/credential-stuffing/) 是它常處理的一種自動化流量。程式送出的請求也有要服務的：搜尋引擎爬蟲、合作夥伴的批次作業、帶 API 金鑰的客戶程式，所以這類服務通常內建已知良性程式的清單，並讓網站設定哪些路徑允許程式存取。

## 可觀察訊號與例子

它用到的訊號是請求本身的特徵（TLS 交握與 HTTP 標頭的特徵是否符合它宣稱的瀏覽器）、在瀏覽器裡執行挑戰的結果（回報的執行環境是否像 [Headless Browser（無頭瀏覽器）](/devops/monitoring/knowledge-cards/headless-browser/) 這類沒有畫面、由程式控制的瀏覽器），以及來源的信譽（來源位址屬於資料中心或已知的代理業者、這個位址過去的行為）。限量開賣頁、登入頁、註冊頁與結帳頁是最常部署的位置，程式在這些頁面上送出一個請求換到的價值最高。售票開賣時，它在邊緣擋下只送 HTTP 請求、不執行 JavaScript 的刷票腳本，這些請求不會進到售票系統後面的排隊與扣庫存（[9.0.1 售票搶購的負載路徑](/backend/09-performance-capacity/ticketing-load-path/)）。前提是源站只接受從邊緣轉來的請求（防火牆只放行 CDN 的位址，或要求邊緣回源時帶憑證）；源站的位址外洩又沒有這一層限制時，腳本直接連源站，邊緣的判斷就被繞過。

## 判斷條件與後果

程式要偽裝成瀏覽器才用得了的頁面上，挑戰與客戶端特徵有效：程式要執行一個完整的瀏覽器才通得過挑戰。通過之後，邊緣發出一段時間內有效的放行憑證（Cloudflare 的 `cf_clearance` cookie 預設 30 分鐘，可以調整），所以攻擊者的成本是每段有效期跑一次瀏覽器，有效期內的請求仍可以用一般的 HTTP 客戶端送出；有效期設得越短，攻擊者重跑瀏覽器越頻繁，真人被重新挑戰的次數也越多。驗證碼放在購票流程的哪一步、通過憑證的效期與只能用一次的取捨，在 [7.48 購票流程的伺服器端檢查](/backend/07-security-data-protection/purchase-flow-server-side-enforcement/)。攻擊者改用真實瀏覽器加上住宅代理（residential proxy，經由一般家用網路的位址轉送請求），或付費請人工代解驗證碼時，客戶端的特徵跟真人相同，這一層的判斷接近失效，辨識要移到應用程式，比對帳號的歷史與帳號之間的關聯。真人經由原生 App 呼叫的 API 同樣沒有瀏覽器可以挑戰，而包在 App 裡的金鑰可以被逆向取出，所以這類 API 改用平台的 App 完整性證明（Apple App Attest、Google Play Integrity）判斷請求是不是來自未被修改的 App；攻擊者可以用一批真實手機產生有效的證明再轉給程式使用，這一層也只是提高成本，辨識照樣要回到帳號的歷史與關聯。以程式為呼叫者而設計的 API 沒有瀏覽器也沒有 App 可以驗證，這一層用不上，防護依賴存取憑證與依金鑰的限流。

判斷有誤判，誤判落在特徵偏離一般瀏覽器的真人身上：共用出口位址的公司與校園、電信業者以 CGNAT（carrier-grade NAT）讓大量手機用戶共用少數對外位址的行動網路、使用輔助工具或隱私保護外掛的使用者。處置設成直接擋下時，誤判的真人看到錯誤頁、沒有通過的路；設成挑戰時，他多花一點時間就能通過，代價是攻擊者付費代解時同樣能通過。所以可信度中等的判斷多半設成挑戰，可信度高的才直接擋下。邊緣元件不負責票或庫存的分配，做不到 7.46 寫的影子封鎖（照常回應、分配時不讓它買到），它能選的處置是放行、挑戰、限速與擋下，而擋下與挑戰都讓攻擊者知道自己被認出了。
