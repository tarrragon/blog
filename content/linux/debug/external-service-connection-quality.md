這篇整理量測對外服務連線品質時用到的觀念與工具：連線品質拆成延遲、掉包與延遲變動、頻寬、應用層回應時間，各自對應使用者感受到的哪一種慢；路上的防火牆、代理伺服器（proxy）與負載平衡器怎麼依量測封包的協定與通訊埠（port）處理它，以及量到的數字在什麼條件下代表服務；`ping` 的 ICMP 往返時間量得到什麼；`tracert` 與 `traceroute` 列出的每一跳延遲怎麼讀；`pathping` 與 `mtr` 的每一跳掉包率怎麼讀；`psping` 與 `curl` 對服務實際使用的 TCP port 量連線時間，以及 `curl` 把一次請求拆成 DNS 解析、TCP 連線、TLS 握手與第一個 byte 回來的時間；`iperf3` 量頻寬時為什麼兩端都要由量測的人控制；接著是同網段主機之間、企業內網經過防火牆連外部 SaaS、經 VPN 連公司內部服務、跨國線路與雲端主機這幾種環境裡，同一個工具量到的是服務流量的狀態還是只有 ICMP 受到的處理；最後把判斷整理成協定、路徑與量的種類這幾項檢查。工具涵蓋 Windows（`tracert`、`pathping`、Sysinternals 的 `psping`）與 Linux（`traceroute`、`mtr`），`curl` 與 `iperf3` 兩邊都有。機器根本連不上（SSH 逾時、虛擬機沒有網路）時從哪一層往下查，寫在[機器連不到或起不來](../machine-unreachable/)；這篇處理的是連得上之後，慢在哪裡、慢的是哪一種量。防火牆規則怎麼設定與長期的自動化監控不在這篇的範圍；從使用者所在地區持續探測時，挑選外部探測服務要看的條件寫在[第三方心跳監看與外部探測服務](/backend/04-observability/vendors/prometheus/external-heartbeat-and-probe-services/#外部探測服務的挑選條件)。

## 連線品質的組成：延遲、掉包與延遲變動、頻寬、應用層回應時間

連線品質由下面幾種各自獨立的量組成，使用者說的「網路很慢」可能指其中任何一種，而每一種要用不同的方法量。

- **延遲**（latency）：一個封包從一端送到另一端要多久。量測工具多半量的是**往返時間**（round-trip time，RTT），也就是封包送出去、對方的回應回到發送端的總時間，所以它包含去程與回程兩段路。延遲高時，每一次一來一往的互動都變慢：一個 API 呼叫要先建 TCP 連線、再做 TLS 握手、再送請求，每一步都至少多花一次 RTT 的時間。
- **掉包**（packet loss）與**延遲變動**：掉包是送出的封包有多少比例沒有到達。延遲變動是連續幾個封包的延遲彼此差多少，通訊領域常寫作 jitter（站上的 [Jitter](/backend/knowledge-cards/jitter/) 卡講的是重試排程裡加入的隨機偏移，是另一個概念）。TCP 遇到掉包時會重送掉的封包，並降低自己的傳送速率，所以少量掉包就會讓下載速度明顯下降；視訊會議與語音通話用 UDP、不重送，掉包直接變成畫面破碎或聲音斷續，延遲變動大時接收端的緩衝區要拉長，對話的延遲也跟著變長。
- **頻寬**（throughput，這裡指實際量到的傳輸速率，不是線路的標稱速率）：單位時間內傳得完多少資料。檔案傳輸、備份、影片串流花的時間主要由這一項決定；一次只傳幾 KB 的 API 呼叫幾乎不受它影響，那類呼叫的時間大多花在延遲上。
- **應用層回應時間**：從發出請求到拿到回應的總時間，由幾段組成：名稱解析（[DNS](/devops/infra/knowledge-cards/dns/)）、TCP 連線建立、TLS 握手、伺服器處理請求、回應傳回來。網路很順而伺服器處理很慢時，前三段都正常，只有伺服器處理請求那一段很長（在 `curl` 的計時裡，這一段落在送出請求到第一個 byte 回來之間）。

延遲、掉包、頻寬與應用層回應時間要用不同的工具量：量延遲的工具量不出頻寬，量網路層的工具也量不出伺服器處理花了多久。所以量測之前，先從使用者的症狀判斷要量的是哪一種：使用者在網頁上每點一次都要等一下，多半是延遲或應用層回應時間；大檔案下載慢、小請求正常，多半是頻寬或掉包；通話斷斷續續，是掉包或延遲變動。

## 防火牆、proxy 與負載平衡器對 ICMP 與 TCP 封包的處理

封包從量測端到目標經過的每一道關卡（中間設備，middlebox：主機防火牆、企業邊界防火牆、雲端的 [Security Group](/devops/infra/knowledge-cards/security-group/)、代理伺服器、負載平衡器）都依封包的協定與 port 決定怎麼處理它，所以用的協定與 port 不同，同一條線路上的兩種封包可能得到完全不同的處理方式。

ICMP（Internet Control Message Protocol）是網路層的控制協定，`ping` 送出的 Echo Request 與對方回的 Echo Reply 都屬於它，`traceroute` 類工具依賴的 Time Exceeded 訊息也是。ICMP 沒有 port，跟網頁流量用的 TCP 443、資料庫連線用的 TCP 3306 是不同的協定，防火牆對它另有一組規則。關卡對 ICMP 常見的處理有下列幾種：

- **丟棄**：企業邊界防火牆與雲端的 security group 常常不放行外部來的 ICMP Echo Request。被丟棄的封包沒有任何回應，發送端等不到回應，最後回報逾時，跟主機沒開機的症狀相同（逾時與被拒的分別見 [Connection Refused vs. Timeout（連線被拒與逾時）](/linux/dotfile/knowledge-cards/connection-refused-vs-timeout/)）。
- **限速**：路由器產生 ICMP 回應要用到它自己的處理器（控制平面，control plane），而轉送一般流量用的是轉送平面（forwarding plane）的專用硬體。為了保護控制平面，路由器多半限制自己每秒回幾個 ICMP，超過的就不回。這會讓 traceroute 類工具在那台路由器所在的那一跳（hop，路徑上的一台路由器，〈tracert 與 traceroute：路徑上每一跳的延遲〉另有說明）看到掉包，而那台路由器轉送一般流量時沒有掉包。
- **不同的優先序**：有些網路設備把 ICMP 排在較低的佇列，壅塞時先延後它；也有網路反過來讓它優先。兩種情形下 ICMP 的延遲都跟服務流量不同。

TCP 443 的流量另外會經過 ICMP 封包不經過的關卡。企業常要求員工電腦對外的 HTTP 與 HTTPS 流量經過 proxy，有的 proxy 還會解開 TLS 檢查內容（TLS inspection）再重新加密；這兩件事都會增加連線時間，而 ICMP 封包不經過 proxy，用 ICMP 量測時量不到這一段。有多條等價路徑（ECMP，equal-cost multi-path）的網路裡，路由器依每一條連線的來源與目的位址、port 計算雜湊值來選路徑，所以 ICMP 封包與某一條 TCP 連線的封包甚至可能走不同的實體線路。負載平衡器與 [CDN（內容遞送網路）](/devops/infra/knowledge-cards/cdn/) 常在邊緣節點就接下用戶端的 TCP 連線，再另開一條連線到後端的服務主機；這時對服務 port 量到的 TCP 連線時間是到邊緣節點的 RTT，不含邊緣到後端那一段，而 ping 負載平衡器的位址時，回應的是邊緣設備本身，或者沒有回應。

由這些處理方式可以推出量測結果代表服務的條件：量測封包用的協定與 port 跟服務相同，而且經過同一組關卡（同一個 proxy、同一條 VPN）。條件成立時，量到的延遲與掉包就是服務流量會遇到的；條件不成立時，量到的數字只描述跟量測封包受到相同處理的那一種流量（用 ping 量時就是 ICMP），所以 ping 很快而服務很慢、ping 不通而服務正常這兩種結果都可能出現。

## ping：ICMP 往返時間與它涵蓋的範圍

`ping` 送出 ICMP Echo Request，對方的作業系統核心收到之後直接回 Echo Reply，不經過任何應用程式。所以它量到的是目標主機的網路層是否回應，以及封包來回一趟的時間。

```bash
# Windows：預設送 4 個，-n 指定個數
ping -n 20 <目標主機>
# Linux：預設持續送到按 Ctrl+C，-c 指定個數
ping -c 20 <目標主機>
```

`<目標主機>` 填要量的主機名稱或 IP 位址；個數取 20 是為了讓統計有意義，只送 4 個時一次偶發的延遲就佔了四分之一。每一行輸出的 `time=` 是那一個封包的 RTT；結尾的統計列出掉包比例，以及 RTT 的最小、平均、最大值（Linux 另外印 `mdev`，是 RTT 的變動幅度，可以當成延遲變動的粗略指標）。Windows 印的 `TTL=`、Linux 印的 `ttl=` 是回應封包抵達時剩下的跳數上限，跟延遲無關。

ping 有兩種結果跟服務的狀態對不上。沒有任何回應時，可能是目標主機不在線上，也可能是路上某一道關卡丟棄了 ICMP，從 ping 的結果分不出是這兩種的哪一種；分得出這兩種的是對服務實際 TCP port 的量測（〈psping 與 TCP 連線時間：量到服務實際使用的 port〉與〈curl 的時間拆解：DNS、TCP、TLS 與第一個 byte〉）：TCP 連線建立得起來，代表目標在線、只有 ICMP 被丟棄。回應正常而服務很慢時，ping 的回應只代表網路層來回順暢，服務流量經過的 proxy、TLS 檢查與伺服器處理都不在它量到的範圍裡。

ping 量到的延遲代表服務流量，需要〈防火牆、proxy 與負載平衡器對 ICMP 與 TCP 封包的處理〉推出的條件成立：兩台主機之間每一道關卡對 ICMP 與服務流量的處理相同，服務流量也不經過 proxy。同一個網段或同一個資料中心裡的兩台主機之間沒有邊界防火牆，常滿足這個條件，但兩端的主機防火牆仍可能對 ICMP 另訂規則：Windows 防火牆預設的入站規則不放行 ICMP Echo Request 時，對那台 Windows 主機 `ping` 逾時，而它的服務照常回應。經過網際網路的兩台主機，條件是否成立從這一端看不出來；拿同一個目標的 ping 與對服務 port 的 TCP 量測比對，兩者的 RTT 與掉包相近時，ping 的數字可以代表服務流量。

## tracert 與 traceroute：路徑上每一跳的延遲

`tracert`（Windows）與 `traceroute`（Linux）列出封包從本機到目標經過的每一個路由器（每一個稱為一跳，hop），以及到每一跳的 RTT。它們利用的是 IP 封包裡的 TTL（time to live）欄位：每經過一個路由器 TTL 減一，減到 0 時那個路由器丟棄封包並回一個 ICMP Time Exceeded 給發送端。工具依序送出 TTL 為 1、2、3……的探測封包，工具從每一跳回的 Time Exceeded 讀出那一跳的位址，並以探測封包送出到收到回應的時間算出 RTT，直到目標本身回應為止。

```bash
# Windows：探測封包是 ICMP Echo，-d 跳過把位址反查成名稱（反查很慢）
tracert -d <目標主機>
# Linux：預設探測封包是 UDP；-I 改用 ICMP，-T 改用 TCP SYN，這兩種都需要 root；搭配 -T 時 -p 指定固定的目的 port
traceroute -n <目標主機>
sudo traceroute -n -T -p 443 <目標主機>
```

`tracert` 帶 `-d`、`traceroute` 帶 `-n` 時，工具不對每一跳的位址做反向名稱解析（reverse DNS lookup），輸出只印位址、跑得比較快。Linux 那一條帶 `-T -p 443` 時，`traceroute` 送出的探測封包改成對 443 port 的 TCP SYN，跟 HTTPS 服務用同一個協定與 port；`443` 換成服務實際使用的 port。企業防火牆擋掉 UDP 或 ICMP 探測時，這個版本的探測封包常常比預設版本多通過幾跳。Windows 的 `tracert` 只能用 ICMP。

每一跳的延遲有兩種讀法要分開。某一跳的延遲比前後都高、而後面幾跳又降回來時，延遲高的是那個路由器產生 Time Exceeded 回應的時間（〈防火牆、proxy 與負載平衡器對 ICMP 與 TCP 封包的處理〉寫到的控制平面），它轉送流量並沒有變慢：送往後面幾跳的探測封包也要經過這個路由器轉送，而後面幾跳量到的延遲比這一跳低，所以多出來的時間只發生在這個路由器自己產生回應的時候。延遲從某一跳開始升高、而且一路延續到目標時，那一跳之後的線路才是延遲增加的位置；量測跨國線路時，常在出國的那一跳看到這種持續的升高，那段延遲來自光在海底電纜裡傳遞的距離，換一家業者也降不到 0。某一跳整行顯示 `* * *`（逾時）時，代表那個路由器不回 Time Exceeded，後面的跳數還有回應就表示流量照樣通過它。

每一跳的 RTT 包含回程，而回程走的路徑可能跟去程不同（非對稱路由，asymmetric routing），`traceroute` 只列得出去程。所以某一跳的延遲升高，也可能發生在那一跳回程經過的某一段，從這一端量不出來；對端是自己控制的主機時，從對端往這一端跑一次就看得到回程；對端是外部 SaaS 時，回程從這一端量不出來。

## pathping 與 mtr：每一跳的掉包率

`pathping`（Windows）與 `mtr`（Linux）在 traceroute 的路徑上持續對每一跳送探測，統計一段時間內每一跳的掉包率與延遲分布。單次的 `tracert` 只對每一跳送三個探測，從它的結果看不出偶發的掉包；`pathping` 預設對每一跳送 100 個，`mtr` 送幾個用 `-c` 指定，送得夠多時看得出間歇性的掉包。

```bash
# Windows：先找路徑，再對每一跳送 -q 個探測（預設 100 個，間隔 250 毫秒）
pathping -n <目標主機>
# Linux：-r 跑完輸出報表，-w 不截斷主機名稱，-c 每一跳送幾個探測
mtr -rw -c 200 <目標主機>
# Linux：改用對 443 port 的 TCP 探測
mtr -rw -c 200 --tcp --port 443 <目標主機>
# Linux：改用對服務 UDP port 的 UDP 探測
mtr -rw -c 200 --udp --port <服務的 UDP port> <目標主機>
```

`pathping` 的預設值讓它每一跳要花約 25 秒（100 個探測乘以 250 毫秒），路徑有十幾跳時要等好幾分鐘才出結果；`-n` 跟 `tracert -d` 一樣是不反查名稱。`mtr` 的 `-c 200` 是跑 200 輪、每一輪對每一跳送一個探測，一輪約 1 秒，所以約跑 3 分多鐘；輪數越多，掉包率的統計越穩定，`mtr` 跑的時間也越長。`mtr` 接收各跳回的 ICMP Time Exceeded 要用 raw socket 的權限，ICMP、TCP、UDP 三種模式都一樣；多數發行版安裝時已替 `mtr` 的 `mtr-packet` 加上 `cap_net_raw` 或 setuid，所以這幾條都不必 `sudo`，自行編譯而沒有這一步時都要。`443` 換成服務實際使用的 port；通話這類服務的媒體多走 UDP，`--udp` 那一條的 port 查業者公布的網路需求。`--tcp` 與 `--udp` 每一輪都對目標的服務 port 送一次探測，對外部服務長時間跑時，對方可能把量測端當成掃描而限速，輪數取涵蓋症狀時段所需的最少數量。量間歇性的掉包時，跑的時間要涵蓋使用者反映慢的那段時間。

`pathping` 結果裡每一跳的「Source to Here」欄是從本機到這一跳的掉包率；「This Node/Link」在列出 IP 的那一列是那台路由器本身沒回應的比例（多半是它在限制回 ICMP），在兩台路由器之間、Address 欄印成 `|` 的那一列是那段線路轉送封包時掉的比例。`mtr` 的 `Loss%` 欄對應的是 `pathping` 的「Source to Here」，也就是從本機到那一跳的掉包率；`StDev` 欄是延遲的標準差，數值大代表延遲變動大。讀掉包率時，跟〈tracert 與 traceroute：路徑上每一跳的延遲〉讀延遲的道理相同，路由器自己回應的速度與比例不代表它轉送流量的情形：

- **掉包只出現在中間某一跳、後面幾跳與目標都是 0%**：那個路由器在限制自己回 ICMP 的速率（〈防火牆、proxy 與負載平衡器對 ICMP 與 TCP 封包的處理〉的限速），它轉送給後面的流量沒有掉。這一跳的數字不代表服務流量會掉包。
- **掉包從某一跳開始出現、一直延續到目標**：從那一跳或它前面那段線路開始，流量確實在掉。這個位置是向網路業者回報時最有用的證據：讀報表的人從它就能把掉包定位在某一段，而延續到目標的數字顯示受影響的是一般流量。
- **只有目標本身掉包、路上每一跳都是 0%**：目標主機或它前面的防火牆在限制或丟棄探測封包；改用跟服務相同協定與 port 的探測（`mtr --tcp --port 443`）再量一次，才分得出是服務流量也在掉、還是只有 ICMP 被限速。

## psping 與 TCP 連線時間：量到服務實際使用的 port

對服務實際使用的 TCP port 量連線建立的時間，是讓量測封包跟服務流量經過同一組防火牆規則的直接方法。TCP 建立連線要三次交握（three-way handshake）：用戶端送 SYN，伺服器回 SYN-ACK，用戶端再送 ACK。從送出 SYN 到收到 SYN-ACK 的時間，大致等於一次網路 RTT 加上伺服器作業系統核心回應的時間；它不包含伺服器上應用程式處理請求的時間，因為三次交握由核心完成，應用程式這時還沒讀到任何資料。

```bash
# Windows（Sysinternals psping）：對 443 port 建立 20 次 TCP 連線並統計時間
psping -n 20 <目標主機>:443
```

`psping` 由微軟的 Sysinternals 發布，不隨 Windows 內建，要另外下載；不能安裝時，PowerShell 內建的 `Test-NetConnection <目標主機> -Port 443` 印出 `TcpTestSucceeded`，只顯示連線是否建立、不印連線時間，HTTPS 服務的時間改用內建的 `curl.exe -w` 量。`<目標主機>:443` 的冒號後面是要量的 port，填服務實際使用的那一個（HTTPS 是 443，SQL Server 預設是 1433）；給了 port，`psping` 就做 TCP 連線量測，不給 port 時它做的是跟 `ping` 一樣的 ICMP 量測。輸出最後一段的 Minimum、Maximum、Average 是連線時間的統計；`psping` 預設把開頭第一次連線當成暖身（warmup）不列入統計，次數用 `-w` 改。`-n 20` 的個數取法跟 `ping` 相同：次數太少時，平均值主要反映的是一次偶發的慢連線。

`psping` 另外能量頻寬（`-b`）與指定大小的資料往返延遲（`-l`），這兩種模式需要對端也跑 `psping -s` 當伺服器，所以只能用在兩端都由量測的人控制的環境，跟〈iperf3：兩端都跑量測程式的頻寬量測〉屬於同一類量測。

Linux 上對 HTTP(S) 服務量同一件事，用的是 `curl -w` 的 `time_connect`（讀法在〈curl 的時間拆解：DNS、TCP、TLS 與第一個 byte〉）；服務不是 HTTP(S)（例如資料庫的 port）時，`hping3 -S -p <port> -c 20 <目標主機>` 送出 TCP SYN 並印出每一個 SYN-ACK 回來的時間，作用跟 `psping <目標主機>:<port>` 相同，`hping3` 要自己組封包，需要 root，多數發行版也要另外安裝。

`psping` 的 TCP 連線量測代表服務流量的前提，是服務流量也直接用 TCP 連到目標。企業要求對外流量經過 proxy 時，用戶端直接連目標的 443 port 會被邊界防火牆擋下，`psping` 只量得到逾時，而瀏覽器經由 proxy 照樣用得了服務。這時服務流量實際走的是「用戶端 → proxy → 目標」，量測封包要經過同一個 proxy，量到的數字才代表它；`curl` 會照 proxy 的設定連線，經由 proxy 量連線時間的讀法寫在〈curl 的時間拆解：DNS、TCP、TLS 與第一個 byte〉。

## curl 的時間拆解：DNS、TCP、TLS 與第一個 byte

`curl` 帶 `-w` 時，在請求結束之後照格式字串印出指定的計時變數，把一次 HTTPS 請求拆成幾個時間點。每一個變數都是從請求開始累計到那個時間點的秒數，所以相鄰兩個變數相減，才是那一段花的時間。

```bash
curl -o /dev/null -s -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' https://<目標主機>/<路徑>
# 經由指定的 proxy 連線：-x 後面填瀏覽器實際使用的 proxy
curl -x http://<proxy 主機>:<proxy port> -o /dev/null -s -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' https://<目標主機>/<路徑>
```

`curl` 帶 `-o /dev/null` 時把回應內容寫進 `/dev/null` 丟掉，帶 `-s` 時不印進度列，輸出只剩 `-w` 那一行。`<目標主機>/<路徑>` 填服務實際被呼叫的網址，例如某個 API 的端點；用首頁量的話，量到的是首頁的處理時間，不一定是使用者反映慢的那一個端點。網址會轉址（回 3xx）時，不加 `-L` 量到的只是那一個轉址回應，加了 `-L` 時各個計時變數是每一次請求的加總，下面這張表的相減讀法就不成立；所以先用 `curl -s -o /dev/null -w '%{redirect_url}\n' <網址>` 取得轉址的目的地，再對最後那一個網址量。一次量測只代表那一刻，偶發的慢要把同一條指令跑 20 次左右看分布，理由跟 `ping` 送 20 個相同。格式字串另外加 `ip=%{remote_ip}` 時會印出這次連到的位址，兩次量測打到不同的 CDN 邊緣或不同的位址族（IPv4／IPv6）時從這一欄看得出來。Windows 10（1803 版）以後內建 `curl.exe`，在 PowerShell 裡要打 `curl.exe`，因為 Windows PowerShell 把 `curl` 當成 `Invoke-WebRequest` 的別名；在 Windows 上 `-o` 那一項要寫成 `-o NUL`；在 cmd.exe 裡，cmd 不把單引號當成引號，格式字串外面的單引號要改成雙引號，寫進批次檔時每個 `%` 要改成 `%%`。

各段的讀法：

| 相減的變數（第一列直接讀）               | 這一段的時間                                                  | 這一段很長時代表                                                                                                                                                                                                                                                                                                                                                         |
| ---------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `time_namelookup`                        | DNS 解析                                                      | 本機或公司的 DNS 伺服器回應慢，或快取沒有命中                                                                                                                                                                                                                                                                                                                            |
| `time_connect` − `time_namelookup`       | TCP 三次交握，約一次 RTT                                      | 網路延遲高，或連線經過的防火牆或 proxy 處理慢                                                                                                                                                                                                                                                                                                                            |
| `time_appconnect` − `time_connect`       | TLS 握手，TLS 1.2 約兩次 RTT，TLS 1.3 約一次                  | 延遲高，或路上的 TLS 檢查在解密重新加密                                                                                                                                                                                                                                                                                                                                  |
| `time_starttransfer` − `time_appconnect` | 送出請求到第一個 byte 回來：一次 RTT 加上伺服器處理請求的時間 | 這一段減掉一次 RTT 之後仍然很長時，慢在伺服器處理請求；RTT 可以用上面 `time_connect` − `time_namelookup` 那一段估計（直連時它約等於一次 RTT），經過 proxy 時那一段量的是到 proxy 的 RTT，估不了到目標的 RTT，這一段也還含 proxy 轉送請求的時間；服務前面有在邊緣接下 TCP 連線的負載平衡器或 CDN 時，那一段是到邊緣的 RTT，扣掉之後剩下的還含邊緣到後端的往返與邊緣的處理 |
| `time_total` − `time_starttransfer`      | 回應內容傳完                                                  | 回應很大而傳輸速率不足，或傳輸中掉包重送                                                                                                                                                                                                                                                                                                                                 |

TLS 握手的時間另外寫在 [TLS Handshake（TLS 握手）的成本與連線重用](/backend/knowledge-cards/tls-handshake-cost/) 卡；讀這張表只需要知道 TLS 握手佔幾次 RTT。`curl` 每次執行都建新連線，量到的是第一個請求的時間；瀏覽器與 App 重用連線時，之後的請求不再付 TCP 與 TLS 這兩段，連線重用怎麼改變每個請求分攤的成本也寫在那張卡。

`curl` 會讀 `https_proxy`、`http_proxy`、`all_proxy` 這幾個環境變數（`http_proxy` 只讀小寫，其餘大小寫都讀、小寫優先；Windows 的環境變數不分大小寫），設定了就經由 proxy 連線（列在 `NO_PROXY` 裡的主機除外），也可以用 `-x <proxy 位址>` 直接指定，所以 `curl` 送出的請求能跟走 proxy 的服務流量走同一條路。瀏覽器用的 proxy 常來自作業系統的 proxy 設定或公司發的 PAC 檔（一段替每個網址選 proxy 的腳本），`curl` 不讀這兩種來源，所以量測之前要從瀏覽器或系統的 proxy 設定查出瀏覽器實際用的 proxy 位址，再寫進 `https_proxy` 或 `-x`；proxy 要求認證時回 `407`，Windows 網域環境的 proxy 多半用整合認證，`curl` 加 `--proxy-negotiate -U :` 時沿用目前登入的身分；沒有設定的話，`curl` 直接連目標，量到的就不是瀏覽器走的那條路。經過 proxy 時各段的意思會跟著改變：`time_connect` 量的是到 proxy 的 TCP 連線；`curl` 把目標的名稱交給 proxy 解析，`time_namelookup` 只剩解析 proxy 本身名稱的時間，proxy 設成 IP 位址時接近 0（這是 HTTP proxy 的行為，`socks5://` 的 proxy 由本機解析目標名稱）；proxy 到目標的 TCP 連線與 TLS 握手都算進 `time_appconnect`。proxy 在本機或同一個區網時，`time_connect` 接近 0，proxy 之後那段路程（proxy 到目標的 TCP 連線、TLS 握手與 proxy 自己的處理）花的時間全部算進 `time_appconnect`。所以在 proxy 環境讀這張表時，`time_appconnect` 那一段很長，要把 proxy 到目標的延遲與 proxy 自己的處理都算進可能的成因。

## iperf3：兩端都跑量測程式的頻寬量測

頻寬的量測要一端持續送資料、另一端接收並計算速率，所以兩端都要跑量測程式。`ping`、`traceroute`、`psping` 的 TCP 連線量測只需要對方回應封包，任何主機都量得到；頻寬量測做不到這一點，對一個外部 SaaS 量不了 `iperf3`，因為那家服務不會替量測的人跑 `iperf3` 伺服器。

```bash
# 對端：啟動伺服器，預設聽 TCP 5201
iperf3 -s
# 本機：對對端量 10 秒，預設方向是本機送出（上傳）
iperf3 -c <對端主機> -t 10
# -R：方向反過來，對端送、本機收（下載）
iperf3 -c <對端主機> -t 10 -R
# -P 4：同時開 4 條 TCP 連線
iperf3 -c <對端主機> -t 10 -P 4
# -u -b 50M：改用 UDP、以每秒 50 Mbit 送，接收端回報掉包率與延遲變動
iperf3 -c <對端主機> -u -b 50M
```

`<對端主機>` 填跑著 `iperf3 -s` 的那一台；兩端之間的防火牆要放行 TCP 5201，用 `-u` 時另外放行 UDP 5201（控制連線仍走 TCP）。企業網路與雲端的 security group 預設不放行沒有明列的入站 port，這個預設讓主機只暴露服務本身用到的 port；為了量測開放 5201 時，規則的來源限定在量測端的位址、量完就移除的話，`iperf3 -s` 對外暴露的範圍只有量測端、時間只到量測結束；規則留著時，任何連得到那台主機的人都能拿它佔用頻寬。是否開放由管網路的人決定。`iperf3` 帶 `-t 10` 時量 10 秒，涵蓋 TCP 爬升到穩定速率之後的一段時間，時間拉長，平均值受起始階段與偶發波動的影響越小；`-P 4` 的 4 條連線是比單條多到看得出差異的數量，條數加到總和不再上升時，限制來自線路容量。`-R` 把傳送方向反過來，而上傳與下載的線路容量在多數接取線路上不同，所以使用者反映下載慢時，代表那個症狀的是 `-R` 量到的速率。UDP 模式的 `-b` 是送出的速率，區塊裡的 `50M` 是示範值，填接近服務實際用到的速率（例如視訊會議的位元率）時，量到的掉包與延遲變動才對應服務的負載，但這些數字代表的是本機到那台對端的路徑，通話服務的媒體流量送到業者的中繼伺服器，路徑不同；報表裡的 `Jitter` 與 `Lost/Total Datagrams` 就是〈連線品質的組成：延遲、掉包與延遲變動、頻寬、應用層回應時間〉裡的延遲變動與掉包。

單一 TCP 連線的速率受延遲與掉包限制：TCP 在收到對方確認之前送出的資料量，受接收視窗（receive window）與壅塞視窗（congestion window）兩者中較小的那個限制，所以一條連線的速率上限大約是視窗大小除以 RTT，掉包又會讓 TCP 降低傳送速率。所以跨國這種 RTT 長的線路上，單一連線量到的速率可能遠低於線路容量（線路的標稱速率），`-P 4` 量到的總和明顯較高時，限制來自單一連線的視窗與延遲，不在線路容量。這個差異對應到服務的行為：一次只用一條連線下載的程式，在長延遲線路上就會慢，加大線路容量也改善不了。

對外部服務量頻寬，可行的做法有兩種。一種是在跟那家服務同一個雲端區域開一台自己控制的主機跑 `iperf3 -s`，量到的是本機到那個區域的頻寬，前提是服務流量也走相近的路徑：服務流量經過 proxy 時，`iperf3` 直連 5201 不經過 proxy，路徑不同；服務掛在 CDN 後面時，使用者連到的是邊緣節點，不是那個區域。這兩種情形用下面那一種做法。另一種是直接從服務本身下載一個夠大的檔案，用 `curl` 的 `%{speed_download}`（平均下載速率，單位是 byte／秒）量，量到的是包含伺服器在內的實際速率。

## 同網段主機、企業內網連 SaaS、VPN、跨國線路與雲端主機裡的量測結果

量測結果代表服務的條件（協定與 port 相同、經過同一組中間設備，也就是防火牆、proxy、VPN 閘道這些〈防火牆、proxy 與負載平衡器對 ICMP 與 TCP 封包的處理〉稱為關卡的設備）在不同的網路環境裡成立的程度不同，所以同一個工具在不同環境量到的，可能是服務流量的狀態，也可能只是 ICMP 這種流量受到的處理。

**同一個網段或同一個資料中心裡的兩台主機**：兩端的主機防火牆都回應 ICMP 時，這種環境滿足〈ping：ICMP 往返時間與它涵蓋的範圍〉寫的條件，`ping` 的 RTT 與掉包就代表服務流量的網路層狀態。交換器轉送一個封包只要幾微秒，時間大多花在兩端主機的網路堆疊上，所以同一個交換器底下的兩台實體主機，RTT 通常在 1 毫秒以下（虛擬機之間可能較高）；量到的 RTT 明顯更高、而兩台之間只隔一台交換器時，延遲可能出在某一台主機本身（CPU 滿載、網卡驅動），這時那台主機的負載會比平常高。兩台都由量測的人控制，頻寬可以直接用 `iperf3` 量。

**企業內網經過防火牆連外部 SaaS 的 API**：邊界防火牆可能丟棄 ICMP，對外的 HTTPS 流量可能被要求經過 proxy 與 TLS 檢查。這種環境裡 `ping` 與 `tracert` 的結果（不論通或不通）都只描述 ICMP 受到的處理，代表服務的量測是走瀏覽器實際路徑的那一種：使用者用瀏覽器操作的服務，開發者工具 Network 面板裡那一個請求的 Timing 頁拆出 DNS、Initial connection、SSL、Waiting（第一個 byte）與 Content Download，走的是瀏覽器實際的 proxy、PAC、協定版本與連線重用；沒有瀏覽器的機器上、或要重複量測時，用經由同一個 proxy 的 `curl -w` 重現同一組時間。讀這份時間拆解的人可以把慢的位置分成幾類：`time_appconnect` 那一段長，延遲出在 proxy、TLS 檢查或 proxy 到 SaaS 的路程；`time_starttransfer` 減掉 `time_appconnect` 那一段，經過 proxy 時同時含 proxy 到 SaaS 的一次 RTT、proxy 轉送請求與 SaaS 處理請求的時間，從企業網路這一端分不開。從同一台機器、不經過 proxy 的另一條網路（例如手機熱點）再量一次，那一次是直連，`time_connect` − `time_namelookup` 可以估計到 SaaS 入口的 RTT，扣掉之後剩下的是入口之後的時間：SaaS 掛在 CDN 或負載平衡器後面時，含邊緣到後端的路程，加上 SaaS 處理請求的時間；兩次的 `time_appconnect` 之差包含企業網路的防火牆、proxy 與 TLS 檢查增加的時間，也包含兩條線路本身的延遲差別（行動網路的延遲本來就不同），所以這個差值是那些設備增加時間的估計值。

**跨國或跨區的線路，使用者反映時好時壞**：傳遞延遲（propagation delay）是訊號在線路裡傳遞的時間，隨距離增加，一直存在、不隨時段改變；延遲的基準不變而使用者在某些時段才反映變慢時，可能的成因是某一段線路在那些時段壅塞而掉包。這種環境要量的是掉包隨時間的變化，`mtr` 或 `pathping` 跑的時間要涵蓋使用者反映慢的時段；`pathping` 只送 ICMP，`mtr --tcp --port 443` 送的是跟服務相同協定與 port 的探測。中間各跳回的都是路由器自己產生的 ICMP Time Exceeded，不論探測封包是 ICMP 還是 TCP，中間跳的掉包率都受那台路由器回應 ICMP 的限速影響；兩種探測的差別在探測封包被轉送時受到的處理（防火牆規則、ECMP 選的路徑），以及目標那一列：`mtr --tcp` 的目標回的是服務 port 的 TCP 回應。所以比對兩份報表時看的是延續到目標的掉包，目標那一列以 `mtr --tcp` 的數字代表服務流量。Windows 沒有內建逐跳的 TCP 探測，在 Windows 環境要用 TCP 量路徑時，`mtr --tcp` 要從同一個網路裡的一台 Linux 主機跑。掉包從某一跳開始延續到目標，就把掉包定位在那一段，這份 `mtr` 報表也是向網路業者回報時要附的證據。

**經 VPN 連公司內部服務**：VPN 把封包包進加密通道，`traceroute`、`mtr` 與 `pathping` 只看得到通道兩端的設備，看不到通道經過的網際網路路由器。所以掉包率從通道入口那一跳就延續到目標時，掉包可能發生在通道經過的任何一段，報表定位不到網路業者的某一段，判斷要交給管 VPN 的人，他看得到通道外層的連線。通道會在每個封包外面多包一層標頭，能放進通道的封包大小（MTU）因此變小；路上有設備擋掉通知封包太大的 ICMP 訊息時，小封包的 ping 與 TCP 交握都正常，大封包卻被丟棄，`curl` 卡在 TLS 握手，因為握手裡的憑證訊息是較大的封包：加 `--max-time 15` 時，逾時之後照樣印出 `-w` 那一行，`time_connect` 有值而 `time_appconnect` 是 0；加 `-v` 時，輸出停在 TLS 握手那幾行之後。這種情形多半出在通道的 MTU 設得比外層路徑容得下的大（外層又經過 PPPoE 或行動網路時），確認的方法是對一個會回 ICMP 的內部位址送禁止分段的大封包：Linux 用 `ping -M do -s <大小> <內部位址>`，Windows 用 `ping -f -l <大小> <內部位址>`，`<大小>` 從 1472 往下試，通過的最大值加 28（IP 與 ICMP 標頭）就是這條路徑容得下的封包大小。到目標位址的路由指向哪一個網路介面，是判斷服務流量是否走 VPN 的依據：Linux 用 `ip route get <目標 IP>`，Windows 用 `Find-NetRoute -RemoteIPAddress <目標 IP>`（PowerShell），`ip route get` 輸出裡 `dev` 後面是介面名稱，`Find-NetRoute` 印出兩段，看 `InterfaceAlias` 欄；那個介面是 VPN 的虛擬網卡時，流量走通道。[Mesh VPN（網狀 VPN）](/devops/infra/knowledge-cards/mesh-vpn/) 在點對點直連建不起來時改走中繼伺服器，同一個目標的路徑整條換掉、延遲跟著升高，判讀見 [Tailscale 深入：tailnet、MagicDNS、直連與 DERP 中繼](/linux/tools/remote/tailscale-tailnet-and-relay/)。

**雲端主機的 security group 沒有放行 ICMP**：security group 只放行規則明列的入站流量，規則裡只開了服務的 port 而沒有 ICMP 時，外部送來的 Echo Request 被丟棄。各家業者預建的規則不同（例如 GCP 的 default 網路預建了放行 ICMP 的防火牆規則，AWS 新建的 security group 沒有任何入站規則），要看那台主機實際套用的規則。ICMP 沒有放行時，從外部 `ping` 那台主機逾時是規則的預期結果，跟主機與服務的狀態無關。這種環境裡代表服務可達性與延遲的量測，是對服務開放的那個 port 建立連線：Windows 的 `psping <主機>:<port>`，Linux 的 `curl -w` 或 `traceroute -T -p <port>`。

## 判斷一次量測是否代表服務：協定、路徑、量的種類

一次量測的數字要拿來判斷服務的狀態之前，對它檢查協定、路徑與量的種類。這是[診斷心法：讀權威狀態，不靠肉眼猜表象](../diagnosis-read-authoritative-state/)那套紀律用在網路量測上的形式：ping 的結果是 ICMP 受到什麼處理的權威狀態，不是服務流量的。量測封包用的協定與 port 跟服務是否相同（ICMP 對上 TCP 443 時，量到的只是 ICMP 受到的處理；HTTPS 服務的協定要看瀏覽器實際用的版本，開發者工具 Network 面板的 Protocol 欄是 `h3` 時，服務流量走 UDP 443 的 QUIC，TCP 443 的量測只代表瀏覽器退回 TCP 時的情形，以支援 HTTP/3 的版本建置的 `curl` 加 `--http3` 才量得到同一個協定）；量測經過的路徑跟服務流量是否相同（服務流量走 proxy 或 VPN 而量測封包沒有時，量到的是另一條路；是否走 proxy 寫在瀏覽器或系統的 proxy 設定裡，是否走 VPN 由到目標位址的路由指向哪一個網路介面判斷）；量的種類（延遲、掉包、延遲變動、頻寬、應用層回應時間）是否對應使用者的症狀（使用者反映下載慢時，從 RTT 的數字看不出頻寬）。這幾項都成立時，量到的數字就是服務流量在那一刻、從那一台機器出發時的狀態；任何一項不成立，數字描述的是另一種流量或另一種量。

一次手動量測只代表一台機器在一段時間裡的狀態。使用者分布在不同地區、慢的情形間歇出現時，要從使用者所在的位置持續量，那是外部探測服務的工作；挑選外部探測服務時要看哪些條件（探測點在哪裡、怎麼比對回應內容），寫在[第三方心跳監看與外部探測服務](/backend/04-observability/vendors/prometheus/external-heartbeat-and-probe-services/#外部探測服務的挑選條件)的〈外部探測服務的挑選條件〉。量測的結果是完全連不上（逾時或被拒）時，判斷要回到[機器連不到或起不來](../machine-unreachable/)從網路層與主機側往下查。
