這篇整理規則文件、操作手冊、範本這類文字文件的拆分：判斷一份文件是否承擔了多種職責、沿哪條軸切開，以及拆完之後原檔與引用的處理。程式模組的拆分在[從修改競爭判斷拆檔](/python/07-refactoring/file-split-by-contention/)；文章與系列之間的責任分配在 [SOLID 寫作方法論](/record/solid-writing-methodology/)。一份文件只剩一種職責之後，內部要怎麼把常駐內容與參考細節分層，在[非程式碼的重構](/record/non-code-refactoring/)。

## 修改紀錄裡的職責訊號

一份文件的職責數，可以從它被哪些主題修改過讀出來。單一職責原則把職責定義成「改變的理由」，這個定義對文件同樣成立：一份文件每被一個不相干的主題修改一次，就多一個改變它的理由。[SOLID 寫作方法論](/record/solid-writing-methodology/)的變動理由測試要作者預測「這篇會因為什麼事件需要更新」；版本歷史記錄的是實際發生過的更新，兩者可以互相對照。

文件的 commit 多半不帶需求編號，所以這一步靠讀 commit 標題人工歸類：

```bash
# 列出一份文件近半年的修改，每行是 commit 短 hash 與標題；--follow 讓改過檔名的文件也看得到改名前的紀錄
git log --follow --since="6 months ago" --no-merges --format='%h %s' -- docs/deploy.md
```

`--since` 的時間範圍與最後的檔案路徑換成要檢查的文件；範圍太短看不出重複出現的主題，太長會混進早已不存在的職責，半年到一年是常見的起點。假設一份部署手冊的修改紀錄是這樣：

```text
a1f3e2c 新增 staging 環境的環境變數
9c0d7b1 回滾步驟改成先切流量再降版
5e8a442 值班聯絡人換成新的輪值表
d27c9f0 權限申請改走新的簽核表單
3b61aa8 補上 production 的環境變數預設值
```

五次修改落在四個主題：設定參考（環境變數）、操作程序（回滾）、組織資訊（值班聯絡人）、權限流程。四個主題的修改節奏各自不同——聯絡人隨人員異動改、程序隨系統架構改、設定隨服務的版本改——所以它們會在不同的時間、由不同的人改同一份檔案。代價出現在兩個地方：兩個人同時改不同段落時，Markdown 的合併衝突照樣發生在相鄰的行上；審查一次修改的人得在 diff 裡跳過與這次主題無關的段落。

## 長度與職責

文件的長度影響閱讀負擔，而拆分的軸由職責決定。兩份文件可以給出相反的結果：一份 600 行的設定參數表只描述同一份設定的欄位，讀者逐列查詢，它只有一種職責；一份 80 行的 README 同時寫安裝方式、貢獻規則、發版流程與聯絡窗口，它有四種。依長度切會把參數表切成幾段而讀者要在幾份檔案之間找一個欄位，README 則因為夠短而留在原地繼續累積主題。

聚合型文件要另外處理：CHANGELOG、索引頁、術語表的職責就是集中列出所有項目，每個主題都要在這裡登記一筆，所以被許多主題修改是它的設計使然。依職責把 CHANGELOG 拆成三份，每次登記仍然要改其中一份。這類文件降低的是每次修改的衝突面：每個項目一個片段檔、由產生器合併（towncrier 這類工具讓每個變更各寫一個片段檔，發版時再合成 CHANGELOG），或規定只追加、不修改既有條目。

## 文件職責的切法

把修改紀錄歸類之後，每一類職責是一份候選文件。文字文件常見的職責有四種，它們改變的理由不同：

- **適用範圍與觸發條件**：什麼情況要照這份文件做。隨組織的規定改。
- **操作程序**：怎麼做。隨工具與系統架構改。
- **設計理由與取捨**：為什麼這樣做。很少改，改的時候通常代表做法本身要重新評估。
- **參考資料**：參數、欄位、對照表。隨被描述的系統版本改。

部署手冊的例子切成設定參考、回滾程序、值班聯絡與權限申請四份，各自只在自己的主題變動時被修改。

程序型內容有一個切法上的限制：依角色切（每份給一種角色看）會讓每一份從自己的第一步開始編號，而子文件的後段步驟常常就是全程的中段，讀者走完子文件的最後一步會以為整個程序結束了。程序依步驟切，每一份就是全程的一段，編號只有一套；角色軸適合查表型的內容，那裡沒有一套貫穿全程的步驟編號會跟子文件重複。

## 原檔保留路由表

原檔的路徑已經被其他文件的連結、書籤、腳本與 AI 代理人的指令引用，刪掉它之後這些引用失效，而失效的方式多半是靜默的：連結回 404，代理人找不到檔案就照自己的猜測繼續做。所以原檔留下來，改成一張路由表，每一列寫一種讀者需求、對應的新文件，以及那份文件涵蓋什麼：

```markdown
# 部署手冊

| 需求                       | 文件                                 | 涵蓋                             |
| -------------------------- | ------------------------------------ | -------------------------------- |
| 查某個環境變數的意義與預設 | [設定參考](deploy-config.md)         | 各環境的變數、預設值與生效方式   |
| 部署出錯要回滾             | [回滾程序](deploy-rollback.md)       | 切流量、降版與確認的步驟         |
| 找當班的人                 | [值班聯絡](on-call.md)               | 輪值表的位置與升級路徑           |
| 申請部署權限               | [權限申請](deploy-access.md)         | 簽核表單與審核時程               |
```

路由表依需求排列，因為讀者帶著一個需求來到這個檔案。只列檔名的路由表要讀者逐份點開才知道去哪一份，「涵蓋」這一欄讓他在原檔就能判斷。

## 同一條規則只定義一次

拆分之後，同一條規則常會被幾份新文件用到——例如「所有部署都要在變更視窗內進行」同時影響回滾程序與權限申請。把這條規則複製進每一份讀起來方便，而之後修改規則的人通常只改到其中一份，幾份文件從此各說各的。規則定義在一份文件裡，其他文件引用那個位置。

## 拆完之後的引用更新

新文件建好之後，整個專案裡指向原檔與原段標的引用都要找出來：

```bash
# 找出引用原檔路徑的所有檔案（-r 遞迴、-l 只列檔名）
grep -rl 'docs/deploy.md' .

# 找出連到原檔某個段標的連結，-n 印出行號，逐一改到新文件
grep -rn 'deploy.md#' .
```

路徑換成被拆分的那份文件。段標錨點那一條要特別處理：段落搬到新文件之後，`deploy.md#回滾` 這種連結仍然打得開原檔，只是錨點已經不存在，瀏覽器停在頁面頂端而不報錯，所以連結檢查工具多半放行它。

拆分還會在檔與檔之間造出新的缺陷：新文件之間的互相指引缺了一份、某個詞的定義留在一份而使用在另一份、散文裡的「下面三節」在拆分後已經不是三節。這幾種缺陷在每一份單獨讀的時候都看不出來，形態與檢查方式整理在[拆分產生的缺陷落在檔與檔的交界](/report/split-defects-land-between-the-files/)。

## 拆分之後的追蹤

過一段時間再讀一次修改紀錄，確認每一份新文件只被自己那個主題修改。某一份新文件很快又出現多個主題的修改，代表當初的歸類切錯了位置，要回到修改紀錄重新歸類。
