這篇整理規則文件膨脹之後的精簡做法：用 Progressive Disclosure 把每次都要讀的內容留在決策入口與強制規則，細節移到按需讀取的參考文件。案例是一個以 AI 代理人協作開發的專案，在三個版本之間精簡它的七份流程規則文件。一份文件該不該拆成幾份、沿哪種職責切，在[依職責拆分文字文件](/record/document-split-by-responsibility/)；本篇處理的是一份文件只剩一種職責之後，內部怎麼分層。

當一份規則文件從 50 行長到 450 行，讀者要在腦中同時追蹤的概念數量，跟一個 858 行的程式檔沒有差別（那個程式檔的重構記錄在 Python 模組的[重構的動機與策略](/python/07-refactoring/refactoring-strategy/)）。認知負擔來自要同時追蹤的概念數，與讀的是程式碼還是文字無關。

## 文件膨脹的形態

這個專案的規則文件在 v0.28.0 到 v0.31.0 之間經歷了 9 個版本的迭代。每次迭代都在解決真實的需求：補充遺漏的邊界情況、新增流程步驟、記錄決策理由。每一次修改都合理，累積的結果是：

```text
parallel-dispatch.md     280 行  ← 原本是「什麼時候可以並行」的簡單指南
task-splitting.md        230 行  ← 原本是「怎麼拆任務」的清單
ticket-lifecycle.md      220 行  ← 原本是「Ticket 狀態怎麼轉」的流程
version-progression.md   180 行  ← 原本是「什麼時候推進版本」的判斷
incident-response.md     170 行  ← 原本是「出錯了怎麼辦」的流程
query-vs-research.md     130 行  ← 原本是「查資料要不要派人」的二選一
plan-to-ticket.md        100 行  ← 原本是「計畫怎麼變成 Ticket」的流程
decision-tree.md         452 行  ← 核心決策樹，每次都在「補一個分支」
```

每一行內容都有存在的理由，而讀者讀不動。一個新加入的代理人要讀 `parallel-dispatch.md` 來決定能不能並行派發任務，它真正需要的資訊是觸發條件（5 行）、安全檢查清單（6 行）與決策流程圖（5 行），而它必須在 280 行中找到這些——其餘 264 行是 5W1H 格式範例、分析任務的並行原則、Agent Teams 場景表與進度追蹤模板。這跟在一個 500 行的函式裡找那 20 行核心邏輯是同一種負擔。

這些規則文件是常駐文件：代理人每次做相關的決策都要整份讀進來。常駐文件的長度因此是一個直接的成本，每多一行，每一次決策都多讀一行。

### 膨脹的過程

`parallel-dispatch.md` 的成長軌跡：

| 版本 | 行數   | 新增原因                                       |
| ---- | ------ | ---------------------------------------------- |
| v1.0 | 60 行  | 初始版本：觸發條件 + 決策流程                  |
| v1.1 | 90 行  | 補充：安全檢查清單（因為有人忘記檢查檔案衝突） |
| v1.2 | 130 行 | 新增：Agent Teams 派發方式（新功能）           |
| v2.0 | 180 行 | 新增：5W1H 格式範例（因為有人不知道怎麼寫）    |
| v2.3 | 230 行 | 新增：分析任務並行原則、進度追蹤模板           |
| v2.5 | 280 行 | 新增：並行派發後驗證流程（因為有人忘記驗證）   |

每一次新增都在處理一個實際發生過的疏漏，沒有人刻意讓文件變長。六個版本之後，一份「能不能並行」的判斷指南變成了包羅萬象的操作手冊。程式碼裡的巨型函式也是這樣長出來的：每次加一點都合理，而沒有人在加的那一刻問這個函式該不該拆。

## Progressive Disclosure 的分層

程式碼重構有 Extract Method，把函式內部的細節提取到獨立函式。文件對應的手法是 **Progressive Disclosure**（漸進式揭露）：常駐文件只保留決策入口與強制規則，細節放到參考文件裡按需讀取。

這跟函式設計的道理相同：`main()` 裡不放排序演算法的完整實作，而是呼叫 `sort()`。規則文件的讀者在判斷「能不能並行」時，不需要看到 Agent Teams 的 3-4 倍成本計算方式。

這次精簡依讀者需要的深度把內容分成四層：

```text
Level 0: 快查表（一眼就能找到答案）
Level 1: 強制規則（必須遵守的約束）
Level 2: 決策流程（判斷邏輯）
Level 3: 參考細節（範例、模板、歷史記錄）
```

常駐文件只包含 Level 0 到 Level 2，Level 3 放在 `references/` 目錄下。函式也有同樣的層級：

```python
# Level 0: 函式簽名（一眼就知道做什麼）
def can_dispatch_parallel(tasks: list[Task]) -> bool:
    # Level 1: Guard clauses（強制規則）
    if len(tasks) < 2:
        return False
    if has_dependency(tasks):
        return False

    # Level 2: 核心邏輯（判斷邏輯）
    return not has_file_overlap(tasks)

# Level 3: 實作細節（在被呼叫的函式裡）
def has_file_overlap(tasks):
    # 50 行的具體實作...
```

精簡時用的四條原則與程式碼重構的原則一一對應：

| 程式碼原則 | 文件原則                       | 說明                                         |
| ---------- | ------------------------------ | -------------------------------------------- |
| 單一責任   | 一份文件處理一種決策           | 常駐文件只寫「怎麼判斷」，不寫「細節怎麼做」 |
| 資訊層級   | 決策入口 → 強制規則 → 參考細節 | 讀者按需深入，不必讀完全部                   |
| DRY        | 細節只寫一次，放在 references/ | 多份文件引用同一份參考，不複製貼上           |
| 量化驗證   | 精簡前後行數對比               | 有前後的數字，才知道常駐內容少了多少         |

單一責任那一列的判斷方式跟函式一樣：描述這份文件的用途需要用到「和」，它可能管了不只一種決策。

| 文件                 | 處理的決策          | 不該包含                   |
| -------------------- | ------------------- | -------------------------- |
| parallel-dispatch.md | 能不能並行？        | Agent Teams 的完整操作手冊 |
| incident-response.md | 出錯了怎麼處理？    | 每種錯誤的詳細分析範例     |
| ticket-lifecycle.md  | Ticket 狀態怎麼轉？ | Hook 的技術實作細節        |

DRY 那一列處理的是文件之間的重複：同一段「Wave 獨立性原則」如果在 `parallel-dispatch.md`、`task-splitting.md`、`version-progression.md` 三個地方都寫了，修改時就要改三處，而通常只會改到其中一處。抽到共用的參考文件，其他文件用連結引用。

## 精簡的做法

以 `parallel-dispatch.md` 為例。

### 標出決策入口與參考細節

讀 280 行內容，對每一段問：讀者在做「能不能並行」這個決策時需要這段嗎？

- 觸發條件表格 → 需要（決策入口）
- 安全檢查清單 → 需要（強制規則）
- 決策流程圖 → 需要（快查表）
- 數量原則 → 需要（簡短規則）
- 不適用場景 → 需要（負面清單）
- 5W1H 格式範例 → 不需要（移出）
- Agent Teams 場景表 → 不需要（移出）
- 進度追蹤模板 → 不需要（移出）

### 把參考細節提取到參考文件

```text
# 精簡前
parallel-dispatch.md (280 行，所有內容混在一起)

# 精簡後
parallel-dispatch.md (98 行，決策入口 + 強制規則)
  └→ references/parallel-dispatch-details.md (剩餘細節，按需查閱)
```

### 在常駐文件留下連結

```markdown
## 並行派發後驗證（強制）

所有並行代理人回報完成後，**必須**執行 `git diff --stat` 驗證。

> 詳細驗證步驟和常見原因：.claude/references/parallel-dispatch-details.md
```

讀者讀到這段就知道驗證是強制的，具體步驟在那份參考文件裡；他可以先完成手邊的決策，需要時再點進去。

`incident-response.md` 精簡前後的結構差異：

```markdown
# 精簡前 (170 行)

## 強制流程
（流程圖 + 說明）

## 強制觸發條件
（觸發表格）

## 派發對應表
（代理人對應表）

## 多視角分析原則             ← Level 3
（詳細的分析方法論）

## 安全等級分類               ← Level 3
（安全等級表格 + 處理流程）

## 報告格式範例               ← Level 3
（完整的報告模板）

## 禁止行為
（禁止清單）
```

```markdown
# 精簡後 (64 行)

## 強制流程
（流程圖 + 說明）

## 強制觸發條件
（觸發表格）

## 派發對應表
（代理人對應表）

## 禁止行為
（禁止清單）

## 相關文件
> 詳細規則：.claude/references/incident-response-details.md
```

Level 3 的內容（多視角分析、安全等級、報告格式）整段移到 `references/` 目錄，常駐文件只剩下做決策需要的資訊。

## 七份規則文件的精簡結果

| 文件                   | 精簡前      | 精簡後     | 縮減     |
| ---------------------- | ----------- | ---------- | -------- |
| parallel-dispatch.md   | 280 行      | 98 行      | -65%     |
| task-splitting.md      | 230 行      | 93 行      | -60%     |
| ticket-lifecycle.md    | 220 行      | 70 行      | -68%     |
| version-progression.md | 180 行      | 69 行      | -62%     |
| incident-response.md   | 170 行      | 64 行      | -62%     |
| query-vs-research.md   | 130 行      | 46 行      | -65%     |
| plan-to-ticket.md      | 100 行      | 43 行      | -57%     |
| **合計**               | **1310 行** | **483 行** | **-63%** |

核心決策樹 `decision-tree.md` 從 452 行精簡到 286 行（-37%）。它的縮減幅度較小，因為決策樹本身就是決策入口，大部分內容都是必要的分支判斷。

前後的行數可以用一條指令量：

```bash
# 統計規則文件目錄下每份文件的行數與合計
wc -l .claude/rules/flows/*.md .claude/rules/guides/*.md
```

路徑換成自己存放規則文件的目錄。行數本身不是目標，它是常駐內容少了多少的代理指標：同一份文件精簡前後各量一次，差值就是每次決策少讀的行數。

上面的數字是 v3.0.0 精簡完成時的量測。精簡後不到兩週，`plan-to-ticket.md` 因為新增「執行中額外發現」流程從 43 行長回 87 行，`decision-tree.md` 因為新增 TDD Phase 路由從 286 行長回 434 行。新增的內容都是必要的新功能，所以這兩個數字顯示的是常駐文件會持續長回去，分層要在每一次新增時重新判斷，而不是精簡一次就結束。

## 精簡時的兩種失誤

### 過度精簡

把所有細節都移走，常駐文件只剩下標題和連結。讀者每做一個決策都要點開參考文件，跳轉次數太多反而增加認知負擔。

```markdown
# 過度精簡的常駐文件
## 並行派發
> 詳見：references/parallel-dispatch-details.md

## 任務拆分
> 詳見：references/task-splitting-details.md
```

這等於一個函式裡全是 `call_other_function()`，讀者在常駐文件裡做不了任何判斷。常駐文件至少要包含決策入口（判斷邏輯）與強制規則（不可違反的約束）。

### 只按目錄章節切開，沒有分層

把一份文件按目錄章節切成幾個小檔，每個小檔仍然同時有決策入口與參考細節，讀者在每一份裡都要再找一次核心內容。

分層與依職責拆是兩條處理不同事情的軸。依職責拆決定有幾份文件：一份文件被幾種互不相干的主題修改，就承擔了幾種職責，各自拆成一份（見[依職責拆分文字文件](/record/document-split-by-responsibility/)）。一份文件只剩一種職責之後，Progressive Disclosure 依資訊層級決定哪些內容常駐、哪些移到參考文件。只按章節切，兩條軸都沒有用上。

另一種與分層相關的失誤是移出細節之後沒有在常駐文件加連結：讀者需要細節時找不到入口，跟重構後忘了更新 import 是同一類錯誤。

## 程式碼重構與文件重構的對照

| 維度       | 程式碼重構             | 文件重構                      |
| ---------- | ---------------------- | ----------------------------- |
| 壞味道     | 函式太長、巢狀過深     | 常駐文件太長、層級不分        |
| 核心手法   | Extract Method         | Progressive Disclosure        |
| 單一責任   | 一個函式做一件事       | 一份文件處理一種決策          |
| DRY        | 提取共用模組           | 提取共用參考文件              |
| 量化指標   | 行數、認知負擔指數     | 行數、常駐 vs 參考比例        |
| 驗證方式   | 測試通過               | 讀者能在 30 秒內找到答案      |
| 失敗的重構 | 過度拆分導致跳轉太多   | 過度精簡導致資訊不足          |
| 觸發條件   | 函式超過 30 行         | 文件超過 100 行且混合多個層級 |
| 典型比例   | 858 行 → 296 行 (-65%) | 280 行 → 98 行 (-65%)         |

兩個案例的縮減率接近（-65%），兩者剛好都約有三分之一是決策入口、三分之二是支撐細節。這是兩個案例的觀察，不是一個比例定律。

## 文件精簡的觸發訊號

| 指標     | 訊號                    | 行動                                                                                              |
| -------- | ----------------------- | ------------------------------------------------------------------------------------------------- |
| 常駐長度 | 超過 100 行且混合多層級 | 評估分層                                                                                          |
| 讀者反饋 | 「找不到需要的資訊」    | 重新組織資訊層級                                                                                  |
| 更新範圍 | 每次更新都在不同段落    | 依修改紀錄判斷是不是多種職責（見[依職責拆分文字文件](/record/document-split-by-responsibility/)） |
| 重複內容 | 同一段話出現在 2 份以上 | 提取到共用參考                                                                                    |

長度在這裡是有效的訊號，因為常駐文件每次都整份被讀進來；它決定的是一份文件內部要不要分層。一份文件管了幾種職責、要不要拆成幾份，看的是修改紀錄而不是長度。

## 思考題

1. 一份「什麼都寫在 README」的專案說明，用 Progressive Disclosure 分層時，哪些內容會留在常駐、哪些會移到參考？
2. 為什麼 `decision-tree.md` 的縮減幅度（-37%）比其他文件（-57% 到 -68%）小？這說明了什麼？
3. 文件精簡有一個程式碼重構沒有的風險：過度精簡導致讀者找不到需要的資訊。要怎麼驗證精簡後的文件仍然足夠完整？

## 實作練習

### 評估一份文件的健康度

找一份超過 150 行的文件（專案 README、API 文件、團隊 Wiki），逐項檢查：

- 這份文件處理幾種決策？超過一種時，先依修改紀錄判斷要不要拆成幾份。
- 讀者能在 30 秒內找到最常需要的資訊嗎？
- 有沒有段落只在特定情境下才需要閱讀？

### 執行 Progressive Disclosure

對那份文件做三件事：標記每一段的資訊層級（Level 0 到 3）、把 Level 3 的內容提取到獨立的參考文件、在原文件中加入連結。

### 量化驗證

計算精簡前後的行數和縮減率。縮減率低於 30% 時，思考原本的結構是否已經不錯；超過 70% 時，檢查是否過度精簡。
