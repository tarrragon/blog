這篇整理規則文件膨脹之後的精簡做法：用 Progressive Disclosure 把每次都要讀的內容留在常駐文件，細節移到按需讀取的參考文件。案例是一個以 AI 代理人協作開發的專案，在 2026 年 3 月初精簡它的七份流程規則文件。判斷一份文件是否要拆成幾份、沿哪種職責切，在[依職責拆分文字文件](/record/document-split-by-responsibility/)；本篇處理的是一份文件內部的分層。

認知負擔來自讀者要同時追蹤的概念數，讀的是程式碼還是文字都一樣：規則文件越長，讀者做一個判斷之前要先跳過的條件、例外與範例就越多。

## 文件膨脹的形態

這個專案的流程規則文件從 2026 年 1 月起反覆迭代。每次迭代都在處理一個實際發生過的疏漏：補充遺漏的邊界情況、新增流程步驟、記錄決策理由。精簡之前的行數：

```text
parallel-dispatch.md     444 行  ← 原本是「什麼時候可以並行」的判斷指南
task-splitting.md        325 行  ← 原本是「怎麼拆任務」的清單
ticket-lifecycle.md      286 行  ← 原本是「Ticket 狀態怎麼轉」的流程
incident-response.md     257 行  ← 原本是「出錯了怎麼辦」的流程
version-progression.md   231 行  ← 原本是「什麼時候推進版本」的判斷
plan-to-ticket-flow.md   153 行  ← 原本是「計畫怎麼變成 Ticket」的流程
query-vs-research.md     151 行  ← 原本是「查資料要不要派人」的二選一
decision-tree.md         452 行  ← 核心決策樹，每次都在「補一個分支」
```

這些規則文件是常駐文件：代理人每次做相關的決策都要整份讀進來。常駐文件的長度因此是一個直接的成本，每多一行，每一次決策都多讀一行。一個代理人要讀 `parallel-dispatch.md` 決定能不能並行派發任務，它用得到的是觸發條件、並行安全檢查、決策流程、數量原則、不適用並行的情形、派發方式判斷與派發後的驗證；精簡前的 444 行裡，其餘內容是派發任務用的 5W1H 格式範例（要求寫出 who、what、when、where、why、how 的任務說明）、分析任務的並行原則、Agent Teams（多個代理人組隊並行的派發方式）的場景表與進度追蹤模板。

### parallel-dispatch.md 的膨脹過程

`parallel-dispatch.md` 留在版本紀錄裡的成長軌跡（版本是這份文件自己的版號，v2.0.0 之前的版本沒有留在版本紀錄裡）：

| 文件版本 | 日期       | 行數   | 新增原因                 |
| -------- | ---------- | ------ | ------------------------ |
| v2.0.0   | 2026-01-23 | 162 行 | 第一次進入版本紀錄       |
| v2.2.0   | 2026-02-02 | 282 行 | 新增分析任務並行派發章節 |
| v2.4.0   | 2026-02-25 | 377 行 | 擴充 Agent Teams 場景表  |
| v2.5.0   | 2026-02-26 | 444 行 | 新增並行派發後驗證規則   |

每一次新增都在處理一個實際發生過的疏漏，沒有人刻意讓文件變長，而一個月之內，一份「能不能並行」的判斷指南長到 444 行。程式碼裡的巨型函式也是這樣累積出來的：每次加一點都合理，而沒有人在加的那一刻問這個函式該不該拆。

這次精簡沒有先依修改紀錄判斷職責，直接依資訊層級分層。成長軌跡裡的 Agent Teams 派發方式是新功能，依[依職責拆分文字文件](/record/document-split-by-responsibility/)的判斷，它也可以獨立成一份文件；本篇的做法把它歸進參考細節。

## Progressive Disclosure 的四層

程式碼重構有 Extract Method，把函式內部的細節提取到獨立函式。文件對應的手法是 **Progressive Disclosure**（漸進式揭露）：依讀者做決策時需要的深度把內容分層，常駐文件只放決策用得到的那幾層，其餘放到參考文件裡按需讀取。

這次精簡把內容分成四層：

- **快查表**：一眼就能找到答案的表格，例如觸發條件表。
- **強制規則**：必須遵守的約束，例如並行前的安全檢查清單、數量原則、不適用的情形。
- **決策流程**：判斷邏輯，例如決策流程圖。
- **參考細節**：範例、模板、場景表、歷史記錄。

快查表與決策流程合稱**決策入口**：讀者靠它們做出判斷。常駐文件放決策入口與強制規則，參考細節放在 `references/` 目錄下。這跟函式設計的道理相同：`main()` 呼叫 `sort()`，排序的完整實作留在 `sort()` 裡。函式也有同樣的四層：

```python
# 快查表：函式簽名（一眼就知道做什麼）
def can_dispatch_parallel(tasks: list[Task]) -> bool:
    # 強制規則：guard clauses
    if len(tasks) < 2:
        return False
    if has_dependency(tasks):
        return False

    # 決策流程：核心的判斷邏輯
    return not has_file_overlap(tasks)

# 參考細節：實作留在被呼叫的函式裡
def has_file_overlap(tasks):
    ...  # 50 行的具體實作
```

精簡時用的四條原則與程式碼重構的原則一一對應：

| 程式碼原則 | 文件原則                                 | 說明                                                                         |
| ---------- | ---------------------------------------- | ---------------------------------------------------------------------------- |
| 單一職責   | 一份文件只因一種主題被修改               | 常駐文件只寫怎麼判斷，細節怎麼做放到參考文件                                 |
| 資訊層級   | 決策入口與強制規則常駐、參考細節按需讀取 | 讀者按需深入，不必讀完全部                                                   |
| DRY        | 同一段內容只寫一次                       | 共用的強制規則定義在一份常駐文件，共用的參考細節放 references/，其他文件引用 |
| 量化驗證   | 精簡前後量常駐內容的行數                 | 有前後的數字，才知道每次決策少讀了多少                                       |

單一職責那一列的判定依據是修改紀錄：一份文件被幾種互不相干的主題修改，就承擔了幾種職責（見[依職責拆分文字文件](/record/document-split-by-responsibility/)）。描述文件用途時要用到「和」，可以當讀紀錄之前的初篩。

| 文件                 | 處理的判斷          | 參考細節（不常駐）         |
| -------------------- | ------------------- | -------------------------- |
| parallel-dispatch.md | 能不能並行？        | Agent Teams 的完整操作說明 |
| incident-response.md | 出錯了怎麼處理？    | 每種錯誤的詳細分析範例     |
| ticket-lifecycle.md  | Ticket 狀態怎麼轉？ | Hook 的技術實作細節        |

DRY 那一列處理的是文件之間的重複。一條共用的規則（例如這個專案的 Wave 獨立性原則：不同波次（Wave）的任務在執行時必須完全獨立）如果在幾份規則文件裡各寫一次，修改時就要改好幾處，而通常只會改到其中一處。它是強制規則，所以定義在一份常駐文件，其他文件引用那個位置；共用的範例與模板才放到 `references/`。

## parallel-dispatch.md 的精簡做法

### 為每一段標出它屬於哪一層

逐段問：讀者在做「能不能並行」這個決策時需要這段嗎？需要的話它屬於哪一層。

| 段落               | 層       | 處置 |
| ------------------ | -------- | ---- |
| 觸發條件表格       | 快查表   | 常駐 |
| 並行安全檢查清單   | 強制規則 | 常駐 |
| 決策流程圖         | 決策流程 | 常駐 |
| 數量原則           | 強制規則 | 常駐 |
| 不適用並行的情形   | 強制規則 | 常駐 |
| 5W1H 格式範例      | 參考細節 | 移出 |
| Agent Teams 場景表 | 參考細節 | 移出 |
| 進度追蹤模板       | 參考細節 | 移出 |

### 把參考細節提取到參考文件

```text
# 精簡前
parallel-dispatch.md (444 行，所有內容混在一起)

# 精簡後
parallel-dispatch.md (98 行，決策入口 + 強制規則)
  └→ references/parallel-dispatch-details.md (參考細節，按需查閱)
```

### 在常駐文件留下入口

```markdown
## 並行派發後驗證（強制）

所有並行代理人回報完成後，**必須**執行 `git diff --stat` 驗證。

> 詳細驗證步驟和常見原因：.claude/references/parallel-dispatch-details.md
```

讀者讀到這段就知道驗證是強制的，具體步驟在那份參考文件裡；他可以先完成手邊的決策，需要時再打開那份參考文件。

`incident-response.md` 精簡前後的段落結構：

```markdown
# 精簡前 (257 行)

## 流程總覽
## 多視角並行分析選項        ← 參考細節
## 強制觸發條件
## 執行步驟
## 派發對應表
## 安全問題嚴重等級          ← 參考細節
## Incident Report 格式      ← 參考細節（底下還有報告資訊、錯誤摘要、錯誤分類、根本原因分析、安全風險評估、派發建議等小段）
## 禁止行為
## 相關文件
```

```markdown
# 精簡後 (64 行)

## 強制流程
## 強制觸發條件
## 派發對應表
## 禁止行為
## 相關文件
> 詳細規則：.claude/references/incident-response-details.md
```

參考細節（多視角分析、安全等級、報告格式）整段移到 `references/` 目錄，流程總覽與執行步驟併成一節〈強制流程〉，常駐文件只剩下做決策需要的資訊。

前後的行數可以用一條指令量：

```bash
# 統計規則文件目錄下每份文件的行數與合計
wc -l .claude/rules/flows/*.md .claude/rules/guides/*.md
```

路徑換成自己存放規則文件的目錄。行數是常駐內容少了多少的代理指標：同一份文件精簡前後各量一次，差值就是每次決策少讀的行數。

## 精簡時的失誤：過度精簡、只按章節切開、移出後未留入口

### 過度精簡

把所有細節都移走，常駐文件只剩下標題和連結。讀者每做一個決策都要打開參考文件，跳轉次數太多反而增加認知負擔。

```markdown
# 過度精簡的常駐文件
## 並行派發
> 詳見：references/parallel-dispatch-details.md

## 任務拆分
> 詳見：references/task-splitting-details.md
```

這等於一個函式裡全是 `call_other_function()`，讀者在常駐文件裡做不了任何判斷。判斷有沒有過度精簡，看的是精簡後的常駐文件裡還做不做得出決策：決策入口與強制規則都要留在常駐文件。

### 只按章節切開

把一份文件按目錄章節切成幾個小檔，章節與職責對不上時，每個小檔仍然同時有決策入口與參考細節，讀者在每一份裡都要再找一次核心內容。

分層與依職責拆是兩條處理不同事情的軸。依職責拆決定有幾份文件：一份文件被幾種互不相干的主題修改，就承擔了幾種職責，各自拆成一份（見[依職責拆分文字文件](/record/document-split-by-responsibility/)）。章節剛好對應職責時，依章節切就是依職責切，切完之後每一份仍然要分層。一份文件只剩一種職責之後，Progressive Disclosure 依資訊層級決定哪些內容常駐、哪些移到參考文件。

### 移出後未留入口

移出參考細節之後沒有在常駐文件留下入口，讀者需要細節時找不到它，跟重構後忘了更新 import 是同一類錯誤。

## 程式碼重構與文件重構的對照

| 維度       | 程式碼重構                 | 文件重構                                   |
| ---------- | -------------------------- | ------------------------------------------ |
| 壞味道     | 函式太長、巢狀過深         | 常駐文件太長、層級不分                     |
| 核心手法   | Extract Method             | Progressive Disclosure                     |
| 單一職責   | 一個模組只有一個改變的理由 | 一份文件只因一種主題被修改                 |
| DRY        | 提取共用模組               | 共用規則只定義一次、共用細節提取到參考文件 |
| 量化指標   | 行數、巢狀深度             | 常駐內容的行數                             |
| 驗證方式   | 測試通過                   | 讀者在常駐文件裡做得出決策                 |
| 失敗的重構 | 過度拆分導致跳轉太多       | 過度精簡導致資訊不足                       |
| 觸發訊號   | 一個函式混了多個抽象層     | 一份常駐文件混了多個層級                   |

## 文件精簡的觸發訊號

| 指標     | 訊號                                 | 行動                                                                                      |
| -------- | ------------------------------------ | ----------------------------------------------------------------------------------------- |
| 常駐內容 | 每次決策都要先跳過大量用不到的段落   | 評估分層                                                                                  |
| 讀者反饋 | 「找不到需要的資訊」                 | 重新組織資訊層級                                                                          |
| 修改紀錄 | 每次更新落在不同段落、由不同主題觸發 | 先判斷是不是多種職責（見[依職責拆分文字文件](/record/document-split-by-responsibility/)） |
| 重複內容 | 同一段話出現在兩份以上的文件         | 規則定義在一份常駐文件、細節提取到參考文件                                                |

常駐內容的長度在這裡是有效的訊號，因為常駐文件每次都整份被讀進來；它決定的是一份文件內部要不要分層。判斷一份文件是否要拆成幾份，依據是它的修改紀錄。

## 思考題：README 的分層、決策樹的縮減幅度、精簡後的完整性

1. 一份「什麼都寫在 README」的專案說明，用 Progressive Disclosure 分層時，哪些內容會留在常駐、哪些會移到參考？
2. 為什麼 `decision-tree.md` 的縮減幅度（-37%）比其他文件（-70% 到 -78%）小？這說明了什麼？
3. 文件精簡有一個程式碼重構沒有的風險：過度精簡導致讀者找不到需要的資訊。要怎麼驗證精簡後的文件仍然足夠完整？

## 實作練習：健康度評估、分層與量化

### 評估一份文件的健康度

找一份常駐的規則文件或 README，逐項檢查：

- 這份文件被幾種主題修改過？超過一種時，先依修改紀錄判斷要不要拆成幾份。
- 讀者要做最常見的那個決策時，在常駐文件裡找不找得到需要的段落？
- 有沒有段落只在特定情境下才需要閱讀？

### 執行 Progressive Disclosure

對那份文件做三件事：標出每一段屬於快查表、強制規則、決策流程還是參考細節，把參考細節提取到獨立的參考文件，在原文件中留下入口。

### 量化驗證

計算精簡前後的行數和縮減率。縮減率本身沒有好壞的門檻，要檢查的是精簡後的常駐文件裡還做不做得出決策（見〈過度精簡〉）。
