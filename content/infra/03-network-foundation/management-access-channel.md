這篇整理管理員登入伺服器（SSH、RDP）的通道怎麼設計，內容與雲端廠商無關，適用於雲端 VM、地端主機與混合環境。具體指令目前寫好的是 GCP 版，見 [GCP VM 的 SSH 管理通道：從預設的全開 SSH 規則改走 IAP TCP forwarding](/infra/03-network-foundation/gcp-iap-ssh-access/)。

## 管理通道的三層：網路可達性、通道授權、主機登入驗證

管理通道指管理員從自己的電腦登入伺服器作業系統的那條路徑。一次 SSH 登入要依序通過三層檢查，每一層都可以單獨換做法：

- **網路可達性**：管理員電腦送出的封包是否到達得了伺服器上 sshd 監聽的 port。防火牆規則、伺服器是否持有公開 IP、中間是否經過代理，決定的都是這一層。
- **通道授權**：在封包抵達 sshd 之前，是否有一個元件先確認「這個人可以使用這條通道」，以及它憑什麼確認——來源 IP、VPN 憑證、跳板機上的 SSH 金鑰，或一個身分提供者（[identity provider](/backend/knowledge-cards/identity-provider/)，IdP）上的帳號。
- **主機登入驗證**：封包抵達 sshd 之後，sshd 用什麼判斷這個連線可以登入哪個帳號——`authorized_keys` 裡的靜態公鑰、由中央服務動態提供的公鑰，或 SSH CA 簽發的短期憑證（[SSH Certificate（SSH 憑證）](/infra/knowledge-cards/ssh-certificate/)）。

防火牆對 `0.0.0.0/0` 開 22 port 的狀態，在這個模型裡是網路可達性全開、通道授權不存在、只剩主機登入驗證一層在擋。收斂管理通道的做法，多數是替網路可達性與通道授權換上更嚴格的做法；主機登入驗證另有它自己的換法，從沒有到期時間的靜態金鑰換成收得回來的金鑰。

每一層檢查擋下的攻擊者，是手上的憑證與所在位置過得了前面幾層、過不了這一層的人。網路可達性擋的是只能從網際網路送封包、還沒有任何憑證的攻擊者，例如掃描程式與 sshd 漏洞的利用程式；通道授權擋的是已經能把封包送到通道入口、卻沒有通道身分的人，例如私鑰從筆電外洩、但沒有組織 IdP 帳號的人；主機登入驗證擋的是持有通道權限、卻不該登入某台主機或某個帳號的成員，例如開發者登入他不負責的資料庫主機、或取得他不該有的 sudo。同一個做法可能同時改變兩層（來源 IP 白名單、身分感知代理），所以評估一個做法時要逐層問它改了哪一層；只加強其中一層時，已經過得了那一層的攻擊者面對的仍是另外兩層原本的設定。

## 對外開放管理 port 的實際風險

管理 port 對整個網際網路開放之後，主機的認證紀錄很快就會出現來自陌生 IP 的失敗登入，開一台測試主機查一次紀錄就看得到。紀錄的位置依發行版不同：Debian 與 Ubuntu 是 `journalctl -u ssh` 或 `/var/log/auth.log`，RHEL 系是 `journalctl -u sshd` 或 `/var/log/secure`。這些嘗試要成功，取決於主機登入驗證那一層的設定；而只剩那一層在擋時，風險集中在四個地方：

- **sshd 本身的漏洞**：2024 年的 regreSSHion（CVE-2024-6387）讓未經認證的連線有機會在 OpenSSH 伺服器上執行程式碼。這類漏洞發生在認證之前，金鑰設定得再嚴格也擋不住，能縮短暴露期的只有修補速度與網路可達性。
- **密碼登入**：多數雲端廠商的官方 Linux 映像檔預設關閉 SSH 密碼登入、只接受金鑰，單純猜密碼在沒改過設定的主機上不會成功。有人為了方便打開 `PasswordAuthentication yes`、或建了弱密碼的本機帳號，這道預設就失效，而這類改動發生在主機內部，防火牆看不到。
- **金鑰的生命週期**：私鑰從筆電、CI 或共用資料夾外洩之後，持有者從任何地方都能登入；成員離職時沒從 `authorized_keys` 移除的公鑰持續有效。靜態公鑰沒有到期時間，所以「誰還拿得到這台主機」只能靠人工盤點查出來。
- **RDP**：Windows 的遠端桌面預設接受帳號密碼，暴力猜測對它的成功率比對只收金鑰的 SSH 高，所以 3389 對外開放的被入侵機率高於 22。

同一個內部網段裡的主機之間如果所有 port 互通，一台主機被攻破後，攻擊者從那台機器可以直接連到其他主機的資料庫 port 與管理 port，這種擴散方式叫[橫向移動（lateral movement）](/backend/knowledge-cards/lateral-movement/)。收斂對外的管理 port 時，內部網段之間的規則要一起盤點，最小開放的設計見[網路地基 — VPC、subnet 分層與 security group 設計](/infra/03-network-foundation/vpc-subnet-security-group/)的〈security group 設計：最小開放〉一節。

## 網路可達性的做法：管理 port 對誰開放

網路可達性這一層的目標是讓 sshd 只對經過通道授權的來源可見。可選的做法依伺服器是否仍需接受入站連線分成兩類。

**仍然接受入站、但縮小來源**的做法有四種：

- **來源 IP 白名單**：防火牆只放行公司對外的固定 IP。設定成本最低；代價是遠端工作與 IP 變動時要一直改規則，而且公司網路裡任何一台被入侵的電腦都在白名單內。它同時兼任通道授權，判斷身分的依據是 IP。
- **跳板機（[bastion host](/infra/knowledge-cards/bastion-host/)）**：一台放在公開網段、只用來轉接 SSH 的主機，其他主機只接受來自它的連線。暴露面從每台主機收斂成一台，但那一台仍然對外開著管理 port，要修補、要監控，它的 sshd 漏洞就是整個環境的入口。它同時兼任通道授權，判斷依據是跳板機上的 SSH 金鑰。好處是與廠商無關、可以集中錄製操作紀錄。
- **身分感知代理（[identity-aware proxy](/infra/knowledge-cards/identity-aware-proxy/)）**：由廠商提供或自己架設的代理服務在網際網路上接收連線，向 IdP 驗過身分之後，才從代理服務自己的固定位址段連到主機的內部 IP。防火牆只放行那段代理位址，主機本身不需要公開 IP。GCP 的 IAP TCP forwarding 是這一類的代表。
- **VPN**：讓管理員的電腦加入內部網路，再用內部 IP 連主機，主機接受的入站只來自 VPN 範圍內的位址。它解決的範圍比管理通道大（資料庫用戶端、內部管理介面都能用），代價是 VPN 閘道本身要維運，而連上之後通常整個網段都可達，要另外用防火牆規則限縮。Tailscale 這類 mesh VPN 也屬於這一種：SSH 只綁在 tailnet 的私網介面上，tailnet 裡的裝置預設彼此互通，收窄要靠它的 ACL。可達範圍怎麼收窄、被入侵的一端改不到哪些限制，見 [7.43 兩個網路之間的連線安全](/backend/07-security-data-protection/cross-network-connection-security/)的〈VPN 提供的保證與邊界模型〉；tailnet 的位址與連線方式見 [Tailscale 深入：tailnet、MagicDNS、直連與 DERP 中繼](/linux/tools/remote/tailscale-tailnet-and-relay/)。

**主機不接受任何入站連線**的做法是代理程式（agent）反向連線：主機上常駐一個代理程式，由它主動往外連到管理服務並維持一條連線，管理員的工作階段經由那條連線送進來，防火牆不必為管理用途開任何入站 port。AWS 的 SSM Session Manager 是這一類的代表；Cloudflare Access 搭配主機上的 `cloudflared`、Teleport 的節點以反向通道連到 proxy，在網路可達性上也屬於這一類，同時它們也承擔通道授權。這一類的前提是代理程式持續在主機上執行，而且主機有連到管理服務端點的出站路徑。

這一類的工作階段不一定經過 sshd。SSM Session Manager 預設由代理程式直接在主機上開 shell，決定登入成哪個系統帳號、是否能用 sudo 的是 AWS 端的權限設定與代理程式的設定，主機登入驗證那一層因此跟著換掉；只有改用經由 Session Manager 轉送 SSH 的模式時，sshd 與金鑰才仍然在路徑上。採用前要查清楚該服務的工作階段是直接開 shell 還是轉送到 sshd，再決定主機登入驗證那一層要設計什麼。

## 通道授權的做法：用什麼判斷這個人可以使用通道

通道授權這一層辨識每條連線背後的使用者。比較各種判斷依據時看四件事：分不分辨得出個人、判斷依據能不能被複製給別人、收回之後多久生效、留不留得下「是誰」的紀錄。

- **來源 IP**：任何能從那個網路送出封包的人都通過，分辨不出個人，也留不下「是誰」的紀錄。
- **VPN 憑證**：分辨得出個人；憑證檔案能被複製，綁在硬體 token 上時才複製不了；撤銷要靠 VPN 伺服器持續維護憑證撤銷清單。
- **跳板機上的 SSH 金鑰**：每人一把時分辨得出個人；私鑰檔能被複製；收回要到跳板機的 `authorized_keys` 刪除。跳板機與目的主機接受同一把金鑰時，一把私鑰外洩就同時通過通道授權與主機登入驗證，兩層退化成一層。
- **IdP 帳號**：通道服務把驗證交給組織的身分提供者——Google Workspace、Microsoft Entra ID、Okta 這類。GCP IAP 用的 Google 帳號就是這一種的一個實例；Cloudflare Access 可以接任何支援 OIDC 或 SAML 的 IdP，Teleport 的 Enterprise 版也可以，Community 版只支援 GitHub 登入。帳號停用之後，下一次開通道就會失敗，每一次開通道都記錄得到是哪個帳號。

IdP 帳號在四件事上都最好，前提是 IdP 那一端強制防釣魚的多因素驗證：選用 IdP 帳號之後，管理通道的風險轉移到那個帳號上，帳號被釣魚，攻擊者就能開通道。只有密碼的 IdP 帳號在「能不能被複製給別人」這件事上，不比綁在硬體 token 上的 VPN 憑證好。所以這個做法的前提是 IdP 強制多因素驗證，管理員帳號優先用硬體安全金鑰；要再收緊時，多數 IdP 與代理服務支援裝置狀態（device posture）條件，例如只允許公司管理的裝置。授權範圍也要一起設計：限定在負責維運的群組、限定可以連的 port 與主機，原則見[身分與存取憑證地基 — IAM 模型、OIDC 短期憑證與權限邊界設計](/infra/02-identity-credentials/iam-oidc-privilege-boundary/)的〈最小權限：持續收斂而非一次設定〉。

CI 或自動化工具要使用管理通道時，它的身分是服務帳號或機器身分。長期有效的機器金鑰外洩，等同一把能進所有主機的鑰匙，所以這類身分用 OIDC 換取短期存取憑證，做法見同一篇的〈OIDC：給 CI/CD 的短期憑證〉。

## 主機登入驗證的做法：SSH 金鑰怎麼發、怎麼收回

主機登入驗證這一層決定 sshd 接受哪些金鑰，而設計的重點是金鑰的生命週期：誰發、多久失效、離職時怎麼收回。

- **靜態 `authorized_keys`**：公鑰手動或由設定管理工具寫進主機。沒有到期時間，收回要逐台刪除，主機數量一多就難以盤點；金鑰認證的基本設定見 [SSH](/infra/knowledge-cards/ssh/)。
- **由中央服務動態提供公鑰**：主機在登入當下向中央服務查詢這個帳號的公鑰，帳號或角色被移除，下一次登入就失敗。GCP 的 [OS Login](/infra/knowledge-cards/os-login/)、AWS 的 EC2 Instance Connect（推送只在短時間內有效的公鑰）屬於這一類，兩者都綁定各自的雲端廠商。
- **SSH CA 簽發的短期憑證**：主機只信任一把 CA 公鑰（sshd 的 `TrustedUserCAKeys`），管理員登入前向簽發服務取得一張有效期有限的使用者憑證。憑證過期自動失效，不需要逐台收回；有效期就是能接受的最晚收回延遲。HashiCorp Vault 的 SSH secrets engine 與 Teleport 都以這種方式運作；OpenSSH 本身就支援，用 `ssh-keygen -s` 簽發，所以這一種做法同時與廠商無關、又不需要逐台收回。

三種做法收回的都是下一次登入。已經建立的工作階段不受影響，處理離職或帳號外洩時，要另外在主機上結束那個使用者的工作階段。

這一層與通道授權常由同一個系統提供（例如 Teleport 同時做代理與簽發憑證、GCP 的 IAP 與 OS Login 都依 IAM 判斷），但兩者仍然是兩次檢查：通道授權允許開通道，主機登入驗證決定進了通道之後能登入哪個帳號、是否取得 sudo。

## 移除公開入口之後的出站路徑

管理通道改走身分感知代理或代理程式反向連線之後，伺服器的公開 IP 對管理用途就不再必要，移除它可以讓主機從網際網路上無法定址。移除之前要先處理主機往外的連線：沒有公開 IP 的主機預設連不到網際網路，套件更新、拉容器映像檔、呼叫第三方 API 都會逾時。

出站需求的對應做法是 [NAT](/infra/knowledge-cards/nat/)：讓內部主機主動往外連、外部無法主動連進來。存取同一家雲端廠商的服務（物件儲存、容器 registry）時，多數廠商提供不經過 NAT 的私有端點，流量不出公網。計費依端點類型不同：GCP 的 Private Google Access 與 AWS 的 Gateway Endpoint（S3、DynamoDB）不另收費，可以省下 NAT 的處理費用；AWS 的 Interface Endpoint 另有按小時與傳輸量的計費。採用代理程式反向連線的環境要特別確認：代理程式本身需要連到管理服務端點，出站路徑一斷，管理通道也跟著斷。

對外提供服務的主機（網站、API）移除公開 IP 之後，流量入口改由負載平衡器承接，見[流量入口層 — 請求怎麼從使用者到達應用](/infra/03-network-foundation/traffic-entry-layer/)。

## 切換管理通道時避免把自己鎖在外面

切換管理通道的順序由一個事實決定：舊路徑被移除的那一刻起，所有走舊路徑的連線都會被拒絕，包括正在操作的管理員自己的那一條。所以新通道要在舊路徑還在的時候建好，每一位管理員都用自己的身分實際連通一次，才移除舊路徑。

舊路徑還在時，連通測試有兩種方式會誤報成功。主機同時有公開 IP 與新通道時，連線工具可能優先走舊的直連路徑，所以測試要用工具的強制參數走新路徑（GCP 上是 `gcloud compute ssh --tunnel-through-iap`）。即使連線確實走了新通道，舊的全開規則也同時放行代理的位址段，放行這條連線的可能是舊規則、而新規則根本寫錯了。驗證新規則要先停用舊規則（停用可以還原，刪除不行），或查防火牆紀錄裡命中的是哪一條規則；防火牆規則透過雲端廠商的 API 修改，停用之後連不上 SSH 也還原得回來。

用 IaC 管防火牆的環境，移除舊規則要改在程式碼裡。只在網頁管理介面或 CLI 刪掉，下一次 apply 會把程式碼裡仍然存在的規則建回來，這種落差叫 [drift](/infra/knowledge-cards/drift/)。

## 救援入口：管理通道斷掉時的備用路徑

管理通道的任何一層出錯——防火牆規則寫錯、代理服務的權限設錯、sshd 設定改壞、磁碟滿導致 sshd 起不來——管理員就進不了主機。救援入口是一條不經過主機作業系統的網路設定與 sshd 的路徑：雲端廠商的[序列主控台（serial console）](/infra/knowledge-cards/serial-console/)（GCP 的 Serial Console、AWS 的 EC2 Serial Console），以及地端主機的 IPMI、iDRAC 這類頻外管理介面（out-of-band management）。頻外管理介面有自己的網路埠，它的網路要接在獨立的管理網段。

救援入口本身也是一個能登入主機的入口，所以它的設計與管理通道相反：平時保持關閉或只授權給少數持有救援責任的帳號，只在救援時對單一主機開啟。序列主控台多半用主機上的本機帳號密碼登入，這個救援帳號要在主機還正常時就預先建好；等管理通道斷掉才想到要建，已經沒有路徑可以建。

## 組織層級的護欄與稽核紀錄

單一專案或帳號的收斂只保護那一處，下一個新建的專案仍可能帶著對外開放的管理 port。組織層級的護欄有兩種：限制資源能被建成什麼樣子（禁止建立帶公開 IP 的主機、禁止來源是 `0.0.0.0/0` 的管理 port 規則、強制啟用集中式金鑰管理、預設關閉序列主控台），以及在組織層級評估、優先於專案規則的防火牆政策。IaC 環境另外可以在 PR 階段用 checkov 這類工具擋下全開規則，見 [infra 走 PR 流程](/infra/07-infra-as-pr/plan-review-apply-guardrails/)的〈tflint / checkov / tfsec：抓壞寫法與安全漏洞〉。

稽核要查得出三項紀錄：誰在什麼時候經由哪條通道登入了哪台主機、誰在什麼時候開了救援入口、環境裡是否出現新的對外開放管理 port。防火牆紀錄只看得到來源位址；走代理的環境，來源位址都是代理的位址段，要知道是哪個人，得靠通道授權那一層的紀錄（代理服務或 IdP 的 audit log），或主機登入驗證那一層的紀錄（每人一把時的金鑰指紋、SSH 憑證的識別字串、OS Login 的使用者名稱）。通道授權用來源 IP 時，「是誰」只剩 sshd 紀錄裡的金鑰指紋可查，而且只在每人一把金鑰時對得到人。對外開放規則的盤點方法見 [Security Group 稽核與清理](/infra/03-network-foundation/security-group-audit-cleanup/)。

## 三層做法的組合條件：身分系統、主機位置、人員流動與部署方式

三層的做法依序決定比較不容易互相衝突：先決定通道授權用什麼身分，再依身分與主機位置決定網路可達性，最後決定主機登入驗證的金鑰怎麼發。理由是通道授權的身分來源限制了後面兩層能用哪些服務——一個只認 Google 帳號的代理，對身分在 Entra ID 的組織就用不了。

**通道授權的身分來源**：

- 組織有集中的 IdP → 用 IdP 帳號，先在 IdP 強制防釣魚的多因素驗證。
- 沒有 IdP，管理員有固定的對外 IP → 來源 IP 白名單，接受分辨不出個人的代價，「是誰」靠每人一把的主機金鑰追。
- 沒有 IdP，也沒有固定的對外 IP（遠端工作的小團隊、外包團隊維護客戶的幾台主機）→ VPN 憑證，或跳板機加每人一把的 SSH 金鑰；跳板機與目的主機不接受同一把金鑰。外包團隊的收回事件是合約結束、整個團隊離場，所以要有一份跳板機與所有主機上屬於這個團隊的金鑰清單。

**網路可達性的做法**：

- 主機全在同一家雲端，而那家廠商的代理能接組織的 IdP → 廠商的身分感知代理或代理程式反向連線（GCP 用 IAP、AWS 用 SSM Session Manager）；採用反向連線之前先確認主機有到管理服務端點的出站路徑。
- 廠商的代理只認自家帳號，而組織的 IdP 是別家 → 能接 OIDC 或 SAML 的代理服務（Cloudflare Access、Teleport Enterprise 這類）。
- 主機跨多家雲端或含地端 → 能接組織 IdP、與廠商無關的代理服務，一套通道授權涵蓋所有環境，省下在每個環境各維護一套權限的工作；需要集中錄製管理員在主機上的操作時，選跳板機或有錄製功能的代理；除了 SSH 還要連資料庫與內部管理介面時，選 VPN。
- 主機在不提供代理服務的 VPS 商 → 跳板機、VPN 或自架的代理服務，或主機本身只開放給來源 IP 白名單。

**主機登入驗證的做法**：

- 已經用 IdP 而廠商提供依同一個身分判斷的中央提供公鑰（GCP 的 OS Login）→ 直接用它，導入成本接近零，收回跟著帳號走。
- 主機跨多個環境 → SSH 憑證，OpenSSH 內建、與廠商無關，有效期依能接受的最晚收回延遲設定。
- 主機少、人員穩定、沒有 IdP → 靜態 `authorized_keys` 的盤點成本還可控，收回金鑰要寫進離職與合約結束的交接流程。

**部署方式**也會改變通道要開多久：服務已經用不可變基礎設施（immutable infrastructure）的方式部署，也就是以重新建立主機取代登入修改時，管理通道只在除錯與救援時才用得到，平時可以移除通道授權的綁定，除錯時才臨時授予。

更換 SSH port 與安裝 fail2ban 不在這三層裡。更換 port 之後，sshd 仍然對整個網際網路可達、仍然只靠主機登入驗證在擋，掃描程式找的是開著的 port，不是 22 這個數字。fail2ban 在同一個來源失敗多次之後封鎖它，擋得住重複猜測，擋不住第一次就成功的攻擊（sshd 漏洞的利用、外洩的私鑰），也不改變誰能把封包送到 sshd。兩者減少的是認證紀錄裡的雜訊。
