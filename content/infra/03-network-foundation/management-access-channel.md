這篇整理管理員登入伺服器（SSH、RDP）的通道怎麼設計，內容與雲端廠商無關，適用於雲端 VM、地端主機與混合環境。各家廠商的具體指令另有實作篇，GCP 的版本見 [GCP VM 的 SSH 管理通道：從 default-allow-ssh 改走 IAP TCP forwarding](/infra/03-network-foundation/gcp-iap-ssh-access/)。

## 管理通道的三層：網路可達性、通道授權、主機登入驗證

管理通道指管理員從自己的電腦登入伺服器作業系統的那條路徑。一次 SSH 登入要通過三件彼此獨立的事，每一件都可以單獨換做法：

- **網路可達性**：管理員電腦送出的封包是否到達得了伺服器上 sshd 監聽的 port。防火牆規則、伺服器是否持有公開 IP、中間是否經過代理，決定的都是這一層。
- **通道授權**：在封包抵達 sshd 之前，是否有一個元件先確認「這個人可以使用這條通道」，以及它憑什麼確認——來源 IP、VPN 憑證，或一個身分提供者（identity provider，IdP）上的帳號。
- **主機登入驗證**：封包抵達 sshd 之後，sshd 用什麼判斷這個連線可以登入哪個帳號——`authorized_keys` 裡的靜態公鑰、由中央服務動態提供的公鑰，或 SSH CA 簽發的短期憑證。

防火牆對 `0.0.0.0/0` 開 22 port 的狀態，在這個模型裡是網路可達性全開、通道授權不存在、只剩主機登入驗證一層在擋。收斂管理通道的各種做法，差別在它們把前兩層換成什麼。

這三層要分開設計的理由是它們擋的攻擊不同。網路可達性擋的是還沒取得任何憑證的攻擊者（掃描程式、sshd 漏洞的利用程式）；通道授權擋的是拿到主機金鑰、卻沒有通道身分的人；主機登入驗證擋的是拿到通道、卻不該登入這台主機或這個帳號的人。只加強其中一層，其他兩層的攻擊照樣成立。

## 對外開放管理 port 的實際風險

管理 port 對整個網際網路開放之後，自動掃描程式通常在幾分鐘內就開始嘗試連線，主機的認證紀錄（`journalctl -u ssh` 或 `/var/log/auth.log`）會持續出現來自陌生 IP 的失敗登入。這些嘗試要成功，取決於主機登入驗證那一層的設定；而只剩那一層在擋時，風險集中在四個地方：

- **sshd 本身的漏洞**：2024 年的 regreSSHion（CVE-2024-6387）讓未經認證的連線有機會在 OpenSSH 伺服器上執行程式碼。這類漏洞發生在認證之前，金鑰設定得再嚴格也擋不住，能縮短暴露期的只有修補速度與網路可達性。
- **密碼登入**：多數雲端廠商的官方 Linux 映像檔預設關閉 SSH 密碼登入、只接受金鑰，單純猜密碼在沒改過設定的主機上不會成功。有人為了方便打開 `PasswordAuthentication yes`、或建了弱密碼的本機帳號，這道預設就失效，而這類改動發生在主機內部，防火牆看不到。
- **金鑰的生命週期**：私鑰從筆電、CI 或共用資料夾外洩之後，持有者從任何地方都能登入；成員離職時沒從 `authorized_keys` 移除的公鑰持續有效。靜態公鑰沒有到期時間，所以「誰還拿得到這台主機」只能靠人工盤點查出來。
- **RDP**：Windows 的遠端桌面預設接受帳號密碼，暴力嘗試的成功率比只收金鑰的 SSH 高，對外開放 3389 的風險高一級。

同一個內部網段裡的主機之間如果所有 port 互通，一台主機被攻破後，攻擊者從那台機器可以直接連到其他主機的資料庫埠與管理埠，這種擴散方式叫橫向移動（lateral movement）。收斂對外的管理 port 時，內部網段之間的規則要一起盤點，最小開放的設計見[網路地基 — VPC、subnet 分層與 security group 設計](/infra/03-network-foundation/vpc-subnet-security-group/)。

## 網路可達性的做法：管理 port 對誰開放

網路可達性這一層的目標是讓 sshd 只對經過通道授權的來源可見。可選的做法依伺服器是否仍需接受入站連線分成兩類。

**仍然接受入站、但縮小來源**的做法有三種：

- **來源 IP 白名單**：防火牆只放行公司對外的固定 IP。設定成本最低；代價是遠端工作與 IP 變動時要一直改規則，而且公司網路裡任何一台被入侵的電腦都在白名單內。它同時兼任通道授權，而它用來判斷身分的依據是 IP。
- **跳板機（bastion host）**：一台放在公開網段、只用來轉接 SSH 的主機，其他主機只接受來自它的連線。暴露面從每台主機收斂成一台，但那一台仍然對外開著管理 port，要修補、要監控，它的 sshd 漏洞就是整個環境的入口。好處是與廠商無關、可以集中錄製操作紀錄。
- **身分感知代理（identity-aware proxy）**：由廠商或第三方提供的代理服務在網際網路上接收連線，驗過身分之後才從固定的內部位址段連到主機。防火牆只放行那段代理位址。GCP 的 IAP TCP forwarding、Cloudflare Access、Teleport 的 proxy 屬於這一類。主機本身不需要公開 IP。

**主機不接受任何入站連線**的做法是代理程式反向連線：主機上跑一個代理程式，由它主動往外連到管理服務並維持一條連線，管理員的工作階段經由那條連線送進來。防火牆不必為管理用途開任何入站 port。AWS 的 SSM Session Manager 是這一類的代表；它的前提是代理程式要持續在主機上執行、而且主機要有連到管理服務端點的出站路徑。

**VPN** 讓管理員的電腦加入內部網路，再用內部 IP 連主機。它解決的範圍比管理通道大（資料庫用戶端、內部管理介面都能用），代價是 VPN 閘道本身要維運，而連上之後通常整個網段都可達，要另外用防火牆規則限縮。

## 通道授權的做法：用什麼判斷這個人可以使用通道

通道授權這一層辨識每條連線背後的使用者，而它的強度取決於判斷依據有多難偽造或轉手。

- **來源 IP**：任何能從那個網路送出封包的人都通過，無法分辨個人，也留不下「是誰」的紀錄。
- **VPN 憑證**：分辨得出個人，但憑證檔案能被複製；撤銷要靠 VPN 伺服器持續維護憑證撤銷清單。
- **IdP 帳號**：通道服務把驗證交給組織的身分提供者——Google Workspace、Microsoft Entra ID、Okta 這類。GCP IAP 用的 Google 帳號就是這一種的一個實例；Teleport、Cloudflare Access 可以接任何支援 OIDC 或 SAML 的 IdP。帳號停用時通道權限同步消失，每一次開通道都記錄得到是哪個帳號。

選用 IdP 帳號之後，管理通道的風險就轉移到那個帳號上：帳號被釣魚，攻擊者就能開通道。所以這個做法的前提是 IdP 那一端強制多因素驗證，管理員帳號優先用硬體安全金鑰這類防釣魚的方式；要再收緊時，多數 IdP 與代理服務支援裝置狀態條件（只允許公司管理的裝置）。權限的授予範圍也要一起設計：授權範圍限定在負責維運的群組、限定可以連的 port 與主機，原則與雲端 IAM 的最小權限相同，見[模組二：身分與存取憑證地基](/infra/02-identity-credentials/)。

CI 或自動化工具要使用管理通道時，它的身分是服務帳號或機器憑證。長期有效的機器金鑰外洩，等同一把能進所有主機的鑰匙，所以這類身分用 OIDC 換取短期憑證，做法見[模組二：身分與存取憑證地基](/infra/02-identity-credentials/)。

## 主機登入驗證的做法：SSH 金鑰怎麼發、怎麼收回

主機登入驗證這一層決定 sshd 接受哪些金鑰，而設計的重點是金鑰的生命週期：誰發、多久失效、離職時怎麼收回。

- **靜態 `authorized_keys`**：公鑰手動或由設定管理工具寫進主機。沒有到期時間，收回要逐台刪除，主機數量一多就難以盤點，接手時的回收方法見 [SSH](/infra/knowledge-cards/ssh/)。
- **由中央服務動態提供公鑰**：主機在登入當下向中央服務查詢這個帳號的公鑰，帳號或角色被移除，下一次登入就失敗。GCP 的 OS Login、AWS 的 EC2 Instance Connect（推送只在短時間內有效的公鑰）屬於這一類。
- **SSH CA 簽發的短期憑證**：主機只信任一把 CA 公鑰（sshd 的 `TrustedUserCAKeys`），管理員每次登入前向簽發服務取得有效期以小時計的使用者憑證。憑證過期自動失效，不需要逐台收回。HashiCorp Vault 的 SSH secrets engine 與 Teleport 都以這種方式運作；OpenSSH 本身就支援，用 `ssh-keygen -s` 簽發。

這一層與通道授權常由同一個系統提供（例如 Teleport 同時做代理與簽發憑證、GCP 的 IAP 與 OS Login 都依 IAM 判斷），但兩者仍然是兩次檢查：通道授權允許開通道，主機登入驗證決定進了通道之後能登入哪個帳號、是否取得 sudo。

## 移除公開入口之後的出站路徑

管理通道改走代理或反向連線之後，伺服器的公開 IP 對管理用途就不再必要，移除它可以讓主機從網際網路上無法定址。移除之前要先處理主機往外的連線：沒有公開 IP 的主機預設連不到網際網路，套件更新、拉容器映像檔、呼叫第三方 API 都會逾時。

出站需求的對應做法是 [NAT](/infra/knowledge-cards/nat/)：讓內部主機主動往外連、外部無法主動連進來。存取同一家雲端廠商的服務（物件儲存、容器 registry）時，多數廠商提供不經過 NAT 的私有端點（AWS 的 VPC Endpoint、GCP 的 Private Google Access），流量不出公網，也省下 NAT 的處理費用。採用代理程式反向連線的環境要特別確認：代理程式本身需要連到管理服務端點，出站路徑一斷，管理通道也跟著斷。

對外提供服務的主機（網站、API）移除公開 IP 之後，流量入口改由負載平衡器承接，見[流量入口層 — 請求怎麼從使用者到達應用](/infra/03-network-foundation/traffic-entry-layer/)。

## 切換管理通道時避免把自己鎖在外面

切換管理通道的順序由一個事實決定：舊路徑被移除的那一刻起，所有走舊路徑的連線都會被拒絕，包括正在操作的管理員自己的那一條。所以新通道要在舊路徑還在的時候建好，每一位管理員都用自己的身分實際連通一次，才移除舊路徑。

實際連通的測試要強制走新路徑。主機同時有公開 IP 與新通道時，連線工具可能優先走舊的直連路徑，測試成功不代表新通道可用——各家工具的強制參數見對應的實作篇。

用 IaC 管防火牆的環境，移除舊規則要改在程式碼裡。只在主控台或 CLI 刪掉，下一次 apply 會把程式碼裡仍然存在的規則建回來，這種落差叫 [drift](/infra/knowledge-cards/drift/)。

## 救援入口：管理通道斷掉時的備用路徑

管理通道的任何一層出錯——防火牆規則寫錯、代理服務的權限設錯、sshd 設定改壞、磁碟滿導致 sshd 起不來——管理員就進不了主機。救援入口是一條不經過網路與 sshd 的路徑：雲端廠商的序列主控台（GCP 的 Serial Console、AWS 的 EC2 Serial Console）、地端主機的 IPMI 或 iDRAC 這類頻外管理介面。

救援入口本身也是一個能登入主機的入口，所以它的設計與管理通道相反：平時保持關閉或只授權給少數持有救援責任的帳號，只在救援時對單一主機開啟。序列主控台多半用主機上的本機帳號密碼登入，這個救援帳號要在主機還正常時就預先建好；等管理通道斷掉才想到要建，已經沒有路徑可以建。

## 組織層級的護欄與稽核

單一專案或帳號的收斂只保護那一處，下一個新建的專案仍可能帶著對外開放的管理 port。組織層級的護欄有兩種：限制資源能被建成什麼樣子（禁止建立帶公開 IP 的主機、禁止來源是 `0.0.0.0/0` 的管理 port 規則、強制啟用集中式金鑰管理），以及在組織層級評估、優先於專案規則的防火牆政策。IaC 環境另外可以在 PR 階段用 checkov 這類工具擋下全開規則，見 [infra 走 PR 流程](/infra/07-infra-as-pr/plan-review-apply-guardrails/)。

稽核要查得出兩項紀錄：誰在什麼時候經由哪條通道登入了哪台主機，以及環境裡是否出現新的對外開放管理 port。防火牆紀錄只看得到來源位址；走代理的環境，來源位址都是代理的位址段，要知道是哪個人，得靠通道授權那一層的紀錄（代理服務或 IdP 的 audit log）。對外開放規則的盤點方法見 [Security Group 稽核與清理](/infra/03-network-foundation/security-group-audit-cleanup/)。

## 選擇組合的條件

三層各自的做法可以組合，選擇取決於環境的幾個條件：

- **主機在哪裡**：全部在同一家雲端時，那家廠商的身分感知代理或代理程式反向連線最省維運——GCP 用 IAP、AWS 用 SSM Session Manager。跨多家雲端或含地端時，與廠商無關的跳板機、VPN 或 Teleport 這類自管代理，讓一套通道授權涵蓋所有環境。
- **組織的身分系統**：已經有集中的 IdP 而且強制多因素驗證時，通道授權用 IdP 帳號的收益最大；沒有集中 IdP 的小團隊，來源 IP 白名單加金鑰認證可以當作過渡，代價是分辨不出個人。
- **主機數量與人員流動**：主機少、人員穩定時，靜態 `authorized_keys` 的盤點成本還可控；主機多或人員常異動時，中央提供公鑰或短期憑證省下的是逐台收回金鑰的工作。
- **部署方式**：服務已經用不可變的方式部署（以重新建立主機取代登入修改）時，管理通道只在除錯與救援時才用得到，可以收得更緊，甚至平時完全關閉。

更換 SSH port 與 fail2ban 能減少認證紀錄裡的掃描雜訊，對三層都沒有改變：掃描工具掃完全部 port 只需要幾分鐘，fail2ban 擋的是同一個來源的重複嘗試。它們可以當作輔助，不替代任何一層。
