這篇整理管理員登入伺服器作業系統的通道怎麼設計，內容與雲端廠商無關，適用於雲端 VM、地端主機與 VPS。適用的前提是服務跑在自己管理的主機上、而且有人要登入那台主機的作業系統；跑在不提供主機登入的平台（PaaS、serverless）上，就沒有這條通道要設計。機制以 SSH 說明，RDP 的差異在〈對外開放管理 port 的實際風險〉另外交代。GCP 上的設定與指令見 [GCP VM 的 SSH 與 RDP 管理通道：從預設的全開規則改走 IAP TCP forwarding](/infra/03-network-foundation/gcp-iap-ssh-access/)。

## 管理通道的三層：網路可達性、通道授權、主機登入驗證

管理通道指管理員從自己的電腦登入伺服器作業系統的那條路徑。一次 SSH 登入依序經過三層檢查，每一層的做法可以分開選，但有些做法同時落在兩層：

- **網路可達性**：管理員電腦送出的封包是否到達得了伺服器上 sshd（SSH 的伺服器端程式）監聽的 port。防火牆規則、伺服器是否持有公開 IP、中間是否經過代理，決定的都是這一層。
- **通道授權**：在封包抵達 sshd 之前，是否有一個元件先確認「這個人可以使用這條通道」，以及它憑什麼確認——來源 IP、VPN 憑證、跳板機上的 SSH 金鑰，或一個身分提供者（[identity provider](/backend/knowledge-cards/identity-provider/)，IdP）上的帳號。
- **主機登入驗證**：封包抵達 sshd 之後，sshd 用什麼判斷這個連線可以登入哪個帳號——`authorized_keys` 裡的靜態公鑰、由中央服務動態提供的公鑰，或 SSH CA 簽發的短期憑證（[SSH Certificate（SSH 憑證）](/infra/knowledge-cards/ssh-certificate/)）。

防火牆對 `0.0.0.0/0`（[CIDR](/infra/knowledge-cards/cidr/) 表示法裡的「所有 IPv4 位址」）開 22 port 的狀態，在這個模型裡是網路可達性全開、通道授權不存在、只剩主機登入驗證一層在擋。收斂管理通道的做法，多數是替網路可達性與通道授權換上更嚴格的做法；主機登入驗證另有它自己的換法，從要逐台刪除的靜態金鑰，換成跟著帳號收回、或會自動到期的金鑰。

每一層擋下的攻擊者，是手上的憑證與所在位置過得了前面幾層、過不了這一層的人。網路可達性擋的是只能從網際網路送封包、還沒有任何憑證的攻擊者，例如掃描程式與 sshd 漏洞的利用程式；通道授權擋的是已經能把封包送到通道入口、卻沒有通道身分的人，例如私鑰從筆電外洩、但沒有組織 IdP 帳號的人；主機登入驗證擋的是持有通道權限、卻不該登入某台主機或某個帳號的成員，例如開發者登入他不負責的資料庫主機、或取得他不該有的 sudo。同一個做法可能同時改變兩層（來源 IP 白名單、身分感知代理），所以評估一個做法時要逐層問它改了哪一層。只加強其中一層時，有能力通過那一層的攻擊者（例如持有 IdP 帳號、卻不該碰這台主機的成員）遇到的另外兩層仍是原本的設定。

## 對外開放管理 port 的實際風險

管理 port 對整個網際網路開放之後，主機的認證紀錄很快就會出現來自陌生 IP 的失敗登入，開一台測試主機查一次紀錄就看得到。紀錄的位置依發行版不同：Debian 與 Ubuntu 是 `journalctl -u ssh` 或 `/var/log/auth.log`，RHEL 系是 `journalctl -u sshd` 或 `/var/log/secure`。這些嘗試要成功，取決於主機登入驗證那一層的設定；而只剩那一層在擋時，風險集中在四個地方：

- **sshd 本身的漏洞**：2024 年的 regreSSHion（CVE-2024-6387）讓未經認證的連線有機會在 OpenSSH 伺服器上執行程式碼。這類漏洞發生在認證之前，金鑰設定得再嚴格也擋不住；能降低這類風險的是修補速度（縮短暴露期）與收窄網路可達性（減少能把封包送到 sshd 的來源）。
- **密碼登入**：多數雲端廠商的官方 Linux 映像檔預設關閉 SSH 密碼登入、只接受金鑰，單純猜密碼在沒改過設定的主機上不會成功。有人為了方便打開 `PasswordAuthentication yes`、或建了弱密碼的本機帳號，這項預設就失效，而這類改動發生在主機內部，防火牆看不到。
- **金鑰的生命週期**：私鑰從筆電、CI 或共用資料夾外洩之後，持有者從任何地方都能登入；成員離職時沒從 `authorized_keys` 移除的公鑰持續有效。組織處理離職時停用的是公司帳號（郵件、IdP），這個動作不會碰到任何一台主機上的 `authorized_keys`；主機的登入紀錄記的是金鑰指紋而不是人名，那把公鑰之後被拿來登入，紀錄上也對不到是誰。靜態公鑰沒有到期時間，所以「誰還拿得到這台主機」只能靠人工盤點查出來。
- **RDP**：Windows 的遠端桌面預設接受帳號密碼，暴力猜測對它的成功率比對只收金鑰的 SSH 高，所以 3389 對外開放的被入侵機率高於 22。RDP 在主機登入驗證那一層的對應是 Windows 帳號，其餘兩層的做法與 SSH 相同。

同一個內部網段裡的主機之間如果所有 port 互通，一台主機被攻破後，攻擊者從那台機器可以直接連到其他主機的資料庫 port 與管理 port，這種擴散方式叫[橫向移動（lateral movement）](/backend/knowledge-cards/lateral-movement/)。收斂對外的管理 port 時，內部網段之間的規則要一起盤點，最小開放的設計見[網路地基 — VPC、subnet 分層與 security group 設計](/infra/03-network-foundation/vpc-subnet-security-group/)的〈security group 設計：最小開放〉一節。

更換 SSH port 與安裝 fail2ban 常被當成這些風險的對策，而它們都不改變上面的狀態。更換 port 之後，sshd 仍然對整個網際網路可達、仍然只靠主機登入驗證在擋，掃描程式找的是開著的 port，不是 22 這個數字。fail2ban 在同一個來源失敗多次之後才封鎖它，所以每個來源的第一次嘗試仍然送得到 sshd；它擋得住重複猜測，擋不住第一次就成功的攻擊（sshd 漏洞的利用、外洩的私鑰）。兩者減少的是認證紀錄裡的雜訊。

## 網路可達性的做法：管理 port 對誰開放

伺服器是否仍需接受入站連線，把網路可達性的做法分成兩類；這一層的目標是讓 sshd 只對經過通道授權的來源可見。

**仍然接受入站、但縮小來源**的做法有四種：

- **來源 IP 白名單**：防火牆只放行公司對外的固定 IP。設定成本最低；代價是遠端工作與 IP 變動時要一直改規則，而且公司網路裡任何一台被入侵的電腦都在白名單內。它同時兼任通道授權，判斷身分的依據是 IP。
- **跳板機（[bastion host](/infra/knowledge-cards/bastion-host/)）**：一台放在公開網段、只用來轉接 SSH 的主機，其他主機只接受來自它的連線。暴露面從每台主機收斂成一台，但那一台仍然對外開著管理 port，要修補、要監控，它的 sshd 漏洞就是整個環境的入口。它同時兼任通道授權，判斷依據是跳板機上的 SSH 金鑰。好處是與廠商無關、可以集中錄製操作紀錄。
- **身分感知代理（[identity-aware proxy](/infra/knowledge-cards/identity-aware-proxy/)）**：由廠商提供或自己架設的代理服務在網際網路上接收連線，向 IdP 驗過身分之後，才從代理服務自己的固定位址段連到主機的內部 IP。防火牆只放行那段代理位址，主機本身不需要公開 IP。它同時承擔通道授權。GCP 的 IAP TCP forwarding 是這一類的代表。
- **VPN**：讓管理員的電腦加入內部網路，再用內部 IP 連主機，主機接受的入站只來自 VPN 範圍內的位址。它解決的範圍比管理通道大（資料庫用戶端、內部管理介面都能用），代價是 VPN 閘道本身要維運，而連上之後通常整個網段都可達，要另外用防火牆規則限縮。Tailscale 這類 mesh VPN 讓每台裝置彼此直連、組成一個私有網路（Tailscale 稱為 tailnet），sshd 只監聽 tailnet 介面的位址；tailnet 裡的裝置預設彼此互通，收窄要靠 Tailscale 的 ACL。Tailscale 依賴它營運的協調伺服器，不想依賴第三方時改用自建的 WireGuard。連上之後的可達範圍怎麼收窄、哪些限制要放在被入侵的一端改不到的位置，見[兩個網路之間的連線安全](/backend/07-security-data-protection/cross-network-connection-security/)的〈VPN 提供的保證與邊界模型〉；Tailscale 與自建 WireGuard 的取捨見 [Tailscale 深入：tailnet、MagicDNS、直連與 DERP 中繼](/linux/tools/remote/tailscale-tailnet-and-relay/)的〈取捨與邊界〉。

**主機不接受任何入站連線**的做法是代理程式（agent）反向連線，一種 [Outbound Tunnel](/backend/knowledge-cards/outbound-tunnel/)：主機上常駐一個代理程式，由它主動往外連到管理服務並維持一條連線，管理員的工作階段經由那條連線送進來，防火牆不必為管理用途開任何入站 port。AWS 的 SSM Session Manager 是這一類的代表；Cloudflare Access 搭配主機上的 `cloudflared`、Teleport 的節點以反向通道連到 proxy，在網路可達性上也屬於這一類，同時它們也承擔通道授權。這一類的前提是代理程式持續在主機上執行，而且主機有連到管理服務端點的出站路徑。

這一類的工作階段不一定經過 sshd。SSM Session Manager 預設由代理程式直接在主機上開 shell，決定能登入成哪個系統帳號、是否能用 sudo 的是 AWS 端的權限設定與代理程式的設定，主機登入驗證那一層因此跟著換掉；只有改用經由 Session Manager 轉送 SSH 的模式時，sshd 與金鑰才仍然在路徑上。採用前要查清楚該服務的工作階段是直接開 shell 還是轉送到 sshd，再決定主機登入驗證那一層要設計什麼。

## 通道授權的做法：判斷連線使用者身分的依據

比較通道授權的判斷依據時看四件事：分不分辨得出個人、判斷依據能不能被複製給別人、收回之後多久生效、留不留得下「是誰」的紀錄。

| 判斷依據            | 分辨個人           | 能否被複製                            | 收回生效                                     | 「是誰」的紀錄               |
| ------------------- | ------------------ | ------------------------------------- | -------------------------------------------- | ---------------------------- |
| 來源 IP             | 分辨不出           | 同一網路的任何人都通過                | 改防火牆規則之後立即生效，但收回的是整個網路 | 只有 IP，對不到人            |
| VPN 憑證            | 每人一張時分辨得出 | 憑證檔能複製，綁在硬體 token 上時不能 | 要靠 VPN 伺服器維護的憑證撤銷清單            | VPN 伺服器的連線紀錄         |
| 跳板機上的 SSH 金鑰 | 每人一把時分辨得出 | 私鑰檔能複製                          | 要到跳板機的 `authorized_keys` 刪除          | 跳板機紀錄裡的金鑰指紋       |
| IdP 帳號            | 分辨得出           | 取決於 IdP 的多因素驗證方式           | 帳號停用之後，下一次開通道就失敗             | 每一次開通道都記錄是哪個帳號 |

跳板機與目的主機接受同一把金鑰時，一把私鑰外洩就同時通過通道授權與主機登入驗證，兩層退化成一層。

IdP 帳號是 Google Workspace、Microsoft Entra ID、Okta 這類身分提供者上的帳號，通道服務把驗證交給它；GCP IAP 用的 Google 帳號就是一個實例。Cloudflare Access 可以接任何支援 OIDC 或 SAML（兩種把登入交給 IdP 的標準協定）的 IdP，Teleport 的 Enterprise 版也可以，Community 版只支援 GitHub 登入。IdP 帳號在分辨個人、收回速度與留下紀錄上都比另外三種好，而「能否被複製」要看 IdP 的設定：選用 IdP 帳號之後，管理通道的風險轉移到那個帳號上，帳號被釣魚，攻擊者就能開通道。所以前提是 IdP 對可以開通道的帳號強制多因素驗證，至少管理員帳號用防釣魚的方式（硬體安全金鑰或 [passkey](/backend/knowledge-cards/passkey/)）——一次性驗證碼會在釣魚頁面上被一起騙走。要再收緊時，多數 IdP 與代理服務支援裝置狀態（device posture）條件，例如只允許公司管理的裝置。授權範圍也要一起設計：限定在負責維運的群組、限定可以連的 port 與主機，原則見[身分與存取憑證地基 — IAM 模型、OIDC 短期憑證與權限邊界設計](/infra/02-identity-credentials/iam-oidc-privilege-boundary/)的〈最小權限：持續收斂而非一次設定〉。

CI 或自動化工具要使用管理通道時，它的身分是服務帳號或機器身分。長期有效的機器金鑰外洩，等同一把能進所有主機的鑰匙，所以這類身分用 OIDC 換取短期存取憑證，做法見[身分與存取憑證地基 — IAM 模型、OIDC 短期憑證與權限邊界設計](/infra/02-identity-credentials/iam-oidc-privilege-boundary/)的〈OIDC：給 CI/CD 的短期憑證〉。

## 主機登入驗證的做法：SSH 金鑰怎麼發、怎麼收回

sshd 接受哪些金鑰由主機登入驗證決定，而設計的重點是金鑰的生命週期：誰發、多久失效、離職時怎麼收回。

- **靜態 `authorized_keys`**：公鑰手動或由設定管理工具寫進主機。沒有到期時間，收回要逐台刪除，主機數量一多就難以盤點；金鑰認證的基本設定見 [SSH](/infra/knowledge-cards/ssh/)。
- **由中央服務動態提供公鑰**：主機在登入當下向中央服務查詢這個帳號的公鑰，帳號或角色被移除，下一次登入就失敗。GCP 的 [OS Login](/infra/knowledge-cards/os-login/)、AWS 的 EC2 Instance Connect（推送只在短時間內有效的公鑰）屬於這一類，兩者都綁定各自的雲端廠商。
- **SSH CA 簽發的短期憑證**：主機只信任一把 CA 公鑰（sshd 的 `TrustedUserCAKeys`），管理員登入前向簽發服務取得一張有效期有限的使用者憑證。憑證過期自動失效，不需要逐台收回；有效期就是能接受的最晚收回延遲，管理員每個工作日開始時簽一次的節奏，對應的有效期是一個工作日左右。[HashiCorp Vault](/infra/knowledge-cards/vault/) 的 SSH secrets engine 與 Teleport 都以這種方式運作；OpenSSH 本身就支援，用 `ssh-keygen -s` 簽發，所以這一種做法同時與廠商無關、又不需要逐台收回。

三種做法收回的都是下一次登入；SSH 憑證的「收回」是到期之後失效。已經建立的工作階段不受影響，處理離職或帳號外洩時，管理員要另外登入主機結束那個使用者的工作階段（systemd 的發行版用 `loginctl terminate-user <username>`）。

這一層與通道授權常由同一個系統提供（例如 Teleport 同時做代理與簽發憑證、GCP 的 IAP 與 OS Login 都依 IAM 判斷），但兩者仍然是兩次檢查：通道授權允許開通道，主機登入驗證決定進了通道之後能登入哪個帳號、是否取得 sudo。

## 移除公開 IP 之後的出站路徑

管理通道改走身分感知代理或代理程式反向連線之後，伺服器的公開 IP 對管理用途就不再必要，移除它可以讓主機從網際網路上無法定址。移除之前要先處理主機往外的連線：沒有公開 IP 的主機預設連不到網際網路，套件更新、拉容器映像檔、呼叫第三方 API 都會逾時。

出站需求的對應做法是 [NAT](/infra/knowledge-cards/nat/)：讓內部主機主動往外連、外部無法主動連進來。存取同一家雲端廠商的服務（物件儲存、容器 registry）時，多數廠商提供不經過 NAT 的私有端點，流量不出公網。計費依端點類型不同：GCP 的 Private Google Access 與 AWS 的 Gateway Endpoint（S3、DynamoDB）不另收費，可以省下 NAT 的處理費用；AWS 的 Interface Endpoint 另有按小時與傳輸量的計費。

採用代理程式反向連線的環境，管理通道本身也走出站路徑：代理程式要連到管理服務端點，出站路徑一斷，管理通道也跟著斷。這種中斷不會出現在服務的監控上。收緊出站規則的理由通常與管理通道無關（拿掉 NAT 省費用、限縮出站的目的地），而對外服務的請求不經過代理程式那條連線，服務照常回應；管理通道平時只在除錯時才有人用，除非另外監看管理服務端顯示的代理程式連線狀態，第一個發現它斷掉的人就是下一次要登入主機的人，往往是在事故當下。出站規則透過雲端廠商的 API 改得回來，代價是事故處理要等找出並恢復出站路徑之後才能繼續。所以收緊出站規則時，要把管理服務端點列進必須保留的目的地。

對外提供服務的主機（網站、API）移除公開 IP 之前，要先把流量入口換到負載平衡器，見[流量入口層 — 請求怎麼從使用者到達應用](/infra/03-network-foundation/traffic-entry-layer/)。

## 切換管理通道時避免把自己鎖在外面

切換管理通道的順序由一個事實決定：舊路徑被移除的那一刻起，所有走舊路徑的連線都會被拒絕，包括正在操作的管理員自己的那一條。所以新通道要在舊路徑還在的時候建好，每一位管理員都用自己的身分實際連通一次，才移除舊路徑。

走舊路徑的不只管理員。CI 或部署腳本用公開 IP 直連主機、設定管理工具、監控探測、第三方廠商的維護連線，都會在舊路徑移除時一起中斷。切換之前先開啟舊規則的防火牆紀錄、觀察一段涵蓋完整部署週期的時間，列出所有來源，把非人員的那些先改走新通道（機器身分用短期存取憑證開通道）。

舊路徑還在時，連通測試在兩種情形下會誤報成功。主機同時有公開 IP 與新通道時，連線工具可能優先走舊的直連路徑，所以測試要用工具的強制參數走新路徑（GCP 上是 `gcloud compute ssh --tunnel-through-iap`）。即使連線確實走了新通道，舊的全開規則（來源 `0.0.0.0/0`）也同時放行代理的位址段，放行這次測試連線的可能是舊規則，而新規則根本寫錯了。驗證新規則要先停用舊規則再測一次——停用的規則一行指令就能恢復原樣，刪除之後要重新建立、重建時可能寫錯——或查防火牆紀錄裡這次連線命中的是哪一條規則；防火牆沒有停用功能時，改用查紀錄這一種。防火牆規則透過雲端廠商的 API 修改，所以停用之後 SSH 連不上，管理員也還原得回來。

用 IaC 管防火牆的環境，移除舊規則要改在程式碼裡。只在網頁管理介面或 CLI 刪掉，IaC 工具下一次執行 apply 時會依程式碼把規則建回來，這種落差叫 [drift](/infra/knowledge-cards/drift/)。

## 救援入口：管理通道斷掉時的備用路徑

管理通道的任何一層出錯——防火牆規則寫錯、代理服務的權限設錯、sshd 設定改壞、磁碟滿導致 sshd 起不來——管理員就進不了主機。救援入口是一條不經過主機作業系統的網路設定與 sshd 的路徑：雲端廠商的[序列主控台（serial console）](/infra/knowledge-cards/serial-console/)（GCP 的 Serial Console、AWS 的 EC2 Serial Console）、VPS 商在管理面板提供的網頁主控台，以及地端主機的 IPMI、iDRAC 這類頻外管理介面（out-of-band management；其他中文資料常寫作「帶外管理」）。頻外管理介面有自己的網路埠，它的網路要接在獨立的管理網段。

救援入口本身也是一個能登入主機的入口，所以它的設計與管理通道相反：平時保持關閉或只授權給少數持有救援責任的帳號，只在救援時對單一主機開啟。這些入口多半用主機上的本機帳號密碼登入，這個救援帳號要在主機還正常時就預先建好；等管理通道斷掉才想到要建，已經沒有路徑可以建。

## 組織層級的護欄與稽核紀錄

單一專案或帳號的收斂只保護那一處，下一個新建的專案仍可能帶著對外開放的管理 port。組織層級的護欄有兩種：限制資源能被建成什麼樣子（禁止建立帶公開 IP 的主機、禁止來源是 `0.0.0.0/0` 的管理 port 規則、強制主機登入驗證改用中央服務提供公鑰、預設關閉序列主控台），以及在組織層級評估、優先於專案規則的防火牆政策。IaC 環境另外可以在 PR 階段用 checkov 這類工具擋下全開規則，見 [infra 走 PR 流程](/infra/07-infra-as-pr/plan-review-apply-guardrails/)的〈tflint / checkov / tfsec：抓壞寫法與安全漏洞〉。

稽核紀錄是在事後用到的：主機上出現沒人認領的設定變更、某把私鑰被回報外洩而要知道它在外洩之後有沒有被用過、成員離職後要確認他的存取確實停了。這些時刻要查的是三項紀錄：誰在什麼時候經由哪條通道登入了哪台主機、誰在什麼時候開了救援入口、環境裡是否出現新的對外開放管理 port（新建的專案或主機照預設建出全開規則，是這一項最常見的來源）。防火牆紀錄只看得到來源位址；走代理的環境，來源位址都是代理的位址段，要知道是哪個人，得靠通道授權那一層的紀錄（代理服務或 IdP 的 audit log），或主機登入驗證那一層的紀錄（每人一把時的金鑰指紋、SSH 憑證的識別字串、OS Login 的使用者名稱）。通道授權用來源 IP 時，「是誰」只剩 sshd 紀錄裡的金鑰指紋可查，而且只在每人一把金鑰時對得到人。這些紀錄多半要事先開啟，只記錄開啟之後的事。AWS 上對外開放規則的盤點方法見 [Security Group 稽核與清理](/infra/03-network-foundation/security-group-audit-cleanup/)。

## 三層做法的選擇：身分來源、連線送達方式與收回方式

選擇三層做法的順序，與封包通過三層的順序不同。封包先過網路可達性，而設計時先定下的是通道授權的身分來源，因為另外兩層能用哪些服務由它篩出來：一個只認 Google 帳號的代理，對身分在 Entra ID 的組織就用不了；OS Login 這類由中央提供公鑰的做法，前提是登入者的身分已經在提供這項服務的雲端廠商的 IAM 裡。所以下面依身分來源、網路可達性、主機登入驗證的順序，說明環境的哪一項條件會排除哪些做法。

### 通道授權的身分來源：集中的 IdP 與固定的對外 IP

組織有沒有集中的 IdP，決定〈通道授權的做法〉那張表裡的兩個屬性能不能達到：收回之後多快生效，以及留不留得下是誰的紀錄。有集中 IdP 的組織，通道授權用 IdP 帳號，前提是先在 IdP 強制防釣魚的多因素驗證；沒有的組織，從來源 IP、VPN 憑證、跳板機上的 SSH 金鑰這三種判斷依據裡，選代價可以接受的那一種。

沒有 IdP 而管理員有固定的對外 IP 時，來源 IP 白名單是最便宜的依據，代價是分辨不出個人，「是誰」只能靠每人一把、登錄在主機 `authorized_keys` 的使用者金鑰的指紋追。沒有固定的對外 IP（遠端工作的小團隊、外包團隊維護客戶的幾台主機）時白名單縮不下來，剩下 VPN 與跳板機兩種：除了 SSH 還要連其他內部服務時選 VPN，每個人用自己的 VPN 憑證；只需要 SSH、或要集中錄製操作時選跳板機，每個人用自己的 SSH 金鑰，而且跳板機與目的主機各用不同的金鑰。外包團隊需要收回權限的時間點是合約結束、整個團隊一起離場，所以要有一份清單，列出跳板機與所有主機上屬於這個團隊的金鑰。

### 網路可達性：代理怎麼把連線送進主機

有 IdP 的組織，網路可達性的選擇取決於代理怎麼把連線送進主機。代理從自己的固定位址段連到主機內部 IP 時（GCP 的 IAP），它只到得了那家廠商網路裡的主機，所以適用的前提是主機全在同一家雲端、而且那家的代理認得組織的 IdP。代理經由主機上的代理程式反向連線時（Cloudflare Access、Teleport），任何有出站路徑的主機都接得上，跨雲、地端與不提供代理服務的 VPS 商都落在這一類，一套通道授權涵蓋所有環境；它的前提換成那條出站路徑，見〈移除公開 IP 之後的出站路徑〉。AWS 的 SSM Session Manager 也能管理地端主機（在主機上安裝代理程式並註冊為受管節點），但通道授權只認 AWS 的 IAM。不想依賴第三方服務時，Teleport Community 版可以自己架設，代價是登入只接 GitHub；`cloudflared` 依賴 Cloudflare 營運的服務。

沒有 IdP 的組織，網路可達性在上一步選身分來源時已經一併選定：白名單、VPN 或跳板機。

不論主機在哪裡，另外兩種需求會把選擇推向跳板機或 VPN。要集中錄製管理員在主機上的操作時（外部廠商或外包人員要登入組織的主機，或內部稽核要求留下逐指令的操作內容、而不只是登入紀錄），錄製要有一個所有工作階段都經過的位置，選跳板機或有錄製功能的代理。除了 SSH 還要連資料庫與內部管理介面時，VPN 的可達範圍本來就比管理通道大。

需求是「沒有任何主機對網際網路開管理 port」（客戶或稽核常這樣要求）時，跳板機與來源 IP 白名單都不符合：跳板機本身仍對外開著 22 port，白名單則是每台主機都對外開著 22 port，只是限制了來源；符合的是 VPN（sshd 只監聽私網位址）、代理程式反向連線，以及從代理位址段連入的身分感知代理（主機只接受代理位址的入站）。

### 主機登入驗證：收回靠什麼發生

網路可達性選了直接在主機上開 shell 的代理程式反向連線（SSM Session Manager 的預設模式）時，sshd 不在路徑上，這一層改由那個服務的權限設定承擔。其餘情形，主機登入驗證的選擇取決於收回靠什麼發生：

- **收回靠人工刪除**（靜態 `authorized_keys`）：成立的條件是主機少、人員穩定，而且收回已經是離職與合約結束交接流程裡的一項。
- **收回靠帳號連動**（由中央服務提供公鑰）：已經用某家廠商的 IdP、而那家廠商提供依同一個身分判斷的公鑰服務（GCP 的 OS Login）時，不必另建簽發服務或金鑰派送流程，收回跟著帳號走；它綁定那家廠商，主機在別的環境就用不了。
- **收回靠到期**（SSH 憑證）：主機跨多個環境（不同雲端、地端、不同 VPS 商，各自管理金鑰的主機群）時，它不依賴任何一家雲端廠商的帳號系統，也不必逐台收回，代價是要維運一個簽發服務並保管 CA 私鑰。SSH 憑證也適用於人員流動高、而且沒有 IdP 的外包團隊：憑證有效期設成一個工作日左右，合約結束的隔天，團隊手上的憑證就全部失效，不必逐台盤點金鑰。自建的中央公鑰查詢（sshd 的 `AuthorizedKeysCommand` 接到 LDAP 或 FreeIPA 這類目錄服務）同樣能跨環境、隨帳號收回，代價換成每台主機在登入當下都要連得到那個目錄服務，目錄服務中斷時所有主機一起登不進去。

### 部署方式與通道開放的時間

服務已經用不可變基礎設施（immutable infrastructure）的方式部署，也就是以重新建立主機取代登入修改時，管理通道只在除錯與救援時才用得到。這時管理員平時可以移除通道授權的權限綁定，除錯時才臨時授予，通道平時對任何人都開不起來。

## AWS 上對應的元件

這篇提到的 AWS 元件按層列在這裡，方便對照：網路可達性有 SSM Session Manager（代理程式反向連線）與 security group（防火牆規則）；通道授權由 AWS IAM 決定誰能開 Session Manager 的工作階段；主機登入驗證有 EC2 Instance Connect（推送短效公鑰）；出站路徑有 NAT Gateway 與 VPC Endpoint；救援入口是 EC2 Serial Console；組織層級的護欄是 AWS Organizations 的 [SCP](/infra/knowledge-cards/scp/)。規則的盤點方式見 [Security Group 稽核與清理](/infra/03-network-foundation/security-group-audit-cleanup/)。
