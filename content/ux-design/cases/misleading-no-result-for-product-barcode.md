book_overview_app 是一個 Flutter 書庫管理教學專案，以下案例取自該專案的實機測試。錯誤回饋的責任是回答使用者下一步該做什麼——一個字面誠實的訊息，若把可本地判定的輸入錯誤混進「查無結果」，就是誤導。

## 觀察

book_overview_app 的掃描器偵測所有 EAN-13 格式條碼。書籍 ISBN-13 一定以 978 或 979 開頭；其他開頭的 EAN-13 是一般商品條碼（飲料、餅乾、日用品）。使用者對準商品條碼掃描時：

| 項目       | 修復前                           | 修復後（W1-089）                                     |
| ---------- | -------------------------------- | ---------------------------------------------------- |
| 判定位置   | 送 Google Books API 遠端查詢     | `IsbnValidationService.isBookIsbn()` 本地判定 prefix |
| 等待時間   | 2 秒以上                         | 即時                                                 |
| 回饋訊息   | 「查無結果」                     | 「此條碼非書籍 ISBN，請掃描書背 ISBN 條碼」          |
| 使用者理解 | 「這本書資料庫沒有」（錯誤歸因） | 「我掃錯條碼了」（正確歸因）＋知道下一步             |
| 掃描狀態   | 中斷                             | 維持掃描中，對準正確條碼即續掃                       |

修復是一個本地 prefix 檢查：非 978/979 開頭的 13 位條碼不進入 ISBN 驗證與 API 查詢流程，直接顯示本地化提示並停留在掃描狀態。978/979 開頭維持既有流程。

## 判讀

1. **可本地判定的錯誤該在本地即時回應**。「這個條碼是不是書籍 ISBN」是純 prefix 規則，毫秒級本地可判。把它丟給 API 等於用 2 秒網路延遲換一個本來就知道的答案 — 違反回饋時間門檻之外，更浪費了「立即告訴使用者掃錯了」的機會。

2. **「查無結果」誠實但誤導**。API 確實查無結果，訊息字面為真。但使用者的歸因是「這本書資料庫沒收錄」，於是重掃、換角度、懷疑 app 壞掉 — 沒有一條路通往真正的解法「去掃書背的 ISBN 條碼」。回饋若不能修正使用者的心智模型，字面誠實沒有價值。

3. **兩種「找不到」是不同的使用者情境，混用同一訊息給錯心智模型**。「輸入本身不合法」（掃錯條碼，本地可判）和「輸入合法但查詢無結果」（確實查無此書，需遠端）需要不同的下一步：前者是換條碼，後者是手動輸入或放棄。訊息合併等於系統放棄了它明明有能力做的錯誤分類。

## 策略

1. **輸入驗證前移**：格式與領域規則（長度、prefix、checksum）在送出前本地攔截，遠端只處理「合法輸入的查詢結果」。設計時對每個送遠端的輸入列一張「本地可判定規則」清單。

2. **錯誤訊息以下一步行動為中心撰寫**：訊息模板是「發生了什麼 + 該做什麼」（「此條碼非書籍 ISBN，請掃描書背 ISBN 條碼」），不是系統視角的查詢結果陳述。寫完自問：使用者讀完知道下一步嗎？

3. **稽核每個「查無結果」訊息**：對既有系統，逐一檢查回「查無結果／找不到」的路徑，問「有沒有本地可判定的原因被混進來」。有，就拆成獨立的即時提示。

## 非書籍條碼分種類的實例：雜誌、期刊，台灣商品條碼，以及誤讀觸發的提示

同一個 APP 在 2026 年 11 月 28 日的實機測試（Samsung SM-S9010、Android 16），使用者拿自己的書與一般商品逐一掃描，暴露出上面那個修正的下一層：本地判定把「不是書的 ISBN」從查無結果裡分出來之後，「不是書的 ISBN」這一句本身又混了幾種下一步不同的情形。

| 讀到的條碼                        | 使用者手上的東西                                   | 這時有用的下一步                                   |
| --------------------------------- | -------------------------------------------------- | -------------------------------------------------- |
| 977 開頭                          | 按期發行、只有 ISSN 的雜誌或期刊                   | 用刊名搜尋；ISSN 只認得出刊名，認不出是哪一期      |
| 471 開頭                          | 台灣的商品條碼；早年在超商、書報攤賣的書常印這一種 | 翻到版權頁找 ISBN 手動輸入；版權頁沒有時用書名搜尋 |
| 其他開頭                          | 一般商品                                           | 換一個條碼掃，或手動輸入、用書名搜尋               |
| 書的 ISBN 被誤讀成非 978 開頭一次 | 一本有 ISBN 的書，相機把條碼讀錯了一次             | 不需要下一步；繼續對準就會讀到正確的號碼           |

修正之前，這四種都顯示同一句「讀到的條碼不是書的 ISBN，請對準標著 ISBN 的那一條」，而且沒有可以按的鍵。拿著雜誌或二十年前的書的使用者照這一句去找 ISBN 條碼，找不到，只能自己猜下一步。修正之後，面板依種類寫出原因，並附「手動輸入」與「改用書名搜尋」兩顆鍵（雜誌、期刊只附書名搜尋，因為它沒有 ISBN 可輸入）；掃描照常繼續，對準 ISBN 就照書的流程查。

這個實例補了兩條上面三條策略沒有涵蓋的判讀：

1. **本地判定出「不是 X」之後，再問「那它是什麼」。** 「不是書的 ISBN」是對的分類，但它是用排除定義的，涵蓋了下一步各不相同的幾種東西。錯誤訊息以下一步為中心時，下一步不同的情形要分開寫；分得開的依據就在輸入裡（條碼的前三碼），本地判得出來。
2. **誤讀觸發的錯誤提示，比沒有提示更糟。** 相機把書的條碼讀錯一次，面板就跳出「不是 ISBN」，使用者以為自己掃錯了東西，移開去找別的條碼，反而離開了正確的那一條。錯誤提示跟「採用一個號碼」要過同一道確認（同一個號碼在短時間內讀到兩次），一次性的誤讀不足以讓 APP 對使用者下結論。

用詞也照使用者的理解調整：提示原本寫「這是期刊的條碼」，使用者以為期刊不包含雜誌，拿著雜誌時不會把這一句對到自己手上的東西，改成「雜誌、期刊」。977、471、192 這幾種條碼各自屬於哪一套編號、號碼裡每一段代表什麼，在 [書上的條碼怎麼設計：EAN-13 的前綴與檢查碼、ISBN 的 978 與 979、ISBN 10 碼與 13 碼、期刊的 ISSN、台灣商品條碼、日本書的兩段條碼與附加碼](/other/book-barcodes-isbn-issn-and-retail-codes/)；掃描辨識與條碼採用規則的排查在 [Flutter 條碼掃描辨識率低的排查：mobile_scanner 的去重複回報與 APP 的二次確認](/work-log/flutter-barcode-scan-detection-speed-and-read-confirmation/)。
