這張卡以一組實際的狀態配色為例，談用顏色標示狀態時，文字對比以外要分開檢查的事：色覺差異（color vision deficiency）的讀者分不分得出兩種狀態、狀態色塊跟背景分不分得開、同一個顏色縮成細標記之後還看不看得清楚，以及同一個顏色在同一個畫面裡被賦予兩種意思。文字對色塊的對比（選中態的成對設計）在 [U.C17 選中態換底色不換文字色 — 對比沒有成對設計](/ux-design/cases/selected-chip-contrast-not-paired/)；每一組顏色的對比數字、相對亮度的算法與色覺差異的換算，在 [狀態色塊配色的對比量測：文字對色塊、色塊對背景、細標記對底色，以及紅綠色覺差異](/work-log/state-color-contrast-and-color-vision/)。

## 觀察

本站 SQL 練習頁（Web、深色背景）在讀者作答後，把四個選項的色塊翻成三種狀態：推薦；選錯，也就是讀者選了而不推薦的選項；不推薦，也就是讀者沒選、也不推薦的選項（近黑的底色加一條灰色內框）。改版前的低明度配色是深橄欖綠 `#38701a` 標推薦、深莓紅 `#a8295a` 標選錯，色塊上的文字是白色，白字對比分別 6.0:1 與 6.7:1，都過了 WCAG（Web Content Accessibility Guidelines）1.4.3 的 4.5:1。

推薦與選錯剛好是綠與紅，文字對比量不到兩個狀態色之間的色相差。用色覺差異的模擬矩陣換算，第二型色覺差異（deutan，綠色錐細胞的差異）的讀者看到的兩色都偏向橄欖褐，色相與亮度都接近；這是模型換算的推論，不是讀者實測。色塊上另有「推薦」與「你的選擇・不推薦」（選錯）的文字標籤，讀者讀得到狀態，所以 WCAG 1.4.1 Use of Color（顏色不能是傳達資訊的唯一方式）是合規的；缺的是另一層：顏色原本讓讀者掃一眼就認出推薦，這一層他們拿不到。

改配色時又碰到兩個跟色塊周圍的顏色有關的檢查：

- **色塊對背景**：色塊跟深色背景的對比太低時，讀者看不出色塊的邊界。WCAG 1.4.11 Non-text Contrast 要求介面元件與理解內容必需的圖形至少 3:1；翻面後的色塊不能操作、狀態另有文字標籤，不在這一條的要求裡，這一頁的色塊邊界門檻仍取 3:1。定案時選錯用的深灰 `#4f4f4f` 白字有 8.2:1，對黑底卻只有 2.6:1，後來換成 `#5a5a5a`（對黑底 3.0:1）。
- **細標記**：原本的深灰 `#4f4f4f` 縮成進度條上的一小段、放在黑底上只有 2.6:1，縮成結果列（每題一列的結果清單）前的一個小方塊、放在列的底色上只有 2.1:1，都低於 3:1；換成 `#5a5a5a` 之後，對列的底色仍只有 2.5:1，細標記另用一個較亮的灰。

題目畫面上原本有一個實心藍綠的「下一題」按鈕；藍綠改標推薦之後，同一個畫面裡的藍綠同時代表「推薦」與「可以按」。

## 判讀

1. **文字對比量的是字對它的底色，兩個狀態色之間的差別要另外量**。兩種狀態只靠紅綠方向的色相差區分時，文字對比全部合格，色覺差異的讀者仍然分不開兩種狀態。

2. **兩種狀態的色相在色覺差異下分不開時，讀者靠的是亮度或「有沒有顏色」**。藍與橘是讀者在紅綠色覺差異下仍然分得開的常見配對（Okabe 與 Ito 2002 年提出的色覺通用配色裡就有藍與橘）；單一彩色配灰時，只有一種狀態有顏色，另一種是中性色，讀者靠有沒有顏色就分得出來。這一頁由本站作者比較了藍／橘、紫／琥珀、藍綠／灰之後選了藍綠配灰，這是設計決策，沒有找色覺差異的讀者實測。

3. **深色背景上的白字色塊，亮度兩端都受限，背景越亮可選的範圍越窄**。色塊太亮時白字不夠清楚，太暗時色塊跟背景分不開；背景亮到一定程度（比 `#2e2e2e` 左右再亮），沒有任何顏色同時滿足白字 4.5:1 與對背景 3:1，這時要改用黑字或給色塊加框線。文字對比過了，色塊對背景不一定過。

4. **同一個顏色在大色塊與細標記上，量的是不同的兩組顏色**。大色塊上有文字，量白字對色塊；細標記上沒有文字，量標記對它旁邊的底色，旁邊的底色隨狀態改變時（預設、指標停留）每一種各量一次。一個顏色的白字對比過了，換成細標記時要再量一次。

5. **形狀是顏色之外的第二個訊號，改的只是線寬**。進度條的未作答段是 2px 細線、作答過的段是 6px 粗段，只看顏色時讀者分不清的兩段，靠粗細分得開，不必新增任何元素；作答過的段之間（答對、答錯、目前這一題）仍然只差顏色。用背景色畫的形狀在強制色彩模式（Windows 對比主題）下會被換成系統色，粗細也一起消失。

6. **一個顏色在同一個畫面裡代表兩種意思時，讀者可能把兩種意思讀成一種**。藍綠標了推薦之後，實心藍綠的「下一題」按鈕改成白框；兩者同色時，讀者可能把「可以按」與「推薦」讀成同一件事。這一點是推論，沒有找讀者實測。

## 策略

1. **狀態色過三道對比檢查，再加色覺差異**：一般字級的文字對色塊 ≥ 4.5:1、色塊對背景 ≥ 3:1、細標記對它旁邊的底色 ≥ 3:1。三道都用 WCAG 2.2 的相對亮度（relative luminance）公式算，看起來清楚不代替計算；算法在開場連到的那一篇。

2. **對照色覺差異的模擬**：把候選配色放在同一個畫面上並排比較，用瀏覽器開發工具的色覺差異模擬（Chrome DevTools 的 Rendering 面板有 Emulate vision deficiencies，負責把畫面換算成色覺差異讀者看到的樣子）檢查兩種狀態是否仍然分得開。

3. **每個狀態另有文字、框線或形狀**：顏色之外至少一個訊號，例如狀態文字標籤、框線、粗細、實心與空心。第二個訊號用背景色畫時，強制色彩模式下會被換掉；用框線，或在 `@media (forced-colors: active)` 裡改用系統色。顏色不作唯一訊號的整理與色彩區分策略，另見 [視覺輔助：對比度、放大、字型 zoom 的 layout 適配](/report/visual-aids-contrast-zoom-responsive/)。

4. **狀態色在同一個畫面裡只有一個意思**：元件規格寫明這個顏色代表哪個狀態，並寫明同一個畫面的其他元件不用這個顏色當強調色。「同一個顏色」比的是讀者分不分得開，不只比色碼：同色系、讀者分不出差別的兩個顏色也算。沒有這個狀態的畫面（首頁、文章頁）可以沿用同一個顏色。
