紋理圖集（texture atlas）是把很多張小圖排進同一張大圖，再記下每一張小圖在大圖裡佔的矩形；要畫某一張小圖時，從大圖裡依那個矩形取出來畫。同一張小圖在畫面上出現很多次時，圖集裡只放一份，每一次出現都取同一個矩形。Flutter 畫圖集的方法是 `Canvas.drawAtlas`（參數改用型別陣列的版本是 `drawRawAtlas`）：一次呼叫傳入一張 `ui.Image`、每一塊的來源矩形，以及每一塊各自的位置、旋轉與等比縮放（`RSTransform`），還可以給每一塊一個顏色、用混合模式跟那一塊的像素混合，一次畫完全部小圖。`dart:ui` 的 API 文件寫的用途是畫 sprite（遊戲裡角色與物件的小圖，一個角色的動畫常常是一組影格）或局部放大這類「從一張圖畫出很多塊」的情形，並寫明它比逐塊呼叫 `drawImageRect` 有效率。圖集裡的小圖常常是啟動時用 [Picture](/programming/flutter/knowledge-cards/picture/) 錄好、再用 `toImage` 或 `toImageSync` [柵格化](/ux-design/knowledge-cards/rasterization/)（把繪圖指令轉成像素）成點陣圖的內容。

這個做法省時間的地方有兩部分。**預先柵格化**是把繪圖指令事先畫成點陣圖，之後每一幀只取樣與貼上，不必把指令重新柵格化；它不靠圖集也拿得到（每一塊各畫成一張點陣圖、逐塊 `drawImage`）。**拼成圖集**是把很多張點陣圖放進同一張大圖，一次呼叫畫完、共用一張紋理；從機制推論，它在小圖塊很多時才有差別。

## 跟其他概念的關係

- **[Picture](/programming/flutter/knowledge-cards/picture/)** 存的是繪圖指令，每一次重播，raster 執行緒都要把指令重新柵格化一次；點陣圖（不論拼不拼成圖集）存的是柵格化好的像素，每一幀只做取樣與貼上。兩者常常一起用：用 `Picture` 錄出每一塊的內容，啟動時柵格化一次，拼進圖集。
- **[RepaintBoundary](/programming/flutter/knowledge-cards/repaint-boundary/)** 決定 UI 執行緒重錄哪些子樹；用圖集畫，減少的是 raster 執行緒每一幀要柵格化的工作，兩者可以一起用。圖集的 `CustomPaint` 跟其他元件放在同一個邊界裡時，圖集每一幀重畫，同一個邊界裡不動的文字與按鈕也跟著每一幀重錄；反過來，鄰居重畫時圖集那一層也跟著重錄，不過圖集的繪製只有一次 `drawAtlas`，這個方向的成本小。所以會動的圖集放進自己的邊界。
- **[FrameTiming](/programming/flutter/knowledge-cards/frame-timing/)** 的 `rasterDuration` 是判斷預先柵格化有沒有效的讀數。engine 量的是整個畫面在 raster 執行緒上的時間，同一個畫面上另有模糊、陰影這類工作時，讀數裡也包含它們；要知道小圖塊自己佔多少，把那些小圖塊拿掉再量一次，比較兩次的差。
- **[Flutter Thread Model](/programming/flutter/knowledge-cards/flutter-thread-model/)** 卡的判斷條件分出瓶頸在哪一條執行緒：瓶頸在 raster 執行緒時，這張卡的做法有用；瓶頸在 UI 執行緒的 rebuild 時，先減少 rebuild。

## 可觀察訊號與例子

〔[Flutter 像素場景的每幀柵格化成本](/programming/flutter/hands-on/pixel-scene-texture-atlas-frame-cost/)〕量的像素樹場景（168 × 100 格的像素畫，每一格在畫面上是 4 × 4 邏輯點）原本每一幀重播背景與 41 張葉叢與枝層的 `Picture`，裡面是一格像素一個 `drawRect`，共 11,046 個。改成啟動時把每一叢拼進一張 1 格 = 1 px 的圖集、每一幀用一次 `drawRawAtlas` 平移後畫上去之後，每個 vsync 都重畫的版本每幀柵格化從 3.71 ms 降到 0.6 ms 左右，幀數不變（2026 年在 macOS 桌面版、144 Hz 螢幕、Skia 渲染後端的量測；同時把背景也畫成一張點陣圖並放進自己的 `RepaintBoundary`、換姿勢時不 rebuild，這幾處改動沒有拆開量，預先柵格化與拼成圖集各佔多少也沒有拆開）。

## 判斷條件與後果

- **小圖塊的內容事先畫得出來時**：內容固定，每一幀只改位置、旋轉、等比縮放、透明度或整塊的色調（用 `drawAtlas` 每一塊的顏色加混合模式調變），或內容從一組有限的影格裡選（sprite 的走路動畫、計分板的 0 到 9），都屬於這一種。後果是每一塊（或每一個影格）啟動時柵格化一次，之後每一幀只做取樣與貼上；換影格時改的是那一塊的來源矩形，不必重做點陣圖。理由是 raster 執行緒每一幀不再把那些指令重新柵格化。
- **每一塊的繪圖指令很多時省得多，很少時省得少**：省下的是重新柵格化那些指令的時間，取樣與貼上的成本則跟這一塊在畫面上蓋住的面積成正比（從機制推論）。一塊只有一個圓角矩形時，取樣一張點陣圖的成本跟直接畫那個矩形差不多，還多付點陣圖的記憶體與固定解析度；很多塊、每塊蓋住大片面積時，取樣本身就是主要成本，改法省不到這一段。是不是值得改，在自己的場景用 `rasterDuration` 量改前改後。
- **小圖塊的內容每一幀都產生新的像素時**（程序產生的形狀、隨資料連續變形、事先窮舉不了），每一幀都得重新柵格化，預先柵格化省不到，拼成圖集也省不到。只是整塊乘上一個隨時間變的顏色，不算新的像素，屬於上面「事先畫得出來」那一種。
- **點陣圖很多塊時**：逐塊 `drawImage` 每一塊是一次繪圖呼叫，拼成圖集之後一次 `drawAtlas` 畫完；`dart:ui` 文件寫圖集比逐塊 `drawImageRect` 有效率。小圖塊的數量怎麼影響這一層省下的比例，沒有量過；只有幾塊時，每次呼叫的固定成本佔得少，逐塊畫成點陣圖就拿得到大部分的收益（推論）。
- **不同內容的小圖放不進一張紋理時**：圖集的長與寬受 GPU 允許的最大 2D 紋理尺寸限制，要算的是不同內容的張數乘上每張的大小，同一張小圖畫幾次都只佔一份。`dart:ui` 文件寫，`toImageSync` 產生的圖超過這個尺寸時，畫它的那一刻才丟出 `PictureRasterizationException`，不是在 `toImageSync` 當下失敗。所以不同內容的小圖多、或照大的顯示尺寸柵格化時，拆成幾張圖集，每一張各畫一次；各裝置的上限不同，要在目標裝置上查。
- **向量風格的小圖要縮放顯示時**：圖集是點陣圖，解析度在柵格化那一刻就固定了，顯示的樣子由 `Paint.filterQuality` 決定。`dart:ui` 文件寫的預設是 `FilterQuality.none`，也就是最近鄰取樣（nearest-neighbor：每個畫面像素直接取最接近的那一個來源像素的顏色），每一個像素放大成一塊同色的方塊；`low` 用雙線性內插，放大時邊緣變平滑；`medium` 另外用事先算好的縮小版本（mipmap），縮小時保留細節。要放大後仍然平滑，柵格化的解析度要配合最大的顯示尺寸，代價是圖片的記憶體照面積增加；之後縮小顯示時，用 `none` 會出現鋸齒，要改用 `medium`（推論，沒有實跑）。
- **像素風的小圖要放大顯示時**：用預設的最近鄰取樣，每一格放大成銳利的方塊。整體縮放倍數（每一格的邏輯點數乘上裝置的像素比）不是整數時，有的格子比相鄰的格子多一個實體像素，格子的寬度不一；逐格畫不反鋸齒的矩形時，邊緣同樣對齊到實體像素，也可能寬度不一，兩種畫法在這個條件下有沒有差別沒有比對過（從取樣的機制推論，沒有實跑）。小圖每一幀平移到不是整數的位置時，最近鄰取樣讓它一次跳一個實體像素，看起來不像反鋸齒的向量圖那樣平順移動（推論，沒有實跑）。
- **取樣方式會混合相鄰像素時**（`low` 以上，或 `medium` 的 mipmap），畫到矩形邊緣時可能混進隔壁那一塊的顏色，所以圖集裡每一塊之間留透明的空隙；用 `medium` 縮小得越多，用到的 mipmap 越小，混合的範圍換算回原圖越寬，空隙也要越寬（推論，沒有查證要多寬，在目標的縮放倍數下目視確認）。最近鄰取樣只取最接近的那一個來源像素，在邊緣不反鋸齒時取到的都落在矩形內，位置不是整數時也一樣（從取樣的機制推論，沒有實跑；`Paint` 預設開反鋸齒，Skia 怎麼對 `drawAtlas` 套用反鋸齒這次沒有查到）。上面那個場景用最近鄰取樣、留 1 px，沒有比較其他寬度。
- **渲染後端不同時**：Flutter 的 Skia 後端有 raster cache，同一個圖層連續幾幀沒變時，engine 把它存成點陣圖重用；Impeller 後端沒有這個快取（engine 原始碼裡 Impeller 的 surface 一律關掉 raster cache）。這個快取只在圖層連續幾幀不變時用得上，每一幀都在動的圖層兩種後端都要重新柵格化，所以影響最大的是不動或很少動的圖層（推論）。同一個改法在兩種後端省下的量可能不同，沒有實跑比較；要知道自己的後端省多少，在那個後端上用 `rasterDuration` 量改前改後。在這一版 Flutter（3.41.3），macOS 桌面版預設用 Skia，App 的 `Info.plist` 設 `FLTEnableImpeller` 才改用 Impeller；iOS 與 Android 的預設後端以官方文件為準。
- **圖集在畫面離開、或場景重建之後不再用時**，呼叫 `ui.Image` 的 `dispose()`：`ui.Image` 持有 engine 端的資源，一直重建圖集而不釋放時，engine 端的記憶體跟著增加（跟 [Picture](/programming/flutter/knowledge-cards/picture/) 卡最後一條相同）。
