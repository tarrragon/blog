事件發生在 2026 年 11 月 28 日。環境是一個 Flutter 3.41 的書庫 APP，在 Android 實機 Samsung SM-S9010（Android 16）上以 profile 版執行，書庫是合成的 5 萬本；量測當下手機的螢幕更新率沒有記下，frame 的預算用 60 Hz 算。操作是在書單的篩選與搜尋改成在 SQLite 裡查詢之後，量兩項畫面指標：搜尋套用到書單更新的 p90，以及打字與捲動時主 isolate 超過 16 ms 的 frame。

這篇整理怎麼把這兩項的時間拆開：在查詢流程與畫面的 provider 上打 timeline 計時點、算出搜尋套用每一段的耗時；在慢 frame 裡分出 BUILD 與 LAYOUT 階段，再開排版的細項；用 `TextPainter` 直接量一個中文字串的排版時間；合成資料的隨機字與找替代字型這兩個推測的成因各自的實驗；以及這段成本歸給資料層還是書單列元件的判斷。量測腳本本身的缺陷與修正在 [Flutter 實機效能量測的排查：integration_test 的打字、無障礙樹、頁面監聽與背景等待，以及 flutter drive 解除安裝 APP 時的資料保全](/work-log/flutter-integration-test-profile-measurement-pitfalls/)；下面拆解用的 timeline 是在量測修正之前錄的，只拿來看比例，修正之後重量的數字在〈排版成本的歸屬〉。

## 中文清單的慢 frame 出現的條件

這個拆解適用於清單一次有十幾列同時進畫面、每一列有好幾段中文文字的 APP，在換一整頁內容（換搜尋結果、快速捲動到新的區段）時出現慢 frame 的情形。它的起點是資料層的工作已經不在主 isolate 上：這個 APP 的篩選與搜尋已經改成 SQLite 查詢、在背景 isolate 執行，一次篩選的查詢約 20 ms。這時兩項畫面指標仍然沒過：搜尋套用 p90 的門檻是 50 ms，量到 97 ms；主 isolate 不該有超過 16 ms 的 frame，量到 10 個。

合成書庫的書名從 U+4E00 起、依 Unicode 順序的 3,000 個漢字隨機挑（多數不是常用字），長度照真實書庫的分布。

## 搜尋套用的時間分段

一次搜尋從改條件到新的一頁畫完，經過這幾個交接：搜尋條件的 provider 改變、id 清單的查詢開始、查詢前檢查有沒有待補算的書、SQL 送出與結果回來、id 清單交給畫面、第一頁的書查詢開始與結果回來、資料庫的列組成 `Book` 物件、畫面拿到第一頁、新的一頁畫完。「待補算的書」指衍生欄位還沒算好的書：這個 APP 把搜尋與排序要用的欄位由書的屬性算好存在資料表裡，查詢前要先補上。每一個交接打一個計時點：

```dart
developer.Timeline.instantSync('q.ids.start');
await _refreshPendingDerivedColumns();
developer.Timeline.instantSync('q.ids.refreshed');
final result = await fetch(db);
developer.Timeline.instantSync('q.ids.fetched');
```

`developer` 是 `import 'dart:developer' as developer;`。沒有錄 timeline 時，這幾行幾乎沒有成本。量測用 `binding.traceAction(() async { ... }, reportKey: 'timeline_query')` 錄 12 次搜尋，再寫一段腳本以每次的「搜尋條件改變」為起點，算出每個計時點的時間差。錄 timeline 本身會讓程式變慢，所以這一次的數字只用來看比例。

12 次的典型分段：

| 段落                                                                | 耗時                                                  |
| ------------------------------------------------------------------- | ----------------------------------------------------- |
| 改條件到 id 查詢開始                                                | 約 1 ms                                               |
| 查詢前的補算檢查                                                    | 約 1 ms                                               |
| id 的 SQL（1 個字的搜尋，用不到 trigram 索引，退回 LIKE 掃 5 萬筆） | 20 到 30 ms                                           |
| 讀第一頁與第二頁的書（含組 `Book`，組 `Book` 本身不到 0.3 ms）      | 各 5 到 7 ms                                          |
| 資料到了之後畫出新的一頁                                            | 27 到 57 ms，其中 LAYOUT 23 到 50 ms，BUILD 2 到 6 ms |

trigram 索引把文字切成連續三個字的片段建索引，搜尋字至少要三個字才查得到；1 個字的搜尋只能逐筆比對。

拆之前列的候選成因，資料層有補算檢查每次開一個 transaction、查詢跨好幾次 isolate、組 `Book` 物件，畫面有一次重建一整頁的列。拆開之後，補算檢查只有約 1 ms；在錄 timeline 的這 12 次裡，資料庫的部分（查 id、讀書）約佔三到四成，最大的一段在資料已經到了之後，畫出新的一頁的 LAYOUT 階段。

## 慢 frame 的 BUILD、LAYOUT 分段與排版細項

打字與捲動的那一段，用同樣的方式錄 timeline，在 UI 執行緒上找出 `Animator::BeginFrame` 超過 16 ms 的 frame，列出每一個 frame 裡的 BUILD、LAYOUT、PAINT 各佔多少。這一次錄製在量測修正之前：打字沒有送進輸入框、無障礙樹還開著，所以量到的是捲動時的 frame；錄 timeline 也讓程式變慢，273 個 frame 裡 21 個超過 16 ms，比沒錄時的 10 個多，只拿來看比例。每一個慢 frame 都是 LAYOUT 佔大部分（12 到 28 ms），BUILD 只有 1 到 3 ms；它們都連續出現在捲動、新的列進入畫面的那幾秒。

LAYOUT 階段裡是哪些 render object（Flutter 負責排列與繪製的物件，每個元件在底下對應一個或幾個），要另外開 `debugProfileLayoutsEnabled = true` 再錄一次（它讓每個 render object 的 layout 各留一個 timeline 事件，本身會讓排版變慢）。錄到的事件裡，`RenderParagraph`（文字排版）佔最多，其次是 `RenderFlex`（它的時間包含子元件，跟 `RenderParagraph` 有重疊）。

## 中文字串的排版時間

確認 LAYOUT 階段的成本在文字排版之後，用 `TextPainter` 直接量：每一種字串準備 60 個，逐一 `layout(maxWidth: 260)`（2 行、17 號字；寬度、行數與字號是這次量測挑的條件，量自己的清單時換成自己那一列文字的寬度、行數與字號），算平均每個多久。

```dart
double layoutMs(TextStyle style, List<String> texts) {
  final sw = Stopwatch()..start();
  for (final t in texts) {
    TextPainter(text: TextSpan(text: t, style: style), textDirection: TextDirection.ltr, maxLines: 2)
      ..layout(maxWidth: 260)
      ..dispose();
  }
  return sw.elapsedMicroseconds / 1000 / texts.length;
}
```

每一種用一批沒排過的字串，避開排版的快取。量了幾次執行，其中一次在錄 timeline；表裡的範圍合併了這幾次執行，各列的對照只在同一次執行裡做。結果：

| 字串                     | 每次排版        |
| ------------------------ | --------------- |
| 中文（隨機漢字），第一次 | 0.74 到 1.22 ms |
| 同一批中文再排一次       | 0.016 ms        |
| 同一批中文，換成 13 號字 | 0.74 ms         |
| 英文書名                 | 0.07 ms         |

中文字串第一次排版是英文的 10 倍左右；同一個字串排第二次幾乎不花時間，因為排版結果有快取；同一個字串換了字號，排版時間又回到第一次的水準，推測快取的鍵包含樣式。書單的一列有 3 到 4 個中文字串：書名、封面上用另一個字號重複的書名、作者、資訊列。一列的字串數乘上十幾列、再乘上每個約 0.8 ms，估得出 25 到 50 ms 的文字排版，跟拆出來的 LAYOUT 階段同一個量級。

## 合成書名的隨機漢字與系統替代字型：兩個推測的實驗

**推測：合成資料的書名是隨機字，字形的快取命中不了，所以比真實書庫慢。** 實驗用 30 個真實書名（例如原子習慣、被討厭的勇氣）各排兩次，60 次的平均是 0.84 ms；後 30 次是同一批字串再排一次、走快取（約 0.016 ms），換算回第一次每個約 1.7 ms，比同一次執行裡的隨機字（1.07 ms）還慢。兩組的長度分布不同（真實書名有十幾字的長書名），所以這組數字不拿來比較兩者誰快，只用來否證推測：真實書名第一次排版也要花這段時間，「隨機字讓合成資料比較慢」不成立。

**推測：APP 沒有指定字型，Android 用 Roboto；Roboto 沒有中文字形，每個中文字串都要在系統的替代字型（fallback font）裡找，所以慢。** 手機上的中文字型是 `NotoSansCJK-Regular.ttc`（32 MB）與 `SECCJK-Regular.ttc`（19 MB），在系統的 `fonts.xml` 裡是沒有家族名稱的替代字型。分兩步試：

- 用名稱指定：`fontFamily` 設成 `Noto Sans CJK TC`、`NotoSansCJK`、`sans-serif`，或 `fontFamilyFallback` 設成 `Noto Sans CJK TC`，第一次執行裡量到 0.77 到 0.78 ms，跟同一次執行的預設樣式（0.76 ms）差不多；第二次執行裡量到 0.81 到 0.86 ms。把 `locale` 設成 zh-Hant-TW，一次是 0.78 ms、另一次是 1.51 ms，兩次差很多，判斷不出效果。這些名稱對不到系統的替代字型，最後還是退回預設。
- 把 Google Fonts 的 Noto Sans TC（可變字型，12 MB）放進 APP 的 assets，在 `pubspec.yaml` 的 `fonts` 宣告後直接指定：`fontFamily` 指定它時 0.75 ms，只給中文用（`fontFamilyFallback`）時 0.84 ms。同一次執行裡，指定系統字型名稱（最後退回系統的替代字型）的那幾組是 0.81 到 0.86 ms，內附字型的兩個值跟它們相近：不必找替代字型的那一組沒有比較快。同一次執行裡預設樣式那幾次是 1.08 到 1.22 ms，比退回同一個替代字型的那幾組還高，前一次執行的預設樣式則是 0.76 ms；推論這幾個值受量測順序影響，不拿來當對照。同一支手機兩次執行之間，預設樣式就差約 ±30%。

換成 APP 自帶、直接指定的字型，中文第一次排版沒有落到預設樣式的起伏之外，所以時間不在找替代字型。剩下的時間花在中文字形的排版本身；其中排字形與斷行（中文每個字之間都可以斷行）各佔多少，這次沒有分開量。實驗用的字型量完之後從 APP 拿掉。

## 排版成本的歸屬

這段文字排版成本隨畫面上同時進場的列數與每一列的中文字串數變大；一頁的列數不隨書庫的本數改變，所以從機制推得它跟書庫的本數無關（小書庫時沒有另外量）。把查詢搬進 SQLite 的那一批工作（量測與修法在 [Flutter 書庫 APP 冷啟動時間的排查：把全部的書載入記憶體、資料庫單例的並行開檔與每次啟動的完整性檢查](/work-log/flutter-cold-start-database-open-and-integrity-check/)），驗收對象是 5 萬本時資料層的門檻：冷啟動到首頁看得到本數不超過 2 秒、載入後記憶體增加不超過 150 MB、查詢不佔主 isolate，三項都過了（1.33 秒、68 MB、背景 isolate）。排版成本不在這三項裡。

量測修正之後重量的數字：停手後約 270 ms 書單換好（其中 150 ms 是刻意的延遲套用（debounce），停止輸入 150 ms 之後才套用搜尋條件），甩動全書單時 449 個 frame 裡 22 個超過 16.7 ms（4.9%），最長 39 ms。修正之後的量測以 16.7 ms（60 Hz 時一個 frame 的時間）為 frame 的預算，原本的指標寫的是 16 ms。原本的 50 ms 門檻量的是搜尋條件改變到書單更新，不含延遲套用；元件驗收的 300 ms 量的是使用者停手到書單換好，含 150 ms 的延遲套用，兩者的起點不同。這個 APP 的處置是把搜尋套用與慢 frame 這兩項，改寫成書單列元件的實機驗收條件（元件庫規格裡每個元件各有一份行為與驗收的條件）：停手到書單穩定 p90 不超過 300 ms、捲動全書單超過 16.7 ms 的 frame 不超過 5%、單一 frame 不超過 50 ms。這三個門檻是把修正之後量到的值（270 ms、4.9%、39 ms）往上取整、經使用者核定的回歸防線，不是從使用體驗推出來的；扣掉 150 ms 的延遲套用，300 ms 對應的是搜尋條件改變之後約 150 ms 內換好，比原本的 50 ms 寬，這是把排版成本認列進來之後重新訂的值。現況三項都過，但沒有餘裕；這支是旗艦機，中階手機上的數字要在那支手機上重量。元件改版時，量測支持的方向是減少每一列要第一次排版的中文字串（封面上的書名用跟書名相同的樣式以共用快取，或不重複顯示），以及把一頁的排版分散到幾個 frame；內附中文字型這個方向被實驗排除了。

## 判斷標準：修法對準的那一段、LAYOUT 階段的文字排版與實驗的對照

一項端到端的畫面指標沒過時，要讓指標動，修法要處理拆出來最大的那一段。這次最大的是 LAYOUT 階段；錄 timeline 的搜尋裡，資料庫的部分約佔三到四成，資料層的修法動得到的只有這一部分，LAYOUT 階段的那一段不會變；拆段的計時點打在每一個跨層的交接上，錄一次 timeline 就分得出比例。

慢 frame 是 LAYOUT 階段佔大部分時，時間花在排列與排版，`debugProfileLayoutsEnabled` 錄下的事件分得出是哪一種 render object。以文字排版為主、內容是中文時，`TextPainter` 量到的第一次排版時間，乘上一列的中文字串數與同時進入畫面的列數，是換一頁內容那一個 frame 裡文字排版時間的估計值。字串的長度與內容會改變單價，估計用的字串要接近真實內容。

一個成因的推論再順，在只改它一個變數的實驗之前都是假設。同一支手機兩次執行之間，同一個樣式就差到約 ±30%，所以拿另一次執行的數字當對照，分不出小於這個幅度的效果，實驗跟對照組要放在同一次執行裡；同一次執行裡也有起伏，所以每個條件交錯重複量幾次，差別超出對照組自己的分布範圍，才算這個變數有效果。這次的字型實驗只量了一輪，對照組取同一次執行裡退回替代字型的那幾組，結論的強度只到這一輪的比較。
