事件說明：2026-11-26，一個 Manifest V3 的 Chrome 擴充功能（未封裝、開發版建置），使用者在書城（Readmoo）的書櫃頁按下提取，書櫃頁首寫著「擁有 1090 本書（封存 21、借出 1）」。這個擴充功能的書目存在 `chrome.storage.local`，最早一批是 2026-03 提取的 96 筆。排查的人改程式、讀程式碼，但沒有使用者瀏覽器的存取權：log 與 storage 的內容由使用者在自己的 DevTools 讀出、貼回給排查的人。

這篇整理一次「提取成功、書庫頁卻停在舊資料」的排查。排查的方法是沿著資料流在每一段取本數，找出第一次對不上的是哪兩段之間；接著整理這次在本數對不上的那幾段找到的成因，popup 預告的本數取自畫面上已載入的元素，而頁首總數的解析規則對不上實際字樣；轉送層把自己的附註寫進事件處理器拿來組 storage key 的欄位，書目寫進一個沒有人讀的 key；同一個書城 ID 在 content script 與事件處理器兩側用了兩種寫法；舊版程式存下的紀錄識別碼取自另一種來源，重新提取時對不上而新增重複。最後是修好程式之後，舊程式寫下的資料怎麼處理。擴充功能的 content script、service worker 與 `chrome.storage` 各自負責什麼、修改之後何時要重新載入，以及 storage 正確而畫面沒有重新讀取（讀取端自己留著舊副本）的成因，這篇沒有處理。

## 資料流各段的本數從哪裡讀

這個擴充功能的書目從網頁到書庫頁經過下面這幾段，每一段的本數各自從一個地方讀得到：

| 段                              | 執行的位置                     | 讀本數的地方                                      |
| ------------------------------- | ------------------------------ | ------------------------------------------------- |
| 來源宣稱的總數                  | 書城網頁                       | 頁首的「擁有 N 本書」                             |
| 載入到 DOM 的數量               | content script（在書城網頁裡） | 捲動載入完成時的 log（`SCROLL_LOAD_COMPLETED`）   |
| 解析成功的數量                  | content script                 | 提取完成時的 log（`EXTRACTION_COMPLETED`）        |
| 寫入時的數量與 storage key      | service worker                 | 寫入前的 log（`[SAVE] 準備儲存 N 本…（key: …）`） |
| storage 裡讀取端那個 key 的數量 | service worker 的 Console      | 直接讀 `chrome.storage`（下面的程式）             |
| 畫面上的數量                    | 書庫頁（擴充功能自己的頁面）   | 畫面上的「全部書目」                              |

本數第一次對不上的是哪兩段之間，缺陷就在前一段的輸出或後一段的輸入。照這張表逐段比對本數，前提是每一段都有一個讀得到的數字；有一段讀不到時，錯在它的前面還是後面就分不出來。相鄰兩段之間有已知理由的差額（封存、借出、刻意保留的紀錄）是口徑不同，不是錯，但扣除的規則本身也要拿實際字樣對照過。比對與清理資料的通用做法見 [Data Reconciliation](/backend/knowledge-cards/data-reconciliation/) 卡。

這幾段的 log 各自只出現在各自的 DevTools：書城網頁按 F12；service worker 在 `chrome://extensions` 該擴充功能的「Service Worker」連結；書庫頁在那個分頁按 F12。使用者在 Console 的 Filter 欄輸入 log 的固定前綴或訊息種類（`SCROLL_LOAD_COMPLETED`、`EXTRACTION_COMPLETED`、`[SAVE]`），就能只把篩出來的那幾行貼回給排查的人。

storage 裡實際存了什麼，使用者在 service worker 的 Console 跑程式讀。先列出每個 key 與它底下的筆數，因為資料寫進錯的 key 時，只讀預期的 key 看不到它：

```js
chrome.storage.local.get(null).then(all => console.log(JSON.stringify(Object.fromEntries(Object.entries(all).map(([k, v]) => [k, Array.isArray(v?.books) ? v.books.length : typeof v])), null, 1)))
```

再讀要查的那一個 key，印計數與樣本：

```js
chrome.storage.local.get('readmoo_books').then(({ readmoo_books: d }) => {
  const books = d.books
  const noCover = books.filter(b => !/^https?:\/\//.test(b.cover || ''))
  console.log('總數', books.length, '沒有封面', noCover.length)
  console.log(JSON.stringify(noCover.slice(0, 5).map(b => ({ id: b.id, title: b.title, cover: b.cover, extractedAt: b.extractedAt })), null, 1))
})
```

`readmoo_books` 是這個擴充功能存 Readmoo 書目的 key，在 `get` 的引數與解構裡各出現一次；換成自己的擴充功能時，兩處都換成它存資料用的 key（第一段程式列出的那些）。`d.books` 與第一段的 `v?.books` 是這個擴充功能存書目的形狀（一個物件，書目陣列放在 `books` 欄位），存成別的形狀時，改取陣列的那一處。資料存在 `chrome.storage.sync` 或 IndexedDB 的擴充功能，`local` 讀到的是空的，要換成它實際用的儲存區。篩選條件與印出的欄位依要查的事改：只看本數，看得出書目消失與重複，看不出某個欄位變了形，所以第二段程式另外數了沒有 https 封面的筆數。這兩段程式只呼叫 `get`，不改資料；第二段先印計數、再印前五筆的完整欄位，讀的人從計數看出範圍、從樣本看出形狀。樣本用 `JSON.stringify` 印成純文字，因為 `console.table` 的表格複製出來會被截斷。

## popup 預告的本數與頁首總數的解析規則

第一個看到的現象是 popup 顯示「提取這 96 本」，書櫃頁首寫 1090 本。popup 的本數由 content script 回報，回報的是 DOM 裡書目元素的數量；書櫃頁是捲動才載入的清單，剛進頁面只有第一批 96 本。按下提取之後，content script 裡的提取程式會把書櫃捲到底，捲動載入的 log 是：

```text
loadedCount: 1068, expectedTotal: 1090, coverageComplete: false, missingCount: 22, stopReason: "count_stable"
```

1068 等於 1090 減去封存的 21 本與借出的 1 本，提取程式捲動載入的書目已經涵蓋書櫃上的全部書。`expectedTotal` 卻是 1090：頁首解析規則比對的是「封存 21 本」「借出 1 本」，數字後面要有「本」字，而實際的字樣是「封存 21、借出 1」，兩條規則都沒對上，扣除項算成 0。提取程式因此一直捲動、等那 22 本，等到連續幾輪（捲動程式設定的穩定輪數）沒有新書，才以 `count_stable` 停下。解析規則對不上時，程式沒有記任何一筆，扣除項安靜地變成 0，跟一個確實沒有封存的書櫃看起來一樣。

頁首解析與 popup 本數的修法：解析規則的「本」字改成可有可無，算出 1068；popup 回報的本數改用頁首總數（扣除封存與借出），讀不到總數的書城仍用已載入的元素數。這次沒有做的有兩項。一項是解析失敗時的紀錄：頁首有「封存」「借出」字樣、而規則抽不出數字時，記一筆 log，下一次字樣再改時才看得見。另一項是讀不到總數的書城：popup 仍然顯示已載入的元素數，而提取會處理全部，預告與實際處理的本數口徑不同。動作前寫出的本數要跟動作實際處理的本數同一個口徑，否則使用者看到預告 96、完成時 1068，分不出哪一個數字是錯的。完成判定要靠總數對照這一點，在 [U.C11 抓到 96/928 本就顯示完成 — 完成判定的證據強度不足](/ux-design/cases/lazy-load-premature-completion/) 有完整的推導。

## 寫入那一段印出的 storage key 與組 key 用的 `source` 欄位

捲動載入了 1068 本，書庫頁仍然只有 96 本，所以再往下兩段取本數：

- 提取完成的 log：`extracted: 1068, total: 1068, failed: 0`，解析沒有掉書。
- service worker 寫入前的 log：`[SAVE] 準備儲存 1068 本書籍到 Chrome Storage（key: [object Object]_books）`。

本數到寫入那一段都是 1068，第一次對不上的是寫入與 storage 裡讀取端那個 key 之間，而寫入那一行同時印出的 key 顯示，書目完整寫進了一個書庫頁不讀的 key。

這個 key 由事件處理器用 `` `${source}_books` `` 組出來，`source` 取自事件資料，事件處理器預期它是書城 ID 的字串（`readmoo`）。事件從 content script 送到事件處理器之前，經過 service worker 裡的訊息轉送層，轉送層替事件資料加上自己的附註：

```js
const enhancedEventData = {
  ...message.data,
  source: { type: 'content-script', tabId: sender.tab?.id, url: sender.tab?.url, frameId: sender.frameId },
  forwardedAt: Date.now()
}
```

轉送層用 `source` 這個名字放「事件從哪個分頁送來」，佔用了事件處理器拿來當書城 ID 的欄位名。content script 送出的事件資料本來沒有帶 `source`，事件處理器的程式碼是 `event.data?.source || 'readmoo'`，原本靠預設值得到 `readmoo`；轉送層補上一個物件之後，物件是真值（truthy），預設值不再生效，樣板字串（template literal）把物件轉成 `[object Object]`。轉送、組 key 與寫入都照常執行，沒有拋錯，只有讀取端讀不到。

事件處理器的單元測試送出的事件都沒有經過轉送層，所以沒有一個測試執行到轉送層佔用 `source` 的那一步。三個測試檔裡有 20 處直接對事件處理器送事件，每一處都明確帶著書城 ID 的字串（`source: 'readmoo'` 這類），是轉送之前的理想形狀。補上的測試照轉送層實際交出的形狀送事件（`source` 是轉送資訊物件，書城 ID 只在每本書自己的 `source` 欄位裡）。

修法改在轉送層與事件處理器：轉送層的附註改放在 `forwardedFrom`，不佔用資料原有的欄位名；事件處理器拿 `source` 組 key 之前，只接受已知書城 ID 的字串，依序取事件的 `source`、`platform`（事件資料裡另一個可能帶書城 ID 的欄位）與每本書自己的 `source`，都沒有才用預設 `readmoo`。這個擴充功能支援 Readmoo、Kobo 與博客來三個書城，三個書城的提取程式都在每本書寫了 `source`，書目非空時用不到預設值；書目是空陣列，或產生端連每本書的 `source` 都漏帶時，才會用到預設值。這次的修法用到預設值時沒有記警告，所以那種時候 Kobo 或博客來的書目會安靜地寫進 Readmoo 的 key。資料有多個來源時，比較安全的處置是拒收或另外隔離並記錯誤，不寫進預設來源的位置（#402 卡的修法有這一項），這次沒有做。

排查組 key 的那一段時，另外找到同一類缺陷的另一個成因：content script 那一側用 `books-com-tw` 代表博客來，事件處理器的書城 ID 是 `books_com_tw`，書庫頁讀的是 `books_com_tw_books`。兩側各有一份書城 ID 清單，差在分隔符，各自對照自己的那一份都合法。就算事件帶到的是 content script 那一側的書城 ID，博客來的書目也會寫進沒有人讀的 `books-com-tw_books`；事件處理器改讀每本書自己的 `source` 之後，這個寫法差異就直接決定 key，修好 `source` 的佔用之後它會變成下一個寫錯 key 的成因。事件處理器因此在對照已知的書城 ID 之前，先把連字號換成底線。中間層換掉欄位的意思、同一個值在兩層用兩種寫法，這兩個形態與修法在 [#402 轉送層把自己的附註寫進下游已經有意義的欄位名：下游照常執行、不報錯，資料完整寫進錯的位置](/report/forwarder-annotation-overwrites-downstream-field/) 整理成一張卡。

## 重新提取時舊紀錄的識別碼比對與新增的重複

重新提取要在建置包含修正之後才做，而這要另外確認。開發版從目前 checkout 的分支建置，修正還在別的分支時，建置輸出裡找不到修正的程式；這時使用者重新提取，跑的是舊程式，會再寫一次錯的資料。建置戳記（建置時寫進程式、在 service worker 的 Console 印出的時間）更新只代表重新建置過，從不含修正的分支重新建置時它一樣會更新，所以確認修正在不在建置裡，要在建置輸出裡搜修正新增、而且修正之前不存在的字串字面值。這次的修正挑不出這樣的字串：`forwardedFrom` 在修正之前就有另一支程式用，從不含修正的分支建置也搜得到；修正新增的字面值只出現在註解裡，建置時會被去掉。挑不出字串時，要在修正裡加一行建置標記再搜。

key 修好、重新提取之後，書庫變成 1072 本，比書櫃上的 1068 本多 4 本，而且仍有書沒有封面。這次寫入前的 log 附了合併摘要：

```text
added: 976, updated: 92, unchanged: 0, notOnPage: 4
```

storage 裡原有 96 筆，合併程式把其中 92 筆對上這次提取的書並更新，4 筆沒對上而原樣留著（`notOnPage`）。沒對上的 4 筆裡，十月堂舊書事１與克蘇魯神話辭典的封面是空字串，書庫頁把它們顯示成沒有封面；極限返航與全知讀者視角03 存的是舊版本參數的封面網址。

重新提取時，合併程式要判斷提取到的每一本書對應 storage 裡的哪一筆，依序比對三個鍵：`id`、書城書號（`platformBookId`）、書名加封面網址。`id` 由提取程式依序嘗試三種來源產生：閱讀連結裡的書號（`reader-10371090`）、封面網址裡的檔名（`cover-f710gcf`）、書名（`title-卡片盒筆記`），取第一個拿得到的。從 `id` 的前綴看，2026-03 那一次提取沒有取到閱讀連結裡的書號（同一時期的修正紀錄寫著，書櫃頁剛渲染時每一本的閱讀連結都是同一個佔位網址），72 筆連封面網址都沒有，提取程式改用書名產生 `id`。這次三種來源都讀得到，`id` 變成 `reader-…`，於是：

- **`id` 對不上**：舊的是 `title-…` 或 `cover-…`，新的是 `reader-…`。
- **書城書號對不上**：Readmoo 的書目沒有這個欄位。
- **書名加封面對不上**：舊紀錄的封面是空字串，或封面網址的版本參數（`?v=`）變了。

識別碼由執行當下拿得到的來源推導、沒有固定成一個值時，來源拿不拿得到一變，同一本書的識別碼就換了；identifier 由各方各自推導而分歧的通則見 [#93 URL slug 必須顯式定義為 fact：跨工具 identifier 用單一定義源](/report/url-slug-must-be-explicit-fact/)，這次的分歧發生在同一支程式的兩次執行之間。

這次提取之前，書名識別碼的比對修法已經合進建置：合併程式在三個鍵都沒對上時，拿提取結果裡的書名識別碼（`identifiers.titleBased`，提取程式每次都會產生）去對 `id` 以 `title-` 開頭的舊紀錄。以書名為 `id` 的舊紀錄，除了十月堂舊書事１與克蘇魯神話辭典，都因此對上，占 92 筆更新的大部分。排查的人用忽略空白與標點的書名，在書庫裡找沒對上的 4 筆的同名書，結果分成三種：

| 舊紀錄的 `id`          | 書名           | 書庫裡同名的書    | 沒對上的原因                                                                                               |
| ---------------------- | -------------- | ----------------- | ---------------------------------------------------------------------------------------------------------- |
| `cover-f710gcf`        | 極限返航       | `reader-10371090` | `id` 取自封面，書名識別碼的比對只收 `title-` 開頭的紀錄；封面網址的版本參數也變了                          |
| `cover-plmltdi`        | 全知讀者視角03 | `reader-16201836` | `id` 取自封面，書名識別碼的比對只收 `title-` 開頭的紀錄；封面網址的版本參數也變了                          |
| `title-十月堂舊書事`   | 十月堂舊書事１ | `reader-17817413` | 產生書名識別碼時只留下漢字與半形英數，全形數字也被去掉，「十月堂舊書事１」與「十月堂舊書事２」的識別碼相同 |
| `title-克蘇魯神話辭典` | 克蘇魯神話辭典 | 沒有              | 這本書已經不在書櫃上（封存或歸還），保留它是對的                                                           |

同名書找得到的三筆是重複；找不到同名書的克蘇魯神話辭典在這次提取的書裡沒有對應，是不在來源上的使用者資料。

撞號的那一筆最不容易看出來。合併程式的索引一個識別碼只記一筆，記的是「十月堂舊書事２」的舊紀錄；合併程式處理２時對上這筆紀錄，處理１時找不到還沒被認領的紀錄，把１當成新書新增，１自己的舊紀錄留下來成了 `notOnPage`。

封面識別碼與撞號的修法改了索引與認領：合併程式的索引同時收 `id` 以 `cover-` 開頭的舊紀錄，合併程式比對時拿提取結果的封面識別碼（`identifiers.coverId`）去對；同一個舊識別碼底下有幾筆紀錄時，合併程式跳過這次已經被認領的，優先選書名完全相同的那一筆。這兩處各補一個測試，用的就是上表的實際資料，把修法拿掉時這兩個測試失敗；另補一個測試，確認克蘇魯神話辭典照樣保留為 `notOnPage`。

產生書名識別碼的演算法本身（只留下漢字與半形英數）這次沒有改：改了之後，所有以書名為 `id` 的舊紀錄都會換一個識別碼，比這次的撞號影響更大。

## 修好程式之後，舊程式寫下的資料

修好的程式只影響之後的寫入。這次舊程式已經寫下的資料，依處理方式分成下面幾種：

- **讀取端可以推導的**：96 筆舊紀錄都沒有 `readingStatus` 欄位（閱讀狀態欄位加入之前寫下的）。書庫頁顯示時照這個擴充功能書目 schema 裡既有的推導規則由進度推導（100% 讀完、大於 0 閱讀中、0 未讀），不寫回 storage；下一次提取對上這些紀錄時，合併程式會寫入正式的值。
- **下一次操作補不上、只能清掉的**：寫錯 key 的 `[object Object]_books` 存著完整的 1068 本，書庫頁不讀它；修正之後的重新提取已經把同一批 1068 本寫進正確的 key，所以它是一份多餘的副本，只佔空間。重新提取時被新增成重複的 3 筆（極限返航、全知讀者視角03、十月堂舊書事１的新紀錄）各有一筆對應的舊紀錄；下一次提取時，合併程式會用 `reader-…` 的 `id` 對上那 3 筆新紀錄，3 筆舊紀錄永遠是 `notOnPage`，修好比對規則也不會把它們合併。
- **保留的**：克蘇魯神話辭典不在書櫃上，它是使用者書庫的一部分，不是殘留。

寫錯 key 的 `[object Object]_books` 與 3 筆重複的舊紀錄，是在使用者確認之後，由使用者在 service worker 的 Console 跑一段會寫入 storage 的程式清掉的。這段程式先把 3 筆舊紀錄上使用者加過的標籤與手動設定的狀態併到同名的新紀錄，再刪掉這 3 筆舊紀錄，因為刪掉之後標籤與狀態就讀不到了；`[object Object]_books` 裡的 1068 本已經全部重新提取進正確的 key，這段程式把整個 key 刪掉。結尾印出刪了幾筆、剩下幾筆（刪除 3 筆，剩下 1069 本，也就是書櫃上的 1068 本加上克蘇魯神話辭典）。

## 判斷標準：本數對不上的位置、寫錯的 key、跳過中間層的測試、舊識別碼與殘留資料

- **本數第一次對不上的是哪兩段之間，缺陷就在前一段的輸出或後一段的輸入**：這需要每一段都有讀得到的本數。寫入那一段的 log 只印本數、不印位置時，「本數對、位置錯」看不出來；印出組出來的 key，`[object Object]` 這類字串一眼就看得到。有已知理由的差額（封存、借出）是口徑不同，扣除規則對不上實際字樣而安靜算成 0 時，口徑本身就錯了。只看本數看不出欄位變形，要變形的那個欄位另外計數。
- **寫入端的本數正確、storage 裡讀取端那個 key 底下沒有這批資料時**，看寫入那一行印出的 key：跟讀取端讀的 key 不同，資料寫進了讀取端不讀的位置。組 key 的欄位值是物件時，上游可能有一層佔用了這個欄位名（另一種可能是產生端本身送出了物件）；某一個來源（這次是某一個書城）的資料寫入成功、畫面上永遠是空的時，其中一種成因是同一個識別值在兩層用了不同的寫法。印出的 key 跟讀取端的相同而資料不在時，成因在寫入之後：寫入失敗、被別的程式用舊副本蓋回去、讀的是另一個儲存區或另一個擴充功能實例（未封裝的開發版與商店版的 storage 互不相通）。storage 裡讀取端那個 key 的本數正確、只有畫面不對時，資料的位置是對的，成因在讀取端何時重新讀取 storage，這篇沒有處理。
- **使用端（事件處理器這類拿資料做事的一方）的測試全部通過而實機失敗時**，其中一種成因是測試的事件沒有經過中間層：只有照中間層實際交出的欄位、型別與值組的事件，或經過中間層的測試，才會執行到中間層改寫資料的那一步。分辨方法是在使用端的入口印出實際收到的事件（這次由使用者在 service worker 的 Console 篩出來貼回），跟測試送出的事件逐欄比對；同型別的值被換掉時（字串換成另一個字串），只比形狀分不出來，要比到值。
- **重新提取之後本數比來源多、多出的那幾筆沒有新欄位時**，先在新提取的書裡找它的對應（同名、同書號）。找得到的，是舊紀錄的識別碼對不上而新增的重複：識別碼由幾種來源依序產生時，舊版程式可能取了較後面的來源（書名、封面），合併程式只拿一種來源的識別碼去對時，取了其他來源的舊紀錄對不上。找不到的，是不在來源上的使用者資料，歸下一項的保留。由書名產生的識別碼會撞號，這次的撞號用完整書名分得開；完整書名也相同時，要靠作者、出版者這類欄位。
- **程式修好之後的殘留資料各自處在不同狀態**：讀取端推導得出的欄位，留在 storage 不影響顯示；下一次操作會補上的，那次寫入之後就是正確值；不在來源上而屬於使用者的資料，刪掉就無法復原，所以保留。寫錯位置的那一份，只有同一批資料已經重新寫進正確位置時才是多餘的副本，沒有重寫時它是唯一的一份，要先搬回正確位置。重複的舊紀錄上可能有使用者加過的標籤與狀態，先併到對應的新紀錄再清；清除由資料的擁有者確認之後才做。
