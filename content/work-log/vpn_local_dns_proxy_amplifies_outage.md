## 情境的形狀

症狀組合是這樣：

```text
git push                  → fatal: Could not resolve host: dev-tea.example.com
ping 8.8.8.8              → 通
curl https://<伺服器 IP>/  → 通
git push（幾分鐘後重試）    → 成功
```

用域名的操作一律失敗、用位址的操作一律成功，而且過一陣子自行恢復。這個組合把診斷推向「網路壞了又自己修好」，而網路層的證據從頭到尾都是通的。

射程是這樣的機器：開發機上裝著會接管 DNS 的常駐程式。mesh VPN 客戶端（Tailscale 的 MagicDNS）、公司 VPN 的 split DNS 客戶端（把內網域名導向公司內部 DNS、其餘照常走外部的那種設定）、本機跑的 `dnsmasq` 或廣告過濾（Pi-hole / AdGuard Home）、Linux 上的 `systemd-resolved` 都算。它們的共同點是在本機開一個 resolver，並把自己設成系統的解析入口。

本文的指令與輸出在 macOS 實機驗證過。Linux 與 Windows 側的對應動作依各自工具的文件寫出、標在對應段落，未經實機驗證。

## 症狀落在解析層，可達性層已經被排除

連線失敗有三層症狀，各自指向不同的方向：解析失敗（名字還沒變成位址）、連線逾時（封包送不到）、連線被拒（送到了、對方拒絕）。三者的分層判別見 [連線逾時 vs 連線被拒](/linux/dotfile/knowledge-cards/connection-refused-vs-timeout/#判讀訊號)。

`Could not resolve host` 是最前面那一層，封包還沒送出去。而 `ping 8.8.8.8` 與直連伺服器 IP 都通，代表鏈路、路由、對外可達性都成立。這兩個證據合起來把範圍收斂到單一問題：**這台機器把名字換成位址的那條路徑，出了什麼事**。

## macOS 的解析設定權威在 scutil，不在 /etc/resolv.conf

Linux 上的第一個檢查是 `/etc/resolv.conf` 裡有沒有可用的 `nameserver`。這個動作搬到 macOS 會讀到一份不決定任何事的檔案，該檔自己就印著這件事：

```text
$ cat /etc/resolv.conf
#
# macOS Notice
#
# This file is not consulted for DNS hostname resolution, address
# resolution, or the DNS query routing mechanism used by most
# processes on this system.
#
# To view the DNS configuration used by this system, use:
#   scutil --dns
#
# ...
#
# This file is automatically generated.
#
nameserver 168.95.192.1
nameserver 168.95.1.1
```

它仍然存在、仍然有內容、`cat` 出來看起來完全正常，所以讀到「有 nameserver」就宣告 DNS 設定沒問題，是在一份不決定路由的檔案上結案。它的內容通常鏡射系統設定，但決定 `git` 與 `curl` 走哪條路的是 `scutil --dns` 那份：

```text
$ scutil --dns
DNS configuration

resolver #1
  nameserver[0] : 168.95.192.1
  nameserver[1] : 168.95.1.1
  if_index : 11 (en0)
```

實際輸出比這長得多，後面還跟著數個處理 `local` 與 mDNS 的 resolver 區塊。上面這份是 VPN 停用後的狀態，第一順位是 Wi-Fi 從 DHCP 拿到的電信業者 DNS。事故當下的同一個指令，第一順位是 `100.100.100.100`，也就是 Tailscale 跑在本機的 resolver 位址。

三件事要一起從這份輸出讀出來，它們決定了後面整條推論成不成立：

- **第一順位是誰**。`100.100.100.100`（Tailscale）、`127.0.0.53`（systemd-resolved）、`127.0.0.1` 這類本機或保留位址出現在這裡，就代表有一個本機 proxy 站在路徑上。
- **有沒有獨立於它的第二條路**。`resolver #1` 底下多一行 `nameserver[1]` 未必是退路——接管 DNS 的元件常常整組替換這份清單，兩行可能是同一個 proxy 的 v4 與 v6 位址。要看的是第二順位屬不屬於另一個元件。即使是，`man 5 resolver` 描述的順序嘗試是**逾時才換下一台**，所以退路的表現是每次查詢都先卡掉一個逾時、全機變慢，而不是透明接手。
- **失敗的名字歸哪個 resolver 管**。帶 `domain :` 的 resolver 只服務該網域。內網域名解析不出來時，要看的是那條 scoped resolver，而不是 `resolver #1`——公司 VPN 的 split DNS 客戶端多半只加 scoped resolver、不動預設那條。

Linux 上的對應動作是看 `/etc/resolv.conf` 指向哪裡與 `resolvectl status` 的 `resolv.conf mode`：值是 `stub` 就代表查詢先進 `systemd-resolved` 的本機 stub，各介面實際用的上游列在下面的 Link 區塊。Windows 上是 `Get-DnsClientServerAddress`。WSL2 是雙層——WSL 內的 `/etc/resolv.conf` 指向 Windows 虛擬網卡，真正的 proxy 在 Windows 那一側，處置也要在那一側做。這是預設形態，新版的 DNS tunneling 與 mirrored 網路模式下 nameserver 不長這樣，先確認自己在哪一種。

## Tailscale 的 resolver 進入了每一次名字查詢的路徑

`100.100.100.100` 在事故當下的設定裡是一個全量 resolver：tailnet（該帳號底下所有裝置組成的那張私網）內部的名字自己回答，其餘的**轉發**給上游 DNS。上游預設是這台機器原本用的那組，tailnet 若設了全域 nameserver 就改送給它。這個設計讓 `ssh my-vm` 這種寫法能成立（MagicDNS 的正常用途見 [Tailscale 深入：tailnet、MagicDNS、直連與 DERP 中繼](/linux/tools/remote/tailscale-tailnet-and-relay/)），代價是它處理的遠不只 tailnet 主機名，`github.com` 這種跟 tailnet 毫無關係的域名同樣要經過它。

「全量」是當次設定的結果，不是這個產品的性質。同一個 Tailscale 也可以只接管 tailnet 網域、其餘照走系統上游，那種設定下它根本不在 `github.com` 的路徑上。前一節那三個檢查就是在確認「它這次確實在必經路徑上」。

於是可用性的算式變了。原本「解析得出來」需要的是：Wi-Fi 通、上游 DNS 活著。插進一個本機 proxy 之後，多一個條件——這個 proxy 此刻運作正常。三個條件串聯，整體可用性是三者的下限。

放大效應就從這裡來。一次 Wi-Fi 瞬斷對純網路操作只是幾個封包重傳（事故當下 ping 對外仍然通，延遲從 10ms 級跳到 363ms），對這條解析路徑卻可能是整段中斷，而中斷期間，**這台機器所有沒被快取住的域名都解析不出來**。一個局部、短暫、原本只造成抖動的事件，被路徑上的位置放大成全機範圍的功能中斷。

至於這個 proxy 為什麼會跟著抖，當下沒有取得它的 log，所以機制未經驗證。手上的證據（對外 ping 通、延遲跳動、間歇恢復）至少支持兩種解釋：它與協調伺服器的連線在丟包下不穩、或者它轉發給上游的查詢在高延遲下逾時，而系統原本的兩台 nameserver 冗餘被它換成了單一入口、失去重試的餘裕。分流測試能證明斷點落在它身上，證明不了它為什麼斷——兩者要分開講。

## 分流測試：對同一個名字，繞過它再問一次

定位方法是把「解析壞了」拆成「路徑上哪一段壞了」，做法是繞過可疑的那一段、直接問下一段。兩個前提決定這個測試有沒有分辨力，先講清楚：

**測試的名字要用當下失敗的那一個。** 內網域名、tailnet 主機名這類只有特定 resolver 答得出來的名字，換一台 resolver 問必然拿不到答案——那是設計如此，不是故障。反過來，拿 `github.com` 去測而故障只發生在內網域名，測試會回報一切正常，因為壞掉的那條路根本沒被走到。

**第二條要問的是那個 proxy 自己的上游。** 轉發型 resolver 把查詢送給上游，上游死掉會表現成它自己死掉。問一台無關的公共 resolver 只能證明「不是全網不可達」，分不出「proxy 壞了」與「proxy 的上游壞了」，而這兩者的處置相反。上游位址從 `tailscale dns status`、或第一順位被接管之前的 DHCP 設定取得。

診斷時不要加 `+short`。實測 `+short` 對 NXDOMAIN 與 SERVFAIL 都印空字串、都 exit 0，兩者的下一步卻完全不同：

```bash
dig +time=2 +tries=1 @<proxy 位址>     <失敗的那個名字>
dig +time=2 +tries=1 @<proxy 的上游>   <失敗的那個名字>
```

要讀的是 `;; ->>HEADER<<-` 那行的 `status:`，配著下一行的 `ANSWER:` 計數看：

- **`NOERROR` 且 `ANSWER` 大於 0**：答出來了。
- **`NOERROR` 但 `ANSWER: 0`**（NODATA）：名字存在、這個型別沒有記錄，常見於只有 AAAA 或 CNAME 鏈的名字。「查不到」最常長這個樣子而非 NXDOMAIN，而 `+short` 對它一樣印空。
- **`NXDOMAIN`**：這個名字不存在。
- **`SERVFAIL`**：這台 resolver 試了但失敗，多半往它的上游查；DNSSEC 驗證失敗也回這個，那條線跟上游無關。
- **`REFUSED`**：它拒絕服務這個 client，多半是 ACL。
- **完全沒回應**：`connection timed out`。

兩條的組合這樣讀：

| proxy 的回答              | 它的上游的回答  | 判讀                                                                          |
| ------------------------- | --------------- | ----------------------------------------------------------------------------- |
| 有位址                    | 有位址          | 解析路徑正常，往程式端查（見下一節的 `dig` 陷阱）                             |
| 逾時 / SERVFAIL / REFUSED | 有位址          | 斷點在 proxy。上游有回應、封包送得出去                                        |
| 逾時 / SERVFAIL           | 逾時 / SERVFAIL | 上游或可達性層，往 [機器連不到或起不來](/linux/debug/machine-unreachable/) 走 |
| 有位址                    | 逾時 / NXDOMAIN | proxy 健康。這個名字本來就只有它答得出來                                      |
| NXDOMAIN                  | 有位址          | proxy 主動擋掉這個名字，是設定而非故障                                        |
| NXDOMAIN                  | NXDOMAIN        | 名字不存在，跟路徑無關                                                        |

「proxy 答得出來、上游答不出來」那一列容易被誤讀成故障，它是 split DNS 與 MagicDNS 正常運作的樣子——內網域名只有公司 DNS 答得出來、tailnet 主機名只有 `100.100.100.100` 答得出來。同一列也涵蓋另一種情形：對外 53 埠被封（旅館、公共 Wi-Fi、企業內網），而 proxy 走 DoH 或走 VPN 隧道轉發、不受影響。

「兩條都失敗」那一列要先排除封鎖。部分網路會封鎖或劫持對外的 53 埠，讓「直接問任意上游」在該網路上本來就走不通，兩條 `dig` 一起失敗而 proxy 無辜。判別方式是換一個網路（手機熱點）再跑同一組指令。

「proxy 回 NXDOMAIN、上游回得出位址」那一列是廣告過濾與企業 DNS 封鎖政策的正常樣子——Pi-hole 擋廣告網域就是回 NXDOMAIN。判成故障會讓人去修一個正在照設定運作的元件；真正該問的是這個名字該不該在阻擋清單上。

**兩邊都回位址、但位址不同**這個組合刻意沒有進表。公網名字經過 CDN 與 GeoDNS，本來就會依 resolver 所在位置回不同的節點，兩台 resolver 給出不同答案是常態、不構成任何訊號。只有在測**內網名字**時，位址不同才值得當 split-horizon 讀（同一個名字在內外網指向不同機器），而那時該檢查的是自己連的是哪一邊。

## 間歇性故障要問幾次才算數

單次成功排除不了問題，而該問幾次取決於故障有多間歇。結案要求的是「連續 n 次都成功」，而它在故障仍然存在時發生的機率是 `p^n`（`p` 是單次成功率）。要把這個誤判機率壓到 `α` 以下，取樣次數是：

```text
n ≥ ln α / ln p        取整往上
```

事故當下觀測到的 `p` 大約三分之一（連問三次中一次，樣本只有三次、這是觀測值而非推導值）。代進去，`α` 取 0.5% 時 `n` 是 5。但這個數字對輕度間歇完全不夠——`p` 是 0.9 時，同樣的 `α` 要問 29 次（`0.9^28` 是 5.2%、仍高於門檻），用五次的話有將近六成機率誤判成已經修好。取樣次數要跟著觀測到的成功率重算，不是一個固定值。

公式吃一個前提：各次取樣互相獨立。間歇性故障通常是時間相關的（壞一陣、好一陣），背靠背連跑五次可能整批都落在同一個好的區間裡，那批樣本的獨立性最差。取樣要拉開間隔，跨過故障起伏的時間尺度：

```bash
for i in $(seq 5); do
  dig +short +time=2 +tries=1 @<proxy 位址> <失敗的那個名字> | rg -c '^[0-9]+\.'
  sleep 20
done
```

計次要過濾出位址行。`+short` 對只有 CNAME 的回答會印出一行網域名（實測 `dig +short ipv6.google.com A` 印 `ipv6.l.google.com.`），直接數行數會把它算成成功。另外要知道這樣量到的失敗率會比程式看到的低：`+tries=1` 關掉了重試，而系統的 resolver 會自己重試幾次。

## dig 問到的答案，不等於程式問到的答案

`dig` 走的是它自己的路徑。man page 寫明：未指定 `@` 時它讀 `/etc/resolv.conf` 取伺服器位址，然後直接對該位址發送查詢。而 `git`、`curl`、`ping` 走的是 `getaddrinfo`，也就是系統的解析函式，在 macOS 上經過 `scutil` 那份設定與 `mDNSResponder` 的快取。

分岔有兩個來源，要分開查。一個是**問了不同的伺服器**：`/etc/resolv.conf` 由系統生成、通常鏡射 `scutil` 的第一順位，但接管 DNS 的元件寫入這兩處的時機未必同步，兩邊不一致時 `dig` 跟程式打的就是不同的 resolver。當下比對一次就知道，`cat /etc/resolv.conf` 的 `nameserver` 跟 `scutil --dns` 的 `resolver #1` 對不對得上。另一個是**繞過了中間那幾層**：即使問的是同一台，`dig` 仍然不經過 `mDNSResponder` 的快取（包含把失敗結果記下來的負快取）、不讀 `/etc/hosts`、也不套用 `scutil` 那份多 resolver 的排序與網域比對。

實務後果是：`dig` 拿到位址、`git push` 仍然回 `Could not resolve host`，這個組合完全可能同時成立，而它不代表 `git` 有問題。

要重現程式實際看到的結果，改用走系統解析路徑的工具。

```bash
dscacheutil -q host -a name github.com   # macOS
getent hosts github.com                  # Linux
```

有位址回來就代表系統解析路徑通了（`dscacheutil` 印在 `ip_address` 欄，`getent` 直接印位址與名字）。這條檢查跟 `dig` 互補。`dig` 定位是哪個 resolver 壞了，`dscacheutil` / `getent` 確認程式那條路徑會不會通。

## 處置與它的代價

處置的通用形式是把本機 proxy 從路徑上移開，讓系統回到原本的上游 resolver。做法隨元件而異：Tailscale 交還 DNS 控制權、`systemd-resolved` 停掉服務並還原 `/etc/resolv.conf` 的符號連結、本機 `dnsmasq` 或廣告過濾則是停掉該服務後把介面的 DNS 設定改回 DHCP 取得的位址。

```bash
tailscale set --accept-dns=false   # Tailscale：交還系統預設 resolver
```

**這個動作的前提是分流測試指向 proxy 本身。** 上游已經死掉時移開 proxy 只會讓系統回落到那個死掉的上游，解析照樣壞、還一併失去該元件提供的能力，比動作前更糟。判讀表裡兩條 `dig` 都失敗的那一列就是這種情形，那裡的下一步是換上游或往可達性層查。

代價隨元件而異，而且差距很大。Tailscale 是 tailnet 主機名失效，`ssh my-vm` 要改回 tailnet 位址；廣告過濾是規則一併停用；**公司 VPN 的 split DNS 客戶端則是整組內網域名解析不出來**——內網名字本來就只有公司 DNS 答得出來，把本機 resolver 移開等於把那條路拆掉。內網域名故障時該診斷的是那條 scoped resolver，而不是把整個解析入口換掉。

重啟該元件是並列的另一條路，它保留原有能力、代價是恢復時間取決於它自己重連的速度，而且根因沒有被排除、同樣的抖動會再發生。臨時要趕工就移開它，想留著能力就重啟並記下發生頻率。

**沒有權限動它的情況要另外算。** 受 MDM 管控的 VPN 客戶端與企業 DNS 過濾 agent 停不掉、也改不動介面設定，而這兩類正好都在本文射程內。此時剩下的動作是繞過與升級：用位址直連、把急用的名字暫時寫進 `/etc/hosts`、重連該客戶端，然後帶著兩條 `dig` 的輸出往 IT 報修。分流測試在這裡的產物是可交付的證據——它把「網路怪怪的」換成「這台 resolver 對這個名字回 SERVFAIL，同一時間它的上游回得出來」。

任一種處置之後，再讀一次權威設定（macOS 的 `scutil --dns`），確認第一順位換成了誰。同一個指令同時是處置前的診斷與處置後的驗收。

## 判準

**一個元件被裝在某項功能的必經路徑上時，它的可用性就是那項功能的可用性上限。** 診斷據此展開：症狀是「整個功能壞了」，要問的是「路徑上哪一段壞了」，方法是繞過可疑的那一段、對同一個問題直接問下一段。

「必經」要先確認，它是四個條件的合取，缺一個這條上限就不成立：那個元件是唯一的入口（沒有次順位可退）、它沒有網域限定（不是只管某個網域的 scoped resolver）、查詢沒有被快取接走、以及出問題的程式確實走系統的解析函式（瀏覽器的 DoH、直讀設定檔的靜態連結程式、容器內的行程都不走）。前兩條在讀權威設定那節有對應的檢查（是不是唯一一條、有沒有網域限定）。後兩條要靠比對：`dig @<proxy>` 直接對伺服器發問、完全不碰系統快取，而 `dscacheutil` / `getent` 走的是程式那條含快取的路。同一個名字兩邊問一次，結果一致就代表快取沒有插手、而且那個程式確實走系統解析函式；結果分岔就是這兩條其中之一沒有成立。

配套的第二條：**間歇性故障用重複取樣判定，取樣次數跟著觀測到的成功率算。** 成功率越接近一，要問的次數越多，而那正是最容易誤判成「已經好了」的情形。

## 這條判準的邊界

同一個形狀出現在各種接管 DNS 的元件上：公司 VPN 的 split DNS 客戶端、Linux 的 `systemd-resolved`（`127.0.0.53`）、本機跑的 `dnsmasq` 或廣告過濾、企業裝的 DNS 過濾 agent。判別方式一致，先讀權威設定，確認第一順位是本機位址、而且滿足上面那四個條件。

第一順位落在**另一台機器**時，是同一個形狀的變體，單點仍然存在、只是它不在本機。架在路由器或 NAS 上的 Pi-hole、公司內網 DNS 都算，WSL2 也是——WSL 內看到的 `nameserver 172.x.x.1` 指向 Windows 虛擬網卡，真正接管 DNS 的元件在 Windows 那一側。分流測試同樣適用，差別在定位到它之後，處置要去那台機器上做；在 WSL2 內手改 `/etc/resolv.conf` 會在重啟後被自動生成蓋掉。

容器內的解析屬於另一個範圍。掛在自訂網路的 Docker 容器，其內嵌 resolver（`127.0.0.11`）只出現在容器自己的 `resolv.conf` 裡，宿主的 `scutil --dns` 看不到它，症狀也限縮在容器內。要查的是容器裡的 `cat /etc/resolv.conf` 與容器執行環境自己的 DNS 設定，本文的宿主層檢查在這裡全部會回報正常。

`/etc/hosts` 的錯誤條目落在整張判讀表之外。它讓名字解析成一個錯的位址，症狀是連得到卻連錯，後續表現為逾時或被拒。之所以要在這裡列出，是因為 `dig` 對它沒有偵測力：`dig` 直接對 DNS 伺服器發查詢、不讀 `hosts`，兩條 `dig` 都會回來正確的位址。要看見 `hosts` 的影響，用走系統解析路徑的檢查（`dscacheutil` / `getent`），或直接讀 `cat /etc/hosts`。

**判準往 DNS 之外泛化時，吃兩個前提**：下一段要能從發問端直接定址，而且要能用相同語意回答同一個問題。HTTP proxy 滿足（清掉 `http_proxy` 直打 origin）、連線池滿足（用新 client 繞過 pgbouncer 直連 DB）。service mesh 的 sidecar 兩個都不滿足——出向流量在同一個 network namespace 被攔截，發問端沒有「繞過去問下一段」這個動作可做。DNS 之所以是個好例子，正是因為任一台遞迴 resolver 都答得出公網名字，這兩個前提罕見地同時成立；而內網域名連 DNS 自己都不滿足第二條，這也是前面要求「用失敗的那個名字測」的理由。

事故本身自行恢復，這篇留下的因此是分流方法。故障自行恢復時，能重複使用的產物是「下次幾條指令內定位到哪一段」這個能力。
