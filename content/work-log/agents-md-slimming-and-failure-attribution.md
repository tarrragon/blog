這篇來自 2026-10-24 到 11-22 對一個教學部落格 repo 的規則檔維護。Claude Code 與 Codex 在這個 repo 共用同一組規則：Codex 讀 `AGENTS.md`，Claude Code 經由 `CLAUDE.md` 的 `@` 匯入讀同一份。維護者（這個 repo 的作者）指揮 agent 縮小入口檔（`AGENTS.md` 本身）、把規則拆到 `docs/rules/` 的分冊，以及改寫規則文字。

這篇整理規則檔維護的經過與判斷依據：工具的讀取上限與每個 session 的載入量、入口檔拆成分冊的做法、拆完之後再次逼近上限的成因、分冊按需載入與讀取檢查、改寫規則文字之前的失敗歸因、修改規則時修法擴張的案例，以及這次維護還沒驗證的部分。文章最後整理規則檔該從大小、載入、規則文字或動筆前對齊的哪一處修的判斷條件。內容適用於由工具在啟動時載入、有大小限制的 agent 規則檔。歸因的完整量法與限制在 [改規則之前先把使用者的糾正逐則歸因：依讀起來模糊挑出來改的規則，多半不是出過事的那幾條](/report/attribute-recorded-corrections-before-rewriting-rules/)，常駐內容與參考細節的分法在 [規則文件的精簡：用 Progressive Disclosure 分出常駐內容與參考細節](/record/non-code-refactoring/)。

## 規則檔的大小限制：工具的讀取上限與每個 session 的載入量

規則檔的大小受兩種限制影響，兩者造成的後果不同。下文的 KB 指 1,000 bytes，KiB 指 1,024 bytes。

**讀取上限**是工具讀進來的最大長度。Codex 用 `project_doc_max_bytes` 控制，預設 32 KiB（32,768 bytes）；[官方文件](https://learn.chatgpt.com/docs/agent-configuration/agents-md)寫明合併後的指令（全域設定與 repo 各層目錄的指令檔接在一起）到達這個大小時，Codex 就停止加入檔案。排在上限之後的規則進不了 agent 的 context，寫得再清楚也不會影響它的行為。

**載入量**是每個 session 一開始就佔掉的 context。Claude Code 在啟動時載入工作目錄往上各層的 `CLAUDE.md`，`@` 匯入的檔案也一起展開進 context（[官方文件](https://code.claude.com/docs/en/memory)）。這份文件建議每個 `CLAUDE.md` 控制在 200 行以內，理由是檔案越長越佔 context，agent 遵守規則的程度也越低。

## 入口拆成分冊的做法與沒有改變的載入量

2026-10-25 的審查者（另派一個 agent 讀規則檔、回報缺陷）查到 `AGENTS.md` 有 110,226 bytes，超過 Codex 預設上限的三倍，Codex 大約讀到句子規則那一節之前就停止加入內容。

維護者把它拆成一個 11 KB 的入口與八份分冊。入口收錄優先序、提交與推送這類每個 session 都可能用到的規則，以及一張依要改的檔案路徑分流的路由表，當時的表沒有依動作分流的項目；寫作、句子、審查這類規則搬到 `docs/rules/`。這次只搬內容，各節原文不改。

拆分處理了 Codex 的讀取上限，Claude Code 的載入量維持原樣：`CLAUDE.md` 用 `@` 匯入入口與全部分冊，每個 session 啟動時讀到的內容跟拆分之前相同。

## 入口檔逼近讀取上限的經過與成因

入口檔拆完之後的四天內從 11 KB 長到 31 KB，之後停在 32 KB 附近：

| 時間               | `AGENTS.md` 大小 | 這段期間加進入口的內容                                   |
| ------------------ | ---------------- | -------------------------------------------------------- |
| 10-25 拆分後       | 11,322 bytes     | 優先序、提交與推送、路由表                               |
| 10-25 多輪審查修完 | 21,909 bytes     | 依改動大小決定做哪些檢查的規則、讀分冊的方式、提交的處置 |
| 10-27              | 25,610 bytes     | 搬移資料夾之前要取得同意的步驟                           |
| 10-29              | 31,261 bytes     | 破壞性指令的完整規則                                     |
| 11-21              | 32,142 bytes     | 提交生成檔時的處置                                       |

增加的 20,820 bytes 有 64% 來自兩節：提交與推送那一節從 2.2 KB 長到 10.3 KB，破壞性指令那一節新增 5.3 KB。這兩節管的動作（提交、推送、刪除檔案）每個 session 都可能做，做錯的代價也高。路由表依檔案路徑分流，這類依動作觸發的規則對不到任何分冊，維護者就把完整的處置寫進入口。入口也沒有大小檢查，這份檔案的長度只受寫規則當下的判斷限制。

## 分冊按需載入與讀取檢查

2026-11-22 的入口檔離 Codex 的上限只剩約 600 bytes，Claude Code 每個 session 啟動時載入約 253 KB 的規則。這次的改動同時處理讀取上限與載入量：

- **把入口縮成路由與每個 session 都用得到的規則**：agent 把提交規則與破壞性指令的細節搬到分冊，在入口保留要點與連結。`AGENTS.md` 從 32.1 KB 降到 12.2 KB，`CLAUDE.md` 從 15.2 KB 降到 2.3 KB，Claude Code 啟動時的載入量從約 253 KB 降到約 14.5 KB。
- **依路徑與動作讀對應的分冊**：入口的路由表分成路徑與動作兩部分，補上了拆分時缺的動作分流；`bin/rule-route` 依路徑列出要讀的分冊。改 `content/` 的文章時，入口加上對應分冊約 171 KB，實際省下的量依這次改的路徑而定。
- **動手之前檢查分冊讀過了沒**：Claude Code 的 PreToolUse hook（工具執行之前呼叫的腳本）在寫檔、提交、推送與 `ssh` 之前查這個 agent 的對話紀錄。對應的分冊在最後一次 context 壓縮（對話太長時工具把舊內容換成摘要）之後沒有整份讀過，hook 就拒絕這次工具呼叫。
- **提交時檢查檔案大小**：pre-commit 在 `AGENTS.md` 達到 14 KiB、任一份分冊達到 60 KiB 時擋下提交。14 KiB 是這個 repo 自訂的入口預算，沒有另外推導；60 KiB 的依據是分冊超過這個長度時，Read 回傳的內容會被截斷，hook 分辨不出 agent 是否讀完。入口變大的那一次提交當場失敗，維護者在那時決定內容該放哪一份分冊。

讀取檢查的依據來自一組探針（派低階模型獨立作答的理解測試）。維護者派 15 份低階模型作答封閉案例題（每題一個具體情境，預期答案事先寫好），只給入口、沒有逼它們讀分冊時，有 12 到 13 份不讀分冊就作答。這個結果顯示少了檢查時模型多半不讀分冊；有檢查時 agent 是否照分冊做事，這組探針量不到。

這組 114 題也用來驗收改動。規則改動前模型全部答對，改動後也全部答對，所以這組題目只驗得出退步，維護者從它看不出規則是否讓 agent 少犯錯。

## 改寫規則文字之前的失敗歸因

入口瘦身之後，下一步原本是逐節改寫讀起來模糊的規則。挑選的依據是**模糊度普查**：每一節派三份低階模型獨立閱讀，回報這一節的觸發條件與通過標準是否查得到。兩批改寫改到 7 節，審查用的 agent 耗掉至少 500 萬 [Token](/llm/knowledge-cards/token/)。

重新檢視這個做法時，歸因的對象換成 agent 實際被糾正的紀錄：17 個 session 裡由維護者親自輸入的 225 則訊息。評分模型從中篩出 39 則糾正，其中 12 則是維護者改變想法或追加新想法，其餘 27 則算 agent 的失敗。評分模型再逐則對照當時的規則版本與 agent 載入過的內容，判斷成因：

| 成因       | 判定                                       | 則數 | 合併同一事件後 |
| ---------- | ------------------------------------------ | ---- | -------------- |
| 需求沒對齊 | 沒有規則管，而這是這個任務特有的方向或取材 | 9    | 5              |
| 規則缺漏   | 沒有規則管，而同樣的缺陷在別的任務也會發生 | 6    | 5              |
| 規則模糊   | 規則在 context 裡，而它的文字容許這個產出  | 5    | 4              |
| 讀了沒做   | 規則在 context 裡也寫得清楚，產出仍然違反  | 4    | 2              |
| 沒讀到     | 有規則管，而那段規則不在 context 裡        | 2    | 1              |
| 未定       | 三位評分者各判一類                         | 1    | 併入規則模糊   |

合併同一事件指同一個判斷引發的連續糾正只算一次。依這個分類，需求沒對齊、讀了沒做與沒讀到合計 15 則，這些失敗的成因不在規則文字，改寫既有規則的措辭解決不了它們。

當時已有規則管的 11 則失敗（規則模糊、讀了沒做、沒讀到）裡，只有 1 則出在普查挑出的 7 節。從這份樣本判斷不了模糊度與失敗之間有沒有對應，普查的讀數本身也不穩定：文字完全沒動的 33 節，四次普查回報「觸發條件查不到」的數量從 19 到 36。

歸因之前先登記了停止線：規則模糊低於三分之一就不再逐節改寫。這次的比例是 19%（27 則裡的 5 則），95% 信賴區間是 8% 到 41%，所以判斷得出規則模糊不是最大的一類，判斷不出它一定低於三分之一。維護者依這條事先登記的線停止逐節改寫。

需求沒對齊的則數最多，合併同一事件之後跟規則缺漏同為 5 則。方向選錯的文章要等寫完才被糾正，修法是重寫，所以下一步處理這一類：新增文章或換角度改寫文章時，agent 動筆之前先寫出讀者、切入角度、起點與不寫什麼，由維護者確認之後才寫。

## 修改規則時的修法擴張：補一句提醒的案例

規則在修改的過程中也會變長。一個案例是寫作規則裡的倒裝條目：它要求把句尾的核心概念搬到句首，而核心概念是「一不一樣」這類正反問句時，搬過去要改成「是否」，例如把「判斷 X，看的是值一不一樣」寫成「值是否相同，是判斷 X 的依據」。這次改動的需求只有補上這一句提醒。

agent 照審查意見補了條件，又改了另一條規則的前導詞清單（前導詞是讓讀者知道接下來是問句的詞）。之後審查標為必修（照做會錯、必須修）的項目，都依賴前一次改過的句子。這個專案在照審查意見修之前有一道**設計稽核**：同一段被修過兩次以上、或必修多半依賴上一輪新寫的句子時，查同一條規則是否有多份完整寫法。這次兩個條件都成立，前導詞清單也確實寫在四個位置、成員不同。agent 停止照意見修，把改動收回成原本的一句，重新審查之後沒有必修。

同一天的下一批把前導詞清單收成一處，agent 替它訂了「會接問句的動詞」這個類別。審查標出的 4 則必修全部指向這個類別的邊界：「問的是」算不算、「比對」算不算、清單是封閉還是舉例。前導詞的判斷沒有照規則就判得出的答案，執行者要判斷讀者讀到問句之前，是否已經有一個詞讓他知道接下來是問句；agent 把答案寫成類別時，審查者就在類別的邊界找到新案例。維護者在這裡決定保留現行版本，類別的邊界留作已知缺口，沒有再補條件。

這兩批是同一天的兩次觀察。有些規則本來就需要分類，它們的邊界同樣會被審查標出必修，所以從這兩批只看得出修法擴張時值得停下來檢查，證明不了分類一定有缺陷。停下來之後的反省做法在 [規則的審查走到設計稽核的停點時，先反省寫法、再反省對規則的理解、最後才簡化：理解要對照使用者的原話與既有規則的住址，必修集中在分類的邊界可能是理解偏掉的訊號](/report/rule-nonconvergence-reflect-form-then-understanding/)，修法製造歧義的結構成因在 [規則檔的修法逐輪製造新歧義：程序寫成有測試的工具，共用的概念只定義一次](/report/rule-patches-breed-new-ambiguity/)。

## 這次維護還沒驗證的部分

規則檔變小與載入量下降是量得到的結果，agent 是否因此更遵守規則，目前沒有證據：

- **Codex 的實際流程沒有跑過**：按需讀分冊在 Claude Code 由 hook 檢查，Codex 沒有這道檢查，要靠 agent 自己照入口讀。
- **hook 只確認讀過**：它查得到分冊是否被讀，查不到 agent 是否照分冊做事。
- **入口大小檢查的長期效果**：這道檢查才剛上線，還看不出入口是否會以別的方式長回去。
- **淨 token 用量沒有量**：啟動載入減少，改文章時仍要讀約 171 KB，加上 [Prompt Cache](/llm/knowledge-cards/prompt-cache/)（供應商快取重複的前段輸入）的影響，總用量的變化還沒有量過。
- **動筆前對齊的效果還沒有結果**：這個做法在試行，累積 5 次對齊後由維護者決定留或撤。這類糾正本來就少，做法完全無效時，5 篇都沒有糾正的機率仍約 75% 到 83%，所以試行要記錄的內容是維護者在對齊時改了哪幾項。
- **歸因的資料範圍窄**：紀錄只有 20 天，27 則失敗有 9 則來自同一個 session，主題集中在音響與音樂文章。評分者是模型，兩位評分者判定成因的一致度 κ 是 0.71，不一致的 9 則交給第三位裁決。這份資料也只涵蓋維護者說出口的糾正。
- **沒有跟 Claude Code 內建的路徑範圍規則比較**：`.claude/rules/` 底下帶 `paths` frontmatter 的規則會依路徑載入，這個 repo 用的是自己的路由表加 hook。

## 判斷規則檔該從哪裡修：大小、載入、規則文字與動筆前對齊

規則檔要修的地方依成因分成幾種情形，各自的修法位置不同。下面的分類來自這一次的事件，修法的效果還沒有量過，其中的歸因要拿得到糾正紀錄，動筆前對齊要有人確認。幾種情形可能同時成立：大小排在最前，因為規則進不了 context 時，改寫它的文字沒有作用；其餘幾項這次沒有比較過優先序，歸因的結果才看得出哪一類失敗最多。

- **合併後的指令接近工具的讀取上限**：Codex 比對的是全域設定與各層目錄指令檔加總的大小，用 `wc -c AGENTS.md` 只量得到其中一份。到達 `project_doc_max_bytes` 之後的規則進不了 context，寫得再清楚也影響不了 agent。調高上限同樣讓這些規則進得來，代價是每個 session 的載入量跟著變大。
- **沒有超過上限，而每個 session 載入大量跟這次工作無關的規則**：代價是每個 session 的 context。Claude Code 的載入量要連使用者層級與組織層級的 `CLAUDE.md` 一起算，這些檔案同樣在啟動時載入。拆成分冊可以降低專案規則的載入量。這次的探針裡，沒有讀取檢查時多數作答的模型不讀分冊，省下 context 的同時也讀不到規則。
- **拆完之後入口持續變大**：依動作觸發的規則對不到依路徑分流的路由表，寫進入口最省事。入口沒有大小檢查時，它的長度只受寫規則當下的判斷限制，這個 repo 的入口在四天內從 11 KB 長到 31 KB。加上檢查之後，入口變大的提交會當場失敗。
- **agent 被糾正，而規則當時不在 context 裡**：新寫的文字同樣進不來，失敗的位置在載入的時機。工具的載入規則也可能造成這種情形：Claude Code 預設在 `AGENTS.md` 與 `CLAUDE.md` 並存時只讀 `CLAUDE.md`，除非 `CLAUDE.md` 匯入了 `AGENTS.md`（[官方文件](https://code.claude.com/docs/en/memory#agents-md)）。
- **agent 被糾正，而規則在 context 裡也寫得清楚**：再改文字的結果相同。能用程式判定的項目（提交前是否跑過 lint）由工具在動作當下檢查，才碰得到這類失敗；不能用程式判定的項目（文章的語氣）仍留在規則文字，靠審查發現。載入的規則太多也可能讓寫得清楚的規則沒被遵守，所以這一條可能跟載入量那一條同時成立。
- **agent 被糾正，而規則的文字容許這個產出**：這是改寫文字對得上成因的情形，範圍限於出過事的那幾條。
- **agent 被糾正，而沒有規則管這件事**：同樣的缺陷在別的任務也會發生時，這是規則缺漏，補一條規則對得上成因。缺陷來自這個任務特有的方向時，規則寫不成通則，失敗的位置在動筆之前的對齊。
- **修改規則時，必修多半依賴上一輪新寫的句子，或同一段被改了兩次以上**：修法可能正在製造新的邊界，再照意見補條件會讓規則繼續變長。這時缺陷可能在規則的寫法，或對需求的理解。
- **手上只有「這段讀起來模糊」的感覺，沒有失敗紀錄**：改寫的順序缺少依據。這次依模糊度挑出的 7 節，只對應到 11 則失敗裡的 1 則，把實際的糾正歸因之後才看得出失敗集中在哪一類；手上還沒有紀錄時，歸因要等紀錄累積。
