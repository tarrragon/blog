2026-11-24 在 macOS 15.3、Chrome 上調整本站 SQL 練習頁的元件配色（深色背景的練習頁，作答後每個選項的色塊翻成結果面），每一輪由本站作者看元件展示頁（把每個元件的各種狀態排在同一頁、供檢視用的頁面）提出回饋，再改 CSS。對比用 python 依 WCAG 2.2 的公式計算，元素實際套用的顏色用 Playwright 1.59.1 驅動的 Chromium 147.0.7727.15 讀。

這篇整理一組狀態配色要分開檢查的事：色塊上的文字對色塊、色塊對頁面背景、同一個顏色縮成細標記之後對它旁邊的底色，這三道對比各自怎麼算、各自擋下了這一輪的哪個顏色；以及只靠紅綠區分兩種狀態時，色覺差異（color vision deficiency）的讀者看到什麼、改用藍綠配灰之後怎麼驗；另外寫同一個顏色同時當狀態色與按鈕色的處置，以及強制色彩模式下這些狀態訊號剩下什麼。CSS 規則寫了沒生效的量測與成因在 [CSS 規則沒生效時的量測與成因：範圍重設的特定性與宿主樣式、container-type 與 subgrid、捲動陰影的覆蓋漸層](/work-log/css-silent-override-measurement/)；讀者分不分得出狀態的判讀與設計策略在 [U.C22 推薦與選錯只用紅綠區分 — 色覺差異、色塊與細標記的對比、一個顏色兩種意思](/ux-design/cases/state-colors-red-green-only/)，這篇寫每一道對比的算法、這一輪的數字與色覺換算。

## 三種狀態與這一輪用過的三組配色

練習頁作答後，每個選項的色塊標出三種狀態：推薦；選錯，也就是讀者選了而不推薦的選項；不推薦，也就是讀者沒選、也不推薦的選項。每個選項是一塊方形的選項磚，不推薦的磚底色是 `#111`，加一條 1.5px 的灰色內框 `#6b6b6b`（對黑底 3.9:1），邊界由內框承擔。這一輪用過的配色依序是下表；第一組取自 Microsoft Metro 設計語言的參考色：

| 配色             | 推薦               | 選錯              | 按鈕與焦點的強調色       | 色塊上的字 |
| ---------------- | ------------------ | ----------------- | ------------------------ | ---------- |
| Metro 參考色     | lime `#a4e600`     | magenta `#e6007e` | cyan `#00bde3`           | 黑字       |
| 低明度配色       | 深橄欖綠 `#38701a` | 深莓紅 `#a8295a`  | 深藍綠 `#0b6e8e`         | 白字       |
| 藍綠配灰（定案） | 深藍綠 `#0b6e8e`   | 深灰 `#5a5a5a`    | 按鈕改成白框，不用實心色 | 白字       |

每一次換色的依據都是計算，畫面看起來夠清楚不代替計算。對比用 WCAG（Web Content Accessibility Guidelines）2.2 的相對亮度（relative luminance）公式算，兩色的對比是較亮的相對亮度加 0.05，除以較暗的相對亮度加 0.05：

```python
# 相對亮度與對比（WCAG 2.2）；hex 換成要比的兩個顏色，格式是 #rrggbb 六位（#fff 這類縮寫要先展開）
def L(h):
    c = [int(h[i:i+2], 16) / 255 for i in (1, 3, 5)]
    c = [x / 12.92 if x <= 0.04045 else ((x + 0.055) / 1.055) ** 2.4 for x in c]
    return 0.2126 * c[0] + 0.7152 * c[1] + 0.0722 * c[2]
def contrast(a, b):
    la, lb = sorted([L(a), L(b)], reverse=True)
    return (la + 0.05) / (lb + 0.05)
contrast("#ffffff", "#00bde3")   # 白字放在 cyan 上
```

## 文字對色塊：WCAG 1.4.3 Contrast (Minimum)

一般字級的文字對它的底色至少 4.5:1。白字放在 Metro 參考色的 cyan 上只有 2.2:1，所以 Metro 參考色的色塊上用黑字（黑字在 cyan、lime、magenta 上分別 9.4、13.9、4.7:1）。本站作者要的是低明度的色階、色塊上的內文也用白字，低明度配色的白字對比是 6.0、6.7、5.8:1，定案的藍綠與深灰是 5.8、6.9:1。SQL 的語法上色放在比色塊更深的程式碼區裡，每一種語法色與每一種程式碼區底色的組合都算一次對比，最低的一組是註解色 `#a0a7ad` 放在藍綠程式碼區 `#042c39` 上，6.1:1。

## 色塊對背景：比照 WCAG 1.4.11 Non-text Contrast

WCAG 1.4.11 要求介面元件與理解內容必需的圖形，對相鄰顏色至少 3:1。翻面後的磚是 `<article>`，不能操作，狀態另有文字標籤，不在這一條的要求裡；這一頁仍取 3:1 當色塊邊界的門檻，因為色塊跟黑底的對比太低時，讀者看不出一塊磚在哪裡結束。

色塊上又要放白字，所以亮度兩端都受限。由白字至少 4.5:1 推得色塊的相對亮度至多約 0.183；由對黑底至少 3:1 推得至少 0.10。低明度的色塊只能從 0.10 到 0.183 之間挑，太亮白字不夠清楚，太暗色塊跟黑底分不開。這個區間只對純黑背景成立：背景的相對亮度是 L 時，對背景 3:1 的下界是 3 × (L + 0.05) − 0.05，背景比 `#2e2e2e` 左右再亮，下界就超過 0.183，沒有任何顏色兩道都過，這時要改用黑字或加框線。

低明度配色的三色對黑底是 3.5、3.1、3.6:1。定案配色一開始用的深灰 `#4f4f4f` 相對亮度只有 0.078，在區間之外，對黑底 2.6:1；它的白字對比有 8.2:1，所以只算文字對色塊時看不出來。改成 `#5a5a5a`（相對亮度 0.102）之後，對黑底 3.0:1、白字 6.9:1；藍綠 `#0b6e8e` 對黑底 3.6:1。

## 細標記對它旁邊的底色

同一個顏色縮成進度條的一段、結果列（作答完一輪之後，每題一列的結果清單）前的一個小方塊時，標記上沒有文字，要量的是標記對它旁邊的底色；旁邊的底色隨狀態改變時（列的預設底色、指標停留時的底色），每一種各算一次。狀態只由這個標記傳達時，1.4.11 要求 3:1；旁邊另有文字標籤時，3:1 是這一頁自己的門檻。

原本的深灰 `#4f4f4f` 當大色塊時白字有 8.2:1，縮成進度段放在黑底上只有 2.6:1，縮成結果列的方塊放在列的底色 `#1c1c1c` 上只有 2.1:1。換成 `#5a5a5a` 之後，對黑底是 3.0:1，對 `#1c1c1c` 仍只有 2.5:1，所以細標記另用 `#8a8a8a`（對黑底 6.1:1、對 `#1c1c1c` 4.9:1）。進度條上的段另外以粗細區分：未作答是 2px 細線，作答過是 6px 粗段，顏色相近的兩段靠粗細分得開。這一輪沒有改的有兩處：結果列推薦方塊的藍綠 `#0b6e8e` 對列的底色只有 2.95:1（指標停留時的底色上 2.5:1），旁邊有「答對」的文字；未作答的 2px 軌道 `#3a3a3a` 對黑底只有 1.85:1。

色塊與進度段都是用背景色畫的。Windows 的對比主題這類強制色彩模式（forced colors）會把背景色換成系統色，在 Chromium 147 用 `forcedColors: 'active'` 量，進度段與色塊都變成跟底色同一個顏色；這時狀態只剩文字標籤，粗細也分不出來。

## 紅綠色覺差異：只靠紅綠方向的色相差時

低明度配色的推薦與選錯剛好是綠與紅。用一般視覺算的相對亮度是 0.125 與 0.106，兩塊的差別主要在色相。依 Machado 等人（2009）的色覺差異模擬矩陣，在線性 RGB 上、取嚴重度 1.0（二色視）換算：第二型（deutan，綠色錐細胞的差異）的讀者看到的兩色都偏向橄欖褐，相對亮度 0.120 與 0.129，幾乎分不開；第一型（protan，紅色錐細胞的差異）時兩色的亮度差較大（0.132 與 0.073），本篇沒有判定這個亮度差夠不夠分開兩種狀態。較常見的異常三色視程度較輕，模擬結果會介於一般視覺與二色視之間。這些都是用模型換算的推論，不是讀者實測。這一頁的狀態另有文字標籤，所以合乎 WCAG 1.4.1 Use of Color；色覺差異的讀者少了哪一層，判讀在 U.C22。

本站作者比較了藍／橘、紫／琥珀、藍綠／灰三組不靠紅綠對立的配色，選了藍綠配灰：只有推薦是彩色，選錯是中性色，讀者靠「有沒有顏色」就分得出來。用同一組矩陣換算，藍綠在兩型下仍然偏藍，深灰仍然是灰；第三型（tritan）沒有換算。

## 一個顏色只代表一種狀態

藍綠標了推薦之後，題目畫面上原本實心藍綠的主要按鈕（「下一題」）改成白框加粗體；文字的選取色原本也是藍綠，在藍綠色塊上選取文字時完全看不見，改成白底黑字。讀者會不會把同色的按鈕讀成「推薦」，這一輪沒有實測，推論與處置整理在 [U.C22 推薦與選錯只用紅綠區分 — 色覺差異、色塊與細標記的對比、一個顏色兩種意思](/ux-design/cases/state-colors-red-green-only/)。

## 判斷標準：三道對比、細標記、色覺差異

- **文字對色塊**：一般字級低於 4.5:1 時，色塊上的字讀起來吃力；這一道過了，色塊對背景不一定過，因為兩者比的是不同的兩組顏色。
- **色塊對背景**：低於 3:1 時，讀者看不出色塊的邊界。深色背景上又要放白字時，色塊的相對亮度只能落在一個窄區間，背景越亮區間越窄，背景比 `#2e2e2e` 左右再亮就不存在。
- **細標記對它旁邊的底色**：同一個顏色縮成細標記時要再算一次，旁邊的底色隨狀態變化時每一種都算；狀態只由這個標記傳達時低於 3:1 就看不出狀態，另有文字標籤時讀者仍讀得到狀態，3:1 是自訂門檻。兩個細標記的顏色相近時，粗細是不必新增元素的第二個訊號。
- **色覺差異**：兩種狀態只靠紅綠方向的色相差區分時，第二型色覺差異的讀者分不開；換算後兩色的相對亮度仍然接近時，換成另一組色相（藍與橘），或只讓一種狀態有顏色。換算後兩色另有亮度差、而亮度差夠不夠分開兩種狀態拿不準時，把兩色放在同一個畫面上用色覺差異模擬並排比較，看兩種狀態分不分得出來。
- **強制色彩模式**：用背景畫的狀態訊號在強制色彩模式下會被換掉，狀態要另有文字或框線才不會只剩一種樣子。
