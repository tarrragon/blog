# 需求盤點：接到需求時要問的問題

> **角色**：`system-design` 的需求盤點步驟。產出一份「已確認 / 假設 / 待問」的清單，後面的容量估算、決策時機分類與上線設計都讀這份清單。
>
> **何時讀**：剛接到一個新系統、新功能或一次服務升級的需求，還沒開始畫架構之前。

## 產出格式

每一題的答案落在三欄之一，**不要讓問題停在「沒問」**：

| 欄位   | 意義                                                                 |
| ------ | -------------------------------------------------------------------- |
| 已確認 | 需求方給了答案，附來源（誰說的、哪份文件）                           |
| 假設   | 先用推估值往下走，寫出推估的依據，並標記「拿到實際值後要重算哪些結論」 |
| 待問   | 答案會改變設計、而目前沒有依據可推估，列給需求方                     |

判錯的代價：沒問的題目會以「設計者腦中的預設值」進入設計，而那個預設值不會出現在任何文件裡，之後沒有人知道要回頭改。

## 業務與失敗代價

- **每一條使用路徑出錯時，誰付代價、能不能收回？** 已經送出去的內容（簡訊、Email、印刷品上的網址、已付款的訂單）收不回來，承接它們的路徑可用性要排在最前面。
- **哪些路徑是營收或信任的直接來源？** 依此排出路徑的優先序，後面的一致性取捨、限流門檻、降級順序都依這個序。
- **使用者是誰、有幾種角色？** 角色不同時，看得到的資料不同，權限模型要在第一版就定。

## 數字的來源

- **每一個數字從哪裡來？** 從業務形狀推估（發送量 × 轉換率 × 集中程度），不用題目式的整數。推估方法見 `capacity-estimation.md`。
- **有沒有一個決定會讓量差好幾個數量級？** 例如「每個活動一條連結」與「每個收件人一條連結」、「每日批次」與「即時」、「只存最新值」與「保留每一次變更」。這類決定要先定，否則估算全部失準。
- **尖峰長什麼樣？** 平均值不決定容量。問尖峰由什麼事件觸發（推播、開賣、廣告上檔、月底結算）、多快到頂、持續多久、能不能預告。

## 資料

- **哪份資料是權威、哪些是衍生的？** 衍生資料（快取、統計、搜尋索引）可以重建，權威資料不行。這決定備份、一致性與哪一層可以丟資料。
- **有沒有個人資料？** 有的話，問保留期、誰能看、能不能匯出、刪除請求怎麼處理。個人資料的範圍常常藏在功能細節裡（每個收件人一條的連結就和個人綁在一起）。
- **資料要保留多久？** 保留期決定儲存量與要不要做歸檔或分割。

## 每條路徑的一致性與延遲

- **每條路徑要的一致性是什麼？** 不同路徑通常不同：讀取路徑偏可用性、寫入唯一性要強一致、統計可以最終一致。逐條路徑寫下來，不要整個系統只給一個答案。
- **延遲目標是多少、在哪裡量？** 寫明是服務端還是使用者端、看 p50 還是 p99。

## 藏在業務需求裡的技術約束

逐條功能問「這個需求對技術有什麼限制」，常見的形態：

- 「要統計每一次點擊」→ 轉址不能用會被瀏覽器快取的狀態碼。
- 「簡訊按字數計費」→ 網址長度、要不要獨立的短網域。
- 「同一個商品頁要分管道比較」→ 同一個輸入不能去重成同一筆資料。
- 「要能追到是誰」→ 資料和個人綁定，權限與保留期跟著變。

## 前端

- **誰在什麼裝置上用？** 內部人員的桌面瀏覽器、消費者的手機、低頻寬地區，對應的打包大小與相容性要求不同。
- **需不需要被搜尋引擎收錄？** 需要才考慮伺服器端渲染；登入後才能用的內部工具通常不需要。
- **前端和哪幾個後端溝通？** 後端不只一個實作或會被替換時，前端只能依賴 API 契約，不能依賴某個後端的頁面渲染機制。
- **要不要離線可用、要不要多語系？** 兩者都是之後補很貴的項目，第一版就問。

## 基礎設施

- **部署在哪裡、預算多少？** 本機、單台虛擬機、託管平台、雲端，各自的擴充手段不同。練習環境與正式環境要分開寫。
- **有沒有法規或資料落地的要求？** 決定區域與能用哪些託管服務。
- **擴充設備要多久？** 從申請到可用的時間（採購、雲端配額、憑證、網域）決定容量要提前多久準備，見 `release-and-rollout.md`。

## 上線方式

- **這個功能要不要能在不部署的情況下關掉？** 要的話需要 feature flag。
- **要不要比較新舊版本的成效？** 要的話是 A/B 測試的需求，先確認流量夠不夠得出結論。
- **上線或切換前要不要先擴充設備？** 要的話，擴充本身是上線計畫的一部分。

三題的設計方法見 `release-and-rollout.md`。

## 設計目的

- **這個設計是為了規模，還是為了學習或比較？** 練習專案裡「同一個 API 用兩種語言實作」是學習目的，不是規模需求。兩種目的要分開標記，否則學習用的設計會被當成規模的理由，或者規模的判斷被學習目的扭曲。
