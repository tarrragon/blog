# 上線設計：功能開關、A/B 測試與先擴充才能上線的變更

> **角色**：`system-design` 的上線設計步驟。處理「這個變更怎麼抵達正式環境」：要不要能不部署就關掉、要不要比較成效、要不要先擴充設備。
>
> **何時讀**：需求盤點的〈上線方式〉有任一題答「要」、API 有更新時機不受控的消費者、前端是行動 App；或設計一次服務升級、遷移、流量切換時。

## 目錄

- 〈功能開關（feature flag）〉：開關的種類與壽命、設計時要決定的事、從後台切換開關
- 〈A/B 測試〉：實驗前要寫下的事、多系統參與、早期何時算過度設計
- 〈先擴充才能上線或切換的變更〉：上線前的準備、切換方式、推進條件
- 〈對外 API 的改版〉：消費者的更新能力、各形態的退場手段
- 〈行動 App 的上線〉：商店審核的前置時間、提前內建、強制更新、熱更新、回退
- 〈上線監控〉：上線前要準備好的比較、指標與告警

## 功能開關（feature flag）

功能開關讓功能的「部署」與「啟用」分開：程式碼先部署上去，啟用與否由開關決定，關掉不需要重新部署。

### 開關的種類決定它的壽命

| 種類     | 用途                                    | 壽命                               |
| -------- | --------------------------------------- | ---------------------------------- |
| 發布開關 | 新功能先部署、再逐步開放                | 短：全面開放後就移除               |
| 維運開關 | 出事時關掉某個非必要功能（kill switch） | 長：保留在系統裡，定期演練         |
| 權限開關 | 只對特定角色或客戶開放                  | 長：屬於產品設定，不是暫時的       |
| 實驗開關 | A/B 測試的分組                          | 實驗期間：結束後依結論移除其中一組 |

建立開關時就寫下它的種類、負責人與預定移除時間。發布開關在全面開放之後沒有移除，就會累積成沒人敢動的條件分支。

### 設計時要決定的事

- **開關的值從哪裡讀**：多個服務或多個實作讀同一個開關時，要讀同一個來源。同一個請求可能先後經過不同的實例，各自讀到不同的值，功能就會時有時無。
- **讀取失敗時的預設值**：開關服務掛掉時，每個開關退回哪個值。發布開關退回「關」，維運開關退回「功能照常」。
- **前端的開關**：前端讀到的值會被快取；開關改了之後，已開啟的頁面多久生效要寫明。前端開關只控制顯示，權限檢查仍由後端執行。
- **依什麼分流**：全部開或關、依百分比、依角色或客戶。依百分比多半用在逐步開放（比例隨推進條件放大到全部）或 A/B 測試；同一個使用者要固定落在同一組（用使用者 ID 雜湊，不用每次隨機）。

### 從後台切換開關

由營運或行銷人員在後台介面切換開關時，開關就成了一個對外的操作介面，要另外設計：

- **誰能切哪些開關**：依角色限制。維運開關（kill switch）只給工程與值班人員；權限開關與發布開關可以開給營運，但要限定範圍（某個客戶、某個比例）。
- **操作紀錄**：記錄誰、在什麼時間、把哪個開關從什麼值改成什麼值。出事時第一個要查的就是最近的切換。
- **生效範圍與時間要看得到**：介面上顯示這次切換會影響哪些使用者、多久之後生效（伺服器與 App 讀取開關各有快取時間）。
- **切換也是一次變更**：切換之後看上線監控的同一組指標（見〈上線監控〉），重要的開關要有一鍵還原。

### 時機

開關機制本身屬於決策時機的「先做」類：第一個需要逐步開放或緊急關閉的功能出現時就建。個別開關則跟著功能出現與移除。

## A/B 測試

A/B 測試把使用者分成兩組以上，各給不同版本，比較某個指標的差異，用來判斷新版本是不是比較好。它和功能開關共用分組機制，但多了統計與記錄的要求。

### 實驗開始前要寫下的事

- **假設與主要指標**：預期新版本改善什麼，用哪一個指標判斷（轉換率、點擊率、完成時間）。只定一個主要指標；同時看很多指標，總會有一個碰巧顯著。
- **防護指標**：新版本不能讓哪些指標變差（錯誤率、延遲、退款率）。
- **分組單位**：以使用者、裝置、工作階段或客戶為單位。單位要和指標的單位一致，且同一單位在實驗期間固定在同一組。
- **樣本數與期間**：依目前的流量、指標的基準值與想偵測的差異大小，算出需要多少樣本、要跑多久。期間至少涵蓋一個完整的週期（例如一週），避開平日與假日的差異。
- **曝光記錄**：記錄每個單位實際看到哪一組、在什麼時間。分組了但沒看到新版本的使用者不算進結果。

### 多個系統一起參與時

前端與後端、或多個後端實作都參與同一個實驗時，分組只決定一次並傳遞下去（例如放在請求的 header 或登入憑證裡），不讓各系統各自計算分組。各自計算時只要雜湊方式有一點不同，同一個使用者就會在前端看到 A、在後端拿到 B。

### A/B 測試在早期常是過度設計

流量小的時候，達到統計顯著需要的期間長到不切實際（幾個月），結果也容易被雜訊左右。觸發條件是：**主要指標的流量足以在可接受的期間內偵測到想要的差異**。在那之前，用上線前後比較、小範圍的使用者訪談或逐步開放觀察防護指標代替，並在設計文件裡寫明這個替代做法與它的限制。

## 先擴充才能上線或切換的變更

有些變更上線之後立刻帶來更大的負載，或需要新舊系統並行一段時間：新功能預期帶來新流量、行銷活動、服務升級要換更大的資料庫、從一個平台遷移到另一個平台。這類變更的上線計畫要包含擴充本身。

### 上線前

1. **估算變更帶來的負載**：用 `capacity-estimation.md` 的方法推估新增的讀寫與儲存，以及並行期間新舊系統各自的負載。
2. **查擴充的前置時間**：從申請到可用要多久（雲端配額、採購、憑證、網域、資料複製時間）。前置時間決定最晚什麼時候要開始，而不是什麼時候上線。
3. **擴充並驗證新容量**：擴充完成後，用壓測確認新容量承受得住估算的負載，不只確認機器開起來了。
4. **寫好退回路徑**：切換失敗時怎麼退回舊系統、退回需要多久、這段期間寫入的資料怎麼處理。退回路徑在切換前就演練一次。

### 切換方式

| 方式       | 做法                                                     | 適合                           |
| ---------- | -------------------------------------------------------- | ------------------------------ |
| 逐步開放   | 用功能開關或負載平衡的權重，把流量依比例移到新版本       | 同一套資料、新舊版本可以並存   |
| 藍綠切換   | 新舊兩套完整環境並存，一次把流量切過去，舊環境保留可退回 | 需要快速整體切換、退回要快     |
| 金絲雀     | 先讓一小部分實例或使用者跑新版本，觀察指標後再擴大       | 想在小範圍內先發現問題         |
| 影子流量   | 把正式流量複製一份送給新系統，只觀察不回應使用者         | 驗證新系統承受得住真實流量形狀 |
| 雙寫後切讀 | 新舊資料庫同時寫入，驗證一致後再把讀取切到新的           | 資料庫或儲存的遷移             |

### 每一階段的推進條件

逐步推進的每一階段，事先寫下「推進到下一階段」與「退回」各自的條件，用指標表達：錯誤率、延遲、資源使用率、資料一致性檢查的結果。條件在推進前寫好，不在推進當下臨時判斷。

### 時機

這一節的內容只在變更會帶來負載或需要並行時才需要；一般功能的上線用功能開關的逐步開放即可。判斷問句是：**這個變更上線後的尖峰，目前的容量接不接得住**。接不住，擴充就是上線的前置條件，而不是上線後的改進項目。

## 對外 API 的改版

API 改版的難度由**消費者能不能跟著一起更新**決定，與 API 的風格或技術無關。

| 消費者形態           | 例子                                    | 舊的呼叫方式存在多久                           |
| -------------------- | --------------------------------------- | ---------------------------------------------- |
| 能跟服務端一起部署   | 內部服務、自家網頁前端                  | 幾乎不存在，兩邊同時上線                       |
| 由對方的團隊排期更新 | 公開 API 的外部整合方、公司內的其他團隊 | 數月到數年，由對方團隊決定什麼時候改程式並上線 |
| 由終端使用者各自更新 | 行動 App 的使用者、裝在別人產品裡的 SDK | 可能一直存在，每個使用者裝置上的版本都不同     |

同一個 API 面對多種消費者時，相容期以停在舊版最久的那一種消費者為準。「由對方的團隊排期更新」與「由終端使用者各自更新」兩種形態共用的設計：

- **只做向下相容的修改**：新增欄位與端點可以；修改語意、移除欄位要走 deprecation。
- **版本策略在第一次發布前選好**：版本放在網址、header，或像 Stripe 那樣讓每個消費者固定在自己開始使用的日期版本。
- **認出呼叫方與版本、依它們統計用量**：退場時才有逐一通知的名單，而不是只有一個總量。
- **退場的通知管道分層**：公告觸及會讀公告的人；回應裡的警告（例如 deprecation 欄位或 Sunset header）觸及正在開發的人；brownout（預告時段內暫時停用舊版）觸及所有人。退場日到了，還在用舊版本或舊欄位的呼叫要收到明確的錯誤，而不是被靜默地改用新語意處理。

一次不相容的修改（例如把整數欄位 `price` 換成含幣別的物件 `amount`）依序走：

1. 新增新欄位或新版本，與舊的並存，舊的行為不變。
2. 回應裡加上 deprecation 警告與退場日，同時公告。
3. 依呼叫方統計誰還在用舊欄位，逐一通知；遷移進度停滯時延長或加強通知。
4. 退場日前安排 brownout，讓沒讀到通知的呼叫方在預告時段內遇到明確失敗。
5. 到期後移除舊欄位，或讓舊版本的請求回明確錯誤。

各形態讓舊版本停止使用的方式不同：

| 手段             | 公開 API                                       | SDK                                                                            | 行動 App                                                    |
| ---------------- | ---------------------------------------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------- |
| 認出呼叫方       | API key、帳號（聯絡得到人）                    | SDK 版本（User-Agent）                                                         | App 版本號（使用者匿名）                                    |
| 讓舊版本停止使用 | 到期後讓舊呼叫失敗，整合方要自己改程式才能恢復 | 舊版 SDK 呼叫的 API 到期後失敗；退場前，SDK 在開發者呼叫將退場的方法時印出警告 | 最低支援版本：內建了檢查或認得「需要更新」錯誤碼的舊版顯示更新提示，使用者到商店更新即恢復；門檻若越過舊系統使用者能裝的最後一版，那群人會被切斷 |
| 服務端上線的延遲 | 部署後立即生效                                 | 套件發布                                                                       | 商店審核                                                    |

行動 App 的商店審核延遲與最低支援版本機制見〈行動 App 的上線〉。

## 行動 App 的上線

網頁部署之後所有使用者立刻拿到新版、也能立刻退回；行動 App 兩件事都做不到。新版本要經過商店審核才能上架，上架之後使用者自己決定什麼時候更新，舊版本會在使用者手機上留很久。上線設計要依這兩個事實調整。

### 商店審核的前置時間

- **上線日往前推**：審核時間不固定，被退件要修改再送，所以功能的上線日要預留審核與一次退件的時間。行銷活動綁定日期的功能，送審日要從活動日往回推。
- **提前內建、遠端啟用**：新功能完整的程式與資源（畫面、素材、新 API 的呼叫）一起放進一個較早的版本，用遠端設定保持關閉；到上線日由後端或後台開啟。這樣上線日只依賴伺服器端，不依賴審核進度。前提是遠端設定的讀取間隔短到上線日開得起來、出問題時關得掉，或已整合即時更新。後端也要依上線日拒絕提前的呼叫，因為遠端設定的值不是祕密，被改過的客戶端能自己打開開關。代價是安裝檔變大、拆包後內容提前外流；素材打包在安裝檔裡的話，出錯時只能送修正版，從伺服器下載的素材則可以直接換。商店政策對隱藏、之後才啟用的功能有規範，所以送審說明要寫明哪些功能由遠端設定控制，並提供審核人員開啟它們的方式。
- **後端先上**：新版 App 要呼叫的 API 在送審前就部署到正式環境，審核人員測試時才呼叫得到。部署時舊版 App 仍在呼叫既有的 API，所以新 API 以新增的方式上線，不改變既有 API 的行為。順序反過來，新版 App 上架時呼叫的 API 還不存在，審核也可能因此被退件。

### 多個版本同時在線

API 的相容紀律與版本回報照〈對外 API 的改版〉；App 多出來的是：

- **每個請求帶 App 版本與作業系統版本**：後端依版本決定回應格式、依版本比較錯誤率、記錄問題出在哪個版本、判斷要不要要求更新；作業系統版本用來算出有多少人裝不了新版。header 的名稱與格式一旦上架就不能改。有用熱更新的話，再帶目前套用的更新識別碼。
- **版本比較與缺少版本的請求**：版本字串拆成整數逐段比較，相同時再比建置號（iOS 的建置號換版本字串時可以重新計數）；直接比字串時 `1.10.0` 會排在 `1.2.0` 前面。先辨識出請求來自自家 App（API key、client id），再把其中缺少版本的請求視為最舊的版本；它們是加入版本回報之前所有版本的總和，彼此分不開。
- **強制更新的兩層**：客戶端啟動檢查（啟動與回到前景時讀遠端設定裡的最低支援版本，低於就顯示更新畫面）只在內建了檢查程式的版本上運作；伺服器端拒絕（後端依版本回報拒絕過舊的請求，回一個專用的「需要更新」錯誤碼）對所有版本有效。客戶端啟動檢查與對錯誤碼的處理都要從第一個上架的版本就內建：之後才加入的話，加入之前的版本仍會被伺服器端拒絕，但只會顯示通用錯誤畫面，使用者不知道要更新。錯誤碼搭配的 HTTP status 選舊版通用處理不會重試、不會登出、也不會清除 token 的 4xx。
- **最低支援版本的保存**：每個平台一個門檻，客戶端啟動檢查與伺服器端拒絕讀同一份（自家設定服務供應兩層，或後端用遠端設定服務的伺服器端讀取介面）；個別壞版本的封鎖清單只在伺服器端。修改要有權限控管，新門檻不得高於該平台已經全量上架的最新版本，也不得高於要保留的舊系統使用者能裝的最後一版。客戶端內建的預設值設成不會擋下任何已上架版本的值，讀不到設定時就不擋。
- **提高最低支援版本之前，分出拿不到新版的使用者**：新版還沒在該平台全量上架（Google Play 分階段推出未到 100%）、裝置作業系統低於新版下限、加入版本回報之前的舊版。這幾群不能被硬阻擋：要保留舊系統使用者，門檻的上限就是他們能裝的最後一版（或讓門檻依作業系統分段，分段格式同樣要從最早的版本就定）；剩下的才是這次提高的代價。
- **Feature Flag 的預設值與移除時機**：App 讀取的 Feature Flag 預設關閉，只對實作完整、沒有已知問題的版本開啟。收斂為開啟的 flag 移除分兩步：先發一版不再讀它、行為寫死為開啟的 App，再等最後一個讀它的版本低於最低支援版本，才刪掉遠端定義；提早刪掉時，仍讀它的版本會改用內建預設值，功能跟著消失。收斂為關閉的 flag 可以直接刪。

### 熱更新

熱更新讓修正不經商店審核就抵達使用者，常見的做法是框架提供的程式碼推送服務（例如 React Native 的 Expo EAS Update、Flutter 的 Shorebird）。

- **範圍限制**：只能更新框架執行的那一層（畫面與商業邏輯），範圍依工具而不同（例如 Shorebird 不能更新圖片、字型等素材檔）；原生程式碼、權限、框架或引擎版本的變更仍要送審。
- **商店政策**：Apple App Review Guidelines 2.5.2 規定 App 不得下載、安裝或執行會新增或改變功能的程式碼；Apple Developer Program License Agreement 3.3.1(B) 允許下載直譯式程式碼，條件包括不改變 App 的主要用途、不用來繞過審核。Google Play 的裝置與網路濫用政策禁止 App 用 Google Play 以外的方式更新自己或下載可執行程式碼，在虛擬機或直譯器裡執行的程式碼例外；某個熱更新服務落不落在例外，看它自己的文件。熱更新服務的文件也都寫明內容合規由開發者負責。熱更新用在修正已通過審核的功能，新功能走送審。
- **熱更新本身也要能回退**：推送的更新出錯時，要能把使用者退回上一個版本的程式碼，並分批推送。

### 出問題時的回退

商店上的版本無法撤回已經安裝的程式，回退要靠事先準備好的手段。各手段對已經裝上出問題版本的使用者多久生效，取決於事前準備，所以下面的順序不代表快慢：

1. **遠端設定關閉功能**：App 下一次讀到並套用新設定時生效。讀取間隔依設定服務而定（Firebase Remote Config 預設 12 小時，整合即時更新才能到分鐘級）。前提是那個功能有開關、讀取間隔夠短或已整合即時更新，而且問題發生在套用設定之後；當機若發生在讀到設定之前，關掉開關無效。
2. **伺服器端依版本調整**：改回應內容繞過問題，或把有問題的版本導向相容的處理方式。前提是 App 每個請求都帶版本號，而且 App 處理回應時能容忍多出來的欄位、未知的列舉值與空值。只能處理由回應觸發的問題。
3. **熱更新推送修正**：有熱更新機制、而問題在可熱更新的那一層時可用；App 下載到更新之後的下一次啟動生效。
4. **只拒絕出問題的那一個版本，或提高最低支援版本**：修正版在該平台全量上架之後才做。只拒絕壞掉的那一版（伺服器端封鎖清單）影響的人比較少，前提是出問題的版本認得「需要更新」錯誤碼，且問題發生在第一次呼叫 API 之後；提高最低支援版本會連帶擋下正常的舊版與裝不了新版的使用者，前提是出問題的版本有客戶端啟動檢查或認得錯誤碼。
5. **送審修正版**：要等審核，只涵蓋會更新的使用者（修正嚴重錯誤時可以申請 Apple 的加急審核）。新版的版本字串（iOS）或 `versionCode`（Android）必須比有問題的版本高，不能重新上架舊的版本號；要回到舊程式，就用更高的版本號重新發布舊程式碼。

發現問題時先暫停分階段發布，擋住還沒拿到新版的人（App Store 的分階段發布只控制自動更新，主動到商店更新的使用者仍會拿到新版）；已經裝上的人用上面的手段處理。設計時逐一確認新功能能用上哪幾項，只能靠送審修正的功能要在上線前多一輪測試。

## 上線監控

上線監控回答一個問題：**新版本或新開關，比舊的好、一樣，還是更差**。它和平常的系統監控用同一批指標，差別在要能依版本與開關分組比較，而且要在上線前就準備好——上線當下才建，問題已經發生了。

### 上線前要準備好的

- **分組維度**：請求與事件帶上版本號（服務版本、App 版本）與開關的狀態，指標才能依它們拆開。
- **比較基準**：新舊版本並存期間，同一時段比較兩組；只看上線前後，會把時段造成的差異當成版本的差異。
- **推進與退回條件**：〈每一階段的推進條件〉寫的指標，就是這裡要準備的告警。

### 要看的指標

| 層       | 指標                                                                                   |
| -------- | -------------------------------------------------------------------------------------- |
| 後端     | 依版本分的錯誤率、延遲、資源用量；新 API 的呼叫量與錯誤                                |
| 網頁前端 | 前端錯誤率、頁面載入時間、關鍵操作的完成率                                             |
| 行動 App | 依版本分的當機率與無回應率、各版本的使用者比例（更新進度）、依 App 版本分的 API 錯誤率 |
| 業務     | 這次變更要改善的指標，以及不能變差的防護指標（見〈A/B 測試〉）                         |

### 告警與值班

上線期間的告警門檻比平常嚴，並指定誰在看、看到之後依哪一個回退手段處理。逐步開放的每一階段推進前，確認上一階段的指標都在推進條件內。
