# 決策時機：依改動成本分類

> **角色**：`system-design` 的核心判斷。把每一個設計決定分進定案、先做、延後三類之一，決定它在哪個階段做。
>
> **何時讀**：列出設計決定清單之後、開始寫設計文件之前；或檢討一份既有設計有沒有過度設計時。

## 分類依據是「之後改要付多少代價」

分類看的是**現在做與之後補的成本差**，不看做起來難不難。同一個設計可以很難但該早做（對外的識別碼格式），也可以很簡單但該延後（加一層 Bloom filter）。

逐項問兩題：

1. **如果之後要改這個決定，改動會碰到已經不在團隊控制範圍內的對象嗎？**（已發出去的網址、外部整合方、已寫入的資料、使用者的書籤）
2. **現在做和之後補，成本差多少？**

| 分類     | 判定                                                 | 處置                                         |
| -------- | ---------------------------------------------------- | -------------------------------------------- |
| **定案** | 第一題答「會」                                        | 第一版就定，寫進設計文件並說明理由           |
| **先做** | 第一題答「不會」，但現在做很便宜、之後補很貴          | 第一版就做                                   |
| **延後** | 第一題答「不會」，而且現在做的成本高於之後補          | 不做；寫下早期的替代做法與觸發指標           |

## 定案：之後改會碰到團隊控制範圍外的對象

- **對外的識別碼與網址格式**：短碼格式、網域結構、公開 API 的路徑。發出去就收不回來。
- **保留給固定路由的路徑**：路由裡有「整段路徑都是參數」的形式（`/{code}`、`/{username}`）時，健康端點（`/healthz`）、`/api`、`/admin` 這類固定路徑會跟參數搶同一個名字。依路徑明確度匹配的路由器（例如 Go 1.22 起的 `http.ServeMux`）遇到兩者都對得上時交給固定路徑，依註冊順序匹配的路由器交給先註冊的那一個；不論哪一種，總有一方的請求永遠到不了它的處理程式，也不會報錯。三種避開方式，依維護成本由低到高：固定路由使用參數字元集產生不出的字元（Base62 短碼沒有 `-`，固定路由放在 `/-/healthz` 這種路徑下，依產生方式就不可能同名）；產生器與自訂名稱的驗證排除固定路由的名字（要維護排除清單，漏加不報錯）；健康端點放在另一個 port。不論選哪一種，都要在第一個識別碼發出去之前定好，之後才改，已經發出去的同名識別碼收不回來。
- **跨服務共用的契約**：API 規格、登入憑證格式、事件的結構、快取 key 與序列化格式。改它要所有使用方同時改。
- **會被客戶端存起來再送回來的值的格式**：分頁的接續標記（cursor，伺服器給的、記錄下一頁從哪一筆接續的字串）、時間格式、續傳用的 token。客戶端拿到之後可能存著，下一個請求才送回來；滾動部署期間新舊版本同時在服務，送回來時可能由另一個版本解讀。格式要在第一版寫死，之後要改就分兩次部署：先部署兩種格式都解得開、仍發舊格式的版本，全部換上之後才開始發新格式。框架內建的接續標記格式通常綁在框架的實作上，多個實作或換框架時互相解不開，要自己定義。
- **登入憑證的撤銷以什麼為單位**：比對的依據必須是撤銷的那一刻拿得到的東西。以單一 token 為單位（記下 token 的識別碼）只撤銷得了手上有的那一個，適合「登出這台裝置」；停用帳號、改權限、登出所有裝置時，系統不知道使用者手上還有哪些 token，要以使用者為單位（記下撤銷時間，拒絕在那之前簽發的 token）。撤銷紀錄的 key 格式與比對規則是每個驗證者都要遵守的契約，第一版定錯，之後要所有驗證者一起改。
- **資料歸屬**：哪份資料是權威、schema 由誰管。之後改要搬資料。
- **個人資料的範圍與保留期**：之後改要處理已經收集的資料。
- **前端的路由結構與對外網址**：使用者的書籤與搜尋引擎的索引已經指向它們。
- **對外的識別資訊與錯誤碼格式**：每個請求帶的呼叫方與版本 header（名稱與格式）、行動 App 認得的「需要更新」錯誤碼。它們寫進已上架的客戶端，之後改名，舊版會一直送出舊的名稱、認不得新的錯誤碼。
- **消費端更新時機不受團隊控制的 API**：消費端包括行動 App 的使用者（自己決定何時更新）、公開 API 的外部整合方（依自己的排期更新）、使用團隊發佈的 SDK 的開發者、以及嵌在第三方系統裡的整合。這些消費端不會跟著服務端一起部署，舊的呼叫方式會持續存在數月到數年，所以 API 第一次對外發布之後，已發布的端點、欄位與行為就屬於定案：之後的修改只能向下相容地新增，移除要走 deprecation 流程等舊消費端退場。版本策略（版本放在網址、header 還是依日期）也要在第一次發布前選好，因為它本身就是契約的一部分。消費端依更新能力的分類（能跟服務端一起部署、由對方的團隊排期更新、由終端使用者各自更新）與各自的退場手段見 `release-and-rollout.md` 的〈對外 API 的改版〉。

判錯的代價：把這一類誤判成延後，之後的改動是遷移專案，而不是一次修改。

## 先做：現在便宜、之後很貴

這一類最容易被誤判成過度設計：

- **量測**：沒有指標，延後類的觸發條件就無從判斷。早期該建的是「觀察觸發條件的能力」，而不是擴充本身。每一個延後的設計都要對應一個現在就在量的指標。
- **應用程式保持無狀態**、設定放在環境變數：之後才拆會牽動整個程式。
- **時間一律存 UTC、識別碼不對外暴露連續序號**：之後改要轉換既有資料。
- **回應標記來源**（哪個實例、哪個版本回的）：多實例之後排查全靠它。
- **前端的 API 呼叫集中在一層**：之後換認證方式或加重試只改一處。
- **基礎設施用設定檔描述**（compose 檔、IaC）：環境變多之後才補，要回頭還原手動做過的設定。
- **依呼叫方與版本統計用量**：之後要讓某個版本退場時，要靠這份統計知道還有誰在用、要通知誰；第一版沒有記錄，就只剩總呼叫量可以看。（識別呼叫方與版本的 header 本身屬於定案，見〈定案：之後改會碰到團隊控制範圍外的對象〉。）
- **行動 App 的強制更新機制**：客戶端啟動檢查與對「需要更新」錯誤碼的處理要從第一個上架的版本就內建。伺服器端拒絕對所有版本都有效，但沒有內建前兩樣的版本被拒之後只會顯示通用錯誤，使用者不知道要更新。
- **行動 App 的遠端設定與當機回報**：遠端設定讓功能能在不重新送審的情況下開關，讀取間隔要短到出問題時關得掉；當機回報（帶版本標記）讓新版本的問題能在使用者回報之前被看見。兩者都要在第一個上架的版本就內建，之後加入的版本才有。
- **服務的健康檢查與它失敗之後的處置**：每個服務要有一個能被外部讀到的健康訊號，形式依服務類型而定：HTTP 服務是健康端點；沒有 HTTP 的 queue worker 是心跳或「最後一次處理成功的時間」（卡住時這個時間不再前進）；跑完就結束的批次工作是完成回報，由外部在預期時間內沒收到回報時告警（dead man's switch）；serverless 由平台管理執行環境，要設的是平台的錯誤率與逾時告警。每一種都寫下三件事：訊號正常時保證什麼（只有程序在運作，還是連關鍵依賴都可用）、誰讀它（容器平台、負載平衡器、外部探測工具）、讀到失敗之後誰做什麼（摘流量、重啟、通知人）。第三件最常漏：同一個健康檢查在不同平台的效果不同，例如 Docker Compose 只把容器標成 unhealthy、不會重啟它，Kubernetes 的 liveness probe 會重啟。只寫了端點而沒寫處置，服務卡住時沒有任何東西會動作，要等使用者回報才知道。多個服務共用一個入口時，另外決定入口的啟動要不要等上游健康：等的話，任一個上游壞掉，入口在下一次重啟時就起不來。
- **功能開關的機制本身**：第一個需要開關的功能出現時，有機制只要加一個開關；沒有機制要先建機制，見 `release-and-rollout.md`。

判錯的代價：把這一類誤判成延後，觸發指標出現時才發現量不到，或者要先花一輪重構才能開始擴充。

## 延後：等觸發指標

現在做的成本（開發、維運、心智負擔）高於之後補的成本。處置是三件事，缺一就不算延後：

1. **寫下早期的替代做法**：現在用什麼較簡單的方式頂著。
2. **寫下觸發指標**：哪個指標到什麼程度時要做。目錄見 `escalation-triggers.md`。
3. **確認那個指標現在就在量**：沒在量的指標不會發出任何訊號，延後的設計之後不會被想起。

**過度設計的定義是「比觸發指標先出現的設計」**，不是「做得太多」。同一個 Bloom filter，在不存在的請求比例升高之後是對的設計；它在那之前出現才是過度設計。

## 目的不是上線服務的設計

上面的分類假設設計是為了一個要上線、要長期營運的服務。目的不同時，分類的結果也不同：

| 目的         | 要達成的事                         | 分類怎麼變                                                                                         | 主要風險                                       |
| ------------ | ---------------------------------- | -------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| 原型         | 驗證需求或技術可不可行，預期會改或丟 | 還沒有對外發布任何版本或 API，就還沒有團隊控制範圍外的對象，定案類多半可以先不定；先做類只留驗證需要的那幾項     | 原型被直接延用成正式服務，跳過的項目沒有人補   |
| 提案 demo    | 讓決策者看到效果、做出決定         | 只把展示路徑做完整，其餘可以用假資料或寫死的值                                                     | demo 被當成成品，假資料與寫死的值留在正式環境 |
| 學習或比較   | 學一項技術，或在同一條件下比較方案 | 刻意做的設計（兩種語言實作同一個 API、換快取伺服器比較）不經過分類，寫明要學到或比較出什麼；延後類的設計若也都要實作，就排成開發順序裡較後的階段：先上最簡單的做法、量出瓶頸，再加上設計並用同一個情境重量 | 為學習做的設計被拿來證明規模需求               |

三種目的都要寫下兩件事：這份設計要驗證、展示或學到什麼，以及為了這個目的**跳過了哪些上線服務需要的設計**（版本回報、強制更新、監控、權限、備份……）。目的不同的設計不互相借理由：學習或展示用的設計不拿來證明規模設計合理，規模判斷也不遷就它們。

**目的改變與第一次對外發布是重新分類的觸發點。** 原型轉成正式服務、demo 被採用直接上線時，以及第一次對外發布（App 上架或發 beta、API 對外開放）之前，回到本檔開頭重新分類一次，從「跳過了什麼」那份清單開始逐項判斷它現在屬於定案、先做還是延後。第一次對外發布特別要提前：行動 App 第一個上架的版本若缺了版本回報或強制更新檢查，那個版本就永遠沒有，即使目的還沒改變。沒有那份清單，跳過的項目在轉正式的那一刻不會被任何人想起。

## 產出

一張決定清單，每一列寫：決定、分類、理由；延後類另加早期替代做法、觸發指標與量測位置。
