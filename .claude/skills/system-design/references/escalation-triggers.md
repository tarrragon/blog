# 延後設計的觸發指標

> **角色**：`system-design` 的查表型目錄。每一列是一個常被提前做的設計、它的早期替代做法、觸發它的訊號，以及那個訊號要靠什麼指標看見。
>
> **何時讀**：決策時機分類把某個設計判為「延後」之後，到這裡找它的觸發指標；或量測顯示某一層到了極限，反查該引入哪個設計。

## 使用方式

- 這是查表，逐列查，不必通讀。表裡沒有的設計，照同樣四欄自己補一列寫進設計文件。
- **觸發訊號寫成相對於目標的條件**（「拉高 p99 到接近延遲目標」），不寫成通用的絕對數字。門檻值依每個系統的延遲目標與資源規格而定，寫進該系統的設計文件。
- 「要先量的指標」欄是決策時機分類裡「先做」類的來源：每一列的指標都要從第一版開始量。
- 一個訊號出現時，先確認是不是更便宜的替代做法還沒用盡（例如加索引、調連線池），再引入表上的設計。

## 後端與資料

| 設計                                                     | 早期替代做法                                         | 觸發訊號                                                                                                                                                                                                                     | 要先量的指標                                                                                                              |
| -------------------------------------------------------- | ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 快取層                                                   | 直接查資料庫，加對的索引                             | 讀取量讓資料庫 CPU 或查詢延遲逼近目標；同一批資料被反覆讀取                                                                                                                                                                  | 資料庫 CPU、查詢延遲、熱門 key 的讀取分布                                                                                 |
| 快取「不存在」的結果                                     | 查不到就回錯誤                                       | 不存在的請求反覆打到資料庫                                                                                                                                                                                                   | 查無資料的請求比例                                                                                                        |
| Bloom filter                                             | 快取「不存在」的結果加來源限流                       | 不存在的請求大多是不重複的鍵（隨機掃描），快取「不存在」擋不住                                                                                                                                                               | 查無資料的請求數、其中不重複鍵的比例                                                                                      |
| 非同步寫入（佇列或 stream）                              | 請求內同步寫入                                       | 尖峰時寫入延遲拉高主要路徑的延遲；連線池被寫入佔滿                                                                                                                                                                           | 寫入延遲、連線池使用率、主要路徑的 p99                                                                                    |
| 資料庫唯讀副本                                           | 單一主節點                                           | 報表或統計查詢拖慢主要路徑；主節點 CPU 持續偏高而讀佔多數                                                                                                                                                                    | 主節點 CPU、各類查詢的佔比與延遲                                                                                          |
| 依時間分割資料表（有保留期的表）                         | 一般資料表加索引                                     | 刪除過期資料變慢；清理作業影響線上查詢。前提：唯一約束要包含分割欄位，靠某一欄的唯一約束防止重複的表（例如短碼）依時間分割時，另建一張不分割的登記表（那一欄當主鍵）擔任唯一的仲裁者，每次寫入多寫一張表，登記表本身也不刪除 | 表與索引大小、清理作業耗時                                                                                                |
| 專門的事件管道（如 Kafka）                               | 資料庫的資料表或快取伺服器的 stream                  | 多個消費者要各自讀同一批事件、需要重播、事件量造成記憶體壓力                                                                                                                                                                 | 事件量、消費延遲、消費者數                                                                                                |
| 分片（sharding）或依唯一鍵的雜湊分割（不刪除的表）       | 垂直擴充加唯讀副本；部分索引、拿掉沒有查詢在用的索引 | 垂直擴充與副本都用盡之後，常用索引放不進記憶體、autovacuum 一輪的耗時或建索引與還原的耗時超過可接受的範圍；列數本身不是訊號                                                                                                  | 表與索引大小的每月成長、索引頁的命中率（PostgreSQL 的 `pg_statio_user_indexes`）、autovacuum 每輪耗時、建索引與還原的耗時 |
| 拆成多個服務                                             | 單一服務內分模組                                     | 不同部分的部署節奏、擴充需求或負責團隊已經不同，互相拖累                                                                                                                                                                     | 各模組的變更頻率、資源用量、事故關聯                                                                                      |
| 多個 API 版本並存                                        | 單一版本，只做向下相容的新增                         | 停在舊版的消費者（舊版 App、未遷移的整合方）佔比高或包含重要客戶，而新需求需要不相容的格式                                                                                                                                   | 依呼叫方與版本分的呼叫量                                                                                                  |
| 讀寫路徑分開部署                                         | 同一組實例                                           | 重的管理或報表請求影響主要路徑；兩者需要不同的擴充節奏                                                                                                                                                                       | 依路徑分開的延遲與資源用量                                                                                                |
| 熱點列的計數拆開（拆成多列、只新增事件、先在記憶體合併） | 每次事件更新同一列計數                               | 同一列的寫入在尖峰時排隊，該路徑的寫入延遲逼近目標；加連線只讓延遲更高                                                                                                                                                       | 該列的鎖等待、寫入延遲、每秒更新次數                                                                                      |
| 統計彙總改成寫入時累加                                   | 排程定期依原始事件重算最近的時段                     | 一輪重算的耗時逼近排程間隔；重算讀的事件量隨流量成長                                                                                                                                                                         | 每輪重算的耗時與讀取列數、重算落後時間                                                                                    |
| 統計彙總改成更細的時間粒度                               | 每小時一列；不支援的時區回錯誤並說明原因             | 開始出現時差不是整小時的時區請求，或確定要接這些時區的客戶                                                                                                                                                                   | 依原因分的時區驗證失敗次數                                                                                                |
| 已到期很久的資料搬到冷表（不刪除的表）                   | 留在同一張表                                         | 同分片那一列的訊號；另確認唯一性由誰檢查：搬出去之後新增資料要同時查兩張表才能確認不重複，除非另建一張登記表擔任仲裁者                                                                                                       | 同分片那一列                                                                                                              |

## 前端

| 設計                 | 早期替代做法               | 觸發訊號                                               | 要先量的指標                               |
| -------------------- | -------------------------- | ------------------------------------------------------ | ------------------------------------------ |
| 伺服器端渲染（SSR）  | 單頁應用（SPA）            | 頁面需要被搜尋引擎收錄；首次載入時間影響轉換           | 搜尋流量需求、首次內容繪製時間             |
| 程式碼分割與延遲載入 | 單一打包檔                 | 打包大小拉長首次載入；使用者只用到少數頁面             | 打包大小、首次載入時間、頁面使用分布       |
| 全域狀態管理函式庫   | 元件內狀態加少量共用 store | 同一份狀態要在多個不相鄰的元件間同步，傳遞路徑難以追蹤 | 跨元件共用狀態的數量、相關缺陷             |
| 共用元件庫或設計系統 | 各應用自己的元件           | 多個應用重複實作同一批元件，外觀與行為開始不一致       | 重複元件數、樣式不一致的回報               |
| 微前端               | 單一前端應用或少數獨立應用 | 多個團隊要獨立部署同一個頁面的不同區塊                 | 團隊數、部署衝突頻率                       |
| 靜態資源走 CDN       | 由網頁伺服器直接提供       | 使用者分布在離伺服器遠的地區；靜態資源佔掉伺服器頻寬   | 各地區載入時間、靜態資源流量               |
| 離線可用（PWA）      | 線上才能用                 | 使用情境常斷線（現場、移動中）                         | 使用環境的連線品質、斷線時的失敗數         |
| 前端錯誤與效能監控   | 瀏覽器開發者工具           | 使用者回報無法重現的錯誤；不同裝置表現差異大           | （這一列本身就是量測，屬「先做」類的候選） |

## 行動 App

| 設計                                 | 早期替代做法                           | 觸發訊號                                                         | 要先量的指標                       |
| ------------------------------------ | -------------------------------------- | ---------------------------------------------------------------- | ---------------------------------- |
| 熱更新（不經商店審核的程式更新）     | 遠端設定關閉有問題的功能，再送審修正版 | 修正常常等不及審核；問題多出在可熱更新的那一層（畫面、商業邏輯） | 從發現問題到修正抵達使用者的時間   |
| 伺服器驅動的介面（server-driven UI） | 介面寫在 App 裡，用遠端設定開關區塊    | 介面調整的頻率高到每次都等審核成為瓶頸                           | 只改介面的版本佔全部版本的比例     |
| 自建的開關與實驗平台                 | 託管的遠端設定服務或簡單的設定表       | 開關數量、切換頻率或實驗數量讓手動管理出錯                       | 開關數、切換次數、因切換造成的事故 |

## 基礎設施

| 設計                            | 早期替代做法               | 觸發訊號                                                         | 要先量的指標                     |
| ------------------------------- | -------------------------- | ---------------------------------------------------------------- | -------------------------------- |
| 容器編排平台（如 Kubernetes）   | 單機或少數機器上的 compose | 服務數與實例數多到手動排程與重啟成為負擔；需要自動恢復與滾動更新 | 實例數、手動介入次數、部署耗時   |
| 自動擴充                        | 固定實例數，依預估尖峰預留 | 流量起伏大，固定實例在離峰浪費、在尖峰不足                       | 各時段的資源使用率、尖峰持續時間 |
| 多個應用實例加負載平衡          | 單一實例                   | 單一實例的 CPU 或記憶體在尖峰時逼近上限；需要不中斷部署          | 實例資源使用率、部署時的錯誤數   |
| 託管資料庫                      | 自架資料庫                 | 備份、升級、故障切換的維運工作超過團隊能負擔的量                 | 維運工時、備份與還原的演練結果   |
| 多可用區                        | 單一可用區                 | 可用性目標高於單一可用區能提供的                                 | 可用性目標、過去的可用區事故     |
| 多區域                          | 單一區域                   | 跨區使用者的延遲超過目標；法規要求資料留在某個區域               | 各地區的延遲、法規要求           |
| 邊緣防護（CDN、WAF、DDoS 清洗） | 來源端限流                 | 異常流量（掃描、機器人、攻擊）讓來源端的限流也擋不住             | 依來源分的請求量、被限流的比例   |
| 秘密管理服務                    | 環境變數檔                 | 秘密數量與輪替頻率增加；多個環境要分開管理                       | 秘密數、輪替紀錄                 |
| 集中式日誌與指標平台            | 各機器上的日誌檔           | 實例超過一台，排查要逐台登入                                     | 實例數、排查耗時                 |
