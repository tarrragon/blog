# 觀察者與限制的獨立性：被保護的一方能不能讓它失效，從失效域、寫入路徑與輸出管道判斷

> **角色**：本卡是 `system-design` 的支撐型原則（principle）、被 `references/decision-timing.md`〈先做〉的主機外訊號、異地備份與跨網路連線三條引用。
>
> **何時讀**：設計階段決定監控的觀察者、異地備份或兩個網路之間的限制放在哪裡，要判斷它是否獨立於被保護的對象時；或看到「放在另一台所以獨立」「備份在另一個業者所以安全」這類判斷時。

一個觀察者（或一條限制）獨立於被保護的對象，條件是**被保護的一方沒有任何方式讓它失效**。要同時查三件事，三件都通過才算獨立：

- **共用的失效域**：它與被保護的對象有沒有共用會一起停掉的依賴（同一台主機、同一個業者帳號、同一條網路、同一個 DNS）。
- **寫入路徑**：被保護的一方（或被假設入侵的那一台）能不能改寫它：存在那台機器上或它取得得到的憑證（API 金鑰、業者 token、雲端實例角色）、已登入的工作階段（管理介面、信箱、業者主控台）、它能推送的設定來源、它在控制平面上的角色。
- **輸出管道**：觀察者的結論送到人手上的那一段（通知管道、收件信箱、推播頻道）也要通過前兩項。觀察者獨立而通知經過被保護的一方，結果與沒有觀察者相同。

評估單位是每一台會被假設入侵的機器，包括管理者日常使用的裝置；那台裝置存著登入每一台主機的憑證，通常是最寬的寫入路徑。

## 以存放位置判斷為什麼會漏

「它放在另一台／另一個業者，所以獨立」回答的只有三件事裡的失效域，寫入路徑與輸出管道它都沒有回答。這個判斷在故障情境下多半成立（停掉的機器不會去改寫別人），在入侵情境下多半不成立（被入侵的機器還在運作，由一個會去找寫入路徑的人操作）。一份只做過故障演練的設計，對入侵的獨立性沒有證據。

實際出現過的形態：

- 心跳監看放在另一個業者，而心跳只證明它自己那一條路通，通知管道壞掉時心跳照常送達。
- 監控主機存著心跳網址，被入侵時攻擊者停掉告警鏈、自己送心跳。
- 外部探測的告警寄到監控主機也存著密碼的信箱，攻擊者設一條過濾規則就刪掉。
- 限制寫在另一端，而被入侵的那一台存著能改那條限制的 API 金鑰。
- 備份放在另一個業者，而寫入它的存取金鑰在服務主機上、上傳權限本身包含覆寫。

## 判讀徵兆

- 文件寫「放在另一台」，而沒有列出被保護的那一台上有哪些憑證與已登入的工作階段。
- 只做過停掉主機、拔網路的演練，沒有推演過「假設這一台被拿下」。
- 修法一再補上「前提是那一台沒有能改寫它的憑證」，而判斷的定義本身仍只看位置。
- 觀察者的告警寄到的信箱或推播頻道，其帳號存在被觀察的機器上，或存在管理者每天用的電腦上。
