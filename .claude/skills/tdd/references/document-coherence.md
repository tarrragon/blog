# 文件連貫性紀律：分級、住址、各 Phase 檢查點

## 目的

TDD 流程的文件鏈很長：Proposal → Spec → UC → 種子包 → feature-spec → 測試 → 實作與註解 → traceability → work-log。Brooks 在《人月神話》對多文件維護的結論是：同時維護多份文件不可能持續，文件之間的進度必然產生落差，而有落差的文件最終完全沒有人更新；他給的方向是把文件盡可能併入程式自身。本 reference 把這個結論落成三條紀律——文件分級、資訊住址、各 Phase 檢查點——目標是讓每份文件的**同步期待與守護機制匹配**：期待最新就要有機制守著、沒有機制就明示降級，不把同步寄託在紀律上（同步對改程式的人當下零收益、收益結構決定它不會自發發生）。

---

## 文件分級表

三級、依「同步期待 × 守護機制」分：

| 級別 | 同步期待 | 必要條件 |
| ---- | -------- | -------- |
| **活文件** | 永遠反映現狀 | 有機制守著：會紅的測試、編譯器、CI 比對腳本 |
| **scaffold** | 只在被消費那一刻正確、消費後即過期 | 標記一次性身分與消費時點、過期後不得被當權威引用 |
| **append-only 記錄** | 記錄寫下當時的事實、永不回改 | 標明時點、讀者知道它是史料不是現狀 |

TDD 文件鏈逐份分級：

| 文件 | 級別 | 機制 / 標記 |
| ---- | ---- | ----------- |
| Proposal | append-only 記錄 | 需求決策史；範圍變更走新 proposal、不回改 |
| Spec（domain）/ UC | 活文件 | `/spec validate` 結構與覆蓋檢核 + 邊界回補流程（gap → DOC ticket 回補）；回補**只修這裡**、不修下游副本 |
| domain-map | 活文件 | `check_domain_coverage.py` 比對 FR 覆蓋 |
| TDD 輸入種子包（Ticket 內） | **scaffold** | 消費者是 Phase 0/1；Phase 1 完成即過期。GWT 種子是 UC 的複本、過期後與 UC 的差異不是 bug、是身分——爭議時以 UC 為準 |
| feature-spec（Phase 1 產出） | **scaffold** | 消費者是 Phase 2 測試設計；Phase 3 綠燈後權威轉移到測試與程式碼、文件頂部標記 `status: archived (superseded by tests)`。之後讀它是讀史料 |
| 測試（名稱 + GWT + assertion） | 活文件 | CI / pre-commit 自動跑——整條鏈裡唯一改壞當下會發聲的載體、**行為的權威載體** |
| 實作註解 | 依判準逐則歸類 | 見「註解判準」節 |
| traceability.yaml | 活文件（有條件） | 條件是 Phase 4 用腳本比對實際測試存在性；沒有比對機制時降級為快照、標盤點日期——`covered` 是宣稱、不是現狀 |
| work-log | append-only 記錄 | 時序史料 |

**漂移只發生在錯配格**：被期待最新、卻沒有機制的文件。發現一份文件跟現狀對不上時、第一個動作是分級、不是補一條「記得同步」的規則。

## 資訊住址表：每類資訊唯一權威載體

複製出去的每一份都是一個不會被履行的同步義務。每類資訊指定一個權威載體、其他位置**引用、不複製**：

| 資訊 | 權威載體 | 其他位置的形式 |
| ---- | -------- | -------------- |
| 行為（做什麼、輸入輸出、順序約束） | 測試（名稱承載意圖、assertion 承載內容） | Spec/UC 是上游來源；種子包與 feature-spec 是 scaffold 期複本、標記過期 |
| 介面形狀 | 程式碼簽名 + 型別 | Spec 介面段在實作落地後改為指涉、不逐欄複寫 |
| 為什麼（repo 內的決策脈絡） | Spec Purpose / UC 前置敘述 | 測試名稱說得出行為的意圖；work-log 記決策過程 |
| 為什麼（repo 外的事實：法規、外部契約、硬體限制） | 實作處的 doc comment | 測試可同時存在（測試守行為、註解留出處） |
| 覆蓋映射（UC 場景 ↔ 測試） | traceability.yaml | 前提是有比對機制；否則它只是快照 |

## 各 Phase 連貫性檢查點

每個 Phase 的驗收多問一組問題、目標是「覆蓋完整 + 表達目的與商業邏輯 + 無重複」：

- **Phase 0 / doc-handoff**：種子包寫入 Ticket 時、標明「scaffold：Phase 1 消費後過期、爭議以 UC 為準」。功能規格種子維持路標引用（現行設計）、不擴大成全文複製。
- **Phase 1（/spec init + validate）**：feature-spec 引用 Spec 的段落用指涉（SPEC-ID + 章節）、不整段複寫；只有「本 ticket 對 Spec 的增量決策」寫在 feature-spec 裡——它才是這份文件的固有資訊。validate 通過後、確認每個 GWT 場景都回答得出「這個行為為誰存在」（Purpose 接得上）、答不出的場景是需求缺口不是文件措辭問題。
- **Phase 2（測試設計）**：GWT 落成測試時、測試名稱要承載場景的意圖（讀名稱知道這是刻意規則、不是實作巧合）；名稱說不出意圖、回 UC 補、不是在測試旁寫敘述性註解。落成後 feature-spec 的場景區段已被消費——它與測試的後續差異以測試為準。
- **Phase 3（實作）**：註解逐則過判準（見下節）；發現 UC 沒寫的邊界、回補 UC + traceability 的 boundaries 區、**不**回改種子包與 feature-spec（scaffold 不回補）。
- **Phase 4（重構 + 收尾）**：(1) traceability 逐 entry 用實際測試檔比對——`covered` 的 entry 找不到對應測試即降回 `gap`；(2) feature-spec 標記 archived；(3) 註解掃一輪：漂移的（描述已不符現狀）修或刪、防護動機的轉測試、重複測試已守內容的刪；(4) 抽查三個測試名稱問「拿到紅燈的人讀得出為什麼嗎」。

## 註解判準（Phase 3 / 4 用）

檢視一則註解的第一個評估：**它有沒有解釋到這個行為、這個事件、或這個 flag 的商業邏輯**。有——留、並確認與現狀相符；沒有——先重新檢討寫它的動機、再決定去留：

1. **動機是防護**（怕有人改壞）：註解不參與執行、改壞當下不發聲；先問約束能不能消除（常是結構選擇的產物）、不能消除就交給一條會紅的測試、測試名稱承載「為什麼這個行為是刻意的」。
2. **動機是說明**：把型別名稱唸出來、看註解還剩什麼資訊；剩不下就刪——那是型別與命名已經講完的話。
3. **來源在 repo 外**（法規條號、外部契約、硬體限制）：這是 doc comment 的正當內容；可與測試並存（測試守行為、註解留出處）。

錯誤的註解比沒有註解更糟：它帶著權威外觀、讀者依它行動、而它不會發聲。

## 重複與割裂的判定

- **重複**：同一段敘述出現在兩份以上文件、且各份都被期待維護。修法二選一——指定權威載體其他處改引用、或把副本降級為標記過期的 scaffold。
- **割裂**：讀者要跨多份文件才能拼出一個行為的全貌。修法是讓權威載體自足（測試名稱 + assertion + reason 讀完即知道行為與意圖）、其他文件當導覽不當內容。
- **判定動作**：對任一段文件內容問兩題——「這段資訊的權威載體是誰」、「這份文件過期時誰會發現」。兩題都答不出來、這段內容就在錯配格裡。
