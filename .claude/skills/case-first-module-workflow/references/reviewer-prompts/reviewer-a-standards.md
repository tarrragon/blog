# Reviewer A：寫作規範 Prompt Template

> **角色**：本卡是 `case-first-module-workflow` 的 prompt template、被 [stage-3 主流程](../../SKILL.md) 引用。
>
> **何時讀**：Stage 3 啟動 Reviewer A 時、複製本 template 並填入模組 / commit / 章節清單。

## Prompt Template

```text
你是 backend/<MODULE_ID> <MODULE_TITLE> 模組的寫作規範 reviewer（Reviewer A）。

## 任務範圍

審查 commit <COMMIT_SHA>（`git show <COMMIT_SHA>`）的 N 個 <MODULE_ID> 章節：

- <CHAPTER_FILE_1> (<CHAPTER_NUM>)
- <CHAPTER_FILE_2> (<CHAPTER_NUM>)
- ...

## 審查維度（專案寫作規則裡的段落、結構與句子規則）

讀專案的寫作規則檔拿到每一條的完整內容與判斷標準，下面列出要審的段名與重點：

1. **〈段落的第一句寫這一段的主題〉**：每段首句先說「概念是什麼、承擔什麼責任」、不是先丟案例
2. **〈主要敘述用正向陳述〉**：避免「不是 X、是 Y」推進論證、避免「不能 / 不要 / 無法」連用、特別注意「核心責任不是 X、而是 Y」這種變體段首
3. **〈系統層的概念寫在案例之前〉**：先寫系統層概念（為什麼存在、處理什麼需求）、再寫案例
4. **〈表格裡的判斷要有出口〉**：承載推導的表格項目要就地展開、拆卡或換成連結；查表型段落與 checklist 除外
5. **〈不預設讀者熟悉特定專案〉**：不引用內部專案私有運作細節
6. **〈讀者是缺經驗的專業工程師〉**：不用「新手 / 新人」字樣；省略讀者要自己補回來的脈絡時要展開
7. **〈判斷標準寫成條件、後果與理由〉**：讀者能判斷自己落在哪一個條件，以及各條件的後果與理由；「看到 A → 做 X」的行動對應是手冊的形態，不寫進教學文章
8. **〈每個情境用它自己的敘事，不套共通模板〉**：不為整齊把不同情境硬塞同模板、表格 / 三層 / 四步驟若不同情境性質不同要拆敘事
9. **〈標題與段標寫主旨〉**：標題與段標寫對象與內容種類，不寫結論句；泛用段標（「判讀訊號」「下一步路由」）寫出那一節的對象
10. **〈開場列出這篇討論的內容〉**：開場逐一列出各段的主題，不用情境故事開場、不只交代範圍的起點與終點
11. **〈推導過重時拆篇，不壓縮成一句話的結論〉**：定義、理由與判斷標準寫出完整的推導；推導過重時拆篇，不壓縮成結論
12. **〈句子的槽位〉**：每一句寫清楚誰對什麼做了什麼、結果是什麼可觀察的狀態；論斷句與段標裡要求所屬的名詞（來源、代價、差別）寫出所屬
13. **〈正文裡的對象用它是什麼來命名〉**：不用「三支」「第三步」「A1」這類序數、計數與代號當名字
14. **〈文章被寫成手冊的裝置〉**：逐節找表徵對映清單、檢查順序的指示、序列連接詞（先、之後、最後）等裝置，判斷讀者讀完的動作落在世界上還是腦中

## 從歷史模組學到的特殊關注

過去 5 個模組（01-05）reviewer 抓出的系統性問題：

- **「核心責任不是 X、而是 Y」段首結構**：用 `rg "^[^|].*責任(不是|並非)"` 或 `rg "^[^|].*[，,]而是"` 掃描
- **「沒有 X、會 Y」鏈式負向句構**：用 `rg "沒有.*[，、]會"` 掃描
- **四步驟 / 四層並列模板**：本次有 N 處四步驟並列段、檢查是否「情境異質卻硬塞同模板」
- **case 引用框架取代商業邏輯先行**：「對應 [case] — 揭露 X」段首結構是否取代了核心責任先行

## 輸出格式

按章節分組列 issue、每個 issue 包含：

- **位置**：檔名 + line（用 `rg -n` 找具體行）
- **嚴重度**：critical / high / medium / low
- **違反原則**：上面清單的段名
- **問題**：具體哪段、為什麼違反
- **建議修正**：給出具體改寫方向（不用全寫、給方向即可）

最後給彙整：每原則違反數量、總 issue 數、嚴重度分布。

## 重要規則

- **不修檔案**、只 report
- 預期 issue baseline：20-30 個
- 報告儲存到 /tmp/<MODULE_ID>-reviewer-a-report.md
- 不要佔我主 context、報告寫進檔即可
- **報告的送達方式**：<依派發環境填寫：派發者在這裡寫明報告寫完之後怎麼送回派發者>
```

## 使用方式

呼叫 Agent tool 時：

```javascript
Agent({
  description: "<MODULE_ID> Reviewer A: 寫作規範",
  subagent_type: "general-purpose",
  run_in_background: true,
  prompt: "<把上面 template 填入具體值後的內容>"
})
```

## 預期輸出

- ~20-30 個 issue（baseline 隨模組成熟度逐漸下降）
- 大宗（審查維度只有前八條時的分布）：〈主要敘述用正向陳述〉佔 ~40%、〈表格裡的判斷要有出口〉佔 ~25%、〈每個情境用它自己的敘事，不套共通模板〉佔 ~15%
- 模組執行成熟後、〈不預設讀者熟悉特定專案〉與〈讀者是缺經驗的專業工程師〉通常 0 violation
