# Bibliography Verification

書單與法條引述寫進文件之前，逐條打開它附的連結，確認頁面上的書目欄位跟正文寫的一致。這份 skill 寫出要核對的欄位與判定、每一條連結用什麼方法打開（curl 直接抓，或用瀏覽器）、對網站的請求守哪些界線，以及查證結果的記錄方式。期刊論文的 DOI、卷期與頁碼不在這份 skill 的範圍。

每個網站用哪一種方法打開，只寫在 `references/site-registry.md` 那一張表：腳本照它分流，執行者照它知道每個網站的欄位在頁面的哪一區。

## 核對的欄位與判定

書目連結核對書名、作者（含譯者）、出版者、出版日期、版次與 ISBN。出版日期指正文寫的那個版本的出版日期，頁面上的再刷日期或另一種裝訂的上市日期不算。正文與頁面一邊寫 ISBN-10、一邊寫 ISBN-13 時，把 ISBN-10 換算成 978 開頭的 ISBN-13 再比對。版次或出版日期在書店頁上找不到時，到出版社的書目頁核對，記錄寫出取自哪一頁；出版社頁也沒有這一欄時，判「沒核對到」。

法條連結核對法規名稱、條號、項次，以及正文對那一項的轉述跟條文內容一致；記下頁面上的最新修正日期。

每一欄寫下一種判定：

| 判定     | 條件                                                                                  | 處置                                                                                                                                                                                                    |
| -------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 一致     | 執行者在頁面上看到這一欄的值，跟正文寫的相同                                          | 記下是哪一條連結、用什麼方法打開                                                                                                                                                                        |
| 不一致   | 執行者在頁面上看到這一欄的值，跟正文寫的不同                                          | 先判斷哪一邊錯，見表下的說明                                                                                                                                                                            |
| 沒核對到 | 頁面上沒有這一欄、這一欄是動態載入的、頁面打不開、被擋，或只看到搜尋結果的摘要        | 寫出原因；正文保留撰稿時的值，記錄裡寫出那個值取自哪裡                                                                                                                                                  |

不一致的時候，頁面不一定是對的一方。連結指到的版本跟正文寫的版本不同時（平裝與精裝、修訂版、電子書、另一個版次），錯的是連結：換成指到正文那個版本的連結，或在正文註明連結是另一個版本，不改正文的書目值；換連結之前，那幾欄記為「不一致」，原因寫「連結指到另一個版本」。版本以 ISBN 判斷：同一本書的不同版本與不同裝訂各有自己的 ISBN，頁面沒寫版次時也分得出來。版本相同而值不同時才改正文。法條的項次或內容跟正文不同時，先看修正日期：正文引用的是修正前的條文時，到那部法規的沿革找當時的條文核對，不把正文改成現行版本。兩個不同網站的頁面給的值互相矛盾時，不自己選一邊，把兩邊的值寫進記錄（見〈記錄〉），標明沒有判定。

一條連結的判定取它最差的一欄：有一欄不一致就算不一致；沒有不一致、而有一欄沒核對到就算沒核對到；每一欄都一致才算一致。記錄裡寫成「沒核對到」，之後的人才知道這一欄還沒有人看過頁面上的值；寫成「一致」的話，兩者在產物上看不出差別。

## 對網站的請求守的界線

- 腳本對每個網站固定送同一個瀏覽器的 User-Agent，一次執行裡每條連結只送一次；第 2 步〈用腳本分流並抓頁面〉的表指定重跑的那幾種情形，重跑時標頭不變。理由是 Amazon 對 curl 的預設 User-Agent 回 503，而它的 robots.txt 沒有禁止商品頁的路徑（robots.txt 禁止全站或商品頁路徑的網站，例如登記表裡的全國法規資料庫，即使 curl 抓得到也登記成 `瀏覽器`）；這是一個固定的設定，不是被擋之後的應變。一個網域第一次登記成 `curl` 之前，先讀它的 robots.txt，確認沒有禁止商品頁那一類路徑；禁止的話登記成 `瀏覽器`。
- 被擋之後（403、驗證頁）不換 User-Agent、不加 Referer 或 Cookie 重試；這樣重試是在繞過網站的機器人防護，這個情形的處置是改用瀏覽器。
- 瀏覽器查證只用使用者看得到的那個瀏覽器工作階段，一次開一頁。不用 headless 或反偵測的瀏覽器工具；`javascript_tool` 只讀目前這一頁的文字，不在頁面裡另外發請求。
- 同一個網站的請求之間留間隔：腳本在同一個主機名的兩次請求之間至少隔 `MIN_INTERVAL_SECONDS` 秒；瀏覽器查證也一頁看完再開下一頁。

## 流程

### 1. 抽出連結清單

從要查證的文件抽出全部外部連結，一行一條，存進 repo 以外的暫存目錄：

```bash
grep -rhoE '\]\(https?://[^)]+\)' <要查證的檔案或目錄> | sed -E 's/^\]\(//; s/\)$//' | sort -u > <暫存目錄>/urls.txt
wc -l < <暫存目錄>/urls.txt
```

`<要查證的檔案或目錄>` 填這次要查證的文件。行數是 0 時，代表路徑給錯或文件沒有用 `[文字](網址)` 的連結語法，修正之後重抽。這條 grep 只抽得到 `[文字](網址)` 這一種寫法：網址本身含右括號時會被截斷，`<https://…>`、參考式連結與裸網址抽不到；文件用了這幾種寫法時，把漏掉的網址手動補進清單。

另外清點文件裡的書目條數，跟連結數對照。沒有附連結的書目另外列出來，每一欄判「沒核對到」，原因寫「沒有連結」，記錄的計數裡寫出條數；它們不在連結清單裡，不列出來的話就不會出現在任何計數裡。

### 2. 用腳本分流並抓頁面

```bash
python3 -I <skill 目錄>/scripts/fetch_pages.py <暫存目錄>/urls.txt <暫存目錄>/pages > <暫存目錄>/fetch.txt
```

`<skill 目錄>` 填這份 SKILL.md 所在的目錄。每條連結最多花 25 秒，加上同一網站的間隔，條數多時總時間會超過 shell 單次執行的上限：連結超過 20 條時，把清單切成幾個檔分批跑（每批用自己的 `pages` 目錄），或放到背景執行。

腳本讀站點登記表，每條連結印一行 `序號|route|http|blocked|網址|title|isbn`，stderr 最後印 `fetch_pages: N url(s), C curl, B browser, K blocked, F failed`；N 要等於〈抽出連結清單〉那一步的行數。各欄的意思與 exit code 寫在腳本的檔頭。每一行依 `route`、`http`、`blocked` 三欄決定下一步：

| `route` | `http`                     | `blocked` | 代表什麼                                          | 下一步                                                                                                                                                                                                                                                 |
| ------- | -------------------------- | --------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| curl    | 200                        | no        | 頁面存在 `<暫存目錄>/pages/<序號>.html`           | 第 3 步〈核對 curl 抓到的頁面〉                                                                                                                                                                                                                        |
| curl    | 403、503，或 200 而頁面含腳本 `BLOCK_MARKERS` 的字樣 | yes       | 這個網站拒絕了 curl 的請求                        | 打開存下來的頁面確認它是驗證頁或拒絕存取的頁面，確認了就照登記表〈新增一列的條件與寫法〉把網域登記成 `瀏覽器`，這一條走第 4 步〈用瀏覽器查證被擋的連結〉；確認頁面是正常的商品頁時（字樣誤判），照第一列走第 3 步〈核對 curl 抓到的頁面〉，並把命中的字樣寫進最後給使用者的總結 |
| curl    | 429                        | yes       | 請求太密，網站要求放慢                            | 不登記成 `瀏覽器`。過一段時間（至少幾分鐘）把這幾條單獨放進清單重跑一次，標頭不變；還是 429 就判「沒核對到」，原因寫「429」                                                                                                                          |
| curl    | 401、407、451              | no        | 要登入或地區限制，連結本身可能沒有失效            | 改走第 4 步〈用瀏覽器查證被擋的連結〉；瀏覽器也要登入時，照第 4 步〈用瀏覽器查證被擋的連結〉的停點處理                                                                                                                                                                         |
| curl    | 404、410 與其餘 4xx        | no        | 連結失效                                          | 換一條指到同一本書、同一個版本的連結，只把新連結放進清單從第 2 步〈用腳本分流並抓頁面〉重跑；找不到替代連結時，這一條每一欄判「沒核對到」，原因寫「連結失效」                                                                                                               |
| curl    | 000                        | no        | 連不上；原因（DNS、逾時、TLS）印在 stderr          | 以網域為單位數：這一批有兩個以上網域，各自送出的每一條連結都是 000 時，這個環境連不到外部網站，走第 5 步〈連線不到書店時的退路〉；否則把 000 的那幾條單獨放進清單重跑一次，還是 000 就判「沒核對到」，原因照 stderr 寫                                                     |
| curl    | 其餘 5xx                   | no        | 對方伺服器出錯                                    | 把這幾條單獨放進清單重跑一次，還是 5xx 就判「沒核對到」                                                                                                                                                                                                |
| browser | -                          | -         | 登記表把這個網站登記成 `瀏覽器`，腳本沒有送出請求 | 第 4 步〈用瀏覽器查證被擋的連結〉                                                                                                                                                                                                                      |

沒有印出計數那一行，或 exit 不是 0：腳本中途中止。讀 stderr 修正後，只把 `fetch.txt` 裡還沒有結果的序號重新放進清單重跑，已經有結果的不再送一次請求；被 shell 的執行時間上限砍掉時 stderr 是空的，照上面分批或背景執行的做法重跑。

### 3. 核對 curl 抓到的頁面

`title` 與 `isbn` 兩欄只是初篩，用來排除明顯指錯的連結：`isbn` 欄收的是頁面上通過檢查碼驗證的 ISBN-13，以及緊接在「ISBN」字樣後面的 ISBN-10，依出現順序列出，上限寫在腳本的 `MAX_ISBNS`；商品頁會把推薦的其他書一起列出來，所以正文的 ISBN 出現在這一欄還不夠。打開存下來的頁面，確認正文的 ISBN 出現在登記表「頁面上取得到的欄位與抓不到的欄位」那一欄寫的書目區塊裡（例如 Amazon 的「產品詳細資訊」），再在同一區核對其餘欄位。登記表沒有這個網域時，核對完照登記表〈新增一列的條件與寫法〉補一列。

書目商品頁的 `isbn` 欄是空的時，打開頁面看它是哪一種：搜尋結果頁、缺貨頁或被轉到首頁時，照第 2 步〈用腳本分流並抓頁面〉表裡「連結失效」那一列處理；電子書頁（只有 ASIN 或電子書 ISBN）時，照〈核對的欄位與判定〉的版本判斷處理；同意牆或登入牆時，改走第 4 步〈用瀏覽器查證被擋的連結〉。法條頁與作者網站本來就沒有 ISBN，這一欄空白是正常的。

### 4. 用瀏覽器查證被擋的連結

用 `claude-in-chrome` 的工具，守〈對網站的請求守的界線〉的瀏覽器那一條：

1. `tabs_context_mcp` 取得目前的分頁狀態，再用 `tabs_create_mcp` 開一個新分頁，不沿用使用者原本的分頁。
2. `navigate` 到連結。
3. `get_page_text` 讀頁面文字，在文字裡找〈核對的欄位與判定〉列的欄位；`get_page_text` 讀不到時，用 `javascript_tool` 讀 `document.body.innerText`。
4. 核對完用 `tabs_close_mcp` 關掉這個分頁，再開下一條。

頁面出現驗證碼、要求登入或拒絕存取時停下來，把網址與畫面上看到的內容告訴使用者，由使用者自己打開；不嘗試通過驗證碼，也不替使用者登入。使用者打開之前，這一條每一欄判「沒核對到」，原因寫「瀏覽器出現驗證碼（或登入），交給使用者」。瀏覽器工具本身連不上時，這幾條同樣判「沒核對到」，原因寫「瀏覽器工具連不上」，寫進最後給使用者的總結。

### 5. 連線不到書店時的退路

第 2 步〈用腳本分流並抓頁面〉判定這個環境連不到外部網站時（雲端沙箱常常只開放部分網域），先用網路搜尋取得連結，從搜尋結果的標題或摘要找 ISBN，確認連結指到正確的書。搜尋結果不是商品頁，所以這一批每一欄都判「沒核對到」，原因寫「只看到搜尋結果，商品頁沒有打開」，即使摘要裡的 ISBN 跟正文相同。之後在連得到的環境從第 1 步〈抽出連結清單〉補做。

### 6. 查不到的事寫成否定宣告

中譯本、新版或某個欄位查不到時，寫出查了什麼：查詢詞、查過的站點、查詢的年月（「以書名與作者名在豆瓣與博客來查詢，2026 年 11 月，沒有找到中譯本」）。只寫「沒有中譯本」的話，讀者分不出是查過而沒有，還是沒查。

## 記錄

查證結果寫進這次改動的 commit message。被查證的文件所屬的集合另有記維護事項的位置時（例如目錄頁的維護段），摘要也寫進那裡。查證之後文件內容沒有任何改動時，把摘要寫進那個維護位置並提交，記錄跟著那個 commit；集合沒有維護位置時，記錄寫進最後給使用者的總結。記錄寫出下列內容，讓沒參與這次查證的人知道哪些值有人看過、在哪裡看到：

- **計數**：連結總數，分成 curl 抓了幾條、瀏覽器打開幾條，以及依〈核對的欄位與判定〉的連結判定，一致、不一致、沒核對到各幾條；沒有附連結的書目幾條。
- **每一條用瀏覽器查證的連結**：網址與頁面上讀到的值（出版者、出版日期、ISBN），因為這幾條沒有存下來的頁面可以回頭對。
- **每一個沒核對到的欄位**：哪一條連結、哪一欄、原因，以及正文的值取自哪裡。
- **兩個網站互相矛盾的欄位**：兩邊的網址與各自的值，標明沒有判定。
- **否定宣告**：第 6 步〈查不到的事寫成否定宣告〉寫下的每一則，查詢詞、站點與年月。

這次新增或改動了站點登記表的列時，`references/site-registry.md` 跟查證結果在同一次改動裡提交，版號照專案的 skill 版號規則更新。

## 範例

下面是一次虛構的查證，數字是為了示範判定與計數而設的。一份書單列了 24 本書，其中 23 本附連結。第 1 步抽出 23 行，沒附連結的那一本另外列出，判「沒核對到」。第 2 步腳本印 `23 url(s), 21 curl, 2 browser, 0 blocked, 0 failed`，兩條 `browser` 是博客來（登記表裡是 `瀏覽器`）。21 條 curl 頁面的 `isbn` 欄都含正文寫的 ISBN；打開頁面在書目區塊核對時，有一條 Amazon 頁面的「產品詳細資訊」沒有版本那一項，到出版社的書目頁找到版次、跟正文一致，那一欄判一致並記下取自出版社頁。兩條博客來在 Chrome 開新分頁讀頁面文字，每一欄都一致，關掉分頁。commit message 寫「書目 24 本：附連結 23 條（curl 21、瀏覽器 2），一致 23；沒附連結 1 本，判沒核對到」，並列出兩條博客來讀到的出版者、出版日期與 ISBN，以及那一條版次取自出版社頁。

版本紀錄在同目錄的 `CHANGELOG.md`。
