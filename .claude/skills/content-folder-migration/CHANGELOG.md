# CHANGELOG

**Version**: 1.1.0 — `--apply` 那一步多給 `--renames <暫存目錄>/renames.txt`，驗證表的 lint 改成 `bin/lint-delta --renames`：配對表直接給出每個被搬的 `.md` 的舊路徑，取代原本的 `git add -A` 加 git 改名偵測，以及低相似度改名的人工對照（`git show HEAD:<舊路徑>` 再 lint）。原因是 git 只把內容相似度 50% 以上的配對成改名，1.0.0 那一次的搬移（commit 52631aac）裡，被搬的 399 個 `.md` 有 31 個在 git 看來是一對刪除與新增。同一次 lint-delta 的比對改成抽掉連結網址與多餘空白，連結被改寫的那一行既有的問題不再算新的，訊息裡的行號（MD024）也不進比對；連續搬移照配對表的行序往回串（路徑被重用時只有行序分得出來源）；content-move 在 `--apply --manifest` 而沒給 `--renames` 時 exit 2（審查時的走查證實，連續搬移漏寫的那一次，事後用 `git ls-tree HEAD <src>` 補不回中間那一層的路徑）。「搬移之後」的 blogsearch 改成指向該 skill 的提醒列，不在這裡另寫處置。單篇改檔名的那條路：原本要求先手改 slug 再搬，審查實測這樣做時 content-move 用新 slug 算舊網址，0 個 alias、0 處連結改寫；改成由 content-move 改 slug（舊網址用改之前的 slug 算），skill 寫明不要先手改，並寫出那條路的位置檢查查哪些檔案。「不處理的情形」補兩條：`[permalinks]` 有鍵的 section 搬進子資料夾時 `cards` 報 L1（審查實跑 posts/ 搬進 posts/hands-on/ 得到 24 個 error，Hugo 的網址本身正確），這種 section 只涵蓋同一層改檔名；單篇改檔名時 `relref` 要手改。`hands-on/_index.md` 寫明在 dry-run 的警告之後、`--apply` 之前建；dry-run 檔案清單排除 `<dest>` 的 pattern 改成 `^<dest>(/|$)`，單篇的 `.md` 也排除得掉。驗證表裡兩條帶管線的指令移到表格外（儲存格裡的 `\|` 照抄進 shell 是字面的豎線）。另外修兩處既有的佔位：empty-sections 的 sed 寫成 `<src>/`（`<src>` 本身已經帶 `content/`），沒有手改時先 `touch hand.txt`。

**Version**: 1.0.0 — 新建。來源是 2026-10-27 把 `content/` 的 going-live、infra、ci、operations、monitoring 收進 `content/devops/` 的那一次搬移：`bin/empty-sections`、`bin/content-move`、`bin/alias-check` 的順序、涵蓋的搬移（資料夾收進大分類、單篇搬進 `hands-on/` 或改檔名）與交給使用者決定的其他搬移、搬移前的兩道檢查、基準值與驗證表、殘留引用的處置表（`references/residual-references.md`）。驗證表另外跑 `bin/alias-check`，依據是同一天在最小 Hugo 站（v0.148.2）的實測：alias 等於另一頁的網址時 `--printPathWarnings` 沒有輸出，該網址輸出的是那一頁本身；兩頁宣告同一個 alias 時它印 `WARN Duplicate target paths`。`mdtools cards` 依檔案路徑解析連結、不讀 aliases；它的 L1-broken-link 涵蓋全站的絕對與相對連結（在一般文章放壞連結，它報錯），所以連結檢查交給 `cards`，沒有另寫工具。那一次的殘留掃描還看不到帶 baseURL 路徑的網址與 repo 根目錄的檔案，審查時才找出漏掉的五處，之後 `bin/content-move` 改成掃全部追蹤中的檔案。
