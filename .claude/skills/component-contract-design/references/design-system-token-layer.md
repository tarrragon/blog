# Design system 與 token 層：組成、前置齊不齊、哪些值取名、分層、來源格式、Web 端的限制、檢查、寫給實作 agent 的限制

>
> **何時讀**：在 `SKILL.md`〈起手〉確認三項前置裡的「design token 層」時；要替專案新建或整理 design system、要決定 token 怎麼分層與存放時；在 step 5 要建執法工具票、或要寫給實作 agent 的樣式限制時。
>
> **簡稱查地址**：本檔出現的方法論、L2（語言與框架的實作規範）、本規格票（正在填的元件庫規格那一張票）、baseline，地址與定義查 `addresses.md`。
>
> **不在本檔**：從既有程式碼萃取 token 的順序（盤點 → 命名 → 固化）照 `foundation-design` skill 的接手模式；元件契約怎麼引用 token 照 step 3。Web 端（HTML／CSS）契約驗收另外要做的事在 `web-platform-notes.md`。

## Design system 由哪幾份產物組成

design system 指一個產品共用的樣式來源與元件集合，產物分五份，各有擁有者：

| 產物 | 內容 | 擁有者 |
|------|------|--------|
| token 層 | 具名的樣式值：顏色、字級與行高、間距、圓角、線寬、陰影、動畫時長、最小命中區 | 本檔寫建 token 層的人要交付什麼才算齊；萃取順序照 `foundation-design` |
| 元件庫 | 元件與容器的契約與實作 | 本 skill（step 1 到 step 5） |
| 元件規則 | Web 端的元件 CSS rule block 與選擇器清單（沒有原生元件邊界的平台才有這一份） | 方法論〈Web/HTML 端 L2 特別判準〉的「元件規則 SSOT」與「元件邊界的可驗產物」 |
| 使用說明 | 每個元件何時用、何時不用、對應的使用者心智模型 | 方法論〈雙向約束判準〉設計端的「元件語意標註」；寫在契約的「語意與內容角色」與「反例」欄 |
| 檢查 | 擋新的寫死值、`!important`、帶 id 的選擇器與原生元件直用的工具（本套件稱執法工具） | 本檔〈檢查：擋什麼、在哪裡擋、用什麼工具、例外怎麼寫、怎麼確認它在讀〉；Dart 專案的執法工具見 `addresses.md` |

只有 token 層而沒有元件庫時，各頁的實作者仍會替同一個語意組出不同的組合（同樣引用 token，兩個頁面的按鈕內距不同）；只有元件庫而沒有 token 層時，實作的人在每個元件各寫一份同一個設計決定的字面值。兩者缺一，就達不成方法論〈雙向約束判準〉設計端的「樣式收斂」。

視覺方向（字型、色彩世界、整體風格）與它的說明文件不在這五份裡：專案另外用 `impeccable` 這類設計 skill 產生 DESIGN.md 時，那一份決定 token 的值該是什麼，本檔決定這些值怎麼取名、怎麼分層、存在哪一份來源檔、怎麼檢查；兩者的對照見〈來源格式：平台原生寫法或 DTCG 檔〉末段。

## 前置「design token 層」齊不齊的判定

`SKILL.md`〈起手〉前置表的「design token 層」照下表判。前三列（每一類都有具名值、名字依用途或階命名、單一定義位置）任一不成立，照前置表建 `foundation-design` 的前置票（token 層的前置票）、設為本規格票的 blockedBy；只有「有檢查擋新的寫死值」不成立時，不擋本規格票，建執法工具票（建立〈檢查〉那道檢查的票），設為 step 5 每一張遷移票的 blockedBy。

| 項目 | 判定問句 | 不成立時，填契約的人會遇到什麼 |
|------|---------|------------------------------|
| 每一類都有具名值 | 契約會引用的每一類樣式值（上方〈Design system 由哪幾份產物組成〉表的 token 層那一列），各有至少一組具名常數嗎？ | 尺寸契約、組合規則與無障礙的命中區填不出 token 名，只能填字面值；之後改值要逐元件找 |
| 名字依用途或階命名 | 名字讀得出用途（`text-body`、`link-fg`）或它在階裡的位置（`size-md`、`teal-500`）嗎？ | 名字寫的是值（`gray-16px`）時，改值之後名不副實，契約引用的名字跟畫面上的值對不上 |
| 單一定義位置 | 改一個 token 的值時，要改幾個地方？ | 超過一處就還不是 token；元件契約引用的名字在兩處各有一個值，哪一個生效依載入順序而定 |
| 有檢查擋新的寫死值 | 有沒有一道檢查在提交或 CI 時報出新寫的字面值？它的正對照（positive control：餵進已知會違規的輸入，確認檢查確實讀到要檢查的對象）跑過嗎？（〈檢查：擋什麼、在哪裡擋、用什麼工具、例外怎麼寫、怎麼確認它在讀〉） | 契約寫了 token，實作照樣可以寫死值，不會有任何訊號；下一次調整的人寫的 15px 留在程式碼裡 |

**判定紀錄**：四列的判定寫進本規格票，每一列附可以重跑的依據，判成立的也寫。第一列列出契約會引用的類別與每一類對到的 token 名；第三列寫出查字面值的指令原文與命中數（例如抽三個 token，用 `rg -n '<值>' <樣式目錄>` 查同一個值在 token 檔以外出現幾處）；第四列寫出檢查的指令原文與它印出的讀取數、違規數，以及正對照的那一次（見〈檢查〉的確認那一段）。

**判錯的代價**：把「有一份 token 檔」當成「單一定義位置」成立。token 檔存在而元件裡仍散著同樣的字面值時，改 token 不會改到那些元件；判定的人要數的是改值時要改幾處，不是檔案存不存在。沒有判定紀錄時，四列都判成立與實際查過，在本規格票上看起來一樣。

## 哪些值寫成 token：數設計決定，不數出現次數

一個值寫成 token 換到的是改它時只改一處、用到它的位置一起變；付出的是讀程式碼的人多讀一層名字。判斷時數的是設計決定：同一個值在兩處代表不同的決定時（同樣是 16px，一處是內文字級、一處是間距），寫成兩個 token。依屬性分四種處置：

| 屬性 | 處置 | 理由 |
|------|------|------|
| 顏色、字級、行高 | 即使只用一次也寫成 token | 這是配合〈檢查〉的選擇：本檔的檢查依寫法擋（凡是 `color` 寫了色碼就報），數不出一個值代表幾個設計決定，所以這幾類一律取名。專案改用 baseline 收下既有的一次性值、或在審查時逐處判斷時，這一列可以照第二列處理，代價是檢查擋不住新寫的一次性色碼 |
| 間距、圓角、線寬、動畫時長，以及用在兩處以上的版面尺寸 | 同一個設計決定出現兩處以上時寫成 token | 只出現一次的值取名之後，要改時仍只改一處，換到的只有多一層名字 |
| 只用一次的版面尺寸 | 留字面值 | 不構成共用的決定 |
| 斷點 | 留字面值，在旁邊註明原因 | Web 端 media query 的條件寫不了 `var()`，見〈Web 端的限制〉；別的平台的斷點取得到常數時，照第二列處理 |

**判錯的代價**：依出現次數判，會把同值而不同決定的兩處合成一個 token；之後調整其中一個用途時，另一個一起變，沒有任何錯誤訊息。

## 分層：兩層的條件、一層就夠的條件、元件層

token 常分兩層，兩層調整的範圍不同：

- **primitive token**（階）：只放值，名字描述它在階裡的位置（`size-md: 16px`、`teal-500`）。元件規則不直接引用這一層。
- **semantic token**（用途）：用用途命名，值引用 primitive token（`text-body → size-md`）。元件規則只引用這一層。

整體調整某一階（16px 全部改 17px）時改 primitive；單獨調整某一種用途（只有說明文字大一點）時，改那個 semantic token 對到哪一階。手機版的字級也寫成「同一組 semantic token 在手機寬度下對到另一階」，元件規則裡不各自寫手機字級。

| 條件 | 處置 |
|------|------|
| 有整階一起調整的需求，而且至少有一階被兩種以上的用途引用 | 兩層：整階調整時只改一個 primitive，不必逐一改引用它的每個用途 |
| 有主題切換（亮色與暗色、多品牌），或要把可用的值限定在一組階上 | 兩層：每個主題只改 semantic token 對到哪一階，值不會離開那組階；跟〈來源格式〉的 Resolver 那一點一起看 |
| 有整階一起調整的需求，但每一階都只有一種用途引用，也沒有主題切換 | 一層用途命名的 token：整階調整時要改的用途只有一個，多一層換不到任何一種調整 |
| 沒有整階一起調整的需求，也沒有主題切換 | 一層用途命名的 token，加一張記錄哪幾種用途同級的表；同級表讓之後出現整階調整的需求時，查得到要一起改哪幾個用途 |
| 某些元件要讓主題或嵌入它的宿主頁面（host page，元件庫被放進去的那個頁面）個別覆寫（第三方嵌入的小工具、多品牌各自調按鈕） | 另加元件層 token（`button-primary-bg → link-fg`），只替要開放覆寫的元件建 |
| 元件之間的差異已經由變體表達（primary／danger） | 不建元件層；變體的外觀直接引用 semantic token，元件層只會多一層同義的名字 |

層數是依「要開放哪幾種範圍的調整」推出來的結果，不是預設值：「token 一律三層」會讓用途少、沒有主題的專案裡，讀程式碼的人每個值多讀兩層名字，而換不到任何一種調整。

**判錯的代價**：只有一層而名字是值時，整階調整之後名字錯；只有一層而名字是用途時，整階調整要逐一改每個用途，每個主題各寫一組字面值時值也可能離開色階。這幾種都不報錯，在改第一次值或加第二個主題的時候才暴露。

## 來源格式：平台原生寫法或 DTCG 檔

token 的來源檔要有單一份。選哪一種看讀取端有幾個：

| 讀取端 | 來源檔 | 代價 |
|--------|--------|------|
| 一個平台（只有網頁的 CSS，或只有一個 Flutter App），沒有設計工具要讀 | 平台原生的寫法就是來源：一份 CSS 自訂屬性（custom properties）檔、一份主題常數檔；用 utility class 框架時是它的設定檔 | 之後出現第二個讀取端時，要轉成交換格式；名字與分層照搬即可 |
| 兩個以上的平台，或設計工具（設計軟體的 token 外掛）要讀寫同一份值 | DTCG 格式的 JSON 檔當來源，各平台的檔案由轉換工具產生，產生的檔案開頭註明不要手改 | 多一道建置步驟與一種表示法；產生的檔案被手改時，下一次建置會蓋掉那次修改 |

DTCG 格式是 W3C Design Tokens Community Group 的 Design Tokens Format Module（2025.10 是第一個穩定版，2025-10-28 發布，與 Color、Resolver 兩個 module 同時發布；三份都是社群小組的最終報告，不是 W3C 標準）。照它寫來源檔時要知道的幾件事：

- **結構**：帶 `$value` 的物件是 token，不帶的是分組（group）；`$type` 寫在分組上時是組內 token 的預設型別；引用寫成 `"{color.teal.500}"`，或用 `$ref` 寫 JSON Pointer；引用不能形成循環。規格建議的副檔名是 `.tokens` 或 `.tokens.json`。
- **規格不定義分層**：分組由作者任意劃分，規格寫明工具不應（SHOULD NOT）從分組推斷 token 的型別或用途；primitive 與 semantic 是兩個分組加上引用，分層照本檔〈分層：兩層的條件、一層就夠的條件、元件層〉由專案自己決定。
- **值的寫法**：`dimension` 是 `{ "value": 16, "unit": "px" }`，單位只能是 `px` 或 `rem`；`color` 是 `{ "colorSpace": "srgb", "components": [...], "hex": "#rrggbb" }`，`hex` 是選填的備援。`em`、百分比、`vw` 與 `calc()` 寫不成合法的 dimension，這些值留在平台端手寫。穩定版之前的草稿把值寫成字串（`"16px"`），轉換工具支援哪一版要先確認。
- **主題**：亮色與暗色、品牌、密度這類情境切換寫在 Resolver Module 的 `.resolver.json`：`sets` 列共用的 token，`modifiers` 列每種情境各自疊上的 token，`resolutionOrder` 決定疊加順序。
- **輸出不在規格裡**：轉成 CSS 自訂屬性、平台常數的是轉換工具（Style Dictionary、Terrazzo 這類）；引用要輸出成 `var()` 保留關係、還是輸出解析後的值，依工具而定（Style Dictionary 用 `outputReferences` 設定）。輸出成 `var()` 時，執行期覆寫 primitive 的寫法照〈Web 端的限制〉的「覆寫 primitive 的位置」。
- **來源檔有兩種寫入者時**：設計師在設計工具裡改值、工程師在 repo 裡改名字或分層時，寫明哪一方的修改以哪一個檔為準、另一方怎麼同步（例如設計工具的外掛提交 PR 到來源檔，工程師審查後合併）；整理 CSS 或比對畫面的期間，來源檔固定在同一個版本。

**DESIGN.md 這類設計說明檔**：專案用設計 skill 產生 DESIGN.md（含 token 的 frontmatter）時，它有自己的讀取端，等於多一個讀取端。照上表第二列處理：選一份當來源（DTCG 檔或 DESIGN.md 的 token 區），另一份由它產生或逐值對照，寫明哪一份是來源。取名與分層的規則照本檔；設計 skill 寫的「不必每個值都取名」這類建議跟本檔〈哪些值寫成 token：數設計決定，不數出現次數〉第一列衝突時，照本檔，並在專案的 L2 寫出這個選擇。

**判錯的代價**：替兩個讀取端各自手寫一份 token。兩份會分別被修改，第一次漂移通常要到兩端畫面並排比對才看得到。

## Web 端的限制

CSS 自訂屬性在下面第一個位置寫不了 `var()`，實作的人在那裡留字面值，並在旁邊註明原因；其餘幾條是容易用錯的位置，各有用 token 的寫法，不算可以留字面值的例外：

- **media query 的條件（寫不了 `var()`）**：`@media (max-width: 599px)` 的條件裡寫不了 `var()`。來源是手寫的 CSS 時，在 token 檔裡另記一份斷點值的對照；來源是 DTCG 檔時，斷點寫成來源檔裡的 token，CSS 的 media query 留字面值，同一行的允許註解寫出它對應的 token 名，不在產生出來的檔裡手記（下一次建置會蓋掉）。兩處要一起改。
- **定義元素的外面**：token 定義在元件根元素（`.app-root`）上時，靠繼承傳給子孫；根元素外面的元素（頁面的 `body`、掛在 `body` 底下的彈出層、宿主頁面的其他區塊）取不到。要在那些元素上用的 token 定義在 `:root`，或在那個元素上重新定義。
- **覆寫 primitive 的位置**：semantic token 寫成 `--text-body: var(--size-md)` 時（手寫的 CSS 與轉換工具保留引用的輸出都是），`var()` 在宣告 `--text-body` 的那個元素上就代換成值，子孫繼承的是代換後的結果。執行期覆寫 primitive 要寫在宣告 semantic token 的那個元素上（通常是 `:root` 或元件根元素），semantic token 才會跟著變；在子孫元素上（局部主題的 class）覆寫 `--size-md`，`--text-body` 不變也不報錯，要在那個子孫元素上連同 semantic token 一起重新宣告。
- **跟宿主頁面的名字相撞**：元件庫嵌在別人的頁面裡時，宿主也可能定義 `--text-body`。token 名加上元件庫自己的前綴（`--app-text-body`）。
- **JavaScript 要用同一個值時**：用 `getComputedStyle(根元素).getPropertyValue('--app-offset')` 讀，不在 JavaScript 裡再寫一份字面值。讀回的是 token 原本寫的字串：token 寫成 `1rem` 時 `parseFloat` 得到 1，寫成 `calc()` 時得到 `NaN`，兩種都不報錯。token 不是 px 時，改讀套用這個 token 的元素的計算後長度，或用 `@property` 把它註冊成 `<length>`；讀值的元素要在 token 的定義範圍裡。

## 檢查：擋什麼、在哪裡擋、用什麼工具、例外怎麼寫、怎麼確認它在讀

**擋的寫法**依屬性判，跟〈哪些值寫成 token：數設計決定，不數出現次數〉表的第一列對齊：

- 任何宣告帶 `!important`。
- `font-size`、`line-height` 寫 `px`、`rem`、`pt`。
- 任何宣告的值裡有色碼（`#…`）或色彩函式（`rgb()`、`hsl()`、`oklch()` 這類）；色名也擋，`transparent`、`currentColor`、`inherit` 放行。
- 帶 id 的選擇器（Stylelint 的 `selector-max-id: 0`）。
- 兩層的專案另外擋兩項：元件規則引用 primitive token（`var(--<primitive 的前綴>…)`），以及 semantic token 的定義值不是 `var()` 引用。這兩項讓「元件只引用 semantic token」由檢查驗，不靠 prompt。

token 的定義本身（屬性名以 `--` 開頭的宣告）寫字面值，不套前三項。間距、圓角、線寬、動畫時長這類「出現兩處以上才取名」的屬性，檢查依寫法分不出該不該取名，不擋；這一類由審查或派發時的清單驗（〈寫給實作 agent 的樣式限制〉）。

**在哪裡擋**：寫死的樣式值不只出現在 CSS 檔的宣告裡。每一個位置寫出用什麼工具檢查；沒有工具涵蓋的位置，寫成「沒有量過」：

| 位置 | 檢查方式 |
|------|---------|
| CSS 檔（含前處理器編譯後的產物） | 下面〈工具〉表的 lint 或腳本 |
| markup 的 `style` 屬性 | 掃模板與 HTML 的 `style=`（`rg -n 'style="' <模板目錄>`），或模板 lint |
| JavaScript 設定樣式的呼叫（`el.style.color =`、`setProperty`）與 CSS-in-JS 的樣板字串 | ESLint 這類 JavaScript lint 的規則，或掃 `\.style\.` 與 `setProperty` |
| utility class 字串（Tailwind 這類） | 檢查 class 字串本身（任意值 `w-[13px]`、`!` 前綴產生的 `!important`），用框架的 lint 外掛；不檢查編譯後的 CSS，那份產物裡的值都是展開後的字面值 |

**工具**：

| 寫法 | 適用 | 限制 |
|------|------|------|
| 以 CSS parser 為基礎的 lint（Stylelint：`declaration-no-important` 擋 `!important`；`color-no-hex` 只擋色碼；色彩函式另用 `function-disallowed-list` 列出 `rgb`、`rgba`、`hsl`、`hsla`、`oklch` 這些函式；`color-named` 擋色名；字級單位用 `declaration-property-unit-allowed-list`；id 用 `selector-max-id`） | 預設選這一種 | 要寫設定檔，規則要逐一對到上一段的每一種寫法；這幾條規則也會檢查 `--` 開頭的宣告，token 檔要用 `overrides` 或 `ignoreFiles` 另外處理，否則 token 的定義會被報出。它的報告只列違規，印不出「讀了幾個宣告」，要另外包一層（例如用 PostCSS 的 `walkDecls` 數受檢的宣告、受檢檔數是 0 時用另一個 exit code 結束）；允許註解用它認得的格式（`/* stylelint-disable-line <規則名> -- <原因> */`） |
| 專案自寫、逐行比對的腳本 | 檔案是每行一條規則的手寫 CSS，要擋的寫法很少 | 讀得到哪些宣告依實作而定：例如只取每一行最後一個 `{` 之後的內容的腳本，餵進壓縮成一行的 CSS 時只讀到最後一條規則。Sass 這類前處理器的原始檔裡，`$brand: #123` 不是 CSS 宣告、`color: $brand` 沒有色碼，兩行都不會被報出，要檢查編譯後的產物 |
| utility class 框架（Tailwind 這類）的設定檔 | 值只開放設定檔裡的 token | 任意值語法繞過設定檔，照〈在哪裡擋〉表的 utility class 那一列另外擋；同一串 utility 在幾個頁面重複出現時，元件規則沒有單一來源，照方法論〈Web/HTML 端 L2 特別判準〉的「元件規則 SSOT」抽成元件 |

**既有違規的 baseline**：接手的 CSS 已經有違規時，檢查一上線就讓每一次改到舊檔的提交都過不了。先把既有違規記成 baseline（白名單，或「違規數不得多於 baseline」），檢查只報新增；baseline 怎麼逐批縮減照 step 5 遷移票的 acceptance。

**例外**：同一行寫允許註解，格式用工具認得的那一種（自寫腳本可以自訂，例如 `/* lint-allow: <原因> */`），原因寫成下一個人判得出該不該信的一句。下面三種是預設的例外種類；專案的 L2 規範列了自己的例外清單時以 L2 為準，沒有列時照這三種。這三種寫進 L2 時，連同「什麼時候可以改寫掉」一起寫：

- `[hidden] { display: none !important }` 要蓋過每一條設定 `display` 的規則。設定 `display` 的規則都在同一份 CSS 時，改寫成條件反轉（顯示的規則加 `:not([hidden])`），不必保留 `!important`；分散在很多份 CSS 或有第三方元件時保留，加允許註解。
- 全站的減少動態效果重設（`*` 上的 `animation-duration` 帶 `!important`）要蓋過現在與以後的每一條動態規則。動態規則都在同一份 CSS 時，改寫成條件反轉（動態規則包進 `prefers-reduced-motion: no-preference`）；分散在很多份 CSS 或有第三方元件時保留，加允許註解。
- media query 的條件裡的斷點值（〈Web 端的限制〉第一條）。

實作 agent 新增允許註解時，原因要對到其中一種；審查的人退回對不到的註解。

**`position: absolute`**：不列進預設要擋的寫法，因為疊層的容器、視覺隱藏的無障礙寫法都要用它。元件的絕對定位只出現在排列不變式宣告為疊層的容器裡（step 3〈容器元件另答排列不變式三項〉）；專案要機械地擋時，在 L2 加一條帶允許註解的規則，允許的位置寫成那幾個容器。

**確認檢查在讀**：檢查回報「0 處違規」有兩種成因，目標確實不存在，或檢查沒有讀到要檢查的宣告。所以：

1. 檢查印出「讀了幾個宣告、幾處違規」，一個都沒讀到時用另一個 exit code 結束，跟「讀到而 0 違規」分開。
2. 拿一份已知會違規、而且跟受檢檔同一種形式的輸入跑一次正對照：重構前的舊檔是現成的選擇。用未壓縮的手寫 CSS 當正對照，證明不了檢查讀得懂壓縮過的 CSS。
3. 受檢的檔案有幾種語法形式（一行一條規則與一行多條規則；色碼、色彩函式與色名），每一種各放一個正對照；沒有放的那幾種，檢查的 0 只代表沒有量過。
4. 正對照的指令原文與它印出的讀取數、違規數，每一種語法形式一行，寫進執法工具票（或 commit message）；只寫「跑過了」不算。
5. pre-commit 檢查 staged 的內容（`git show :<路徑>` 取出），不檢查工作樹裡還在改的版本。

**判錯的代價**：檢查只印違規清單、不印讀到的數量時，路徑寫錯、glob 沒有匹配、檔案格式讀不懂，都印出跟「全部合規」相同的空清單；這個 0 會被當成通過，之後新寫的寫死值不會被任何檢查報出。

## 寫給實作 agent 的樣式限制

「只能用 token、不准寫死值、不准 `!important`」寫在 prompt 裡是限制的說明，不是驗收：agent 對照規則檔自查一次，查到的是它記得的那幾條。派發的人跑〈檢查：擋什麼、在哪裡擋、用什麼工具、例外怎麼寫、怎麼確認它在讀〉的工具，依它印出的計數驗收。派發時寫進 prompt 的是：

- token 來源檔的位置（用 DTCG 時寫來源檔，產生出來的檔不改），以及〈分層：兩層的條件、一層就夠的條件、元件層〉決定的引用規則（元件只引用 semantic token；兩層的專案由檢查驗）。
- 允許註解的格式與例外種類（〈檢查〉的例外那一段，或專案 L2 的清單）；新增允許註解要寫出對到哪一種。
- 檢查的指令原文；驗收的人看它印出的「讀了幾個宣告、幾處違規」，不看 agent 自述「已遵守」。這個計數只涵蓋〈檢查〉擋的寫法：間距、圓角、線寬、動畫時長另外驗收，agent 列出這次新寫的每一個這類字面值與不引用既有 token 的理由（只出現一次，或缺 token 而建了前置票），驗收的人拿 `git diff` 核對這份清單。
- Web 端的票另外照 `web-platform-notes.md`〈限定改動的範圍，不等於限定影響的範圍〉寫影響範圍的驗收。
- 缺 token 時的處置：照方法論〈雙向約束判準〉的「缺件前置範圍擴充」停下來、建 token 層的前置票，不在元件裡就地寫一個值。
