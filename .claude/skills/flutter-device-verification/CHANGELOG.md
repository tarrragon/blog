# flutter-device-verification 版本紀錄

新到舊。版號規則與兩個住址（本檔與 `SKILL.md` frontmatter 的 `metadata.version`）見專案的 skill 同步規範。

**Version**: 1.3.0 — `references/profile-measurement.md` 依多輪審查改寫：檔頭改成〈何時讀〉並寫出不適用的情境（含資料不在 SQLite 的 APP）；資料保全的要件改成查得到的事實（`pm path` 有輸出就做，執行者自認是測試機不算），備份集是 APP 的全部檔案（去掉快取），拉回與推上手機時保留相對路徑，暫存檔放在 `<暫存目錄>/measure/`；新增〈第二次以後的量測〉（保全只做一次，重量前先裝上能 `run-as` 的版本）；`watchPerformance` 固定用 16 ms 預算的陷阱與刷新率的讀法；還原前先確認設備仍在、裝回原版本用另一份 git worktree 建、刪掉不在清單裡的 `-wal`／`-shm`／`-journal` 與量測新建的檔、還原後逐檔比雜湊再比內容、原值不在檔裡時停下來問；release 版與 `unknown package` 的處置；新增〈開始之前：設備與變數〉（序號、applicationId 與 APP 資料目錄寫進暫存目錄的 `env.sh`，每次呼叫先 source；含引號的遠端指令整串交給 `adb shell`，原本的 `find` 照寫在手機端會語法錯誤）；資料保全先記下使用者原本裝的版本並檢查 `run-as` 可用，列出 APP 的全部檔案與資料庫檔並存成清單（不照 `databases/` 猜，資料庫清單是空的就停下來問，資料庫以外的檔也要保），備份前先停 APP、拉回的檔跟手機上的原檔比對雜湊、記下目錄與檔案的權限，內容清單的查詢存檔並固定排序，手機端的還原檔放在專屬子目錄，清資料的檢查與刪除分兩次執行、刪除前比對手機上的檔仍等於備份、`rm` 用絕對路徑，寫出跟〈會寫入資料的點按〉的範圍差別，步驟之間改用步驟名引用；新增〈跑量測〉（指令、逾時、成敗的讀法、`Uninstalling old version` 時重做放入檔案）；`flutter drive` 失敗或中途停掉時不依賴 APP 還在；唯讀模式會不會寫入 `-shm` 文件沒有說明，所以內容清單一律開副本；螢幕常亮的原值寫進暫存檔；不碰手機的理由改成系統手勢讓 APP 進背景（觸控被攔下是推論）；陷阱表的引言分成產出錯數字與卡住兩種，`autoDispose` 標明是 Riverpod，DDS 的成因標成推論；成本模型更正：Mac 上的背景 isolate 只重現往返次數、驗收數字在實機量，拿掉換 drift 之前的 1,000 本對照，起伏改寫成同一次執行裡也要重複量；50 ms 計時器寫出取值的理由；還原改成不論 APP 在不在都裝回使用者原本的版本（留在手機上的是量測版）、用 `pm path` 確認、重裝之後先不開 APP、先停 APP 再刪殘留的 `-wal`／`-shm`、權限照備份時的紀錄、還原後的資料庫拉到 `backup/` 以外的目錄再比對、比對不同時先確認備份雜湊再重做、仍不同時請使用者先不要開 APP、清掉專屬子目錄裡的副本。SKILL.md 的觸發詞 `integration_test` 收窄成 `integration_test 效能量測`，profile 那一條路寫明不走截圖的〈前置〉與流程。

**Version**: 1.2.0 — `references/profile-measurement.md`〈跑之前：資料保全〉更正：`flutter drive` 跑完（測試通過或失敗）時解除安裝 APP；原本寫「被中斷時也一樣」，實測中途停掉的那一次 APP 還在，改成寫出實測並提醒不要依賴。

**Version**: 1.1.0 — 新增 `references/profile-measurement.md`：在 Android 實機以 profile mode 跑 `integration_test` 量效能時，跑之前的資料保全（`flutter drive` 結束時會解除安裝 APP 連同資料；備份全部資料庫檔與雜湊、用唯讀模式從副本產生內容清單、手機上也放一份還原檔、會寫入的量測先清掉資料庫）、手機與主機的狀態（螢幕常亮的設定與改回、量測期間不碰手機、不清 Gradle 快取騰空間）、量測本身的陷阱（`enterText` 要先 `testTextInput.register()`、`semanticsEnabled: false`、`autoDispose` provider 要有監聽者、背景期間不 `pump`、`traceAction` 要 `--no-dds`、每個動作後斷言狀態、逾時訊息帶出狀態）、量對成本模型（資料庫用正式的執行器、主執行緒卡頓用計時器量、對照組放在同一次執行），以及跑完之後的還原與逐行比對。來源是一個 Flutter 書庫 APP 在 Samsung SM-S9010 上量 5 萬本與匯入 5 萬本的十幾次量測。SKILL.md 加路由與觸發詞。

**Version**: 1.0.0 — 初版。來源是一個 Flutter APP 版型改版時，在 Android 實機（Samsung，三鍵與手勢導覽）與 iPhone 16 模擬器上拍了十幾輪審查證據：`scripts/drive.dart` 經由 VM service 在執行中的 APP 裡換頁、點按、長按、拖曳捲動、返回與輸入，並讀出裝置像素比（`dpr`）（在 isolate 的根函式庫裡求值；文字引數先跳脫再嵌入求值的字串，座標引數先驗證）；`scripts/drive.sh` 包住它，負責等待動畫（`WAIT` 可調）、喚醒螢幕、截圖（動作失敗時不截）與在截圖當下把 APP 的 commit 和工作樹雜湊記進 `SHOT_LOG`（APP 不在 git 底下時記成 `no-git` 並警告）；`scripts/montage.sh` 把一組截圖拼成總覽。SKILL.md 寫出前置檢查，以及啟動並寫好 `env.sh`（等待迴圈有上限並印出停下的原因；兩台設備各用一個子目錄放 pid、log 與 `env.sh`）、列出要拍的狀態（`states.md`，一行一個截圖路徑，檔名帶設備、亮暗、字級與導覽方式）並記下設備設定、操作與截圖（`back` 不是系統返回鍵）、熱重啟（偵測編譯錯誤；原生碼與拿掉系統列宣告時改成重新執行；`--dart-define` 與被 gitignore 的設定檔不在雜湊裡，靠改動紀錄分前後；每次改動記一行並照 component-contract-design 標出待重拍的行）、看圖（貼著下緣的狀態裁出導覽列）、還原（每一批開拍前與收尾各拍一次計數畫面比對）、逐行回填交付紀錄（已拍、未驗（模擬器：成因）、未拍（原因）、使用者驗；拍在最後一次改動之前的圖不算已拍）與收尾的流程，前置另寫加 `vm_service` 依賴之前先問使用者、只在 macOS 主機上實測，以及不照做會出的錯；`references/device-pitfalls.md` 收症狀與處置（螢幕鎖上、連線中斷、動作送得太密之後不再換頁、點到暗幕、返回鍵連對話框一起關、type 求值失敗或寫錯輸入框、模擬器預設不出現螢幕鍵盤、模擬器沒有相機、Samsung Edge Panel、熱重啟之後畫面沒變、系統列設定沒有回到預設、Gradle 快取損壞）、會寫入資料的點按，以及設備設定的還原（Android 深色模式、導覽方式與字級，iOS 模擬器外觀與字級）。
