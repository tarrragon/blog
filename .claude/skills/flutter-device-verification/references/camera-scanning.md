# 相機掃描的實機驗證：使用者掃、agent 看 log，短暫的畫面自動截圖

> **何時讀**：要在 Android 實機上驗證相機掃描（條碼、QR code）的辨識率、掃描之後的流程，或掃描頁上只出現一下子的畫面（提示、說明列），而對準條碼這個動作只能由人拿著設備做的時候。SKILL.md「啟動 APP」那一步之前就要讀〈開始之前：使用者的資料〉。〈短暫出現的畫面：輪詢狀態，出現時自動截圖〉與〈不寫入資料，叫出寫入之後才出現的畫面〉兩節跟相機無關，驗任何短暫出現的畫面、或寫入之後才出現的提示列（SnackBar）時也照做。截圖與熱重啟的基本流程照 SKILL.md；本檔寫的是相機掃描多出來的分工與做法。
>
> **不適用**：iOS 實機。`drive.sh shot` 在 iOS 只支援模擬器（`simctl`），模擬器沒有相機；本檔的做法也只在 Android（Samsung SM-S9010）上實測過，mobile_scanner 在 iOS 上的回報行為也跟 Android 不同（見〈用讀取序列模擬採用規則〉末段）。

下面的 `$D`、`$S` 是 SKILL.md「啟動 APP，取得 VM service 位址，寫好 `env.sh`」那一步在 `env.sh` 裡定義的（`drive.sh` 的完整路徑、截圖目錄），每次呼叫先 `source <暫存目錄>/env.sh`。`states.md` 指 SKILL.md「列出要拍的狀態」那一步建的 `<暫存目錄>/states.md`。

**判定要留下材料**：本檔裡每一個會讓後續動作變少的判定（`pm path` 沒有輸出、`Uninstalling old version` 零命中、讀取序列是空的、計數沒變、某個號碼是同一件物品上真的條碼、套件的回報條件是什麼、某支函式只負責顯示、標成「使用者驗」），交付紀錄裡附上第三方重跑得出同樣結果的材料：指令與它存下來的輸出檔路徑、程式碼的 `<檔>:<行>`，或使用者的原話。只寫結論的判定，跟沒有判定在紀錄上分不出來，審查的人會把它當成沒做。

## 開始之前：使用者的資料

使用者拿自己的設備掃時，掃描流程的面板上有寫入資料的鍵（例如掃到 APP 資料裡沒有的條碼時出現的「加入」），使用者可能會按。所以在 SKILL.md「啟動 APP」那一步之前，先判斷設備上有沒有這個 APP 的資料，有就先備份：`flutter run` 之後再停 APP 會斷掉 debug 連線，而 `flutter run` 安裝失敗、設備上又已經裝了這個 APP 時（例如簽章不同），會先解除安裝再裝（flutter_tools `lib/src/android/android_device.dart` 的 `installApp`，log 印 `Uninstalling old version...`），備份晚了，做錯的代價是使用者的資料沒了。

1. **建變數**：照 `profile-measurement.md`〈開始之前：設備與變數〉建它的 `<暫存目錄>/measure/env.sh`（序號從 `adb devices` 讀，`applicationId` 從 APP 的 `android/app/build.gradle` 或 `build.gradle.kts` 讀，含 flavor 的 `applicationIdSuffix`，以及 APP 資料目錄），再 `source` 它。
2. **判斷要不要備份**：跑 `"${ADB:-adb}" -s "$ANDROID_SERIAL" shell pm path "$APP_ID" > <暫存目錄>/measure/pm-path.txt; echo "exit=$?" >> <暫存目錄>/measure/pm-path.txt`，再把套件名換成 `android`、輸出換成 `<暫存目錄>/measure/pm-path-android.txt` 跑一次當正對照（一定有輸出）。正對照有輸出、`pm-path.txt` 沒有路徑時，設備上沒裝這個 APP，跳過第 3 步；有路徑時，裡面可能是使用者的資料，做第 3 步。執行者自認「這是測試機」不算跳過的理由。
3. **備份**：照 `profile-measurement.md`〈跑之前：資料保全〉做〈記下使用者原本裝的版本〉（含 `run-as` 檢查；回 `package not debuggable` 時停下來問使用者）到〈在手機上也放一份還原檔〉這五步，後兩步產生的內容清單與手機上的還原檔是還原時要用的。〈清掉 APP 的資料〉與〈放入 APP 要讀的檔案〉不做：掃描驗證不跑 `flutter drive`，也不在使用者的資料上換資料。

啟動之後，照 SKILL.md 第 1 步等到印出 `ready`，再跑 `grep -c 'Uninstalling old version' <暫存目錄>/flutter.log`，把印出的數字記進交付紀錄。不是 0 時停下來：`flutter run` 已經解除安裝舊版，資料跟著刪了；照 `profile-measurement.md`〈跑完之後：還原〉的〈把還原檔放回去〉與〈逐行比對內容〉放回備份，再跟使用者確認。是 0 時，照 SKILL.md「列出要拍的狀態」那一步截 `count-before.png`，記下資料筆數；這一批只截這一次，後面各節不重截。

agent 每次做會寫入資料的操作（點寫入鍵、`eval` 呼叫會寫入的函式）之前與之後，各跑一次 `wc -l < <暫存目錄>/flutter.log`，兩個行數與操作內容寫進 `<暫存目錄>/write-ops.txt`。收尾時截一次 `count-after.png` 比對；有做第 3 步時，另外照〈跑完之後：還原〉〈逐行比對內容〉的做法拉一份副本跑 `content-queries.sql`，跟 `content-list.txt` 比對，因為計數抓不到修改既有的資料與一增一刪。計數或內容變了時，拿 log 裡寫入紀錄（`add`、`update`、`delete` 這類字樣）的行號對照 `write-ops.txt` 的區間分出是誰寫的；APP 沒有記寫入的 log 時，把差異與 `write-ops.txt` 列給使用者，直接問：

- **落在 agent 操作的區間裡**：照 `device-pitfalls.md`〈會寫入資料的點按〉的誤寫處置。
- **不在任何 agent 操作的區間裡**：使用者在驗證期間自己按的，不照那一條刪，本檔這一條優先。把寫入的時間與對象給使用者，問是不是自己做的、要不要還原；使用者要還原時，照 `profile-measurement.md`〈跑完之後：還原〉用第 3 步的備份做〈把還原檔放回去〉與〈逐行比對內容〉，結果記進交付紀錄。

收尾時，有做第 3 步就做兩件事，問的內容與使用者的回答都記進交付紀錄；問不到時照專案的延後動作處理（寫進給使用者的最後一則總結）：

- 問使用者要不要裝回 `app-version.txt` 記的那一版：手機上留著的是這次 `flutter run` 裝的 debug 版（可能含這次暫加的 log），裝回照〈跑完之後：還原〉的〈裝回使用者原本的版本〉。
- 不論裝不裝回，都照同一節的〈清掉手機上的副本〉列出 `/data/local/tmp/<applicationId>-measure/` 裡的檔，`ls` 的輸出給使用者看，問過再刪：那些是使用者資料的還原檔，留在手機上，任何能用 adb 的人都讀得到。

## 分工：使用者對準，agent 看讀取序列

把相機對準實體條碼只能由人在設備上做，agent 做不到；而辨識的結果在 APP 的 log 裡，使用者看不到。所以分工是使用者照 agent 給的順序掃（哪幾樣東西、按哪個鍵、哪一步不要按），agent 在背景讀 log，掃完再看結果。掃之前把這份順序寫進 `<暫存目錄>/scan-order.txt`，〈用讀取序列模擬採用規則〉取正確答案時要用。給使用者的順序裡要寫出**會寫入資料的鍵不要按**，理由在〈開始之前：使用者的資料〉。

**讀取序列**是 APP 收到的號碼依時間排出來的清單。APP 的相機服務每收到一個號碼就記一行 log 時，驗證時從 `flutter run` 的 log 取出這幾行。先讀 APP 的原始碼確認那一行 log 的記錄點：在套件回報之後（被套件的回報條件壓掉的號碼不會出現），以及在轉送規則（相機服務挑出要交給 ViewModel 的號碼）之前還是之後；log 呼叫與轉送規則各自的 `<檔>:<行>` 與判定記在 `states.md` 下方。記在轉送之後時，被轉送規則丟掉的號碼不在序列裡。APP 沒有這行 log、要看轉送之前的號碼、或後面要讀的值只存在於 widget 內部時，要改 APP 的程式碼：先問使用者，同意之後再改（log 記到號碼與格式就夠），照 SKILL.md「改程式碼之後熱重啟」那一步確認熱重啟成功，在 `states.md` 下方記一行改動，在交付紀錄寫出加了什麼，收尾時問使用者要不要還原。

開始掃之前記下 log 的行數，掃完之後只看這個位置以後的行，前一輪的紀錄不混進來：

```bash
# 開始掃之前：記下標記
wc -l < <暫存目錄>/flutter.log | tr -d ' ' > <暫存目錄>/log-mark.txt
# 掃完之後：讀標記之後的讀取序列，每行帶 flutter.log 的絕對行號（字樣含 [ . ( * + 這類字元時，用下一行的 -F 寫法）
M=$(( $(cat <暫存目錄>/log-mark.txt) + 1 )); grep -nE '<讀到號碼的 log 字樣>|<開始掃描的字樣>|<查詢的字樣>' <暫存目錄>/flutter.log | awk -F: -v m="$M" '$1>=m'
M=$(( $(cat <暫存目錄>/log-mark.txt) + 1 )); grep -nF -e '<讀到號碼的 log 字樣>' -e '<開始掃描的字樣>' -e '<查詢的字樣>' <暫存目錄>/flutter.log | awk -F: -v m="$M" '$1>=m'
```

`wc -l` 記下的是標記當下最後一行的行號，所以加 1，那一行不算進來；`awk` 只留行號不小於它的行，輸出開頭的行號就是交付紀錄要附的行號範圍。`wc` 的輸出前面有空白，存檔時先用 `tr -d ' '` 去掉，`$(( ))` 才算得出數字。三個字樣從 APP 相機服務、ViewModel 與頁面的 log 呼叫裡取（或在 `flutter.log` 裡找一行現成的）：讀到號碼的那一行組成讀取序列；開始掃描的那一行把序列切成一場一場（每次開始掃描到逾時或採用為止算一場），也是序列的內部對照；查詢的那一行用來看採用之後查詢流程有沒有開始。`grep -E` 把字樣當成正規表示式，`[scan]` 這類方括號前綴會被當成字元集合而一行都不印。**判讀序列是空的之前，先確認同一份輸出裡有開始掃描的那一行**：連它都沒有時，是指令或字樣錯了，不是掃描器沒解出，修指令再讀。

從讀取序列分得出下面幾種情形，成因分屬拍攝條件、掃描器的解碼、掃描套件的回報規則、APP 轉送與採用號碼的程式，以及相機與 ViewModel 的狀態：

- **對準的期間序列是空的（開始掃描的那一行在）**：掃描器沒有解出條碼，或解出了而套件沒有回報（`noDuplicates` 下移開再對回同一本書、條碼落在掃描範圍之外）。沒解出的成因在拍攝條件（對焦、距離、光線）、掃描格式沒涵蓋這種條碼，或掃描器沒在跑（上一次沒關乾淨、權限、生命週期）。這種情形跟 APP 的採用規則（讀到幾次才把號碼當成結果）無關，改採用規則沒有作用；交付紀錄寫出這一類，掃描器沒在跑時照〈掃描之後的狀態：讀 ViewModel 與頁面當下的值〉讀狀態。
- **序列有正確號碼，跟誤讀交錯**：回報模式是 `noDuplicates` 時先歸入下一條，那個模式下正確號碼每次重現之前都要先夾一次讓號碼清單改變的讀取。回報模式是 `normal` 時，成因在拍攝條件（反光、角度）或掃描器的解碼，採用規則要求「連續讀到幾次」時誤讀會讓計數歸零。要改採用規則時，照〈用讀取序列模擬採用規則〉比較候選規則。
- **條碼清楚、手很穩，同一個號碼只出現一次（回報模式是 `noDuplicates`，Android）**：成因在掃描套件的回報規則加上 APP 的採用規則。套件做了去重複的回報（mobile_scanner Android 實作的 `DetectionSpeed.noDuplicates`：這一格的號碼清單跟上一次回報的相同就不回報，空畫面不清紀錄），APP 又要求讀到兩次才採用，APP 等不到第二次讀取，這個號碼不會被採用。照〈用讀取序列模擬採用規則〉末段從套件原始碼確認回報條件，寫進交付紀錄；改回報模式是改 APP 的程式碼，先問使用者。
- **同一本書的 ISBN 與另一條條碼的號碼交替出現（log 記在轉送之後），或同一格畫面同時有 ISBN 與另一條、ViewModel 收到的只有另一條（log 記在轉送之前）**：成因在 APP 接收掃描結果的回呼只取一格畫面裡的第一個號碼。例如日本書封底下排 192 開頭的分類價格碼排在上排的 ISBN 前面時，ISBN 被丟掉。log 記在轉送之後時，這個外觀跟上一條的「誤讀交錯」很像，差別在另一個號碼每次都相同、前綴查得出它屬於哪一套編號；要直接看到同一格有幾個號碼，照上面的做法問使用者，加一行轉送之前的 log。交付紀錄寫出轉送規則；要改程式碼時同樣先問。
- **正確號碼重複出現、沒有誤讀，卻一直沒有採用**：先照〈掃描之後的狀態：讀 ViewModel 與頁面當下的值〉讀狀態，ViewModel 已經停止接收（逾時、或採用之後等頁面接手）時，成因在相機、ViewModel 與頁面的狀態，不在採用規則。ViewModel 仍在接收時，比對序列裡相鄰兩次的時間差與採用規則的時間窗：書時進時出、對焦不穩時間隔也會變長，所以請使用者把書拿穩不動再掃一次；那時時間差仍一直比時間窗長，才是這台手機每分析一格花的時間比規則假設的長，時間窗要照〈用讀取序列模擬採用規則〉用這台手機的序列重選。

一次實測在 `noDuplicates` 下的 8 場、85 次讀取（其中 32 次是誤讀）每一個號碼都通過 EAN-13 檢查碼；mobile_scanner 的 Android 實作把 ML Kit 解出的 `rawValue` 原樣轉給 APP，由此推得 ML Kit 回報之前已經驗過檢查碼（推論，沒有查到 ML Kit 的文件寫明），所以 APP 再驗一次檢查碼擋不下到達 APP 的誤讀。

## 用讀取序列模擬採用規則

採用規則的效果（讀到幾次、在多長的時間窗內、中間夾了別的號碼時計數是否歸零）取決於誤讀的頻率與位置，兩者都在讀取序列裡。所以改規則之前，agent 拿同一份序列套上現行規則與至少一條候選規則，比較每條規則採用了幾場、有沒有採到錯的號碼、從第一次讀到正確號碼到採用要多久。模擬的腳本與結果表存在 `<暫存目錄>/`，交付紀錄附路徑。

每一場的正確答案取 `scan-order.txt` 裡那一場對準的物品；順序沒記下時，才取讀到次數最多的號碼，並在紀錄裡寫明這個取法（次數最多的不一定是要的那一條：一次實測的日本書那一場，192 碼的次數比 ISBN 多）。同一場的其他號碼，agent 逐個查是不是同一件物品上另一條真的條碼（書上另印的商品碼或價格碼、商品上的兩條條碼）；是的話，採用規則採到那個號碼不算採錯，另列一欄，每個號碼附依據（使用者確認的原話、前綴規則與它的來源，或實物照片的路徑）。沒有依據的照誤讀算。

序列要在跟正式版相同的回報模式（mobile_scanner 的 `DetectionSpeed`）下取得：`noDuplicates` 會把讓號碼清單改變的誤讀都送上來，卻壓掉正確號碼的重複讀取，誤讀的比例因此比 `normal` 高，在它底下評估要求讀到兩次以上的規則，量到的是誤讀帶出的重現。改了回報模式之後，用新模式下的序列重新模擬。

時間窗與次數是從這一份序列選出來的值，寫進程式碼的註解時寫出樣本（幾場、哪一台手機、哪一種回報模式）。換手機或換一批條碼時，用新的序列重新模擬。逾時或採用之後，APP 的相機服務可能仍在記讀取，而那時 ViewModel 已經不收：agent 算場次與次數時，把序列切在逾時或採用的那一刻。

套件的回報行為從套件的原生程式碼讀，agent 拿它核對模擬的結論，不照套件的說明文件或記憶推；交付紀錄寫出套件版本（`package_config.json` 裡的版本）與判定條件所在的 `<路徑>:<行>`。原始碼目錄是 `<APP 專案根目錄>/.dart_tool/package_config.json` 裡那個套件的 `rootUri`（預設在 `~/.pub-cache/hosted/pub.dev/<套件>-<版本>/`；mobile_scanner 的 Android 實作在它底下的 `android/src/main/kotlin/`，iOS 實作在 `darwin/`，7.1.2 的 iOS 實作不比對號碼清單，`noDuplicates` 在 iOS 上分析過的每一格都回報，前一格還在分析時來的畫面會跳過）。條件的細節（空畫面時是否清掉上一次回報的紀錄、等待期間是否分析畫面）只寫在程式碼裡，說明文件沒有寫到。

## 掃描之後的狀態：讀 ViewModel 與頁面當下的值

掃完一本之後畫面停住、看起來在等卻沒反應時，agent 從截圖分不出停住的是相機、ViewModel 還是頁面。用 `drive.sh eval` 讀當下的狀態：

```bash
source <暫存目錄>/env.sh
$D eval 'ProviderScope.containerOf(ctx).read(<掃描狀態的 provider>).<表示階段的欄位>'
```

`<掃描狀態的 provider>` 從掃描頁原始碼裡 `ref.watch(` 讀的那一個取（記下 `<檔>:<行>`），`<表示階段的欄位>` 是那個狀態類別裡表示目前階段的欄位（例如 `status`）。寫運算式時要注意：

- `ctx` 是 `drive.dart` 從根元素前序走訪、最後找到的那個 Navigator 的 context（只有一層 Navigator 的 APP 就是畫面上那一個；巢狀時見 SKILL.md〈前置〉）。`ProviderScope.containerOf(ctx)` 取到的是 ctx 往上最近的那個 container：掃描頁底下另有自己的 `ProviderScope` 時，讀到的是另一個 container 的值；讀一個沒有人在監聽的 `autoDispose` provider，會建出一個初始值。所以先確認 provider 正在被掃描頁 `ref.watch`、掃描頁沒有自己的 `ProviderScope`。呼叫要用 Overlay 或 Scaffold 的函式時，巢狀 Navigator 可能取到看不見的那一層。
- 運算式用到的名字（provider、狀態類別）要在求值的函式庫裡看得到。根函式庫沒有 import 它們時，設 `FLUTTER_DRIVE_LIB=package:<APP 套件名>/<掃描頁在 lib/ 底下的相對路徑，例如 ui/scan_page.dart>` 再跑；指定的函式庫也要 import Flutter widgets（`drive.dart` 嵌進運算式的 Navigator 走訪要用）。
- 外層用單引號：用雙引號時 bash 會展開運算式裡的 `$`（Dart 的字串插值）。
- 讀單一欄位，不印整個狀態物件：`drive.sh` 只留輸出的最後一行，多行的 `toString()` 只看得到最後一行。
- 回傳 `Future` 的運算式印的是 `Instance of 'Future<…>'`，副作用照常發生、值讀不到；要讀非同步的值，先存進狀態再讀。
- Riverpod 以外的狀態管理，換成那一套從 context 取狀態的寫法。

讀到的組合例如：掃描狀態停在「已讀到」而查詢流程停在「閒置」，代表採用之後查詢流程沒有被觸發（頁面的去重複擋掉了查詢，或號碼殘留）；掃描狀態是「逾時」而相機還在跑，代表逾時沒有停相機。

## 短暫出現的畫面：輪詢狀態，出現時自動截圖

只在某個條件成立的那一刻出現的畫面（例如相機對著剛查過的那本書時才出現的說明），不等使用者說「出現了」再截：從使用者說出口到 agent 下指令至少隔幾秒，畫面可能已經消失。所以 agent 在背景輪詢那個條件，成立時馬上截圖。條件寫成回傳 `bool` 的運算式，`drive.sh eval` 印出 `true` 或 `false`；迴圈之前先在前景跑一次，確認它印 `false`（印出別的值或 `求值失敗` 時，先修運算式），印出的值記進迴圈的輸出檔：

```bash
source <暫存目錄>/env.sh
for i in $(seq 240); do
  r=$($D eval '<條件的運算式>' 2>><暫存目錄>/eval-err.log)
  case "$r" in
    true) SHOT_DELAY=0 $D shot "$S/<截圖檔名>.png" && echo "shot $(date +%T)" || echo "截圖失敗"; break ;;
    false) ;;
    *) echo "eval 失敗（${r}），見 eval-err.log"; break ;;
  esac
  [ "$i" = 240 ] && echo "timeout：條件沒有成立"
  sleep 0.3
done | tee <暫存目錄>/poll-<截圖檔名>.log
```

`<截圖檔名>` 填 `states.md` 截圖路徑欄去掉開頭的 `shots/` 與結尾的 `.png`（`$S` 已經是截圖目錄）。用 agent shell 工具的背景執行跑這個迴圈，再請使用者照順序操作。迴圈印出 `timeout` 時，畫面在五到六分鐘內沒有出現：先在前景再跑一次條件運算式，確認它在畫面出現時會變成 `true`，再請使用者重做那一步；標成「未拍」時附 `poll-<截圖檔名>.log` 的路徑與重跑時印出的值。`eval` 不等換頁動畫（`drive.sh` 對 `eval` 不加 `WAIT`），一次約 1.1 秒（Samsung SM-S9010 實測，含每次重新啟動 `drive.dart`、連上 VM service 與送喚醒鍵），加上 0.3 秒的間隔，迴圈上限 240 次約五到六分鐘。`SHOT_DELAY=0` 拿掉 `drive.sh shot` 截圖前固定等的 1.2 秒。從條件成立到截下畫面，最多隔一次輪詢（約 1.4 秒）加上 screencap 本身的時間（未量）；畫面停留比這段短的狀態，輪詢可能錯過，改在狀態裡加一個計數欄位記下出現過幾次（改程式碼之前照〈分工〉那一段先問使用者）。截到之後照 SKILL.md「看圖」那一步裁出那一塊確認。

辨識事件也可以當觸發：條件是 log 裡出現某個字樣時（例如讀到非書籍條碼），迴圈改成每兩秒查一次標記之後的新行，出現時截圖。這種畫面在事件之後停留幾秒，查 log 的間隔可以比輪詢狀態長。迴圈開始之前另記一個標記，存成 `event-mark.txt`（不覆寫讀取序列用的 `log-mark.txt`）：沿用掃描之前記的標記時，之前已經出現過的同一個事件會讓迴圈第一圈就截圖，截到的不是事件之後的那一刻：

```bash
source <暫存目錄>/env.sh
wc -l < <暫存目錄>/flutter.log | tr -d ' ' > <暫存目錄>/event-mark.txt
M=$(( $(cat <暫存目錄>/event-mark.txt) + 1 ))
for i in $(seq 150); do
  if tail -n +"$M" <暫存目錄>/flutter.log | grep -qF '<事件的 log 字樣>'; then SHOT_DELAY=0 $D shot "$S/<截圖檔名>.png" && echo "shot $(date +%T)" || echo "截圖失敗"; break; fi
  [ "$i" = 150 ] && echo "timeout：事件沒有出現"
  sleep 2
done | tee <暫存目錄>/poll-<截圖檔名>.log
```

## 不寫入資料，叫出寫入之後才出現的畫面

有些畫面只在寫入之後出現（批次修改之後的提示列與「復原」鍵），為了截圖去改使用者的資料不值得，改了也要還原。agent 用 `eval` 直接呼叫 APP 顯示那個畫面的正式函式，在動作的回呼參數傳入一個什麼都不做的函式。呼叫之前先讀那支函式，確認它只負責顯示（函式體裡沒有 repository、資料庫或網路呼叫），把 `<檔>:<行>` 與這個判定寫進交付紀錄；函式裡有寫入時不用這個方法，照 `device-pitfalls.md`〈會寫入資料的點按〉。`count-before.png` 照〈開始之前：使用者的資料〉在這一批開頭截一次，這裡不重截：

```bash
source <暫存目錄>/env.sh
FLUTTER_DRIVE_LIB=package:<APP 套件名>/<提示列函式在 lib/ 底下的相對路徑> \
  $D eval '<顯示提示列的函式>(ctx, "<訊息>", actionLabel: "<鍵名>", onAction: () {}, duration: const Duration(seconds: 30))'
$D shot "$S/<截圖檔名>.png"   # 提示列出現之後截
```

具名參數（`actionLabel`、`onAction`、`duration`）照那支函式實際的簽名改，參數只填顯示用的字串與空的回呼，不傳使用者的資料。函式回傳 `void` 時 `drive.sh eval` 印 `null`，回傳物件時印 `Instance of '…'`，兩種都代表函式已經執行。APP 沒有獨立的顯示函式、在事件處理裡直接 `ScaffoldMessenger.of(context).showSnackBar(SnackBar(…))` 時，照〈分工〉那一段問使用者要不要抽出成函式，或把那段 `SnackBar(…)` 照抄進 `ScaffoldMessenger.of(ctx).showSnackBar(…)` 求值，交付紀錄寫明是照抄的。

呼叫的是正式的函式，外觀與位置跟寫入之後出現的一樣；`duration` 拉長讓截圖來得及，正式版的時間不同。用這個方法只驗得到畫面，驗不到寫入之後是否會出現這個畫面，所以結果欄照〈交付紀錄怎麼標〉標成「已拍（eval 叫出）」。資料筆數在收尾時照〈開始之前：使用者的資料〉截 `count-after.png` 比對一次。

## 交付紀錄怎麼標

`states.md` 的結果欄照 SKILL.md「交付與收尾」那一步的標籤標，相機掃描多出來的是下面幾種：

- **已拍**：讀取序列與 `eval` 讀到的狀態，結果欄附 `flutter.log` 的行號範圍或截圖路徑，以及當時 APP 的版本（`shots.log` 最後一行的 commit 與工作樹雜湊，或 `git -C <APP 專案根目錄> rev-parse --short HEAD` 與 `git status --porcelain` 的結果）。行號範圍早於 `states.md` 下方最後一筆相關改動（例如暫加 log 之後的熱重啟）的，照 SKILL.md 的規則算待重拍。對準條碼的動作寫明由使用者做。
- **已拍（eval 叫出）**：用〈不寫入資料，叫出寫入之後才出現的畫面〉叫出的畫面，驗到外觀，驗不到觸發條件。
- **使用者驗（實機）**：只用在 APP 沒有可讀的 log 行、而使用者拒絕加 log 的時候，附使用者拒絕的原話；其餘由使用者口頭回報的結果，先照〈分工〉讀 log 驗證。執行者自認讀不到 log，不改變本款結果。
