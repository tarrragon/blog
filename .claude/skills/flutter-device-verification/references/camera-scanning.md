# 相機掃描的實機驗證：使用者掃、agent 看 log，短暫的畫面自動截圖

> **何時讀**：要在實機上驗證相機掃描（條碼、QR code）的辨識率、掃描之後的流程，或掃描頁上只出現一下子的畫面（提示、說明列），而對準條碼這個動作只能由人拿著設備做的時候。截圖與熱重啟的基本流程照 SKILL.md；本檔寫的是相機掃描多出來的分工與做法。

## 分工：使用者對準，agent 看讀取序列

相機對準實體條碼只能由人在設備上做，agent 做不到；而辨識的結果在 APP 的 log 裡，使用者看不到。所以分工是使用者照 agent 給的順序掃（哪幾樣東西、按哪個鍵、哪一步不要按），agent 在背景讀 log，掃完再看結果。給使用者的順序裡要寫出**會寫入資料的鍵不要按**（掃到不在資料裡的東西時，面板常出現「加入」），理由同 `device-pitfalls.md`〈會寫入資料的點按〉。

**讀取序列**是 APP 收到的號碼依時間排出來的清單。APP 的相機服務每收到一個號碼就記一行 log（沒有的話先加，記到號碼與格式就夠），驗證時從 `flutter run` 的 log 取出這幾行。開始掃之前記下 log 的行數，之後只看這個位置以後的行，前一輪的紀錄不混進來：

```bash
wc -l < <暫存目錄>/flutter.log | tr -d ' ' > <暫存目錄>/log-mark.txt
M=$(cat <暫存目錄>/log-mark.txt); tail -n +"$M" <暫存目錄>/flutter.log | grep -E '<讀到號碼的 log 字樣>|<開始掃描的字樣>|<查詢的字樣>'
```

`tail -n +` 後面接的是行號，`log-mark.txt` 裡有空白時 macOS 的 `tail` 會報 `illegal offset`，所以存檔時先用 `tr -d ' '` 去掉 `wc` 補的空白。

讀取序列分得開幾種情形，各自的成因落在不同的層：

- **對準的期間序列是空的**：掃描器沒有解出任何條碼。成因在相機與畫面（對焦、距離、光線、掃描格式沒涵蓋這種條碼），或掃描器沒在跑（上一次沒關乾淨、權限、生命週期）。改 APP 的採用規則對這種情形沒有作用。
- **序列有正確號碼，跟誤讀交錯**：掃描器解得出來，誤讀頻繁。採用規則要求「連續讀到幾次」時，誤讀會讓計數歸零。
- **條碼清楚、手很穩，同一個號碼只出現一次**：掃描套件做了去重複的回報（mobile_scanner 的 `DetectionSpeed.noDuplicates`：這一格的號碼清單跟上一次回報的相同就不回報，空畫面不清紀錄），APP 又要求讀到兩次才採用，兩條規則合起來永遠不成立。
- **序列裡是同一張紙上另一條條碼的號碼**：轉送的那一段只送了一格畫面裡的第一個號碼（書上常見 ISBN 加上 192 或 471 開頭的另一條）。

誤讀多半也通過 EAN-13 的檢查碼（一次實測 77 次讀取全部正確），所以「再驗一次檢查碼」不是區分誤讀的方法。

## 用讀取序列模擬採用規則

採用規則（讀到幾次、在多長的時間窗內、中間夾別的號碼算不算）的效果取決於誤讀的頻率與位置，兩者都在讀取序列裡。所以改規則之前，拿同一份序列套上幾條候選規則，比較每條規則採用了幾場、有沒有採到錯的號碼、從第一次讀到正確號碼到採用要多久。每次重新開始掃描算一場，每一場取讀到次數最多的號碼當作正確答案（商品那幾場可能有兩個號碼都是真的條碼，不算採錯）。

時間窗與次數是從這一份序列選出來的值，寫進程式碼的註解時寫出樣本（幾場、哪一台手機）。換手機或換一批條碼時，用新的序列重新模擬。

結論要跟套件的原始碼對：套件的回報行為從 `~/.pub-cache/hosted/pub.dev/<套件>-<版本>/` 的原生程式碼讀（mobile_scanner 的 Android 實作在 `android/src/main/kotlin/`），不照套件的說明文件或記憶推。說明文件常只寫一句，條件的細節（空畫面清不清紀錄、等待期間分不分析畫面）只在程式碼裡。

## 掃描之後的狀態：讀 ViewModel 與頁面當下的值

掃完一本之後畫面停住、看起來在等卻沒反應時，截圖分不出是哪一方停了。用 `drive.sh eval` 讀當下的狀態：

```bash
$D eval "ProviderScope.containerOf(ctx).read(<掃描狀態的 provider>).status"
```

`ctx` 是最上層 Navigator 的 context。運算式用到的名字（provider、狀態類別）要在求值的函式庫裡看得到：根函式庫沒有 import 它們時，設 `FLUTTER_DRIVE_LIB=package:<APP 套件名>/<掃描頁所在的檔案>` 再跑。Riverpod 以外的狀態管理，換成那一套從 context 取狀態的寫法。讀到的組合常見的幾種：掃描狀態停在「已讀到」而查詢流程停在「閒置」，代表採用之後沒有人接手（頁面的去重複擋掉了查詢，或號碼殘留）；掃描狀態是「逾時」而相機還在跑，代表逾時沒有停相機。

## 短暫出現的畫面：輪詢狀態，出現時自動截圖

只在某個條件成立的那一刻出現的畫面（例如相機對著剛查過的那本書時才出現的說明），等使用者說「出現了」再截，畫面多半已經消失。改成在背景輪詢那個條件，成立時馬上截圖：

```bash
source <暫存目錄>/env.sh
for i in $(seq 240); do
  r=$($D eval "<條件的運算式>" 2>/dev/null)
  if [ "$r" = "true" ]; then $D shot "$S/<截圖路徑>.png"; echo "shot $(date +%T)"; break; fi
  sleep 0.3
done
```

用 agent shell 工具的背景執行跑這個迴圈，再請使用者照順序操作。`eval` 不等換頁動畫（`drive.sh` 對 `eval` 不加 `WAIT`），一次約 1.1 秒（Samsung SM-S9010 實測，多數時間花在每次重新連 VM service），加上 0.3 秒的間隔，迴圈上限 240 次約五到六分鐘；畫面停留不到 1.5 秒的狀態，這個間隔可能錯過，改用狀態裡的計數欄位記下出現過幾次；條件要讀的值不在狀態裡時（只存在於 widget 內部），先在狀態裡加一個欄位，否則輪詢讀不到。截到之後照 SKILL.md〈看圖〉裁出那一塊確認。

辨識事件也可以當觸發：條件是 log 裡出現某個字樣時（例如讀到非書籍條碼），迴圈改成每兩秒查一次 log 位置以後的新行，出現時截圖。這種畫面在事件之後停留幾秒，查 log 的間隔可以比輪詢狀態長。

## 不寫入資料，叫出寫入之後才出現的畫面

有些畫面只在寫入之後出現（批次修改之後的提示列與「復原」鍵），為了截圖去改使用者的資料不值得，改了也要還原。用 `eval` 直接呼叫 APP 顯示那個畫面的正式函式，動作的回呼給一個什麼都不做的函式：

```bash
FLUTTER_DRIVE_LIB=package:<APP 套件名>/<提示列函式所在的檔案> \
  $D eval "<顯示提示列的函式>(ctx, '<訊息>', actionLabel: '<鍵名>', onAction: () {}, duration: const Duration(seconds: 30))"
```

呼叫的是正式的函式，外觀與位置跟寫入之後出現的一樣；`duration` 拉長讓截圖來得及，正式版的時間不同。這個方法只驗畫面，驗不到「寫入之後真的會出現這個畫面」，交付紀錄裡寫明是用 `eval` 叫出的。拍完照 SKILL.md〈還原設備設定並確認〉拍一次計數畫面，確認資料筆數沒有變；計數變了時，對照 log 裡寫入的紀錄（`add`、`update`、`delete` 這類字樣）分出是誰寫的：使用者在拍攝期間自己操作的寫入不必還原，問過使用者再記進紀錄。

## 使用者自己的操作與資料

使用者拿自己的設備掃時，掃描流程的面板上常有寫入資料的鍵，使用者可能會按。開始之前照 `profile-measurement.md`〈跑之前：資料保全〉的做法備份 APP 的資料（那一節是為效能量測寫的，掃描驗證不跑 `flutter drive`，只取它備份與比對雜湊的步驟），收尾時比對計數；計數跟開始時不同，先從 log 找出寫入的時間與對象，再問使用者是不是自己做的，不自己刪。
