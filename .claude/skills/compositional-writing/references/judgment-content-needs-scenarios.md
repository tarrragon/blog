# 判讀內容要給系統形態與觸發事件

> **角色**：本卡是 `compositional-writing` 的情境型 reference、被判讀 / 選型 / 決策類內容的寫作與審查引用。
>
> **何時讀**：寫「該怎麼判斷」那一層的內容時、或讀者提問「什麼情況會需要這個」時。

## 這個 reference 解決什麼

判讀類內容寫成純機制陳述時，只有已經有相關經驗的人讀得懂——因為讀者必須自己補上「什麼時候會用到這個屬性」，而能補上的人本來就會判斷了。內容的實際受眾因此收斂成「已經懂的人」。

要補的是**情境**，不是實作。兩者常被一起排除，但它們的住址不同：

|      | 內容                           | 該在哪         |
| ---- | ------------------------------ | -------------- |
| 實作 | 怎麼做——程式碼、配置、指令     | 下游內容       |
| 情境 | 什麼系統會遇到、什麼事件會觸發 | **判讀層自己** |

判讀層宣告「不展開實作」是正確的分工。但判讀的定義就是「遇到 X 時該怎麼選」，把 X 拿掉之後，剩下的是分類學而不是判準。

情境有兩種，服務讀者的兩個時刻：**系統形態**服務設計階段（我做的是哪一種系統，所以該注意什麼）、**觸發事件**服務事故與維運階段（現在發生了這件事，該動哪一層）。判讀類內容常見的「判讀訊號」欄有時序陷阱——訊號要等設計落地才觀察得到，設計階段的讀者手上是空的，系統形態填的正是這個空缺。

## 六步程序

1. **判定適用**。兩個問題連著問。第一，這篇在給判準嗎？分流型入口（本身就是路由）、純參考（規格表、API 文件）、程序型（步驟一二三四）都不適用。第二，**這篇的讀者站在哪個時刻**？讀者若是「已經有系統在跑、正在考慮要不要動它」，他手上有現象可觀察，內容給訊號就夠了、補形態是冗餘；讀者若在設計階段還沒有系統，訊號欄對他是空的，形態才是他能對照的東西。同一個分類裡不同篇可以落在不同時刻，逐篇判定、別整批套用。
2. **先掃出已經寫對的地方**。同一篇裡通常有一兩節已經給了具體形態。它們是本篇的參照樣本——語感、顆粒度、篇幅比例都照它們對齊，比另立標準可靠。
3. **逐節列出機制陳述**：描述屬性、承擔判準、但沒有情境的句子。
4. **對每一個問兩個問題**：什麼樣的系統會走到這裡（形態）、什麼事件會逼出這個動作（觸發）。多數判讀項目只需要其中一個，看它服務的是設計還是維運。
5. **決定補寫形式**。動筆前先查該內容是不是已經在別節或案例庫裡——分散在別處也算有，不必為了形式整齊而複製。形態份量夠（累計超過一段）就獨立成節、緊接判讀表之後；不夠就在既有段落補前半拍。
6. **掃兩個副作用**（見下）。

## 判定不需補時，檢查換一個維度

判定「這篇不需要補形態」不等於這篇沒有缺口。缺形態與缺術語入口是同一個問題的兩種形式——**讀者都得自己補上一塊才能使用內容**，差別只在缺的是情境還是名詞。所以判定不需補形態時，接著查卡連結覆蓋：

掃主線術語的出現次數與連卡次數。同一個術語在一篇裡出現十幾次卻一次都沒連卡，讀者要嘛已經懂（那這篇對他有價值的部分不在這裡）、要嘛得自己去查。實測到的形態是：某篇的標題就寫著某個術語、它是該篇的核心概念，全篇卻零連卡，而同分類其他篇的卡連結數是它的三倍以上——**同分類內的卡連結數落差本身就是偵測訊號**，比絕對數量可靠。

補的規則是每篇第一次出現時連、後續裸用。這一步的成本遠低於補形態（幾個連結 vs 一節內容），但對落在該篇的搜尋讀者影響一樣大。

## 正反例

### 例一：機制屬性缺觸發事件

**反例**——三句都正確，但讀者不知道什麼時候會用到：

> 使用者層可以撤銷單一 session 而不影響他人；系統層的憑證由所有呼叫共用，撤銷等於中斷整條整合；對應層沒有可撤銷的憑證，處理的是映射資料的一致性。

**正例**——每一層配上誰會逼出這個動作，並讓後果變成可感受的量：

> 使用者層的撤銷由個別的人的事件觸發：帳號被回報盜用、員工離職當天、使用者改完密碼要踢掉其他裝置。這一層可以撤銷單一 session 而不影響他人，所以處置能立刻執行。
>
> 系統層的撤銷由憑證本身的事件觸發：密鑰被 commit 進公開 repo、知道那把密鑰的人離職、廠商通報他們那端外洩、輪替週期到期。這一層的憑證由所有呼叫共用，撤銷等於中斷整條整合——落到實際操作是先找到對方的窗口、約一個雙方都能配合的維護時間、兩邊同時換。同一個「立刻撤銷」的需求，在這一層要用天或週計算。

差別在最後一句：屬性（撤銷等於中斷整合）本身沒有份量，換算成時間尺度之後才有。

### 例二：分類缺對號入座的入口

**反例**——分類正確、定義清楚，但讀者無法判斷自己屬於哪一類：

> 機密性：讓內容對持有密文的人不可讀。來源與完整性：證明內容出自持有密鑰的一方且未被竄改。可讀性遮蔽：讓內容在載體上不以明文出現。

**正例**——給一條貫穿的判準軸，再讓每一類掛上具體處境：

> 判斷自己需要哪一類，看的是資料會在哪裡、被誰看到：
>
> - 資料會離開自己控制的範圍時要**機密性**——備份送到第三方儲存、跨區複製、筆記型電腦上的離線副本。
> - 系統之間互相呼叫、或要接收外部推送時要**來源與完整性**——webhook 訂閱、B2B API 整合、對外發佈的授權憑證。
> - 內容要印在會被看到的載體上時要**可讀性遮蔽**——實體標籤、QR Code、放進網址的參數。

判準軸（資料會在哪裡、被誰看到）比逐類舉例更重要——沒有軸的例子清單，讀者遇到清單外的情況仍然無法判斷。

### 例三：問題節點表缺系統形態

**反例**——表格的「判讀訊號」欄要等設計已經落地才觀察得到，設計階段的讀者對照不到任何東西。

**正例**——在表後補一節，逐類給架構長相、成因與識別特徵：

> **系統憑證下放到客戶端**出現在想省掉後端中繼的架構：行動應用直接呼叫第三方 API、前端直接打雲端儲存或地圖服務、IoT 裝置與桌面應用。動機通常是離線也要能運作、或少一跳延遲。這一類的識別特徵最明確——產出物裡有一把對方系統認得的憑證。

三個成分各有用途：**架構長相**讓讀者對號入座、**成因**讓他判斷自己是不是正在走向這裡、**識別特徵**給一個可立刻執行的檢查。三者之中識別特徵最有價值也最難寫，寫不出來時通常代表這一類的邊界還沒想清楚。

### 例四：不需要補的情況

以下三種形態已經足夠，再加形態是冗餘：

**已用其他措辭給了情境**。「驗證素材定義不一致是跨團隊對接最常見的耗時來源」——「跨團隊對接」就是形態，不必再加一句「什麼樣的系統會遇到」。

**程序型內容**。判讀流程的步驟一二三四是操作順序，它的可用性靠每一步夠不夠具體，不靠形態。

**分流型入口**。整段責任是把讀者導到別處的內容，補形態會讓它變成它本來要路由過去的那篇。

## 兩個修法副作用

**補情境會引入第二人稱**。具象化的敘述天然帶出「你的產出物」「你得先找到窗口」，因為講情境時會不自覺對著人講。中性陳述的規範在這一步最容易破功——補完專門掃一次，把主詞換成受詞或省略（「產出物裡有一把……」「先找到對方的窗口」）。

**原本的封閉計數會失準**。缺情境常伴隨缺段落：正文寫「三種混法」而判讀表有四列，因為第四類從來沒有展開段。補上之後那個數字才浮現為錯誤。反過來用：**封閉計數與表格列數對不上，本身就是缺段落的偵測訊號**，可以在動筆前先掃一次。

檢查缺不缺的單位是「內容」而非「段落」——同一列的內容分散在別節也算有，硬要每列都有獨立段落會製造重複。

## 判讀徵兆

- 讀者的提問是「什麼情況會需要這個」「什麼樣的系統會這樣做」——缺情境的直接訊號，不是讀者不夠用功。
- 通篇是屬性陳述（X 具備 Y 特性、A 與 B 的差異在 C），沒有一句是「什麼時候會遇到」。
- 判讀表的每一列都有訊號欄，但那些訊號都要等設計落地才觀察得到。
- 同一篇裡有一兩節寫了具體形態、其餘沒有——能力在、檢查點不在。
- 內容被資深同事評為「寫得很清楚」，同時被新人評為「看不懂要幹嘛」。
