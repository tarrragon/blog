# 散文裡夾了一段程式，就把程式與逐行解釋移進區塊；推導留在散文

> **角色**：本卡是 `compositional-writing` 的支撐型原則（principle），被 `demonstrating-commands.md`〈散文裡夾了一段程式，就把程式與逐行解釋移進區塊〉與字句層 keyword bank 的「散文夾程式」類別引用。
>
> **何時讀**：一段散文裡的行內程式碼拼起來是一段查詢或指令，讀者要在腦中把它組回去時；或者要決定一段解釋該寫成註解還是散文時。

散文段落的職責是推導，程式碼區塊的職責是讓讀者整段看、整段複製。一段散文把同一段查詢或指令的零件——條件、子句、關鍵字、執行計畫的輸出——一個個用行內程式碼嵌進句子，讀者就得一邊讀推導、一邊在腦中把那些零件組回原本的程式，而組回來的程式在頁面上從來沒有完整出現過。修法是分兩層：**程式與只屬於某一行的解釋進區塊，寫成那一行旁邊的註解；跨行的推導與它對論證的意義留在散文。**

## 失效的形態

一篇 SQL 教材說明靜態分析判得出哪一種錯法，原文是一整段散文，行內程式碼十幾處：

> 「不等於五」的錯法是它判得出來的例子。`WHERE 評價.星等 <> 5` 對外連接補上 `NULL` 的列判成未知，那些列全數被 `WHERE` 濾掉，所以 `LEFT JOIN` 為了保留沒有評價的訂單而補出來的列一列都留不住：這段查詢與把 `LEFT JOIN` 改成 `JOIN` 的版本在任何資料上都回同一批列。……PostgreSQL 的 `EXPLAIN` 對「不等於五」那段查詢印的是 `Hash Join`，對正解印的是 `Hash Left Join`。……評價表的訂單編號在建表時沒有宣告 `NOT NULL`，表結構已經說了那一欄可能是 `NULL`，而子查詢只要交出一個 `NULL`，`NOT IN` 對每一列都判不成真。

這一段講的是兩段查詢、兩份執行計畫、一份建表語句，五段程式沒有一段完整出現，全部拆成零件散在句子裡。每一句單獨看都正確，讀者要做的卻是把 `WHERE 評價.星等 <> 5`、`LEFT JOIN`、`Hash Join` 分別放回它們所屬的那段程式，再回頭理解句子在說什麼。

改寫後，散文只留推導（這段查詢寫了外連接而篩選條件讓補出來的列留不住、等價由三值邏輯決定、最佳化器改寫時不產生警告），兩段查詢與它們的 `EXPLAIN` 並列在一個區塊，每一行的註解寫這一行判成什麼、這份計畫代表什麼；建表語句與 `NOT IN` 查詢並列在另一個區塊，因為風險由兩者合起來決定。

## 跟既有規則的衝突與調和

`demonstrating-commands.md` 原本寫「推導與機制：註解裝標籤，機制寫散文」。照字面，上面那段的每一句都是機制，應該留在散文——那正是失效的來源。規則要分的是**解釋的作用範圍**：只屬於某一行的解釋（這一行做什麼、這個值判成什麼、這行輸出代表什麼）離開那一行就要讀者自己對回去，所以寫成那一行的註解；跨行成立的道理與它對論證的意義沒有單一的一行可以附著，所以寫散文。

同一處另有一條「錯誤用法不進區塊」，理由是區塊是可以複製的位置。錯法本身是主題的時候（診斷、錯法與正解的對照）這條不適用：錯的寫法要完整出現才讀得出它錯在哪，處置是進區塊、用上方整行註解標明它是錯的、與正解並列。

## 偵測

計數掃得到候選：去掉程式碼區塊之後，一個散文段落裡的行內程式碼達到十處以上。在全站教學內容跑一次有 57 段，linux、backend、llm 最多。

計數分不出兩種情形，命中之後逐段問：**這些行內程式碼拼起來，是不是一段讀者該整塊看的程式（一個查詢、一條指令、一段輸出）。** 各自是獨立名字的不必移——欄位名、函式名、設定鍵、檔案路徑被當成名詞提到；一整串工具名被列舉的，是清單的問題，改成條列或表格。

## 論述基礎與限制

依據是一段改寫與一次全站計數。十處是取來縮小候選的門檻，不是判定條件：五處行內程式碼就拼成一段查詢的段落一樣違規，二十處檔案路徑的段落可能合規。
