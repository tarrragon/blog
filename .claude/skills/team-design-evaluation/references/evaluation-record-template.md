# 評估記錄模板

> **角色**：本檔是 `team-design-evaluation` 的產出模板、被 SKILL.md 的出口條件段引用。
>
> **何時讀**：跑完 lens 要落記錄、或評估前想知道產出長什麼樣時。

## 記錄骨架

```markdown
# 團隊設計評估記錄：{受評對象}

- 受評對象：{團隊 / 框架名與範圍}
- 評估日期：{date}
- 評估方法：team-design-evaluation 判讀協議（出處：{skill 所在 repo URL 或路徑——記錄可能離開 skill 所在環境、讀者要能循此取得方法本身}）
- 觸發緣由：{基線（第一次評估）/ 重組 / 症狀（哪一條）}
- 承擔者：{發起評估並負責歸檔的人 / 角色}
- 前置定位：{人類 / agent / 混合}端、{編組數量軸找缺的還是多的}
- 任務單位：{ticket / release / incident / version}

## 總表

| Lens               | 現狀 | 判讀 | 行動 |
| ------------------ | ---- | ---- | ---- |
| 常設 vs 編成       |      |      |      |
| 執行與安全監理分線 |      |      |      |
| 業務 vs 編組       |      |      |      |
| 指揮中樞           |      |      |      |
| 對外協作面         |      |      |      |

## 逐 lens 判讀與證據

### {lens 名} — {保留 / 改 / 新增 / 不適用}

{現狀描述 + 可指認證據（檔案路徑、log 筆數、hook 行為）+ 正當化理由或缺口 + 行動}
```

「逐 lens 判讀與證據」可以逐 lens 分段、也可以用聚合的證據清單——條件是每條證據能回溯到總表的一格判讀。

## 欄位語意

- **現狀**：結構長什麼樣——用受評團隊自己的詞（名冊、dispatch、審查會、on-call 表）
- **判讀**：正當化理由、或「答不出來」——必附可指認證據；無證據時標「證據缺口」並列補證行動
- **行動**：`保留`（理由成立、留下記錄供下次重組對照）/ `改`（結構在、理由答不出或機制失效）/ `新增`（該有的結構缺席）/ `不適用`（附理由與退出訊號、標明由誰複查）/ `未評`（本次範圍外——只在症狀觸發的單 lens 路徑合法、整套評估的主力三 lens 不得標未評；跟要附退出訊號的不適用是兩回事）

## 填寫範例（假想的 agent 開發團隊、節錄三列）

| Lens               | 現狀                                     | 判讀                             | 行動                       |
| ------------------ | ---------------------------------------- | -------------------------------- | -------------------------- |
| 常設 vs 編成       | 名冊二十四個角色、任務 dispatch 沒有記錄 | 答不出「這張任務誰參與過」       | 改：dispatch 留下編成記錄  |
| 執行與安全監理分線 | reviewer 由交付 orchestrator 派發並彙整  | 否決落在彙整者手上、獨立只是形式 | 改：否決直接寫入 gate 狀態 |
| 業務 vs 編組       | 格式檢查是一個具名 agent                 | 無獨立判斷、可規則化             | 改：降為 lint / hook       |

## 歸檔 checklist（出口條件）

- [ ] 記錄放進固定位置（團隊決策記錄或 repo、與受評對象同倉）；位置與檔名已向使用者 / 團隊確認
- [ ] 記錄含評估方法出處（skill 名 + 可取得位置）——跨 repo 歸檔時讀者要能找到方法本身
- [ ] 承擔者具名（發起評估的人歸檔）
- [ ] 每條判讀都有可指認證據
- [ ] 「不適用」判定含退出訊號與複查者
- [ ] 缺口清單分流：屬共用框架設計的 → 框架的 issue 追蹤；屬單一專案修正的 → 專案的任務系統
- [ ] 下次整套觸發點（重組）已記錄；症狀表留作單 lens 監看入口
