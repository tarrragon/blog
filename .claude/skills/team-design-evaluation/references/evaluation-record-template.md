# 評估記錄模板

> **角色**：本檔是 `team-design-evaluation` 的產出模板、被 SKILL.md 的出口條件段引用。
>
> **何時讀**：跑完 lens 要落記錄、或評估前想知道產出長什麼樣時。

## 記錄骨架

```markdown
# 團隊設計評估記錄：{受評對象}

- 受評對象：{團隊 / 框架名與範圍}
- 評估日期：{date}
- 承擔者：{發起評估並負責歸檔的人 / 角色}
- 前置定位：{人類 / agent / 混合}端、{編組數量軸找缺的還是多的}
- 任務單位：{ticket / release / incident / version}

## 總表

| Lens               | 現狀 | 判讀 | 行動 |
| ------------------ | ---- | ---- | ---- |
| 常設 vs 編成       |      |      |      |
| 執行與安全監理分線 |      |      |      |
| 業務 vs 編組       |      |      |      |
| 指揮中樞           |      |      |      |
| 對外協作面         |      |      |      |

## 逐 lens 判讀與證據

### {lens 名} — {保留 / 改 / 新增 / 不適用}

{現狀描述 + 可指認證據（檔案路徑、log 筆數、hook 行為）+ 正當化理由或缺口 + 行動}
```

## 欄位語意

- **現狀**：結構長什麼樣——用受評團隊自己的詞（名冊、dispatch、審查會、on-call 表）
- **判讀**：正當化理由、或「答不出來」——必附可指認證據，寫不出證據的判讀視同未評
- **行動**：`保留`（理由成立、留下記錄供下次重組對照）/ `改`（結構在、理由答不出或機制失效）/ `新增`（該有的結構缺席）/ `不適用`（附理由與退出訊號、標明由誰複查）

## 填寫範例（假想的 agent 開發團隊、節錄三列）

| Lens               | 現狀                                    | 判讀                             | 行動                       |
| ------------------ | --------------------------------------- | -------------------------------- | -------------------------- |
| 常設 vs 編成       | 名冊三十個角色、任務 dispatch 沒有記錄  | 答不出「這張任務誰參與過」       | 改：dispatch 留下編成記錄  |
| 執行與安全監理分線 | reviewer 由交付 orchestrator 派發並彙整 | 否決落在彙整者手上、獨立只是形式 | 改：否決直接寫入 gate 狀態 |
| 業務 vs 編組       | 格式檢查是一個具名 agent                | 無獨立判斷、可規則化             | 改：降為 lint / hook       |

## 歸檔 checklist（出口條件）

- [ ] 記錄放進固定位置（團隊決策記錄或 repo、與受評對象同倉）
- [ ] 承擔者具名（發起評估的人歸檔）
- [ ] 每條判讀都有可指認證據
- [ ] 「不適用」判定含退出訊號與複查者
- [ ] 缺口清單分流：屬共用框架設計的 → 框架的 issue 追蹤；屬單一專案修正的 → 專案的任務系統
- [ ] 下次觸發點記錄在案（重組時、或症狀表命中時）
