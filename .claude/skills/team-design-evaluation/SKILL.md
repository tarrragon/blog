# Team Design Evaluation（發射管制隊視角）

評估**既有工作團隊結構設計**的判讀協議——人類專案團隊或 AI agent 開發團隊都適用。把一個實際運轉數十年的高風險任務體制（JAXA 打上げ管制隊、發射管制隊）的組織概念抽成一組判讀 lens，逐項檢視受評團隊的結構選擇有沒有能說出口的正當化理由。產出是檢核與缺口清單，不是團隊設計藍圖。

體制原型的四個事實（詳細推導見 `references/lenses.md` 各 lens 的概念段）：

1. 管制隊是跨越平時組織框架、為單次發射編成的任務編組，有單一隊長、任務結束人員回歸常設單位
2. 指揮結構分執行與安全監理兩條責任線，發射可否的判斷拆成三份由三人分持
3. 氣象工作分量極重、卻以業務形式掛在企劃班下，沒有自己的組——功能的分量與是否成組是兩個獨立變數
4. 編成裡有一半的組在管協調、行政、公關與對外

來源是公開文件：[JAXA 打上げ計画書（H3 6 號機）](https://www.jaxa.jp/press/2026/04/files/jaxa20260424-1_01.pdf)與[種子島 press kit](https://www.jaxa.jp/countdown/h2bf1/pdf/presskit_tnsc_j.pdf)。

## 推導源頭

組織結構是被任務風險、協調成本與編組成本這類理由正當化的**選擇**；外部強制（法規、合約）也是合法來源。功能的存在與組的存在是兩個獨立的事實，中間隔著一個要被回答的理由。每個 lens 都在問同一個問題的一個面向：**這個結構選擇的成本，由什麼正當化？**答得出來的結構留下，答不出來的進缺口清單。

## 前置兩步（跑 lens 之前）

1. **定位編組成本端**。人類團隊編組成本高、失效方向是**該編不編**（lens 主要找缺的結構）；agent 團隊編組成本趨近零、失效方向是**不該編也編**（lens 主要找多的與有名無實的結構）。方向差異只適用編組數量軸；協調結構（編成記錄、指揮中樞、交接承擔者）在兩端都往缺的方向失效。方向是預設而非定律——編組是地位資源的組織裡（headcount 代表位階）人類端也會過度編組。
2. **定義任務單位**。以什麼為一次任務（release / ticket / incident / version）。起訖模糊時常設 vs 編成 lens 會空轉，先定清楚再跑。

## 五個 lens 速查

| Lens               | 判讀問題                                                          | 條件-行動摘要                                                         |
| ------------------ | ----------------------------------------------------------------- | --------------------------------------------------------------------- |
| 常設 vs 編成       | 這次任務的編成圖畫得出來嗎——誰參與、誰是隊長、記錄在哪、有解編嗎  | 跨專業 + 有起訖 + 協調密度高 → 顯式編成並留記錄；日常工作歸常設分工   |
| 執行與安全監理分線 | 「不能上」這一票誰持有、行使要不要經過交付方或同一個 orchestrator | 失敗成本過量尺 → 否決落點寫入 gate 狀態、不以報告交回有裁量權的彙整者 |
| 業務 vs 編組       | 這個功能需要獨立判斷權、還是純執行分量？併進既有組會失去什麼      | 需判斷權或顯式責任歸屬 → 編組；可規則化 → 做成確定性工具、當業務掛    |
| 指揮中樞           | 要知道全局狀態、讀哪一份記錄——答案唯一才算有中樞                  | 並行單位三個以上或跨線協調 → 單一狀態記錄 + 單一統括者                |
| 對外協作面         | 對外溝通與交接有顯式承擔者嗎？沒指定時實際落在誰身上              | 有外部利害關係人或跨期交接 → 顯式承擔者、交接產出定成任務出口條件     |

主力是前三個；次要兩個在並行單位達三個以上、或存在外部利害關係人時跑。每個 lens 的完整四段（概念、判讀問題、條件-行動、失真邊界）與微案例在 `references/lenses.md`。

## 症狀觸發（單跑一個 lens 的入口）

整套評估之外，日常症狀可以觸發單一 lens（同一症狀可能指向多個 lens，表列首選入口）：

| 症狀                                       | 該跑的 lens        |
| ------------------------------------------ | ------------------ |
| 事後回答不了「這次是誰做的」               | 常設 vs 編成       |
| reviewer 標了 block、該版本仍然上了        | 執行與安全監理分線 |
| 名冊持續變長、每次任務實際用到的角色是少數 | 業務 vs 編組       |
| 要知道全局狀態得讀多個來源拼湊             | 指揮中樞           |
| 交接文件在任務中斷時最先被犧牲             | 對外協作面         |

## 證據要求與出口條件（不可沉默跳過）

- **判讀引可指認證據**：dispatch 記錄、block 事件、編成名單、hook 或 gate 的源碼行為。寫不出證據的判讀視同未評——「看起來有審查」不等於有審查、要確認否決的落點與訊號由誰寫入。
- **評估記錄有固定位置與承擔者**：進團隊的決策記錄或 repo、由發起評估的人歸檔。格式與範例見 `references/evaluation-record-template.md`。
- **「不適用」的判定寫進同一份記錄**、標明退出訊號由誰複查。
- **整套評估有兩個觸發點**：第一次建立基線、之後每次重組。
- 症狀偵測可規則化（記錄不存在、block 後仍上線都是工具可偵測的訊號），lens 判讀才是判斷工作。

評估量級：單人、手邊有編成記錄時，五個 lens 是小時級桌面演練；人類團隊要回答「否決由誰持有」通常得問到當事人，隨訪談對象數以天計。

## 何時不適用

- **單人短任務、低協調密度**：結構選擇成本趨近零、正當化檢核沒有對象
- **探索期**（任務起訖未定、stakes 未知）：先做再評；退出訊號是起訖能定義、失敗成本能估計，屆時跑第一次評估
- **從零設計團隊**：本協議評估既有設計；生成設計要回到任務本身推導，拿 lens 清單當藍圖會生出「每個 lens 配一個機制」的過度設計

跟既有框架的分工：Team Topologies 這類是設計處方、本協議是既有設計的正當化檢核，接在不同時點；incident command（ICS）與發射管制隊是同型體制，可互為佐證。
