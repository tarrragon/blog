# 在使用者的瀏覽器上診斷

> **何時讀**：錯誤只在使用者的瀏覽器重現（要登入的網站、使用者累積的資料），Playwright 載入的副本裡沒有這些；或使用者回報「資料抓到了但畫面沒更新」「多出重複」「數字對不上」。

真實網站的 DOM 與登入狀態，以及使用者累積了幾個月的 storage 資料（舊版程式寫下的格式、舊的識別碼），只在使用者的瀏覽器裡有，測試環境沒有。這類錯誤要請使用者跑指令、貼回輸出；這一份寫怎麼請、請什麼、讀到之後怎麼判。

## 先認 log 在哪一個 console

擴充功能的程式分散在幾個執行環境，各自的 `console` 只出現在各自的 DevTools：

| 執行環境 | 打開方式 | 看得到的 |
|---------|---------|---------|
| content script | 在那個網頁按 F12 → Console（頂端的 context 下拉選單可切到擴充功能的 isolated world） | 提取、DOM 掃描、捲動載入的 log |
| service worker | `chrome://extensions` → 該擴充功能的「Service Worker」連結 | 訊息路由、事件處理、寫入 storage 的 log |
| popup | 在 popup 上按右鍵 → 檢查 | popup 自己的 log；popup 一關，這個 DevTools 跟著關 |
| 擴充功能頁（`chrome-extension://<id>/…`） | 在那個分頁按 F12 | 該頁的 log |

請使用者貼 log 時寫明是哪一個分頁的 Console。使用者貼錯 console 是常見情形：貼回來的是 service worker 的啟動 log，而要找的提取結果在網頁那一側。

log 很多時請使用者在 Console 的 Filter 欄輸入一個關鍵字（結構化 log 裡標示訊息種類的欄位值、`[SAVE]` 這類前綴），只貼篩出來的幾行。service worker 重啟、網頁重新整理之後舊的 log 就清掉；篩不到時請使用者先開著網頁的 Console 與 service worker 的 Console、Filter 留空，再重做一次操作。

## 讀 storage：service worker 的 Console 直接讀得到

`chrome.storage.local` 在 service worker 與擴充功能頁的 Console 都可以直接呼叫，不必改程式。先在程式碼裡查這個擴充功能把資料存在哪一個儲存區（`rg 'storage\.(local|sync|session)|indexedDB'`），片段跟著換；`get(null)` 回傳 `{}` 時，先回頭確認儲存區，不直接判成沒有資料。寫給使用者貼的片段時：

- **只讀**：片段只呼叫 `get`，結尾印出摘要。印給人讀的部分用 `JSON.stringify(x, null, 1)` 輸出純文字，不用 `console.table`，表格複製出來會被截斷。
- **先列出全部 key，再印計數與少量樣本**：資料寫進錯的 key（例如 `[object Object]_books`）時，只 `get` 預期的 key 看不到它，所以第一段片段先用 `get(null)` 列出每個 key 與各自的筆數：

  ```js
  chrome.storage.local.get(null).then(all => console.log(JSON.stringify(Object.fromEntries(Object.entries(all).map(([k, v]) => [k, Array.isArray(v) ? v.length : Array.isArray(v?.books) ? v.books.length : typeof v])), null, 1)))
  ```

  `v?.books` 是一個例子裡存書目的欄位名，換成這個擴充功能存陣列的欄位。接著對要查的 key 印總數、符合某個條件的數量、依某個欄位分組的數量（例如依提取日期），再挑三到五筆印出完整欄位。只印樣本時看不出受影響的紀錄有多少。
- **寫明這段只讀**：使用者要判斷自己貼的東西會不會改到資料。
- **Chrome 第一次在 Console 貼上程式碼時會擋下**，提示輸入一段確認字句（英文介面是 `allow pasting`，其他語言的介面照提示上顯示的字句）；先告訴使用者照提示輸入一次再貼。

會修改或刪除 storage 的片段（清掉重複的紀錄、刪掉寫錯 key 的資料）另外處理：先用唯讀片段列出要動的紀錄，給使用者看過；寫入的片段最後印出動了幾筆、剩下幾筆；由使用者決定要不要跑。依要刪的是什麼，寫入片段多做一步：

- **重複的紀錄**：保留識別碼是修好的程式會產生的那種格式的那一筆；舊格式的紀錄把使用者加過的資料（標籤、手動設定的狀態）併到保留的那一筆，再刪掉。留下舊格式的那一筆的話，下一次提取又會新增一份。兩筆格式相同時，保留更新時間較晚的那一筆，另一筆上使用者加過的資料併過去。
- **整份寫錯 key 的資料**：先用唯讀片段比對它跟正確的 key 裡有沒有同一批紀錄（例如修正之後重新提取過）。有的話，寫錯 key 那一份裡使用者加過的資料併到正確 key 的對應紀錄，再刪掉整個錯的 key；沒有的話先搬過去，不直接刪。

## 沿著資料流逐段計數

「畫面上的數字不對」可能出在資料流的任何一段。請使用者取每一段的計數，找出第一次對不上的是哪兩段之間；缺陷在前一段的輸出或後一段的輸入，寫入那一段印出的 key 分得出是哪一邊：

1. **來源宣稱的總數**：網頁頁首寫的「擁有 N 本」、API 回應的 total。
2. **載入到 DOM 的數量**：捲動或分頁載入之後的元素數。
3. **解析成功的數量**：content script 解析出的物件數。
4. **寫入時的數量與 key**：service worker 寫入 storage 前的數量，以及寫進哪一個 key。
5. **storage 裡讀取端那個 key 的數量**：畫面從哪一個 key 讀（查程式碼），那個 key 底下現在有幾筆（唯讀片段）。
6. **畫面上的數量**：畫面實際顯示幾筆。這一段跟上一段分開取：storage 對、畫面不對時，資料的位置是對的，成因在讀取端何時重新讀取 storage（記憶體裡的舊副本、沒有監聽 `storage.onChanged`）。

每一段的計數最好本來就寫在 log 裡（提取完成時印出解析數與總數、寫入前印出數量與 key）。某一段沒有 log 時，寫唯讀片段取得（DOM 的數量在網頁 Console 頂端的 top context 跑 `document.querySelectorAll('<書目元素的選擇器>').length`），或在程式裡加一行暫時的 log；兩者都做不到的那一段標「未取得」，它之後的段不能當成第一次對不上的位置。寫入那一段同時印出 key，才看得出「數量對、位置錯」：key 是由某個欄位組出來的時候（`${platform}_books`），那個欄位的值型別不對，key 會變成 `[object Object]_books` 這類字串，資料完整寫進去了，讀取端照舊讀不到。

## 請使用者做會寫入資料的操作之前，先確認建置裡有修正

開發版是從目前 checkout 的分支建置的。修正放在另一個分支、還沒合進建置來源時，使用者照新的流程操作（重新提取、匯入），跑的是舊程式，會把錯的資料寫進 storage：重複的紀錄、寫錯位置的資料。這些資料在修正上線之後仍然留著。

請使用者做這類操作之前：

1. 確認目前建置的分支包含修正：`git branch --contains <修正的 commit>` 的輸出裡有建置所用的分支（目前的分支前面帶 `*`，在別的 worktree 裡 checkout 的分支前面帶 `+`；detached HEAD 時改用 `git merge-base --is-ancestor <修正的 commit> HEAD`，exit 0 算通過）才算通過。
2. 確認修正被打包進建置：`rg -F '<修正新增的字串>' <建置輸出目錄>`。字串取自 `git show <修正的 commit>` 裡 `+` 開頭的行，而且 `git grep -F '<字串>' <修正的 commit>^` 零命中（修正之前不存在，搜到才代表是新的程式）。搜字串字面值（log 訊息、storage key 名、錯誤訊息），不搜函式名與變數名：壓縮過的建置會改掉後者，搜不到不代表沒打包。修正沒有新增任何字面值時（只刪一行、只改條件），在修正裡加一行建置標記再搜（標記的做法在 `chrome-extension-playwright-testing` skill）。`<建置輸出目錄>` 取使用者在 `chrome://extensions` 該擴充功能的詳情裡顯示的載入路徑，不假設是自己建置的那個目錄。
3. 確認擴充功能已重新載入：建置戳記（自動重新載入時 service worker 的 Console 印出的時間）已更新。戳記只代表重新建置過，不代表建置裡有修正，所以第 2 步不能用它代替。
4. content script 的修正，另外請使用者重新整理那個網頁。
5. 前兩步任一步不通過時，不請使用者操作：切到修正所在的分支或把它合進建置的分支（合併照專案的流程，要使用者同意的先問），重新建置，再從第 1 步檢查一次。

## 修好程式之後，舊程式寫下的資料要另外處理

修好的程式只影響之後寫入的資料。舊程式已經寫下的錯誤資料（寫錯 key 的整份資料、重複的紀錄、缺欄位的舊格式）不會自己消失，有些還會讓修正看起來沒有生效：舊紀錄的識別碼跟新提取的對不上時，重新提取只會再多一份。

判斷每一種殘留資料由誰處理：

- **下一次操作會自然覆蓋或補上的**（缺欄位的舊紀錄，在重新提取時被更新）：不用另外處理，但要確認舊紀錄的識別碼跟新提取的識別碼一致，否則補不上。確認的痕跡是印出一筆舊紀錄與新提取的同一個項目的識別碼，兩者並列寫進給使用者的回覆。
- **讀取端可以在顯示時推導的**（缺的狀態欄位可以從進度推導）：在讀取端推導顯示，不寫回。
- **不在來源上的使用者資料**（重新提取時沒對上的紀錄裡，在新提取的資料找不到同名、同書號對應的那些，例如書已經從來源移走）：保留，它不是殘留；刪掉就無法復原。
- **只能清掉的**（寫錯 key 的資料、已經重複的紀錄；重複指在新提取的資料裡找得到對應的那些）：照〈讀 storage：service worker 的 Console 直接讀得到〉裡會修改或刪除 storage 的片段那一段與它底下兩項的程序，由使用者決定。
